You execute **ONE task** of an increment via the [dev-workflow](../../implementation/dev-workflow.md), test-first.

**Read first:** `CLAUDE.md` (invariants), [dev-workflow.md](../../implementation/dev-workflow.md), the milestone's settled decisions in `DECISIONS.md` + the roadmap, and the design section your task names. Earlier tasks of this increment are already committed — build on them.

**Run the full dev-workflow for your one task only:**
- **Scope** — restate the task + its observable done-criterion; read the design section.
- **Red** — write the failing test(s) **first**; confirm they fail for the **right reason** (not a compile error standing in for the assertion). Parser / serialization / state-persistence work uses **golden** tests. **When the deliverable is an agent- or user-facing emitted artifact** (a composed `Run:` line, an emitted command string, a rendered view), the test must drive the **emitted artifact itself** — extract the composed line and run it verbatim — **never** a reconstructed/hand-built equivalent. A test that rebuilds the command in test code can pass while the emitted bytes an agent would actually run are broken (a *masking test*); the emitted bytes are the contract, so assert on and execute the emitted bytes. **When the deliverable is context-scoped** (a slot-fill on a step, an override on a workflow, a knob a command path reads), the happy-path test is **not enough**: also test the feature composed into a context that **omits** the target and assert the correct behaviour there (usually *inert*, never *error*) — a green pass over a single composing context hides a scope bug in every omitting context (the M4 front-door brick; Validation hardening #5). **When the deliverable is reproducible/order-invariant** (a merge, a join, any "by task id, not completion order" output; Validation hardening #7), one green run is **not** a valid red→green — the red test must feed the same input under **≥2 divergent orders** (minimum id-order **and reverse**) and assert **byte-identical** output, and the implementation must keep merge/aggregation paths on `BTreeMap`/sorted-`Vec` keyed by the stable id, never letting a `HashMap`'s iteration *order* reach output unsorted (a hash container sorted at the boundary before emission is fine). Force genuine overlap in the fixture (same slug minted, a cross-area ref, a self-referential colliding doc) — a non-overlapping fixture proves nothing.
- **Green** — the **minimal** implementation.
- **Refactor** — only what this task touches.
- **Gate** — run **`dev/gate`** as the **last step before commit, FULL and UNSCOPED**. It runs the gate's five commands **bare**, in order — probe prebuild · `cargo fmt --check` · `cargo clippy --all-targets -- -D warnings` · `cargo build` · `cargo test` — capturing each exit code directly, and on a red it names the failing **step** and the failing **test names**. **Never `--quick`**: it skips the tests entirely, so it is a pre-check and never a gate. Add `--private-target` when another agent may hold the shared `target/` lock. `dev/gate` **accepts no scope arguments**, which is the point: its `cargo test` is the WHOLE suite — a scoped run silently skips other targets (the `--bin jigc` pack/describe goldens live there, and a new workflow/step/command/doctype **must** bump their inventory assertions or they fail there). Read **`dev/gate`'s own summary**: the `tests   passed=N failed=M  (over B test binaries)` totals line — printed only on a full run — and the `GATE: PASS` / `GATE: FAIL (step:…)` verdict. Do **not** read raw `cargo test` output instead: `test result:` proves nothing about scope (a `-p`-scoped run prints a genuine summary too, and undelimited the string also matches test *names* such as `test result::tests::alpha ... ok`). Do **not** commit on a scoped green; a red gate is a blocker to fix, never to commit past (M23: inc-1 committed a red gate from a scoped run).
  - **What the probe prebuild is** — `dev/gate` runs it first, so you never run it yourself: `cargo build --manifest-path crates/cli/probes/doc-code/Cargo.toml --target-dir crates/cli/probes/doc-code/target`. ~30 suites shell out to cargo for that detached workspace and all share one `target/`; co-resident in a group binary, one can replace `target/debug/doc-code` while another executes it. Prebuilt, every in-test build is an up-to-date no-op. The `--target-dir` is **not** optional: hand-run with `CARGO_TARGET_DIR` set (which `--private-target` and `JIGC_GATE_TARGET` both set) it builds into the private dir while the suites still build into `crates/cli/probes/doc-code/target`, so the prebuild silently stops preventing the race it exists to prevent, at exit 0.
  - **Run it in the FOREGROUND, and do not return until it has reported.** The gate is now **~5 minutes** (measured 4m34s–5m18s after the M47 test-target consolidation), comfortably inside the 10-minute Bash ceiling, so a plain foreground `dev/gate` run is the right call. **Background it only when you expect a full recompile** (you changed `Cargo.toml`, a workspace profile, or a widely-included module) — and if you do, you must still wait for its result and commit **in the same turn**. **Returning after backgrounding the gate abandons your work**: you are a subagent, so returning ends you, and your commit never happens — this cost two complete-but-uncommitted fixes on 2026-08-09, both recovered by hand. The old `run_in_background` rule below was written for a **2.5-hour** gate that no longer exists, and for the main loop, which *does* get re-invoked. Scoped `cargo test -p cli <suite>::` runs during red→green are short enough for the foreground too — but a scoped green is never a gate (see above).
  - **Historical note — why the old rule existed (it no longer applies).** The full gate was measured at **~7 min of `cargo test`, ~20 min cold with clippy** — under the old 252-target layout it was **~2.5 h**, and the "30–50 minutes"/"52 minutes" previously recorded here were wrong (see [DECISIONS.md](../../DECISIONS.md) → 2026-08-05: the 52-minute figure summed ~6.4 runs of each suite; one clean run's test execution is 7.9 min, and the real cost was a macOS Gatekeeper scan per freshly-linked binary). At those lengths the gate overran the **10-minute Bash tool ceiling** (`timeout` max 600000 ms) on a cold run, so the rule told agents to run it with `run_in_background: true` and to let the harness re-invoke them when it exited — true of the main loop, false of a subagent. It also forbade backgrounding it and then waiting in the foreground, because at that length `until grep -q "EXIT=" log; do sleep 10; done`, `while kill -0 <pid>; do sleep 20; done`, or a plain foreground `cargo test` all hit the ceiling, timed out, and cost a full model round-trip per retry on a large context (M47 burned **17.3 hours across 104 such timeouts**). On today's ~5-minute gate that hazard is gone, which is why the paragraph above governs and this one is only the record of the measurement it corrected.
  - **A new test file must be registered.** `autotests = false`: the ~250 suite files are compiled into twelve group targets via `crates/cli/tests/groups/*.rs`. Add your new suite to exactly one group root as `#[path = "../<name>.rs"] mod <name>;` or it compiles nowhere and **silently never runs** — `tests/test_target_registration.rs` fences this and will redden. If your suite calls `env::set_var`/`env::remove_var`, it needs its **own** `[[test]]` target (`g_solo_*`); the same guard enforces that.
- **Commit** — ONE conventional commit to the **current branch, in place**, scoped like the existing history (`feat(engine):` / `fix(cli):` / …), **no** co-author trailer. Do **NOT** create or switch branches (`git checkout -b` / `git switch -c`) — even though you are on the default branch, commit directly to it. The harness builds the whole milestone as one **linear** chain and lands it on `main` at the end; a side branch silently strands every subsequent increment off `main` (M30 hit exactly this — one planner branched and the rest of the milestone landed off `main`). **Stage only the paths your change touched** (`git add <path>…`), **never `git add -A` / `git add .`** — an unrelated uncommitted change already in the working tree (another agent's or the orchestrator's in-flight edit) must not ride your commit; this is M30's index-as-change-manifest discipline applied to the builder itself. If the full gate needs a file you didn't stage, that's the signal you missed one of *your* paths, never a licence to sweep the tree.

Record any genuine design choice / elaboration pin in `DECISIONS.md` as it lands. Stay **minimal and in scope** (every changed line traces to the task; no inert/dead code; don't refactor working code). You **are** authorized to commit to `main`.

**Halt** (do not guess) on a **genuine new design fork** not covered by the milestone's settled decisions and not resolvable from the locked docs — report `status: halted` instead of guessing past it, per *Reporting* below. **A discovered violation of a retired invariant (byte-stability `render(parse(x))==x`, the determinism boundary, the engine-empty rule) on a *production* path is *also* a halt** — surface it as a fork for the human, even when finalize/the gate happens to tolerate it. You must **not** route around it by **logging a deferral and narrowing your test to dodge it** (scoping a round-trip assertion to a subtree that avoids the broken case is a *masking test* — the exact pattern the milestone audit exists to catch; M13's inc-5 leading-slot defect was masked this way). Found-on-a-production-path invariant breakage is escalated, never self-deferred-and-hidden.

## Reporting — what to place where

Your transcript is **not** read back, so nothing load-bearing may live only there:

- **Code** → one git commit (this task). **Decisions / elaboration pins** → `DECISIONS.md` (committed). **`notes`** → 1–2 lines (what shipped + any pin id) — no essay.
- **On halt, leave a CLEAN tree:** revert your uncommitted changes (`git restore` / `git checkout --`) so the run resumes from a known base — do **not** leave orphaned edits for the human to discover (your attempt stays recoverable from your transcript/diff). Then fill the structured `halt` report fully: `root_cause`, `evidence` (the failing tests/commands), `tree_state` (which commits landed + confirm the tree is clean), `recommendation`.

**Use the repo's dev tools — they exist because these two shapes cost delegated runs measurably.**

- **`dev/gate`** is the gate — see **Gate** above for how to run and read it. **Never pipe a command whose exit status you read**, here or anywhere: a scan of 139 subagent transcripts found that shape blocked **215 times across 117 of 137 agents**.
- **`dev/jigc-rig <state>`** builds a throwaway jigc corpus and prints shell assignments — use `out=$(dev/jigc-rig <state>) || exit; eval "$out"`, never a bare `eval "$(...)"`, which swallows the failure. Its root is minted with `mktemp -d`, so **there is nothing to tear down**. `dev/jigc-rig --list-states` shows the states; `--print-only` emits a paste-runnable repro for a finding.

**Never `rm -rf` a path built from variables.** It is refused *before it runs* by a static scan that cannot prove the variables are non-empty — so no allowlist suppresses it, every retry re-prompts, and in a delegated run you **park on a prompt nobody is watching**. The rig removes the need; `mktemp -d` covers the rest. See [CLAUDE.md](../../CLAUDE.md) → Build / lint / test.
