You execute **ONE task** of an increment via the [dev-workflow](../../implementation/dev-workflow.md), test-first.

**Read first:** `CLAUDE.md` (invariants), [dev-workflow.md](../../implementation/dev-workflow.md), the milestone's settled decisions in `DECISIONS.md` + the roadmap, and the design section your task names. Earlier tasks of this increment are already committed — build on them.

**Run the full dev-workflow for your one task only:**
- **Scope** — restate the task + its observable done-criterion; read the design section.
- **Red** — write the failing test(s) **first**; confirm they fail for the **right reason** (not a compile error standing in for the assertion). Parser / serialization / state-persistence work uses **golden** tests. **When the deliverable is an agent- or user-facing emitted artifact** (a composed `Run:` line, an emitted command string, a rendered view), the test must drive the **emitted artifact itself** — extract the composed line and run it verbatim — **never** a reconstructed/hand-built equivalent. A test that rebuilds the command in test code can pass while the emitted bytes an agent would actually run are broken (a *masking test*); the emitted bytes are the contract, so assert on and execute the emitted bytes. **When the deliverable is context-scoped** (a slot-fill on a step, an override on a workflow, a knob a command path reads), the happy-path test is **not enough**: also test the feature composed into a context that **omits** the target and assert the correct behaviour there (usually *inert*, never *error*) — a green pass over a single composing context hides a scope bug in every omitting context (the M4 front-door brick; Validation hardening #5). **When the deliverable is reproducible/order-invariant** (a merge, a join, any "by task id, not completion order" output; Validation hardening #7), one green run is **not** a valid red→green — the red test must feed the same input under **≥2 divergent orders** (minimum id-order **and reverse**) and assert **byte-identical** output, and the implementation must keep merge/aggregation paths on `BTreeMap`/sorted-`Vec` keyed by the stable id, never letting a `HashMap`'s iteration *order* reach output unsorted (a hash container sorted at the boundary before emission is fine). Force genuine overlap in the fixture (same slug minted, a cross-area ref, a self-referential colliding doc) — a non-overlapping fixture proves nothing.
- **Green** — the **minimal** implementation.
- **Refactor** — only what this task touches.
- **Gate** — run **`dev/gate`** as the **last step before commit, FULL and UNSCOPED**. It runs the gate's four commands **bare**, in order — `cargo fmt --check` · `cargo clippy --all-targets -- -D warnings` · `cargo build` · `cargo test` — capturing each exit code directly, and on a red it names the failing **step** and the failing **test names**. **Never `--quick`**: it skips the tests entirely, so it is a pre-check and never a gate. Add `--private-target` when another agent may hold the shared `target/` lock. `dev/gate` **accepts no scope arguments**, which is the point: its `cargo test` is the WHOLE suite — a scoped run silently skips other targets (the `--bin jigc` pack/describe goldens live there, and a new workflow/step/command/doctype **must** bump their inventory assertions or they fail there). Read **`dev/gate`'s own summary**: the `tests   passed=N failed=M  (over B test binaries)` totals line — printed only on a full run — and the `GATE: PASS` / `GATE: FAIL (step:…)` verdict. Do **not** read raw `cargo test` output instead: `test result:` proves nothing about scope (a `-p`-scoped run prints a genuine summary too, and undelimited the string also matches test *names* such as `test result::tests::alpha ... ok`). Do **not** commit on a scoped green; a red gate is a blocker to fix, never to commit past (M23: inc-1 committed a red gate from a scoped run).
  - **Run it in the BACKGROUND, wait for it in this same turn, and do not return until it has reported.** The full gate measures **about ten minutes** (598 s and 601 s on 2026-10-05 — [DECISIONS.md](../../DECISIONS.md) → *The gate's fast tier is cut by measured seconds*), which is the **10-minute Bash tool ceiling** itself (`timeout` max 600000 ms): a foreground run can be killed at the ceiling with nothing reported. So launch `dev/gate` in the background with its output redirected to a log file, then wait in **slices of under five minutes** — each slice one call that returns when the log holds the gate's verdict line (`GATE: PASS` / `GATE: FAIL …`) or the slice is over. Never one wait as long as the gate, which meets the same ceiling; and a wait of five minutes or more costs a full rewrite of your prompt cache where a shorter one costs a read ([run-performance.md](../../completions/artifacts/M55/fix-pass-rc25/perf/run-performance.md) §4, lever 4). Then read the gate's own last lines from the log — never an exit status through a pipe. **Returning while the gate still runs abandons your work**: you are a subagent, so returning ends you, and your commit never happens — this cost two complete-but-uncommitted fixes on 2026-08-09, both recovered by hand. **`dev/gate --fast`** (about a minute and a half) is the pre-check to run first, for the registry row or the fence your change owes; it prints `PRE-CHECK: …` and neither of the full gate's two lines, and it is **never a gate**. Scoped `cargo test -p jigc <suite>::` runs during red→green are short enough for the foreground — but a scoped green is never a gate either (see above).
  - **Historical note — the three durations this rule has stood on.** Under the old 252-target layout the gate ran **~2.5 h** (the "30–50 minutes"/"52 minutes" once recorded here were wrong — [DECISIONS.md](../../DECISIONS.md) → 2026-08-05), and the rule said to background it and let the harness re-invoke you: true of the main loop, false of a subagent, and an agent that waited on it with one long foreground call instead hit the ceiling, timed out, and paid a full model round-trip per retry (M47 burned **17.3 hours across 104 such timeouts**). After the M47 test-target consolidation it measured 4m34s–5m18s, and until 2026-10-05 this paragraph said *foreground*. The suite has since grown it back to the ceiling, so the paragraph above governs. What every version has in common: you wait for your own gate in the turn that launched it, and never in one call longer than the ceiling allows.
  - **A new test file must be registered.** `autotests = false`: the ~250 suite files are compiled into twelve group targets via `crates/cli/tests/groups/*.rs`. Add your new suite to exactly one group root as `#[path = "../<name>.rs"] mod <name>;` or it compiles nowhere and **silently never runs** — `tests/test_target_registration.rs` fences this and will redden. If your suite calls `env::set_var`/`env::remove_var`, it needs its **own** `[[test]]` target (`g_solo_*`); the same guard enforces that.
- **Commit** — ONE conventional commit on the **increment branch your prompt's `BRANCH:` line names** (`milestone/<slug>/<increment-slug>`), scoped like the existing history (`feat(engine):` / `fix(cli):` / …), **no** co-author trailer. The harness has already checked it out; **before committing, `git branch --show-current` must print exactly that name** — if it does not, commit nothing and halt (a resume can replay the step that checked it out, so the name in your prompt is the check, not the tree you found). Do **NOT** create, switch, merge or push branches (`git checkout -b` / `git switch` / `git merge` / `git push`): the harness's `build-git` steps own every branch act, and a side branch strands the work off the milestone (M30 hit exactly this — one planner branched and the rest of the milestone landed elsewhere). **Stage only the paths your change touched** (`git add <path>…`), **never `git add -A` / `git add .`** — an unrelated uncommitted change already in the working tree (another agent's or the orchestrator's in-flight edit) must not ride your commit; this is M30's index-as-change-manifest discipline applied to the builder itself. If the full gate needs a file you didn't stage, that's the signal you missed one of *your* paths, never a licence to sweep the tree.

Record any genuine design choice / elaboration pin in `DECISIONS.md` as it lands. Stay **minimal and in scope** (every changed line traces to the task; no inert/dead code; don't refactor working code). You **are** authorized to commit to your increment branch — and to no other.

**In a stabilization run your one task may be a stage's record step.** *A contract change of 2026-10-05* ([DECISIONS.md](../../DECISIONS.md) → *The stabilization workflow, as ruled*, rulings 12, 13 and 16). **It binds only when your prompt opens with `RECORD STEP` and names a run** — a milestone build's prompt never does, and under it nothing in this paragraph applies. The task is then a record, not code: there is no red test and no source edit, and its done-criterion is the commit. You run the `dev/stabilize-record` calls your prompt lists, in its order, with exactly the rows it gives — the report check first. **Where the prompt gives rows, or a list of calls, as text to write to a file under the scratch root, with the sha256 that file must then have,** you write exactly that text, check the hash, and hand the script the file — a row is never retyped from memory, and a hash that still differs after a second write is a halt. **A failed check (`check-reports`, `check-ledger`) or any refusal is a halt**, the script's one line being the evidence: you never write a file under the run's directory by hand, never supply or correct a row the prompt did not give, never pass another attempt number, and never repair a missing or an extra report. Then the full gate, run and read as above — no commit is exempt from it by its path — and **ONE commit of the run directory's paths and nothing else**, typed as this repository's history types a record, on the branch the `BRANCH:` line names (the loop branch in the `test` stage, the round branch in `fix`). You return `status`, the `commit` sha, the gate's totals line and its `GATE: PASS`, and each check's JSON line as printed. The push is a git step's, never yours.

**Halt** (do not guess) on a **genuine new design fork** not covered by the milestone's settled decisions and not resolvable from the locked docs — report `status: halted` instead of guessing past it, per *Reporting* below. **A discovered violation of a retired invariant (byte-stability `render(parse(x))==x`, the determinism boundary, the engine-empty rule) on a *production* path is *also* a halt** — surface it as a fork for the human, even when finalize/the gate happens to tolerate it. You must **not** route around it by **logging a deferral and narrowing your test to dodge it** (scoping a round-trip assertion to a subtree that avoids the broken case is a *masking test* — the exact pattern the milestone audit exists to catch; M13's inc-5 leading-slot defect was masked this way). Found-on-a-production-path invariant breakage is escalated, never self-deferred-and-hidden.

## Reporting — what to place where

Your transcript is **not** read back, so nothing load-bearing may live only there:

- **Code** → one git commit (this task). **Decisions / elaboration pins** → `DECISIONS.md` (committed). **`notes`** → 1–2 lines (what shipped + any pin id) — no essay.
- **On halt, leave a CLEAN tree:** revert your uncommitted changes (`git restore` / `git checkout --`) so the run resumes from a known base — do **not** leave orphaned edits for the human to discover (your attempt stays recoverable from your transcript/diff). Then fill the structured `halt` report fully: `root_cause`, `evidence` (the failing tests/commands), `tree_state` (which commits landed + confirm the tree is clean), `recommendation`.

**Use the repo's dev tools — they exist because these two shapes cost delegated runs measurably.**

- **`dev/gate`** is the gate — see **Gate** above for how to run and read it. **Never pipe a command whose exit status you read**, here or anywhere: a scan of 139 subagent transcripts found that shape blocked **215 times across 117 of 137 agents**.
- **`dev/jigc-rig <state>`** builds a throwaway jigc corpus and prints shell assignments — use `out=$(dev/jigc-rig <state>) || exit; eval "$out"`, never a bare `eval "$(...)"`, which swallows the failure. Its root is minted with `mktemp -d`, so **there is nothing to tear down**. `dev/jigc-rig --list-states` shows the states; `--print-only` emits a paste-runnable repro for a finding.

**Never `rm -rf` a path built from variables.** It is refused *before it runs* by a static scan that cannot prove the variables are non-empty — so no allowlist suppresses it, every retry re-prompts, and in a delegated run you **park on a prompt nobody is watching**. The rig removes the need; `mktemp -d` covers the rest. See [CLAUDE.md](../../CLAUDE.md) → Build / lint / test.

**Never push to or merge into `main`, force-push any branch, merge a pull request, push a tag, approve or reject a deployment, or yank a crate.** Those acts are the human's ([release.md](../../implementation/release.md) → *What agents may not do*). You may merge an increment branch into its milestone branch locally, and push `milestone/*`, `fix/*` and `work/*` branches — always by name (`git push origin <branch>`), never a bare `git push`, and never forced (no `--force`, `--force-with-lease`, `-f` or `+` refspec). `.claude/settings.json` denies the commands that perform the human's acts; a denial is the answer, never something to route around.
