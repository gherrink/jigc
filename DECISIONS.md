### Document-type definition schema

- **Doc unit model — shallow ID'd tree** (`section → block → leaf`) — flat denies items the IDs validation needs; recursion is a CMS smell against small-footprint docs.
- **Trichotomy `section/slot/field`, split by adjudicability** — a field is a value the CLI can adjudicate, a slot only a human/LLM can judge; the determinism boundary drawn through one doc, and cross-refs prove fields must be a distinct kind.
- **One bounded `repeatable` construct** — a section body may be a list of ID'd blocks (per-item structure from v1, so each SPEC criterion is individually validatable); no recursion, no repeatable-in-repeatable.
- **Addressing = URI grammar `type:name#section/item/leaf`** — separates *which doc* (resource) from *where inside* (fragment); a whole-doc ref stays a clean, type-checkable atom.
- **IDs author-named vs minted** — types/sections/leaves are named in the schema; instances and repeatable items are minted, so runtime minting happens at exactly two sites (doc creation, item add).
- **Minted IDs = frozen content-slugs** — slugged from a required id-source field, frozen at creation, deterministic suffix on collision; ordinal-looking IDs rejected as a position-smell; chosen for diff-legibility.
- **Cross-ref = field + relation (two facets)** — field is the placed endpoint (home + address), relation is the type-level constraint (target type, cardinality, inverse); the ORM pattern, giving placement *and* graph integrity.
- **Cross-refs bidirectional, inverse derived not stored** — forward ref authored once, reverse edge computed into read-views; single source of truth, diff-clean, concurrency-safe; implies a rebuildable edge index. *(The "inverse-cardinality enforced at `finalize`" clause is **superseded 2026-05-25**: completeness obligations are advisory at task scope, hard-enforced only at store/milestone scope — see that date's "Review remediation" entry and [validation.md](design/validation.md) → Integrity vs completeness.)*
- **Field types split engine-native vs pack-provided** — enum/string/date/bool/int/ref are engine-native; domain types like `code-anchor` are pack-provided with a pack-supplied adjudicator, keeping the engine empty.
- **One structural grammar, two dialects** — shared skeleton (units, ordering, blocks, repeatable, addressing, minting, include, override, validation engine); doc and workflow differ only in leaf kinds + annotations and never share a leaf kind (slot/placeholder stay opposites); two built-in dialects, not a public plugin framework.

### Write-command vocabulary

- **Write-layer ≠ override-layer** — write fills *instances* (slot/field values, repeatable items); override customizes *types* (sections/structure); they share addressing + unit kinds, not verbs.
- **Primitives are the core; the form is deferred sugar** — 6 per-leaf write verbs, MVP-sufficient and placement-safe; the fillable form compiles to a transactional batch, deferred until multi-slot flows — placement-safety comes from address-keying, not verb granularity.
- **Verb set + surface** — writes `create / set-slot / set-field / add-item / remove-item / reorder` as `jigc doc <verb> <addr>`; lifecycle `diff / validate / finalize / discard` as `jigc task <verb> <id>`.
- **The task is the staging unit** — the per-task isolated working area (already locked for concurrency) *is* the staging area; no separate proposal object, so "propose/review/apply" = "write/validate/finalize."
- **Write-time vs finalize-time checks** — local adjudication (field type, enum, slug) at write-time; referential/cross-doc integrity at `finalize`; the split is what stops the bootstrap deadlocking.
- **`finalize` defaults to autonomous** — the confirm-gate is an opt-in cascade setting; git/PR review is the durable correction point.
- **Content handoff splits by leaf kind** — fields inline (`--value`), slots via stdin (`--from-file -`, file-path convenience), never inline prose; `add-item` takes the id-source inline → returns the item address → prose via follow-up `set-slot` (all-at-once would resurrect the deferred form).
- **Instance provisioning: CLI creates, two triggers** — CLI always mints+places; triggered either workflow-provisioned (deterministic, id-source set by the workflow) or agent-initiated (`create`, judgment); deciding-to-create is reasoning, creating/placing is structure.
- **Agent-initiated `create` is workflow-gated** — the catalog of creatable types in a context is structure (workflow/cascade-owned); choosing among them is reasoning; the gate is a cascade setting.
- **`finalize` ≡ `validate` + commit** — one validation engine, two entry points, so report and gate can't diverge; findings are severity-tagged and finalize blocks only on the *blocking* class (severity per check is a cascade setting); `--dry-run` dropped — `validate` is the preview, `diff` shows the changeset.
- **Out-of-band reconciliation: binary, human-decided, blocks at `finalize`** — detect via `file ↔ CLI-state` hash; the agent blocks-and-routes on drift; import vs discard is the human's call; import needs round-trippable serialization (MVP detects + discards now, import lands with the format); three-way merge deferred.

### On-disk storage

- **Single-file canonical Markdown** — the `.md` *is* the source of truth, not a view over a model file; our locked principles (plain files are source, humans edit through git, OOB detected/reconciled) already imply it — a hidden model file would make the edited `.md` second-class.
- **Schema-driven parse** — the file is read against its type's schema, so sections/slots/fields are schema-located and need no markers; only instance-minted identity gets marked.
- **`{#id}` heading anchors are the only in-body markers** — they mark repeatable items (the one instance-minted body identity); the on-disk token *is* the address fragment, and the frozen slug survives a title rename.
- **One field syntax, two locations** — fields are always `key: value`; the doc's header block → front-matter, a section/item block → a trailing `key: value` group; slots are the prose.
- **id-source = the heading** — a doc's title is its H1 (frozen id = filename), an item's title is its `###` heading (frozen id = `{#id}`); same pattern at both levels.
- **One prose slot per section preferred** — multi-slot renders under schema-fixed sub-labels (matched like headings, no new marker); nudges schemas toward one-purpose sections.
- **One `.md` per instance; path = identity** — filed at the type's location, filename = frozen id; items live inside the parent file; physical order = order (reorder = move a block, no renumber).
- **Committed Markdown is the only source of truth** — everything else is a rebuildable cache or transient working area; delete it all, rebuild from the `.md`, lose nothing — the system degrades to plain Markdown.
- **All CLI state under gitignored `.jigc/`** — edge index + file↔state hashes are derived caches, gitignored not committed (committing churns diffs and reintroduces dual-source-of-truth); they invalidate/rebuild when the checkout moves (stamped with HEAD/fingerprint).
- **Staging = gitignored scratch dir of working copies** — `.jigc/tasks/<task-id>/` in the same Markdown format; realizes the concurrency primitive directly (isolated subdirs + CLI by-task-id join), not git worktrees (git's text-merge ≠ our deterministic join); a task is pinned to its base, base-mismatch is detected-and-routed (rebase deferred).
- **CLI orchestrates, git executes VCS** — the CLI never reimplements branch/worktree/merge; a workflow may trigger git deterministically; a fresh worktree rebuilds caches and seeds only local config, copies nothing else.
- **git merges code; the CLI merges managed docs — never the reverse** — blind text-merging a `.md` would corrupt `{#id}` anchors/structure and reintroduce non-determinism; overlapping doc-writes go through the CLI join, disjoint coarse work may use worktrees + git merge.

### Workflow dialect

- **Dialect shape: shared definition-grammar, divergent runtime** — a workflow is the skeleton's steps / addressing / `include` / override with read-path-only leaves (`placeholder`, `instruction`) and a `fan-out`/`join` step marker; no write path, no slots/fields, no persisted instance, no minting. The one-grammar bet holds on *how a workflow is built/addressed/composed/overridden*; doc = fill & persist, workflow = resolve & emit.
- **Composed output is ephemeral** — a derived view, re-composed each call from `definition + cascade + live state`, never persisted or source-of-truth; `--explain` re-computes the resolution tree on demand.
- **Composition is substitution, not control flow** — structure is fixed by `definition + cascade` (task-independent); only resolved values vary by task; adaptation lives at the cascade (project) or in agent reasoning (situation), never in composer branching.
- **Three placeholder kinds** — command-ref (cascade → literal CLI invocation, overridable, validated), data-value (live-state value / doc-slice, embedded), include (step/block by id, recursively expanded, cycle-checked); includes expand first then values resolve; an empty resolution yields empty text, never conditional prose.
- **Data-values: full graph navigation, no logic** — multi-hop relation traversal + fragment slicing, no filtering/selection; broken paths caught at validate-time (`workflow ↔ references`).
- **`fan-out` realization** — a step marker declaring a list-source (a data-value resolving to a collection) + a referenced sub-workflow; the CLI resolves the list and emits dispatch instructions, the assistant adapter launches (CLI owns the payload, assistant owns the launch — the CLI never spawns); sub-agents re-enter the composer (referenced, not inline); sub-task id = the fanned item's id; ack is `status + task_id`, state is re-derived from the CLI, never trusted from the message.
- **`join` is a barrier, merged by task-id order** — all sub-tasks complete, the CLI merges working areas by task-id (never completion order), the main workflow re-composes its post-join steps against the merged state; synchronization is via CLI state, not messages.
- **Fan out over the whole collection; nested `fan-out` banned** — no subset filtering (selection is logic; each sub-agent's workflow + reasoning handles "nothing to do"); parallelism is capped at one bounded level, mirroring no-repeatable-in-repeatable — tree-parallelism deferred.

### Validation engine

- **Validation is mechanical, never semantic** — the engine checks the CLI-owned half (references, structure, state) and never judges prose; deterministic predicates, no LLM in the engine. The integration advantage is guaranteed referential integrity, not content quality; detect & route, never auto-fix; read-only — same effective state → same findings.
- **Fat engine, thin probes** — the engine owns scope→target resolution, the read-only effective-state graph/edge-index, scheduling, severity assignment, aggregation/report, and the `finalize` gate; a probe just declares an id + target-type + default-severity and implements a read-only `check(target, ctx) → [finding]`.
- **Engine-owns severity, via the cascade** — the probe suggests a default; the engine assigns the final severity from `project > team > pack-default`; the only option that honors the locked "severity is a cascade setting" — self-classify (severity baked into probe code) is rejected.
- **Finding = `{target, probe, severity, message, route?}`** — `route` is an optional tagged union (`fill-leaf` / `run-command` / `reconcile` / `none`) the engine **never executes**; message always present. Findings are navigable state, so a `fix-drift` workflow can `fan-out` over them and route each repair — closing the loop while staying detect-&-route.
- **Scope = effective state** — `task` validates `committed + working deltas + referential blast radius` (deltas overlaid on the committed edge index; what `finalize` gates on), plus `doc` and `store` scopes; blast-radius is required so a task can't commit breakage elsewhere.
- **Uniform probe interface, two implementations** — engine-native probes are built in (in-process); pack probes are deferred invoked processes (JSON-in/out, read-only and deterministic by contract — `doc-code` parses real code, so not declarative), behind the "not a public API yet" line.
- **MVP probes** — `workflow-refs` (every placeholder/include/command-ref resolves) and `file-state` (on-disk hash matches recorded state), both engine-native; `override-default` is engine-native at contract level (full logic awaits the override ladder); `doc-code` is the deferred pack probe.
- **The engine runs at validate/finalize** — the per-write field-type/enum/slug checks are the schema's *local adjudication*, a separate fast path, not the validation engine.

### Override system

- **Cascade: `project > team > pack-default`, by specificity** — `team` is a cross-project generality layer (not per-developer); most-specific-wins, so the project — the layer that differs most — overrides. Per-developer config doesn't fit a governance domain (doc types, workflows, conventions, severities).
- **Cascade disk locations** — pack-default ships with the pack; project = a committed config dir (source of truth, diff-reviewed); team = external `~/.config/jigc/`; the in-repo `.jigc/` stays purely derived/transient (no config in it).
- **Determinism = pure function of the resolved cascade** — composition is reproducible given the resolved cascade (a declared input), not project-state alone; anything that must be reproducible from the repo alone belongs at project level.
- **Per-developer `local` layer deferred** — if ever added it sits on top (`local > project`), restricted to non-structural / tighten-only; the cascade is layer-count-agnostic, so adding it later is free.
- **One delta model; the ladder's rungs are delta kinds** — `scalar-set` / `structural-op` / `slot-fill` / `tracked-fork`; the cascade is the ordered application of recorded deltas over a versioned base, so "ladder" and "cascade" are one system.
- **Delta manifest = config-format per layer; content as native files** — `scalar-set` is inline (`key = value`); content-bearing deltas reference native-format files (a step file), never inline-in-config — no prose-in-config.
- **Base-hash on all content-bearing deltas** — each records base-version + the target's base-hash, making upgrade reconciliation a stateless existence + hash compare (no old pack kept around).
- **`override-default` reconciliation** — engine-native probe on a guarded `jigc upgrade`: per delta, target gone → `orphaned`; target content changed *and the delta depends on it* → `conflict`; else `clean`. Emits validation findings + routes (orphaned → remove/re-target; conflict → 3-way merge — agent proposes, human confirms).
- **Knobs = config-level fields, closed surface** — a scalar knob is a pack-declared typed field (enum/string/bool/int + default), type-checked like `set-field` and reconciled like any delta; only declared keys are settable (undeclared → error); structural change beyond the knob surface uses structural-ops by address.
- **Step/workflow definition format** — one file per step (md + YAML front-matter config + body = the prompt, with placeholders); a workflow is one file (front-matter + body = ordered `{{include}}`s); id = filename (frozen slug); step-ids resolve through the cascade (same-id higher-layer wins = override for free). Doc-type schema definition format kept separate (open).
- **Mermaid flow is a generated view** — derived from the composition (the includes), output on demand (`--explain` / `--diagram` / composed output), descriptive never prescriptive; never a hand-authored second source (would drift and back-door the banned DAGs/conditionals).

### Bootstrap sentence

- **One routing pointer, not content** — the bootstrap replaces the static rules file with a single permanent-context line that *routes*, never embeds rules/conventions; the moment it carries content it's the bloated rules file again. It names categories (workflow, project state, doc context), never their contents.
- **Single state-aware front door** — the agent runs one zero-knowledge entry; the CLI composes orientation / the right workflow / setup as appropriate, and the agent learns every other command just-in-time via command-refs. The agent's entire a-priori knowledge is "run the front door and follow it."
- **Must signal the benefit, not just instruct** — the sentence establishes `jigc` as the *authoritative, current, assembled, validated* source (vs raw/scattered/possibly-stale files), so the agent perceives it as the path of least resistance; the front-door's self-describing output reinforces it (advertise + demonstrate). "Get your instructions" alone is too thin a hook to beat the grep instinct.
- **Three jobs, nothing more** — (1) `jigc` is the interface + single current source for what you need; (2) files are storage — never read/edit managed docs directly (code untouched); (3) one front door + all writes through the CLI.
- **Form: a 3-sentence micro-block** — final wording is current truth in [design/bootstrap.md](design/bootstrap.md); command tokens (`jigc` / `jigc start`) are product-name placeholders, placement is the per-assistant adapter (separate topic), and the sentence is assistant-neutral.

### Doc-type schema definition format

- **Doc-type definitions are config, not documents** — a schema is declaration-heavy with only light prose (hints), so it joins the *config* family (with the delta manifests), not the md + front-matter *document* family. Content lives in its natural format; this was never "everything is md + front-matter."
- **Structured config, YAML, document-order, self-documenting** — sections listed top-to-bottom as they appear in the doc, leaves under them, one-line hints inline, so the source reads like the doc's shape for humans and LLMs alike; YAML (over TOML/JSON) for readable nesting.
- **One file per type (definition); instances stay one-file-each** — the whole schema for a type is one bounded file (`adr.yaml`) that doesn't grow with usage; the actual ADRs are separate `.md` instances ([storage.md](design/storage.md)). Rule: *externalize a unit for reuse* (workflow steps), *inline it for self-containment* (doc-type sections); `include` is the escape hatch for a genuinely-shared section.
- **Generated `--template` view** — the engine renders a blank instance from the schema on demand (derived, like the mermaid flow), so "what does this produce" is legible without the source being a template.
- **Validation hooks fall out** — no separate probe declaration: a `code-anchor` field means `doc-code` applies, a relation's cardinality is checked, severities are cascade knobs. The schema's typed leaves + relations + the cascade drive validation.
- **One config language (YAML) across the config family** — the delta manifests are re-expressed in YAML to match schemas (notation only; decisions unchanged).

### Assistant adapter

- **Neutral core, per-assistant profile** — the core CLI knows nothing about any assistant; a small adapter *profile* (config-family YAML) holds all assistant-specific knowledge (inject / allowlist / spawn). Swap the profile → new assistant, zero core changes. Two orthogonal axes: domain = pack, assistant = profile.
- **Generated + minimal, not hand-maintained** — `jigc setup` / `adapter install` generates the adapter from the profile and regenerates it on upgrade, so it can't rot into a new bloated rules-pile; no per-command wrappers (the agent shell-calls `jigc`, learning commands JIT).
- **Three responsibilities** — (1) inject the bootstrap; (2) make `jigc` frictionless (allowlist/permissions — the path-of-least-resistance the bootstrap relies on); (3) bind the spawn mechanism.
- **Inject via best mechanism: hook (primary) + static line (floor)** — a hook that *calls the CLI* injects the bootstrap + a thin live nudge at session start (fresher, higher-salience; e.g. Claude Code `SessionStart`); a static line in the always-loaded file (`CLAUDE.md` / `AGENT.md` / Cursor rules) is the universal floor. Both, profile-driven; capability-dependent (profile declares what the assistant supports).
- **Hook stays routing + thin nudge, never a content dump** — same "routing, not content" discipline; its value is freshness/salience, not volume; the agent still pulls real context JIT. It also makes the bootstrap's "advertise + demonstrate" automatic (the hook runs the front door, so the first context already shows live orientation).
- **Spawn binding = a launch template in the profile** — the CLI renders its fan-out dispatch (`task_id` + entrypoint) through the profile's template into the assistant's primitive (Claude Code: a Task-tool call running `jigc workflow W --task <sub>`); CLI owns the payload, the template is the only assistant-specific bit.
- **Profiles ship with the CLI + are installable** — known assistants (Claude Code first) ship in-box; more profiles can be installed later — a swappable layer parallel to packs.

## 2026-05-25

### Review remediation

Resolutions to gaps surfaced by a four-agent read-only review of all docs.

- **Task origination: `jigc start` is the front door *and* create verb** — `jigc start ["<intent>"] [--workflow X]` mints the task (slug-from-intent, base = HEAD, opens `.jigc/tasks/<id>/`), minted at workflow-*selection* time (not the bare orientation call). Closes the MVP's missing "discover" entry.
- **Workflow selection: hybrid, options-always-shown** — the catalog is always offered with a *recommended* default (a hint, never a silent force); the agent picks; a human can force one via a catalog-generated adapter command. The CLI never infers a workflow (model-free).
- **The default is a router workflow** — "no workflow specified" composes a cascade-overridable *selection-guidance* workflow that presents the catalog + each workflow's "when-to-use" hint and routes the agent to pick. Workflow definitions gain a "when-to-use" front-matter hint; task context roles (e.g. `spec`) are workflow-declared and agent-bound (CLI never infers).
- **Data-value path grammar** — `head ("." relation)* ("#" fragment)?`: `.` crosses a relation edge (inter-doc), `#` enters a doc (intra-doc), `:` names a doc literally; `head` is a declared live-state root (engine-native `task`/`store`, pack-provided `milestone`/domain) or a literal `type:name`. Resolves to scalar / doc-slice / collection; pure navigation, no logic; validated at compose-time.
- **Finalize blocks only on task-controllable integrity** — forward-ref integrity, required slots, malformed values block (the task can fix them). Inverse/minimum-cardinality ("a PRD must have ≥1 SPEC") is *completeness*, not integrity — advisory by default, hard-enforced only at store/milestone scope, **never** a per-task finalize gate. Resolves the cross-task deadlock.
- **fan-out join: sub-agents validate but never commit; the parent finalize is the commit boundary** — one commit per sub-task in task-id order (squash a cascade knob). Slug collisions are handled by isolation + CLI-owned wiring (the join suffixes the loser and rewrites its *local* self-refs in the merge pass; workflow-provisioned ids are sub-task-derived and can't collide). No sub-agent runs git → no races.
- **Out-of-band reconciliation: files are truth** — a conformant, non-conflicting external edit is *accepted* (import is just the normal canonical-Markdown parse, not a deferred feature); a nonconformant edit *blocks* with a precise conformance error; a true conflict *routes to the human* — discard is an explicit choice, never silent. No silent data loss; three-way merge deferred.

### Implementation foundation

First decisions about *how we build it* (vs. `design/`'s *what it is*).

- **New `implementation/` directory, parallel to `design/`** — build decisions are a new category that don't fit the language-neutral design docs; same conventions (descriptive names, no number prefixes, cross-reference never restate). `design/` = what the system is; `implementation/` = how we build it. Detail in [implementation/language-runtime.md](implementation/language-runtime.md).
- **Core language = Rust** ([implementation/language-runtime.md](implementation/language-runtime.md)) — engine + CLI in Rust because the design is union-heavy (≥5 tagged unions + enums) and the project's value *is* exhaustive correctness; Rust makes "handle every case" a compile error, not a discipline. Ties or wins on cold-start, binary size (~2–5 MB), and Markdown byte-offsets; borrow-checker cost is low for per-invocation parse→transform→serialize work. **Why-not:** TS-on-Bun (compiled-binary startup is tens-of-ms not single-digit; `ink` is Node-bound so Bun XOR a good TUI; the Markdown edge dissolves into a language-agnostic strategy), Go (close — best TUI/velocity, but no exhaustiveness), Python (startup + distribution hit our hardest constraints; AI-ecosystem edge moot since the core makes no LLM calls). Decided after research that **reversed an initial TS-on-Bun lean**.

### Implementation: parsing & on-disk round-trip

How the CLI reads/edits/serializes the canonical Markdown ([implementation/parsing.md](implementation/parsing.md)). Mechanism only; the on-disk *format* stays in [design/storage.md](design/storage.md).

- **Offset-splice, never re-stringify; re-parse to validate** — every Markdown AST stringifier reformats, so the diff-clean path is splicing edits into the original byte buffer (the `markdownlint --fix` model). This is the strategy the whole doc hangs on; it makes lossless round-trip a property of *approach*, not library.
- **Parse model: full CommonMark block parse (`pulldown-cmark`), mapped onto the schema** — a line scanner misreads `##` inside code fences; a real block parse gives trustworthy byte offsets. Slot prose is an **opaque span** — parsing draws the determinism boundary literally (CLI owns block structure, never interprets prose). Rejected `comrak` (line/col-only spans) and `tree-sitter-markdown` (C dep, highlight-grammar) — the latter kept as a fallback.
- **Front-matter is a flat field block, not full YAML** — "one field syntax, two locations" forbids two field syntaxes; fields are schema-typed so YAML's dynamic typing fights us; flat lines splice diff-clean. Body field groups are a trailing **bullet list** (a distinct block type the schema disambiguates against prose). One grammar, two structural frames (`---` fences / bullets).
- **`{#id}` via pulldown's heading-attributes extension** — gives clean title text + frozen id separately; items only (doc identity is the path); missing→mint-on-import, duplicate/malformed→conformance error; slug rules stay minting's, not parsing's.
- **Write pipeline: splice to edit, generate only new** — one canonical writer (serves `create`/`add-item`/field-insert/`--template`) with golden-tested parse↔write symmetry; **validate-after-write** re-parses and aborts on anomaly (local gate, distinct from the `finalize` engine). Edits land in the task working area; committed file untouched until finalize.
- **Conformance falls out of the parser** — the schema-mapping *is* the conformance check; diagnostics are located, collected-with-resync, and use the validation `finding` shape. Conformance is **binary/intrinsic** (the pre-gate below the engine); validation severity is graded/cascade-tunable.
- **Round-trip contract: idempotent on canonical content, surgical on edits** — minimally + locally canonicalizing on first touch (final newline, BOM strip, EOL matched locally never globally rewritten); UTF-8 only; enforced by golden + property/fuzz tests, not assertion.

### Implementation: module layout

How the locked architecture becomes Rust crates ([implementation/module-layout.md](implementation/module-layout.md)). Realization only; the architecture itself stays in VISION/CLAUDE.

- **Two-crate workspace: `engine` (lib) + `cli` (bin), `cli → engine`** — the engine/frontend boundary is the one with architectural weight (neutral, empty, makes no LLM calls; an `mcp` bin later is a third crate over the same engine). Engine internals are **modules** (cascade/schema/parse/registry/compose/validate/state/index), not micro-crates; `parse` is the first split-out if needed. Rejected single-crate (engine not separately consumable) and micro-crates (premature ceremony).
- **Dev pack (and adapter profiles) embedded in the `cli` binary** — data not logic, embedded so `jigc` is one self-contained artifact; the engine reads pack-default through a **source abstraction**, staying empty. Pack versions with the release (= what override-reconciliation needs). Filesystem/installable packs come later through the same abstraction. Boundary stays internal discipline, not a public API.
- **I/O split: CLI locates, engine resolves** — `cli` locates the three cascade layers (embedded pack-default · external team · in-repo project) + repo root and renders results; `engine` resolves the cascade and owns managed I/O (docs, `.jigc/`, edge index). Feed layers in, assert results out → the core is directly testable.
- **Renderers live in `cli`, downstream of engine result types** — result types are `Serialize`, so JSON is generic; agent-text/human are per-type. Default agent-text (the agent reads non-TTY stdout); TTY→human-pretty; `--format` overrides; ratatui TUI is an additive post-MVP module preserving the non-interactive floor. The composed-workflow agent-text renderer is gated on the open emitted-format micro-syntax.
- **Adapter generation in `cli`** — profiles embedded (Claude Code first); generates/regenerates the static line + allowlist + catalog-derived launchers into the host project. MVP = line + allowlist; hook + spawn binding are post-MVP (spawn rides on fan-out).
- **Probe boundary in `engine`: `Probe` trait, in-process (MVP) + subprocess seam (post-MVP)** — MVP ships the trait + in-process probes only; the trait must admit the subprocess (JSON-contract) impl with zero engine change; probe executables live outside the workspace (any language).

### MVP scope clarifications

Pinning what the first runnable single-task loop actually reads/writes, before phase planning. Current MVP boundary lives in [CLAUDE.md](CLAUDE.md); this is the reasoning.

- **MVP single-task is spec-*less*** — no `task.spec` reference, no `spec` schema ships; the "what" comes from the human `intent` + the codebase. A spec type with no creation flow and a deferred `doc-code` validator would be dead weight; adding spec support later is a trivial pack addition (schema + one `locate` placeholder). Refines an earlier "spec-optional." The placeholder taxonomy is still fully proven spec-lessly — command-ref (`{{cli.finalize}}`), include (the workflow's step includes), data-value (intrinsic task `intent` + the provisioned commit-doc context).
- **Front door built, router not** — `jigc start` (mint task, resolve default workflow, orient) is essential; the **router** selection-guidance workflow is not built. The "no-workflow-specified" default is a cascade knob, set to `single-task` for the MVP (the design's sanctioned alternative to a router-default); it flips to the router when ≥2 work-workflows exist. Model-free and never-force hold vacuously at one option.
- **MVP deliverable = `engine` + `cli` + a minimal embedded dev pack + the Claude Code profile** — the engine ships empty by invariant, so a runnable MVP *must* include pack content. Pack: **`commit`** doc-type only (engine-native field types → no adjudicator), **`single-task`** workflow (no router) + its ~3 steps, cascade pack-default config (no-workflow default = `single-task`, MVP probe severities, finalize-autonomous, commit→git rendering), and **zero probes** (the two MVP probes are engine-native code, not pack data). Out of MVP: spec/ADR/PRD types + their creation flows, the router, planning/milestone/setup workflows, pack probes (`doc-code`), fan-out/join, and the adapter hook + spawn binding.
- **`finalize` renders the commit doc into the git commit** — the `commit` doc-type's *sink* is the git commit message, not a repo file (transient instance, working-area only). Finalize validates (required `summary`, valid `type`, no drift) → renders `type(scope): summary` + body + trailers via the commit schema + cascade → `git add` + `git commit` the task's code changes + promoted managed docs as **one** commit → discards the working area. Clarifies that **the CLI commits code too** — the agent *authors* code directly (the bootstrap's "code untouched" is about authoring), but *committing* is the CLI's job at finalize ("CLI orchestrates, git executes"); one task → one logical commit. MVP: current branch, working-tree staging (precise task-scoping is a refinement), refuse empties.

### MVP thickening — add a persisted doc type (pre-planning review)

A two-agent read-only review before phase planning (consistency + MVP red-team) found the commit-only MVP **builds machinery it never exercises**: `commit` is transient (sink = git message, no committed file), so the MVP would build the offset-splice parser, `file-state`, and the storage path yet never run them against a persisted, re-readable, human-editable file — leaving the **#1 technical risk (lossless round-trip) unretired** and the integration-advantage + context-assembly differentiators unproven. (Consistency stragglers fixed in a separate commit.)

- **Add the `adr` doc-type, agent-created in-task (A-full).** `adr` persists to `decisions/` with engine-native fields (`status` enum, `date`) + prose slots + the optional **`supersedes`** relation (adr→adr, 0..1). The agent creates one via the workflow-gated `create` flow when a decision is warranted. This makes the MVP exercise — and de-risk — the core paths commit-only dodged: persist-to-location + finalize-promote, **round-trip on a committed file (retires the #1 risk)**, `file-state` drift + OOB reconciliation, context-slice assembly, and — via `supersedes` — the **referential-integrity advantage** (edge index + forward-ref integrity at finalize). Chose **A-full** (with the relation) over A-thin (relation-less) to prove the integration advantage — the strongest differentiator vs `CLAUDE.md` — now, accepting the edge index + relation-integrity as MVP scope.
- **`task.intent` is an engine-native `task` data-value root** — the composed `single-task` embeds `{{task.intent}}` so `workflow-refs` validates a real data-value (previously `intent` was only the minting slug-source).
- **Validation = two probes + the intrinsic finalize gate** — `workflow-refs` + `file-state` are the engine-native *probes*; forward-ref/relation integrity is the engine's **intrinsic finalize integrity** (not a probe), now genuinely exercised via the `supersedes` edge. Still zero *pack* probes; `doc-code` deferred; inverse/min-cardinality stays advisory at store scope.
- **finalize promotes the created ADR** (not "nothing") alongside the rendered commit; **"render commit schema → message string" is a fifth canonical-writer caller** ([parsing.md](implementation/parsing.md)); finalize stages the dirty working tree (precise task-scoping is a refinement).
- **Still spec-less, still no router** — the ADR is an *output the agent optionally creates*, not an input; the "what" still comes from intent + codebase.

### Addressing — variable-depth, one grammar for every reference

- **Addresses point at the depth of their target.** Formalized in [structural-grammar.md](design/structural-grammar.md#addressing): `type:slug` / `type:slug#unit` / `type:slug#unit/leaf` / `type:slug#unit/item` / `type:slug#unit/item/leaf` are all first-class — schema determines which depths are valid at any given unit, grammar permits every depth uniformly. Settles Pass 1 F8 not by tightening to "always strict full form" but by recognizing variable-depth addressing as the right design: a reference system that targets at the granularity of what it actually wants to reference.
- **One grammar, every reference.** The same address atom is used everywhere references live — write commands, validation targets, override ops, data-values, *and* the values of `ref` fields that author cross-references (the `supersedes: adr:foo` pattern). Made explicit because thinking of "ref values" as a separate grammar is a common misread; they're the same address grammar at whichever depth the reference needs.
- **Single-slot sections resolve naturally** — `#unit` is the unit, which equals the slot when that's all the section contains. No special-case shorthand; the unit's address sits at the depth where the slot is.

### `jigc start` semantics — four forms, two orthogonal knobs

- **Four `jigc start` forms, each deterministic.** Bare `jigc start` orients (read-only); `jigc start "<intent>"` composes the cascade-default workflow; `jigc start --workflow X "<intent>"` composes X explicitly; `jigc start --task <id>` resumes. Settles Pass 1 F3 (a cross-pass theme also flagged by Passes 2, 3, 4) and removes the conflation across `CLAUDE.md`, `write-commands.md`, `bootstrap.md`, and `assistant-adapter.md`.
- **`creates-task: true|false` is a workflow declaration** ([workflow-dialect.md](design/workflow-dialect.md)) — the workflow's own front-matter says whether running it mints a task; default `true`. The router declares `false`; work-workflows take the default. CLI reads it and acts — never infers.
- **`default-workflow: <id>` is a cascade knob** ([overrides.md](design/overrides.md)) — the cascade names which workflow `jigc start "<intent>"` composes when no `--workflow` is given. Pack-default for MVP: `default-workflow: single-task`.
- **The two knobs are orthogonal** — any workflow can be the default; any workflow can mint or not. The router being the post-MVP default isn't *because* of its `creates-task: false`; it's because the cascade flips `default-workflow` to point at it. Clean separation prevents the "the one with `creates-task: false` is the default" smell.
- **Bare `jigc start` is read-only**, so the adapter `SessionStart` hook runs it directly — no `--orient` flag. Drops the undefined `--orient` from [assistant-adapter.md](design/assistant-adapter.md).

### Slot-author directives use slot syntax in definitions

- **Workflow definitions use `<<author: <address>>` for slot-author directives** ([workflow-dialect.md](design/workflow-dialect.md) → Leaves) — the same syntax as emitted output, not `{{ author: … }}`. Settles Pass 1 F10 (also flagged by Pass 3 as an invariant-6 violation). The `<<…>>` and `{{…}}` syntaxes stay strict opposites: an author directive is *never* a placeholder, regardless of position in the pipeline. Embedded `{{…}}` inside the `<address>` parameter is fine — that's a placeholder doing its normal job (resolve to a value), and the surrounding `<<…>>` survives composition.

### Data-value resolution — address by default, `@` for content

- **A data-value path inside `{{…}}` resolves to the address of its target by default; prefix with `@` to dereference** ([workflow-dialect.md](design/workflow-dialect.md) → Leaves: Address vs content). One uniform rule across all depths. Mnemonic: bare path = the reference; `@` = at that reference (= the content), like `@username` or `*ptr`. Settles the address-vs-content question that surfaced while resolving F10: an author directive's parameter wants an address (`<<author: {{task.commit#summary}}>>`); step prose embedding doc content wants the content (`{{@task.spec#criteria}}`).
- **`@` on a scalar path is a conformance error** caught at compose-time by `workflow-refs`. ("`@` requires a path ending at a doc/section/item/leaf; this resolves to a scalar.") No silent no-op — wrong intent gets a clean error.
- **Implications for existing examples**: VISION's worked example and workflow-dialect's "How a workflow composes" example are updated to use `@` where content is wanted; the author-directive parameter now reads as a single placeholder (`{{task.commit#summary}}` resolving to the slot address) rather than literal text appended to a placeholder.

### id-source = the title field, rendered as the heading

- **A repeatable item's id-source is a typed `string` field** declared in the schema (`id-from: title` referencing the field, see [document-type-schema.md](design/document-type-schema.md)), **rendered on disk as the item's `###` heading** with the minted `{#id}` anchor. Structurally a field (typed, adjudicable, schema-located); on-disk a heading (diff-clean, human-editable). Settles Pass 1 F12 — the apparent contradiction between "id-source must be a field" ([structural-grammar.md](design/structural-grammar.md)) and "id-source = the heading" ([storage.md](design/storage.md)) is resolved by stating explicitly that the heading *is* the field's rendering. One field, two readings.
- **Editing the heading edits the field's value** (the title is mutable); the `{#id}` anchor is frozen at creation (the id is immutable). Survives retitle: `spec:auth-flow#criteria/rate-limit` keeps the frozen id even after the heading text changes. No design change — the underlying model was already locked; this is documentation precision.

### Task-id collision policy — suffix in parallel, reject in serial

- **Re-issued `jigc start "<intent>"` that slugs to an active task is rejected, not silently suffixed** ([write-commands.md](design/write-commands.md) → Task origination). The agent gets the existing task's status and a resume/discard prompt. Silent suffixing would strand the prior work and turn a forgotten resume into two parallel tasks. Settles Pass 2 F6 follow-up.
- **The deterministic collision-suffix is scoped to `fan-out` parallel merges** — where two sub-agents *intentionally* mint the same slug because the join needs to disambiguate. At task-origination scope, the suffix rule does not apply: a serial retry is a different question (resume vs new) and gets a different answer (reject + offer resume).
- **Base mismatch on any existing task** (collision *or* `--task <id>` resume) uses the same divergence-routing prompt as OOB reconciliation. The CLI never operates a task off its pinned base; switch back or discard, no in-place rebase.
- **Finalized task ids are reusable** — the working area is gone after `finalize`, so the task-id slot is free; the prior task's managed-artifact ids (e.g. `adr:<slug>`) live in committed storage and follow the artifact minting rule's collision-suffix if a fresh task tries to mint the same artifact name.

### Emitted micro-syntax — four classes, `Run:` formalized

- **The composed output uses four marker classes** ([workflow-dialect.md](design/workflow-dialect.md#emitted-format)): `` Run: `<cmd>` `` for executable commands (Run class), `> ` blockquote for embedded content from resolved `{{@…}}` (Content class), `<<author: <addr>>` on its own line for slot-author directives (Author class, already settled), and plain prose with no marker for reasoning (Reason class, the default). Settles Pass 2 F7 — the cross-pass theme #1 flagged as MVP-blocking by Passes 1, 2, 3, and 4. With this resolved, **no MVP-blocking opens remain.**
- **`Run: ` at line-start is reserved for the composer.** Instruction prose in a step definition may not start a line with `Run: `; the `workflow-refs` probe checks this at compose-time as part of its existing reference-resolution scope (no new probe — keeps the MVP engine-native probe set at two). A definition that shadows the marker is rejected before the composed output ever reaches the agent.
- **The backticked command form** (`` Run: `jigc …` ``) is doubly load-bearing: visually distinct for a reader, *and* machine-extractable by a strict line-pattern (`` ^Run: `(.+)`$ ``). Both readings of the surface are served by the same shape.
- **Reasoning is the default.** Anything that isn't Run, Content, or Author is reasoning, with zero marker overhead. Aligns with "great defaults beat ceremony" — the most common line-class carries no weight.
- **Recognition is convention, not parser-enforced on the agent side.** Agents read the emitted text as humans do; the markers' job is to be unambiguous *to a reader*. Consistent with the honest-boundary note (F17): compliance is by ergonomics.
- **Why this over alternatives.** The existing `Run: ` token in worked examples needed only formalization — no churn-heavy replacement (`` ```run `` fences, `# Run` / `# Reason` heading classes). The four-class split mirrors what the worked example already showed; reasoning-as-default keeps the markup cheap; backticks resolve the soft-marker ambiguity that "promote the convention" alone would have left.

### `finalize` transaction spec — ordered phases, atomicity rules, rollback discipline

- **`design/finalize.md` is the owned spec for the commit boundary** — the previously asserted but unspecified transaction. Settles Pass 2 F1 (cross-pass theme #4) and absorbs Pass 2 F11 (commit-doc → git-message rendering).
- **Seven ordered phases**: preflight → validate → render → promote → stage → commit → post-commit. **Atomic through phase 6 (commit); post-commit is best-effort with cache-stamp self-healing** — a failed hash update or cleanup never threatens commit truth.
- **Promotion is copy, not move.** Working area stays intact across phases 4–6 so rollback on hook rejection or git error is simple (delete the copies); only phase 7 removes `.jigc/tasks/<task-id>/` after the commit is real.
- **Dirty-tree policy: all tree-diff-from-base is the task's work.** No declared touch-set, no `--include-all` flag, no auto-stash. The base-pin mismatch routing catches "parallel hand-editing → committed" upstream; the `jigc task diff <id>` preview catches uncommitted parallel edits at validate-time. Honest model: if you started a task on a checkout, the tree-diff from base **is** the task.
- **`fan-out` finalize: one commit per sub-task in task-id order, plus parent commit.** Squash is a cascade knob (`finalize.fan-out.squash`, pack-default `false`). Preserves graph reproducibility under the determinism boundary.
- **Pre-commit / commit-msg hook failure rolls back to "as if `finalize` was never called"** — `git restore --staged --worktree` on promoted paths, promoted copies deleted, working area intact, hook stderr surfaced verbatim to the agent. **Never `--no-verify`** — hooks are user policy and the CLI respects them.
- **Empty diff after validate aborts cleanly** — "task validated but produced no diff — nothing to finalize." No empty commits.
- **Commit-doc rendering (F11) absorbed** — `<type>(<scope>): <summary>` subject + optional body + optional trailers footer; Conventional Commits is the pack-default; the schema is cascade-overridable for projects with custom commit conventions. Line-limit checks are advisory at pack-default severity (cascade-promotable to blocking, like every other check).
- **What `finalize` does NOT do**, made explicit to bound scope: no three-way merge, no schema migration, no LLM call, no `--no-verify`.
- **Reading-order placement**: after `validation` (which it composes), before `bootstrap`/`assistant-adapter` (integration layers). Updated in [CLAUDE.md](CLAUDE.md).

### Out-of-band reconciliation — state machine, strict MVP, no auto-repair

- **`design/reconciliation.md` is the owned spec** for handling out-of-band edits. Settles Pass 2 F5: the previous write-commands.md OOB section stated the philosophy as bullets; this turns it into a deterministic state machine with explicit detection timing, hash re-baselining sites, and MVP/post-MVP scope split.
- **Two-axis state machine: committed-state (`UNKNOWN` / `IN_SYNC` / `DRIFTED`) × task-state (`UNTOUCHED` / `TOUCHED`)** — five pair-outcomes, all deterministic. Same `(file content + recorded hash + task working area + schema)` in → same classification out.
- **Three classifier outcomes for the agent**: **absorb** (clean external edit, hash advances), **conformance-block** (parse / schema failure surfaces precisely), **conflict-block** (both sides changed; file-level granularity in MVP). Never silent — every outcome surfaces.
- **Detection timing — six trigger points**: task `start`, every read through the CLI, every write through the CLI, `jigc task validate`, `finalize` preflight, ad-hoc `jigc validate`. The classifier runs at each; parse only fires when state is `DRIFTED`.
- **Hash re-baselines at three sites**: baseline adoption (first encounter — absent-hash is not drift), absorb (clean external edit accepted), commit (`finalize` phase 7). Task writes do **not** advance the committed-state hash — the working area is separate.
- **Strict MVP auto-repair scope: none.** Even mechanically-obvious repairs like re-minting a dropped `{#id}` from the recorded id-source value are post-MVP. The conformance error names exactly what's missing; the human pastes the anchor back. Silently reconstructing identity is precisely the "the CLI just does things" behavior the determinism boundary is meant to prevent. *Easier to relax later than to tighten.*
- **Conflict granularity, MVP: file-level.** Both-sides-changed blocks at the doc; resolution is explicit discard of one side (agent `jigc task discard-write <addr>`, or human reverts the file). Section/leaf-level granularity and three-way merge are deferred together — they pair with the same machinery as override-conflict resolution ([overrides.md](design/overrides.md)).
- **`jigc import` for entirely new untracked files deferred.** [implementation/parsing.md](implementation/parsing.md) flag preserved and cross-refed to reconciliation.md's scope split: MVP imports are only edits to *managed* docs the CLI already knows about; brand-new `.md` files authored outside the CLI need the full import flow (mint-on-import) and ride post-MVP.
- **`file-state` probe scope unchanged** ([validation.md](design/validation.md)) — its output (the `reconcile` finding) is what the classifier consumes; the classifier is *not* a new probe.
- **Reading-order placement**: between `validation` (whose `file-state` output it consumes) and `finalize` (whose preflight runs the classifier). Updated in [CLAUDE.md](CLAUDE.md).

### Relations are `ref` fields, not a parallel schema block

- **A cross-reference is a `ref`-type field carrying relation metadata** (`to`, `card`, `inverse`, `inverse-card`), not a separate `relations:` block alongside `fields:` ([document-type-schema.md](design/document-type-schema.md#cross-references--ref-fields-with-relation-metadata)). Settles Pass 2 F3 — the schema format now reflects the conceptual "field-backed edge" model end-to-end.
- **Why merged**: the conceptual "two facets" model (instance endpoint + type-level constraint) is right, but those two facets are properties of the same thing — a typed field with extra metadata. Splitting them across two schema blocks would have forced parsing, validation, writer-generation, and overrides to consult two declarations for one cross-reference, and left "is `supersedes` a field, a relation, or both?" with no good answer.
- **Cardinality syntax**: UML strings (`"0..1"`, `"1"`, `"0..*"`, `"1..*"`); already in use, well-understood, default `"0..1"`.
- **Inverse name lives on the forward field only** (`inverse: <name>`). The target type does not redundantly declare it. The CLI computes the inverse view at read-time by walking the edge index — consistent with "bidirectional at the graph/view level, single-authored at the storage level."
- **`inverse-card` is the completeness obligation** ("a PRD must have ≥ 1 SPEC"). Advisory at task scope (depends on other tasks), hard-enforced only at store/milestone scope ([validation.md](design/validation.md)) — unchanged from the previous model; F3 just makes the declaration location explicit.
- **Storage rendering unchanged**: a `ref` field renders like any other field — front-matter key in a header section, trailing bullet in a body section, inline flow list when `card > 1`. F3 is a schema-format clarification; [storage.md](design/storage.md) on-disk format is already aligned.
- **Pack-provided ref-like types (`code-anchor`) stay as separate types** with their own adjudicators. Only managed-artifact refs use `type: ref`. Pack types that also want relation semantics is a post-MVP question.
- **Validation timing unchanged**: address-shape at write-time (local adjudication), target-existence at `finalize` (forward-ref integrity), inverse-cardinality at store/milestone scope (completeness, never per-task gate) — all already settled by [validation.md](design/validation.md); F3 just makes the *binding* between schema-declared `ref` and these checks explicit.
- **Address grammar interaction**: a `ref` field's *address* (`adr:bar#status/supersedes`) and its *value* (`adr:single-node-cache`) both use the same variable-depth grammar — the "one grammar, every reference" rule from [structural-grammar.md](design/structural-grammar.md#addressing) holds end-to-end.

### Override resolution algorithm — 9 phases, structural deltas before expansion

- **The cascade applies through a single 9-phase algorithm** ([overrides.md](design/overrides.md#resolution-algorithm)) that covers workflows and schemas uniformly (workflows add the include-expansion / placeholder-resolve / emit tail). Settles Pass 2 F4.
- **Phase order is load-bearing**: resolution → by-id shadowing → scalar deltas → structural deltas → slot-fills → cycle detection → (workflow) expansion → (workflow) resolve → (workflow) emit. Phases 1–6 produce a fully-resolved, cycle-free composition tree *before* expansion or placeholder resolution runs.
- **By-id file shadowing is atomic** — a project's `step:locate.md` shadows pack-default's entirely. No field-level merge across layers. Want partial change? Use a `scalar-set` (knob), `structural-op` (insert / replace / remove), or `tracked-fork` (content fork with base-hash). The implicit-merge failure mode that bites every layered config system is eliminated by construction.
- **Delta application order: pack → team → project**, each on top of the prior result. Within a layer, deltas apply in **file order** (the manifest's intent is surface-visible). A later delta targeting a now-removed id surfaces an `orphaned` finding from `workflow-refs`.
- **Structural deltas precede include expansion** — the load-bearing clarity F4 demands. `insert-step --after locate` operates on the workflow's **include list** (ordered step references), not on already-expanded content. A reader can predict the post-cascade include list from the manifest alone. The alternative (apply-after-expand) would let `insert-step` land inside unexpected places depending on what each step's body happens to expand to.
- **Cycle detection runs after all deltas, before expansion** — phase 6. Catches cycles introduced by a delta. `workflow-refs` is the probe that runs this; no new probe added.
- **`replace` vs `tracked-fork` locked precisely**: `replace` swaps which step/section id appears at a position in the structural list (the replacement is another id, not inline content). `tracked-fork` copies a unit's body into a new file at the overriding layer with `base-version` + `base-hash`; at compose-time it's just another shadowed file (the base-hash matters only at upgrade-reconciliation time).
- **No partial field-level merge, no expansion-before-deltas, no silent cycle handling, no LLM call** — the four "does NOT do" guardrails, made explicit to bound the algorithm.
- **Doc location**: extended `overrides.md` (cascade+delta is its core concern); `workflow-dialect.md`'s "steps resolve through the cascade" line and the cycle-check note both sharpen to point at the algorithm's specific phases.

### Validation severity inventory — every MVP check, intrinsic vs tunable

- **Every MVP check is enumerated in a single table** ([validation.md](design/validation.md#severity-inventory)) with default severity, intrinsic-or-tunable classification, and a cascade key per check. Settles Pass 2 F2.
- **Two-tier rule**: **intrinsic** checks are locked at `blocking` (cascade cannot demote — a `scalar-set` below the floor is rejected at cascade resolution as a config-conformance error, logged-not-applied, visible via `--explain`); **tunable** checks default to their declared severity and the cascade can promote or demote freely.
- **Intrinsic set = `workflow-refs.*` + `schema-conformance.*`** — 10 checks total. These are the load-bearing minimum: composition correctness (`workflow-refs`) and structured-value integrity (`schema-conformance`). Demoting them would break the determinism boundary's mechanical floor — composition would emit broken output, or the integration advantage's forward-ref-resolution gate would silently let dangling refs commit.
- **Tunable set = `file-state.*` + `schema-completeness.*` + `override-default.*` + `commit-rendering.*` + `doc-code.*`** — 6+ checks (`doc-code` post-MVP). Each protects itself with its route, default severity, or default scope rather than with a lock: `file-state` drift routes to reconciliation regardless of severity; `inverse-cardinality` is advisory at task scope by design (completeness depends on other tasks); commit line-limits are conventional and a project may rationally not enforce them.
- **Cascade key convention**: `validation.<probe>.<check>.severity` for per-check tuning; `validation.<probe>.severity` for probe-coarse default. Per-check wins via normal cascade resolution ([overrides.md](design/overrides.md) → Resolution algorithm phase 3).

### Command catalog — typed args, three arg kinds, POSIX shell-safe rendering

- **`design/command-catalog.md` is the owned spec** for `{{cli.<id>}}` command-refs ([command-catalog.md](design/command-catalog.md)). Settles Pass 2 F8. Previously the docs asserted "command-refs resolve to literal invocations via the cascade" without defining the shape; this binds parameters, interpolation sources, validation, and shell-safety end-to-end.
- **Each catalog entry is `{id, command, args[], stdin?, hint}`** — a stable id matching `{{cli.<id>}}`, an executable, an ordered args list, optional stdin documentation, a one-line hint.
- **Three arg kinds**: **literal** (a plain string token), **`{ from: <data-value-path> }`** (resolved at compose-time against the workflow's data-value context using the same grammar as workflow-step placeholders), **`{ agent: <name>, hint: ... }`** (rendered as `<NAME>` in the emitted command for the agent to substitute at run-time).
- **Workflow placeholders live only inside `from:` args** — never bare in literal positions. Narrow surface, parseable, predictable. Same data-value grammar as everywhere else (`task.commit#summary`, `task.id`, etc., with `@` for content per the F7 / address-vs-content rule).
- **Agent-substitution marker `<NAME>` is a third bracket family** alongside `{{...}}` (placeholders, filled at compose) and `<<...>>` (slot-author, filled via write-path). Visually distinct: single-angle vs double, uppercase identifier with no payload vs `name: address` payload. They cannot be confused.
- **POSIX shell-safety is per-arg and deterministic**: bare if the arg matches `[A-Za-z0-9._:#/=@+-]+` (addresses, identifiers, flag names); single-quoted otherwise (with embedded `'` closed-escaped-reopened). Same args in → same emitted line, every time. The emitted backticked command is copy-paste safe in any POSIX shell.
- **Validation extends `workflow-refs.command-ref-resolves`** (already in the F2 inventory) — no new probe. At compose-time: catalog entry exists, every `from:` path resolves, every `agent:` arg has a `hint`, the rendering is clean. All findings are intrinsic-blocking; a broken command-ref would emit a broken or ambiguous Run line — the determinism-boundary leak the system exists to prevent.
- **Cascade overrides use the normal 9-phase resolution algorithm**: `insert` a new catalog entry, `replace` an existing one (e.g., point at a project's wrapper script), `remove` an unused one (any workflow `{{cli.X}}` that referenced it surfaces a `workflow-refs` finding). `scalar-set` can tweak individual fields but most one-line changes are clearer as a `replace`.
- **What the catalog does NOT do**: no control flow (literal / data-value / agent — that's it), no multi-line commands (heredocs are out of scope; project scripts live separately), no agent-side selection between entries (workflows name one `{{cli.<id>}}` per Run line — selection is workflow-routing, not catalog-routing), no LLM call (resolution is deterministic).
- **Reading-order placement**: after `workflow-dialect` (defines command-refs as placeholders) and before `validation` (whose `command-ref-resolves` check targets it). Updated in [CLAUDE.md](CLAUDE.md).

### Pass 3 #1 + #2 — slot / field-group boundary discipline (parser identifies structure by markers, never by content-sniffing)

Cross-pass theme #3 (Passes 3, 5) settled: both attacks #1 (slot prose containing `## Decision` or `### thing {#id}` perturbs the block parse) and #2 (slot prose legitimately ending with `- status: TBD` gets silently reclassified into the field group) share one root cause — **the parser was inferring structural boundaries from content**. The fix is one principle, two rules: *the parser identifies structure by markers the CLI controls (sentinels, schema-fixed `##`/`###` headings, `{#id}` anchors), never by sniffing content against the schema.*

- **Rule A — Field groups are marked by a sentinel** ([parsing.md](implementation/parsing.md) → Field-group delineation, [storage.md](design/storage.md) → "One field grammar"). The canonical writer emits `<!-- fields -->` on its own line, blank-line separated, immediately before the bullet list, in schema order. The parser identifies field groups by *sentinel + following List*, never by matching bullet content against declared field names. Slot prose ending with `- status: TBD` has no sentinel and is unambiguously prose — the silent prose-to-field reclassification is gone. The sentinel is a **reserved structural marker**: `<!-- fields -->` anywhere other than the canonical trailing position is a conformance error (slot prose may not include it as decorative content; a sentinel without a following list, or with one whose keys don't match declared fields, is also a conformance error).
- **Rule B — Slot prose has a heading-depth ceiling** ([parsing.md](implementation/parsing.md) → Slot heading-depth ceiling, [storage.md](design/storage.md) → "Slot prose has a heading-depth ceiling"). Slot prose may not contain ATX headings at `##` (section) or `###` (repeatable-item) depth, or Setext underline-style headings at any depth. `####` and deeper are allowed for slot-internal structure. The CLI's structural depths are unambiguous: `##` and `###` always mean structural marker, never "prose that happens to look like one."
- **Two enforcement sites** for both rules: **`set-slot` (write-time)** scans the agent's content and rejects with a precise conformance error pointing at the offending line; **the parser (read-time)** surfaces the same conformance error on an OOB-edit re-parse. Per Pass 2 F5 strict-MVP scope, no auto-repair — the error names exactly what's missing or out of place; the human (or agent via a follow-up write) fixes it.
- **Sentinel emitted only when fields exist** (decision row "C: only when needed"). Sections / items with no declared body / item fields have no sentinel. Visual cost is bounded — sentinels appear only where the schema warrants them.
- **Heading-rule scope: forbid both `##` and `###`** (decision row "B: forbid both depths"). Uniform rule, no edge cases. The alternative (forbid `##` only, allow `###` since `{#id}` is what makes it item-shaped) would have left the question "is this `###` line a new item or just prose?" sniffable by anchor presence — exactly the content-sniffing the system is eliminating.
- **Setext headings forbidden in slots** (decision row "A: forbid all Setext"). Setext (`===` / `---` underlines) is unusual in agent prose, and the underline syntax has its own depth-confusing edge cases (`---` is also a thematic break depending on context). Simpler rule wins.
- **Multi-slot sections deferred** (decision row "B: defer multi-slot"). Per [storage.md](design/storage.md) one-prose-slot-per-section is preferred; multi-slot rendering is an open question and pairs with the multi-slot sub-label syntax already flagged in [storage.md](design/storage.md) and [implementation/parsing.md](implementation/parsing.md) open questions.
- **Conformance, not graded validation.** Both rules are **parser-pre-gate conformance** (binary / intrinsic — [parsing.md](implementation/parsing.md) → Conformance diagnostics), not entries in the validation severity inventory ([validation.md](design/validation.md)). Conformance-blocking is not a severity knob — a malformed file is malformed regardless of project policy. The conformance-diagnostics table in [parsing.md](implementation/parsing.md) is updated to list both new blocking cases.
- **The SPEC example in [storage.md](design/storage.md)** is updated to show the sentinel before the criterion's `maps-to-test` bullet, so the canonical form is concrete in the reading order's storage doc.
- **Why this resolves both attacks together.** The two attacks are not separate bugs — they're two faces of the same content-sniffing leak in the parser. A fix that addresses only one (e.g., field-group sentinel without the slot heading ceiling) would still let slot prose with `## Decision` headings re-introduce the structural-mis-locate path; a fix that addresses only the other would still let prose lists silent-promote. The two rules together close the leak end-to-end.

The parsing-level changes do **not** add new entries to the validation severity inventory ([validation.md](design/validation.md)); the new conformance errors propagate via the same `finding` shape the parser already produces (the "one finding shape, two producers" rule in [parsing.md](implementation/parsing.md)).

### Pass 3 #6 — cross-task forward-ref policy (committed store + same-task only; no provisional syntax)

Cross-pass theme #5 settled. Codex walked the scenario where T1 authors `supersedes: adr:b` with B planned in T2 — claiming forward-ref integrity blocks T1's finalize and the task cannot fix. Two distinct claims to disentangle:

- **Codex's specific example doesn't actually walk.** `supersedes` is a **backward** relation by ADR convention ("I replace an earlier accepted decision"). The agent authoring `supersedes: <future-thing>` is misuse of the relation, not a legitimate pattern the invariant must protect. The MVP doc-type-schema text already implied this; this batch makes it explicit (see below).
- **The general concern is real and was under-specified.** Strip the `supersedes` semantics: what if *any* ref field in T1 legitimately points at *any* doc T2 will create? The validation.md language "blocks only on integrity the task can fix" silently assumed the task can always fix (true for same-task creates, false for sibling-task creates). The invariant survived only by an undocumented policy.

**Policy locked**: forward-ref resolution covers refs whose targets sit in *exactly* two reachable surfaces — **(a) the committed store** (already on disk), or **(b) the same task's working area** (overlaid via the edge-index working overlay, [storage.md](design/storage.md) → Edge index lifecycle). A ref to a doc in *neither* is a blocking integrity error at `finalize`. **Cross-task forward-refs are not supported in MVP** (or post-MVP without an explicit provisional-ref feature). The deadlock Codex walked is rejected at its source — the agent never authors a cross-task forward-ref; if it does, finalize blocks with a precise error naming three routing options: **(i)** order the tasks so the target exists first (T2 before T1), **(ii)** move the target's creation into this task, **(iii)** drop the ref.

- **MVP scope verification**: `single-task` is the only workflow. No fan-out, no router, no multi-task planning. A task's `supersedes` value can only point at a previously committed ADR (or, hypothetically, an ADR the same task itself created). The MVP doesn't hit the deadlock at all; the policy defends the invariant for post-MVP and for the rare edge case where an agent mis-uses a ref.
- **Why not introduce `?` provisional refs now**: nothing in MVP (or near-post-MVP) needs them. Adding syntax to the address grammar — one of the most load-bearing surfaces in the system — for a feature with no real use case is the speculative over-build the project guards against. Easier to relax later than to ship grammar now. If a real cross-task pattern lands (e.g. fan-out sub-tasks coordinating creates), provisional refs get their own design including the deferred-validation state machine at store/milestone scope.
- **Doc placements**:
  - **[validation.md](design/validation.md)** §"Integrity vs completeness" — new paragraph "Forward-ref resolution — the two reachable surfaces" makes the policy explicit, names the three routing options, and explicitly rejects the cross-task forward-ref pattern. This is where the invariant defense lives.
  - **[document-type-schema.md](design/document-type-schema.md)** §"Bidirectional, but the inverse is derived" — the existing "Forward-ref integrity *is* gated at `finalize`, because the task can satisfy it by creating the target in the same task" line is sharpened to enumerate the two surfaces and cross-ref validation.md. A new bullet states the semantic rule: `ref` fields declare backward relationships to existing or same-task-created artifacts; never planning markers; `supersedes` means "replaces an earlier accepted decision," not "plans to supersede a future one."
- **Write-time stays local-adjudication-only** ([write-commands.md](design/write-commands.md) → write-time vs finalize-time checks): the locked split is unchanged. Ref-field writes check address *shape* at write-time; *existence* at finalize. A ref whose target won't exist by finalize fails at finalize, not at the write. Catching it earlier would constrain authoring order (a task creating A then B with B→A would fail when B's ref is written before A is created), which is a worse tradeoff than catching it at finalize where the full working area is visible.
- **Pass 4 "partially proven differentiator" concern is separate and deferred.** Pass 4 flagged that `supersedes` as a *self-relation* that's also *optional* doesn't fully exercise the integration advantage even with `supersedes` in MVP. That's a question about MVP differentiator *strength* (whether the MVP is convincing enough), not about the invariant Pass 3 is testing (whether the boundary holds). It rides in the Pass 4 batch.

### Pass 3 #5 + #3 — fan-out coordination-boundary defenses (cross-area refs rejected at join; adapter launch templates typed-schema validated at install)

Two paired attacks on the fan-out coordination boundary settled together. Fan-out is post-MVP, but locking the design rules now is cheap and forces the implementation to respect them when it ships.

- **#5 (outbound, sub-task → CLI)** — sub-agent B authors `supersedes: adr:cache`, guessing sub-agent A's slug; collision-suffixing rewrites only A's *local* self-refs; B's hand-typed cross-area ref can dangle or silently retarget. The previous workflow-dialect.md disclaimer "isolation guarantees the only references to a sub-agent's new doc are from its own area, so cross-area rewriting never arises" was wrong on its face: filesystem isolation prevents *writes into* a sibling's area, but not the LLM *typing* a plausible sibling slug.
- **#3 (inbound, CLI → sub-task)** — the assistant adapter's launch template decides whether the sub-agent ever sees the CLI's payload. A stale or broken template (omits `task_id`, paraphrases inline instructions, fails to invoke `jigc workflow`) lets the sub-agent write outside the working area or never reach the CLI at all; the join's assumptions collapse silently.

**Same root cause: a boundary the design treated as "obviously honored" without an enforcement mechanism. Same fix shape: explicit defense at the boundary.** Two rules:

- **Rule C (#5) — fan-out cross-area refs are rejected at join.** Each sub-task's outgoing refs are validated at join against `(committed store ∪ this sub-task's own working area)` only. A ref pointing into a *sibling* sub-task's area is a blocking integrity error at join — **same shape as the cross-task forward-ref policy** (Pass 3 #6 above). Coordination patterns that require cross-area refs belong in **sequential steps** before the fan-out splits; if a real fan-out cross-area pattern lands post-MVP, ID reservation / provisional refs get their own design (no speculative grammar now). Lands in [workflow-dialect.md](design/workflow-dialect.md) → `fan-out` / `join` (replaced the old "Isolation guarantees …" bullet with sharper Slug-collisions + Cross-area-refs + Never-started bullets) and cross-refed from [validation.md](design/validation.md) → Forward-ref resolution.
- **Rule D (#3) — adapter launch templates are typed-schema validated at install.** The profile's launch template carries a schema declaring required placeholders (`{{task_id}}`, `{{workflow}}`), the required invocation pattern (must invoke `jigc workflow --task <id>`; no inline paraphrase), and forbidden patterns. Validation runs at `jigc setup` / `jigc adapter install` / regeneration; a broken template is an **install-time error**, not a runtime mystery. Lands in [assistant-adapter.md](design/assistant-adapter.md) → Bind the spawn mechanism.
- **Runtime backstop (made explicit)** — the join derives every sub-task's state from the CLI ("messages are notifications, CLI state is truth" — [VISION.md](VISION.md) → Sub-agents). A sub-task with **no recorded CLI activity** is treated as **never-started**, distinct from "started and failed." Catches the case where a template passes schema but somehow still doesn't reach the CLI (assistant API changed, user mis-wrapped, spawn primitive misfires). Lands as a new bullet in [workflow-dialect.md](design/workflow-dialect.md) → `fan-out` / `join`.

Decisions (recommended → chosen):

- **Cross-area ref policy = α (forbid at join)**, not β (ID reservation) or γ (provisional refs). Mirrors the #6 cross-task policy. No new grammar. If a real fan-out coordination pattern needs cross-area refs, that's the moment to design β or γ — but the project explicitly guards against speculative grammar for surfaces that don't exist yet.
- **Adapter template validation timing = install + runtime backstop**, not install-only or runtime-only. Two complementary layers: install catches the broken template before any sub-agent runs (fast feedback to the profile author); the runtime backstop surfaces the silent "sub-agent never started" case as a distinct routing outcome rather than a deadlock.
- **Start-ack mechanism = implicit via CLI state**, not a new explicit `jigc task ack` command. The existing "CLI state is truth, messages are notifications" pattern already supports it; we just made the never-started case explicit. No new command surface.
- **Missing-activity treatment at join = block + distinct routing.** A sub-task with no CLI activity surfaces as "never-started" — separable from "started and failed" so the human knows whether to look at the adapter or the sub-agent's work.
- **Doc placement = split across three docs**, not one big section. Each rule lives in its natural home (workflow-dialect for fan-out coordination; assistant-adapter for the template schema; validation as the integrity-rule home cross-refs both). One-purpose homes; cross-reference, don't restate.

The two attacks' resolutions inherit the discipline of #6: **the boundary the design treated as "obviously honored" is now enforced; the failure mode is rejected at its source.** Pass 3 themes #5 (cross-pass) and the single-pass adapter-spawn concern are now closed against the invariants they targeted.

### Pass 3 #4 — OOB rename: path-rename is identity-change, detected and routed (MVP); `jigc doc rename` post-MVP

Codex's scenario: a human runs `git mv decisions/rate-limit.md decisions/gateway-rate-limit.md`. Because identity = path, the CLI sees `adr:rate-limit` as deleted and `gateway-rate-limit.md` as new untracked; every `supersedes: adr:rate-limit` ref in the store now dangles. The hash-on-known-path state machine ([reconciliation.md](design/reconciliation.md) → State machine, Pass 2 F5) didn't cover this case — it classifies *edits*, not *renames*; Pass 2 F5 explicitly deferred untracked-file handling to post-MVP, which silently left the rename gap uncovered.

- **Reframing**: VISION's honest-boundary note "IDs survive rename" was meant for **title rename** (H1) — the title field is mutable, the id is frozen. A **path rename** is a different operation: it's an **identity change** because id = filename slug (storage.md's "identity is the path"). The locked invariant doesn't promise path-rename survival; this batch makes the distinction explicit.
- **Path rename must be CLI-orchestrated.** Consistent with [VISION.md](VISION.md) principle #2's "splits and merges are explicit CLI ops." Auto-rewriting referrer refs to follow an OOB rename would be the "the CLI just does things" failure mode the determinism boundary exists to prevent.

**Policy locked**: rename detection runs at the existing `file-state` probe trigger points as a separate classifier. Two signals, two outcomes:

- **Strong signal** (tracked path missing + untracked path with same content hash) — **suspected rename**. Conformance error names old/new paths + the `git mv` revert one-liner + a forward pointer to the post-MVP `jigc doc rename` op.
- **Weak signal** (tracked path missing, no content-matching new file) — **deletion-or-loss**. Conformance error routes the human to restore the file (or run post-MVP `jigc doc delete`).

**MVP policy: block, route to revert. No auto-rewrite of refs, no in-MVP rename op.** Same shape as the rest of strict-MVP scope (Pass 2 F5 Auto-repair scope): the conformance error names exactly what's missing; the human resolves it explicitly. The conformance error carries enough detail (old path, new path, matching hash, revert one-liner) that the human can choose between reverting or waiting for the post-MVP op.

**Post-MVP `jigc doc rename <addr> --to <new-addr>`** is a single atomic transaction (transactional like `finalize`): re-key the `file-state` hash · rewrite every referrer ref across the committed store · commit as one logical change. Pinned in [write-commands.md](design/write-commands.md) → Post-MVP verbs with a one-line contract; not designed in detail until the verb is needed. The parallel `jigc doc delete` lands the same way.

- **Doc placements**:
  - **[reconciliation.md](design/reconciliation.md)** — new top-level §"Rename detection" placed after §"The state machine" (since rename is a separate classifier, not a state-machine pair-outcome). MVP scope vs post-MVP table extended to list rename-detection (MVP) and `jigc doc rename` / `jigc doc delete` (post-MVP). §"What reconciliation does NOT do" gains a "No silent rename" line.
  - **[storage.md](design/storage.md)** §"Identity, order, fields, slots, items" — the "Identity is the path" bullet now explicitly distinguishes title-rename (survives, id frozen) from path-rename (identity change, CLI-orchestrated).
  - **[write-commands.md](design/write-commands.md)** §"The verbs" — new "Post-MVP verbs — pinned, not designed in detail" subsection listing `jigc doc rename` and `jigc doc delete` with one-line contracts.
- **Decisions (recommended → chosen)**:
  - **Detection signal = two-tier** (strong + weak), not strong-only. The path-missing-alone case is real (accidental delete, file loss) and deserves its own routing rather than being silently ignored.
  - **MVP policy = block + route to revert**, no in-MVP `jigc doc rename`. Same shape as Pass 2 F5 strict scope; no rushing a CLI op into MVP for a case that hasn't yet caused real pain.
  - **No auto-rewrite of refs in MVP**, even on confirmation. Post-MVP `jigc doc rename` does it atomically by design; MVP is detect-and-route only.
  - **Conformance error content = rich**: old path, new path, matching content hash, copy-pasteable `git mv` revert, forward pointer to the post-MVP op. Enough detail that the human chooses between reverting now and waiting for the op.
  - **Doc placement = split across three docs** (reconciliation primary; storage sharpening; write-commands pin), one-purpose homes per the cross-reference-not-restate discipline.

The cross-pass theme this closes: **storage.md said "identity is the path" and "a retitled H1 changes the title, never the frozen filename-id" — but the disclaimer covered only H1 retitle, not path rename.** The gap is now closed by making path rename an explicit identity-change operation that the CLI orchestrates (post-MVP) and detects-and-routes (MVP).

### Pass 3 #8 — "Never positions" precisely: position-token IDs banned, physical-order serialization fine; workflow body is include-only

Codex's attack: workflow files use a body of ordered `{{include}}` lines, but invariant 3 ([VISION.md](VISION.md) principle #2) says "ordering lives in a separate ordered list of IDs, never in positions." Hand-editing a workflow body to move an include changes structure by position, apparently contradicting the invariant.

The attack is real but it's **a language gap, not a substance gap**:

- "Never positions" was meant to ban **position-token identifiers** — the GSD `01-locate.md`, `02.5-implement.md` rot pattern, where the ID itself encodes order and renumbering breaks every reference.
- Physical-order serialization of an ordered list — where the items carry their own non-positional IDs — is fine. A line move is a reorder; nothing renumbers; cross-refs to `workflow:single-task#locate` keep resolving regardless of include position.
- The pattern is used uniformly: doc instances' repeatable items ([storage.md](design/storage.md): "Order = physical order. Reordering is moving a block — a clean diff move, never a renumber") and workflow bodies' include lines ([workflow-dialect.md](design/workflow-dialect.md)) follow the same shape. Same principle, two surfaces.

There's also **a conformance gap**: workflow-dialect.md said "the body is the ordered `{{include}}`s" without formally requiring that includes are *all* that's allowed. A workflow body with prose interleaved between includes would be ambiguous — is that prose embedded in the workflow, instructions to the agent, both? Two rules close both gaps:

- **Rule E — Language clarification.** [VISION.md](VISION.md) principle #2 and [structural-grammar.md](design/structural-grammar.md) sharpened: "never positions" bans IDs that *encode* order (`01-`, `02.5-` prefixes; numeric positions used as references), not physical-order serialization of an ordered list whose items carry their own non-positional IDs. The clarification names both surfaces (doc instances' items, workflow bodies' includes) so the pattern is recognized as one principle.
- **Rule F — Workflow body is include-only at top level.** A workflow file's body may contain only `{{include: step:X}}` lines, blank lines, and HTML comments (`<!-- ... -->`, for human notes about why a step is included). Prose, ATX headings, other placeholders, or any other top-level content is a conformance error — `workflow-refs.body-include-only`, intrinsic blocking, same tier as the other workflow-refs checks ([validation.md](design/validation.md) → Severity inventory). Step files carry the prose; the workflow file is purely composition. The ambiguity Codex spotted ("is this prose embedded or instruction?") is eliminated by construction.
- **Decisions (recommended → chosen)**:
  - **Approach = both rules** (language clarification + conformance tightening), not language-only or conformance-only. The invariant overpromised, *and* the workflow-body parser contract was loose; both want fixing.
  - **Allowed at body top-level = `{{include}}` lines + blank lines + HTML comments**. Comments are useful (human-readable rationale notes about why a step is included) and survive diffs cleanly. Including them keeps the rule from being so strict that it pushes useful rationale into commit messages or external docs.
  - **Enforcement = extend `workflow-refs` probe**. Adds one row to the severity inventory (`body-include-only`, intrinsic blocking). No new probe; same in-process compose-time check as the other `workflow-refs` rules. MVP count goes 16 → 17 checks.
  - **"How a workflow composes" example label sharpened** — the existing example used `## locate` headings with inline content under each, mislabeled as "A definition." The actual on-disk format uses `{{include: step:X}}` lines per the new Rule F. Label updated to **"Conceptual shape"** with a clarifying note that the on-disk format uses includes; each `##` heading and its content lives in its own step file.
  - **Doc placement = split across four docs** ([VISION.md](VISION.md) principle #2 + [structural-grammar.md](design/structural-grammar.md) for the language clarification; [workflow-dialect.md](design/workflow-dialect.md) for the include-only rule and the example label; [validation.md](design/validation.md) for the severity inventory entry). One-purpose homes per cross-reference-not-restate discipline.

The substantive invariant survives: stable IDs, never renumber on insert/reorder. The language has been sharpened to defend it against the read Codex made; the conformance rule eliminates the remaining ambiguity at the surface where it would have leaked.

### Pass 3 #11 — pack-probe determinism contract (six rules + four meta-finding failure modes; locked now, implementation post-MVP)

Codex's attack: `validation.md` called pack probes "read-only and deterministic by contract," with sandboxing flagged as deferred. A subprocess pack probe behind a JSON contract could call an LLM, hit the network, read time, mutate files, or return inconsistent results — and its findings still feed `validate` / `finalize`. "By contract" is aspiration, not enforcement; the determinism boundary leaks through a surface labeled "deterministic by contract."

Pack probes are post-MVP. MVP ships none. But the rules need to be locked **before** the implementation lands — same forward-binding-rule discipline as Pass 3 #3/#5/#4. If the implementation ships without rules, the rules get retrofitted under pressure.

**Contract locked**: six rules + four meta-finding failure modes, both intrinsic-blocking when they fire.

- **The six rules** ([validation.md](design/validation.md) → Pack-probe determinism contract): (1) no network access (no sockets to external endpoints); (2) no model calls (LLM-free interface); (3) no time/random reads (deterministic randomness seeded by input is allowed); (4) read-only filesystem outside a probe-supplied scratch dir (engine cleans between invocations; no persistent state); (5) bounded resources (engine-set CPU/memory/output limits); (6) JSON-in / JSON-out only (no shelling out).
- **Failure semantics**: every misbehavior surfaces as a **meta-finding** through the standard `finding` shape; engine never crashes. Four modes: **timeout** (probe exceeded time budget), **crash** (non-zero exit, no JSON), **malformed output** (JSON parse failure), **sandbox violation** (blocked network call, fs write outside scratch, etc.). All **intrinsic blocking** — a probe that timed out, crashed, returned malformed output, or violated its sandbox can't be trusted to have validated anything, and a missing finding could mask a real integrity error.
- **Implementation deferred, contract binding.** OS-level sandboxing (seccomp, Landlock, or equivalents) is the post-MVP implementation question; the contract above is the floor it must stand on. When subprocess probes ship, the severity inventory gains a `pack-probe-integrity.*` category mirroring the four failure modes (parallel to the `doc-code.*` placeholder).
- **Decisions (recommended → chosen)**:
  - **Rule scope = six rules**, not a subset (network + model only) or a broader spec (specific syscall lists). The six cover the failure modes that break determinism in practice; specific syscalls are an implementation question for the sandbox tech chosen.
  - **Failure semantics = all four modes intrinsic-blocking meta-findings, engine never crashes**, not advisory + propagation. A probe that failed silently could mask an integrity error; the meta-finding is the audit trail.
  - **Enforcement timing = lock contract now, defer implementation**, not full-deferral. Same shape as Pass 3 #3/#5/#4 — the rules bind the implementation; the implementation lands when the verb is needed.
  - **MVP severity inventory updates = prose only**, not placeholder rows. Pack probes don't ship in MVP; cluttering the inventory with post-MVP placeholders would noise the MVP surface. Rows land when subprocess probes ship.
  - **Doc placement = split across two docs**: [validation.md](design/validation.md) as the contract home (new §"Pack-probe determinism contract" between §"Probes" and §"Severity inventory"); [implementation/module-layout.md](implementation/module-layout.md) §"Probe boundary (in `engine`)" cross-refs the contract as a binding requirement on the subprocess impl.
- **Side effects**:
  - The `validation.md` open-question entry "Pack-probe sandboxing — deferred" is replaced by "Pack-probe implementation — the OS-level sandboxing tech, the concrete enforcement mechanism for the locked determinism contract, and the JSON request/response schema; the contract itself is locked."
  - The same shape lands in `implementation/module-layout.md` open questions.

The contract closes the leak Codex spotted: "deterministic by contract" is now an enforceable spec, not aspiration. The implementation can't ship without satisfying it.

### Pass 3 #16 — bootstrap compaction resilience (routing footer always; resume hook per-assistant capability)

Codex's attack: the bootstrap pointer is the agent's *entire* a-priori knowledge ("run the front door and follow it"), but the hook only runs at session start. Mid-task compaction can drop or dilute the injection — even the static line in `CLAUDE.md` is summarizable away. The agent then resumes without the routing intent. Low severity (state isn't lost, just orientation), but the fix is cheap and lasting.

Two complementary defenses:

- **Routing footer on every CLI output** (universal baseline, no assistant capability required). Every composed workflow / `jigc start` / `jigc task validate` output in **agent-text** and **human-pretty** format ends with a one-line footer: `— jigc · run \`jigc start\` for orientation; all writes through \`jigc\`.` JSON-format output carries no footer (it's consumed by code, not the agent's reading flow). Self-reinforcing: compaction can drop one injection, but every CLI call re-shows the routing pointer. Specced in [workflow-dialect.md](design/workflow-dialect.md#emitted-format) → Routing footer; emitted at phase 9 of the [resolution algorithm](design/overrides.md#resolution-algorithm) after step content (step bodies never author it).
- **Resume / post-compaction hook** (per-assistant capability). The adapter profile gains a `resume` event slot parallel to `SessionStart`. If the assistant exposes a "context resumed" or "compaction completed" event, the adapter re-injects the bootstrap on that event. Claude Code: ships when the API exposes such an event; the seam is designed, no implementation gated on it. Lands in [assistant-adapter.md](design/assistant-adapter.md) → Inject the bootstrap as a third bullet and as a new `Resume` hook line in the profile example.

The two defenses mirror the existing universal-floor + best-available-primary discipline that bootstrap injection itself uses: the footer is the universal floor; the resume hook is the per-assistant strengthening.

- **Decisions (recommended → chosen)**:
  - **Routing footer scope = always in agent-text + human-pretty**, not just long-running outputs. One line is cheap; consistency reinforces. JSON output excluded (it's tooling-consumed).
  - **Footer content = one-line routing reminder** (`— jigc · run \`jigc start\` for orientation; all writes through \`jigc\`.`), not multi-line or richer. Stays within "routing, not content" — names the entrypoint, embeds no rules. Cascade provenance (#15) is a separate header line; the footer is bootstrap reinforcement.
  - **Resume hook design = the seam now, ship when supported**. The profile slot is declarative; assistants without the capability simply omit it. Same shape as the rest of capability-dependent profile entries.
  - **Doc placement = split across three docs**: [bootstrap.md](design/bootstrap.md) is the strategy home (new §"Context compaction resilience" between §"Benefit detection" and §"Placement is the adapter"); [assistant-adapter.md](design/assistant-adapter.md) §"Inject the bootstrap" gains the third bullet + the profile example shows the `Resume` hook line; [workflow-dialect.md](design/workflow-dialect.md) §"Emitted format" specs the footer. One-purpose homes per the cross-reference-not-restate discipline.

### Pass 5 (Area 1, row 22) — absent optional sections generate at their schema-ordered insertion point

Codex (Area 1 yellow): the offset-splice model edits existing byte spans, but a section can be *optional* and therefore **absent** — so `set-slot` into it has no span to splice and the splice model lacked a canonical insertion point for the absent structural home. MVP-relevant via the `commit` doc's optional `body` slot.

- **Rule = one unifying principle** ([parsing.md](implementation/parsing.md) → The write pipeline): *the canonical writer materializes any absent structural home at its schema-ordered position before the leaf write proceeds.* Already true for an absent `set-field` (generate-and-insert); now lifted from leaves to sections — `set-slot` on an absent optional section, and `add-item` on an absent optional repeatable container, generate the `##` home first, then write. Not an error, not a require-add-section-first: sections aren't per-instance structural variation (only repeatable *items* are, [write-commands.md](design/write-commands.md)), so an optional section's absence is just "its slot is unfilled," and first-write materializes it.
- **Insertion point = deterministic from schema document-order** ([storage.md](design/storage.md): schema order = physical order). The writer knows the full schema section list and which are present, and inserts so present sections stay in schema order. No positional ambiguity.
- **Generation scope = the structural home only** — heading + the leaf being written; field groups / sentinel / sibling slots materialize when their own writes land, incrementally. Required-but-absent fields stay a `finalize` integrity concern, not forced at this write. Validate-after-write covers the inserted region like any other edit.
- **Canonical-writer caller count 5 → 6** — `set-slot`-when-section-absent joins the enumeration (parallels the four → five bump logged in the 2026-05-27 MVP thickening for the commit string sink). `add-item` was already a generation caller; the new behavior is that it also generates an absent container.
- **Doc placement**: [parsing.md](implementation/parsing.md) only (the write-pipeline mode table + a new paragraph + the caller enumeration); cross-refs document-type-schema (optional sections) and storage (schema order). No design-doc change — this is mechanism realization.

### Pass 5 #4 — subprocess-probe wire seam sketched; `ctx`-serializable is what secures "zero engine change"

Codex (foreclosed #4, SEV med): the `Probe` trait's "zero engine change" claim for post-MVP subprocess probes was unsupported until the JSON wire contract was at least sketched. Pass 3 #11 deliberately deferred the *full* schema; this resolves the tension by sketching the **seam** (validating the claim) while keeping the concrete schema deferred.

- **The crux is `ctx`, not field names.** The in-process trait is `check(target, ctx) -> Vec<Finding>`. For a subprocess impl to satisfy the *same* trait with no engine change, **`ctx` must be effective-state the engine can serialize** — in-process and subprocess impls consume one logical input (a live graph vs its serialized projection). A `ctx` defined as a live in-memory handle would force a new engine mechanism when subprocess probes ship — exactly the foreclosure. So sketching the wire contract now *constrains the in-process trait's `ctx` design today*; that is the real value, beyond satisfying Codex.
- **Effective-state access falls out of the already-locked six rules.** No callbacks (rule 6) + no network (rule 1) ⇒ the engine **materializes a read-only effective-state snapshot** (rule 4 permits read-only fs) and the request carries a **path-ref**, not a live handle. No new constraint — a consequence of Pass 3 #11's rules.
- **Sketched, explicitly illustrative** ([validation.md](design/validation.md) → The wire contract): `request { probe_id, target, effective_state{snapshot_path}, config, schema_version }` / `response { findings[], schema_version }`. `severity?` advisory (engine owns final severity via cascade); `target` uses the one address grammar; `schema_version` present *as a field* now (the versioning *policy* stays deferred).
- **Still deferred** (honors Pass 3 #11): the concrete finding envelope, versioning policy, snapshot format, and OS sandboxing tech. Decision was **sketch-now** over keep-fully-deferred — the seam de-risks a forward-binding claim, same discipline as locking the determinism contract before implementation.
- **Doc placements**: [validation.md](design/validation.md) → Pack-probe determinism contract gains §"The wire contract" + the MVP-scope and open-question lines retargeted; [module-layout.md](implementation/module-layout.md) probe-boundary bullet + open question cross-ref the seam. The `pack-probe-integrity.*` severity category stays post-MVP (no inventory rows in MVP).

## 2026-05-31

### Address grammar parse/Display + id-hop newtypes (inc 1)

- **Fragment parse is structural by hop-count** — 1 hop = `unit`, 2 = `unit/leaf`, 3 = `unit/item/leaf`. `#unit/item` and `#unit/leaf` are byte-identical, so a schema-free parser yields `UnitLeaf`; the `UnitItem` variant exists in the typed model but is reachable only with schema knowledge. Both render to the same two-hop bytes, so round-trip holds either way.
- **Id hops are thin `String` newtypes** (`Type/Slug/Unit/Item/Leaf`, via a small macro) carrying raw token text verbatim — no normalization on the parse path (slug/minting normalization stays deferred to inc 3/4 per decisions-pending). `Display` writes the bytes back unchanged, giving byte-for-byte round-trip.

### Result envelope: `Orientation`/`Catalog`/`CatalogEntry` + `SCHEMA_VERSION` (inc 1)

- **`schema_version` is a root scalar marker on the result envelope** (`pub const SCHEMA_VERSION: u32 = 1`, stamped by `Orientation::new`), not a per-type or wrapper field — one bump point covers the whole projection, and a contract test pins the exact JSON shape so any rename is intentional.
- **`Catalog` is `#[serde(transparent)]` over `Vec<CatalogEntry>`** so it projects as a bare `workflows[]` array under `Orientation`; entry keys are the verbatim `id`/`when` from the bootstrap orientation example.

### `PackSource` provider trait + `PackResourceKind`/`ResourceId` (inc 1)

- **`PackSource` is a plain object-safe trait** (`pack_version`/`list`/`read`), no serde derives — it's the *input* provider boundary the engine resolves over, not a result type, so it stays off the versioned-API surface.
- **Sketch's `Version`/`Bytes`/`Result` ground out as `String`/`Vec<u8>`/`Result<_, PackError>`** — no new dep (no `semver`); `pack_version` carries the binary version verbatim and reconciliation parsing belongs to the override layer, not this seam. `ResourceId` is a thin `String` newtype (the `address` id-newtype style); `PackError::NotFound{kind,id}` is the only read failure mode.

### `EmbeddedPack` + embedded dev-pack layout (inc 1)

- **Embedded pack tree = `crates/cli/pack/`, one sub-dir per `PackResourceKind`** (`workflows/` `schemas/` `steps/` `config/`); a resource's `ResourceId` is its **file stem** (so `workflows/single-task.yaml` → id `single-task`). Embedded whole via `include_dir!("$CARGO_MANIFEST_DIR/pack")`; `list`/`read` resolve the kind→sub-dir then match/strip the stem. `pack_version` = `env!("CARGO_PKG_VERSION")` (built-in pack-default version = binary version).
- **Inc-1 ships a minimal `single-task.yaml` stub** (id + `when` only) so the catalog is non-empty and `read` returns non-empty bytes; the full workflow definition (steps/slots/`allows-create`) lands in inc 3. `EmbeddedPack` is `#[allow(dead_code)]` until the cascade-location task wires it into `main` (later in inc 1).

### Workflow-metadata catalog builder: parse `when` from front-matter (inc 1)

- **`engine::catalog::build_catalog(&dyn PackSource) -> Result<Catalog, CatalogError>`** derives the catalog: per `Workflows` resource it reads the bytes, slices the leading `---`-fenced front-matter, and `serde_yaml_ng`-parses *only* `when` (a `WorkflowFrontMatter { when: Option<String> }` — extra config-family keys like `allows-create`/`creates-task` are ignored, not rejected, so richer inc-3 defs don't break the catalog). Entry **id is the `ResourceId`** (filename stem), never a front-matter field — per workflow-dialect "the id is the filename". Order = the pack's `list` order.
- **Missing `when` (or absent/blank) is a hard, id-bearing `CatalogError`, not a silent skip** — a workflow earns its catalog place by declaring its hint, so a missing one is a definition bug. `CatalogError` (thiserror) also covers NotUtf8 / MissingFrontMatter / MalformedFrontMatter. Front-matter detection reads the canonical LF form (`---\n` … `\n---`), matching the writer's LF default.
- **`serde_yaml_ng` opted into `engine` deps** (pre-declared load-bearing crate; no new external dep). Note: the embedded `single-task.yaml` stub is still pure-YAML (no fences) from the inc-1 pack task; aligning it to the canonical fenced-front-matter form is left for the wire-up/inc-3 step — this task is engine-only (fake `PackSource`), so the stub mismatch is latent, not active.
