# Working principles

Rules of judgment the human has set that hold across every workflow — design, dev, increment, milestone, stabilization — and that no single workflow doc owns. Each is one section: the rule, why it holds, how it is applied, and the `DECISIONS.md` entry that set it. A rule that belongs to one workflow lives in that workflow's doc, never here; a rule here is pointed at, never restated.

## Neither the doc nor the code is the oracle — the behaviour that makes sense wins, and whichever is wrong changes

**The rule.** A question of what the product should do — a doc is silent, says two things, allows what a sibling command or the project's invariants contradict, or disagrees with the code — is judged on the **behaviour first**: what makes sense for a user, the architectural invariants, the exit rule, how the sibling commands behave. Only then does it name which of the doc, the code, or both is wrong, and that one changes. Neither *"the doc catches up with the code"* nor *"the code obeys the doc"* is an answer on its own, and readings are not chosen so that every sentence already written, or every line already built, stays true.

**Why.** The design docs were written one milestone at a time, and a sentence often records a local fix: true when written, narrower than the rule it sits beside. The code is the same kind of record. Taking either as the oracle freezes a local fix into a rule and loses the project's general invariants — writes are transactional, a refusal changes nothing, a conflict is blocked and routed and never silently merged, one command behaves as its siblings do ([VISION.md](../VISION.md), [CLAUDE.md](../CLAUDE.md) → Architectural invariants).

**How it is applied.** It binds every agent that judges — triage, verify, the robust advocate, and the builders and fixers of a test table — and the orchestrator. A question put to the human leads with the robust end state: what the product *should* do by the project's general principles, then which of the doc and the code would change (a finding, routed like any other), and only then the readings. A finding may be against the doc, the code, or both, and says which. A test or table built before the ruling follows the stricter reading and marks the cell, as it does today.

## Deterministic first — what a script or test can establish is checked there, before an agent judges, hunts or builds; and an agent's tools are handed on

**The rule.** In the human's words: *jigc is deterministic, so many things can be checked by a script or tool; whatever a script or test can establish is checked there first, before an agent judges, hunts or builds. The tools and scripts exist to support the agents in their work. But tools can be incorrect: an agent that suspects a bug in a tool investigates it and reports it as a finding with its evidence — it neither works around it nor trusts it blindly.* And their addition, on the tools agents make: *agents tend to create scripts in the scratchpad, and the next agent builds a similar tool — total waste.* So **every agent says, at the end of its work, what script it wrote and kept using, or what tool it needed and did not have**, and **the orchestrator triages each into the candidates list** of [tooling.md](tooling.md) — to be built into `dev/` with its tests, or declined with the reason.

**Why.** A tool nothing points at is a tool that gets rebuilt — [CLAUDE.md](../CLAUDE.md) records it for the trial corpus template, and it held in general: the route hunter was put to the human as owed when the route catalog, a deterministic instrument of this repository, had grown to cover most of what the hunter was for, and the agents that found the tools found them by grep, each from its own task's angle. An agent's judgment is the expensive and the variable instrument; a script's answer is cheap and the same every time. And a scratch script dies with the agent that wrote it, so the next one pays for it again.

**How it is applied.** Before an agent judges a question, hunts for a defect or builds a tool, it looks in [tooling.md](tooling.md) — one row per tool and deterministic instrument, the question each answers — and uses what answers its question. A tool's answer is evidence, not an oracle: a suspected bug in one is investigated and reported as a finding with its evidence, never silently worked around. An agent that wrote a script or probe it ran more than once, or needed a tool that does not exist, says so under **Tools** in its report, or in its return where it writes no report — what it does, the question it answers, and its text if it is short. The orchestrator triages each into the candidates list; a candidate built is a row like any other, in the commit that builds it. Every agent definition carries the one paragraph that says this, and `tooling-tests/tooling_index.rs` holds the paragraph and the index.

## What we will need again lives in the repository — never only in a scratch directory or elsewhere on the machine

**The rule.** In the human's words: *"We should track plans in the repository and not somewhere else (general thing). I know agents tend to put things in scratchpads or somewhere else on this computer but then the things are gone. That's fine for testing things out but in the end it needs to come into the repo and not somewhere on the machine where it will be forgotten or be deleted!"*

**Why.** A session's scratch directory is removed by a restart, and a folder elsewhere on the machine is forgotten, or lost with the machine. The stabilization workflow's build kept its plans, their versions and reviews, its briefs and the opening's draft fact sheet in a folder outside the repository and in the scratch directory, and its scratch was copied out by hand before a restart, 786 files in all; a build plan of that week had already planned two tools around *"two scratch scripts [that] still exist in the session scratchpad"*. What is not in the repository is not shared, reviewed, versioned or found again.

**How it is applied.** Scratch is for trying things out. **Before the work that made it ends** — and always before a session can end — everything someone will need again is in the repository: plans and every version of them, the reviews of each, briefs, fact sheets, measurement tables and scripts run more than once, each in the record directory of the work it belongs to under `completions/artifacts/`, or in the doc that owns it. A script that is not built into `dev/` goes in as text beside its record, with a row in [tooling.md](tooling.md) → *Candidates* (→ *Deterministic first*, above). What can be made again is not kept: a clone of the repository, a rig, build and CI output (a CI run is recorded by its id), a draft whose final form is committed. Every kept file is sanitized first, because the repository is public: no host path, no session or agent id, no person's name, no environment variable's value, never a raw transcript ([public-hygiene.md](public-hygiene.md)). An orchestrator that hands a builder a brief or a plan writes it where it will be kept, or brings it in at the work's end.

## What we write takes the shape of the jigc doctype that would hold it — and where our need does not fit, the misfit is a finding

**The rule.** In the human's words, of the plan before the stabilization run's opening: *"That will basically be a file that jigc can hold later. So we should use the rules we have there to reformat that doc! That's what we always should do — we do something, improve it and use it later for jigc."*

**Why.** This repository is jigc's first real corpus: the port migrates it onto jigc, under the rule that the project is migrated to fit the product, never the product bent to fit the project ([CLAUDE.md](../CLAUDE.md) → Project state). A document written now in the shape jigc would hold it in is one the port takes as it is; one written in a shape of its own is a rewrite owed later, or a pressure to bend the CLI. And writing it in jigc's shape tests the shape — what does not fit is learned now, as a finding, not at the port.

**How it is applied.** A document we write takes the shape of the doctype of the methodology pack that would hold it ([design/methodology-docs.md](../design/methodology-docs.md); the `milestone-record`, [design/team-ready-state.md](../design/team-ready-state.md)):

- **a plan** — the `roadmap` doctype's entry: a title, what it proves, and its decomposition as prose, one level;
- **progress** — the `milestone-record` doctype: a base, a status, and the ordered tasks, each with its id, its intent, its workflow and its status;
- **a plan's gate answers** — the `planning-record` doctype: each of its gates answered with its evidence, or N/A and why.

**Checked with jigc itself**: the document is authored through jigc in a throwaway repository — [`dev/jigc-rig`](../dev/jigc-rig) builds one — and the rendered shape is what we write. **Where our need does not fit a doctype, the document does not bend**: the misfit is a `jigc-feedback` row in [the seed ledger](../completions/artifacts/M55/seed-ledger.md), in that ledger's own grammar, for the port to triage — a finding, never a requirement. Where a document lives does not change: a record under `completions/artifacts/` stays a plain file (the port's recorded direction keeps that tree plain), and it still takes the shape.
