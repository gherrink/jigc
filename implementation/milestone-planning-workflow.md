# Milestone planning workflow (scope → detect gaps → settle → review → decompose)

The loop for **opening a milestone** — the *planning* half of the milestone lifecycle, the bookend to [milestone completion](milestone-completion-workflow.md). Before a milestone's increments can be built, the milestone is **scoped against the full-product roadmap, adversarially checked for gaps, those gaps settled, and the milestone cut into ordered increments**. This doc owns only that opening; building the increments is the [increment workflow](increment-workflow.md), and auditing the finished whole is [milestone completion](milestone-completion-workflow.md).

It completes the set: [design](design-workflow.md) governs a *decision*, [dev](dev-workflow.md) a *task*, [increment](increment-workflow.md) an *increment*, **this one the opening of a milestone**, and [milestone completion](milestone-completion-workflow.md) its close — the `milestone > increment > task` hierarchy ([structural-grammar.md](../design/structural-grammar.md) → Work-units), bracketed end to end. Running it by hand now is the dogfood for the product **`milestone-planning`** workflow we will eventually compose.

## Where this sits: the product-build loop

The whole product is built on one loop, run once at the top and then repeated per milestone:

> **once:** full-product [roadmap](roadmap.md) (milestones only) → light doctype/relation map
> **per milestone:** *this workflow* (plan) → [increment workflow](increment-workflow.md) × N (build) → [milestone completion](milestone-completion-workflow.md) (ship) → repeat

The discipline that makes the repeat honest: **plan increments for the *next* milestone only**, never all milestones up front — the same rule the roadmap applies to tasks (`roadmap.md` → "tasks are cut per-increment when that increment is picked up, so the list stays honest against what the prior increments actually produced"), lifted one level. A milestone's real shape is only knowable against the state the prior milestone actually left behind.

## Why detect gaps first (planning isn't just decomposition)

Decomposing a milestone into increments assumes you know *what* it builds. Often you don't yet — the milestone needs a design decision that's still open, a doc that doesn't exist or has gone stale, or a doctype whose schema no prior workflow has driven. Cutting increments over those holes produces a plan that halts mid-run (the [increment workflow](increment-workflow.md) → *Precondition: settle the gates first* is where an unsettled gate becomes a halt). So planning runs an explicit **forward-looking** pass — symmetric to completion's backward-looking audit — that finds the holes *before* they become halts.

This is also where the **doctype contract gets set at the right moment**: a doctype's fields, slots, and cross-references are determined by the workflow that creates it and the one that reads it. The milestone that ships those workflows is exactly when its doctypes earn their schema — not before (defining a schema with no driving workflow is generality for a single-use thing, [PRINCIPLES](../PRINCIPLES.md) → Keep it minimal).

## The loop (one milestone)

1. **Scope** — restate, from the full-product [roadmap](roadmap.md), what this milestone *proves* and its risk-first place in the sequence. Establish the done-picture: the runnable slice it must deliver and the worked-example flow(s) that will demonstrate it. This is the bar everything below is measured against. **And verify the baseline it builds on:** the done-picture is the target, but the milestone also has a *starting point* — what prior milestones actually shipped — and the roadmap's "shipped" prose is a claim, not proof (trusting it is what cost M3 three build halts). **The roadmap's framing of *this* milestone's difficulty is a claim too** — a "design-locked / planning-light / trivial-addition" entry is exactly the framing that suppresses the spike instinct, so it must *raise* baseline-audit intensity, not relax it: run the full capability-auditor pass regardless of how easy the roadmap makes the milestone sound (M10's "the trait shipped, add the subprocess impl" and M11's "design locked, planning is light" were *both* overturned by the spike — the trait was the wrong shape; the cascade substrate was entirely net-new). So Scope also produces a **verified capability ledger** — what is genuinely built *proven by exercising it*, plus the known stubbed / deferred / latent gaps — established by delegated recon (subagents that exercise the real binary, not the orchestrator reading code). The ledger is the factual ground *Detect gaps* measures against; it is a verified-at-this-sha map, not gospel, so the gap pass still spikes each new shape. Doing this once per milestone, at its start, is cheaper than discovering a hollow baseline mid-build. **And the baseline must exercise the milestone's genuine value-delivering end-to-end flow on the real binary — not only the surface the milestone will *change*.** The auditors reflexively scope to "what this milestone touches," but a milestone's *value* usually rides a flow it leaves largely unchanged, and a pre-existing break *there* surfaces as a completion-e2e surprise instead of a plan-time finding. So name the one genuine end-to-end flow the milestone claims to make real and **drive it through the binary at Scope**: either it is broken-and-in-scope, or it is a pre-existing finding surfaced *now* (plan-time, where it can be scoped or split deliberately) rather than at the milestone audit. (M31: the milestone's whole value is *real* fan-out, but the genuine `jigc workflow sub-task --task <id>` authoring re-entry was broken — the baseline audited only the code-isolation substrate M31 would change, so the break surfaced at the completion e2e and split late to M32; driving the genuine fan-out flow at Scope would have surfaced it a phase earlier.) **And pull this milestone's deferred topics first:** before fixing the done-picture, read [decisions-pending.md](decisions-pending.md) → *Before planning* for the entries keyed to this milestone — the discussion topics earlier work parked "to settle before milestone N." Fold them into the done-picture and the gap list so a long-ago deferral is resolved *now, at its trigger*, not rediscovered mid-build or quietly forgotten (the failure this log exists to prevent: a topic we promised to revisit before a milestone, lost because nothing resurfaced it at the milestone).

2. **Detect gaps** — a forward-looking, **adversarial** pass over the milestone's done-picture against the assembled product: what is *missing or unfit* to build it cleanly. Categories:
   - **Decisions** — the forward look in [decisions-pending.md](decisions-pending.md): each `(D)` this milestone forces, plus any cross-cutting one due before it.
   - **Docs** — design part-docs the milestone needs that don't exist, or that drifted as earlier milestones changed reality.
   - **Doctypes** — types this milestone's workflows will create or read, whose schema is not yet defined (consult the [doctype map](doctype-map.md) for what's coming and how it connects).
   - **Capabilities & open questions** — engine/CLI surface the milestone assumes, and any part-doc `## Open questions` that block planning.

   Two hunts run **across** every category, not as a fifth one:
   - **Cheap-vs-robust.** Where the plan — or a "ready cut" inherited from a fixer — leans toward the low-effort path, ask whether it is the *robust* solution to the real problem or a discount that ships a fragility, guarantees a rework milestone, or is a **regression-in-disguise**. Minimal is the smallest *robust* solution, not the least effort ([PRINCIPLES](../../PRINCIPLES.md) → Keep it minimal); the cheap path is a fork to surface *with its long-run cost*, never a silent default. The discriminator keeps this from becoming scope-creep: building for a *hypothetical future* need is premature generality (defer); doing the harder correct thing for a problem the scope *already has* is just solving it (do). (M30: the ready 3-task cut narrowed the squash path the cheap way — a data-loss regression that dropped sub-agent code; the robust fix was the worktree redesign, more work but the actual minimal-correct solution, split to M31. It took a human push to surface the fork — the gap pass should surface it unprompted.)
   - **Foreclosed-by-doc.** A doc/decision the milestone leans on can block a *clearly better* solution, or rest on a basis that has changed. Don't treat it as a wall — surface it as a fork (the *proactive* form of Settle's "question the doc, don't bend"; engage its rationale, don't just obey). (M30: the 2026-06-04 "no worktrees" decision foreclosed the robust code-isolation path until questioned — its rationale held, but its *scope* was reopenable.)

   Output: a ranked gap list, each gap concrete enough to act on.

3. **Settle** — *the human-in-the-loop step.* For each blocking gap, resolve it through the right loop and **record it**: decisions via the [design workflow](design-workflow.md) → [DECISIONS.md](../DECISIONS.md) (graduating the `(D)` out of the pending list); docs/doctype schemas elaborated via the [design workflow](design-workflow.md) where this milestone's workflows now drive them. **Surface genuine scope and judgment calls** rather than silently deciding them — must-settle-now vs. defer-to-a-later-milestone; whether a gap warrants building machinery at all; **and, where the plan leans cheap, the cheap-vs-robust fork with its long-run cost** (minimal = smallest *robust* solution, not least effort — [PRINCIPLES](../../PRINCIPLES.md) → Keep it minimal; reaching for the cheaper path silently is the lazy failure this gate exists to catch). The human owns this gate. A gap consciously deferred is **logged in [decisions-pending.md](decisions-pending.md) → *Before planning*, keyed to the milestone that will own it** — not forgotten, and not left as DECISIONS prose with no trigger (that is the write side of the same ledger Scope reads; a deferral with no trigger is a deferral that evaporates).

   **Settle's own design is a claim, not a fact** — the same *exercise-don't-infer* discipline the baseline ledger applies, now applied to the design *this phase writes*. The traps the audits charged to this phase:
   - **Pin the scope of every check the design introduces.** A new validation/finding ("an orphaned slot-fill is blocking", "a dangling ref blocks finalize") is under-specified until you state *against what surface it fires* — the composed workflow? the target unit? the whole store? An unscoped check is a fork the build will resolve *for* you, often wrong (M4's `slot-fill-orphan` was settled as "M4 owns it" but its scope — composed-workflow vs target-step — was left open, and the build picked the front-door-bricking reading).
   - **Spike every acceptance flow against the real engine before locking it.** A worked-example flow that becomes the milestone's acceptance test silently encodes assumptions about engine behaviour ("`{{include:}}` expands in place", "this composes in that order"). *Exercise the claim* — a quick spike against the real binary, or a read of the path that confirms it — before writing the flow as the bar. M4's flow-3a assumed in-place include expansion the engine didn't have; written on faith, it shipped as a defect. Treat an acceptance-flow assumption like a reuse claim: unverified until exercised.
     - **The flow's *invocation commands* are claims too — not just the outputs it asserts (M8).** A `$ jigc …` line in an acceptance flow encodes a **CLI-surface** claim (the verb exists; those flags combine) as much as its asserted output encodes an engine-behaviour claim. Spike the *commands* against the built command grammar — run them, or read the clap `conflicts_with` / verb set — not only the behaviour they exercise. M8's flow-10 wrote `jigc start --workflow … --task …` while `start` had `--workflow conflicts_with --task` *reaffirmed in the same Settle*; the contradiction surfaced only when the build-planner halted at it, because the spike was applied to what the flow *asserts* and not to what it *runs*. One `jigc <the exact flow command>` at Settle moves that catch a phase earlier (from a build halt to a Settle fix).
   - **Don't price a fork you haven't spiked.** When you surface an option to the human — here, or in [completion](milestone-completion-workflow.md) triage — the cost/scope you attach to it ("~10 lines", "additive", "low-risk") is *itself* an unexercised claim. Verify it, or label the scope **unverified**, so the choice prices in that uncertainty. (M6 triage: a "~10-line" hardening option in fact forced *every* pack — incl. all test fixtures — to declare the full intrinsic knob surface; caught cheaply by the gate, but the estimate was false precision that shaped a decision.)
   - **Spike the integration seams, not just the novelty.** Adversarial energy gravitates to the scary *new* thing and skips the boring seam where it meets *proven* code — and that seam is exactly where the gap hides. When the design says "feed into / reuse the existing `<transaction/path>`" (finalize, the cascade, the edge index, a doctype's read path), confirm that path's **input preconditions are satisfied by the new producer** — don't assume the existing machinery accepts the new shape. This is the *reuse-is-a-claim* discipline turned on integration, not capability: same failure, one altitude in. (M7's *only* halt was here — inc-4 "feed the merged overlay into the existing finalize transaction" assumed finalize would render a commit message, but a milestone has no commit doc; the precondition mismatch surfaced at the increment's Plan instead of at Settle. The same shape recurs: M3's create-gate hardcoded `single-task`, M4's "existing resolver" was unwired, M5's probe re-read the wrong layer.)
     - **A new *rule* has more than one application site — census them all at plan time (M14).** The integration trap's sibling: when the milestone introduces a *resolution/behaviour rule* (not just a producer feeding one existing consumer), the failure is applying it to the **primary/front-door** site while a second, boring site performs the *same* operation unchanged. The novelty draws the eye; the duplicate entry point hides. So when a rule governs an operation, **enumerate every code path that performs that operation** — not just the one the worked example walks — and make each an explicit increment scope-bullet + acceptance. (M14's pack-local body-reference rule landed on the *fresh-compose* front doors but not the *resume/re-entry* spine `compose_task_workflow` — a second compose path nobody enumerated — so resuming a loser-pack workflow silently composed the precedence-winner's bodies; the milestone audit caught it, but a plan-time "how many compose entry points are there?" census would have caught it a phase earlier. The baseline ledger mapping `make_pack()` *call sites* is not the same as mapping *compose entry points* — census the operation the rule governs, not an adjacent surface.)
     - **The census extends from *rules* to *properties* — and is a REQUIRED Settle output, not a hunt that may or may not fire (M31).** A property the milestone *establishes* — WIP-safety, hook-execution, determinism, byte-stability, idempotency, no-data-loss — has the same multi-site shape as a rule, and the same blind spot: secure the headline path, coast on its sibling. So for **every property the milestone establishes**, write the census down as a Settle artifact — `property → { every path that must uphold it } → { acceptance per path }` — where the path set is exhaustive across the obvious siblings (the *other* knob value, *re-entry* vs *front-door*, the *abort* path vs the *success* path). A property asserted on one path and silent on its sibling is an unscoped fork the build resolves for you, and it resolves it by reaching for the *old* pattern. Making this a written table (not prose the gap pass might surface) is the forcing function — the same lift that turned `cheap-vs-robust` from prose into a required tag. (M31: review S2 established WIP-safety for the squash:**true** combine — off-line build, never `git reset --hard` the live checkout — but the squash:**false** sibling was planned with live-apply + reset-on-abort, re-introducing the exact data-loss hazard S2 had just killed; it was the milestone's *only* escaped defect. A plan-time census — *WIP-safety → {squash:true, squash:false} → acceptance each* — catches it before a line is written, and the same row would have caught the hook-execution property the build-halt caught instead.)
   - **A pre-existing locked doc you build *around* is a claim too — if satisfying it forces a contortion, *or if a clearly better solution exists that the doc forecloses*, question the doc, don't bend.** Settle elaborates the docs this milestone *drives*; it must also be willing to question the docs it merely *leans on* — and not only when there is friction: a doc that "works fine" can still be blocking a more robust architecture, and obeying it on faith is the same lazy failure as taking the cheap path ([PRINCIPLES](../../PRINCIPLES.md) → The record is rebuttable). **Whichever response below, engage the doc's *rationale*, not just its conclusion** — show the new path serves the same intent, or consciously override it with the *why* recorded; that rationale-engagement is what separates a principled revision from churn (and from a reckless rewrite of a load-bearing rule). When the clean resolution keeps fighting an existing rule (a cascade invariant, a schema constraint, a design-doc decision), that friction is **signal, not an obstacle to engineer around** — the rule may be an early-milestone simplification meeting a shape it wasn't cut for, not a law. Graded response: **elaborate** the doc to cover the new shape within its existing model (the normal case — most frictions); **revise** a locked design-doc decision when the model itself is wrong for where the product is heading (legitimate — record the *why* in DECISIONS, and treat the revision's own design as a claim like any other); **revise VISION** only in special cases (its invariants are load-bearing — a VISION change is a deliberate, flagged event, never a planning convenience). The tell between *bend* and the right move: a bend pulls the mechanism off its natural home to satisfy the rule, while the model-consistent path usually already exists. (M11: the scalar-knob path pulled authored `description:`/`usage:` prose *off* the definition into the knob surface purely to dodge whole-file shadow — the bend; whole-file definition shadow, the same way steps already resolve, was the model working as designed, and `overrides.md` needed only a one-paragraph elaboration. Reach for *revise* when the contortion **recurs across milestones**, not on first contact — one near-miss is absorbed by elaboration, and the latent pressure is logged with a trigger in case it returns.) (M30 is a clean *revise* exemplar: the 2026-06-04 "fan-out isolates by directory, **not** worktrees" decision foreclosed the robust code-isolation fix. Questioned, its rationale — *never let git text-merge structured managed docs* — was found to **still hold** under the new design (docs stay on the CLI by-task-id join; only *code* uses worktrees, disjoint-applied or blocked, never git-merged), so the *scope* was reopened by an explicit DECISIONS amendment and the worktree path scheduled as M31 — a rationale-honoring revise, neither a bend nor blind obedience. It surfaced only because a human pushed; the gap pass's *foreclosed-by-doc* hunt should raise it unprompted.)

   **For an off-substrate milestone, also review the harness itself — forward.** When the milestone is genuinely novel — *not* riding the proven substrate (M4–M6 rode the override/validation theme; M3 and M7 did not) — run a forward-looking adversarial review of *our own gates* during Settle, scoped to the milestone's novel risk: *"what failure class could our green gates still pass that we've never personally hit?"* Every hardening we have is a reactive post-mortem of a failure already eaten; on novel ground this is the one move that names a new failure class *before* the build instead of at the audit ([self-hosting.md](../design/self-hosting.md) → the graduation pass, part 4 — run **per-novel-milestone**, not once). M7 ran it during Settle and it named the concurrency-determinism class — *single-execution determinism trust*, now [increment-workflow.md](increment-workflow.md) hardening #7 — *before* inc-3 built; the join was then held to it and passed, and the milestone audit found no new concurrency-class shape. Substrate-riding milestones **skip** this — the existing gates already cover their shape, so the pass would only re-confirm.

4. **Review** — an **independent** pass over what *settle* produced. A separate agent that **did not author** the decisions, docs, or doctype schemas reads them adversarially for coherence, gaps the first pass missed, over- or under-design, and conflicts with the locked invariants ([CLAUDE.md](../CLAUDE.md), [VISION.md](../VISION.md)). The same-model [`design-reviewer`](../.claude/agents/design-reviewer.md) is the **always-on baseline** — hardened against the blind-spot classes it has demonstrably shared with the author (bound-vs-deferral conflation, hidden circular co-dependency; its prompt). A **cross-model** second opinion (e.g. `/review-codex`) is a **human-approved *suggestion*, never auto-run**: it has empirically caught **blocking** items the same-model pass blessed (2026-06-06: M10's contract-vs-sandboxing conflation + the M12↔M14 circularity), so **suggest it for high-stakes calls** (milestone-creation, a load-bearing scope bound) — but it costs and isn't universally available, so **the human decides whether to run it**. Findings from either pass are **baked back into the docs** through the [design workflow](design-workflow.md) *before* anything is decomposed: a settled doc that survives an adversarial read is a sound basis for increments; an unreviewed one propagates its flaws into every increment cut from it. The human owns accepting or rejecting each finding — the same gate as *settle*.

5. **Decompose** — cut the milestone into ordered, **risk-first** increments straight from the (now reviewed) scoped done-picture, each carrying its *Deliverable* / *Grouped scope* / *Proves* and naming the design docs it builds against — the form the [increment workflow](increment-workflow.md) consumes. Keep the cut **minimal**: the smallest sequence that delivers the milestone, no creep into a later one. The spine stays linear — each increment builds on the last. Record the increments in the [roadmap](roadmap.md).

The milestone is **planned** when its blocking gaps are settled (or consciously deferred), the decisions/docs/doctypes it needs are in place and have survived an independent review, and its increments are cut and ordered in the roadmap — ready for the [increment workflow](increment-workflow.md) to build the first one.

### The plan-time gate-record (where the recurring forcing-functions live)

The recurring plan-time failure-classes — *reuse-exercised · cheap-vs-robust · foreclosed-by-doc · census (rules **and** properties) · integration-seam · check-scope-pinned · acceptance-spiked · value-flow-exercised* — are consolidated as a **required gate-record**, specified pack-shaped in [methodology-docs.md](../design/methodology-docs.md) → The planning gate-record (a required slot per gate, presence-enforced, judgment-content agent-authored — never scored). The worked instances scattered through *Scope*/*Detect gaps*/*Settle* above are the **rationale** for each gate; the gate-record is the forcing function that points at them. **Accretion discipline:** a new plan-time lesson is added as a **new gate-row** (+ a one-line rationale pointer), not as another inline paragraph here — this doc keeps the worked instances as the *why* and stops growing the *checklist* prose. (Until the planning workflow is pack-encoded, the gate-record is run by hand from that table; the live encode is deferred behind external proof — [DECISIONS.md](../DECISIONS.md) → 2026-06-21 Direction.)

## Orchestration

Run as the **`/milestone-plan <id>`** command — the runnable overlay of this loop. Unlike the build loops (the `milestone-build` *workflow*, which runs autonomously and halts on the rare fork), planning is **human-led**, so it is driven from the **main session** as a conversation: the autonomous bursts delegate to subagents (a fanned-out baseline-ledger recon (`capability-auditor` ×N over the built surface) in *Scope*; `gap-detector` ×4 in parallel for *Detect gaps*; `design-reviewer` for *Review*), while **Settle** and **Decompose** stay inline with the human. A background workflow is the wrong vehicle here — its center of gravity is settling forks, which is irreducibly the human's. The vehicle matches the work: a *workflow* for autonomous loops, a *command* for human-led planning.

## Why this shape

- **Gaps before increments.** Decomposing over an unsettled decision or a missing doc produces a plan that halts mid-build. Finding the holes first is what lets the increment loop run unattended — a settled gate is implemented, an undiscovered one is a stop.
- **Reuse is a claim, not a fact.** The gap pass's most dangerous miss is "this capability already exists, the milestone just reuses it" — reasoned by analogy from a *proven* path to the milestone's *new shape*. The operation usually does exist; the gap is the shape it's applied to (a repeatable section where the proven path read a slot, a second workflow where one was hardcoded). Such a claim is **unverified until the new shape is exercised** — a spike against the real binary or a read of the path's code confirming it branches for the new shape — and an unverified reuse claim is a blocking gap, not a covered one. (M3 lost three build halts to analogy-reasoned reuse; the gap-detectors now spike instead.)
  - **The new shape includes its *cold-start* state — spike the empty/freshly-created form, not a conveniently-populated fixture (M13).** A write/authoring primitive (a `create`/mint verb, a setter, a writer) has two states, and the defects live in the *first*: the **empty, freshly-created** structure before it is filled. Spiking the primitive in a *populated* state — `add_item` round-tripping an item that already carries its fields, `set_item_field` targeting a field bullet that is already present — confirms the operation exists and branches for the new shape, yet says **nothing** about the create→fill *seam*: the parser records an empty slot/field span *without* canonical surrounding blanks, the fill verb has *no present bullet* to splice into, and the mint verb's empty output must itself round-trip. So when the milestone authors a new structural shape (a new doctype, a repeatable section, a new write verb), the spike must exercise the **real composition in its cold-start state — create empty → it round-trips → fill one leaf at a time → each intermediate round-trips** — because the populated fixture is precisely what hides it. (M13's spike proved the *pieces* (a filled-item round-trip, a present-field splice) but never the mint-empty→fill seam, so the two create→fill defects — an absent item-field with no generation path, and non-canonical byte output from an empty span — surfaced as **build halts** instead of plan-time spikes; a third, the same defect on an empty *leading* slot, surfaced at the milestone audit.)
- **The design Settle writes is a claim too.** The gap pass exercises *reuse* claims; Settle must exercise its *own* — a check it adds without pinning the surface it fires against, or an acceptance flow that asserts engine behaviour nobody ran, is the same unverified-claim failure one phase later. Both M4 audit defects trace here: an unscoped check the build resolved wrong, and an acceptance flow written on a false engine assumption. Exercise the design's claims before review, not after the build.
- **The human owns settling.** Which gaps block now vs. later, and whether a gap deserves machinery at all, are decisions, not mechanics — they surface, never get silently picked ([CLAUDE.md](../CLAUDE.md) → design decisions are surfaced to the human).
- **Review before decompose, not after.** The increment plan inherits every flaw in the docs it's cut from, so an independent, adversarial read of the settled design — folded back *before* decomposition — is far cheaper than discovering the flaw mid-build. The author can't grade its own design, the same reason completion's audit and the increment validator are independent.
- **Next milestone only.** Planning all milestones up front plans against state that doesn't exist yet. The roadmap holds the milestone *spine*; this workflow turns exactly one milestone into increments, when it's picked up.
- **It is the design and increment workflows' customer.** Settling delegates to the [design workflow](design-workflow.md); decomposition feeds the [increment workflow](increment-workflow.md). This doc owns only the scope, the gap pass, and the cut around them. Cross-reference, never restate.
