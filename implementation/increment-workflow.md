# Increment workflow (plan → execute → validate → fix)

The loop for **building one increment** of the MVP — how a whole [roadmap](roadmap.md) increment goes from "not started" to "validated and committed." It is the **outer** loop that orchestrates the [dev workflow](dev-workflow.md) (the inner, per-task TDD loop) across every task of an increment, then **independently validates** the result against the roadmap and **fixes until clean**.

Five loops, five homes: [design-workflow](design-workflow.md) governs *decisions* (discuss → converge → write); [dev-workflow](dev-workflow.md) governs a *single code task* (scope → red → green → refactor → gate → commit); the [milestone-planning workflow](milestone-planning-workflow.md) *opens* a milestone (scope → detect gaps → settle → review → decompose); **this doc** governs a *whole increment* (plan → execute → validate → fix); and the [milestone-completion workflow](milestone-completion-workflow.md) is the outer one that, once all of a milestone's increments are built, independently audits the whole assembled milestone and remediates before it ships. Like the dev loop, it is shaped as named, ordered phases on purpose — it maps onto the planned `milestone > increment > task` work-units ([structural-grammar.md](../design/structural-grammar.md) → Work-units): the increment is "the unit `milestone-planning` decomposes a milestone into," so running this by hand now (and its [planning bookend](milestone-planning-workflow.md)) is the dogfood for the `milestone-planning` workflow we will eventually compose.

## Precondition: settle the gates first

**Before an increment runs, the genuine design decisions it forces are decided and logged.** [decisions-pending.md](decisions-pending.md) is the forward look — each `(D)` it carries for the increment (and any cross-cutting one due before it) is resolved *up front*, recorded in [DECISIONS.md](../DECISIONS.md), and graduated out of the pending list. Only then is execution autonomous.

This is the discipline that lets the loop run unattended without violating [CLAUDE.md](../CLAUDE.md)'s rule that **design decisions are surfaced to the human, never silently picked**. A gate decided in advance is a gate the executor *implements*; an undecided gate hit mid-run is a **halt** (below). The complement holds too: *doc-elaboration pins* — the concrete on-disk form a locked doc leaves illustrative (canonical byte layout, task working-area files, edge-index format, injection markers) — are **made and logged by the executor**, not halted on, because they are elaborations *within* a settled spec, not open forks.

## The loop (one increment)

1. **Plan** — cut the increment into ordered, **single-concern tasks** straight from the [roadmap](roadmap.md) increment (its *Deliverable* / *Grouped scope* / *Proves*) and the design docs it names. Each task carries an **observable done-criterion** (a named test that passes, or a command that exits clean with asserted output) — the same bar the dev loop's Scope step demands, set here so every task has a real red step. Keep the cut **minimal**: the smallest set of tasks that delivers the increment's Deliverable, no creep into later increments. *Halt* if planning surfaces a genuinely **new fork** not covered by the settled gates and not resolvable from the locked docs.

2. **Execute** — run each task through the [dev workflow](dev-workflow.md) verbatim (scope → red → green → refactor → gate → commit). Tasks run **strictly serially**: they share one working tree and each ends in one commit, and the spine is linear (each task builds on the last). One task = one focused concern = one conventional commit **on the increment's branch** (→ Branches, below). *Halt* on a blocked task (a real ambiguity, a new fork, or a green gate unreachable without overstepping scope).

3. **Validate** — an **independent, read-only** check of the increment against the roadmap, run by an agent that **did not build it and cannot edit or commit** (so it cannot certify its own work). It verifies, with concrete evidence:
   - **gate green** from a clean state (`fmt --check` · `clippy -D warnings` · `test` · `build`);
   - **deliverable holds** end-to-end — by *running the real binary / commands and observing output*, not trusting the tests alone;
   - **proves** holds — the increment proves what the roadmap says it proves;
   - **invariants** honored ([CLAUDE.md](../CLAUDE.md) — engine makes no LLM calls / ships empty / presentation-free; CLI-locates / engine-resolves; result types are the Serialize contract; slots vs placeholders distinct; splice round-trip discipline; deterministic composition; transactional finalize);
   - **scope honest** — *the critical check*: no inert/dead feature (a flag parsed but ignored), no stub presented as done, no `todo!()` masquerading as complete, no creep into a later increment, no tautological test that asserts nothing real;
   - **no earlier increment broken** — the validator also receives **the milestone's diff so far** (from the milestone branch's fork point to this increment's tip: the earlier increments' landed work plus this one), and for every surface this increment touches that an *earlier* increment of the milestone also built or changed, it **re-drives that increment's acceptance claims** (its roadmap *Proves* and *Grouped scope*) against the current tip. A regression, or an interaction defect — two increments' work that holds alone and breaks together — is blocking. *Since 2026-10-03* ([DECISIONS.md](../DECISIONS.md) → *one land step per increment*): M55 validated every increment clean and its audit still found five defects, the clearest an interaction between Increment 1's doc-only text and Increment 3's sub-task composition — a defect no validator looking at one increment alone can see.

   It returns **findings**, each *blocking* (the deliverable/proves/invariants/scope are not genuinely met) or *advisory* (real but non-blocking).

4. **Fix until valid** — for each **blocking** finding, a [dev-workflow](dev-workflow.md) fix task (red that fails *because of the defect*, minimal green, gate, commit) → then **re-validate**. Bounded to **3 rounds**. *Halt* if blocking findings remain after the cap — thrash is a signal for a human, not for a fourth round. Advisories are surfaced, not gated.

The increment is **done** when validation passes (zero blocking findings, gate green, deliverable genuinely holds) **and it has landed** — merged into the milestone branch and pushed (→ Branches). The next increment then begins on top of it.

## Branches

*Since the branching switch, 2026-10-01* ([DECISIONS.md](../DECISIONS.md) → *the branching switch*; the model and its names are [CLAUDE.md](../CLAUDE.md) → Branches). An increment's whole life is one branch:

1. **Open** — `milestone/<slug>/<increment-slug>` is forked from the milestone branch `milestone/<slug>/main`, which itself was forked from `main` (at planning, or by the build's first step). The increment slug is derived from the roadmap increment title, deterministically; the increment's **order** is the roadmap's, never its name's.
2. **Build** — Plan, Execute, Validate and Fix all run on it: the planner's decomposition commit, every task commit, every fix commit. No build agent creates, switches, merges or pushes a branch; each checks that the branch it is on is the one it was named before it commits.
3. **Land** — once validation is clean, **one step** (since 2026-10-03; it was a land step and a push step): the increment branch is merged with **`--no-ff`** onto the milestone branch's **current** tip, so the milestone's first-parent history reads one merge per increment; the increment branch is **deleted locally** (it is never pushed); and the milestone branch is **pushed by name**, so each increment is one CI run on the real runner and a dead disk loses at most the increment in flight. The step does **not** assume the increment branch descends from the tip: a tip that moved after the increment branched is merged onto, a conflict confined to the append-only logs (`DECISIONS.md`, `implementation/project-history.md`) is resolved by [`dev/merge-logs`](../dev/merge-logs), and any other conflict is `git merge --abort` and a halt to the human. When the tip did not move, the merge's tree must equal the increment's. A pushed milestone branch carrying commits the local one lacks, or a rejected push, is a halt — never a pull, a rebase or a force.
4. **Planned human halts** — an increment whose roadmap entry *ends in* a human halt (`Ends in H2 (the human's)`) is a **stage boundary**: after it lands and is pushed, the build **returns** with the human's checklist instead of an agent waiting on him (a workflow takes no mid-run input). The next increment opens with an entry-gate task that verifies the human's act. → Halt and resume.
5. **Close** — the [milestone-completion](milestone-completion-workflow.md) audit runs over the milestone branch from its fork point, its fixes land on the milestone branch, `main` is merged in ([dev-workflow.md](dev-workflow.md) → Before a pull request to `main`), and the orchestrator opens the pull request to `main`, which the human merges.

**Parallel increments — the rule, prepared and not built** (decision 7). Today every increment is serial: each builds on the one before. The harness is already cut for it: **open** (the increment's first act) and **land** (its last) are separate steps, deliberately not coupled to another increment's, and the land is the one act on the shared milestone branch — the **serialized critical section** — which already merges onto a tip that moved since the increment branched. When a decomposition **declares** increments independent ([milestone-planning-workflow.md](milestone-planning-workflow.md) → Decompose), they branch off the **same** milestone-branch commit and are **joined in plan order**, never completion order — the same by-id, not by-completion rule the fan-out join keeps. **A conflict at the join is a planning error**: the declaration was wrong, so it routes to the human and is never auto-resolved. The mechanism is built when the first milestone declares independent increments ([decisions-pending.md](decisions-pending.md) → *Parallel increments*); until then the harness builds every increment serially, declared independent or not.

## Validation hardening (audit-derived)

Each external, adversarial milestone-completion audit has caught real issues the per-increment validator had passed over: the M3 audit found a reachable parser panic on out-of-band input, an MVP-scope component built and unit-tested but never wired to a command, and a masking-test that hid a broken emitted line; the M4 audit found a **context-scoped check exercised only in the context that includes its target** (a front-door-bricking bug that cleared every per-increment gate); the M5 audit found an **unowned cross-increment deferral** — part of an increment's *approved* scope was quietly punted to "a later task" that never delivered it, and each per-increment validator treated it as the other increment's job. The lessons fold back here as **mandatory validator checks**, because they are the exact blind spots an automated validator inherits:

1. **Every grouped-scope bullet, not just the headline.** "Deliverable holds" must be asserted for *each* bullet of the roadmap increment's *Grouped scope*, every one **exercised through the binary** — not only the marquee acceptance path. A passing headline flow can hide a sibling sub-deliverable that has no command surface.
2. **`pub`-but-test-only is a scope finding.** A `pub fn` whose only callers live under `#[cfg(test)]` is dead in production — and it slips past a `#[allow(dead_code)]` grep *precisely because it is public*. The validator must trace that every shipped capability is reachable from a command path, and flag any public surface invoked only from tests.
3. **Parsers get a hostile-input pass, not only round-trip-on-conformant.** Property/round-trip tests over *conformant* input prove losslessness but never exercise the malformed-input contract ("every mismatch is a located finding, never a panic"). Any parser or reader must be fuzzed on hostile/foreign input — non-ASCII, BOM, truncation, mixed EOL — as its own check.
   - **The round-trip's *writer* half needs the hostile-input pass too (M9), and "the agent owns the prose" makes it load-bearing.** A canonical writer that round-trips *conformant* prose can still emit **non-reparseable output from valid-but-messy prose** — and because the [determinism boundary](../VISION.md) makes the **agent** the author of slot content, the writer must round-trip *any agent-plausible* input, not just CLI-canonical input. An acceptance/red test that only ever feeds well-formed input (e.g. always newline-terminated) is a **masking test for input-conditional defects**: it certifies the CLI's own output shape, never the messy forms the agent will hand. The writer/round-trip red step must feed the edge forms an agent could author — no trailing newline, odd interior whitespace, empty-then-filled. (M9's audit caught the canonical writer producing non-reparseable output when a *non-terminal* slot was filled with prose lacking a trailing newline — **masked** by a flow-11 acceptance that always passed newline-terminated prose; the per-increment gate passed, the independent e2e audit did not.)
   - **Fixture-topology masking — the acceptance fixture shaped to the *handled case* (M10), the sibling of input-coverage on the *fixture* axis.** When an implementation handles only a *subset* of the real-world shapes (only top-level items, only one layout, only the happy structure), an acceptance fixture authored in that handled shape passes while the **dominant** real-world shape false-fails — the acceptance certifies a narrower capability than the deliverable claims. The fixture must be the *dominant* real case; when the implementation narrows what it resolves/accepts, the red/acceptance fixture must exercise a shape it does **not** obviously handle. (M10's audit caught the `doc-code` resolver matching only *top-level* items — blind to the dominant `#[test]`-in-`#[cfg(test)] mod tests` + impl-method layout — with the flow-13 fixture written in the rare top-level layout that **masked** it; the per-increment gate passed, the independent audit did not.)
   - **Cold-start composition — a new write primitive is proven against its create→fill seam in the *empty* state, not a pre-populated fixture (M13).** When an increment builds a write/authoring primitive (a `create`/mint verb, an item/section setter) that a real flow composes with a fill sequence, its done-criterion and the validator must exercise the **cold-start round-trip**: create the structure *empty* → it round-trips → fill one leaf at a time → **each intermediate state** round-trips byte-stably. The defects live in the empty form (a slot/field span recorded *without* canonical surrounding blanks; an absent field bullet the splice-only setter cannot reach), which a fixture built in the *populated* state never touches — and a round-trip assertion **scoped to a populated subtree to route around a known empty-state defect is a masking test** (the M9 input-axis / M10 fixture-axis mask, now on the *create→fill-state* axis). A low-level setter "validated clean" against only its filled fixture is **not** done: its real first use is the freshly-minted empty structure. (M13's increment-2 item setters passed in isolation against canonically-rendered items, so the mint-empty→fill seam — two byte-stability defects + an absent-field gap — surfaced as build halts a later increment; and an inc-5 executor *scoped* its byte-stability assertion to the filled `## Components` subtree to dodge the empty leading-slot defect it had found — the audit caught both the defect and the mask.)
4. **Agent-facing contracts are validated through the emitted bytes, not a reconstruction.** When a deliverable is something an agent or user runs from composed output (a `Run:` line, an emitted command, a rendered view), the test — and the validator — must drive the **emitted artifact verbatim**, not a command rebuilt in test code. A test that reconstructs the args can stay green while the emitted line an agent would actually run is broken (a *masking test*). The emitted bytes are the contract; assert on and execute the emitted bytes. (The M3 audit caught a `jigc task bind` line missing a required positional precisely because the e2e appended that positional in test code — the per-increment validator had passed it as "clean.")
   - **A golden/snapshot *widened to admit* new output is a masking test at the snapshot layer (M8).** When a change makes a golden grow a line, "should this golden change?" is a scope claim to *adjudicate*, not auto-accept: a golden updated to *admit* output the feature now emits can be papering over a leak, not recording an intended addition. The strong tell is the **same widening across N goldens** — a single leak propagated into every snapshot that observes it. (M8's audit caught the finalize-less `sub-task` workflow leaking into the router catalog *because* the relaxation had been absorbed into the routing test **plus three production goldens**, all green; the per-increment validators passed it, the independent audit did not.) The validator/reviewer treats an output-*adding* snapshot diff — especially a repeated one — as a finding to justify, never a routine re-pin.
   - **A capability tested through its *core function*, below the shipped verb's entry gate, is masked (M38).** When a verb *assembles* its work before calling a core function — builds a job list, applies an eligibility filter, dispatches on a discriminator — a test that calls the **core function directly** proves the transform while the **entry-gate assembly** (exactly where the integration defect lives) is never exercised. The acceptance must drive the capability **through the shipped verb / binary**, not the core fn beneath its gate; a green core-level test is unit coverage, not acceptance. (M38's audit caught the `changelog` relocation **inert through the real `jigc migrate-corpus`** — its job-list gate filtered out the now-`location: None` placement doctype before the walk — while *every* relocation test called the core `migrate_committed_corpus` directly and passed, and the same shape hid a second `docs-root` defect in the same verb. The per-increment gate passed; the independent e2e audit, which drives the binary, did not. Its sibling on the *read* side: the committed edge index dropped the same placement doctype, untested because no test built a placement doc as an edge referrer.)
5. **Context-scoped features are exercised against a context that OMITS the target, not only one that includes it.** When a deliverable's behaviour depends on *which surrounding context* it composes into — a slot-fill applied to a step, an override applied to a workflow, a binding read by a role, a knob read by one command path — exercising it only in a context that **includes** the target proves the happy path while hiding a scope bug in the **omitting** path. The test and the validator must compose the feature against at least one context that does *not* contain the target and assert the correct behaviour there (usually *inert*, never *error*). A green happy-path acceptance over a single composing context is not coverage. (The M4 audit caught a `slot-fill-orphan` check keyed on the *composed workflow* instead of the *target step*: a recorded slot-fill on `step:implement` exited 1 for every workflow that omitted `implement` — including the default front door reached by bare `jigc start` — because the acceptance only ever composed the one workflow that included it. It cleared Plan, Execute, and the independent per-increment Validate, and was caught only at the milestone audit.)
6. **Completeness against the *approved* scope — a documented reduction is not an approved one.** The validator checks the build delivered **every *Grouped scope* bullet as the roadmap approved it**, not merely that what *was* built is honest about itself. A build that quietly narrows its approved scope and *documents* the reduction (a module comment, a `DECISIONS` pin: "X rides along, lands in a later task") has not been **approved** to reduce it — *documented ≠ approved* — so an undelivered approved-scope bullet is a **blocking** finding, never advisory. The **cross-increment deferral** is the sharpest case: "punted to a later task/increment" belongs to *no* single validator unless tracked, so the validator must **follow the punt to its named landing and confirm it actually delivered** — an untracked punt no increment delivers is exactly the gap the M5 `scalar-set`/`insert` orphan-classification fell through (increment 2's validator saw a deferral note and assumed increment 4 owned it; increment 4's scope was slot-fill; neither built it; caught only at the milestone audit).

These six checks instantiate **one principle**: the per-increment gate owns **completeness against the approved plan**, not just the internal honesty of what got built. A masking test (M3), a single-context exercise (M4), and an unowned cross-increment deferral (M5) are three faces of one blind spot — *the build delivered less than the approved scope and nothing independent caught it before the milestone audit*. Treat a new variant as a new **face of this principle** — extend the check — not a new category to enumerate. Operationally the scope-honesty check becomes: prove each approved-scope bullet is delivered and reachable through the binary, each parser is panic-free on garbage, each agent-facing line runs verbatim as emitted, each context-scoped feature is exercised in a context that omits its target, and every deferral is tracked to a verified landing.

### A second principle (M7): determinism by re-execution

The six above are one principle: *completeness against the approved plan*. **M7 surfaced a seventh that is genuinely orthogonal** — and, for the first time, it was caught **forward-looking**: an adversarial review of the harness *before* the milestone built ([self-hosting.md](../design/self-hosting.md) graduation-pass part 4, run during M7 Settle), not reactively by an audit after the failure. That break in the reactive cycle is itself the lesson — a concurrency milestone is exactly where our audit-derived checks were blind, because all six were learned on substrate-riding (completeness) failures, none on concurrency.

7. **Single-execution determinism trust — a gate that observes one run certifies a property that only fails across runs.** #1–6 are all "the build delivered *less* than approved scope." #7 is the opposite shape: the build delivered the *full* scope, honestly, and it is **still wrong** because the output is **not a pure function of its input** — a `HashMap` iteration order, a `read_dir` order, or completion order leaks into committed bytes. A single green `cargo test` cannot see it (Rust's hasher is seeded per-process, so one run is internally stable; the test asserts against whatever order *that* run produced). This repo already defends by *reflex* — sort-after-`read_dir`, `BTreeMap`-for-serialization everywhere — but **no gate enforces it**; every sort is a developer remembering. M7's net-new join is where reflex and gate diverge.

   **The principle:** *any output the spec calls reproducible — "same resolved cascade in → same workflow out", "by task id, not completion order" — must be proven reproducible by **re-execution**, never by inspecting one run. A determinism claim is a claim, unverified until the same logical input is fed through ≥2 deliberately-divergent conditions (scrambled order, repeated invocation, forced map-iteration variance) and the bytes are asserted identical.* This is "reuse is a claim, not a fact" turned on the determinism boundary the product exists to draw.

   Operationally, for any deliverable the roadmap calls reproducible/order-invariant, the dev-workflow **Red phase** and the **validator** MUST:
   - **re-run under ≥2 divergent orders/seeds** (minimum: id-order **and reverse**) and assert **byte-identical** output — reverse is mandatory, since an id-ordered fixture makes completion-order trivially equal id-order and hides the bug;
   - **never let an `A==A` re-run stand in for correctness — the equivalence oracle must be an *independent* path (M14).** Re-running the path under test and asserting it equals *itself* proves only **stability/idempotence**, never that the path composes the *right* content. When an equivalence assertion is *also* meant to prove a behavioural property (the path resolves the correct thing), its reference operand must come from a **different, trusted path** — a fresh-compose golden, a known-good oracle — not a second run of the suspect path. The tell is a comment claiming a correctness property while the code compares a path to itself. (M14's audit caught flow-17 6a comparing **resume-vs-resume** — byte-identical even though *both* runs silently mis-resolved a loser-pack workflow's bodies to the precedence winner — where **resume-vs-fresh** exposes it; its comment even *named* a content check while the code only checked idempotence. The fix de-masks it to resume-vs-fresh. Re-execution shows *stability*; an independent oracle shows *correctness* — one must never masquerade as the other. This is the inverse risk of the bullet above: there, re-execution is the *cure*; here, re-execution against the wrong oracle is the *mask*.);
   - **forbid *unsorted* `HashMap`/`HashSet` iteration from reaching emitted/committed output** — a hash container is fine if its contents are **sorted at the boundary** before emission; what's banned is iteration *order* leaking into output (prefer `BTreeMap`/`BTreeSet`/sorted `Vec` keyed by the stable id; this codifies the existing hand-sort habit into a gate);
   - **build fixtures whose natural `read_dir` order differs from id order**, so a report sorted only because the fixture was created in id-order is caught;
   - **force genuine overlap** in isolation tests (same slug minted; a cross-area ref; a *self-referential* colliding doc) — never rely on naturally-disjoint inputs, which prove isolation trivially.

   Stated principle-first so it transfers past jigc (the graduation-pass portability discipline): *any id-collision-rename must rewrite self-references, not only cross-references; the isolation test must force overlap, never rely on disjoint inputs.* The M7 instance is [worked-examples.md](../design/worked-examples.md) flow 9.

### M8 faces (spawn / adapter class — forward-looking review at Settle)

M8's forward-looking harness review (the conditional Settle phase for an off-substrate milestone) probed *"what spawn/adapter-class failure could a green gate still pass?"* and confirmed the M7 lesson again: **no new numbered principle — three new faces of #4, #5, #7, plus one capability gap the gates cannot close.** Fold these in:

- **#4 face — the adapter-rendered launch line is an emitted-bytes contract too.** A spawn template that passes the install-time *syntactic* schema can still render a verb that does not exist (the L1 landmine) or a misspelled `jigc workflow`. So the Red phase + validator must **render the spawn template through the CLI for a real `(workflow, task_id)`, extract the rendered command verbatim, and execute it as a process**, asserting it resolves to a working verb and reaches the CLI. A test that hand-writes `jigc workflow --task` in test code is a masking test; the *rendered* bytes are the contract.
- **#5 face — a marker that parses but does nothing is a parsed-but-ignored flag.** M8 makes step front-matter active (`fan-out`/`join`/the `Spawn:` class) where pre-M8 it was silently stripped (a `fan-out:` fixture marker composes green as inert prose today — `compose.rs`). The symmetric trap to #5: a parser that reads the marker into a struct while compose still ignores it. So exercise a step that **carries** the marker and assert compose output **differs** from the same step without it (dispatch fires, N `Spawn:` directives emit) — *and* a step without it stays inert. Output unchanged with the marker present = blocking scope finding.
- **#7 face — exercise the *enforcement point*, not its already-correct output.** M8 adds the write-time `--task`-scoped barrier — a *new* enforcement point *before* the join. A fixture that pre-stages the correct area never exercises the barrier; the barrier could no-op and the join (reading correctly-staged input) still passes. So the isolation test must **drive a write through the barrier from the binary** (not pre-stage) and **attempt a write outside the named sub-area**, asserting it is refused/redirected, never silently landing. (The M8 face of "force genuine overlap": force a genuine *out-of-bounds write attempt*.)
- **The capability gap — the genuine spawn is unprovable by any automated gate.** By the determinism boundary the launch is assistant-owned and non-deterministic; a Workflow/Task **subagent runs headless and cannot itself spawn the assistant's Task tool**, so no automated gate can drive a real concurrent spawn. This is *not* a validator check — it is a **human/orchestrator-driven milestone-completion audit artifact** ([milestone-completion-workflow.md](milestone-completion-workflow.md) → the spawn-class artifact). The automated half (an N-process binary sim of `jigc workflow --task`) is honest but proves only the CLI payload + join; presenting it *as* the genuine-spawn proof is the **hollow-spawn trap**. The blackboard invariant (sub-agents coordinate only through the CLI, never reading a sibling's area) is likewise witnessable only in that recorded artifact, never by a permutation test whose "sub-agents" are CLI calls by construction.

## The design of record is a claim, not a fact (M42, 2026-07-14)

The [dev-workflow](dev-workflow.md)'s *"a recorded rationale is a claim"* rule (M41) binds the **author**. M42 extends it to the **consumer**: **the increment planner must verify the design's load-bearing *factual* claims against the binary before it decomposes.** A design doc is written by someone who was reasoning; it can be internally coherent, independently reviewed, cross-model reviewed, and **still assert something the code does not do.**

M42's Increment 9 **halted three times**, and every halt was the planner refusing to build against a design-of-record claim that proved false when it ran the binary:

1. The pinned `task-discard` ack carried an effect key justified by *"the idempotent already-absent no-op."* **That no-op does not exist** — `jigc task discard <absent-id>` exits 1. The design pass had trusted `run_discard`'s own doc comment, which claimed idempotence; the guard that comment described was **dead code**. So the contract pinned a key that could only ever hold one value, one increment from a 1.0 freeze. *(A lying comment authorizes the next wrong pin — which is exactly how it happened.)*
2. The finding-key sweep declared the degenerate-key class **closed**. It was not: two whole clusters (47 codes) were outside the enumeration, one of them colliding **inside a single JSON document**.
3. The enforcement seam for that class was **itself a census** — three hand-listed funnels — and a fourth serializing surface was emitting a *different key for the same defect*.

**Every earlier catch in that wave came from a reviewer** (the gap-detectors, the robust-advocates, the design-reviewer, a cross-model pass). **These three came from the builder refusing to build** — with a filled gate-record and an approved scope in hand. The planning gate-record is **necessary and not sufficient**: a cell can be filled confidently and wrongly, and no amount of reading catches a claim that only the binary can falsify.

**The obligation:** before decomposing, run the design's factual assertions. Not its *judgments* — its **facts**: "this verb is idempotent," "this parameter is already threaded," "this family has nine members," "this primitive already does X." Each is a claim about the code, and each is cheap to check and expensive to inherit. **If a claim is load-bearing for the cut and you cannot check it, halt** — a halt costs one session; a contract frozen on a false premise costs a major version.

**Pack-shape** ([DECISIONS.md](../DECISIONS.md) → 2026-06-21 Direction): **a step in the `increment` workflow's plan phase** — `step:verify-design-claims`, composed *before* the decomposition step, so the planner meets it at the moment it is about to inherit the claims. Text to encode: *"List the design's load-bearing **factual** claims about the code — not its judgments: 'this verb is idempotent', 'this parameter is already threaded', 'this family has N members', 'this primitive already does X'. **Run each one against the binary.** A claim you cannot check, and that the cut rests on, is a halt."* The **done** is the planner's own halt-or-proceed; jigc composes the step and can never grade the answer (the A-3 bound — presence, never content).

## Halt and resume

The loop **stops and surfaces to the human** at exactly three points: a **new fork** at Plan, a **blocked task** at Execute, **still-blocking after 3 rounds** at Validate — plus a git step that refuses (a dirty tree, a diverged branch, a merge conflict outside the append-only logs, a rejected push), which is a branch to reconcile rather than code to fix. A land that halts after its merge commit exists reports it, so the human knows the increment is on the milestone branch and only the push (or the delete) is owed. A halt returns a structured report — which increment, which phase, which branch, the precise reason — and is **resumable**: prior committed work stands, completed steps replay from cache, and the run continues once the human clears the blocker. Nothing is guessed past a point the design says is the human's.

**A planned halt is not a halt** (→ Branches, step 4). It returns `planned-halt` with the human's checklist, and the **default resume is the run's own `resumeFromRunId`**, with the halt's id added to `cleared`: every agent call before the boundary replays from cache and the next increment runs live. A fresh run with `skipThrough` set to the increment the halt ended is the fallback. The return prints both, ready to paste.

**Clearing a halt: the orchestrator decides, a subagent codes.** The orchestrator (with the human) owns only the *judgment* — diagnose, decide the fork. *Executing* the fix (edit → gate → commit **on the halted increment's branch**, which the halt leaves checked out) is delegated to a **`build-fixer` subagent**, never done in the orchestrator's own session: coding inline bloats the orchestrator's context window and can exhaust it before the milestone finishes, defeating the whole reason each phase is a subagent. The fixer commits on that branch and reports the commit sha + gate evidence; the orchestrator then cache-busts the halted call and resumes from that report — its window holding summaries and shas, not file bodies.

**A transient halt has three tree states, not two — and the third is the dangerous one (M48, 2026-08-15).** The harness's resume guidance *used to* read *"if `git status` is clean there is NOTHING to fix — resume immediately"*, which read the tree as a binary: clean ⇒ resume, dirty ⇒ something broke. **A killed executor produces a third state: finished, gate-green, uncommitted.** M48 lost two executors to API overload; one died between *green* and *commit*, leaving **511 insertions across four files that compiled and whose acceptance suite passed** — its whole deliverable, one `git commit` short. Resuming per that guidance would have started the re-run against modifications it did not write, with its **test-first step already green** — which is exactly how a task convinces itself it is done without ever having been red, the failure the red step exists to prevent. Discarding would have thrown away verified work. **That is why the binary form is gone**: `.claude/workflows/milestone-build.js` now carries the classify-first rule in short form and names this section as canonical, so the two cannot drift back apart.

So on a transient halt with a **dirty** tree, classify before acting: **(a)** does it build · **(b)** does the halted task's own acceptance criterion pass · **(c)** does the *full unscoped gate* pass. All three ⇒ the work is finished and the commit is the only thing owed — **commit it, and say in the message that the work was recovered rather than authored**, so the completion audit can weigh it accordingly. Any of the three failing ⇒ discard and let the task re-run clean; a half-written edit from a dead agent is not something to build on. **Never resume onto a dirty tree** either way: the state the re-run inherits is unexplained by construction.

**A killed harness can keep its loop registered, and then no resume is possible (M52, 2026-09-20).** When the M52 build's shell was stopped mid-increment, `TaskStop` reported the run killed but its loop never exited, and every resume was refused as *"would run two copies of its agents against the same journal"*. The recovery that worked, in this order: classify the dirty tree as above (that executor had passed its gate — committed as recovered); finish the interrupted increment's remaining tasks with `build-executor` subagents outside the harness, on its increment branch; run the `increment-validator` and any fix rounds exactly as the harness would; **land it by hand** — merge it into the milestone branch with `--no-ff`, delete it, push the milestone branch by name; then start a **fresh** run with `skipThrough: <that increment>` and **no** `resumeFromRunId` — the harness's own header names this fallback (rule 6). The tell that a resume is replaying a *cached halt* instead is a run that returns in milliseconds with zero subagent tokens; that case needs the increment-keyed resume note in the script snapshot, not a fresh run.

**A halt resolution that re-scopes an increment or swaps a mechanism is a first-class settlement — it gets the planning gates, not a momentum pass.** Most halt clearings are a localized fix the `build-fixer` lands. But when clearing the fork *widens an increment's approved scope* or *changes a mechanism* (not merely patches a bug), it is a **Settle-grade decision made mid-build** — under momentum, by the same person, with **none** of the [planning](milestone-planning-workflow.md) gates a planning-time settlement gets (no independent review, no property census). So before resuming, the orchestrator must (1) run the **property census** ([milestone-planning-workflow.md](milestone-planning-workflow.md) → Settle: every property the milestone establishes → each path that must uphold it → acceptance) over the *new* mechanism, and (2) give the resolution a **quick independent adversarial pass** — a `design-reviewer` over the re-scoped slice, or at minimum the focused question *"does this mechanism re-introduce a hazard we already solved on a sibling path?"* — recording the answer before the build runs on. (M31: the milestone's only escaped defect entered exactly here — resolving the Inc-5 hook fork swapped squash:false's mechanism from the reviewed WIP-safe temp-index build to a live-apply + `git reset --hard`, re-introducing the data-loss hazard review S2 had killed for squash:true; the planning design-reviewer had blessed the safe form and **never saw the swap**, because halt resolutions carried no review gate.)

## Orchestration

Run by hand, the phases above are steps one person walks. Run as an orchestrated workflow, **each phase is its own agent**, so the loop's independence is structural rather than self-policed:

- **Plan** — one planning agent per increment (just-in-time, after the prior increment lands), emitting the ordered task list **and recording the decomposition in [DECISIONS.md](../DECISIONS.md)** as its own commit before the tasks run (as the first milestone's increments did).
- **Execute** — one agent **per task**, each running the whole [dev workflow](dev-workflow.md) loop to a single commit; tasks run serially over the shared working tree.
- **Validate** — one **independent, read-only** agent (it cannot edit or commit), handed the milestone's diff so far beside its own increment.
- **Fix** — one agent **per blocking finding**, each a dev-workflow fix task, then re-validate; bounded to 3 rounds.
- **Git** — every branch act is a small `build-git` step with a fixed command list: the milestone branch once, then per increment **open** and **land** (two git agents, down from three), and the close's **sync**, which the build returns for the orchestrator to spawn. **The git steps run on Sonnet**, every other role on the run's model (Opus by default): a git step needs no Opus — M55's 34 git agents spent ~30–55k fresh tokens each — and not Haiku either, because what the step is trusted with is halting on a surprise rather than improvising past it.

Halts (above) surface to the human; nothing is auto-resolved past a fork.

This mapping is **runnable, not just descriptive**: `.claude/workflows/milestone-build.js` drives the whole loop for a milestone (read its roadmap decomposition → per increment plan/execute/validate/fix → the milestone-completion audit), one agent per phase with the role prompts in `.claude/agents/`. Invoke it as `Workflow({name: "milestone-build", args: {milestone, slug}})` — `slug` is required and names the milestone branch; the audit base is that branch's fork point, so there is no `base` to pass — and the script's own header carries the resume rules (RULE 0, planned halts, the three tree states). So a milestone build *runs* this loop rather than re-interpreting this doc each time. The agents still read the canonical docs (this file, [dev-workflow.md](dev-workflow.md), `CLAUDE.md`, the milestone's `DECISIONS.md`/roadmap entries) for the specifics; only the orchestration is fixed.

## Why this shape

Framing notes, not extra phases:

- **Independent validation is the payoff.** The builder cannot grade itself; a fresh, read-only, adversarial pass against the roadmap is what catches *scope dishonesty* — the inert flag, the stub-as-done, the test that asserts nothing — which a self-check structurally misses. (This is precisely the class of gap a by-hand review caught once and this phase now catches every time.)
- **Gates-first is what makes it autonomous.** Deciding the forced `(D)`s up front converts "stop and ask mid-run" into "implement a settled decision," so the loop honors the surface-decisions guardrail *and* runs unattended.
- **It is the dev workflow's wrapper.** Execute delegates to [dev-workflow](dev-workflow.md) unchanged; this doc owns only the orchestration around it — the cut, the independent gate, the bounded fix loop. Cross-reference, never restate.
- **Serial by necessity.** Shared working tree, one commit per task, a linear spine — the loop is sequential by construction, the same property that makes each commit a clean, reviewable unit. Within an increment it stays so; *across* increments, a decomposition that declares independence is what would let two run side by side (→ Branches → Parallel increments), and nothing builds that until a milestone declares it.
