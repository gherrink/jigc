# Release

**The home for how jigc is versioned, packaged, published and installed.** Settled at M54's planning, 2026-09-28, with the independent design review's findings accepted the same day ([DECISIONS.md](../DECISIONS.md) → *M54 settled*), and **built in M54** ([roadmap.md](roadmap.md) → M54): the version stamp is the release PR's, no longer the hand edit the [milestone close](milestone-completion-workflow.md) performed (→ The release PR), and the first versions its release pipeline published are `jigc 1.0.0-rc.22` and `jigc-engine 0.1.0-rc.1`, on 2026-10-01 ([publish-proof.md](../completions/artifacts/M54/publish-proof.md)). The crate *architecture* this rides on is [module-layout.md](module-layout.md); the CI jobs are [dev-workflow.md](dev-workflow.md) → Gate; the machine that proves an install is [`dev/runner-faithful`](../dev/runner-faithful), committed beside [`dev/gate`](../dev/gate) at M54 Increment 7. This page states the rules and cross-references the rest.

**Two kinds of statement below, and each is marked.** *Settled* is the human's decision and changes only through a new one. **Pinned by the build** is an implementation pick M54's build made and recorded here — named so nobody mistakes an open detail for a decided one.

## Versioning

*Settled:*

- **`jigc` is on the `1.0.0-rc.N` track** until the 1.0.0 call. The rc track **is the version string**: the release tool only increments `N`. Leaving the track — `release-plz set-version` by hand to `1.0.0` — **is** the human's 1.0.0 call, and nothing automated performs it.
- **`jigc-engine` is versioned independently** — 0.x, its own prerelease track starting at **`0.1.0-rc.1`**, bumped only by changes to its own paths. `jigc` pins it with **`=`**, so a `jigc` build names exactly one engine.
- **Each crate carries its own `version` field**, never `version.workspace = true`: release-plz silently fails to write an inherited one, so an inherited field is a bump that does not happen.
- **Versions are computed from conventional commits, by the paths each commit changed.** Docs-only commits never bump anything — this repository's doc-heavy history would otherwise release on every record edit. The filter that enforces it (the spike's `release_commits` regex admitted `feat`, `fix`, `perf`, `refactor`, `revert`) is **pinned by the build**.
- **The version the product reports is `jigc`'s.** The `.jigc/version` store stamp ([storage.md](../design/storage.md) → Store provenance) and the embedded packs' `pack_version` ([module-layout.md](module-layout.md) → The dev pack's home) both carry `jigc`'s version, never the engine's — the engine has no `CARGO_PKG_VERSION` use and gains none. So does the probe's build id ([module-layout.md](module-layout.md) → Probe boundary).
- **A bump moves no golden.** In the ten version-bearing compose goldens (`Pack: dev/<ver> | methodology/<ver>`), exactly the string equal to `env!("CARGO_PKG_VERSION")` is normalized to `<jigc-version>` — narrowly, so a regression to `0.1.0` or to the engine's version still diffs. The `env!("CARGO_PKG_VERSION")` test pins are left alone: they follow the bump by construction. `CLAUDE.md` stops carrying a pipeline-owned version number a fence pins; how `foldback_truth`'s *built and installed* arm is re-cut is **pinned by the build** — **pinned 2026-09-30 (M54 Increment 5):** the normalization lives in the golden harness (`crates/cli/tests/support/goldens.rs`, `VERSION_TOKEN`), beside `<REPO>` and as its only sibling; and the arm keeps its failure, a fold-back announcing a binary the tree does not carry, under three constraints — (a) `CLAUDE.md` names **no** built-and-installed version, and the arm asserts it carries none rather than comparing one; (b) a bump of `crates/cli/Cargo.toml` alone leaves the arm green, because the record's newest claim is held to *not ahead of* the crate in semver precedence instead of *equal to* it; (c) the arm still **rejects**, over fixtures, a newest-span claim naming a version the crate has not reached (`rc.9` precedes `rc.10`; `1.0.0` follows every `1.0.0-rc.N`).

## The release PR — how a version is proposed

*Settled:* the tool is **release-plz**. *Why not knope, which was spiked beside it:* knope attributes a change by commit **scope** rather than by the paths it touched, does not bump a dependent when its dependency moves, and so breaks the `=` pin above.

1. On every push to `main`, release-plz opens or updates **one workspace release PR** — not one per package (release-plz docs, `usage/release-pr.md`) — carrying every releasable package's version bump and changelog section. Its title comes from a **conditional** `pr_name` template: `{{ package }}` is populated only when a single package releases, and an unconditional use of it fails the run (`config.md`), so the template guards it with `{% if package and version %}`.
2. **The PR is opened with a GitHub App token**, not the workflow's own token. The App — created by the human — has **Contents: read/write and Pull requests: read/write**, is installed on `gherrink/jigc` — and, **for the rehearsal only**, on the private rehearsal repository (below), from which the human uninstalls it afterwards — and its ID and private key live in repository secrets. **Pinned by the build** (M54 Increment 9, 2026-09-30): the secrets are **`JIGC_RELEASE_APP_ID`** and **`JIGC_RELEASE_APP_PRIVATE_KEY`**, under the repository's `JIGC_` prefix. The App's repository permissions are exactly **Contents: read/write**, **Pull requests: read/write** and the **Metadata: read** GitHub makes mandatory. It needs no webhook and no events. `release.yml`'s `release-pr` job mints the token with `actions/create-github-app-token` at `v3.2.0`'s commit (Publishing → *Action pins*) and uses it for the checkout, for `release-plz release-pr` and for the git identity `release-plz/git-config` derives from it. *Why the App and not the workflow's token:* GitHub starts no workflow for a PR that the workflow's own `GITHUB_TOKEN` opens, so the release PR would never run CI. *Why `@v3`, and the App ID as `client-id`* (2026-10-01): `v2` declares the retired `node20` runtime, and `v3` is the lowest major on `node24`. From `v3.1.0` the action deprecates `app-id` for `client-id` and reads `client-id || app-id` into the one value it signs with, which takes an App ID or a Client ID, so `JIGC_RELEASE_APP_ID` goes in as `client-id` unchanged. Every action pin — its commit and its runtime — is held by `crates/cli/tests/workflow_action_runtime_fence.rs`.
3. **Merging the release PR is the go.** The human merges it; nothing else starts a publish.

**Changelogs.** Each crate keeps its own generated changelog at `crates/<dir>/CHANGELOG.md`. **The root `CHANGELOG.md` is not written by release tooling**: it is reserved for jigc's own `changelog` doctype, and whether this repository's changelog is the generated one or a jigc-authored one is a fork keyed to M56's Settle ([decisions-pending.md](decisions-pending.md) → *The road to 1.0.0 and the port* → M56).

**release-plz knobs — pinned by the build** (M54 Increment 9, 2026-09-30). The spike proved one fact on its throwaway workspaces: a per-crate `version` field is written, and a workspace-inherited one silently is not. Everything else is pinned here, in `release-plz.toml` at the repository root, and `crates/cli/tests/release_pipeline_fence.rs` holds each fenced row; the letter is its arm. **The version the proofs ran is release-plz `0.3.169`**, the one `release-plz/action` `v0.5.139` installs by default, and the one [`dev/install-release-plz`](../dev/install-release-plz) pins (Publishing → *The release-plz binary*).

**Driven on a scratch clone** (M54 Increment 9 T2), with `--registry-manifest-path` at a clone of the parent commit standing in for rc.21 as released: a `docs:` commit that edits `crates/cli/src/main.rs` changes no file (*"jigc: no commit matches the `release_commits` regex"*), and a following `feat(cli):` commit takes `jigc` `1.0.0-rc.21 → 1.0.0-rc.22`, leaves `jigc-engine` *"already up to date"*, moves `Cargo.lock` and writes `jigc`'s changelog. **Once a release is triggered, the changelog lists every commit that touched the package, not only the ones `release_commits` admits:** the docs commit appeared under *Other*. The filter decides *whether* a version moves, never what its changelog section holds.

**The constraint `release_always = false` leaves the bootstrap (Increment 10):** a publish starts only from the merge of a release PR, so the first versions reach `main` through a release PR, the path the rehearsal exercises — never through a hand-edited version pushed to `main`.

## Publishing

*Settled:*

- **Workflow `release.yml`; the publish job runs in GitHub environment `release`** with the human as **required reviewer** and **`can_admins_bypass: false`** — agents run `gh` with the human's admin credentials, so an admin bypass would let an agent skip the approval (set at the first halt, with the reviewer rule, once the repository is public; the free plan's support for it is verified then). The environment's **deployment policy admits branch `main` only** (policy 61391261; the `v*` tag policy 61287763, left from the superseded tag-triggered design, deleted), *[Corrected 2026-09-30, M54 Increment 9: this cited the `main` policy as 61320798; the environment's only policy, read by the API, is 61391261]* because the release job runs on the `main` push after the release-PR merge. The job does **not** key on a commit subject — the merge strategy is unchosen, and a default merge commit reads *Merge pull request #N*, not `chore(release)`. Instead a **preceding job outside the environment** checks whether any workspace package's version is missing from crates.io and outputs a flag; the environment-bound job `needs` it and runs **only when the flag is set**. So the approval prompt appears for a push that has something to publish and for no other.
- **crates.io Trusted Publishing** (OIDC): the job holds `id-token: write`, and **no `CARGO_REGISTRY_TOKEN` exists** in the repository. The trusted-publisher configuration on crates.io names repository `gherrink/jigc`, workflow `release.yml`, environment `release`, for both crates — **verified by the crates.io API** on 2026-09-30 (M54 Increment 9): config `22294` for `jigc`, `22295` for `jigc-engine` ([ci-runtime.md](../completions/artifacts/M54/ci-runtime.md)).
- **Publish order: `jigc-engine`, then wait until the index serves it, then `jigc`** — the `=` pin makes `jigc` unpublishable before its engine is resolvable.
- **Tags** are `<package>-v<version>` (`jigc-v1.0.0-rc.22`, `jigc-engine-v0.1.0-rc.1`), created by the release job; GitHub releases for an `-rc` version are marked prerelease.
- **Rehearsed dry before it runs for real — a required step.** Before the real rc.22 publish, the whole pipeline — release-pr, then release with `--dry-run` — runs on a **private throwaway repository, `gherrink/jigc-release-rehearsal`** (a mirror push of `main`), with the **same** GitHub App installed on it for the rehearsal, so the first run of the workflow's wiring is not the one that spends a version. It is **dry-run only**: Trusted Publishing is bound to `gherrink/jigc`, so nothing can publish from there. Afterwards the human uninstalls the App from it and **deletes the repository** — irreversible, so a human-confirmed step, never an agent's. **Rehearsed 2026-09-30, runs `36756306377` and `36761534078`, recorded by id in [release-rehearsal.md](../completions/artifacts/M54/release-rehearsal.md)** (M54 Increment 10): one release PR under the conditional title, carrying only the two generated changelogs; `missing=true` on both pushes; after the merge, the dry run behind the overlay step, `jigc-engine` then `jigc`, naming both tags; no tag or release created. It did not rehearse the approval prompt (Known gaps).
- **Real prerelease publishes, not dry runs.** M54's pipeline made its first real publish, **`jigc 1.0.0-rc.22`** plus **`jigc-engine 0.1.0-rc.1`**, on 2026-10-01 ([publish-proof.md](../completions/artifacts/M54/publish-proof.md)); M55 publishes the next. A crates.io version is permanent — that is why the pipeline is exercised on prereleases before the version that matters. The human approves each one at the environment.
- **CI checks publishability and the lock on every push**: `cargo publish --workspace --dry-run` and a lock-current check (`cargo metadata --locked`) are CI jobs ([dev-workflow.md](dev-workflow.md) → Gate).

**The workflow — pinned by the build** (M54 Increment 9, 2026-09-30). `.github/workflows/release.yml` runs on a push to `main` and nothing else. Its top-level permission is `contents: read`, and every checkout has `fetch-depth: 0`. `crates/cli/tests/release_pipeline_fence.rs` holds each row, and the letter is its arm. The file lints clean under `actionlint` 1.7.12, with shellcheck 0.11.0 on `PATH`, and with no ignores: the repository's actionlint config, whose two ignores covered 1.7.12's stale metadata for `create-github-app-token@v3`, was deleted with the SHA pins, which that metadata no longer matches (*Action pins*, below).

| Job | What it does | Arm |
|---|---|---|
| `release-pr` | Mints the App token (The release PR, above), checks out with it, installs release-plz through `dev/install-release-plz`, sets the git identity with `release-plz/git-config` on the token, and runs `release-plz release-pr` on it, with the argv `release-plz/action` `v0.5.139` built: `--git-token`, `--repo-url`, `--forge github`, `-o json`. | (m) |
| `check` | No environment. It runs [`dev/unpublished-versions`](../dev/unpublished-versions), which asks the crates.io sparse index whether each publishable workspace version is there, and outputs `missing`. It fails closed: a fetch or parse error writes no flag. | (l) |
| `release` | `needs: check`, `if: needs.check.outputs.missing == 'true'`, `environment: release`, permissions `contents: write` (tags and GitHub releases), `pull-requests: read` (release-plz's release-PR lookup) and `id-token: write`. It installs release-plz and sets the git identity as `release-pr` does, then runs `release-plz release --git-token … --forge github -o json` on the workflow's own `GITHUB_TOKEN`. It is the only job that holds `id-token`, and the workflow level grants none. | (k) |

- **No registry token, anywhere under `.github/workflows/`** (arm (i)). release-plz performs the Trusted Publishing exchange itself when no registry token is set and it is not a dry run. It mints one token before the first upload, reuses it for both, and revokes it afterwards.
- **Nothing keys on a commit subject** (arm (n)): no `if:`, `run:` or `${{ … }}` expression reads `github.event.head_commit` or `github.event.commits`.
- **Both release-plz jobs install release-plz `0.3.169` through `dev/install-release-plz`** (arm (o)), the release-plz every proof above ran, checked against the SHA-256 the script records (*The release-plz binary*, below). The order is fenced: checkout, install, identity, run. No workflow names `release-plz/action` any more (2026-10-01).
- **The rehearsal is keyed on the repository, never on an input a human sets** (arm (p)). Off `gherrink/jigc`, the release runs with `--dry-run`, and a step writes `[patch.crates-io] jigc-engine = { path = "<checkout>/crates/engine" }` into `$CARGO_HOME/config.toml` before release-plz runs. **Without that overlay, the rehearsal's `jigc` dry run fails**: its verify build cannot resolve the `=` pin on an engine version crates.io does not carry. With the overlay, the dry run exits 0 and handles the engine first (driven at Increment 9's planning). **Declared bound:** the rehearsal's `jigc` dry run verifies against the local engine, not a registry one. It is the same bound the tarball install carries (Verifying a publish). **The dry run is the `DRY_RUN` environment value `${{ github.repository != 'gherrink/jigc' && 'true' || '' }}`, read by the step's `run:` body, never spliced into it.** The body maps `true` to `--dry-run` and the empty string to nothing, and stops the job on any other value, so the bare boolean's string `false` cannot reach release-plz as a dry run of the real publish. That was the trap of `release-plz/action`'s `dry_run` input, which added `--dry-run` whenever it was non-empty. The fence runs the body verbatim against a stub `release-plz` for `true`, for the empty string and for `false` (2026-10-01).
- **Concurrency:** `release-pr` and `release` each hold their own group on the ref, and neither is cancelled in progress, so a release is never cut off mid-publish and the `release-pr` job is not held behind a release waiting at its approval prompt. Under GitHub's rule a newer queued job replaces an older *pending* one in its group, which is harmless here: the newer one carries the newer `main`. **Observed on `gherrink/jigc` on 2026-09-30** (runs `36753643562` and `36785068612`, [release-rehearsal.md](../completions/artifacts/M54/release-rehearsal.md) → The real repository): a job waiting at the prompt holds its group like a running one. The newer `release` job stays `pending` behind it and does not replace it, while the newer `release-pr` runs to success in its own group. What a third push does to that pending job is still unobserved. The rehearsal could not show any of this, because its environment has no reviewer and no job waited.
- **`timeout-minutes`:** `check` 10, `release-pr` 15 and `release` 30. The 30 minutes are the trusted-publishing token's life (`publish_timeout`, above). **Measured by the rehearsal** (2026-09-30, [release-rehearsal.md](../completions/artifacts/M54/release-rehearsal.md) → The six jobs): `check` 32 s and 30 s; `release-pr` **405 s and 488 s**, the history walk over the `0.0.0` placeholders, which is up to 54 % of its 15 minutes; `release` 34 s (a skip) and **108 s** (the dry run of both crates). The real publish's uploads and index waits are not in that 108 s.

**Action pins — by commit, never by tag** (2026-10-01, the M54 completion audit). Every `uses:` in `release.yml` **and** `ci.yml` names its action at a full 40-hex commit SHA, with the release tag it was read from as a trailing comment: `uses: actions/checkout@fbc6f3992d24b796d5a048ff273f7fcc4a7b6c09 # v5.1.0`. *Why:* a tag is a movable name, and `release.yml`'s jobs hold the crates.io OIDC token (`release`) and the App's private key (`release-pr`), so a moved or compromised tag would run new code with the right to publish a permanent crates.io version. `ci.yml` holds no publish rights; it is pinned the same way so one convention is fenced. `crates/cli/tests/workflow_action_runtime_fence.rs` holds every pin to a vetted `(action, sha, tag, runs.using)` row and every line to its tag comment; `release_pipeline_fence.rs` arm (o) reads the release-plz pin from that one home.

- **Pins are bumped deliberately, by hand — no Dependabot.** To move one: resolve the new tag with `gh api repos/<owner>/<repo>/git/ref/tags/<tag>`, dereferencing an annotated tag (`object.type: tag`) through `git/tags/<sha>` to its commit; read `runs.using` from `action.yml` at that commit (never `node20` or older; a `composite` action through the actions its steps use); move the fence's row and every `uses:` line with it. The fence reddens on any pin or comment that does not match its row.
- **What the pins cost:** `actionlint` carries input metadata per tag, so at a SHA it no longer checks the four actions' inputs. The inputs that matter to the release are held by `release_pipeline_fence.rs` instead: the App token's `client-id` and key (m), the release-plz argv, its version and its dry run, each of which is now a `run:` body or the install script rather than an action input (m, o, p).

**The release-plz binary — installed against a recorded digest** (2026-10-01, the M54 completion audit's finding 2, approved by the human). Both credentialed jobs install release-plz with [`dev/install-release-plz`](../dev/install-release-plz) instead of through `release-plz/action`. The script fetches release-plz's own x86_64 Linux release asset, the one `cargo-binstall` had picked on the runner, and refuses it unless its SHA-256 is the one below. Only then does it unpack the binary, check that it reports `release-plz 0.3.169`, and put its directory on the job's `PATH`. Any failure exits 1 before anything is placed on `PATH`. `crates/cli/tests/release_pipeline_fence.rs` arm (o) holds the script's version and digest to this row, and drives the script with two mismatching archives. One is garbage. The other is a well-formed archive carrying a `release-plz` that would pass the version check, so only the digest refuses it. Both exit 1, and neither places a binary.

| Binary | Version | Asset | SHA-256 |
|---|---|---|---|
| release-plz | `0.3.169` | `release-plz-x86_64-unknown-linux-gnu.tar.gz` | `1455106d3263712dd796ee04869eaee98b274e1e2e18011f67682b1f2840b64d` |

- **How the digest was read** (2026-10-01): the `digest` field GitHub reports for that asset on release `release-plz-v0.3.169` (`gh api repos/release-plz/release-plz/releases/tags/release-plz-v0.3.169`), and the same value from `shasum -a 256` over a fresh download. The script's success path ran in the `linux/amd64` runner-faithful image: it verified, installed, and appended its directory to `$GITHUB_PATH`, and the binary reported `release-plz 0.3.169`.
- **To move it:** read the new release's asset digest the same two ways, change `RELEASE_PLZ_VERSION` and `RELEASE_PLZ_SHA256` in the script and this row together, and re-read the argv the action built at the matching `release-plz/action` commit. The fence reddens on any disagreement between the script, this row and its own pinned version.
- **The bound that remains: trust on first use.** The digest is GitHub's record of a release asset, read once. The release is not marked immutable, and release-plz publishes no signature. A replaced asset now turns the job red instead of running in it, but the digest does not prove the asset is the publisher's.
- **What runs where.** The `release-pr` job runs the install path on every push to `main`. The reshaped `release` job's first real run is the next publish, M55's. Until that run, the only evidence for the `release` job's body is the fence's stub run of it.

**Declared bounds of the workflow:**

- **Until the first publish, every push to `main` raises an approval prompt.** The bootstrap's versions, `jigc 1.0.0-rc.22` and `jigc-engine 0.1.0-rc.1`, are not on crates.io, so `check` reports `missing=true` on every push. **Approving such a prompt publishes nothing:** `release_always = false` skips any commit that is not a release-PR merge. Rejecting it is equally safe. The same rule holds after every publish: a release-PR merge whose own deployment does not publish is published by no later push (Known gaps).
- **The App and its two secrets must exist before `release.yml` reaches a repository's `main`.** Otherwise the `release-pr` job goes red on its first step. This holds for `gherrink/jigc` and for the rehearsal repository alike, and each also needs its own `release` environment.

## Verifying a publish

*Settled:* the proof of a release is an **install**, not a build — and the two installs prove different things. M54 ran both: the tarball install before the publish (Increment 7) and the registry install after it (Increment 11).

- **Before the publish**, the `dev/runner-faithful` image installs from the packaged tarball. **Declared bound on `--locked`:** cargo 1.95's `--locked` uses the lock as written and does not refuse an incomplete or stale one, and the path/patch overlay that lets the tarball resolve its unpublished engine bypasses the engine's lock entry. So this install proves only *the packaged lock was used* — checked by byte-comparing the lock and by a compiled-in version check — not that a registry install reproduces it. **Pinned by the build** (M54 Increment 7):
  - **The command** is `dev/runner-faithful [--platform <os/arch>] [--commit <rev>] tarball`. On a clean clone of the named commit (default `HEAD`) it runs `cargo package --workspace`, unpacks both `.crate` files under the container's home, outside any workspace, and installs with `cargo install --path <jigc> --locked --config 'patch.crates-io.jigc-engine.path="<unpacked engine>"'`. Without the overlay the install exits 101, because the `=` pin names an engine the registry does not have. Its steps are `package` · `lock-compare` · `install` · `version` · `setup` · `probe-override` · `control-finalize` · `drift-finalize`. The first one that fails is named and exits 1. The last five are one function, `post_install <version>`, which the registry mode reuses.
  - **The compare.** A copy of the unpacked `jigc` is resolved with the **same overlay, unlocked** (`cargo metadata`), so cargo writes the lock it resolved. That lock must be **byte-equal** (`cmp`) to the packaged lock with exactly one rewrite removed: the one the overlay declares. The `jigc-engine` entry loses its `source` and `checksum` lines, and the compare refuses a lock where that removes anything other than exactly two lines. **What it proves:** the packaged lock is complete and current under the overlay, so the `--locked` install that follows builds from exactly its entries. **What it does not prove:** that a registry install resolves the engine's own entry the same way. That is the bound above, and the after-publish install closes it. *Why not compare the packaged lock with the workspace's `Cargo.lock`:* they legitimately differ, because `cargo package` prunes the engine's dev-dependencies (`proptest` and its closure) and re-spells the disambiguated names. *Why not compare the lock before and after the install:* cargo 1.95 re-resolves an ephemeral install workspace without writing anything back, so that compare stays green whatever the lock holds. **Controls, applied to the unpacked lock:** dropping the `anyhow` entry makes the compare red, because the resolved lock re-adds `anyhow 1.0.104`. Altering `anyhow` to `1.0.100` without its checksum also makes it red, because the resolved lock restores the checksum.
  - **The version check** asserts that `jigc --version` is exactly `jigc <v>`, where `<v>` is the commit's `crates/cli/Cargo.toml` `[package]` version, the source `stamp_of` reads. A mutated expected version makes it red.
  - **The flow.** The identity comes only from `GIT_AUTHOR_*`/`GIT_COMMITTER_*`. `JIGC_DOC_CODE_PROBE` must be unset. An arch-doc whose `implemented-by` anchor is `src/pad.ts#pad` finalizes with exit 0. Then `pad` is renamed and committed, and a **task editing that committed arch-doc** (its `overview` slot) finalizes with exit 3, naming `doc-code.symbol-exists`, with `HEAD` unchanged. The edit copies the doc in for update, and finalize re-gates its anchors, so the spike's fallback form (a new doc anchoring the missing symbol) is not needed.
  - **The platforms** are the host's (`linux/arm64` under colima) and `linux/amd64`, the runner's architecture.
- **After the publish**, the same image runs `cargo install jigc --version <v> --locked` against crates.io, then `jigc setup` in a throwaway repository and one flow that exercises the `doc-code` probe. **This is the first faithful registry proof.** The trial harness's **registry mode** installs by version the same way and is the blind trial's instrument ([completions/trial-harness/README.md](../completions/trial-harness/README.md)). **Pinned by the build** (M54 Increment 7):
  - **The command** is `dev/runner-faithful [--platform <os/arch>] registry [<requirement>]`, run as `dev/runner-faithful registry '^1.0.0-rc.1'` with the install line's requirement. No source tree enters the container and nothing is patched: it runs `cargo install jigc --version '<requirement>' --locked` against crates.io, then the same `post_install` the tarball mode runs. With the requirement omitted it runs the **unpinned** `cargo install jigc --locked`, which resolves nothing now that both placeholders are yanked (→ Installing). `--commit` names only the `rust-toolchain.toml` the image's toolchain is read from. Its steps are `install` · `version` · `setup` · `probe-override` · `control-finalize` · `drift-finalize`, and the first that fails is named and exits 1.
  - **The version check** compares `jigc --version` with the version `cargo install --list` reports it installed, because no source tree states one.
  - **Driven before the first publish** (2026-09-30, crates.io listing only the `0.0.0` placeholders, `linux/arm64`): `registry '^1.0.0-rc.1'` exits **1** at `FAIL install`, surfacing cargo's *could not find `jigc` in registry `crates-io` with version `^1.0.0-rc.1`*. `registry '=0.0.0'` and the unpinned `registry` each install the placeholder and exit **1** at `FAIL version`, because the placeholder prints its reservation notice, not `jigc 0.0.0`. So the positive proof was Increment 11's.
  - **Driven after the first publish** (2026-10-01, before H4, so both `0.0.0` placeholders were still unyanked): `registry '^1.0.0-rc.1'` exits **0** on `linux/arm64` (32 s) and on `--platform linux/amd64` (90 s), every step `ok`. It installs `jigc 1.0.0-rc.22` and `jigc --version` prints `jigc 1.0.0-rc.22`. `jigc setup` exits 0 and leaves `.jigc/AGENT.md`. `JIGC_DOC_CODE_PROBE` is unset. The control finalize exits 0, and the drift finalize exits 3 naming `doc-code.symbol-exists` with `HEAD` unchanged. The package declares a single `[[bin]]`, `jigc`, so the blocking probe is that binary's self-exec child. In the same session `registry '=0.0.0'` and the unpinned `registry` each exit **1** at `FAIL version`, so the line resolves `1.0.0-rc.22` and not the placeholder. **S9's bound is closed for this publish:** the published `Cargo.lock`, re-resolved against crates.io without an overlay, is byte-equal to itself, and its `jigc-engine 0.1.0-rc.1` checksum equals the registry's ([publish-proof.md](../completions/artifacts/M54/publish-proof.md) → The registry install).

## The main branch

*Settled 2026-10-01* ([DECISIONS.md](../DECISIONS.md) → *the branching switch*, decision 4). `main` is the trunk and changes **only through pull requests**; the branches that feed it are [CLAUDE.md](../CLAUDE.md) → Branches. Ruleset **24313429** (*main: no force-push, no deletion*) is extended to:

| Rule | Setting | Why |
|---|---|---|
| Pull request required | yes | Every change reaches `main` as a reviewed unit: a milestone, a fix, a work branch, a release PR. |
| Required status checks | **`ci-ok` only** | One aggregate that `needs` every CI job (below), so adding a job never means editing the ruleset, and a job left out of `ci-ok` reddens a fence instead of going unrequired. |
| Branch must be up to date | **no** | A milestone branch is not rebased onto every release-PR merge; the merge commit carries the integration, and CI runs on the PR's merge ref anyway. |
| Merge method | **merge commits only** — squash and rebase off | release-plz computes versions and changelogs from the conventional commits of the merged history ([Versioning](#versioning)); a squash would collapse a milestone into one subject. |
| Required approvals | none | The human is the only reviewer; his merge is the approval. |
| Bypass | **none, the human included** | A bypass the human holds is a bypass every agent holding his credentials holds (What agents may not do, below). |

**Applied at the end of the switch, by the human** — after the switch's own PR is open and green, so that PR is the first one under the rules; if the ruleset lands before the merge, the switch PR is simply merged through it. **Until it is applied, the ruleset blocks only force-push and deletion**, and the deny list below is the only thing between an agent and a push to `main`.

**`ci-ok`** is the last job of [ci.yml](../.github/workflows/ci.yml): `needs` every other job, `if: always()` — without it GitHub *skips* the job when a leg fails, and a skipped job reports success to a required check — and a body that is green only when every needed job's result is `success`. `crates/cli/tests/ci_matrix_fence.rs` arms (g) and (h) hold both halves ([dev-workflow.md](dev-workflow.md) → Gate).

## What agents may not do

*Settled:* **agents never merge the release PR, never push a tag, and never approve a deployment**; the deployment-approval API is denied in the agents' permissions (agent definitions and settings). **This is adapter-enforced, not by construction** — agents run `gh` with the human's own credentials, so a permission entry is the only thing between an agent and a merge — the same *adapter-enforced, not sandboxed* bet [VISION.md](../VISION.md) principle #3 names for jigc itself. The real fix is a **restricted agent token** that cannot merge, approve or tag, owed at [decisions-pending.md](decisions-pending.md) → *The road to 1.0.0 and the port* → *The 1.0.0 call*.

**The deny list — pinned by the build** (M54 Increment 9, 2026-09-30). `.claude/settings.json` → `permissions.deny` holds the entries below, and yanking a crate — the H4 act — sits beside the three. **Each entry was driven, not assumed:** Claude Code 2.1.284, `claude -p … --permission-mode bypassPermissions`, in a `mktemp -d` scratch repository holding a copy of the list, once directly and once through an Agent-tool subagent. Every probe command below reported a `permission_denials` record both ways. Each uses `--help` or a remote that does not exist, so nothing could happen had a rule failed.

| Entry | Act | Probe commands |
|---|---|---|
| `Bash(gh *pr merge*)` | merge a PR | `gh pr merge --help` · `gh -R gherrink/jigc pr merge --help` |
| `Bash(gh api *pulls/*/merge*)` | merge a PR (REST) | `gh api -X PUT repos/gherrink/jigc/pulls/1/merge --help` |
| `Bash(gh api *mergePullRequest*)` | merge a PR (GraphQL) | `gh api graphql -f query='mutation { mergePullRequest(…) … }' --help` |
| `Bash(gh api *enablePullRequestAutoMerge*)` | merge a PR (GraphQL auto-merge) | the same with `enablePullRequestAutoMerge` |
| `Bash(git *push *--tags*)` | push a tag | `git push nowhere-remote --tags` · `git -C . push nowhere-remote --tags` |
| `Bash(git *push *--follow-tags*)` | push a tag | `git push nowhere-remote main --follow-tags` |
| `Bash(git *push *refs/tags/*)` | push a tag | `git push nowhere-remote refs/tags/jigc-v1.0.0-rc.22` |
| `Bash(gh *release create*)` | push a tag (a release creates one) | `gh release create --help` · `gh -R gherrink/jigc release create --help` |
| `Bash(gh api *git/refs*)` | push a tag (REST ref creation) | `gh api -X POST repos/gherrink/jigc/git/refs --help` |
| `Bash(gh api *pending_deployments*)` | approve a deployment | `gh api -X POST repos/gherrink/jigc/actions/runs/1/pending_deployments --help` |
| `Bash(cargo *yank *)` | yank a crate | `cargo yank --help` |

- **The controls still run under the same list, both ways.** These are `git push origin main` and `git -C . push origin main` (the orchestrator's push), `gh pr view`, `gh run view`, `gh api repos/gherrink/jigc/releases`, `git ls-remote --tags` (reads Increments 10–12 need) and `cargo publish --workspace --dry-run`. Each reported no denial and ran.
- **The leading `*` is deliberate.** `gh *pr merge*` also catches `gh -R <repo> pr merge`, and `git *push …` also catches `git -C <dir> push …`. Compound commands (`cd . && gh pr merge …`) and an environment prefix (`GH_PAGER=cat gh pr merge …`) were denied as well: Claude Code matches each subcommand.
- **The settings are the enforced layer, and an agent definition only instructs.** Every definition under `.claude/agents/` carries one *Never* paragraph naming the four acts and pointing here. A scoped deny cannot live in a definition. Driven through the Agent tool, frontmatter `disallowedTools: Bash(gh pr merge:*)` removed Bash from the subagent **wholesale**, as a scalar and as a list alike; the same definition without it had Bash. (With `--agent`, planning found the scalar ignored.) `release_pipeline_fence` arm (q) holds both: the settings carry every entry above, and every definition carries the paragraph verbatim.
- **What the list does not stop** — each form either catches a control, or no pattern can see it:
  - **A command hidden inside another interpreter.** `bash -c 'gh pr merge --help'` ran (driven). So would a script file or a subprocess: the rules match the command line Claude Code sees, not what it spawns.
  - **A tag pushed by its bare name.** `git push <remote> jigc-v1.0.0-rc.22` reached git (driven), because no pattern tells a tag name from a branch name.
  - **A release, and its tag, created through REST.** `gh api -X POST repos/gherrink/jigc/releases` ran (driven). A pattern on `releases` would catch the `gh api repos/gherrink/jigc/releases` control, and `gh api` switches to POST on its own when it is given fields.
  - **A GraphQL mutation read from a file** (`-F query=@merge.graphql`) keeps the mutation's name off the command line. Reasoned, not driven.
  - **Acts that remove the protection rather than exercise it.** Editing the `release` environment's reviewers through the API, or editing `.claude/settings.json` itself, are outside the pinned set.
  - **The matcher is Claude Code's.** Arm (q) pins the list, not how a future Claude Code matches it, so an upgrade calls for re-driving the probes.

  The restricted agent token (above) closes every one of these at the credential, which no permission list can.

## The one-time bootstrap

## Known gaps

- **A publish whose tag step fails is not re-tagged by a re-run** — release-plz sees the version already on crates.io and skips it. The manual fix is the human's: create `<package>-v<version>` at the release merge commit, push it, and create the GitHub prerelease by hand.
- **A release-PR merge whose deployment does not publish is not retried by any later push.** If the merge commit's `release` job is rejected, expires at the prompt, or fails mid-publish (an index timeout, an OIDC exchange error), the version stays unpublished. From then on every push to `main` has `check` report `missing=true` and raises a prompt whose approval publishes nothing, because release-plz publishes only from a commit whose associated PR has a head branch starting `release-plz-` (`should_release` in `release_plz_core` 0.38.6, the core release-plz 0.3.169 requires; read, not driven). **The recovery is the human's:** reject the newer prompts first, since a job waiting at the prompt holds the group (Publishing → Concurrency). Then re-run the merge commit's own Release run, `gh run rerun <run-id> --failed`, which re-runs its `release` job on that commit, and approve the deployment again (not yet driven here). A package already on crates.io is skipped as *already published*, so a partial publish completes with the other one; a tag the skipped package lacks is the entry above. **Past GitHub's 30-day re-run window no recovery is driven.** The human can publish by hand from the merge commit, engine first, on a personal token rather than Trusted Publishing, and then tag as above. Or a new release PR can be merged, but whether release-plz opens one while the manifest is already ahead of crates.io (the bootstrap's *Only changelog will be updated* case) is unverified; it needs a commit `release_commits` admits, so a `docs:` or `chore:` commit cannot trigger one. `release-plz set-version` alone recovers nothing, since its commit is not a release-PR merge.
- **The build id does not see a same-version rebuild.** It is `CARGO_PKG_VERSION`, which catches the realistic skew (an upgrade mid-run) and not a dev rebuild at one version; on Linux, spawning `/proc/self/exe` removes the replaced-binary case outright ([module-layout.md](module-layout.md) → Probe boundary).
- **The OIDC exchange cannot be rehearsed.** The trusted-publisher configuration names `gherrink/jigc`, so the rehearsal repository cannot exchange its token for a crates.io one and `--dry-run` does not need one: the first exchange is the real rc.22 publish. Acknowledged at M54's planning, not fixable by design.
- **The approval prompt is unrehearsed.** The rehearsal repository's `release` environment has no required reviewer, and both rehearsal runs' approvals are `[]` ([release-rehearsal.md](../completions/artifacts/M54/release-rehearsal.md) → What the rehearsal did not exercise). No rehearsal job waited at a prompt or was approved. The first approval of a job that publishes is the real rc.22 publish, like the OIDC exchange above.
- **An agent can publish outside the pipeline.** `~/.cargo/credentials.toml` on the development machine holds a crates.io token that authenticates as the human: it answered the authenticated trusted-publisher API at Increment 9's planning. So `cargo publish` without `--dry-run` would upload from an agent's shell, and a deny pattern matches text, so it cannot require `--dry-run` to be absent without also catching the `cargo publish --workspace --dry-run` control. Whether to remove that token is the human's call at H2.
- **Agents cannot read the App's installation or its repository selection.** Their credentials are the human's `gh` OAuth token, and the installation endpoints refuse it: `gh api user/installations` answers 403 (*You must authenticate with an access token authorized to a GitHub App*), `repos/gherrink/jigc/installation` and `users/gherrink/installation` answer 401 (they want the App's JWT), and `apps/gherrink-jigc-release` answers 404. `release.yml`'s `create-github-app-token` step names no `owner` or `repositories`, so its token is scoped to the running repository and cannot list them either. So which repositories the App is installed on is the human's read, never an agent's, and a gate that needs it records the human's read verbatim beside what the API can show: a deleted repository's 404, and a run whose App-token step passed ([DECISIONS.md](../DECISIONS.md) → *Increment 11's installation leg is proved by three reads, not by listing the installations*). It sits beside the restricted agent token owed under What agents may not do: neither credential an agent can hold today reaches the installation.
