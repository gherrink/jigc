# Roadmap

The full-product build order — **the milestone spine**, risk-first, each milestone a runnable slice that *proves* one thing. This is sequencing, not design: each entry names what it proves and the [VISION](../VISION.md) workflow(s) it lands; the milestone-level *what* and *why* live in the design docs. For scope and the determinism boundary see [CLAUDE.md](../CLAUDE.md); for the *why* of the ordering, [DECISIONS.md](../DECISIONS.md).

This doc owns the **milestone spine** plus the increment decomposition of milestones *already planned*. A milestone is turned into ordered increments by the [milestone-planning workflow](milestone-planning-workflow.md) **when it is picked up** — never all milestones up front — so M2–M8 below stay milestone-only until then, while M1 (shipped) carries its full decomposition. Work-unit terms are `milestone > increment > task` ([structural-grammar.md](../design/structural-grammar.md) → Work-units); **tasks are not enumerated** — they're cut per-increment at pickup, so the list stays honest against what prior increments produced. *How* an increment goes from "not started" to "validated and committed" is the [increment workflow](increment-workflow.md); how a milestone *opens* and *closes* are the [planning](milestone-planning-workflow.md) and [completion](milestone-completion-workflow.md) workflows.

The ordering principle is **risk-first**: stand up the spine, retire the #1 technical risk in isolation, build the loop, prove the differentiators, then widen. The spine is strictly linear — each milestone builds on the one before.

## The milestone spine

Each entry is milestone-level only — its increments are cut by the [milestone-planning workflow](milestone-planning-workflow.md) when the milestone is picked up. M1 is shipped; its decomposition follows below.

### M1 · single-task execution loop — ✅ shipped (2026-05-31)
The core loop (discover → compose → execute → validate → finalize), proving it beats a plain `CLAUDE.md` via the superseding-decision flow. VISION: `single task execution`. **Decomposition below.**

### M2 · router + second work-workflow — ✅ shipped (2026-06-01)
A second work-workflow (`quick-fix` — commit-only, `allows-create: []`) ships and the cascade's `default-workflow` flips from `single-task` to a **router** (`creates-task: false`), so `jigc start "<intent>"` routes to a model-free selection among the work-workflows. **Proves:** the orthogonal `creates-task` / `default-workflow` knobs (designed in [write-commands.md](../design/write-commands.md), unexercised in M1) hold, and the model-free selection path. No new doctype. *Engine cost (corrected from the first-draft "no engine change" after the planning review — see [DECISIONS.md](../DECISIONS.md)):* a **minimal engine-native `catalog` data-value root** exposing the live work-workflow list to composition, plus the **`creates-task: false` compose contract** (no task minted, intent threaded by agent-substitution). Form D (`jigc start --workflow <X>`) was designed but never built in M1.

### M3 · spec-driven planning — ✅ shipped (2026-06-02)
The `spec` doctype + the flow that creates it, so a spec-driven workflow reads `{{@task.spec#…}}` (the MVP was deliberately spec-less). **Decomposition below.** **Proves:** the doc-creation differentiator beyond `adr`, and the intent → spec → implementation arc — `spec` earns its schema from its real creator and consumer, not up front. VISION: `project planning` / `milestone planning`.

### M4 · override application
Recorded **deltas** — `scalar-set` · `structural-op` by id (insert/replace/remove) · `slot-fill` · `tracked-fork` — applied through the cascade's 9-phase resolution so a project composes a workflow/schema **differently from the pack default without forking** ([overrides.md](../design/overrides.md)). **Proves:** principle #5's *individualize* half — customize one thing against a versioned base via tracked deltas, the cascade wired **live** (today the resolver is a unit-proven pure function with no runtime feeder — `cascade::resolve` is called only for the provenance header; compose reads from a single layer). **Sequenced before fan-out** because customization is core to the adoption story and touches far more of the system than the bounded concurrency primitive does.

### M5 · upgrade reconciliation
The other half of principle #5: the engine-native **`override-default` probe** + a guarded **`jigc upgrade`** that re-applies each recorded delta against a new pack version and reports **clean / conflict / orphaned** (stateless `base-hash` compare). On `conflict` it **blocks with a review route** (keep / re-target / drop, showing what changed) — the true 3-way-merge authoring is deferred (matching `file_state`'s own deferral, [reconciliation.md](../design/reconciliation.md)); `override-default`'s checks ship **blocking-by-default** (cascade-tunability is M6). **Proves:** principle #5's *inherit-upstream* half — *inherit every upstream improvement for free; every divergence surfaces at a known moment* — entirely unbuilt in code today (no `upgrade` command, no probe, no version trigger). Rides on M4's recorded-delta substrate — hence immediately after it ([overrides.md](../design/overrides.md) → Upgrade reconciliation). *(Split from the old combined M5 — see [DECISIONS.md](../DECISIONS.md) 2026-06-03; the severity subsystem the probe's tunability rests on became M6.)*

### M6 · severity tuning & demotion-lock
The validation-severity subsystem the cascade has always promised but no probe yet honors: **severity assigned via the cascade** (every tunable probe site reads `validation.<probe>.<check>.severity` from `project > team > pack-default` instead of a hardcoded literal), **per-check knob granularity** (replacing M4's per-probe keys), the **intrinsic / tunable two-tier** model with the **demotion-lock floor** (a `scalar-set` demoting an intrinsic check below `blocking` is rejected at cascade resolution), and a **non-task probe entry point** so non-task-scoped probes (like `override-default`) participate. **Proves:** "severity is a cascade setting, never a code change" ([validation.md](../design/validation.md) → Severity inventory) holds end-to-end. **Sequenced here** to finish the override/validation theme (M4 apply · M5 reconcile · M6 tune) before the concurrency primitive — and because nothing in the product yet *needs* tunable severities, so it follows the milestone that introduces the first tunable probe (`override-default`). *(Split from the old combined M5 — see [DECISIONS.md](../DECISIONS.md) 2026-06-03.)*

### M7 · milestone execution — the deterministic join core (data plane)
The engine half of the single bounded concurrency primitive: a **`milestone` work-unit** (`milestone > task`, one shared base) with task-list verbs (`create` / `add-task` / `add-from-spec`), **isolated sub-task area dirs** + a **join-time isolation check**, **parallel doc minting** with a deterministic task-id-ordered collision-suffix + intra-doc self-ref rewrite (over `created` vs `edited-from-base` provenance), and the **by-task-id join merge** (edge-index "site 4") — a disjoint union, **blocking** on a same-doc clash, with **cross-area refs rejected** (resolved per sub-area against `committed ∪ that sub-task's own area` only). **Proves:** the join is a *pure function of the set of sub-task areas* — reproducible regardless of completion order — proven by **permutation tests over real multi-area fixtures** (not a real agent spawn; that's M8). The **highest architectural risk**, isolated to the engine data plane. *(Split from the old combined M7 — see [DECISIONS.md](../DECISIONS.md) 2026-06-04; the spawn binding + workflow + genuine end-to-end became M8.)* VISION: `milestone execution`.

### M8 · milestone execution — spawn binding + acceptance (control plane) — ✅ shipped (2026-06-05)
The assistant half: **`fan-out`/`join` step kinds** + the spawn-instruction emit class, the **`{{milestone.tasks}}` data-value root** the fan-out step consumes, the **adapter spawn binding** + the `jigc workflow W --task <id>` sub-agent re-entry + the **write-time `--task`-scoped barrier**, the **`milestone-execution` workflow** that composes the fan-out over `{{milestone.tasks}}` (entered via `jigc milestone execute <id>`), and the **genuine real-Task-tool end-to-end** acceptance ([worked-examples.md](../design/worked-examples.md) flow 10, driven by real spawn). **Proves:** parallel sub-agent work stays reproducible *under the blackboard model end-to-end* — the CLI emits spawn instructions deterministically, the adapter launches, the M7 join recombines. Rides directly on M7's data plane. *(Split from the old combined M7 — see [DECISIONS.md](../DECISIONS.md) 2026-06-04.)* VISION: `milestone execution`. **Decomposition below.**

### M9 · project setup (new & existing) — ✅ shipped (2026-06-06)
The setup workflows: bootstrap a **new** project (with idea development) and **ingest an existing** one. **Proves:** jigc wires into a real project from zero. **Last of the foundational spine** because it is the broadest and least-defined — legacy ingestion was flagged research-grade in [VISION.md](../VISION.md) → Open questions (bounded to detect-and-route; auto-migrate deferred). VISION: `project setup (existing)` + `project setup (new + idea development)`. **Decomposition below.**

## The post-spine arc (M10–M14)

The foundational spine (M1–M9) is complete — the MVP loop, the override/validation theme, the milestone-execution primitive, and project setup all shipped. The post-spine arc completes the product: the **last deferred differentiator** (doc↔code validation), the **introspection surface**, the **designed terminus** (self-hosting), the **doctype/surface completion** the terminus reveals, and the **generalization** (multi-pack). Created 2026-06-06, shaped suggestion-by-suggestion ([DECISIONS.md](../DECISIONS.md) 2026-06-06). Still strictly linear and milestone-level only — each is decomposed by the [milestone-planning workflow](milestone-planning-workflow.md) when picked up. The one hard dependency: **multi-pack (M14) needs a second pack, which self-hosting (M12) mints** — so it sits last.

### M10 · doc↔code validation — the pack-provided probe family
The first pack-provided **probe** and first pack-provided **field type** — the embedded dev pack already supplies doctypes/workflows/steps/commands, so what's new here are the *probe* and *field-type* extension axes (engine-native until now): the **subprocess probe contract** + the **pack-probe determinism contract** ([validation.md](../design/validation.md) — six rules + four meta-finding failure modes) that let the *dev pack* supply `doc↔code` checks, plus the **`code-anchor`** field type (+ adjudicator) that lets `adr`/`spec` reference code structurally. **Proves:** VISION principle #6's headline — *validate against reality, the integration advantage* — documentation drift caught deterministically at the task boundary (an `adr` citing code that no longer exists; a `spec` criterion that maps to no test), the differentiator deferred since the MVP shipped only the engine-native probes (`workflow-refs`, `file-state`). **Bounded slice (to decompose at pickup):** the mechanism + **symbol/file existence** (floor) + **criterion→test mapping** (headline — the VISION example + the spec's reason to exist) + the `code-anchor` field type; **staleness** (code changed after the doc) a stretch. **The determinism contract is *satisfied, not waived*** — the six rules (no network/model/time/random, read-only fs outside scratch, bounded resources, JSON-only IO) are binding and the meta-findings detectable without OS isolation (timeout / crash / malformed-output) are enforced ([validation.md](../design/validation.md) → Pack-probe determinism contract: *"cannot ship without satisfying the contract"*). What's **deferred** is **OS-level sandboxing** (seccomp / Landlock) + the sandbox-violation meta-finding it backs, under the **trusted-pack** model (the only pack is our own; safely running an *untrusted* third-party probe is the post-MVP "not a public API yet" line). Whether `doc-code` ships subprocess-from-the-start or as an in-process prototype that still satisfies the contract is an M10-planning call. Targets the shipped `adr`/`spec`; `arch-doc↔code` rides the same mechanism at M13. VISION: the validate loop (`jigc validate`).

### M11 · describe / introspection — the self-description surface
`jigc describe` — an on-demand **prose projection of the resolved definitions** (`project > team > pack-default`) an LLM calls (or is pointed at via left-behind pointers) to orient on *what can be composed here and how it's used*: the **menu**, distinct from bootstrap's runtime-nudge, `--explain`'s single-command, and validation's correctness-check ([design/introspection.md](../design/introspection.md) — direction locked 2026-05-30, planned + promoted 2026-06-07). **Proves:** the document model applied to jigc describing *itself* — structure CLI-owned, prose human-authored, assembly deterministic and cascade-reflecting; it can't drift because it's generated from the same definitions that drive composition. **Two constraints (locked):** *facts, not advice* (what exists + how it's used, never "you should compose X" — advisory output would hand structural judgment back to the LLM, the thesis inverted one level up); and *non-contractual by design, enforced by format* — the authored `description:`/`usage:` prose is *assembled* through the cascade (the CLI makes no LLM calls) and stays discursive/**hostile to parsing** so nothing depends on it (dissolving the "not a public API" non-goal). **The substantive design work (the open thread, to settle at planning):** which definition types carry the authored fields — **workflows + doctypes the floor**, command-refs + data-value roots a stretch — required-vs-optional per type, and the **cascade merge semantics** (replace vs append when a project overrides a pack's authored prose). De-parked at M11 planning: promoted to [design/introspection.md](../design/introspection.md), wired into the reading order. **Ordering:** before self-hosting (M12) deliberately — the methodology-pack dogfood is exactly what an agent would `describe` to learn the methodology. *Caveat (for M11 planning):* `describe` projects **usage/intent prose** (`description:`/`usage:`), **dialect-shape-agnostic** by the facts-not-mechanism constraint, so it survives M12's dialect extensions; if M11 planning finds the projection must reflect step *structure*, re-order M11 after M12. VISION: a new read-path surface (the introspection loop).

### M12 · self-hosting — distill the harness into a methodology pack + dogfood *(exploratory)*
The project's **designed terminus** ([self-hosting.md](../design/self-hosting.md)) — and deliberately **exploratory**, not a locked design. Three moves: **distill** the hand-run harness (the [planning](milestone-planning-workflow.md) / [increment](increment-workflow.md) / [dev](dev-workflow.md) / [completion](milestone-completion-workflow.md) workflows + their folded learnings) into portable, project-agnostic form (the four-part graduation pass — portability · rationale index · enforced-vs-trusted · a forward-review of the process itself); **encode** it as a jigc *methodology pack* (workflows as definitions, gates as probes/steps); **dogfood + measure** on a fresh project, tracking halts/fix-rounds/audit-findings against the M1–M9 hand-run baseline. **Proves:** jigc can run its own development methodology on a fresh codebase — and, as a forcing function, **sorts the harness into the three-way determinism cut** the product exists to draw: *mechanizable step* (becomes a probe/lint) · *irreducible judgment* (stays the agent's — gap-detection, design-review, settle) · *owner-assigned recorded artifact* (real but un-automatable — the M8 genuine-spawn class). **Honest caveat:** distilling-into-jigc ≠ automating judgment — jigc owns the *structure* (compose, place writes, walk deterministic gates), the agent fills the judgment slots. **The hidden weight (why exploratory):** encoding multi-phase, human-gated, fan-out workflows as jigc definitions needs **workflow-as-managed-artifact dialect surface beyond the MVP** (human-gate steps, conditional phases, bounded fix-loops, the owner-artifact gate) — which **can only be designed by attempting the encode**. So M12's first slice is *distill + encode one workflow (the dev-workflow is simplest) + a bounded dogfood*, and the attempt **may reveal a dedicated workflow-dialect-extension milestone** (named when M12 surfaces its shape — not guessed now). **What M12 dogfoods (the M13 seam):** M12 encodes the *workflows*; the methodology's own working docs (roadmap / deferral-ledger / decisions-log) stay **plain markdown** — **direct/unmanaged file edits under workflow instruction, not jigc-placed writes** (the "jigc places every write" proof, [self-hosting.md](../design/self-hosting.md), waits for M13's doctypes) — the encoded workflows read/write them at fixed paths; *graduating* them to managed doctypes is the M13 fold-back (a fold-back can't precede the thing it enables). Read this consequence honestly: M12's baseline comparison measures **workflow-composition fidelity**, not yet self-managed methodology docs. (If M12 planning finds the dogfood can't be faithful without a specific doctype — e.g. `Scope` mechanically consuming a *managed* deferral-ledger — promote that one doctype into M12, leaving the rest in M13.) **Done/good:** a fresh project, jigc-driven, **matches or beats the hand-run build-health trend** on a comparable-difficulty milestone *and* the judgment slots stay genuinely exercised (not hollowed). Open thread: which project to dogfood — ideally **unlike jigc**, so jigc-shaped gates aren't flattered by a jigc-shaped project. **Prereqs:** M7/M8/M9 ✅ for the *substrate*; the **workflow-as-managed-artifact dialect surface** that [self-hosting.md](../design/self-hosting.md) + [VISION.md](../VISION.md) name as a hard prerequisite is deliberately **re-cast here as *discovered by attempting the encode*** (the hidden-weight note above), not pre-built — so "substrate prereqs ✅" is not "fully unblocked." **What M12 composes (the M14 seam):** M12's dogfood runs the **methodology pack as the sole composed pack** — whatever dev surfaces it needs (`commit`/`adr`, the dev loop) are **vendored into or subsumed by** the methodology pack, *not* co-composed with a separate dev pack; **true dev + methodology multi-pack co-composition is M14's distinct proof**. This breaks the M12↔M14 circularity (M14 needs the pack M12 mints, so M12 must not need M14's composition to run). Whether the methodology pack *subsumes* the dev surfaces or stays thin (so only M14 composes it with dev) is an M12-planning fork. **Mints the second (methodology) pack M14 needs.** *Planning settled 2026-06-07 — de-parked to [self-hosting.md](../design/self-hosting.md); the four forks resolved (reduced-linear dev-workflow encode · subsume · composition-fidelity bar · `gherrink-galey` dogfood) and the decomposition cut below.*

### M13 · doctype & surface completion — the self-hosting fold-back
Acts on what M12's dogfood reveals: the doctypes the methodology needs that don't exist yet, each **earning its schema from its driving workflow** (the M3-`spec` / M9-`prd` discipline), plus the fold-back of M12's emergent learnings. **Two halves.** (1) **`arch-doc` finally earns its driver** — *living architecture documentation*, named in VISION's starting set and driverless since ([doctype-map.md](doctype-map.md): the `cites→adr` edge already drafted), via a general architecture-documentation workflow; this also activates **`arch-doc↔code`** over M10's probe mechanism (the richest doc↔code case, now with a doc to check). (2) **The methodology's own working docs graduate from hand-run markdown to managed doctypes** — the **roadmap**, the **deferral-ledger** ([decisions-pending.md](decisions-pending.md)), the **decisions-log** ([DECISIONS.md](../DECISIONS.md)) — each with the authoring workflow that creates/maintains it. **Proves:** VISION's named *starting set* is complete (`arch-doc` was its last unbuilt doctype), **plus** the methodology working-doc candidates (roadmap / deferral-ledger / decisions-log) folded back as managed doctypes *if M12 earns them* — so jigc manages the methodology's own documents, the self-hosting loop closed. **Two honesty flags:** the exact doctype set is **candidate, not locked** — it's confirmed at planning *after* M12 surfaces what the dogfood actually needs (the four above are the visible candidates); and each is an **engine/pack-split call** (a roadmap / deferral-ledger is broadly useful → dev pack; a decisions-log may be methodology-pack-specific). Depends on M12 (folds back what it revealed); before M14 (richer doctypes only help multi-pack). *Surface completion = the named graph, **nodes and edges**:* M13 planning also triages the still-open named relations (e.g. `spec —decided-by→ adr`, [doctype-map.md](doctype-map.md)) in-or-out, not just the `arch-doc` node. VISION: completes the `arch-doc` row in [doctype-map.md](doctype-map.md). **Planning settled 2026-06-07 — M13 = half #1 (`arch-doc`) only; half #2 (methodology working-docs → managed doctypes) deferred behind the dialect-extension milestone** (its drivers, the planning/completion workflows, are unencoded — M12 earned zero methodology doctypes), per [architecture-documentation.md](../design/architecture-documentation.md) + [decisions-pending.md](decisions-pending.md). The human chose the **repeatable-component** arch-doc shape (real engine surface: a per-field-type `check:` predicate selector + the item-authoring verbs), relations triage → only `cites → adr` IN. **Decomposition below.**

### M14 · multi-pack composition
One project composing **>1 domain pack** at once (dev + methodology) — how packs compose in the cascade. Today the cascade is `project > team > pack-default` with a **single** pack-default; M14 makes pack-default a composition of **multiple** packs, with deterministic **collision resolution** (two packs defining the same doctype / workflow / command id) and pack precedence/namespacing. **Proves:** the architectural invariant *engine-neutral, packs supply content* generalizes — real architecture validated at scale, not just internal discipline. **Bounded slice (at planning):** compose **our two packs only** (dev + methodology) with deterministic collision rules. The bound is at the **publication** boundary, not the *generality* one: the precedence/namespacing **mechanism is inherently general** (it can't honestly be cut to a two-pack special case), but it **stays internal — not published or stabilized as a public pack-authoring API**. VISION's *"not a second domain / not a public extension API"* non-goal holds at that publication line (two packs compose internally without jigc becoming a public pack platform). **Blocked until a real second pack exists — M12 mints it (the methodology pack), so this sits last; and M12's dogfood deferred dev + methodology co-composition to here, so M14 is its distinct proof, not a repeat.** VISION: [Open questions](../VISION.md) → Multi-pack composition.

## The adoption arc (M15–M17)

The post-spine arc (M10–M14) completed the *product*; this arc **completes self-hosting and then proves adoption in the wild**. M12 ran only a *reduced-linear* dogfood (the dev-workflow, judgment steps as prose); M15 + M16 **close the self-hosting loop** (encode the *harder* harness workflows + graduate the methodology's own working docs to managed doctypes), and M17 runs jigc on *real* projects with a *measure* of whether it actually helps the agent. Created 2026-06-08 after the post-spine arc closed, on the human's direction (multi-domain composition proven → drop the single-domain framing; build the two self-hosting-completion prerequisites, then dogfood-and-measure). Milestone-level only — each decomposed by the [milestone-planning workflow](milestone-planning-workflow.md) at pickup. *Settled at pickup:* **M15** shipped the increment-workflow encode (the `checkpoint` step kind, 2026-06-09); the **M15/M16 boundary** resolved by moving the deferred planning/completion encodes into **M16**, which now **fuses** them with the working-doc → doctype graduation (earn-from-driver). **Gap-filling is need-driven** ([decisions-pending.md](decisions-pending.md)): M15 + M16 are the *only* deferrals built **ahead** of need (the human-set prerequisites); every other deferral fills **when a dogfood surfaces it as actually blocking**, never speculatively.

### M15 · workflow-dialect extension — ✅ shipped (2026-06-09)
Encoding the harness's **harder** workflows (increment / planning / completion) as jigc definitions needs dialect surface the MVP lacks — M12's reduced-linear encode **named five triggers**, each with the failure class it prevents ([self-hosting.md](../design/self-hosting.md) → The named dialect-extension trigger; [decisions-pending.md](decisions-pending.md)): **(1)** a mechanizable **test-first-ordering / assertion gate** (the headline — prose → structure; the M14 `A==A`-oracle lint rides here as a candidate sub-check), **(2)** a structural **human-gate / checkpoint step kind** (the most-reused — planning's Settle, increment's halts), **(3)** a **portable gate-command knob**, **(4)** a **bounded fix-loop primitive + halt→re-run resumption**, **(5)** an **owner-assigned-artifact gate step** (the M8 genuine-spawn class). Conditional steps stay **barred** (the task-independence invariant). **Proves:** jigc can compose its *own* multi-phase, human-gated, fix-looping development workflows — the deepest self-hosting proof, beyond M12's reduced-linear slice. **Likely slices at planning** — the trigger fires on "the *second* harness workflow (increment or completion)," so the increment-workflow encode is the natural first slice; the full set may span more than one milestone. **Prereq #1 — built ahead of the dogfood on the human's direction.** VISION: closes the *exploratory outcome* M12 predicted.

### M16 · close the self-hosting loop — encode planning/completion + graduate the working-docs they drive — ✅ shipped (2026-06-09)
**Re-scoped 2026-06-09 (the fuse decision, [DECISIONS.md](../DECISIONS.md)):** M15 sliced to the increment-workflow only, so M16's doctype drivers — the **planning and completion workflows** — are still unencoded. By earn-from-driver a doctype earns its schema from the workflow that authors it, so M16 now **encodes each driver and graduates its doctype in one motion** (the M13 `arch-doc` pattern), rather than retrofitting doctypes onto separately-encoded workflows. Two halves: **(1)** encode the **planning** workflow (Settle = the human-gate = the **checkpoint step kind M15 already built**, so *no new dialect primitive*) + graduate the **roadmap** + **deferral-ledger** ([decisions-pending.md](decisions-pending.md)) doctypes it authors; **(2)** encode the **completion** workflow — which forces the deferred **#5 owner-assigned-artifact gate** (the genuine-spawn class, a *new* dialect primitive) — + graduate the **decisions-log** ([DECISIONS.md](../DECISIONS.md)) / completion-record doctype. Each doctype is an **engine/pack-split call** (a roadmap/ledger is broadly useful → dev pack; a decisions-log may be methodology-specific). The honest single-agent-spine bound holds as in M15 (the multi-agent orchestration stays the build harness's). **Likely slices at planning — planning-half first (cheaper, rides the checkpoint), completion-half second (builds #5).** **Proves:** jigc composes its full planning/completion workflows *and* manages its own methodology's documents — the self-hosting loop fully closed. **Prereq #2 of the adoption arc.** Was M13 half-#2 + the M15-deferred planning/completion encode, now fused.

### M17 · dogfood + measurement
**Planned + settled 2026-06-12** ([DECISIONS.md](../DECISIONS.md) → M17 planning; design home [measurement.md](../design/measurement.md)). Run jigc to develop **real** projects, and **measure whether it helps the agent** — the three-way cut applied to measurement itself: **mechanized facts** — **adapter-adherence** (managed-doc writes *through* jigc vs. OOB edits, deduped per path per run — the core-bet signal, since the adapter is *enforced-not-sandboxed*) and **drift-caught** (finalize blocks keyed on a distinct validation-blocked exit code — the *validate-against-reality* payoff) — · **protocol-counted facts** — **build-health** (halts / fix-rounds / audit-findings, counted from transcript + hook log per written rule, *not* engine-emitted; this homes the M12-deferred quantitative comparison **as protocol**, its hand-run-trend comparator **superseded by the A/B control**) — · the **verdict** ("is the agent working well with jigc?") a **human/LLM-judge slot**, never an engine opinion. Capture = a versioned PostToolUse **hook artifact** + three binary soundness increments (finalize-success findings emission · absorb baseline-advance at landed finalize · the exit code); the per-run **`dogfood-record`** doctype (spiked green through the binary at planning) is authored through jigc in the twin and exported. **Three real test cases, pilot-first behind a four-condition gate:** (1) the **pilot** — `gherrink-galey` (unlike-jigc, TS — jigc-shaped gates can't flatter a jigc-shaped target, the M12 lesson) **+ the A/B control** (twin /tmp copies at one baseline, matched real intent as a single dev-task vs. the repo's own static `CLAUDE.md`); (2) **`gherrink-lacon`** — existing project with a real docs corpus composed in (exercises M9's ingest/detect-and-route — *note:* non-conformant foreign docs route to a human, not auto-migrate, capping how "automatic" this case feels — [legacy auto-migration](decisions-pending.md) stays deferred; the one case where doc↔code genuinely adjudicates, Rust); (3) a **human-driven greenfield** from `jigc setup` onward (intent named at the pilot gate). ## Increment 1 — `Leaf::Repeatable`: the multi-level repetition lift (the headline risk)

**Deliverable:** the schema model expresses a repeatable nested inside a repeatable, and a two-level instance parses, renders, validates, and is addressable — round-tripping byte-stable. General recursion with a documented depth cap; the changelog exercises exactly two levels.

**Grouped scope:**
- **Schema variant** — add `Leaf::Repeatable(Repeatable)` to `crates/engine/src/schema.rs` (`Leaf = Slot | Field` today); the loader parses a nested `repeatable:` under a block leaf. **Heading-depth grammar:** item heading level = `2 + nesting-depth` (section `##`, L1 item `###`, L2 item `####`), capped at **H6 (4 levels)** — a documented cap, not silent truncation.
- **Depth-aware recursive parse** — `parse.rs` (`ItemTemplate::from`, `parse_items`, `next_section_heading`, `is_reserved_depth`): the item-region scanner treats a deeper heading as a sub-item boundary within its parent's region and recurses per the schema block; the duplicate-anchor `seen` check **resets per parent item** (two releases may each carry `#added`; one release with two `#added` blocks).
- **Recursive render** — `write.rs` `render_item` emits headings at the schema depth and recurses; a nested item's `{#id}` anchor is deterministic from its `id-from`.
- **Recursive validate** — `validate.rs` `check_repeatable` recurses, running required-slot/required-field/field-value conformance over each nested item's leaves at every level.
- **Parent-scoped path locator (NOT a vocabulary extension — review finding S1)** — replace the global single-level `write::locate_item_block` (matches at `###`, by anchor alone, globally) with a locator that resolves `item/subitem` by walking each path segment within its parent's byte region; `set_item_slot`/`set_item_field`/`add_item` and the `target_surface.rs` address builder consume it, so `#section/item/subitem/leaf` resolves unambiguously.

**Proves:** a fixture doctype with a two-level repeatable round-trips byte-stable cold and warm; a hand-malformed nested entry (empty required nested slot) **blocks** at `schema-conformance.required-slot-present` naming the **nested** leaf address; two same-anchor groups within one parent block while across two parents pass; nested `add-item`/`set-slot`/`set-field` reach the nested item. ## Milestone 23 — auto-migration (G1, changelog-first): decomposition

**Planned + settled 2026-06-14** ([DECISIONS.md](../DECISIONS.md) → 2026-06-14 M23 planning; design [auto-migration.md](../design/auto-migration.md)). **Four increments, risk-first + linear:** the headline net-new **migrate spine** first (verb + source seam + migration workflow, staged-only — fail-fast on whether the LLM-rewrite-through-CLI shape composes and yields a conformant staged doc), then the small independent **enum-on-id-from** conformance-rigor lift (the "adopt iff conformant" guarantee the adopt gate leans on), then the riskiest **commit boundary** (the review gate + the first byte-destructive retire + adopt, transactional), then the **flow-25 end-to-end acceptance + the measured corpus run** that consumes all three. ## Increment 1 — the `migrate` spine: verb + CLI-owned source seam + migration workflow (staged-only)

**Deliverable:** `jigc migrate <path> --as changelog` reaches a root `Unmanaged` foreign `CHANGELOG.md`, mints an **off-router** migration task (the `record-change` shape: `creates-task: true`, `selectable: false`, `allows-create: [{type: changelog, as: changelog}]`), stages the foreign bytes, surfaces them into the composed `migrate-changelog` workflow via a **CLI-owned source seam** (a read-only context placeholder, syntactically distinct from a managed-doc `{{@…}}` deref), and the LLM authors the canonical `changelog` through the existing `doc create` / `add-item` / `set-slot` / `set-field` spine. Ends at a **staged, conformant** changelog in the task working area — no commit/retire/adopt yet.

**Grouped scope:** the `migrate` CLI verb + dispatch (`crates/cli/src/cli.rs` + a new `migrate.rs`); the off-router migration task minting + foreign-bytes staging into the task; the source seam (the read-path placeholder + its resolution in `compose.rs`/`data_value.rs`, carrying raw foreign bytes as read-only context); the `migrate-changelog` workflow + its author step (dev-pack, mirrors `record-change`/`author-change`); the historical-`date` authoring path (`set-field …/date` overwrites the on-create stamp — verified at planning).

**Proves (red on real input):** `jigc migrate <real foreign CHANGELOG.md> --as changelog` over a `git init` temp repo mints the task and composes with the **foreign content present** in the emitted workflow (the seam resolves); driving the author spine produces a staged `changelog/changelog.md` that **round-trips byte-stable** (`render(parse(staged)) == staged`), with a multi-release foreign file authored from scratch in one task (cold/empty spike: a single-release and an empty-`[Unreleased]` foreign file both author clean). Built against [auto-migration.md](../design/auto-migration.md) → The mechanism (verb / source seam / migration workflow).

## Increment 2 — enforce the `enum` on `id-from` fields (conformance rigor)

**Deliverable:** the strict conformance gate rejects a change-group whose `category` (an `enum`-typed `id-from`) is outside the enum, so "adopted iff conformant" is real for the one enum the changelog has. A **new** validate code path reads the id-from value off the parsed item **heading** (not `item.fields`) and, when the field declares an `enum`, checks membership by **re-slugging** the heading value against the slug-form enum members — `Fixed`→`fixed` passes, `Performance`→`performance` is rejected; no coercion.

**Grouped scope:** the new id-from enum check in `crates/engine/src/validate.rs` (`check_item_leaves`); pin the emitted finding code (expected `schema-conformance.field-value-conformant`) + the slug-cased address, and update [worked-examples.md](../design/worked-examples.md) flow-25 RED 1 to the pinned shape. **No blast radius:** a non-`enum` `id-from` stays exempt — every other shipped doctype's `id-from` is a `title`/`key` string (verified at planning), so none newly fails (the regression watch asserts this).

**Proves (red on real input):** a foreign `Performance` change-group **blocks** at conformance naming its slug-cased address; a `Fixed`/`Added` change-group **passes** (re-slug membership); the existing doctypes (`adr`/`spec`/`prd`/`arch-doc`/methodology) conformance is **unchanged** (regression watch). Built against [auto-migration.md](../design/auto-migration.md) → Engine/validation work #1.

## Increment 3 — the commit boundary: review gate + retire + adopt (the first destructive op)

**Deliverable:** on a migration task, `jigc task finalize <id>` *without* `--approve` renders the **fidelity diff** ({staged source-seam bytes} vs {the task working-area rendered doc}) and **exits non-zero, committing nothing**; `finalize <id> --approve` executes the transaction: write the canonical doc → **retire the foreign original** → `git` commit → adopt, **all-or-nothing**. Rejection (no `--approve`) is byte-safe — the foreign original is untouched, nothing adopted.

**Grouped scope:** the net-new finalize `--approve` gate + the fidelity-diff render (a finalize-time gate, **not** the compose-time `checkpoint` step kind); the retire step as a `FinalizePlan.retirements` field (`crates/engine/src/finalize.rs`) executed **inside the commit closure** so `git add --all` stages the deletion (`crates/cli/src/task.rs` → `try_execute_finalize_plan`); **extend `rollback_promotions`** to restore each retired path on commit failure (so an approved-but-failed commit never leaves the foreign file deleted with no commit — review B1); the **path-collision guard** (foreign path == canonical managed path → skip retire, rewrite in place — review S1, handles the in-`changelog/` squatter); the adopt-after-write (the existing register-only `index.absorb_doc` + file-state hash).

**Proves (red on real input):** `--approve` on a conformant migration writes `changelog/changelog.md` byte-stable, the foreign original is **gone**, a follow-up `ingest` reports it `adopted`; finalize **without** `--approve` blocks (non-zero, no commit, foreign file intact); a **human-reject** (discard) leaves the foreign original untouched and the edge index unchanged; a **commit-failure-after-approve** (seeded hook reject) **rolls back** the retire (foreign file restored). Cold/empty spike: migrating a single-release file commits + retires clean. Built against [auto-migration.md](../design/auto-migration.md) → The review gate / Retire-the-foreign-original.

## Milestone 4 — override application: decomposition

Cut 2026-06-03 via the [`/milestone-plan`](../.claude/commands/milestone-plan.md) command (scope → detect gaps → settle → review → decompose). Four `capability-auditor` subagents established the baseline, four `gap-detector` subagents + an independent `design-reviewer` reshaped the design ([DECISIONS.md](../DECISIONS.md) 2026-06-03). The headline finding: M4's reuse claims were mostly **`unverified-reuse`** — the cascade resolver (`cascade::resolve`, phases 2–3) is unit-proven but **unwired** (zero production callers for `Resolved::file_owner`/`scalar`; its one live caller uses it for the provenance header alone), resolution **phases 4 (structural-op) and 5 (slot-fill) are absent**, the content `Address` grammar is instance-scoped and does **not** fit a definition-target (spiked + refuted), and no typed knob is declared anywhere. So M4's real cost is *wiring the unwired cascade live into compose + building two resolution phases from scratch + a full config-write verb surface* — not "add delta application on a working cascade." The milestone was also split from the old "override machinery" entry (upgrade reconciliation → [M5](#m5--upgrade-reconciliation)); everything `override-default` / `jigc upgrade` / base-hash-compare / 3-way-merge / severity-floor-enforcement is **out**, deferred to M5. The design for every shape below is settled in [overrides.md](../design/overrides.md) (the home of record), [storage.md](../design/storage.md) (config layout), [workflow-dialect.md](../design/workflow-dialect.md) (`{{fill:}}`), and [worked-examples.md](../design/worked-examples.md) flow 3 (the acceptance flow). Risk-first, linear: the determinism-trap wiring first, then the two from-scratch resolution phases with their verbs, then `tracked-fork`, then the acceptance. **Status: planned, not yet built.**

**Pack content rides along.** Two pack additions accrete where first needed: the `config/knobs.yaml` declaration in increment 1, and the `{{fill: extra-guidance}}` extension point in `steps/implement.yaml` in increment 4.

### Increment 1 — Config loader + live scalar cascade (the wiring spine + the determinism trap)

**Deliverable:** a `scalar-set` recorded in `.jigc/config/manifest.yaml` resolves through the cascade and changes composed output — `default-workflow` overridden at the project layer flips bare-`jigc start` minting — while the **no-override** path stays **byte-identical** to today. Proven on a hand-authored fixture manifest + `jigc config set`.

**Grouped scope:**
- The `config/knobs.yaml` declaration format (`{key, type, of?, default}` reusing `schema::FieldType`) + the loader that seeds the `PackDefaultLayer` scalar surface (closed key set + materialized defaults) from it; `default-workflow` + the `validation.*.severity` keys declared, `pack-id` kept as a non-knob identity field ([overrides.md](../design/overrides.md) → Scalar knobs).
- The `.jigc/config/manifest.yaml` loader for the `scalar:` block → a populated `OverrideLayer`; wire the resolved cascade into the live compose path so `default-workflow` is read via `resolved.scalar(...)`, not ad-hoc `serde_yaml_ng::get()` ([overrides.md](../design/overrides.md) → Resolution algorithm, [storage.md](../design/storage.md) → Config layout).
- The **read-side determinism invariant**: `resolved.scalar(k)` returning `None` for a compose-read key is a hard error, not a fallback; a **no-delta byte-identical golden** over the existing `start_compose` fixtures + a test that an undeclared read-key fails loudly.
- `jigc config set <key> <value>` (clap `config` subcommand tree + dispatch) writing the `scalar:` block, adjudicated at write time via `check_value` (undeclared key / wrong type rejected).
- Correct the overstated `cascade.rs` / `compose.rs` doc-comments that claim phase-2 shadowing is "already wired into compose."

**Proves:** the unwired resolver is wired **live** for the scalar path, the cascade *applies* a delta (not just locates a layer), and the determinism boundary holds (no-override = byte-identical) — the milestone's #1 risk, retired in isolation.

### Increment 2 — Structural-op application: step shadowing (phase 2) + include-list mutation (phase 4)

**Deliverable:** a `structural-op` delta (insert / replace / remove) in a hand-authored manifest changes a composed workflow's include list — a project step shadows or augments the pack's, proven on fixtures (worked-examples flow 3a's compose-time application), not yet a verb.

**Proves:** the second from-scratch resolution phase — structural deltas mutate the composition tree deterministically before expansion, over a target namespace that does not collide with document addressing — the milestone's #2 risk.

**Proves:** M4's headline — a project composes differently from the pack default via recorded deltas across all four kinds, with the cascade applied live and the determinism boundary intact — the mandated acceptance path. ## Milestone 5 — upgrade reconciliation: decomposition

Cut 2026-06-03 via the [`/milestone-plan`](../.claude/commands/milestone-plan.md) command (scope → detect gaps → settle → review → decompose) — the first run against the M4-hardened harness. Four `capability-auditor` subagents established a clean post-M4 baseline ("no claim-vs-reality landmines"); four `gap-detector`s + an independent `design-reviewer` (both spiking the real binary per the hardening) shaped the design ([DECISIONS.md](../DECISIONS.md) 2026-06-03). Key settled calls: the milestone was **split** (the severity-tuning subsystem the probe's tunability rests on became [M6](#m6--severity-tuning--demotion-lock)); the conflict path **detects-and-surfaces** (blocks with a String review route — 3-way merge deferred, since the stateless base-*hash* design can't feed a true merge); `jigc upgrade` is **report-and-route only** (no manifest mutation); the version is **narrative-only** (the hash compare needs no version diff); and the genuine `v1→v2` e2e rides a new **`FilesystemPack` + `JIGC_PACK_DIR`** seam. The design-reviewer's catch that shaped increment 2: a `tracked-fork` *shadows the same step id*, so the probe must re-read the **pack-default** unit (`PackSource::read`), never the cascade-resolved owner, or every fork falsely classifies `clean`. Risk-first, linear: the recording substrate first, the classifier (the core logic) next, the test seam, then the command + genuine acceptance. **Status: planned, not yet built.**

### Increment 1 — base-hash substrate for `replace` / `remove`

**Deliverable:** `jigc config replace-step`/`remove-step` record the displaced pack unit's `base-version`+`base-hash` (pack-direct blake3, the same basis `config fork` already writes), so all three content-bearing delta kinds carry a re-comparable basis — proven on fixtures (manifest round-trip + recorded-basis), with the no-override compose **byte-identical**.

**Grouped scope:**
- `config.rs`: `replace-step`/`remove-step` resolve the *displaced pack unit's* bytes (pack-direct — reuse `resolve_fork_bytes`/`hash_bytes`) and write `base-version`/`base-hash` keys on the manifest entry ([overrides.md](../design/overrides.md) → Per-kind base-hash basis).
- **Representation pin (design-review B2):** the basis rides in a **separate in-memory record keyed by target**, *not* as new fields on the compose-facing `StructuralDelta` — so phase-4 compose and its byte-identical goldens are untouched; the loader parses the keys **Optional** for `replace`/`remove` (old manifests lack them), while `tracked-fork`'s stay required.
- Tests: manifest round-trip with and without the basis; the recorded basis equals an independent pack-direct hash; a compose golden proving `StructuralDelta` (hence composed output) is unchanged.

**Proves:** the conflict table's content-dependent kinds carry a basis recorded the *same pack-direct way* for all three, without perturbing the compose path the basis must never touch.

### Increment 2 — the `override-default` classifier (the core logic)

**Deliverable:** an engine classifier maps each recorded delta against a given `PackSource` to **clean / conflict / orphaned / needs-rebasing** — existence + pack-direct re-hash with the fork shadow-bypass — proven in-process over a two-version `FakePack`, including the changed-fork→conflict case and a delta whose target the v2 pack omits.

**Grouped scope:**
- engine: the `override-default` classifier `(deltas, &dyn PackSource) → Vec<Finding>` — per-kind existence + content compare; **re-reads the pack-default unit via `PackSource::read`, never the cascade-resolved owner** (the tracked-fork shadow-bypass — design-review B3; a shadow-aware read compares a fork to itself and falsely says `clean`); each delta identified in its finding by its **target string**; a **`String` route**; **blocking-by-default** ([overrides.md](../design/overrides.md), [validation.md](../design/validation.md) → `override-default`).
- The four outcomes, with **`needs-rebasing` (no recorded basis) distinct from `clean` (basis present and equal)**.
- Tests (FakePack `v1→v2`, per [Validation hardening](increment-workflow.md) #5 — exercise a context that *omits* the target): clean (unchanged fork), conflict (changed `replace`/`remove`/**fork**), orphaned (target absent in v2), needs-rebasing (basis-less legacy delta).

**Proves:** M5's core logic — correct classification including the fork shadow-bypass a naive read would silently defeat — in isolation, before any command or CLI surface. The #1 risk.

### Increment 3 — `FilesystemPack` + the pack-source factory seam

**Deliverable:** a `FilesystemPack` `PackSource` (reads a pack tree from a dir; `pack_version` from the dir's `config/defaults.yaml` `version` key, `fs-local` sentinel if absent), selected by a **`JIGC_PACK_DIR`** env var via **one pack-source factory** that replaces every production `EmbeddedPack::new()` site; with the env unset, all output is **byte-identical** to today.

**Grouped scope:**
- `FilesystemPack` impl (`list`/`read`/`pack_version` over a directory) ([overrides.md](../design/overrides.md) → the FilesystemPack seam; [module-layout.md](module-layout.md)).
- The factory honoring `JIGC_PACK_DIR`; route **every** production pack-source construction through it — the *recording* verbs and the *upgrade* path read the **same** env-selected pack (design-review N1: the obligation, not a site count).
- **Determinism guard:** a no-env golden over the existing fixtures stays byte-identical; `JIGC_PACK_DIR=<dir>` loads the directory pack; the two pack dirs report distinct `version`s.

**Proves:** a genuine alternate pack can drive the built binary (the `v1→v2` testability seam) with zero behavior change when unused.

### Increment 4 — `jigc upgrade` + the genuine v1→v2 acceptance

**Deliverable:** `jigc upgrade` runs the `override-default` classifier over every recorded delta against the current pack, renders findings+routes, blocks on non-clean, mutates nothing; a **genuine two-pack e2e** (`JIGC_PACK_DIR=<v1>` record → `JIGC_PACK_DIR=<v2>` upgrade) classifies every outcome and the re-pin→clean loop.

**Grouped scope:**
- `cli`: `Command::Upgrade` (clap + dispatch); **report-and-route only** — load the cascade deltas, run the classifier, render via the existing findings+routes renderer, exit non-zero on blocking; no manifest write, no transaction ([overrides.md](../design/overrides.md) → The `jigc upgrade` command).
- e2e via the FilesystemPack seam: record the deltas against v1, `jigc upgrade` against a v2 that changes some targets, removes a `{{fill:}}` point, leaves others — assert clean / conflict (incl. the **fork** conflict) / orphaned / needs-rebasing per [worked-examples.md](../design/worked-examples.md) flow 7; then resolve via `jigc config` verbs and re-run to all-clean.

**Proves:** M5's headline — `jigc upgrade` surfaces every divergence at one known moment (*no upstream change silently lost; no override silently broken*), proven **genuinely** through the binary across a real pack change = [worked-examples.md](../design/worked-examples.md) flow 7. The recorded deltas (now with complete bases) are M6's input.
