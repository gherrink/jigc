# Roadmap

The full-product build order — **the milestone spine**, risk-first, each milestone a runnable slice that *proves* one thing. This is sequencing, not design: each entry names what it proves and the [VISION](../VISION.md) workflow(s) it lands; the milestone-level *what* and *why* live in the design docs. For scope and the determinism boundary see [CLAUDE.md](../CLAUDE.md); for the *why* of the ordering, [DECISIONS.md](../DECISIONS.md).

This doc owns the **milestone spine** plus the increment decomposition of milestones *already planned*. A milestone is turned into ordered increments by the [milestone-planning workflow](milestone-planning-workflow.md) **when it is picked up** — never all milestones up front — so M2–M8 below stay milestone-only until then, while M1 (shipped) carries its full decomposition. Work-unit terms are `milestone > increment > task` ([structural-grammar.md](../design/structural-grammar.md) → Work-units); **tasks are not enumerated** — they're cut per-increment at pickup, so the list stays honest against what prior increments produced. *How* an increment goes from "not started" to "validated and committed" is the [increment workflow](increment-workflow.md); how a milestone *opens* and *closes* are the [planning](milestone-planning-workflow.md) and [completion](milestone-completion-workflow.md) workflows.

The ordering principle is **risk-first**: stand up the spine, retire the #1 technical risk in isolation, build the loop, prove the differentiators, then widen. The spine is strictly linear — each milestone builds on the one before.

## The milestone spine

Each entry is milestone-level only — its increments are cut by the [milestone-planning workflow](milestone-planning-workflow.md) when the milestone is picked up. M1 is shipped; its decomposition follows below.

### M1 · single-task execution loop — ✅ shipped (2026-05-31)
The core loop (discover → compose → execute → validate → finalize), proving it beats a plain `CLAUDE.md` via the superseding-decision flow. VISION: `single task execution`. **Decomposition below.**

### M2 · router + second work-workflow — ✅ shipped (2026-06-01)
A second work-workflow (`quick-fix` — commit-only, `allows-create: []`) ships and the cascade's `default-workflow` flips from `single-task` to a **router** (`creates-task: false`), so `jigc start "<intent>"` routes to a model-free selection among the work-workflows. **Proves:** the orthogonal `creates-task` / `default-workflow` knobs (designed in [write-commands.md](../design/write-commands.md), unexercised in M1) hold, and the model-free selection path. No new doctype. *Engine cost (corrected from the first-draft "no engine change" after the planning review — see [DECISIONS.md](../DECISIONS.md)):* a **minimal engine-native `catalog` data-value root** exposing the live work-workflow list to composition, plus the **`creates-task: false` compose contract** (no task minted, intent threaded by agent-substitution). Form D (`jigc start --workflow <X>`) was designed but never built in M1.

### M3 · spec-driven planning — ✅ shipped (2026-06-02)
The `spec` doctype + the flow that creates it, so a spec-driven workflow reads `{{@task.spec#…}}` (the MVP was deliberately spec-less). **Decomposition below.** **Proves:** the doc-creation differentiator beyond `adr`, and the intent → spec → implementation arc — `spec` earns its schema from its real creator and consumer, not up front. VISION: `project planning` / `milestone planning`.

### M4 · override application
Recorded **deltas** — `scalar-set` · `structural-op` by id (insert/replace/remove) · `slot-fill` · `tracked-fork` — applied through the cascade's 9-phase resolution so a project composes a workflow/schema **differently from the pack default without forking** ([overrides.md](../design/overrides.md)). **Proves:** principle #5's *individualize* half — customize one thing against a versioned base via tracked deltas, the cascade wired **live** (today the resolver is a unit-proven pure function with no runtime feeder — `cascade::resolve` is called only for the provenance header; compose reads from a single layer). **Sequenced before fan-out** because customization is core to the adoption story and touches far more of the system than the bounded concurrency primitive does.

### M5 · upgrade reconciliation
The other half of principle #5: the engine-native **`override-default` probe** + a guarded **`jigc upgrade`** that re-applies each recorded delta against a new pack version and reports **clean / conflict / orphaned** (stateless `base-hash` compare). On `conflict` it **blocks with a review route** (keep / re-target / drop, showing what changed) — the true 3-way-merge authoring is deferred (matching `file_state`'s own deferral, [reconciliation.md](../design/reconciliation.md)); `override-default`'s checks ship **blocking-by-default** (cascade-tunability is M6). **Proves:** principle #5's *inherit-upstream* half — *inherit every upstream improvement for free; every divergence surfaces at a known moment* — entirely unbuilt in code today (no `upgrade` command, no probe, no version trigger). Rides on M4's recorded-delta substrate — hence immediately after it ([overrides.md](../design/overrides.md) → Upgrade reconciliation). *(Split from the old combined M5 — see [DECISIONS.md](../DECISIONS.md) 2026-06-03; the severity subsystem the probe's tunability rests on became M6.)*

### M6 · severity tuning & demotion-lock
The validation-severity subsystem the cascade has always promised but no probe yet honors: **severity assigned via the cascade** (every tunable probe site reads `validation.<probe>.<check>.severity` from `project > team > pack-default` instead of a hardcoded literal), **per-check knob granularity** (replacing M4's per-probe keys), the **intrinsic / tunable two-tier** model with the **demotion-lock floor** (a `scalar-set` demoting an intrinsic check below `blocking` is rejected at cascade resolution), and a **non-task probe entry point** so non-task-scoped probes (like `override-default`) participate. **Proves:** "severity is a cascade setting, never a code change" ([validation.md](../design/validation.md) → Severity inventory) holds end-to-end. **Sequenced here** to finish the override/validation theme (M4 apply · M5 reconcile · M6 tune) before the concurrency primitive — and because nothing in the product yet *needs* tunable severities, so it follows the milestone that introduces the first tunable probe (`override-default`). *(Split from the old combined M5 — see [DECISIONS.md](../DECISIONS.md) 2026-06-03.)*

### M7 · milestone execution — the deterministic join core (data plane)
The engine half of the single bounded concurrency primitive: a **`milestone` work-unit** (`milestone > task`, one shared base) with task-list verbs (`create` / `add-task` / `add-from-spec`), **isolated sub-task area dirs** + a **join-time isolation check**, **parallel doc minting** with a deterministic task-id-ordered collision-suffix + intra-doc self-ref rewrite (over `created` vs `edited-from-base` provenance), and the **by-task-id join merge** (edge-index "site 4") — a disjoint union, **blocking** on a same-doc clash, with **cross-area refs rejected** (resolved per sub-area against `committed ∪ that sub-task's own area` only). **Proves:** the join is a *pure function of the set of sub-task areas* — reproducible regardless of completion order — proven by **permutation tests over real multi-area fixtures** (not a real agent spawn; that's M8). The **highest architectural risk**, isolated to the engine data plane. *(Split from the old combined M7 — see [DECISIONS.md](../DECISIONS.md) 2026-06-04; the spawn binding + workflow + genuine end-to-end became M8.)* VISION: `milestone execution`.

### M8 · milestone execution — spawn binding + acceptance (control plane) — ✅ shipped (2026-06-05)
The assistant half: **`fan-out`/`join` step kinds** + the spawn-instruction emit class, the **`{{milestone.tasks}}` data-value root** the fan-out step consumes, the **adapter spawn binding** + the `jigc workflow W --task <id>` sub-agent re-entry + the **write-time `--task`-scoped barrier**, the **`milestone-execution` workflow** that composes the fan-out over `{{milestone.tasks}}` (entered via `jigc milestone execute <id>`), and the **genuine real-Task-tool end-to-end** acceptance ([worked-examples.md](../design/worked-examples.md) flow 10, driven by real spawn). **Proves:** parallel sub-agent work stays reproducible *under the blackboard model end-to-end* — the CLI emits spawn instructions deterministically, the adapter launches, the M7 join recombines. Rides directly on M7's data plane. *(Split from the old combined M7 — see [DECISIONS.md](../DECISIONS.md) 2026-06-04.)* VISION: `milestone execution`. **Decomposition below.**

### M9 · project setup (new & existing) — ✅ shipped (2026-06-06)
The setup workflows: bootstrap a **new** project (with idea development) and **ingest an existing** one. **Proves:** jigc wires into a real project from zero. **Last of the foundational spine** because it is the broadest and least-defined — legacy ingestion was flagged research-grade in [VISION.md](../VISION.md) → Open questions (bounded to detect-and-route; auto-migrate deferred). VISION: `project setup (existing)` + `project setup (new + idea development)`. **Decomposition below.**

## The post-spine arc (M10–M14)

The foundational spine (M1–M9) is complete — the MVP loop, the override/validation theme, the milestone-execution primitive, and project setup all shipped. The post-spine arc completes the product: the **last deferred differentiator** (doc↔code validation), the **introspection surface**, the **designed terminus** (self-hosting), the **doctype/surface completion** the terminus reveals, and the **generalization** (multi-pack). Created 2026-06-06, shaped suggestion-by-suggestion ([DECISIONS.md](../DECISIONS.md) 2026-06-06). Still strictly linear and milestone-level only — each is decomposed by the [milestone-planning workflow](milestone-planning-workflow.md) when picked up. The one hard dependency: **multi-pack (M14) needs a second pack, which self-hosting (M12) mints** — so it sits last.

### M10 · doc↔code validation — the pack-provided probe family
The first pack-provided **probe** and first pack-provided **field type** — the embedded dev pack already supplies doctypes/workflows/steps/commands, so what's new here are the *probe* and *field-type* extension axes (engine-native until now): the **subprocess probe contract** + the **pack-probe determinism contract** ([validation.md](../design/validation.md) — six rules + four meta-finding failure modes) that let the *dev pack* supply `doc↔code` checks, plus the **`code-anchor`** field type (+ adjudicator) that lets `adr`/`spec` reference code structurally. **Proves:** VISION principle #6's headline — *validate against reality, the integration advantage* — documentation drift caught deterministically at the task boundary (an `adr` citing code that no longer exists; a `spec` criterion that maps to no test), the differentiator deferred since the MVP shipped only the engine-native probes (`workflow-refs`, `file-state`). **Bounded slice (to decompose at pickup):** the mechanism + **symbol/file existence** (floor) + **criterion→test mapping** (headline — the VISION example + the spec's reason to exist) + the `code-anchor` field type; **staleness** (code changed after the doc) a stretch. **The determinism contract is *satisfied, not waived*** — the six rules (no network/model/time/random, read-only fs outside scratch, bounded resources, JSON-only IO) are binding and the meta-findings detectable without OS isolation (timeout / crash / malformed-output) are enforced ([validation.md](../design/validation.md) → Pack-probe determinism contract: *"cannot ship without satisfying the contract"*). What's **deferred** is **OS-level sandboxing** (seccomp / Landlock) + the sandbox-violation meta-finding it backs, under the **trusted-pack** model (the only pack is our own; safely running an *untrusted* third-party probe is the post-MVP "not a public API yet" line). Whether `doc-code` ships subprocess-from-the-start or as an in-process prototype that still satisfies the contract is an M10-planning call. Targets the shipped `adr`/`spec`; `arch-doc↔code` rides the same mechanism at M13. VISION: the validate loop (`jigc validate`).

### M11 · describe / introspection — the self-description surface
`jigc describe` — an on-demand **prose projection of the resolved definitions** (`project > team > pack-default`) an LLM calls (or is pointed at via left-behind pointers) to orient on *what can be composed here and how it's used*: the **menu**, distinct from bootstrap's runtime-nudge, `--explain`'s single-command, and validation's correctness-check ([design/introspection.md](../design/introspection.md) — direction locked 2026-05-30, planned + promoted 2026-06-07). **Proves:** the document model applied to jigc describing *itself* — structure CLI-owned, prose human-authored, assembly deterministic and cascade-reflecting; it can't drift because it's generated from the same definitions that drive composition. **Two constraints (locked):** *facts, not advice* (what exists + how it's used, never "you should compose X" — advisory output would hand structural judgment back to the LLM, the thesis inverted one level up); and *non-contractual by design, enforced by format* — the authored `description:`/`usage:` prose is *assembled* through the cascade (the CLI makes no LLM calls) and stays discursive/**hostile to parsing** so nothing depends on it (dissolving the "not a public API" non-goal). **The substantive design work (the open thread, to settle at planning):** which definition types carry the authored fields — **workflows + doctypes the floor**, command-refs + data-value roots a stretch — required-vs-optional per type, and the **cascade merge semantics** (replace vs append when a project overrides a pack's authored prose). De-parked at M11 planning: promoted to [design/introspection.md](../design/introspection.md), wired into the reading order. **Ordering:** before self-hosting (M12) deliberately — the methodology-pack dogfood is exactly what an agent would `describe` to learn the methodology. *Caveat (for M11 planning):* `describe` projects **usage/intent prose** (`description:`/`usage:`), **dialect-shape-agnostic** by the facts-not-mechanism constraint, so it survives M12's dialect extensions; if M11 planning finds the projection must reflect step *structure*, re-order M11 after M12. VISION: a new read-path surface (the introspection loop).

### M12 · self-hosting — distill the harness into a methodology pack + dogfood *(exploratory)*
The project's **designed terminus** ([self-hosting.md](../design/self-hosting.md)) — and deliberately **exploratory**, not a locked design. Three moves: **distill** the hand-run harness (the [planning](milestone-planning-workflow.md) / [increment](increment-workflow.md) / [dev](dev-workflow.md) / [completion](milestone-completion-workflow.md) workflows + their folded learnings) into portable, project-agnostic form (the four-part graduation pass — portability · rationale index · enforced-vs-trusted · a forward-review of the process itself); **encode** it as a jigc *methodology pack* (workflows as definitions, gates as probes/steps); **dogfood + measure** on a fresh project, tracking halts/fix-rounds/audit-findings against the M1–M9 hand-run baseline. **Proves:** jigc can run its own development methodology on a fresh codebase — and, as a forcing function, **sorts the harness into the three-way determinism cut** the product exists to draw: *mechanizable step* (becomes a probe/lint) · *irreducible judgment* (stays the agent's — gap-detection, design-review, settle) · *owner-assigned recorded artifact* (real but un-automatable — the M8 genuine-spawn class). **Honest caveat:** distilling-into-jigc ≠ automating judgment — jigc owns the *structure* (compose, place writes, walk deterministic gates), the agent fills the judgment slots. **The hidden weight (why exploratory):** encoding multi-phase, human-gated, fan-out workflows as jigc definitions needs **workflow-as-managed-artifact dialect surface beyond the MVP** (human-gate steps, conditional phases, bounded fix-loops, the owner-artifact gate) — which **can only be designed by attempting the encode**. So M12's first slice is *distill + encode one workflow (the dev-workflow is simplest) + a bounded dogfood*, and the attempt **may reveal a dedicated workflow-dialect-extension milestone** (named when M12 surfaces its shape — not guessed now). **What M12 dogfoods (the M13 seam):** M12 encodes the *workflows*; the methodology's own working docs (roadmap / deferral-ledger / decisions-log) stay **plain markdown** — **direct/unmanaged file edits under workflow instruction, not jigc-placed writes** (the "jigc places every write" proof, [self-hosting.md](../design/self-hosting.md), waits for M13's doctypes) — the encoded workflows read/write them at fixed paths; *graduating* them to managed doctypes is the M13 fold-back (a fold-back can't precede the thing it enables). Read this consequence honestly: M12's baseline comparison measures **workflow-composition fidelity**, not yet self-managed methodology docs. (If M12 planning finds the dogfood can't be faithful without a specific doctype — e.g. `Scope` mechanically consuming a *managed* deferral-ledger — promote that one doctype into M12, leaving the rest in M13.) **Done/good:** a fresh project, jigc-driven, **matches or beats the hand-run build-health trend** on a comparable-difficulty milestone *and* the judgment slots stay genuinely exercised (not hollowed). Open thread: which project to dogfood — ideally **unlike jigc**, so jigc-shaped gates aren't flattered by a jigc-shaped project. **Prereqs:** M7/M8/M9 ✅ for the *substrate*; the **workflow-as-managed-artifact dialect surface** that [self-hosting.md](../design/self-hosting.md) + [VISION.md](../VISION.md) name as a hard prerequisite is deliberately **re-cast here as *discovered by attempting the encode*** (the hidden-weight note above), not pre-built — so "substrate prereqs ✅" is not "fully unblocked." **What M12 composes (the M14 seam):** M12's dogfood runs the **methodology pack as the sole composed pack** — whatever dev surfaces it needs (`commit`/`adr`, the dev loop) are **vendored into or subsumed by** the methodology pack, *not* co-composed with a separate dev pack; **true dev + methodology multi-pack co-composition is M14's distinct proof**. This breaks the M12↔M14 circularity (M14 needs the pack M12 mints, so M12 must not need M14's composition to run). Whether the methodology pack *subsumes* the dev surfaces or stays thin (so only M14 composes it with dev) is an M12-planning fork. **Mints the second (methodology) pack M14 needs.** *Planning settled 2026-06-07 — de-parked to [self-hosting.md](../design/self-hosting.md); the four forks resolved (reduced-linear dev-workflow encode · subsume · composition-fidelity bar · `gherrink-galey` dogfood) and the decomposition cut below.*

### M13 · doctype & surface completion — the self-hosting fold-back
Acts on what M12's dogfood reveals: the doctypes the methodology needs that don't exist yet, each **earning its schema from its driving workflow** (the M3-`spec` / M9-`prd` discipline), plus the fold-back of M12's emergent learnings. **Two halves.** (1) **`arch-doc` finally earns its driver** — *living architecture documentation*, named in VISION's starting set and driverless since ([doctype-map.md](doctype-map.md): the `cites→adr` edge already drafted), via a general architecture-documentation workflow; this also activates **`arch-doc↔code`** over M10's probe mechanism (the richest doc↔code case, now with a doc to check). (2) **The methodology's own working docs graduate from hand-run markdown to managed doctypes** — the **roadmap**, the **deferral-ledger** ([decisions-pending.md](decisions-pending.md)), the **decisions-log** ([DECISIONS.md](../DECISIONS.md)) — each with the authoring workflow that creates/maintains it. **Proves:** VISION's named *starting set* is complete (`arch-doc` was its last unbuilt doctype), **plus** the methodology working-doc candidates (roadmap / deferral-ledger / decisions-log) folded back as managed doctypes *if M12 earns them* — so jigc manages the methodology's own documents, the self-hosting loop closed. **Two honesty flags:** the exact doctype set is **candidate, not locked** — it's confirmed at planning *after* M12 surfaces what the dogfood actually needs (the four above are the visible candidates); and each is an **engine/pack-split call** (a roadmap / deferral-ledger is broadly useful → dev pack; a decisions-log may be methodology-pack-specific). Depends on M12 (folds back what it revealed); before M14 (richer doctypes only help multi-pack). *Surface completion = the named graph, **nodes and edges**:* M13 planning also triages the still-open named relations (e.g. `spec —decided-by→ adr`, [doctype-map.md](doctype-map.md)) in-or-out, not just the `arch-doc` node. VISION: completes the `arch-doc` row in [doctype-map.md](doctype-map.md). **Planning settled 2026-06-07 — M13 = half #1 (`arch-doc`) only; half #2 (methodology working-docs → managed doctypes) deferred behind the dialect-extension milestone** (its drivers, the planning/completion workflows, are unencoded — M12 earned zero methodology doctypes), per [architecture-documentation.md](../design/architecture-documentation.md) + [decisions-pending.md](decisions-pending.md). The human chose the **repeatable-component** arch-doc shape (real engine surface: a per-field-type `check:` predicate selector + the item-authoring verbs), relations triage → only `cites → adr` IN. **Decomposition below.**

### M14 · multi-pack composition
One project composing **>1 domain pack** at once (dev + methodology) — how packs compose in the cascade. Today the cascade is `project > team > pack-default` with a **single** pack-default; M14 makes pack-default a composition of **multiple** packs, with deterministic **collision resolution** (two packs defining the same doctype / workflow / command id) and pack precedence/namespacing. **Proves:** the architectural invariant *engine-neutral, packs supply content* generalizes — real architecture validated at scale, not just internal discipline. **Bounded slice (at planning):** compose **our two packs only** (dev + methodology) with deterministic collision rules. The bound is at the **publication** boundary, not the *generality* one: the precedence/namespacing **mechanism is inherently general** (it can't honestly be cut to a two-pack special case), but it **stays internal — not published or stabilized as a public pack-authoring API**. VISION's *"not a second domain / not a public extension API"* non-goal holds at that publication line (two packs compose internally without jigc becoming a public pack platform). **Blocked until a real second pack exists — M12 mints it (the methodology pack), so this sits last; and M12's dogfood deferred dev + methodology co-composition to here, so M14 is its distinct proof, not a repeat.** VISION: [Open questions](../VISION.md) → Multi-pack composition.

## Milestone 1 — single-task execution loop (shipped): decomposition

The six-increment decomposition of M1, kept as the shipped record and the worked example of what a milestone-planning cut produces. A usable `jigc` an agent is pointed at, proving the core loop (discover → compose → execute → validate → finalize) beats a plain `CLAUDE.md`. The **superseding-decision** flow ([worked-examples.md](../design/worked-examples.md) → Superseding decision) is the headline acceptance test — it's what converts the differentiators from *supported* to *proven*. Once all the increments below are built, the milestone is finished through the [milestone-completion workflow](milestone-completion-workflow.md) (independent audit → triage → fix → re-verify) — the acceptance gate before it ships.

**Pack content rides along, not as its own increment.** The embedded dev pack accretes where each increment first needs it: the `commit` schema in increment 2, `single-task` + its steps in 3, the `adr` schema in 5, pack-default config (`default-workflow: single-task`, the `allows-create` create-gate) across 3–5, and the whole pack finalized in 6.

**Deliverable:** bare `jigc start` (read-only) runs end-to-end against the embedded pack — prints project state, the workflow catalog with each workflow's `when` hint, and the routing footer.

**Grouped scope:**
- Workspace deps wired in; the two gating build decisions closed: **embed mechanism** (`rust-embed` vs `include_dir` vs build-script) and the **config-family YAML crate**.
- Address grammar + core id/newtypes ([structural-grammar.md](../design/structural-grammar.md) → Addressing).
- `PackSource` trait + `EmbeddedPack`; config-family YAML loading ([module-layout.md](module-layout.md), [overrides.md](../design/overrides.md)).
- Cascade-layer location + read-path resolution for the layers present ([overrides.md](../design/overrides.md)).
- Result-type foundation + the agent-text / json renderers + routing footer ([module-layout.md](module-layout.md) → Renderers).
- The `jigc` command tree skeleton + the bare-`start` orientation output ([bootstrap.md](../design/bootstrap.md), [write-commands.md](../design/write-commands.md) → Task origination).

**Proves:** the CLI-locates / engine-resolves spine, cascade, pack loading, and rendering — with no writes, no composition, no git.

## Increment 2 — Round-trip parser/writer (the risk spike)

**Deliverable:** schema-driven parse + canonical writer + surgical splice for the MVP doc-types, proven by **golden + property/fuzz** tests. Exercised via fixtures, not yet the loop.

**Grouped scope:**
- In-memory doc-type schema model + loading the `commit` (and skeleton `adr`) schema YAML ([document-type-schema.md](../design/document-type-schema.md)).
- `pulldown-cmark` parse → schema mapping; the canonical writer (parser inverse); the splice/generation write pipeline; validate-after-write; conformance diagnostics ([parsing.md](parsing.md), [storage.md](../design/storage.md)).
- The round-trip contract as tests: idempotent-on-canonical + surgical-on-edit golden tests, plus the parse→no-op-write fuzz test ([parsing.md](parsing.md) → Round-trip guarantees).

**Proves:** the **#1 technical risk** — lossless, diff-clean, schema-driven editing of the source-of-truth files — retired before the loop depends on it.

## Increment 3 — Compose (read path)

**Deliverable:** `jigc start "<intent>"` mints a task and emits the composed `single-task` workflow with every placeholder resolved (four-class emitted format).

**Grouped scope:**
- Workflow/step definition loading; include expansion; placeholder resolution — command-refs (via the catalog), data-values (`{{…}}` / `{{@…}}`), includes ([workflow-dialect.md](../design/workflow-dialect.md), [command-catalog.md](../design/command-catalog.md)).
- The four-class emitted format (Run / Content / Author / Reason) + `--explain` ([workflow-dialect.md](../design/workflow-dialect.md) → Emitted format).
- `workflow-refs` validation at compose-time ([validation.md](../design/validation.md)).
- Task origination + minimal task working area + base pin ([write-commands.md](../design/write-commands.md) → Task origination, [storage.md](../design/storage.md)).

**Proves:** the context-compiler core — deterministic composition from definition + cascade + live state.

## Increment 4 — Write path + commit-only finalize

**Deliverable:** the full commit-only loop — `jigc start "..."` → implement → `set-slot`/`set-field` the commit doc → `task validate` → `task finalize` → **one git commit**.

**Grouped scope:**
- Write verbs against the commit doc (`create`, `set-field`, `set-slot`) staging into the working area ([write-commands.md](../design/write-commands.md), [parsing.md](parsing.md) → write pipeline).
- `task diff` / `task validate` / `task discard`; `schema-conformance` integrity checks (required-slot/field, field-value) ([validation.md](../design/validation.md)).
- `finalize` for the commit-only case: validate → render the commit doc to the git message → stage code → `git commit` → post-commit ([finalize.md](../design/finalize.md)).
- `file-state` baseline/hashing for the working area ([reconciliation.md](../design/reconciliation.md), [validation.md](../design/validation.md)).

**Proves:** the cheapest thing that **beats `CLAUDE.md`**. = [worked-examples.md](../design/worked-examples.md) flows #1 + #4.

## Increment 5 — Persisted ADR + edge index (the differentiator)

**Deliverable:** the superseding-decision acceptance path — supersede a committed ADR, context-slice it into a later task, and have finalize walk the edge index (passes when the target exists, blocks when it dangles).

**Grouped scope:**
- ADR `create` via the create-gate (`allows-create: [{type: adr, as: decision}]`); promotion to `decisions/` at finalize ([write-commands.md](../design/write-commands.md) → The create-gate, [finalize.md](../design/finalize.md) → Promote).
- The edge index (committed rebuild + working overlay) + forward-ref integrity (`ref-resolves`) at finalize ([storage.md](../design/storage.md) → Edge-index lifecycle, [validation.md](../design/validation.md) → Forward-ref resolution).
- Reconciliation: the file-state state machine — baseline-adopt, absorb, conformance-block, conflict-block, rename detection ([reconciliation.md](../design/reconciliation.md)).
- The `superseded-context` step + context-slice over the persisted ADR ([worked-examples.md](../design/worked-examples.md) → Superseding decision).

Built via the [milestone-build](milestone-build) harness across five risk-first increments with **0 design halts / 0 in-increment fix rounds** — the subprocess-vs-in-process and pack-field-type forks were converted at **plan-time** (the win condition), so the build had no architectural fork to resolve (the only interruption was a transient API-overload mid-run, cleanly resumed from the journal). The [milestone-completion audit](milestone-completion-workflow.md) (independent code-review + real-binary e2e) confirmed the engine machinery genuinely holds and returned **3 findings, all human-triaged fix-now, all remediated + re-verified**: (FIXED `55d96c7`) **HIGH** — the `doc-code` probe was excluded from the workspace and built only by fixture tests (all selecting it via `JIGC_DOC_CODE_PROBE`), so on a real install the production path resolved a nonexistent binary → every anchor-carrying finalize a permanent floor-locked `crash` meta-finding; a `build.rs` now produces the probe alongside `jigc` and a new e2e exercises the **production default path** (no env override); (FIXED `1d21bf6`) **MEDIUM** — the tree-sitter resolver walked only top-level items, so the **dominant** Rust unit-test layout (`#[test]` in `#[cfg(test)] mod tests`) + impl methods were invisible (false-block), and the flow-13 fixture was shaped to the rare top-level layout that **masked** it → the resolver now descends into `mod`/`impl` at any nesting and the fixture is **de-masked** to the dominant layout (so the acceptance proves the real case); (FIXED `a946119`) **LOW** — the empty-stdout→`malformed-output` strictness lived only in engine code → documented in the wire contract. ## Milestone 14 — multi-pack composition: decomposition

Cut 2026-06-08 via the [`/milestone-plan`](../.claude/commands/milestone-plan.md) command (scope → 3 `capability-auditor`s → 4 `gap-detector`s → settle → review → decompose) — **the last post-spine-arc milestone**. The exercised baseline confirmed single-pack is baked into the **data shape** (`PackDefaultLayer.pack_id` scalar), the **factory** (`make_pack()` → one `Box<dyn PackSource>`), the **read boundary** (`PackSource` keyed `(kind,id)`, no pack dimension), **provenance** (one `Pack:` segment), and **reconciliation** — *no N-pack scaffold exists*, so M14's mechanism is net-new (not a flag-flip). Human-settled forks: **KEEP-SUBSUME** (thinning the methodology pack is *forced out* — it breaks 7/8 `methodology_pack_*` regression tests + compose-alone, and finalize's hardcoded `COMMIT_TYPE` means a `creates-task` pack *must* vendor `commit`), so M14 is **compose + collision-adjudicate**; **precedence-override, whole-definition** collision resolution for top-level ids (doctype/knob — the M11 whole-file-shadow model, **no new merge primitive**); **pack-local body-reference resolution** as a *separate correctness rule* for the three body-reference kinds (`{{include: step:X}}`, `{{cli.X}}`, schema field-types) — each resolves against the pack that **defines** the definition, never a merged namespace (the M3-class silent-corruption class); **`.jigc/config/packs:` ordered list** (pre-cascade input, base pack lowest; pack-precedence a sub-order *within* pack-default — the team layer stays inert); scope = compose + collisions + provenance-of-winner + the single-pack **byte-identity floor**, DEFER reconciliation-over-a-composed-base + cross-pack probe/field-type *collision* + enum-union + finer precedence. Design home of record: new [multi-pack.md](../design/multi-pack.md); acceptance = [worked-examples.md](../design/worked-examples.md) → **flow 17**. **Two review passes before this cut, both baked:** the same-model `design-reviewer` caught the **command-catalog** body-reference gap (the catalogs aren't mutual supersets — a whole-file shadow would strip the loser's `{{cli.X}}`), and a human-approved cross-model `/review-codex` pass added the **field-type** body-reference axis (a dev doctype's `code-anchor` must resolve from dev's pack though methodology — the precedence winner — ships none), the in-binary cold-start floor formulation, and `--explain` provenance by **path + content-hash** (a `.jigc/config/packs:` dir's id/version is not its identity). **Two collision axes, kept independent:** *top-level* ids resolve by precedence; *body-references* resolve pack-locally. Linear, **risk-first**: the composite substrate + the byte-identity floor first (the headline regression), then the pack-local correctness axis (the M3-class trap), then the e2e acceptance + provenance completeness.

### Increment 1 — the composite pack-source + the single-pack byte-identity floor (the substrate spine + the headline regression)

**Deliverable:** an ordered **composite `PackSource`** assembled from the `.jigc/config/packs:` list (highest-precedence first) over the base pack (`JIGC_PACK_DIR`/`EmbeddedPack`, lowest), behind the **existing** `&dyn PackSource` so the ~22 call sites don't ripple. `read(kind,id)` returns the highest-precedence pack owning the id; `list(kind)` returns the union **deduped-by-id then sorted** (the existing single-pack `list()` contract). `.jigc/config/packs.yaml` is parsed at **pack-assembly time** as a pre-cascade input (not a cascade knob). The orientation `Pack:` header lists the composed pack-set (degrading to today's single segment for one pack). Top-level precedence-override falls out of composite `read` (a colliding `knobs.yaml`/`commit`/workflow id resolves to the winner's whole file).

**Grouped scope:**
- `crates/cli/src/pack.rs`: generalize `make_pack()`/`make_pack_from` to assemble the pack-set (base + listed dirs); the `.jigc/config/packs.yaml` reader; the composite `PackSource` (`read` = precedence-winner, `list` = dedup-then-sort union).
- The multi-pack `Pack:` orientation header (`orient.rs`) — one pack → byte-identical to today; N packs → highest-first segments.
- Tests (real binary + goldens): **the floor** — `Composite([base])` composes byte-identically to the single-pack path (the existing no-delta `start_compose` goldens drive through the composite; the M12 `methodology_pack_*` compose-alone tests stay green untouched); a **two-pack set loads** — both packs' non-colliding resources resolve via `list`/`read`, and a colliding top-level id (`default-workflow` knob → `dev-task`; `commit` schema) resolves to the precedence winner.

**Proves:** the composite substrate exists and the **single-pack byte-identity floor holds** (the headline regression — if the composite perturbs the one-pack path, everything downstream is poisoned), and top-level precedence-override resolves a colliding doctype/knob deterministically. Risk-first: the foundation, proven before any correctness logic rides on it. **Does not yet pack-localize body-references** — so a *loser*-pack workflow including a colliding step is still mis-resolved here (exercised + fixed in increment 2); increment 1's tests assert loading + the floor + top-level winner only, never correct cross-pack workflow composition. Builds against [multi-pack.md](../design/multi-pack.md) → The pack-set; Collision resolution; Where it sits.

### Increment 2 — pack-local body-reference resolution (the correctness axis — the M3-class trap)

**Deliverable:** **pack-of-origin scoping** so a definition's body-references resolve against the pack that defines it: a workflow's `{{include: step:X}}` against *its* pack's steps, its `{{cli.X}}` against *its* pack's `commands.yaml`, and a schema's field-type names against *its* pack's `field-types.yaml`. The `workflow-refs` / `command-ref-resolves` / field-type checks fire **per-definition against its own pack**. `--explain` names which pack won each top-level collision.

**Grouped scope:**
- Thread pack-of-origin through the composite source + `CascadeStepSource::step` / `CascadeDefs::read_workflow` (`start.rs`), `load_catalog`/`load_command_catalog`, and `pack_field_types` (`pack.rs`) — a pack-scoped read for body-references, distinct from the precedence read for top-level ids.
- `--explain` collision-winner line (the resolved winner per adjudicated top-level collision).
- Tests (real binary): dev's `single-task` composes **dev's** `step:implement` + `{{cli.create-adr}}` even though methodology (the precedence winner) ships a divergent `implement` and lacks `create-adr` (the loser-pack-workflow correctness — the M3-class corruption averted); methodology's `dev-task` composes **methodology's** test-first `implement` + `set-commit-type/scope/body`; a dev doctype (`spec`/`arch-doc`) loads with its `code-anchor` field-type resolving from **dev's** `field-types.yaml`. The scope boundary (project/team references go through the cascade) is stated, not exercised.

**Proves:** the **correctness axis** — both packs' workflows and doctypes resolve their *own* body-references regardless of which pack wins a top-level id, so co-composition never silently corrupts the loser's definitions. Risk-first second: the trickiest net-new logic (pack-of-origin tracking, no precedent), built once the substrate + floor are proven. Builds against [multi-pack.md](../design/multi-pack.md) → Pack-local body-reference resolution.

### Increment 3 — the flow-17 acceptance + provenance completeness (the integration proof)

**Deliverable:** the end-to-end **dev + methodology co-composition** acceptance ([worked-examples.md](../design/worked-examples.md) → flow 17) driven through the real binary, plus `--explain` surfacing each composed pack's **resolving directory path + blake3 content-hash**.

**Grouped scope:**
