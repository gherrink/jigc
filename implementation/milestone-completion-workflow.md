# Milestone completion workflow (audit → plan → fix → re-verify)

The loop for **finishing a milestone** — the *completion* half of the milestone lifecycle, the bookend to [milestone planning](milestone-planning-workflow.md). **Planning** a milestone (detecting gaps, then decomposing it into ordered increments) is the [milestone planning workflow](milestone-planning-workflow.md); building those increments is the [increment workflow](increment-workflow.md). This doc owns only what comes *after* the last increment lands: once a milestone's increments are all built and individually validated, independently **audit the whole assembled milestone** and remediate before calling it shipped.

It is the outermost *execution* loop, completing the set: [design](design-workflow.md) governs a *decision*, [dev](dev-workflow.md) a *task*, [milestone planning](milestone-planning-workflow.md) the *opening of a milestone*, [increment](increment-workflow.md) an *increment*, and this one a milestone's *close* — the `milestone > increment > task` hierarchy ([structural-grammar.md](../design/structural-grammar.md) → Work-units), bracketed end to end.

## Why a separate audit (the per-increment validate isn't enough)

The increment workflow already validates each increment. So why audit again at the milestone boundary? Two reasons, both learned the hard way:

- **In-line validators share the builders' blind spots.** A validator spawned inside the build loop — even an independent one — inherits the same assumptions about what "done" means. It checks the increment's *headline* deliverable; it does not adversarially attack the finished whole.
- **Per-increment validation checks one slice.** Integration defects that span increments, latent failures on hostile input, and emergent gaps only appear when the *entire assembled system* is attacked end to end.

The evidence: the first milestone's external audit found a reachable parser panic and an MVP-scope differentiator that was built and unit-tested but **never wired to a command** — issues that five in-line increment validators and 177 passing tests had all passed over. An external, adversarial pass over the finished artifact is **not optional**; it is the milestone's acceptance gate.

## The loop (one milestone)

1. **Audit** — two **independent, adversarial** passes, run in parallel:
   - **Code review** — a read-only agent that **did not build the milestone and cannot edit or commit** (so it cannot certify its own work), reviewing the whole milestone diff for correctness bugs, invariant violations, and *scope honesty* (inert/dead features, stubs-as-done, `pub`-but-only-called-from-tests, tautological tests, creep) — **and *fix-completeness*: for each rule-shaped fix in the wave, does its acceptance test iterate the class axis, or pin the reported instance?** ([dev-workflow.md](dev-workflow.md) → *a fix is complete over its class's axis* — the incomplete-fix sibling is the top recurrence producer across trials, so an instance-pinned test on a rule-shaped fix is itself a finding). Severity-ranked findings with file:line evidence. **And each finding states its own class, or admits it does not have one (M49, 2026-09-01).** An audit finds a defect by *hitting* it — one repro, one site — and bounding the class is a different act, so the enumeration comes out low **by construction**: at M49 all six audit-derived fixes found a larger class than the finding reported (6→9 message literals · 5→47 freeze doors · 1→8 `location` concatenation sites · 2→8 untrackable-home movers · one leaked-target branch→nearly every break shape · 1→3 leftover-probe doors), and **two of those widenings were data loss that appeared in no finding at all** — a `{single-slot, nested}` slot truncating prose at exit 0, and `jigc uninstall` destroying a planted file at exit 0 past M48's own destroying-door guard. So a finding names **how its count was derived** — the grep and its hit-count, the registry read — or says plainly *"instance, unbounded"*. **A finding that names N sites without saying how N was reached is an instance, not a class, and must be labelled one**, because the triage brief downstream is written from it (step 3's *brief the fixer with the finding, never with the finding's boundary* is the fix side of this; this is the report side).
   - **End-to-end tests** — an agent that drives the **real binary** through the milestone's [worked-example](../design/worked-examples.md) flows in throwaway repos — *not* trusting the builders' own tests. Per-scenario pass/fail with concrete repro for each failure. **Probe *misuse* shapes, not only the done-picture arms**: undeclared fields, wrong addresses, pre-staged git state, the command the flows *don't* specify — the acceptance flows encode intended use, and a gate blindness lives exactly off that path (M40: the wave's only genuine audit finding — an undeclared nested field committing silently past 1,676 green tests — came from a misuse probe no worked example named). **Drive them over the standing trial-shaped fixture states, not ad-hoc fresh repos** ([pinning.md](pinning.md) → §4) — create-fresh-only fixtures are a named recurrence mechanism; a state a run needs and does not find is added *there*, not improvised locally.

   Run them concurrently (the reviewer reads committed history; the e2e author writes test files but does not commit — no contention). Output: ranked findings + a green/red verdict on whether the milestone's deliverable genuinely holds. **The audit's full record persists as `completions/artifacts/<milestone>/VERDICT.md` in the same motion as the completion entry** — the ranked findings with evidence, the per-arm e2e results, and the repro blocks — because a DECISIONS summary is not the record (M45 learned this the hard way, 2026-07-24: its audit persisted no VERDICT, so the auditors' findings lists and repro blocks are permanently unauditable and its VERDICT is a marked reconstruction — the drift twin of "a fact left in a verification report has no fence": *an audit left only in a summary has no record*). **Delivery format (2026-07-22): every verdict an audit or triage establishes by driving the binary — CONFIRMED *and* REFUTED alike — arrives with a repro block** (setup · argv sequence · expected exit/JSON assertions), so the verification *is* the test-in-waiting: confirmed findings' blocks become the fix's red test as always, and **refuted claims' blocks get pinned as standing tests too** — a refutation is a verified fact ("both address forms resolve"), and unpinned refuted-claim facts are exactly the ones that drifted silently across waves (the rc.5 `#type`-alias verification is the poster child). A verdict without a repro block, or a pinnable fact left unpinned without saying so, is itself an audit-quality finding. (Block schema + the conversion discipline: [pinning.md](pinning.md) → §3.)

   **An rc-chartered wave ships the version it is named for (2026-07-24).** When the wave carries an rc name (the rc.N wave), its close bumps the workspace version to rc.N, regenerates any version-bearing goldens, re-runs the gate, and installs the release binary — in the same motion as the completion entry, so the following trial's invocation log attributes to the binary that actually contains the wave. This was convention, not rule, and it broke exactly once proving the need: M45 (the rc.9 wave) closed without its bump, and the final trial would have logged itself `rc.8`; caught only by the confidence-audit wave's stamp-confirmation step ([DECISIONS.md](../DECISIONS.md) → 2026-07-24 the confidence-audit completion; commit `6cf6cd7`). **[Since M54 — settled 2026-09-28, true since the first release PR was merged on 2026-10-01 (PR #1, `jigc 1.0.0-rc.22`) — the stamp is no longer a hand edit.** The rc bump is the **release-plz release PR** ([release.md](release.md) → The release PR): the close's obligation becomes *the wave's releasable commits have landed and the human has merged the release PR*, and nothing edits a version by hand — the goldens and test pins that a bump used to move are normalized, so there is nothing to regenerate. The install that follows is from the published version (`cargo install jigc --version <v> --locked`), which is the one the next trial's invocation log should attribute to. The rule's point — the wave ships the version it is named for — is unchanged; the one hand act left is the 1.0.0 `set-version`, and it is the human's.**]**

   **Spawn-class milestones carry a third, orchestrator-driven audit artifact.** When the milestone's deliverable includes an **assistant-driven launch the CLI does not execute** (a `fan-out` spawn, any adapter-owned launch primitive), the automated e2e half is an **N-process binary sim** of the launch — honest (the CLI is exactly what a real sub-agent invokes), but it proves only the CLI payload + the join, never that the real assistant primitive reaches the CLI. The genuine launch is therefore a **recorded main-session artifact run by the orchestrator** — *not* a subagent, because a headless Workflow/Task subagent cannot spawn the assistant's Task tool. The orchestrator drives the real spawn primitive against the same fixture the automated golden uses and asserts the committed **tree-hash matches the automated golden byte-for-byte**, and the recorded transcript **witnesses the blackboard invariant** (each sub-agent reached state via `jigc` calls only, no direct read of a sibling sub-area — a property no permutation test can see). **The milestone is not shippable until this artifact exists and matches**; a missing artifact is a blocking completion finding, never an implicit pass on the sim alone (the **hollow-spawn trap**). The e2e-tester agent, being headless, must explicitly flag in its summary that this genuine-spawn artifact is the orchestrator half it did *not* run.

2. **Plan (triage) — verify-real, then fix-now by default.** For each finding: **verify it is real** (reproduce it — a red test, a source trace — because an audit is a hypothesis generator, not an oracle) and severity-rank it. **A coverage claim inside a finding — *"nothing tests this"*, *"this file is untouched"* — is verified the same way, from the enumeration and the suites, never from the diff or a prior analysis ([pinning.md](pinning.md) → §5).** **The default is fix-now, not ask.** Context is freshest the moment the milestone is built, so a confirmed finding is repaired immediately (step 3) rather than parked behind a permission round-trip — this mirrors the **build** phase, which auto-executes every task and lets the human review the gated, committed *result* rather than pre-approve each step. **The human gate fires for exactly two cases, not for every finding:**
   - **(a) Too big for the completion-fix lane.** A fix substantial enough to be its own unit of work is **recorded as its own task/increment** ([decisions-pending.md](decisions-pending.md) → *Before planning*, keyed to the milestone that will own it; or a roadmap increment) rather than patched inline. Deferral makes sense only when the work is genuinely large — not as a way to dodge a fresh, cheap fix. **Size is not the only test — the `cheap-vs-robust` gate fires here too ([milestone-planning-workflow.md](milestone-planning-workflow.md) → the gate-record).** A defer that leaves a *known hole in the milestone's declared / goal-complete surface*, or trips a *one-way-door* tell, is **not a valid defer even when large**: it means the declared deliverable is hollow, so the milestone **isn't done**. The robust fix is the minimal-correct disposition (fix-now-in-this-milestone; if genuinely huge, the milestone is **blocked / not shipped**, never quietly shipped hollow). The same two rationalizations are **barred**: *"no live case to test"* ≠ *"not needed"* (a reconstructed/synthetic case proves a now-needed capability), and *"premature"* holds **only** if the trajectory doesn't commit. **And this fork is never self-framed by the orchestrator:** before surfacing a `too-big → defer` recommendation, spawn an **independent robust-case advocate** (a read-only subagent, the recon-agent sibling) to argue the vision-robust case at full strength, so the human decides between two honestly-argued cases — never the proposer's lone cheap recommendation. (M34: the orchestrator recommended deferring the milestone's *declared* structural-migration deliverable — hollow because the shipped verb could reach only the stamp add-field — and strawmanned the robust fix as "premature generality against a hypothetical"; the human had to override. The advocate + the bars exist so the robust case is argued at full strength, by someone other than the party reaching for cheap.)
   - **(b) Contested — the "fix" would revise a settled decision or change intended behavior.** An audit is a hypothesis generator, and an auditor can be over-strict or wrong; a finding's right resolution is sometimes to *document a deliberate coupling* rather than build machinery (generality for a single-use thing is itself a defect — the global *PRINCIPLES* → Keep it minimal). **Revising a settled design decision is a deliberate, human-gated act, never an auto-fix** — the same discipline Settle applies to the docs it leans on ([milestone-planning-workflow.md](milestone-planning-workflow.md) → Settle). If a finding can't be cleanly reproduced as a red test because the behavior is *intended*, that is the signal it is contested, not a defect.

   **A tier-1 finding inside a fix wave's own new mechanism is a fix pass, not a wave (M52, 2026-09-21).** Six consecutive waves ended the same way: the wave's tier-1 rows were closed, and the next review's tier-1 rows sat inside a mechanism the wave itself had minted — a new disposition, a new family, a new registry — one un-swept sibling cell over. A full wave over those rows mints the next mechanism and the next row; the loop is infinite by construction. So such a finding is answered with a **fix pass** — a row in a registry that already exists or a condition on a guard that already exists, no new mechanism, acceptance = the affected axes re-driven — and a fix that needs new mechanism to be complete is a **halt to the human** with its sibling cells enumerated, never a build decision. The exit criterion that makes this bind is the human's and lives in [decisions-pending.md](decisions-pending.md) → *The rc.17 fix pass (M53)* → *The exit rule*.

   Everything outside those two — the common case, including most LOW/MEDIUM and any clear bounded defect regardless of severity (a HIGH that is a two-line fix is still fix-now; size, not severity, decides the lane) — is **fixed immediately** via step 3, no asking. **A *pre-existing* defect is not automatically a defer:** "it predates this milestone" is not by itself grounds to track-as-known — if the milestone's own flow **provably exercises** it *and* a builder test **masked** it (especially in a retired-risk area), it is a **fix-now** case, because the milestone is what surfaced it and a green gate hid it (M9's writer round-trip bug: pre-existing across `spec`/`adr`, but the `prd` flow hit it and a flow-11 acceptance masked it → fixed, not deferred). A finding **deferred to a later milestone** (case (a)) is recorded in [decisions-pending.md](decisions-pending.md) → *Before planning*, keyed to that milestone — not left as a triage note the next planning run won't see (the write side of the forward look; e.g. M7's edges that only become reachable on M8's real-write path).

3. **Fix** — each confirmed finding through the [dev workflow](dev-workflow.md) (red → green → refactor → gate → commit), **one finding per commit**. **Brief the fixer with the finding, never with the finding's boundary (M46, 2026-08-20).** An audit reports the sites it *found*; the fix is owed over the sites that *exist*, and a fixer handed a site list will fix the list. So the brief says **derive the axis and report its full membership** — convert what it finds, or state why a member is out — rather than naming the sites as the scope. M46's `base.json` finding named **two** sites in one crate; told to derive the class instead (*gitignored shared `.jigc/` workbench files another door parses*), the fixer disposed every member and found a **fifth writer nobody had counted** — a truncating write on a live door's failure path, in a **different crate**, outside the doc-comment's own *"all four of its writers"* count. Two sites as reported; **three across two crates** as fixed, with the claim re-keyed to the file class and pinned by an axis-iterating test rather than a writer count. The same brief-shape earned the other three fixes their corrections: one found the blast radius was **18 goldens, not the 12 the finding named**; one **refused to fabricate an address** to satisfy a format, on the ground that a repeatable section carrying zero items still has an unfilled leaf; one found the violated rule was **the code's own comment three lines above the violation**. This is [dev-workflow](dev-workflow.md)'s complete-fix rule one step earlier — that rule makes the *test* iterate the axis, this one stops the *brief* from pre-deciding what the axis is. The red test *is the finding reproduced*; a finding that a capability is unwired flips its e2e scenario from documenting-the-gap to a **regression test**. Small fixes run inline; larger ones (and anything design-sensitive, with a scope go/no-go gate) are **delegated to an executor agent** on the same loop.

   **Each confirmed fix is its own agent in its own worktree — the round is a fan-out, and that is a fence rather than a rule to remember.** `jigc milestone provision` isolates each sub-task in **its own git worktree, keyed by task id** — the M31 primitive, built precisely so concurrent agents cannot share a tree — so two fixers *physically cannot* race one index. `crates/cli/packs/methodology/steps/fix-gate.yaml` is the encode, and it composes the round: partition the confirmed findings by each fix's **projected write-set** — a finding spanning two files is one sub-task, two findings landing in one file are one sub-task — then `jigc config set finalize.fan-out.squash false`, `jigc milestone create`, one `jigc milestone add-task <m> "<finding>" --workflow fix-task` per partition, `provision`, `execute` (whose `Spawn:` lines *are* the fan-out), `join`, `finalize`. The knob is what gives each fix its own commit — under its default the whole round lands as one — and it is a project setting, not a per-round flag: the write lands uncommitted and the milestone's own finalize carries the `.jigc/config/` layer into its aggregate commit, so it stays in effect. **Shared artifacts stay out of the partition and are applied serially after the join** — an artifact every fixer would have to edit to land its own change (a test-registry root a new suite has to be listed in, a generated snapshot set, a lockfile or manifest, the doc every fix folds back into); no partition makes those disjoint, and no fixer knows what its siblings will need until they are done. A round whose write-sets **cannot** be made disjoint says so before it mints anything and falls back to running the fixers one at a time in the main working tree, each staging only the paths it touched — stated up front rather than discovered at a blocked `join`, where two sub-tasks staging one path stop with `combine.code-collision` and nothing is committed.

   **Why the fence, and why here.** The serial rule was broken at **M38** (two parallel hand-spawned fixers, one's in-flight edit broke the other's build; it survived only because one defensively staged just its own paths) and **again at M42**, by an orchestrator who had not re-read this doc — three fixers, one tree, `migrate_corpus.rs` mid-edit and not compiling, every fixer's gate running against the others' half-finished work. It survived, again, only because the fixers defensively gated in isolated worktrees and staged only their own paths. **The reasoning that led there is worth naming, because it is this project's signature failure wearing a methodology costume:** *"these three findings touch different concerns, so they are independent"* — a claim about the members being looked at, not about **what they have in common**. What they had in common was the working tree. Every remedy was the same shape — M38 reinforced the prose, M42 added the ⚠, M49 moved it into an agent file — and **a rule that lives in prose the actor must remember to read is the same object as a hand-maintained census: it rots at exactly the moment it is needed** ([dev-workflow.md](dev-workflow.md) → *a grep is not a fence*). Audit fixes are the one set in this methodology that is **independent by construction**, which is why the primitive fits here and nowhere else: the [increment workflow](increment-workflow.md)'s Execute phase stays serial because each task builds on the last, not because of the tree. *(Note what this says about the four rules above it: three of them can only reach **tier 3** — a step that always appears — because they are judgments. This one reaches **tier 1**, and a tier-1 fence needs no words at all. Always check whether the rule you are about to write is really a missing fence.)*

4. **Re-verify** — the full gate green (`fmt` · `clippy -D warnings` · `test` · `build`) **and** re-run the affected audit slice to confirm the finding is actually closed. **Loop to clean:** fixes regress and audits miss, so repeat audit-relevant checks until the slice and the gate are both green. **A fact verified by hand leaves a test behind, or it is an observation, not verification** (project-alpha-3.0, 2026-07-22): any cross-surface contract this phase — or a trial triage — establishes by driving the binary (an address form resolves · a severity→exit-code mapping · stdout parses as one JSON document) either lands as a **standing test in the same motion** or is recorded as **explicitly unpinned**. The address grammar, the exit-code taxonomy, and JSON purity were each hand-verified once (rc.5 · M42 · M41), held by nothing, and later waves moved them silently — the drift twin of *a deferral left in prose has no trigger*: **a fact left in a verification report has no fence.**

5. **Leave no litter** — after the re-verify and the rc bump's release build + install, run **[`dev/clean-litter`](../dev/clean-litter)** (`cargo clean` over the workspace's one target tree — **one** since M54 Increment 2, 2026-09-29, when the probe's detached workspace and its `target/` went). Cargo garbage-collects nothing: `target/debug/deps` only grows, and every gate run every build agent makes adds to it. Left alone it reached **1,825,219 entries (26 GB)** by 2026-09-14, which is not a disk problem — macOS Gatekeeper rescans the tree on every link, and a full `dev/gate` measured **~20 min** against **~9.5 min** on the same tree with the stale sidecars gone. The close is the one moment the cold rebuild it costs is free, and `dev/gate` prints the count at the top of every run so the next wave can see it coming.

The milestone is **done** when every confirmed finding is closed (or consciously tracked), the gate is green, and the deliverable holds under the re-run end-to-end flows.

## Close — the pull request, the human's merge, the release PR

*Since the branching switch, 2026-10-01* ([CLAUDE.md](../CLAUDE.md) → Branches). The whole loop above runs on the milestone branch `milestone/<slug>/main`: the audit reads it from its fork point, and every triage fix commits there. Then, in order:

1. **The milestone branch is pushed by name**, and its CI run is green — `ci-ok`, the one required check ([release.md](release.md) → The main branch).
2. **The orchestrator opens the pull request** `milestone/<slug>/main → main` (`gh pr create --base main --head milestone/<slug>/main`), titled for the milestone, its body pointing at the completion entry and the `VERDICT.md`. Opening it is an agent's act; **merging it is the human's alone**, by a merge commit — no squash, because release-plz reads the conventional commits the milestone carries.
3. **The human merges it**, and the release PR updates from that merge on `main`.
4. **The release PR is the release boundary, and it is not the milestone's.** It accumulates every milestone merge since the last release; the human merges it **when the planned set is in** — one milestone or several — and nothing publishes before that merge. When the version release-plz derived differs from the one the plan named (a planned rc number, the 1.0.0 call), the human runs `release-plz set-version` on the release PR before merging it ([release.md](release.md) → The release PR). So an rc-chartered wave's *ships the version it is named for* (step 1, above) is honoured at the release PR's merge, not at the milestone PR's.

The fold-back and the `VERDICT.md` ride the milestone branch like any other close commit, so they reach `main` in the same pull request.

**Where the fold-back lands (2026-09-27).** The completion entry's prose half — the wave's `**M<nn> — …**` span — appends to [project-history.md](project-history.md), the running record, and its two `crates/cli/tests/foldback_truth.rs` arms are re-aimed onto the new span in the same edit (that suite's module doc carries the inversion rule: *say no more about the audit than the audit found*). It does **not** go in `CLAUDE.md`, whose `## Project state` carries current truth and a pointer; touch that only when current truth moved — the instrument still owed, what comes next. **It names no installed version** (since M54): the version a wave shipped is its record span's claim, and `foldback_truth` fails a built-and-installed claim in `CLAUDE.md` ([release.md](release.md) → Versioning). The record left `CLAUDE.md` because one paragraph had reached 157 KB, preloaded whole by every session.

## Why this shape

- **External adversarial audit is the acceptance gate.** Only a fresh pass over the finished whole — by something that did not build it and cannot fix it — catches the integration, latent, and emergent issues that in-line, per-slice validation structurally misses.
- **Verify before fixing.** The audit generates hypotheses; reproduce each as a red test so you fix a real thing and prove the fix. A wrong finding fixed is churn.
- **Fix-now by default; the human gate is narrow.** Context is freshest at completion, so a confirmed finding is fixed immediately — the same autonomy the build phase has (auto-execute, review the gated result), not a per-finding permission ask. The gate fires only for *too-big* (→ its own task/increment) and *contested* (→ the fix would revise a settled decision or change intended behavior); those two are genuine decisions and still surface. Everything else — including a clear bounded defect at any severity — is a tested commit the human reviews after, never ceremony-taxed (the [trivial lane](../CLAUDE.md), applied to remediation). Verify-real still precedes every fix: a wrong finding fixed is churn.
- **It is the dev workflow's customer.** Every fix is a dev-workflow task; this doc owns only the audit, the triage, and the loop around them. Cross-reference, never restate.
- **Loop to clean, don't one-shot.** Re-verification against the audit *and* the gate is what makes "milestone complete" a verifiable claim rather than a hopeful one.
- **Orchestration.** Run as a workflow, the two audit passes are two parallel agents and each confirmed fix is its own agent (a dev-workflow task) in its own worktree — a milestone sub-task minted on `fix-task`, fanned out by `jigc milestone execute` and joined at the barrier (step 3). It is the agent-per-phase mapping the [increment workflow](increment-workflow.md) → Orchestration states, and the Fix phase is the one phase where it stops being a mapping an orchestrator has to apply and becomes the primitive the CLI runs.
