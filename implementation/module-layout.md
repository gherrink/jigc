# Module layout

How the locked architecture — engine / CLI / domain pack / assistant adapter — becomes **real Rust crates and modules**. The *architecture* (the engine/CLI/pack separation, the determinism boundary, "engine ships empty," "MCP could be another frontend") is settled in [VISION.md](../VISION.md) and [CLAUDE.md](../CLAUDE.md); this doc is purely its physical realization in code. The language and single-binary goals are in [language-runtime.md](language-runtime.md); the parse module's internals are in [parsing.md](parsing.md). For the *why*, see [DECISIONS.md](../DECISIONS.md).

## Crate topology

**A two-crate workspace: `engine` (lib) + `cli` (lib + `jigc` bin), `cli → engine`.**

- **`engine`** — the neutral, **empty** core library: cascade resolution, the document/schema model, parsing & serialization, the doc registry, workflow composition, the validation engine, task/staging state, the edge index. It depends on no frontend and no domain content, and makes **no LLM calls**. Because it's a standalone library, a later **`mcp` bin** is just a third crate over the same engine — the one boundary that carries architectural weight.
- **`cli`** — the `jigc` frontend: argument parsing, command dispatch, the three renderers, adapter generation, and cascade-layer *location*. Depends on `engine`. **It is a library with a thin binary on top** (M45): the whole module tree lives in `lib.rs` as `pub mod`s and `main.rs` keeps only `fn main` + the invocation-log output tee. That shape is load-bearing, not cosmetic — it is the **enumeration seam** the pinning suites read their members from ([pinning.md](pinning.md) §1/§2: the pack registry, the clap tree via `CommandFactory`, and the exit-code constants), so a sweep can never degrade into a hand list. Cost paid once: making the tree a library activates rustdoc doctests over it, so an indented block in a doc comment must be fenced.

**The published shape (M54 — settled 2026-09-28, true when M54 lands).** The two crates become the two published packages **`jigc`** (this `cli` crate: the `jigc` bin, `default-run`, plus the `cli` lib) and **`jigc-engine`**. The engine's lib is renamed **`jigc_engine`** and `jigc` declares it as `engine = { package = "jigc-engine", version = "=…", path = … }`, so no `engine::` path in the workspace moves. The `cli` lib stays what the paragraph above says it is — the enumeration seam — and is marked `#![doc(hidden)]` and declared **not an API, no semver promise**: publishing it is a packaging fact, not an offer. The bundled `doc-code` probe joins the **`jigc` bin's** module tree, never the lib (§ [Probe boundary](#probe-boundary-in-engine)). Versioning, packaging and publishing rules live in [release.md](release.md); this doc keeps only the topology.

Rejected: a **single crate** (engine not separately consumable → "MCP later" becomes a refactor, and the frontend boundary blurs); **many micro-crates** (a shared-types crate + version churn + compile-graph overhead, premature for the MVP). Engine internals are **modules**, split into sub-crates only if compile times or reuse later force it — `parse` is the natural first split-out.

## The dev pack's home — embedded

The development pack (doc-type schemas, workflows, steps, default config) is **data, not logic**. The **engine consumes the pack-default layer through a `PackSource` provider trait** — the named, specified form of the previously hand-wavy "source abstraction" — so it stays empty of domain content. Minimal shape (illustrative):

```rust
// in `engine` — the provider boundary; the engine knows only this
trait PackSource {
    fn pack_version(&self) -> Version;                          // built-in: = binary version (override-reconciliation, below)
    fn list(&self, kind: PackResourceKind) -> Vec<ResourceId>;  // schemas | workflows | steps | config
    fn read(&self, kind: PackResourceKind, id: &ResourceId) -> Result<Bytes>;
}
```

`PackSource` is **how `cli` provides the pack-default cascade layer** to the engine — pack-default is just one located layer ([the I/O boundary](#the-io-boundary--cli-locates-engine-resolves)), not a special case. Two impls: **`EmbeddedPack`** (MVP — bytes embedded via `include_dir`, so `jigc` is one self-contained artifact, the single-binary value from [language-runtime.md](language-runtime.md)) and **`FilesystemPack`** (post-MVP — installable third-party packs read from a path). The dev pack versions *with* the release, which is exactly what override-reconciliation needs (built-in pack-default version = binary version, [overrides.md](../design/overrides.md)).

**Where the built-in bytes live — embed in `cli` now, relocate when a second frontend lands.** For the MVP's single frontend the `EmbeddedPack` bytes live embedded in the `cli` binary. The moment a second frontend exists (the post-MVP `mcp` bin), the embedded built-in pack + its `EmbeddedPack` impl **relocate to a shared `pack-builtin` data-crate** both bins depend on — so neither re-embeds the pack nor depends on the other's packaging, and **the engine never changes** (it only knows the `PackSource` trait). The crate is *not* created now: for one frontend it would be the premature ceremony [Crate topology](#crate-topology) already declined; the forward-binding rule makes MCP a mechanical move, not a retrofit. Installing the built-in pack to a filesystem path was likewise rejected for now — it only adds path-discovery + a second install step for a single built-in — and arrives later as `FilesystemPack` **through the same trait**, a free extension. Adapter profiles follow the same pattern (embedded now; relocate with the pack if a second frontend shares them).

**The seam is prepared now, the crate still is not (M54 — settled 2026-09-28).** A published crate carries only its own directory, so both packs move to **one home, `crates/cli/packs/{dev,methodology}/`**, and the forward-binding rule above gets a seam it can bind to: **one module** owns every `include_dir!` embed, the `EmbeddedPack` impl, and the pack version as an **explicit input** (still `jigc`'s version — nothing here changes what [overrides.md](../design/overrides.md) keys on). Tests take pack paths from that module — a `macro_rules!` that expands to a literal where `include_*!` needs one, a single engine test-only macro for the engine's one pack root, and cli in-source tests reading through `EmbeddedPack` where they can — and a fence holds that **no production code outside that module names a pack path** — its scope is non-`#[cfg(test)]` code under `crates/*/src`, and a *pack path* is any string naming a pack directory; the engine test macro is the one named exemption. So the MCP move stays mechanical: the day a second frontend lands, the module becomes the `pack-builtin` crate. **Extraction stays triggered by that second frontend**, and so does the other split it will force — lifting the `cli` lib's shared frontend code into a crate of its own. **One thing that trigger must also decide:** the bundled `doc-code` probe lives in the `jigc` **bin's** tree and runs by self-exec (§ [Probe boundary](#probe-boundary-in-engine)), so a `jigc-mcp` binary cannot spawn it by spawning itself — where the probe lives once there are two frontends is decided there, not now.

This preserves the locked boundary as **internal discipline, not a public API** ([CLAUDE.md](../CLAUDE.md) non-goals): the engine loads pack content generically; domain specifics never leak into engine code. A second domain is what would turn the boundary into a real API — not yet.

### Pack distribution — the methodology pack rides in the binary too (M21)

The dev pack embeds via `include_dir!`; the **methodology pack** (the M12 second pack — `roadmap`/`planning`/`completion`/…) lived **only on disk** at `packs/methodology/`, reachable only via `JIGC_PACK_DIR`/a hand-written `packs.yaml`. So a clean `cargo install jigc` shipped **one** pack — a real project got no milestone/roadmap authoring out of the box. **M21 embeds the methodology pack as a second `EmbeddedPack` and composes it at `jigc setup`** (the Flow-A production-readiness goal — [multi-pack.md](../design/multi-pack.md) → Embedded second pack + setup auto-wiring; [DECISIONS.md](../DECISIONS.md) 2026-06-14).

- **Embed mechanism — a second `include_dir!`, not the M20 `include_bytes!` probe pattern.** The probe is one built *artifact* (`include_bytes!` of an `OUT_DIR` binary, extracted beside `jigc` at setup). The methodology pack is a **39-file YAML tree of pure data** — so it embeds directly via a second `include_dir!("…/packs/methodology")` (~45KB; **no `target/` bloat risk** — the bloat lesson was about embedding a build tree, which a data pack has none of). **No extraction, no on-disk path:** the pack is composed *in-binary*, so unlike the probe nothing is written to the filesystem and there is no `packs.yaml` path to resolve (sidesteps the M14 CWD-relative-path landmine).
- **`EmbeddedPack` becomes field-carrying.** Today `EmbeddedPack` is a unit struct whose `list`/`read` reference one module-global `static PACK`. M21 parameterizes it over a selected `&'static Dir` (e.g. `EmbeddedPack(&'static Dir)` or an enum), so two embedded packs can be composed. The factory (`make_pack`/`make_pack_from`, `crates/cli/src/pack.rs`) gains a path that builds `CompositePack([dev_embedded, methodology_embedded])` with **dev highest** (the precedence that resolves the `default-workflow`/`commit` collisions favorably — [multi-pack.md](../design/multi-pack.md)).
- **Opt-in by a setup-written marker.** Composition fires only when `jigc setup` has written the wiring marker — the key **`compose-embedded-methodology: true`** in `.jigc/config/packs.yaml`, the file the factory already reads pre-cascade (no new discovery walk — [multi-pack.md](../design/multi-pack.md) → Embedded second pack). Absent it, the pack-set is `[dev]`, **byte-identical to today** (the single-pack floor + every dev-only test stay green). Writing the marker is a **neutral install step** in `jigc setup` ([assistant-adapter.md](../design/assistant-adapter.md) — pack-wiring is assistant-independent, like project-layer init and the M19 backstop).
- **Home (M54).** The pack's source moves from the repo-root `packs/methodology/` into the crate, at `crates/cli/packs/methodology/`, beside the dev pack's `crates/cli/packs/dev/` (previously `crates/cli/pack/`), behind the one embedding module above. Moving a pack's directory changes no hash — `schema-hash`, the pack content hash and the pack identity are path-free, exercised at the M54 baseline — so the move is a layout change, never a freeze event. The `include_bytes!` probe pattern the first bullet contrasts against retires at M54 (§ [Probe boundary](#probe-boundary-in-engine)); the contrast stands as the record of why the pack took `include_dir!`.
- **Version ties to the binary.** The embedded methodology pack reports `pack_version = binary version` (the same `EmbeddedPack` invariant the dev pack holds), not its file's `0.1.0` — so override-reconciliation keys both embedded packs to one release.

## The I/O boundary — CLI locates, engine resolves

A clean split that keeps the engine neutral *and* testable:

- **`cli` does bootstrap & presentation I/O** — it locates the three cascade layers (pack-default **embedded** · team **external** `~/.config/jigc/` · project **in-repo** config dir, per [overrides.md](../design/overrides.md)), finds the repo root, and hands the engine its run context; then it renders the engine's results.
- **`engine` does logic & managed I/O** — it resolves the cascade and owns all managed content I/O: the documents, the `.jigc/` tree (committed config + gitignored caches/staging), the edge index ([storage.md](../design/storage.md)).

So the engine is fed its layers and asked for results — *feed layers in, assert results out* — which is what makes the deterministic core directly testable.

## Renderers (in `cli`)

Presentation is strictly **downstream of the deterministic engine result** — the engine never formats for a surface.

- **The engine's public result types are the renderer contract** — `ComposedWorkflow`, `DocView`, `Vec<Finding>`, `TaskStatus`, `Catalog`, … all `Serialize`. **JSON is then generic** (`serde_json` over any result, no per-type code); **agent-text and human are per-type** rendering in a `cli::render` layer. These types are a **versioned semantic API, not incidental `serde` output**: their JSON projection is part of the contract (explicit serde attributes + a schema-version marker), and changes are intentional and versioned — so the renderers *and* any external JSON / future `mcp` consumer bind to a stable surface, not to whatever `#[derive(Serialize)]` happens to emit. MVP keeps this as internal discipline (one frontend, [CLAUDE.md](../CLAUDE.md) non-goals); locking the stance now means a non-CLI consumer is zero-rework rather than silently broken by a field rename.
- **Format selection:** default **agent-text** (the primary consumer is an agent reading piped, non-TTY stdout); **interactive TTY → human-pretty**; `--format=agent|json|human` overrides. MVP human-pretty is *agent-text + light styling*; the **`ratatui` TUI is an additive `render::tui` module, post-MVP**.
- **The non-interactive floor** is intrinsic: the agent path never blocks on a prompt. It's trivially met at MVP (no interactive prompts — `finalize` is autonomous); the post-MVP TUI must preserve it (every interactive affordance keeps a flag/JSON twin).
- **Settled dependency** (carried here as an *honest dependency* until M49): the agent-text renderer *for composed workflows* renders the **emitted-format micro-syntax**, which is **not** an open question — it was decided 2026-05-28 and is specified in [workflow-dialect.md](../design/workflow-dialect.md#emitted-format) → Emitted format, extended there by `Spawn:` (M8) and `Checkpoint:` (M15). The seam (`render` over `ComposedWorkflow`) has shipped that output since M1, and the reserved `Run:` line-pattern is the contract the acceptance suites extract and execute verbatim. What survives of the original note is the **direction of the dependency, not a block**: a change to the micro-syntax is a change to this renderer, which is why the line-classes are stated in that one home and not restated here.

## Adapter (in `cli`)

- **Profiles are embedded data** (Claude Code in-box; more installable later), same pattern as the pack. `jigc setup` / `jigc adapter install --assistant claude-code` **generates** the adapter from `profile + engine catalog` and **regenerates on upgrade**, so it can't rot into a static pile ([assistant-adapter.md](../design/assistant-adapter.md)).
- The generator **writes into the host project's assistant files** — the bootstrap static line into `CLAUDE.md`, the `jigc` allowlist into `.claude/settings.json`, and catalog-derived per-workflow launchers (slash commands), each just `jigc start --workflow X`.
- **MVP scope:** the static-**reference** floor (a managed `.jigc/AGENT.md` + an `@`-import line in the always-loaded file), the **`SessionStart` hook** (primary injection — bare `jigc start` orientation at session start), the **allowlist** (the path-of-least-resistance the bootstrap depends on), and **project-layer init** (`.jigc/config/`). The **`Resume`/post-compaction hook** (capability-gated) and the **spawn binding** stay post-MVP — the spawn payload is composed by the *engine* and rendered through the profile's launch template, but it rides on fan-out (post-MVP).

## Probe boundary (in `engine`)

- A **`Probe` trait** (read-only); the engine owns scope→target resolution, severity-via-cascade, aggregation, and the `finalize` gate (the fat-engine/thin-probe split, [validation.md](../design/validation.md)). *Built shape vs. design (corrected at M10 planning):* the M6 seam shipped `check(&self, ctx)` with **no `target`** and a **non-serializable** `OverrideCtx { deltas, pack }` (a live handle), sized to its one consumer (`override-default`). **M10 reshapes it** to carry a `target` + a *serializable* effective-state ctx — the work the earlier "zero engine change to admit subprocess" framing had wrongly assumed was already in place ([DECISIONS.md](../DECISIONS.md) 2026-06-06).
- **Two implementations:** **in-process** (engine-native `workflow-refs`, `file-state`, `override-default`-at-contract) compiled in; **subprocess** (pack probes, JSON-in/out) — the only place a non-Rust program runs. The **determinism contract the subprocess impl satisfies** is locked in [validation.md](../design/validation.md) → Pack-probe determinism contract: six rules (no network, no model, no time/random, read-only fs outside scratch, bounded resources, JSON-only IO) + four meta-finding failure modes (timeout / crash / malformed-output / sandbox-violation, all intrinsic blocking). **M10 enforces the contract + the timeout/crash/malformed-output meta-findings**; OS-level sandboxing (seccomp, Landlock, equivalents) + the `sandbox-violation` meta-finding it backs are deferred under the trusted-pack model.
- **M10 builds the subprocess seam (the first pack probe, `doc-code`).** The split keeps the **engine shell-free** ([finalize.md](../design/finalize.md) — the engine never shells out): the **engine** owns the serializable effective-state snapshot it materializes in the probe's read scope, ingestion of the probe's findings into the `ValidationReport`, and meta-finding synthesis; the **CLI** owns the subprocess invoker (`std::process::Command` + a wait-timeout). The `ctx` is **effective-state the engine can serialize**, so in-process and subprocess impls consume the same logical input (a live graph vs. its read-only snapshot + path-ref) — the [wire contract](../design/validation.md#the-wire-contract--request--response), concretized in M10. **Probe executables live outside the workspace** (any language) — **since M54 that is the rule for third-party probes, and the bundled one is the exception** (the bullet *The bundled probe ships inside `jigc`* below); the dev pack's `doc-code` is a separate **tree-sitter**-based program (multi-language symbol resolution; the *is-a-test* predicate Rust-first), wired in because the schema's typed leaves imply it (`code-anchor` ⇒ `doc-code`, [document-type-schema.md](../design/document-type-schema.md#pack-declared-field-types-m10)).
  - **Shipping invariant (M10 audit fix, `063cccc`):** because the probe is externally resolved (production resolves `<jigc-bin-dir>/doc-code`), it **must be produced by a normal build and placed beside `jigc`** — else a real install resolves a missing binary and every anchor-carrying finalize floor-locks on a `crash` meta-finding. A `crates/cli/build.rs` produces it; **the production resolution path is e2e-tested with no `JIGC_DOC_CODE_PROBE` override** (the env var is a test/dev convenience, never the proven path — testing only the override masks a probe that doesn't ship). (This is the project-side home for the M10 invocation-path-masking lesson: any externally-resolved artifact's *production* resolution must be exercised, not just a test shim — kept here as a jigc build invariant, deliberately **not** folded into the domain-agnostic build harness.)
  - **The bundled probe ships inside `jigc` — self-exec, one binary (M54 — settled 2026-09-28, true when M54 lands; supersedes the M20 bullet below and the build-tree mechanics of the one above).** The probe's sources move into the **`jigc` bin's** module tree (never the `cli` lib, which names no tree-sitter symbol — Cargo has no per-target dependencies, so the lib's code is what keeps it out), and tree-sitter core plus every grammar join the `jigc` package **pinned `=`**. Gone: `build.rs`, the detached `crates/cli/probes/doc-code` workspace and its source-tree `target/`, the gate's and CI's probe prebuild, the `include_bytes!` embed, `setup`'s extract step (`setup.extract-probe` retires) and every machine-global write — an install is **one file**. What each piece of the old shape was for survives in a new form:
    - **One function says how the probe is run: `doc_code_command() -> (program, args)`.** Production: `(current_exe(), ["__probe", "doc-code", "--build", <id>])`, where the program is **`/proc/self/exe` on Linux** — which names the running image's inode even after the file on disk is replaced. In-process tests (the ones that call the invoker from inside a test process rather than through the binary — `store_sweep_acceptance.rs`'s direct invoker cases, `doc_code_probe.rs`'s): `(CARGO_BIN_EXE_jigc, the same args)`. The `JIGC_DOC_CODE_PROBE` override stays what it is: **a standalone executable spawned with no args** — the crash and timeout stubs. **Shell-wrapper shims are forbidden** (a script that re-adds the args would be a second spelling of the command, and the command has one owner).
    - **The intercept is the first statement of `main`** — before `route_fence::install()`, the invocation-log gate and the output tee (`main.rs`) — and it matches the literal argv `__probe`, never through clap, which even as a hidden subcommand would trip eight surface fences and surface in did-you-mean. Fenced: **a probe spawn in a repository with the invocation log on adds zero records**, so the measurement channel never counts jigc's own child as an agent's call.
    - **The subprocess seam and its determinism contract are unchanged** — it is still a separate process speaking the [wire contract](../design/validation.md#the-wire-contract--request--response), invoked by the CLI with a timeout, so the engine stays shell-free. The probe keeps its **own, independently declared wire types** and imports neither `engine` nor `cli` (fenced), which is what keeps the *any-language* claim proven rather than asserted: the one shipped probe still could have been written in anything.
    - **Skew is guarded, and the guard is honest about its reach.** The build id is **`CARGO_PKG_VERSION`**. A child whose version differs writes its reason on **stderr** and exits non-zero; the invoker — whose `ProbeOutcome` today keeps stdout and the exit status and discards stderr (`invoke.rs`) — carries a **bounded** stderr into the finding's message. That catches the realistic skew, a `jigc` upgraded while a run is in flight; on Linux `/proc/self/exe` removes even that case. **A same-version dev rebuild is declared uncovered.** The stale-probe silent pass the M54 baseline drove (a wire-compatible old probe, `schema_version` never compared) has no separate binary left to occur in.
    - **No new check id.** A spawn failure and a skew both stay **`pack-probe-integrity.probe-failure`, check `crash`**, so the 34-check census does not move; what changes is that each message says what happened. A spawn failure reads *"could not start: `<io error>`"* — the invoker previously mapped a spawn error to `Exited { code: None }`, which is how the gate's `ENOENT` race read as *exited non-zero (exit-code signal)* ([DECISIONS.md](../DECISIONS.md) → *M54 settled*, S1) — and a skew carries the child's stated reason. The finding's **route** is rewritten with it: `probe.rs`'s *"`jigc setup` reinstalls the shipped probes"* names an act that no longer exists, and so do `jigc uninstall`'s help (*"the machine-global `doc-code` probe"*) and the rig's comment. **Acceptance runs per path that reaches the probe:** the store sweep (both of `cli.rs`'s `doc-code` call sites), `jigc task validate` and `task finalize` (`task.rs`), the milestone join (`milestone.rs`), orientation's `findings_unavailable`, and the pre-commit hook.
    - **The shipping invariant above keeps its point.** The production path, **with no override**, is still exercised end to end: the suites that drive the real `jigc` binary without setting `JIGC_DOC_CODE_PROBE` — today `cargo_install_probe`, `doc_barrier` and the `flow13` · `flow29` · `flow30` · `flow31` · `flow32` acceptance suites, the set the build re-derives rather than trusts — now reach the probe by self-exec, and every suite that used to build a probe of its own drives the real `jigc` instead.
    - **The pre-commit hook's silent pass on a missing probe** (the M54 baseline's S3 — [assistant-adapter.md](../design/assistant-adapter.md) → the hook's case (iv)) goes by construction: a `jigc` that runs always carries its probe.
    - **Cost, measured on the Settle's spike:** one **15.1 MB** binary against **24 MB** for the pair it replaces, no measurable cold-start difference, symlinked installs resolve. Building `jigc` from source now needs a C compiler, which the install prerequisites state ([release.md](release.md) → Installing).
  - **Probe distribution — ride in the binary, extract at setup (M20).** **[Superseded 2026-09-28 by the M54 bullet above, when M54 lands; kept as the record of the shape it replaces. One stale datum in it, recorded rather than smoothed: the embedded probe is ~8.4 MB at rc.21, not the ~2 MB below.]** The M10 build-tree path (`build.rs` copies the probe beside `jigc`) only works in a *build tree*: `cargo install` relocates only declared `[[bin]]` targets, so the build-script sibling doesn't travel, and an installed `jigc`'s code-anchor work breaks. M20 makes `cargo install` a **supported channel** by shipping the probe *inside* the binary and **extracting it at `jigc setup`**. **The fix is two-part, and the bloat and the missing-extract are *separate* sites** (the design-review correction — don't conflate them): (1) **Stop the 418MB bloat at its real source** — `pack.rs`'s `include_dir!("$CARGO_MANIFEST_DIR/pack")` sweeps the *entire* `pack/` tree, and the probe's gitignored ~401MB `target/` build-tree lives **under** `pack/probes/doc-code/`, so it's embedded as dead weight `include_dir` never serves (`include_dir` honors no `.gitignore`, has no exclude filter). The fix is to **relocate the probe *source* out of the embedded `pack/` tree** (or otherwise scope the embed to exclude `probes/`), so `PACK` carries only the ~55KB of real pack content. (2) **Add** an `include_bytes!` of the built ~2MB `doc-code` executable for the extract path — the probe is **not embedded today** (it rides as a build-script-copied sibling), so this is *new*, not a swap of (1). `jigc setup` then adds a **neutral install step** that writes the embedded probe to `current_exe().parent()` (beside the installed `jigc`) with the exec bit. **Setup-write policy (pinned — heal/upgrade):** write the embedded copy when the sibling is **absent** *or* when an existing sibling's **bytes differ** from the embedded copy; a byte-identical sibling is a **no-op**. Overwriting a byte-different sibling *heals* a corrupt stub (which would otherwise surface as `pack-probe-integrity.malformed-output`) and *upgrades* a stale probe left by a prior `jigc` after a binary upgrade. The honest consequence: running `jigc setup` **in a build tree** overwrites the `build.rs`-placed sibling with the embedded copy — harmless, since both are functional probes built from the same probe source (debug builds are not byte-reproducible, so the build-tree sibling and the embedded copy legitimately differ in BuildID/embedded paths/timestamps). On a read-only target dir, **one operational error** (the probe-missing failure shape), not a panic. This is the **first machine-global** setup write (every other setup write is repo-local) — flagged so its idempotency is judged at that scope, not per-repo. **(I)-pick at pickup:** `include_bytes!` needs the probe at a path nameable at macro-expansion (after `build.rs` runs) — likely an `OUT_DIR` indirection (`build.rs` copies the probe into `OUT_DIR`, the macro reads `concat!(env!("OUT_DIR"), …)`). The task-scope absence path is fixed in the same motion — probe-absent reports **one operational error** (porting M18's store-scope `require_doc_code_probe` pre-flight to task scope), not a floored per-anchor `pack-probe-integrity.crash`. *(Graduated from the [decisions-pending.md](decisions-pending.md) cargo-install trigger at M20 planning, 2026-06-14.)*

## The dependency graph

*(Crate names as of today; from M54 the left node is the `jigc` package — bin `jigc`, which also carries the bundled `doc-code` probe, plus lib `cli` — and the right node is `jigc-engine`, lib `jigc_engine`, aliased back to `engine`. In the post-MVP line, "probe executables (external, any lang)" then means third-party probes; the dev pack's own runs inside `jigc` by self-exec.)*

```
cli (bin) ──depends──▶ engine (lib)
  ├─ embeds: dev-pack data (EmbeddedPack) + adapter profiles
  ├─ provides cascade layers: pack-default (PackSource::EmbeddedPack) · team (~/.config/jigc) · project (in-repo)
  ├─ render: agent-text · json · [tui post-MVP]   (over engine result types)
  └─ adapter generation (profile + engine catalog → host project files)

engine (lib) ──depends──▶ (no frontend, no domain content)
  ├─ modules: cascade · schema · parse · doc-registry · compose · validate · state · index
  ├─ PackSource trait: EmbeddedPack (MVP) + FilesystemPack seam (post-MVP installable)
  ├─ Probe trait: in-process impls (MVP) + subprocess seam (M10; CLI owns the invoker)
  └─ result types (Serialize, versioned API) = the renderer / JSON / MCP contract

post-MVP:  mcp (bin) ──▶ engine          probe executables (external, any lang) ◀── subprocess Probe
           cli + mcp ──▶ pack-builtin (shared EmbeddedPack data-crate)   # built-in pack relocates here when a 2nd frontend lands
```
