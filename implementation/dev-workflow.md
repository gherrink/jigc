# Dev workflow (TDD)

The loop for **building jigc** — how a single implementation task is taken from "not started" to "committed," test-first. This is distinct from the **design-collaboration loop** in [CLAUDE.md](../CLAUDE.md) → How we work together: that one governs *decisions* (discuss → converge → write a design doc); this one governs *code tasks*. It runs **per task within an increment** ([roadmap.md](roadmap.md)); tasks are cut when an increment is picked up. This is the **inner** loop: the [increment workflow](increment-workflow.md) is the outer one that cuts an increment's tasks, runs each through the loop below, then independently validates the increment and fixes until clean.

The loop is shaped as named, ordered steps on purpose: each maps onto a future jigc `step:` and the whole onto a future `workflow:dev-task`. We run it by hand now; when jigc can compose, it promotes into the workflow dialect almost verbatim ([workflow-dialect.md](../design/workflow-dialect.md)).

## The loop (one task)

1. **Scope** — restate the task in one line, and its **done-criteria as an observable check**: a test that passes, a command that exits clean. Read the design-doc section the task implements (the [roadmap](roadmap.md) increment names it). If the restatement reveals a different problem than the task assumed, stop and check (understand before acting; make success verifiable). **If the task fixes a rule-shaped defect** — a guard, a printed statement, a workflow demand, a contract — **fill the axis card before cutting the red test**: name the *class*, sweep the standing axes (doctype shape · write path · verb family · surface · task/store scope · corpus state), and mark every member **covered / already-safe / excluded-with-reason** (see *a fix is complete over its class's axis*, below).
2. **Red** — write the failing test(s) that encode the done-criteria **first**. Run them; confirm they fail, and **for the right reason** (not a compile error standing in for the assertion). Parser / serialization work is **golden + property/fuzz** tests — the #1-risk discipline ([parsing.md](parsing.md) → Round-trip guarantees) lives here, not as an afterthought.
3. **Green** — the **minimal** implementation that makes the test pass. No extra scope, no speculative generality (keep it minimal).
4. **Refactor** — tidy while green, touching **only what this task touches**. Pre-existing mess is not this task's to fix (stay in scope).
5. **Gate** — the verification gate; all **four** pass or the task isn't done, in this order:
   - `cargo fmt --check`
   - `cargo clippy --all-targets -- -D warnings`
   - `cargo build`
   - `cargo test` — which `dev/gate` runs as two `cargo nextest run --workspace --no-fail-fast` runs, a fast tier and then its complement, and then `cargo test --workspace --doc`, falling back to `cargo test` itself where nextest is not installed (*What the gate's test step runs* and *The gate stops at the first red stage*, below)

   **[Retired 2026-09-29 (M54 Increment 2) — kept as the record: until then a fifth step ran first, the probe prebuild `cargo build --manifest-path crates/cli/probes/doc-code/Cargo.toml --target-dir crates/cli/probes/doc-code/target`.** Dozens of suites shelled out to cargo for the detached `doc-code` probe workspace and all drove one `target/`; co-resident in a group target, one suite's build could replace `target/debug/doc-code` while another executed it (reproduced at 5.5 % under load, 39 suites relinking one file — [DECISIONS.md](../DECISIONS.md) → *M54 settled*, S1 · S4), and prebuilding made every in-test build an up-to-date no-op. Its `--target-dir` was not optional: hand-run with `CARGO_TARGET_DIR` set, it built into the private dir while the suites still raced, at exit 0 (the bullet itself once omitted it and sat third — corrected 2026-09-15, M51 Increment 9, T11). **The probe now runs inside `jigc` by self-exec ([module-layout.md](module-layout.md) → Probe boundary), so no suite builds a probe, no file is left to race on, and `dev/gate` runs no probe step.]**

   **Measure the gate unpiped — `cmd | tail` reports *tail's* exit status, not the command's** (2026-08-13, the pre-1.0.0 trial session, where this one habit produced **four** near-misses in a day). A pipeline's `$?` is its *last* stage, so `cargo test 2>&1 | tail -40` exits 0 over a failing suite, and `cargo fmt --check | tail -3` exits 0 over a real diff — both were nearly recorded as green, and a `tail` also silently discarded the per-target counts that would have shown the run was never measured at all. The same shape produced two *false findings* against the product in the same session (`jigc validate`'s exit code read through a pipe; an authored item "missing" because `head -8` cut the render before it), both caught only by re-measuring and both recorded as died-in-verification in [the trial's verification](../completions/artifacts/RC-pre-1.0/findings-verification.md).

   **So: run `dev/gate`.** It is the four commands above, in order, each run **bare** with its exit code
   captured directly, stopping at the first red stage — plus the aggregate totals and, on a red, the
   failing step *and the failing test names*. It exists because this habit is a **reflex, not an oversight**: a scan of 139 subagent
   transcripts found the piped form blocked **215 times across 117 of 137 agents**, and an independent
   verifier that had the tool named in its context from the first token still reached for
   `cargo build 2>&1 | tail -5`. Naming the alternative is the fix; forbidding without naming one is
   what produced 239 post-rule violations of the rule two paragraphs above.

   ```sh
   dev/gate                  # the full gate — fmt · clippy · build · test (nextest in two tiers + doctests)
   dev/gate --keep-going     # the full gate, and no red step stops it — for a red that is compared with another run's
   dev/gate --fast           # fmt · clippy · build · the fast test tier — a pre-check, never a gate
   dev/gate --quick          # fmt · clippy · build, no tests
   dev/gate --private-target # a private CARGO_TARGET_DIR, for a tree with concurrent gates
   ```

   By hand, if you must: redirect, capture `$?` directly, then inspect the file —
   `cargo test > /tmp/gate.log 2>&1; echo "EXIT=$?"`. Never through a pipe.

   The general form is the one this doc already legislates elsewhere: **a green that means "nothing was measured" is indistinguishable from "nothing was wrong."** It is the vacuous-pass family — a filter that matches no test, a snapshot that cannot witness an invariant, a fixture reachable only by the defect — arriving through the shell instead of through the test. **Pack-shape: step prose in `step:gate`**, beside the no-masking rule: *"Did you read the command's own exit code, or a pipe's? Did the run report the counts you expected, or zero?"*

   **The gate is still FULL and UNSCOPED** — the `--bin jigc` pack/describe goldens live in a target a scoped run silently misses (M23: an increment landed a red gate off a scoped run). What changed at M47 is only *how many binaries* that costs: the ~250 suite files are compiled into **thirteen `[[test]]` group targets**, not one target each — a macOS Gatekeeper assessment per freshly-linked binary was charging ~44 s × 252 on every gate run. Twelve hold the suites under `crates/cli/tests/` (the twelve of M47); the thirteenth, `g_tooling`, holds the repository's own tooling suites, which live outside `crates/` (*Where the tooling's own tests live*, below). **A new suite file must be registered in exactly one group root** of its own home — `crates/cli/tests/groups/` for a product suite — as `#[path = "../<name>.rs"] mod <name>;`: `autotests = false` means an unregistered file compiles nowhere and silently never runs, which `tests/test_target_registration.rs` fences, over both homes. To run one suite: `cargo test -p jigc <suite_name>::` (the suite is now a *module* inside its group, so `--test <file>` no longer addresses it) — or `cargo nextest run -p jigc --profile scoped <suite_name>::`, under which a hung test is a named `TIMEOUT` and not a stalled run (*The gate stops at the first red stage*, below). **Two group roots are `g_solo_*` and must stay at one suite each** — they mutate process-global env vars, which only stays sound while nothing else shares their process; the same guard enforces that. **In CI, the full gate is the union of these jobs, every one named** (`.github/workflows/ci.yml`, M54 S8): `hygiene` (the [public-hygiene](public-hygiene.md) guard, and the branch-name rule of [CLAUDE.md](../CLAUDE.md) → Branches) · `fmt` · `clippy` · `build` · `test`, a matrix of **one row per `[[test]]` group target** · `unit` (the lib, bin and engine unit tests, and the doctests) · `manifest-freeze` (the CI-only freeze leg, its argv pinned) · `publish-dry-run` (`cargo publish --workspace --dry-run`) · `lock-current` (`cargo metadata --locked`, never `--no-deps`) · and **`ci-ok`, the one aggregate** (2026-10-01, the branching switch): it `needs` every other job, runs `if: always()`, and is green only when every one of them reports `success` — a failure, a cancellation and a skip all turn it red — so it is the single check `main`'s ruleset requires ([release.md](release.md) → The main branch). No leg `needs` another, every job has `timeout-minutes: 10`, every leg checks out with `fetch-depth: 0` and prints `nproc` in a step named `CPU count`, the matrix runs `fail-fast: false`, and every `cargo test` carries `--no-fail-fast` except the freeze leg's pinned one-test argv. `tooling-tests/ci_matrix_fence.rs` holds that **the matrix equals the test targets `cargo metadata` reports, plus the `unit` job** — derived, never a hand list, so a group added here and forgotten there reddens rather than going unrun — and that every job S8 names exists and runs its pinned command; it also holds `ci-ok`'s `needs` to exactly every other job and drives its body over each result a job can report. The workflow lints clean under **`actionlint` 1.7.12** (shellcheck 0.11.0 on `PATH`), the pinned linter `.github/workflows/release.yml` — the release workflow, never part of the gate ([release.md](release.md) → Publishing) — is held to as well. The bound is a green push in **≤ 15 min** of slowest-job wall clock on a standard public 4-vCPU runner, and a red push that reports **every** failure. **The green half is measured on the runner** ([ci-runtime.md](../completions/artifacts/M54/ci-runtime.md) → The final after run): every job reads `nproc` 4, and the slowest is **`test (g_flow)` at 430 s** warm on Increment 11's tree (run `36843531774`) and 448 s cold on Increment 8's tip (run `36720872051`). The single-job gate it replaced took 2020 s. The red half is no run's measurement, since all three runs were green. It is held by the shape above, which `ci_matrix_fence.rs` fences. Should a later run cross the bound, the lever in reserve is S8's nextest partitioning of the group. **The per-leg proxy, measured** ([ci-runtime.md](../completions/artifacts/M54/ci-runtime.md) → The per-leg proxy): the instrument is **`dev/runner-faithful --cpus 4`**, each leg's exact argv run cold in a fresh container capped by a cpuset, so `nproc`, cargo's `-j` and libtest's thread count all read 4 as on the runner. Against a per-leg budget of 878 s (15 min less the before run's 22 s of non-cargo steps), the slowest leg is **`g_flow` at 221 s**; no leg is over budget, so each leg compiles for itself and the build-once-share lever (a nextest archive) stays unpulled. **The proxy is not the runner**: arm64 here against the runner's x86_64, no cache, M1 Max cores rather than vCPUs — for the same group the before run's test time was 1.67–2.10× the proxy's, and `g_flow` scaled by the worst of that (~464 s) still fits. Locally nothing changes: `dev/gate` is still the whole thing in one process, and *full and unscoped* above still binds.

   **Where the tooling's own tests live (2026-10-06, the human's ruling — [DECISIONS.md](../DECISIONS.md) → *The stabilization workflow's build, reviewed red*, ruling 2; what was built is the entry *The tooling's own test suites live in `tooling-tests/`*).** A suite that tests this repository's tooling or its records — a `dev/` script, the CI and release workflows, the stabilization harness, a doc's links, a ledger — and never drives `jigc` or reads a file under `crates/` as its subject, lives in **`tooling-tests/`** at the repository root, registered in that directory's one group root, `tooling-tests/groups/g_tooling.rs`. *Why:* the stabilization workflow classes paths by directory — what is under `crates/` is product and moves only through an audited round's merge ([stabilization-workflow.md](stabilization-workflow.md) → Branches) — and while these suites sat beside the product's in `crates/cli/tests/`, every change to a `dev/` script or to a fence was a change to a product path. Outside `crates/`, the rule stays a rule by directory, with no list of exempt files. **Adding a tooling suite touches only that directory**: the file, and its `#[path = "../<name>.rs"] mod <name>;` line in the group root. `crates/cli/Cargo.toml` declares the target once (`g_tooling`, a `[[test]]` of the `jigc` package rooted outside it, so `cargo test -p jigc <suite>::` addresses a tooling suite exactly as before, and `env!("CARGO_MANIFEST_DIR")` in one is still `crates/cli`); the published crate is unchanged, because cargo drops a test target whose root the package does not carry. The registration fence, the temp-mint fence and the message-whitespace fence find the directory through that manifest entry (`crates/cli/tests/support/test_homes.rs`), never by a list, and CI runs it as its own matrix row. **A suite that also uses the product — the binary, `cli::`/`engine::` beyond the shared temp-name mint, or a source file under `crates/` as its subject — stays in `crates/cli/tests/`**, whatever else it asserts, and so does the shared `tests/support/`.

   **No commit is exempt from the gate by its path (2026-10-03, M55's close).** A commit touching only a register, a ledger, the fold-back record or a doc's links is inside the gate's reach, because fences read exactly those files — `seed_ledger`, `foldback_truth`, `count_fences`, `doc_link_fence`. At M55's close a register row committed without the gate (`92f279c3`) turned `seed_ledger::the_ledger_carries_every_source_row_exactly_once` red, and `72f54033` repaired it. The trivial lane ([CLAUDE.md](../CLAUDE.md) → Conventions) skips the loop's ceremony, never the gate.

   **What is accepted of a stabilization run's record commit (2026-10-06, the human's ruling — [DECISIONS.md](../DECISIONS.md) → *A stabilization run's record commit under a red candidate*; as built, the entry *The record step, rebuilt*).** The rule above is unchanged in what it demands: the full gate runs before that commit too, on the tree with the records — no path exempt, no tier skipped, never `--fast`. What differs is which result is accepted. **A record commit is accepted when its gate shows nothing red — no step, no test — that the gate of the round's candidate did not already show red.** The candidate's gate is run by the stage's preflight; what it showed red is a table of the round, written from the gate's own output (`dev/stabilize-record gate-set`); and one command holds the record's gate to that table and makes the commit, or refuses and names what is red only with the records (`dev/stabilize-step record`). **On a green candidate this is exactly the rule that a commit follows a green gate**, and it is the acceptance of no other commit: a fix, a doc and a tool change follow a green gate as before. *Why:* a candidate that fails the gate is the most important thing a round can find, and it was the one thing a round could not write down. *Its price, intended:* a flaky test shows as newly red and halts the record step. **Both gates are run as `dev/gate --keep-going`** (below), so what each shows red is all that is red and the two are held against each other test by test; the record script refuses a red gate that was run without it. *Its bound:* a candidate whose **build** is red — no test can be built on either tree, so what the records would turn red is seen first on a candidate that builds.

   **The gate's own speed is a tree property, and the tree is watched.** Cargo garbage-collects nothing: `target/debug/deps` only grows, and by 2026-09-14 it held **1,825,219 entries (26 GB)** — 1,823,960 of them `*.rcgu.o` split-debuginfo sidecars, median age 15 days, one batch per gate run per agent. The cost lands on the same Gatekeeper assessment the group targets addressed: a full `dev/gate` measured **~20 min** against **~9.5 min** on the same tree with the stale sidecars deleted mid-run. `[profile.dev] split-debuginfo = "packed"` (Cargo.toml) stops new litter being produced — one `.dSYM` bundle per binary instead of hundreds of loose objects per link, and `[profile.test]` inherits it — `dev/gate` prints `gate: deps <N> entries` at the top of every run and warns above 100 000, and **[`dev/clean-litter`](../dev/clean-litter)** is the reset, run at the [milestone close](milestone-completion-workflow.md) so the cold rebuild it costs is free. **`clean-litter` resets cargo's two `target/` trees and nothing else — `dev/gate --private-target` mints a fresh `$TMPDIR/jigc-gate-target-*` per run, and by 2026-09-26 eighty-two of them stood (one at 3.2 GB) with Spotlight indexing all of them: a full gate measured **~2 h** (test step 7197 s) on a tree that ran in **16 min** (970 s) the same day after `clean-litter` — so those trees are the one litter the reset does not see, and until `--private-target` reuses one directory by default (a candidate in [decisions-pending.md](decisions-pending.md)), `JIGC_GATE_TARGET=<one dir>` is how a session keeps them to one.**

   **What the gate's test step runs, and why it is fast enough to run in full (2026-10-02, the human's decision — [DECISIONS.md](../DECISIONS.md) → *The local gate runs under the real git, on nextest, with optimized dependencies*).** A full `dev/gate` measured **19.1 min**, 98 % of it the test step and 40 % of that CPU in the kernel; with the three levers below it measures **8.9 min**, every one of the suite's 4222 tests still run ([gate-speed-measurement.md](../completions/artifacts/M55/gate-speed-measurement.md) carries each lever's two runs). **The real git, not the trampoline:** nearly every suite drives the binary through git in a throwaway repo, ~174 k git calls a gate, and on macOS `/usr/bin/git` is an `xcrun` shim that resolves the developer directory on every call (~11 ms). So when `git` resolves to `/usr/bin/git`, `dev/gate` puts `dirname "$(xcrun --find git)"` first on `PATH` (−29 % alone) — and exports `SDKROOT="$(xcrun --show-sdk-path)"` with it, unless one is already set, because the C compiler in that directory finds the SDK only through the shim, and tree-sitter's C build fails without it. It prints `gate: git <path>` either way, and on Linux and CI changes nothing. **nextest, then the doctests:** the test step is `cargo nextest run --workspace --no-fail-fast` — one process per test over one pool, instead of `cargo test`'s binary after binary — followed by `cargo test --workspace --doc`, because nextest runs no doctests; the two together are the full suite (−9 % alone). **[Since 2026-10-05 the suite is two such runs, a fast tier and then its complement — the next paragraph.]** [`.config/nextest.toml`](../.config/nextest.toml) used to forbid certifying a gate on nextest, because the detached probe workspace raced under its pool; that workspace is gone since M54. Without nextest installed the step falls back to `cargo test` — the same full suite, slower — and says so with the install line ([machine-setup.md](machine-setup.md)). The report layer reads nextest's `Starting … across B binaries` and `Summary [` lines for the totals and its `FAIL [` status lines (`<binary> <test>`) for the names, and still reads the doctest step's `test result:` lines. **Dependencies at `opt-level = 2`:** `[profile.dev.package."*"]` in `Cargo.toml` optimizes every non-workspace crate (−16 % alone); the workspace's own crates stay unoptimized, and `debug-assertions`/`overflow-checks` are separate keys left on, which the rig's debug-only route-fence panics depend on. The cost is **+40 s on a cold build and +2.5 s on an incremental one**, and CI's cold builds (a cache miss) pay it too. **Measured and not landed:** `GIT_TEST_FSYNC=0` (0), a fresh or RAM-disk `TMPDIR` (0 / −1 %), the ambient-git-config mask (−1 %), clippy overlapping the test build (≤ 3 s — cargo's lock serializes them); the Developer Tools exemption ([machine-setup.md](machine-setup.md)) stays a per-machine choice. *Full and unscoped* above is unchanged: the full suite's verdict is still every task's done-check.

   **The gate stops at the first red stage, and the suite runs in two tiers (2026-10-05, the human's ruling — [DECISIONS.md](../DECISIONS.md) → *The stabilization workflow, as ruled*, ruling 15, levers 1, 6 and 9 of [run-performance.md](../completions/artifacts/M55/fix-pass-rc25/perf/run-performance.md) §4).** In the rc.24 fix pass 23 gates were red; the slowest failing test in any of them ran 6.3 s, and each red was reported after 8–10 minutes, because the gate ran every step whatever came before it (§3.6 of that report). **The standing rule is unchanged — the full gate precedes every commit, and a green gate runs every test.** What changed is what a *red* costs, and what the log keeps.
   - **Where it stops.** `fmt`, `clippy` and `build` all run, so one cycle shows a format diff and a lint together; a red among them launches no test. Then the **fast tier**; if it is red, neither the second tier nor the doctests are launched. **So a red names the stage that stopped the run, and the failures it lists are that stage's — a second-tier failure can still be waiting behind a red fast tier.**
   - **The tiers are measured, never listed.** Each tier writes a JUnit report, and the gate folds every test's seconds into `<target>/jigc-gate/test-seconds.tsv`. The fast tier is every test that record does not hold at 2 s or more (`JIGC_GATE_FAST_UNDER`); the second tier is `not (<the fast tier's filter>)`, built from the same shell variable, so the two are every test whatever the record says — a wrong or stale row costs time, never coverage. `dev_gate_report.rs` pins the second filter as the first one negated; listed with `cargo nextest list` on 2026-10-05 the two profiles held 3478 and 1166 tests, none in both, together the 4644 the unfiltered list held on that tree — a tree one test short of the commit that landed the tiers, whose own gate ran 4645. **A test with no row runs in the fast tier**, so a new suite needs nobody to place it — it runs first, where a new test's red belongs, and is placed by its own seconds from the next run on — and where no record exists (a fresh clone, the run after `dev/clean-litter`, a fresh `--private-target`) the fast tier is the whole suite for one run, which the run says. *Why seconds, and not the rule the planning pass proposed* — a suite that spawns no child process, derived from the group roots: derived that way (a suite file that names no `Command` and no support module leading to one) the tier is 37 of the 479 suite files and would have stopped 7 of the 23 reds, because the fences that reddened most (`git_span_aim`, `task_area_writer_registry`, `help_truth`, `migrate_route_family`, `repo_relative_paths`) each share a suite with tests that drive the binary. By seconds it would have stopped 18, judged by the failing tests' own seconds as that report lists them — the 15 with a fence among their failures (each such fence under 1.4 s, or beside one that is) and the 3 others that were red at fmt or clippy; the 5 red on a behaviour test alone are not counted, since a test that fails early does not say how long it takes to pass. **Bound:** the cut is this machine's last measurement, under that run's load, so two machines, or one machine on two days, cut it differently; that moves when a red is seen and never whether a test runs.
   - **`dev/gate --keep-going` is the full gate for a red that is compared (2026-10-06 — [DECISIONS.md](../DECISIONS.md) → *The gate, repaired*).** Stopping at the first red is what a builder wants of a red gate, and the wrong thing for whoever holds one run's red against another's: a stabilization run accepts a record commit when its gate shows nothing red that the candidate's own gate did not (above), and under a candidate that was red early neither gate had run what lay behind the stop — a record commit could turn a test red unseen. So the gate can be asked to keep going. **Nothing red stops it, with one exception: a red build launches no test in any mode, because there is nothing to run one from** — the binary's (`build`), or the tests', which this mode builds as a step of its own (`test-build`), so that tests that do not compile are a red build and never a red suite that names no failing test. A red `fmt` or `clippy` still runs every test, and a red suite still runs the doctests. **And the suite is one nextest run — the step `test` — never two tiers:** a tier is a place to stop, which this mode never does, and a test's tier is this machine's last measurement of it — a failing test that took two seconds is in the second tier on the next run, so the *step* it is red in would differ between two runs that are red in the same test, and the comparison names a step that is newly red. It reads no timing record, so none can touch it; it writes one, as every run does. **Green, it is a full gate like any other** — the same tests, the `tests   passed=…` totals line and `GATE: PASS` — and its mode line reads `gate: mode   full, keep-going (…)`, which is what [`dev/stabilize-record`](../dev/stabilize-record) looks for before it takes a red gate as evidence. With `--fast` or `--quick` it is refused: a pre-check that kept going is neither. **A plain `dev/gate` is unchanged**, and is still what a builder runs before a commit: it shows a red sooner.
   - **A record that is stale against the tree costs time — never coverage, and never a red gate (2026-10-06, the review's `M11` — [DECISIONS.md](../DECISIONS.md) → *The gate, repaired*).** The record is this machine's last measurement, and nothing keeps it true of the tree: a test binary is removed or renamed, a branch is switched under one target directory, a second checkout builds into it, two gates write it at once. As built, one of those reddened the gate for good — a row for a binary that no longer exists puts `binary_id(=<gone>)` in the filter, nextest refuses a filter that matches no binary before it runs a test (exit 96), and a tier that never ran rewrote no row. Each member of the class is now decided, and held by `dev_gate_report.rs`:

     | The record… | What the gate does |
     |---|---|
     | names a **binary** the tree no longer has — removed, renamed, or built into this target directory by another branch or checkout | **Before any tier, the run asks nextest whether it takes the tiers the record gives** (`cargo nextest list --list-type binaries-only` under the fast tier's profile: it builds the test binaries the tier would build anyway and executes none). Refused — for this reason or any other — the run goes on as if there were no record: the fast tier is the whole suite, the run says so, and **its timings replace the record**. One slow run, nothing to delete by hand. The question is no step: it is in neither the verdict nor the exit status. |
     | names a **test** the tree no longer has | The name matches nothing. The row leaves when a run whose tiers are all green rewrites the record from what it ran. |
     | holds a **line that is no row** — cut short, two rows run together | Only a line of three fields whose first is a number of seconds is read, by any reader. Its test is a test without a row: the fast tier. A line that happens to be shaped like a row is one of the two cases above. |
     | holds **seconds that are no longer true** | A test moves between the tiers. |
     | was written by **another target directory** | Not read: the record lives in the target directory it measures. |
     | is being written by **another gate** | The record is replaced by a rename, never rewritten in place: a gate reading it has the old one or the new one, whole, and the last writer wins. Each run keeps its JUnit reports in a store of its own under `$TMPDIR`, so two gates building into one target directory never read each other's seconds. |

     *Its bounds:* the row of a test that is gone, and of every test a run did not measure, stays until a run whose tiers are all green — a target directory that only ever sees `--fast` keeps them, which costs bytes in a filter; and a record that cannot be written at all (a target directory that is read-only) is the whole suite in the fast tier on every run, and a run that says so.
   - **`dev/gate --fast` is the fast tier as a pre-check** — lint, build and the fast tier, for the registry row or the fence a change owes, which `--quick` cannot see. Measured on 2026-10-05 over 3478–3601 tests, three runs took 88, 97 and 104 s — the 97 after a source edit that relinks every test binary (10-core M1 Max). **It is never a gate**: it prints `PRE-CHECK: PASS` or `PRE-CHECK: FAIL (step: …)` and a `fast tier  N passed, M failed` count, and neither of the two lines the build harness accepts as a passed gate — no `tests   passed=…` totals line, no `GATE: PASS` ([milestone-build.js](../.claude/workflows/milestone-build.js)). Without nextest there is no fast tier to run, and it says so.
   - **The log keeps the timings.** One `step-seconds` line per step (name, exit code, seconds) and one `test-seconds` line per test the run measured (seconds, binary, test), tab-separated at column 0; every run prints its five heaviest suites and tests from them, so a suite's cost is seen when it lands. The report that recommended this had to re-run the suite to learn them.
   - **A test that passed without running what it tests is named beside the verdict (2026-10-06).** A test may need a tool this machine lacks and CI has — the suites that run the stabilization harness need `node` ([stabilization-workflow.md](stabilization-workflow.md) → The simulation of a stage). Such a test fails under CI, and anywhere else passes and says so on stderr — which a test runner shows nobody for a test that passed. So every run names a file in `JIGC_GATE_SKIPS`, the test appends its one line to it, and the summary carries `==> NOTE    N test(s) PASSED WITHOUT RUNNING what they test on this machine:` with each distinct line and its count, above the verdict. It is no step and changes neither the verdict nor the totals; the log keeps each as a `test-skipped` line, so `--report` prints the same note. A test that skips goes through the one helper that writes that line (`node_or_skip`, `tooling-tests/dev_stabilize_step.rs`), never through a bare `return`.
   - **A scoped run has a timeout.** `cargo nextest run -p jigc --profile scoped <suite>::` runs under `[profile.scoped]` of [`.config/nextest.toml`](../.config/nextest.toml), which terminates a test after two minutes and reports it as `TIMEOUT` by name; under `cargo test`, which has no per-test timeout, a test blocked on a FIFO once held a scoped run until the ten-minute tool ceiling. `dev/gate` never runs under that profile, and a scoped green is still never a gate.

   **A green gate here is a measurement under *this machine's* ambient git config — and on macOS the obvious mask does not remove it (2026-09-27, the CI repair).** Nearly every suite builds a throwaway repo, and what those inherit here is not what a runner's inherit: the first green GitHub run on `main` took four commits and two of them were fixtures living off ambient config — an initial branch name nobody set, and a missing `user.name`/`user.email` — each supplied by this machine and by no runner ([DECISIONS.md](../DECISIONS.md) → 2026-09-27, *D4 is discharged*). **The trap is that the usual mask is not one.** Apple Git reads `/Library/Developer/CommandLineTools/usr/share/git-core/gitconfig` as an **additional** system source rather than as the one `GIT_CONFIG_SYSTEM` replaces — so `GIT_CONFIG_SYSTEM=/dev/null` leaves it in force, and it sets `init.defaultBranch = main`, which is exactly the value a fixture must not be allowed to inherit. The faithful mask is `GIT_CONFIG_NOSYSTEM=1` — which drops **every** system source, Apple's included — plus an empty `GIT_CONFIG_GLOBAL`, and, to stop git inventing an identity out of the account's passwd gecos field when none is configured, `user.useConfigOnly = true`:

   ```sh
   export GIT_CONFIG_NOSYSTEM=1          # drops every system source, Apple's additional one included
   export GIT_CONFIG_GLOBAL=/dev/null    # drops ~/.gitconfig
   git -c user.useConfigOnly=true <verb> # no identity invented from the passwd gecos field
   ```

   Without the last one, a fixture that "proves" it sets its own identity proves nothing on a machine whose gecos field is populated. **And when the question is what the *runner* sees, the instrument is a container built to match it** rather than a flag: `ubuntu:24.04` with its stock git, the toolchain `rust-toolchain.toml` names, a non-root user with an empty gecos field, no git config at any level, and the target directory inside the container. Both remaining defects of that repair were observed in it locally, instead of one hour-long push at a time. ~~**Honest bound:** its Dockerfile lived in a session scratch directory and **is not in this repository** — whether one is committed under `dev/` is a candidate for M54, not a decision ([decisions-pending.md](decisions-pending.md) → *The road to 1.0.0 and the port* → M54).~~ **[Decided 2026-09-28 (M54 Settle, S10), landed at M54 Increment 7: it is committed as [`dev/runner-faithful`](../dev/runner-faithful), beside `dev/gate` and `dev/jigc-rig` — `dev/runner-faithful cargo <args…>` builds that image, with the toolchain read from the named commit's `rust-toolchain.toml` and the posture asserted at build time, and runs the one cargo command on a clone of the commit (default `HEAD`), never a bind mount, so uncommitted changes are not what runs; the install acceptance M54 adds runs in the same image.]** The fixture half of this — which isolation a test-support builder owes and which it currently skips — is [pinning.md](pinning.md) §4.

   **A green gate on macOS never ran a file that was still open for writing (2026-10-06).** Linux refuses to execute a file that any process has open for writing — `execve` fails with `ETXTBSY`, "Text file busy" — and macOS makes no such check: a script held open for append by another process runs here and is refused there (probed on both, 2026-10-06). And a handle a test opens is not only the test's. A child forked by **any other thread** while it is open inherits a copy and keeps it until its own `exec`, which is when close-on-exec closes it; the suites fan their arms out over threads, and `cargo test` — which is what CI runs — makes a whole group the threads of one process. So a rig that copied a script with `fs::copy` and ran it a moment later raced every other thread's `Command::spawn`, and the hosted runner failed two or three **different** tests of `dev_stabilize_record` on each of four consecutive pushes of `fix/rc24-tier1` while every gate here was green. **A tooling suite places a file it will execute through `placed_executable::write` or `placed_executable::copy`** ([`tooling-tests/placed_executable.rs`](../tooling-tests/placed_executable.rs)): a child process, `cp`, does the write and is waited for, so no thread of the test process ever holds the handle and no fork can inherit one — where a retry around the `exec` would only have waited for the sibling. That file holds it three ways: a control that makes the mechanism deterministic (a child held between its fork and its exec while a handle is open) and reads the refusal on Linux; an arm that drives both helpers with such children forked during the placement; and a source fence over every suite of `tooling-tests/` — no executable bit granted and no `fs::copy` made outside the helper, but for the data copies it names. **Two bounds.** The second arm cannot be red on macOS whatever the helpers do, so it is read in `dev/runner-faithful`, never here. And the product's suites under `crates/cli/tests/` still write their hooks and stubs in the test process: each hands the file to `git` or `jigc`, which runs it several process starts later, and no run has shown one busy — the same class, counted and left where it is ([DECISIONS.md](../DECISIONS.md) → *2026-10-06 — A tooling suite places a file it will execute through a child process*).

   **A green gate does not prove a proptest-guarded invariant holds** (see *A proptest is not a gate*, below). If your change touches behavior an existing property test guards, **pin the invariant with a deterministic case in the same commit** — and if you mean to *retire* an invariant, reconcile its proptest explicitly and state a rationale you have actually checked.
6. **Commit** — one logical change, conventional message. One task = one focused concern = one commit. **It lands on the branch the work belongs to, never on `main`** ([CLAUDE.md](../CLAUDE.md) → Branches): inside a milestone build, the increment branch the harness checked out and named in the task's prompt (check `git branch --show-current` against that name before committing); outside one, a `fix/<slug>` or `work/<slug>` branch. `main` changes only through a pull request the human merges, so a commit here is never also a push to it — branches are pushed by name, the milestone branch by the harness after each landed increment.

## Starting a branch from `main`

*The human's decision, 2026-10-02* ([DECISIONS.md](../DECISIONS.md) → *Merge `main` into the branch before every pull request*). **This is the rule's one home**, beside its twin below. Every new branch — a `milestone/`, `fix/` or `work/` branch ([CLAUDE.md](../CLAUDE.md) → Branches) — starts from the **current remote `main`**, never from whatever local `main` last saw:

1. `git fetch origin`, then `git switch --no-track -c <branch> origin/main` — the branch's first commit's parent is the `origin/main` just fetched.
2. Or, to bring local `main` along first: `git switch main && git merge --ff-only origin/main`, then branch from it. **If the fast-forward refuses, local `main` has diverged from `origin/main`: halt and hand it to the human — never reset it**, because what it carries that the remote lacks is unknown.

The build harness's milestone-branch step does step 1 when it creates `milestone/<slug>/main`, checks that the new branch's tip and fork point both equal `origin/main`, and halts on a local `main` that is not an ancestor of `origin/main` ([milestone-build.js](../.claude/workflows/milestone-build.js) → `milestoneBranchPrompt`).

## Before a pull request to `main`

*The human's decision, 2026-10-02* ([DECISIONS.md](../DECISIONS.md) → *Merge `main` into the branch before every pull request*). **This is the step's one home**: the milestone close ([milestone-completion-workflow.md](milestone-completion-workflow.md) → Close), the build harness and [CLAUDE.md](../CLAUDE.md) → Branches point here. Every pull request to `main` — a milestone's, a `fix/` branch's, a `work/` branch's — is opened only after these, in order:

1. **Merge `main` in** — `git fetch origin && git merge origin/main` on the branch: a merge commit, **never a rebase**, which would rewrite pushed commits and need the force-push no agent may make.
2. **Resolve only what is the logs'.** A conflict confined to the append-only logs — `DECISIONS.md` and `implementation/project-history.md` — is resolved by keeping both sides' entries in date order: run [`dev/merge-logs`](../dev/merge-logs), which does exactly that (`DECISIONS.md` newest first, the branch's entry above `main`'s on one date; the record newest last) and refuses, writing nothing, any hunk where a side changed text that was already there; then `git commit --no-edit`. **Any other conflict, or a refusal, goes to the human**: `git merge --abort`, and stop. That includes a conflict in `crates/cli/README.md`, which is generated and never resolved in place: the human resolves the root `README.md` and regenerates the crate README with [`dev/crate-readme`](../dev/crate-readme) ([findings-channel.md](../design/findings-channel.md) → 8).
3. **Gate** — `dev/gate` green on the merged tree, because `main` may have brought in a change the branch's own gate never saw.
4. **Push** the branch by name, then **open the pull request** (`gh pr create --base main --head <branch>`).

A milestone build carries steps 1–2 as the close's `build-git` **sync** step, which the harness returns to the orchestrator in `close.sync` instead of running, because it follows the triage ([milestone-build.js](../.claude/workflows/milestone-build.js) → `syncMainPrompt`). *Why the step exists:* PR #6 conflicted with PR #5 on `DECISIONS.md` — each had added a top entry — and the conflict was resolved by hand in `adeb53e7`; `dev/merge-logs` reproduces that resolution byte for byte.

## Why this shape

Two framing notes, not extra steps:

- **One task, one concern.** The unit of work is a single focused thing — the smallest change with its own observable done-criteria. Keeping tasks small is what keeps the loop honest (a vague "make it work" task has no red step).
- **The loop is jigc in miniature.** Scope ≈ `jigc start` / compose, Gate ≈ `jigc task validate`, Commit ≈ `jigc task finalize` (one task → one commit, [finalize.md](../design/finalize.md)). Running it by hand is deliberate dogfooding — the friction we hit informs the real `single-task` workflow we're building.
- **One agent when orchestrated.** Run as a workflow, a single agent carries this whole per-task loop (scope → commit) and yields the one commit — the [increment workflow](increment-workflow.md) → Orchestration spawns one such agent per task.
- **A recorded rationale is a claim, not a fact** (M41, 2026-07-11 — [DECISIONS.md](../DECISIONS.md)). A justification written into `DECISIONS.md`, a doc-comment, or a commit message is **load-bearing**: the next reader — human or agent — trusts it and *stops questioning the choice*. So **never record a rationale you have not actually checked.** M41 produced **two false ones in a single wave**: an increment retired `slugify`'s idempotency invariant on the claim that *"the fixed-point set was exactly the valid-slug set within the caps"* (demonstrably false — and it is precisely *why* the un-reconciled proptest went unnoticed for two increments), and another wrote a doc-comment asserting a slug-only finding key was chosen *"so two dangling targets yield distinct keys"* (backwards — the full `<type>:<slug>` is strictly **more** distinct). Both passed a green gate; both survived an independent same-model review; the second fell only to a cross-model pass. A confident falsehood is worse than an admitted gap, because it **disables the next reader's skepticism**. If you cannot check it, write what you actually know and mark the rest open — an honest *"unverified"* is cheap. **Pack-shape** ([DECISIONS.md](../DECISIONS.md) → 2026-06-21 Direction): **step prose in `step:implement`** — it binds while the agent is *writing* the rationale, so it must be in front of it then, not in a doc it read last week.
- **A proptest is not a gate** (M41, 2026-07-11 — [DECISIONS.md](../DECISIONS.md)). `cargo test` runs the property/fuzz suites over **random** inputs, so a green gate means *"no counterexample was sampled this run,"* not *"the invariant holds."* An invariant guarded **only** by a proptest is therefore not gate-enforced: a change can break it, pass its own increment's gate, and surface runs later (or in the wild) once a run happens to sample the counterexample — which is exactly what happened to `slugify`'s idempotency in M41 (an edge-stopword change broke "a slug is a fixed point of normalization," passed its increment green, and was caught two increments later when the shrink seed persisted and made the failure deterministic). Two obligations follow: **(1)** a load-bearing invariant gets a **deterministic** case alongside its proptest — the proptest explores, the point test *enforces*; **(2)** an invariant is never retired by silence — if a change means to drop one, say so, reconcile the test in the same commit, and check the rationale (M41's break shipped a rationale that was demonstrably false, which is what let the un-reconciled proptest stand). Randomized coverage is a *finder*, not a *fence*. **Pack-shape: step prose in `step:gate`** — it binds at the moment the agent would otherwise accept a green run as proof.

- **A defect at a distance — fence the assumption where the set is *defined*, not where it is *used*** (M42, 2026-07-14 — [DECISIONS.md](../DECISIONS.md)). The bug class no diff review can catch, **by construction**. M42's flagship: `strip_stamp(current)` — the corpus-migration v0 arm — was written **2026-06-25 and was correct**: every doctype was at v1, so *"a v0 doc's shape is the current schema minus the stamp"* was **true**. On **2026-07-03**, **57 commits later**, `adr` bumped to schema-version 2 — also correct — and **that commit did not touch `migrate_corpus.rs` at all**. Two clean diffs; a permanent dead-end bug living in the space between them. **A reviewer looking at either change sees nothing wrong, because nothing *in* either change is wrong.** The defect is in the *relationship*, and it was created by a later, unrelated, **correct** decision quietly falsifying an earlier assumption. *(Same shape: the freeze-assert hole was accepted with the trigger "revisit if packs are ever loaded from the filesystem"; multi-pack shipped at M14, **the trigger fired, and nobody noticed** — it was prose in a ledger.)* **The rule: when your change rests on an assumption about a *set* — every doctype is at v1 · every pack is embedded · every finding has an address · every serializing surface is one of these three — do not merely satisfy it. Fence it, at the point the set is defined**, so that **growing the set trips your fence and reddens the *other* author's gate.** Had `strip_stamp`'s assumption been an assert against the manifest, M36's bump would have gone red **in its own build**, and the conversation would have happened then, for free. **This is the same medicine as *a grep is not a fence*, aimed backwards in time:** that rule says *don't enforce a property with a list*; this one says *don't leave an assumption unfenced just because it is true today*. **Pack-shape: step prose in `step:implement`** — *"Does this change assume something about a set that someone else can grow? Name the set. Then put the assumption where the set is defined, as an assert, so their change fails and not yours."* **And prefer tier-1: an assumption you can assert is not a rule at all.**
- **A grep is not a fence** (M42, 2026-07-14 — [DECISIONS.md](../DECISIONS.md) → *a census cannot enforce a predicate*). The exact sibling of the rule above, one level up: **a search finds the members you told it to look for.** A census done *by grep* — which [methodology-docs.md](../design/methodology-docs.md) → the `census` gate already requires over a hand-list — is still a census, because **the pattern encodes an assumption about where the members live.** M42 proved it nine times over. The `schema.location` census greped `schema.location` and missed `prior.location`. The `finalize.*` census greped `finalize.rs` and missed two members in the CLI. The finding-key census enumerated five clusters and missed two more (47 codes). Each fix added the missed members — **and the list stayed a list**, so it rotted again the moment the set grew. **The rule: if a property must hold of every member of a growing set, the check must live where membership is *decided*** — on the constructor, the trait impl, the serialization — **never on a list of the places you currently remember.** M42's own worst instance is the tell: the finding-key *membership* census was correctly replaced by a **predicate** (*a finding projects a key iff it serializes as a `Finding`*) — and then the predicate's **enforcement** was installed at *three hand-listed funnels*, and a fourth surface was silently emitting a different key for the same defect. The doc comment said, in as many words, *"call it at each of the three funnels."* **A guard that has to ask to be called is not a guard.** Searched coverage is a *finder*, not a *fence* — the same relationship a proptest has to an invariant. *(This binds on methodology too, not just code: a rule that lives in a workflow doc the actor must remember to read is the same object. See [milestone-completion-workflow.md](milestone-completion-workflow.md) → the serial-fixer rule, which was written after M38 and broken again at M42 by the orchestrator who had not re-read it.)*

  **Pack-shape: step prose in `step:gate`**, phrased to be inert when it does not apply (the dialect bars conditionals — a step always composes). Text to encode: *"If this change establishes a property that must hold of every member of a set, say where the property is **enforced**. If the answer is a list of sites — a grep, a census, a call-site enumeration — it is a finder, not a fence, and it will rot when the set grows. Move the check to where membership is decided (the constructor, the trait impl, the serialization), or state honestly that it is list-enforced and expected to rot."* **This one has a tier-1 sibling and the sibling is better:** where the property *can* be structural, no step is needed at all — which is what M42's finding-key seam now does in code.
- **Two masking shapes M42 added to the ban** (2026-07-14). The [gate](#gate)'s no-masking rule already forbids weakening an assertion to get green; these two pass a *green* gate while proving nothing. **(1) A snapshot assertion where the claim is an invariant.** M42's flow-43 discard arm asserted the record settled and the workbench was gone — and then **never ran a milestone verb afterwards**. The claim (*"a discarded milestone stays discarded"*) is a **lifecycle invariant**; a snapshot of the moment after the op cannot witness it, and `provision` cheerfully resurrected the milestone from its own settled record. **If the claim is a property that must hold *over subsequent operations*, the test must perform them.** **(2) A proof fixture built with the defective path.** Increment 7's `setup_partially_joined_milestone` minted its "partially-joined" record by doing `finalize` → `add-task` — i.e. **the fixture that proved the claim was itself an instance of the bug it was proving absent.** Ask of every fixture: *could this state have been reached only by the defect?* If yes, the test is circular and its green is worth nothing. **Pack-shape: step prose in `step:gate`**, folded into the existing no-masking rule's slot. Text to encode: *"Two questions before you accept a green: (1) if the claim is a property that must hold **over subsequent operations**, does the test perform them — or does it snapshot the moment after? (2) Could this fixture's state have been reached **only by the defect**? If yes, the proof is circular."*
- **Widen a guard's trigger, re-derive its response across the *whole* new domain** (M44, 2026-07-21 — [DECISIONS.md](../DECISIONS.md)). When you generalize a check, advisory, or derivation from its *motivating case* to a broader domain — the guard now fires for more inputs — its **response** (the message, the route, the edge-behaviour) was written for the narrow case and does **not** automatically stay correct across the widening. M44's completion audit caught this **twice in one wave**: the byte-floor migrate advisory was generalized from `--as adr` to *every* doctype, but its message and route stayed adr-specific (`jigc start --workflow record-decision`), so a trivial `--as changelog` migration was told to author an **ADR** — the surface-contract law-1 lie the wave itself was built to remove; and the fidelity word-boundary guard was widened from "kill `project-alpha-2.0`" to "reject any dotted run preceded by an alphanumeric," which also silently rejected the conventional `v1.0.0`. Both changes were locally reasonable and *looked* like tightening; both left the response mis-fitted to the widened domain. **The rule: when a change widens what a check *triggers on*, enumerate the new domain and re-check the response holds across all of it — most sharply at its edges (the doctype with no from-knowledge path; the `v`-prefixed version) — because the response was only ever validated on the case that motivated the check.** *(This is the build-side sibling of the planning reuse lesson — [milestone-planning-workflow.md](milestone-planning-workflow.md) → "generalize X to all cases" mis-verified at the primitive — the same generalize-without-re-deriving-the-widened-domain shape at two altitudes.)* **Pack-shape: step prose in `step:implement`**, beside the *set-fence* prompt above (both fire while the generalization is being written): *"Does this change widen what a check fires on? Enumerate the new domain and re-derive the response — message, route, edges — across all of it; the response was written for the case that motivated the check, not the domain you just gave it."* This one has **no** tier-1 sibling — "did you re-check the response across the domain" is a judgment, not a structural assert — so it stays a prompt.
- **Moving a path from relative to absolute is a widening, and it raises two questions the rule above does not name (M53's cwd arc, 2026-09-23).** *Does it survive a shell?* and *does everything that consumes it still parse it?* The arc that made every printed `git` span and the fan-out `Spawn:` line runnable from any cwd got this wrong **three times in nine commits**: the new absolute `cd` was unquoted and broke on a repository path with a space; the installed pre-commit hook's awk assumed `git -C <home>` was one field, so a quoted spaced home shifted `mv` to `$5` and the out-of-band-rename guard **failed open** silently; and `migrate <PATH>` flipped from root-based to cwd-based while five producers still *printed* a root-relative path into that verb. All three were masked by one property of the fixtures: every root came from `std::env::temp_dir()`, which never has a space — input-coverage masking, the same shape as a fixture whose single member is the special case. **The rule: when a change moves a path onto the shell (an absolute, a `-C`, a `cd`), drive at least one cell under a shell-hostile root (a space, a `'`, a `#`) and enumerate every consumer that re-parses the emitted bytes** (`command grep` for the span's shape across hooks, tests and the trial driver) — the first question is the quoting fence's, the second is nobody's until it is asked. ([pinning.md](pinning.md) §1 carries the fixture half.)
- **A fix is complete over its class's axis, never its repro** (the project-alpha-3.0 verification trial / M45 charter, 2026-07-22 — [DECISIONS.md](../DECISIONS.md); evidence [RC-alpha3/findings-verification.md](../completions/artifacts/RC-alpha3/findings-verification.md) → §4). The trial's dominant finding class — **~19 of ~44** — was the same defect returning through an axis the original fix never swept, and the axis is almost always one the engine already *enumerates*: the slot-heading guard covered the section-slot **write path** while the item-slot path corrupted at every depth (M1 guard, M16 delimiter, never joined); ref-edge workflow demands were fixed **per-field** twice (maps-to-test at M42, cites at M41) and never generalized over *doctypes-with-refs*; the staging-contract statement landed on the single-task steps and never the fan-out **siblings**. M41's audit had already named the mechanism ("the un-enumerated sibling… committed in the fix for it") — this rule is its scope-time fence. **Two obligations: (1)** at Scope, fill the **axis card** (the standing axes: doctype shape · write path · verb family · surface · task/store scope · corpus state) — a brainstormed edge-case list is a *finder*, the enumerated axis is the *guarantee*; **(2)** at Red, the acceptance test **iterates the axis** (for every shipped doctype shape × slot context …), so a member added later is covered by construction, not by memory. And prefer the **fix-shape hierarchy**, strongest first: **unify the seam** (N sibling paths is the bug behind the bug) **> derive from the registry** (the M41 erase-the-complement precedent — new members refuse loudly) **> property test iterating the real enumeration > hand-enumerated cases > prose**. *(Kin, one level apart: the set-fence rule above guards an **assumption** about a set; this guards a **repair** over one. The M43 corollary from the same trial: a seam-generated statement is only as true as its constant — a context-dependent rule needs the context as a fence input, or the fence guarantees the lie renders consistently everywhere.)* **Pack-shape: step prose in `step:scope` (the card) + `step:red` (the axis-iterating test).** *(The substrate the axis-iterating test runs on — registry enumeration, the compose goldens, the contract property suites, the trial-shaped fixture states — is [pinning.md](pinning.md).)*
