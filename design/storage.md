# On-disk storage

How managed content lives on disk: the **document file format** and the **repository layout** around it. One format serves committed documents, the staging working copy, and the future fillable form.

Builds on [structural-grammar.md](structural-grammar.md) (addressing, units, minting), [document-type-schema.md](document-type-schema.md) (slot/field/relation), and [write-commands.md](write-commands.md) (staging, `finalize`, reconciliation). For the *why*, see [DECISIONS.md](../DECISIONS.md). Notation is **illustrative** ([what that disclaims](../CLAUDE.md#how-we-work-together)).

## Source of truth

**The committed Markdown at type locations is the only source of truth.** Every other artifact — the staging working area, the edge index, the file↔state hashes — is either a rebuildable cache or a transient working copy. Delete all of it, rebuild from the `.md`, and nothing committed is lost; the system degrades cleanly to *plain Markdown a human can read and edit*. This is what keeps "documents live in the repo as plain files" honest.

**The milestone record joins this set (M39) — a strengthening, not a relaxation.** In-flight **milestone** state (the base-SHA pin + the ordered sub-task list with each sub-task's `intent`/`status`) once lived only as raw engine JSON in the gitignored `.jigc/milestones/<id>/{base,tasks}.json` — a *second*, clone-invisible island outside the `.md` set. M39 graduates it to a committed **`milestone-record`** doctype (`docs/milestone-records/<slug>.md`) and **demotes** that JSON to exactly a *rebuildable cache* (re-derived from the record when absent or stale), so the milestone record becomes a first-class member of the only-source-of-truth `.md` set: delete `.jigc/`, rebuild from the `.md`s, and milestone state survives too. The principle underneath — **`.jigc/` is the workbench, the repo is the record** (working state gitignored by *identity*, the record committed at a legible home) — is the design of record in [team-ready-state.md](team-ready-state.md); this invariant is revised in the *strengthening* direction (a new committed `.md` member), never relaxed toward a second raw-JSON source of truth.

**`source-path` is the one exception, and it is *authority* (M51).** Everything else in `.jigc/tasks/<id>/` is a working copy or a cache: lose it and the committed `.md` rebuilds the truth. A migration task's recorded `source-path` is neither. It is the **only** record of which file `jigc task finalize --approve` will `remove_file`, it exists nowhere else, and it is read back **one commit closure after** the door that wrote it — so it is a value the model above has no room for: a mutable, gitignored line that a destructive act obeys. Driven at `c5f7a85`, rewriting it to an absolute host path deleted a file in another tree at exit 0. The consequence is stated where it is enforced rather than inferred from this invariant: the raw read is **private to its loader**, which yields a typed `ValidatedRetirement`, and the sink re-validates **in the same function as the unlink** ([auto-migration.md](auto-migration.md) → Retire-the-foreign-original). Naming it here is the point — *a cache may be wrong and cost a rebuild; this one may be wrong and cost bytes.*

**And the trackability predicates are typed repo-root-relative, which is why a caller token is resolved before they are asked (M51).** This doc already says so in its own words twice: a `placement` home is *a repo-root-relative literal path*, and `config.unusable-root` refuses an **absolute** value as a law-1 lie the door tells about itself ([Placement](#placement--direct-file-and-root-located-homes-m38) → What a root knob refuses). `crate::trackable::untrackable_reason` inherits that typing and opens by trimming leading slashes, so handing it `/private/tmp/victim/keepme.md` re-reads the value as `<repo>/private/tmp/…` and answers **trackable**. The predicate is correct for its parameter; the missing step was the caller's. Every door taking a caller-supplied path therefore **resolves the token to a repo-relative path, or refuses an absolute one outright**, and only then asks ([write-commands.md](write-commands.md) → The source-side sibling).

## The document file format

### Single-file canonical Markdown

The `.md` *is* the document — not a view rendered from a hidden model file. A dual scheme (canonical model + regenerated Markdown) would make the file humans actually edit second-class, contradicting our locked principles (plain files are the source; humans edit through git; out-of-band edits are detected and reconciled). The cost — robust parsing — is paid by the format below.

### Schema-driven parse

The CLI parses an instance **against its type's schema**, never as blind Markdown. The schema already knows every section (id, heading, order) and every leaf (which slots, which fields), so the file needs **no markers for any of that** — sections match by their schema-fixed headings, slots are the prose in their schema position, fields are the labeled values the schema tells the parser to find. The only thing the schema does not know — and the only thing the file marks — is **instance-minted identity**.

### Anatomy

Three parts, and only the first and third carry any "machine" content:

1. **Front-matter** — the document's *header block* fields (status, dates, doc-level refs, and the **schema-version stamp**), as `key: value`. A **flat field block** (a strict YAML *subset*, not an arbitrary YAML document — values are typed by the schema, not coerced by YAML); a list-valued field uses **inline flow** (`relates-to: [adr:a, adr:b]`). Doc-level refs here keep the graph scannable without parsing the body. The **schema-version stamp** (M34) is a **schema-declared, engine-valued** front-matter field on every persisted doctype recording the schema version it was authored against (the `status`/`date` model — in-schema, engine-set) — so the engine emits a `---` block even for doctypes that declare no other `header:` section ([corpus-migration.md](corpus-migration.md)).
2. **Body** — schema-fixed section headings; under each, the slot prose plus (if any) a trailing field group rendered as a **bullet list** (`- key: value`). The field *grammar* is the same as front-matter; the bullet is the body's structural frame (the counterpart to front-matter's `---` fences) that keeps fields distinct from the opaque prose around them.
3. **`{#id}` item anchors** — the *only* in-body marker, on each repeatable item.

An ADR (header-heavy, all-prose sections):

```markdown
---
status: accepted
date: 2026-05-23
supersedes: adr:single-node-cache
---

# Rate-limit at the gateway

## Context
Per-client limits were enforced ad hoc in each service.

## Decision
Centralize rate limiting at the gateway.
```

A SPEC (a repeatable `criteria` section with per-item structure and a local field):

```markdown
## Acceptance criteria

### Rate limit holds at 100/min  {#rate-limit}
The gateway rejects the 101st request in a 60s window.

<!-- fields -->
- maps-to-test: `test/rate_limit_spec.rb#burst`

### Burst allowance  {#burst-allowance}
A short burst above the limit is tolerated for 2s.
```

### Identity, order, fields, slots, items

- **Identity is the path** — `docs/specs/auth-flow.md` → type `spec`, id `auth-flow`. No redundant id in the file. An **ordinary retitle** (editing the H1) changes the title field with the id held frozen (see next bullet) — identity-stable. A **path/slug rename** *is* an **identity change** (the path *is* the identity), allowed **only** through one explicit, atomic CLI op — **`jigc rename <old-slug> --to "<New Title>"`** (top-level): re-slug from the new title, rewrite the H1, repoint every structured referrer old→new, `git mv`, one transaction ([write-commands.md](write-commands.md) → `jigc rename`). An **out-of-band** `git mv` is *not* an identity change the CLI honors — it's detected and routed ("adopt as `jigc rename`" / revert), never an untracked move ([reconciliation.md](reconciliation.md) → Rename detection). A doc that is **not yet committed** has no path to be the identity of, and no committed referrer by construction, so its id moves through the in-task sibling **`jigc doc rename <addr> --to "<New Title>"`** (M48) — one owned, atomic op likewise, over the CLI-owned task working area; the moment the identity *is* committed that verb refuses and routes here ([write-commands.md](write-commands.md) → `jigc doc rename`). The surgical line is **not** "ids never change" but "ids change only through one owned, atomic operation"; **reference-integrity** survives the change (referrers repointed in lockstep) even though identity-stability does not — and diff-legibility *improves*, a slug tracking its title beating one frozen out of sync.
- **id-source = the title field, rendered as the heading** — the schema declares a `string` field as the item's id-source (`id-from: title`, see [document-type-schema.md](document-type-schema.md)); that field is rendered on disk as the item's `###` heading text (not as a trailing `- key: value` field), with the minted `{#id}` anchor carrying the frozen id slugged from the field's value at creation. A doc's title is its H1 (filename = frozen id); an item's title is its `###` heading (`{#id}` = frozen id). The title is mutable (editing the heading edits the field's value — and because the heading **is** the `id-from` field's value, a retitle of an **enum** id-source (changelog's `id-from: category`) is an enum-*value* edit and **re-validates** against the field's declared type; [write-commands.md](write-commands.md) → `jigc doc retitle-item`, M40); the id is frozen under an **ordinary retitle**, so `spec:auth-flow#criteria/rate-limit` survives editing the heading text. *(A deliberate doc-level **re-slug** — `jigc rename`, above — does change the doc's id, atomically and with every referrer repointed; that is an identity refactor, distinct from the identity-stable retitle here. Item-level ids are not yet renameable: `jigc rename` is doc-level in v1.)*
- **Order = physical order.** Reordering is moving a block — a clean diff move, never a renumber.
- **One field grammar** (`key: value`), two structural frames — header block → a flat front-matter block between `---`; a section/item block → a trailing **bullet list** (`- key: value`) preceded by an `<!-- fields -->` sentinel on its own line (the field-group boundary marker — see [implementation/parsing.md](../implementation/parsing.md) → Field-group delineation). The sentinel makes the field group unambiguous *by marker*, not by content-matching the bullet keys against the schema — so slot prose that legitimately ends with `- status: TBD` stays prose. `code-anchor` values carry presentational backticks (stripped on read, re-added on write) so the diff stays readable without polluting the stored value.
- **One prose slot preferred.** Multiple slots are allowed but each renders under a schema-fixed sub-label (matched like a heading — no new marker), which nudges schemas toward one-purpose sections. **Correction recorded at M45 planning:** this bullet — and [document-type-schema.md](document-type-schema.md) — described multi-slot **sections**, a shape the engine does not model (`SectionBody::Simple` carries a single `slot`). The shipped multi-slot is at **item** level: a repeatable item's leaves. The sub-label form is settled in [Open questions](#open-questions) below.
- **Slot prose has a heading-depth ceiling**, and it is **schema-relative** — the reserved depths follow the slot's own context (section, item nesting depth, multi-slot sub-label), so there is no fixed "safe" depth to quote here; the rule and its enforcement sites live in [implementation/parsing.md](../implementation/parsing.md) → Slot heading-depth ceiling. What it buys the format is what matters here: a heading at a reserved depth always means "structural marker," never "prose that happens to look like one."
- **Items live inside their parent file** (the criteria-in-doc decision); no per-item files.

**The slug rule is itself a versioned rule (M42).** Everything above rests on one function: `slugify` ([slug.rs](../crates/engine/src/slug.rs)) is jigc's **identity-derivation function** — it mints every doc slug, every task and milestone id, and every `{#id}` item anchor. And it is not only a minter: it is a **recognition-by-renormalization predicate** at four *production* sites over *committed* bytes — the parse path (`crates/engine/src/parse.rs:385`, where a mismatch aborts the whole-doc parse), the splice path (`write.rs:3263`), `validate` (`validate.rs:1452`), and — the irony — `migrate_corpus.rs:470`, the migration engine's own idempotency guard. The tool that would have to repair a slug-rule change is built on the function being changed.

Yet the rule is an **unversioned schema**. It sits in **no `schema-hash` and in no manifest**, so the pack-load freeze assert — the gate that blocks you from renaming a *field* — is entirely **blind** to a change in the function that names every id in every corpus ([corpus-migration.md](corpus-migration.md) → the freeze). And **no transform kind can re-mint an id**, so a slug-rule change **cannot be migrated after the fact**: *"fix it later"* is not on the table, and the freeze's usual bound-the-lock-in-cost answer does not reach it.

So the rule is **declared**: a **`slug-rule-version`** integer is recorded beside the schema manifest, with a **pack-load fixed-point assert** — the frozen-doctype freeze assert's shape, applied to the identity-mint *function* instead of a schema *shape*. A change to the slug rule is then a **declared, detectable, recorded** event, never a silent one.

**Declaring it is not optional, and the gate has three arms.** The `slug-rule.hash` arm catches the drift; the `slug-rule.version` arm stops a re-pinned hash from buying silence (a rule change owes its declared bump, in every manifest); and an **absent `slug-rule:` block blocks too** — a manifest that freezes doctype *shapes* may not decline to declare the rule the ids inside them are *minted* by. Absent-means-unchecked would have left the first two arms silenceable by deleting three lines, and any project- or third-party-authored manifest fenceless by default, over the one change no migration can repair. Opting out of the freeze remains available, but only as the **wholesale, visible** act it always was: ship **no** `config/schema-manifest.yaml` and the pack is skipped entirely. The error names the missing key and carries the exact block to paste (M42 completion audit; `engine::manifest::ManifestError::SlugRuleUndeclared`).

The honest consequence is stated once, out loud, rather than discovered in a corpus: **a corpus that spans a rule change carries two id generations permanently.** Ids minted under the old rule keep their bytes (they are frozen anchors and frozen paths); ids minted after it follow the new rule; **no migration exists or can exist** to reconcile them under the current transform model. That permanence is the price of the change — and it is exactly why the rule is *versioned* rather than merely *edited*. M42's own change is the trigger, shipped as **its own governed increment** sequenced behind the item-`id` read projection ([DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 planning: the Settle; [roadmap.md](../implementation/roadmap.md) → Milestone 42).

**The shipped rule is `slug-rule-version` 3** — `engine::slug` (`SLUG_RULE_VERSION` + `rule_fingerprint()`, pinned as the `slug-rule: {version, hash}` block in *both* shipped manifests, checked at every pack-load):

| generation | the separator map | the edge-stopword drop | `auth/session` | `1.0.0` | `On-call handoff artifact` |
|---|---|---|---|---|---|
| **1** (M39 → M42) | space, `_` → `-`; `/` and `.` **stripped** | any edge token | `authsession` (two words *fused*) | `100` (*collides* with a release titled `100`) | `call-handoff-artifact` |
| **2** (M42 → M47) | space, `_`, **`/`**, **`.`** → `-` | any edge token | `auth-session` | `1-0-0` | `call-handoff-artifact` |
| **3** (M47, current) | space, `_`, `/`, `.` → `-` | only a **whole separator-delimited word** | `auth-session` | `1-0-0` | `on-call-handoff-artifact` |

Everything else is unchanged (the transliteration table, the 5-word cap, the 50-char backstop). The `and`/`or` stopword widening the charter floated was **cut**: it fixes nothing broken and would *pay* by retiring the fixed-point property of already-minted slugs (`slugify("search-and") == "search"` — an id that no longer re-mints to itself).

**Generation 3 (M47) is the second fork: the edge-stopword drop becomes word-aware.** Generations 1–2 tokenized a hyphenated compound *before* dropping edge stopwords, so a compound's first or last component was eaten — `On-call handoff artifact` minted `call-handoff-artifact`, `Telemetry consent opt-in` minted `telemetry-consent-opt` — and the correct identity was **unreachable through every shipped command in every sequence** (`add-item` has no `--slug`, `retitle-item` freezes the anchor, `rename` is doc-level). Under generation 3 an edge token is droppable only when the boundary joining it to the rest of the slug came from a **separator** (space, `_`, `/`, `.`) or the string edge. `-` is the *join* char, not a separator, so `on_call handoff artifact` still drops its `on` — a decided cell, resolved against the rule's own separator map. The provenance is carried **positionally**, so `on On-call` drops the first `on` and keeps the compound's. Only the *mint* rule forks: `renormalize` is byte-unchanged, so all four recognition sites read committed bytes exactly as before. **Adopter note:** every rc.9 corpus spans this change. Nothing needs doing and nothing can be done — minted ids keep their bytes, no migration exists, and a driver **reads** an id (it never re-mints one), so the split is invisible to every read path; only *new* mints follow generation 3.

**The rule states itself where it mints (M47).** A versioned rule nobody can read is still a surprise, and the stated-at sentence (`slug::mint_statement`, rendered at the `{{schema:<doctype>}}` projection's `title:` line, in `jigc doc create --help`, and in `jigc doc add-item --help`) named only the two **caps** — so the two steps that produce every reported *"roughly five tokens, except when it isn't"* were stated on no surface at all: the **renormalization** (a `.` splits a token, so `v1.1` is two words — the entire reported surprise) and the **edge-stopword drop**. The sentence now states all four steps, and it is generated from the rule's own constants (`MAX_WORDS`, `MAX_CHARS`, **`EDGE_STOPWORDS`**), with the separator clause fenced against `renormalize`'s *behaviour* over every printable-ASCII char: a hand-typed member list — the failure mode a stated-at sentence rots into — cannot survive a change to the const or to the map (`slug::tests::mint_statement_states_the_whole_mint_rule`; [surface-contract.md](surface-contract.md) → The stated-at fence, seam-generated tier).

**From this commit forward the two hashes move only with their versions.** A **schema-shape** change moves a doctype's `schema-hash` only together with its `schema-version`, and a **slug-rule** change moves `slug-rule.hash` only together with `slug-rule.version`. **Stated here at M47 Increment 1, fenced at M48 Increment 11:** the check fires in CI, over the pushed range, reading both manifests at the range's base and tip and failing on any entity whose hash moved while its co-located version stood still — the slug rule among them, since the one function that names every id in every corpus sits in no schema-hash. It is **not a pack-load assert**: pack-load still only recomputes each hash against the shipped schema, and one state of the tree cannot tell a legitimate re-pin from a silent breach. A legitimate re-pin declares itself per entity on the commit that does it — `Manifest-Repin: <doctype | slug-rule>`, never blanket. **Two declared bounds:** it protects **this repo only, not adopters**, and it is **a build fence, not a surface** (no finding code, no route, no verb). The two other mechanisms stay refused — an **append-only** `(type, version) → hash` ledger is **a new stored format**, and the rule as an in-process check is **unimplementable in-process**, since a pack-load assert cannot observe a *change* **without a recorded prior** ([corpus-migration.md](corpus-migration.md) → The freeze — declared *and* enforced, which owns the fence's full statement). **M47 Increment 1, which states the rule, is its declared genesis exemption and the only one**: its two coordinated changes move a pinned hash without a shape change *by construction* — the schema-hash becomes a **presentation projection**, so all 16 doctype hashes re-pin at unchanged `schema-version`s (no schema's shape moves; only what the hash is computed over), and the slug rule forks to generation 3, moving `slug-rule.hash` together with its co-located `slug-rule.version` 2→3, which already satisfies the rule. Each re-pin lands in the same commit as the code that makes it correct, so the exemption is reviewable as a diff rather than asserted.

The **two-generation split is permanent, and there is no corpus-side gate**: nothing stamps a doc with the generation that minted its ids, and nothing should — a frozen id is *read*, never re-derived (the recognition sites read the heading's `{#id}` anchor or `renormalize` it; none of them re-mints). So a pre-M42 corpus keeps `100` under the heading `1.0.0` indefinitely, and a driver that wants an item's address must **read** it (`jigc doc show --format json` → `id`; the emitted `add-item` address), never slugify a title and guess which generation it was minted under. Two honest bounds: **`--slug`** is the escape hatch at mint time on `jigc start` / `jigc doc create` (and identity can still be refactored by `jigc rename`), but a *changelog release anchor* has neither — its id comes from the version-string title, so the fork is the only repair; and a pack that ships a **non-slug section id** still round-trips by luck (schema ids are not `is_slug`-validated at load — pre-existing, unchanged, out of scope here).

## Repository layout & state location

Committed source of truth and derived/transient state live apart:

```
docs/decisions/ docs/specs/ docs/prds/ docs/architecture/ docs/changelog/   # committed .md docs at per-doctype locations under docs-root — the only source of truth
.jigc/                      # one project-state home (committed config + bootstrap; gitignored caches)
  AGENT.md                  #   committed — the managed bootstrap routing sentence (CLI-owned; the host file references it)
  version                   #   committed — the binary-provenance stamp: which jigc built the store (recommended home; see Store provenance)
  config/                   #   committed — the project cascade layer (see Config layout)
    packs.yaml              #     pack composition (e.g. compose the embedded methodology pack)
    manifest.yaml           #     scalar-set knobs + the deltas list — created on the first `jigc config` delta
    steps/<id>.yaml         #     native step files for structural-op / tracked-fork deltas — created lazily
    fills/<id>.md           #     native content for slot-fill deltas — created lazily
  .gitignore                #   ignores the derived/transient subdirs below
  tasks/<task-id>/          #   gitignored — per-task working area (staging)
  index/                    #   gitignored — edge index (rebuildable cache)
  state/                    #   gitignored — file↔CLI-state hashes (rebuildable)
  milestones/               #   gitignored — milestone WIP (merge staging, worktrees) + the {base,tasks}.json cache re-derived from the committed milestone-record (M39; team-ready-state.md)
  displaced/                #   gitignored — the parking home for bytes jigc moved rather than destroyed: a working area's foreign entries under `<unit-id>/` with their relative paths preserved (M52), and the foreign file `relocate` parks out of a destination, by basename, at its root (M39). Nothing cleans it; emptying it is the human's
  worktrees/<sub-task-id>/  #   gitignored — ephemeral per-sub-agent code worktrees (provisioned per fan-out; torn down on a LANDED boundary, or by `milestone discard` — an aborted finalize leaves them intact for the re-run). No door removes such a path silently: each probes it first and then either refuses what it cannot prove is disposable (`--force` the one consent) or names every byte it is about to destroy — which arm a given door takes, and why, is derived where the rule lives, never re-listed here (team-ready-state.md)
```

**Per-doctype locations are human-chosen, not mechanical.** Each **located** doctype declares its own `location:` (`adr → decisions/`, `spec → specs/`, `prd → prds/`, `arch-doc → architecture/`) — deliberately the most readable name for that doctype (`decisions/` over `adrs/`, `architecture/` over `arch-docs/`), **not** a uniform `<type>s/` rule. `changelog` is **not** among them: it left the located set at **M38** for `placement: { file: CHANGELOG.md }`, carried to the repo root by the first location-only frozen migration ([Placement](#placement--direct-file-and-root-located-homes-m38), below, which owns that branch). The list above kept listing it as a `location:` doctype under a folder home from that relocation until **M46**, and it is corrected against this doc's own Placement section rather than against the pack — this is the sentence read before anything is planted at a managed home, and it sent its reader to a directory that does not exist. These nest under the **`docs-root`** parent (default `docs/` → `docs/decisions/`, `docs/specs/`, …; see [Config layout](#config-layout)) — one tidy home rather than five dirs polluting the repo root — committed, human-reviewable plain Markdown alongside the project's own `src/`. (A pre-existing same-named dir with non-conformant content is detected and routed by `ingest`, not silently overwritten.)

The three cascade layers ([overrides.md](overrides.md)) live in three homes: the **project** layer is **committed** in-repo at `.jigc/config/` (deltas + knobs, diff-reviewed); the **team** layer is **external** (`~/.config/jigc/`, same internal layout); **pack-default** ships with the installed pack (its knob surface in `config/knobs.yaml`). So `.jigc/` is one home: its `config/` subdir + the `AGENT.md` bootstrap are committed, while `tasks/`, `index/`, `state/`, `milestones/`, `worktrees/` and `displaced/` are gitignored (via `.jigc/.gitignore`). All but the last are **fully disposable** — staging and rebuildable caches. `displaced/` is not, and it is listed here because it is the exception: it holds bytes that were somewhere else until jigc moved them, so it is the one gitignored subdir whose contents no operation can reconstruct.

### Config layout

A cascade layer's `config/` dir has one fixed shape (settled M4 planning, [overrides.md](overrides.md) → Delta representation / Authoring deltas):

- **`manifest.yaml`** — the layer's deltas: a top-level `scalar:` map (`scalar-set` knobs, inline `key: value`) and a `deltas:` list (one entry per `structural-op` / `slot-fill` / `tracked-fork`, each referencing a native file, never inline prose). Every content-bearing delta records its `base-version` + the target's `base-hash` ([overrides.md](overrides.md) → Delta representation) for the **(M5)** reconciliation.
- **`steps/<id>.yaml`** — native step files in the **same form the pack's `steps/` ships** (a step body — verbatim instruction prose with `{{…}}` placeholders, optional `---`-fenced front-matter only for a `fan-out` marker; *not* a front-mattered workflow definition). Referenced by `insert`/`replace` structural-ops and `tracked-fork`; the id is the filename basename.
- **`fills/<id>.md`** — native Markdown content for `slot-fill` deltas (the body that fills a `{{fill:<id>}}` point).
- **`packs.yaml`** — pack-composition for the project (e.g. `compose-embedded-methodology: true`, composing the embedded methodology pack as `[dev ▸ methodology]`; [multi-pack.md](multi-pack.md)). Written by `jigc setup`; the only config-dir member present before any `jigc config` delta. *(`manifest.yaml`, `steps/`, `fills/` are this fixed shape but materialize lazily — only once a delta is authored.)*

The pack-default layer adds **`config/knobs.yaml`** — the closed, typed knob *declaration* (`{key, type, of?, default}`, [overrides.md](overrides.md) → Scalar knobs); override layers carry only *values* (`scalar:` in their manifest), never re-declare the surface. The loader reads these into the `PackDefaultLayer` / `OverrideLayer` the resolver consumes.

**`docs-root`** — the managed-doc parent dir (`string`, default `docs/`), one of the dev pack's knobs. The resolved `docs-root` is prepended to every persisted doctype's `location:` at schema load (`docs/decisions/`, `docs/specs/`, …), so the doctype id, addressing (`adr:foo`), and stable-id invariants are unchanged — only the on-disk path gains the prefix. Per-project overridable (`jigc config set docs-root <path>`); `.` (or `""`, which the config-set path canonicalizes to `.`) restores the flat repo-root layout. It is an **opt-in** knob: it nests only where the resolved cascade carries the key — a pack whose knob surface omits `docs-root` (e.g. the methodology pack) stays flat. Applied uniformly at **every** schema-load surface (compose/describe, finalize-promote, doc copy-in, ingest/unmanage, milestone join) so the read and write paths always resolve the same parent.

**Changing `docs-root` can orphan docs at the old root.** When `jigc config set docs-root` re-points the parent, committed managed docs already at the *prior* resolved root no longer resolve under any doctype location — they become **orphans**, detected store-side by the `file-state.orphaned-doc` advisory ([validation.md](validation.md) → Orphan detection). To catch it at the source, `jigc config set docs-root` **warns when the change would orphan committed docs** under the prior resolved root (enumerated via `git ls-files`, matched by the location-directory-basename predicate — [validation.md](validation.md) → Orphan detection, *not* a bare `.md` match), routing the operator to move them or re-point back before the knob lands. This is a **net-new seam**: `config set`'s `run_set` has no store access today, so the warning gives the config-set path its first read of the committed doc surface.

### Placement — direct-file and root-located homes (M38)

`location:` above resolves a doctype's home as **a directory** (`<docs-root>/<location>/<slug>.md`) — right for a **multi-instance** doctype (many `docs/specs/*.md`), wrong for a **singleton**, which lands one file alone in its own folder (`docs/changelog/changelog.md`, the one-file-in-a-folder anti-pattern). The **placement convention** (M38) fixes this and puts ecosystem-idiomatic singletons where an agent and a human look for them.

**The rule (binds every doctype):**
- **Singleton, ecosystem-idiomatic** → a **managed direct file at the repo root**: `VISION.md`, `CHANGELOG.md`, `README.md`. *Managed* (reconciliation applies — an out-of-band human edit is detected and routed, never silently overwritten), not a generated mirror.
- **Singleton, project-internal** → a **direct file** (no per-type folder): `docs/roadmap.md`, `docs/deferral-ledger.md`, `docs/decisions-log.md`.
- **Multi-instance** → a **folder** under `docs/` (unchanged): `docs/specs/`, `docs/decisions/`, `docs/research/`, `docs/ideas/`.
- **Killed:** every `docs/<x>/<x>.md` one-file-folder.

**The declaration — a structured `placement:` key** (schema-level, optional, skip-when-absent so the freeze hashes of doctypes that don't use it are unchanged; the additive-`Option`-with-serde-skip precedent of `display-title`/`root-render`, so absent ⇒ hash byte-identical, only `changelog` re-hashes to v2). Declared in [document-type-schema.md](document-type-schema.md) (the schema-format home); the key:

```yaml
placement: { file: VISION.md }        # repo-root-relative literal path, case-preserved
placement: { file: docs/roadmap.md }  # a direct file under docs/ (the docs/ is in the literal)
placement: { file: CHANGELOG.md }     # repo-root idiomatic singleton
# absent → today's folder behavior (location: decisions/ → docs/decisions/<slug>.md), byte-identical
```

`file:` is a **repo-root-relative literal path** (case-preserved, bypassing the lowercase-`[a-z0-9-]` slug), so `VISION.md`/`CHANGELOG.md`/`docs/roadmap.md` are each reachable exactly as written. **`docs-root` never applies to a placement doctype** — the home is the literal, so the resolved path is *composition-invariant* (`docs/roadmap.md` is the same under methodology-alone and `[dev ▸ methodology]`, fixing the flat-vs-`docs/` ambiguity that bit M37). This is the first per-doctype opt-out from `docs-root`'s uniform prepend; it honors the anti-root-pollution intent by scoping root homes to the handful of files humans already expect there (`VISION.md`/`CHANGELOG.md`). *(No `root:` flag — the literal path already encodes root-vs-under-`docs/`.)*

**The cascade layer — `placement-root` (M49).** The literal above is a doctype's **declared** home; since M49 it is not always the **resolved** one. **`docs-root` still never applies to a placement doctype** — the sentence above is unchanged and driven (`docs-root: notes` leaves `docs/roadmap.md` exactly where it was). What applies is **`placement-root`**, a knob of its own whose subject is disjoint from `docs-root`'s: a declared home **carrying a leading directory component** re-roots to `<placement-root>/<remainder>` (`docs/roadmap.md` → `notes/roadmap.md`), and a home declared **at the repo root** is never re-rooted. That derivation **is** the scope answer — `VISION.md` and `CHANGELOG.md` are unburiable by construction, so the ecosystem-idiomatic rule needs no doctype allow-list that could go stale as packs come and go.

*Why it exists, and the whole argument for it:* the **asymmetry**. A `location:` home resolves through `docs-root`; a `placement:` home resolved through **nothing** (it is the literal its schema ships), and since M38 that literal sits inside the doctype's frozen `schema-hash`, so `jigc relocate` refuses to move it. An adopter whose managed docs do not live under `docs/` therefore had **no path at all** to `docs/roadmap.md` — not a knob, not a verb, not a shadow ([completions/artifacts/M49/settle-record.md](../completions/artifacts/M49/settle-record.md) → D6, which argues the override **solely** on that asymmetry).

*Three values, not two.* `""` is **unset** (every declared home stands, byte-identical to a build carrying no knob); `.` is the **repo root** (`docs/roadmap.md` → `roadmap.md`); anything else is that directory. Unlike `docs-root`, whose two empties mean one thing, these name **different outcomes** and are unmixable by type (`Option<&str>`) rather than by convention — and `jigc config set placement-root ""` canonicalizes to `.`, so the intuitive spelling reaches the repo root while the empty string stays reserved for *never set* ([overrides.md](overrides.md) → Scalar knobs).

*Composition-invariance survives* — the property this whole section exists to protect. A project override is **one fixed value**, so a placement home still does not vary by which packs composed. That holds only while the knob is declared **identically in both shipped packs**: `knobs.yaml` collides by whole-file shadow, so a key present in one file is invisible whenever the other wins, and a home that stood in one composition and re-rooted in another would be exactly the composition-variance the literal `placement.file` was introduced to end. Pinned by a standing arm over both packs' `knobs.yaml` (`cli::pack::placement_root_is_declared_in_both_packs_identically`), not left to review.

*A re-point moves what it would strand.* `jigc config set placement-root` **detects + routes + moves** every committed doc at a placement doctype's prior home *before* the knob lands — the sibling of the `docs-root` floor above, in the same place and the same best-effort posture, and delegating to `relocate::relocate_stranded` so a foreign file squatting the new home is parked in the gitignored `.jigc/displaced/` workbench rather than clobbered. **Both homes are computed from the declaration**, never by re-rooting the prior *resolved* one: once the root is `.` a resolved home has no leading component left, so re-rooting *it* under the next value returns the same path — a destination equal to the source, a silent skip, and the doc stranded at the repo root. A **hand-edited** manifest bypasses the floor entirely; the strand it leaves is what the placement arm of the orphan sweep detects (census row below), because until the knob shipped a placement home could not move and that arm could not exist.

*What a root knob refuses, and why the refusal is at the door.* Both knobs re-point where every managed doc lives and then **move** the committed docs the re-point would strand, so the value is adjudicated **before anything moves and before the knob lands** — the alternatives are the ones that lose bytes: a warn-and-proceed moves the docs to the bad home at exit 0, and a landed knob with no move leaves the store pointing at a home no doc is at. Both knobs are bound by the same rules (`cli::config::ROOT_KNOBS` is their one home, so a rule added at one is added at both), and there are three, each asking a **different question about the same path**:

- **git cannot record it** — `config.untrackable-root` (M49): a path resolving outside the repository root, inside git's own dirs (any `.git` component, or wherever `--git-dir`/`--git-common-dir` actually point), or owned by another repository (a submodule or an embedded repo). This is not about gitignore: an *ignored* destination is a path git tracks perfectly well and has merely been told to skip — it stages a real `R` rename — and `relocate`'s squatter displacement into the gitignored `.jigc/displaced/` workbench depends on exactly that.
- **it is jigc's own workbench** — `config.workbench-root` (M50): the repo-root `.jigc/` directory, or any path inside it. Not a widening of the rule above but a **predicate of its own beside it**, because `.jigc` is a path git records perfectly well; what disqualifies it is ownership. The workbench is the tree `jigc uninstall` removes **whole**, so a managed doc homed there is one teardown away from bytes no index has a copy of. The value is **normalized lexically first** (a `./` folded, a `..` applied against the components accumulated so far) and only its **first normalized** component is asked — the workbench is exactly one directory (`<repo-root>/.jigc`), and a nested `docs/.jigc` is somebody else's directory that shares the name. The normalization is what makes the rule hold over the destination rather than the spelling: asking the value *as typed* refused the three literal forms while `placement-root docs/../.jigc` landed at exit 0 and staged `R docs/decisions-log.md -> .jigc/decisions-log.md`, because git normalizes the path it records even when the predicate does not (M50, found in increment 4's own validation). By the same token a value that climbs back **out** (`.jigc/../docs`) lands on an ordinary home and is not refused here, and one that climbs above the repository root (`../.jigc`) is the rule above's question, not this one's. The comparison is **case-insensitive** for git's own reason (`core.protectHFS`/`protectNTFS`): driven, `placement-root .JIGC` staged `docs/roadmap.md → .JIGC/roadmap.md` while the bytes landed in the real `.jigc/`, leaving the index and the worktree naming different directories for one file.
- **the store could not go on describing its docs there** — `config.unusable-root` (M50): a **file-shaped** root, an **absolute** value, or a root reached **through a symlink**. The first two are law-1 lies the door tells about itself — driven, `placement-root README.md` lands the knob at exit 0 with *every* move failed and `jigc doc list` then drops the re-rooted docs from the store surface altogether (the state this section's own "before anything moves" rule exists to prevent, produced by the door that states it), and `placement-root /tmp/elsewhere` stages `docs/roadmap.md → tmp/elsewhere/roadmap.md` while `jigc config get` reads back the absolute form, so the knob and the store name different homes. The third is git's rule rather than jigc's: git records the **link**, never a path through it, so the move stages `RD` — an index entry the worktree has no path for. **Both on-disk shapes take every existing component of the value as their subject, not its leaf**, and are asked in one walk: a symlinked *ancestor* (`linked/sub`) reaches the identical `RD` state, and a file-shaped *ancestor* (`README.md/sub`) reaches the identical vanished-store state, because a destination directory can no more be created under a file than the leaf itself can be one. The walk starts at the repository root and **never canonicalizes the root itself**: a repository legitimately sits under a symlinked ancestor, so canonicalizing would refuse every root in every such repo. **Four more shapes joined the same code by the same route, one driven cell at a time** (M51, M52): a value **padded with edge whitespace**, which cannot read back as itself — driven, `docs-root '   '` landed at exit 0 and `jigc config get` then printed a reading no operator can tell from unset; a component carrying **git pathspec magic** (a leading `:`, or a `*`, `?`, `[` or `\` anywhere), because a root prefixes every managed doc's path and `git add -- <path>` prevents *option* parsing and never magic — driven, `docs-root ':!docs'` landed at exit 0 and the promoted doc matched the exclude pathspec and reached no commit; and a component the filesystem **cannot name** (over `NAME_MAX`) — driven, `docs-root <300 bytes>` landed at exit 0 and the next `jigc validate` failed with a code-less, route-less `File name too long`, while `placement-root <300 bytes>` discovered the same fault by *attempting* the move and rolling it back, handing the operator a per-doc fault whose route cannot be followed because the value is the problem and the corpus is not. The ceiling is `NAME_MAX` **bare**, not the slug family's derived ceiling: a root's components become directories, and nothing is appended to a directory name. And a root **jigc's own install writes its adapter artifacts under** — the roots read from the installed adapter profile's declared artifact paths (the assistant's settings file, the owned guide artifact, the always-loaded bootstrap file), never spelled — because a home there mixes managed docs with the files `jigc setup` rewrites on every run and `jigc uninstall` takes back out. It is asked **last** of the seven, so a value the other six already refuse keeps the sentence it already had; the workbench is excluded from its subject, being the sibling rule's with its own code. The same pair of predicates is what `jigc relocate --from` asks of a prior home, taking these codes rather than minting its own ([corpus-migration.md](corpus-migration.md) → The freeze-exempt sibling). One code for every shape in the family, with the reason in the message — `config.untrackable-root`'s five-reasons-one-code shape — because the operator's fix is the same in each: supply a different root. A value naming **no component at all** (`""`, `.`) is the repo root, which is the flat layout both knobs document, and stays admitted — **and the ack says so**: the door folds a root value once for every reader, so a value whose landed spelling differs from the typed one (`""` → `.`, `x/../y` → `y`) lands with the fold named beside it. The empty value is the one that needs saying: a root knob has no *unset* spelling, so an operator asking for unset is given the repository root, and through rc.15 nothing on the surface said which of the two had happened.

**Identity stays explicit, never filename-derived; and `location` stays `None`.** A placement doctype sets **no `location`** (`location: None`, like the transient `commit`) — the home comes from `placement.file`, not `<location>/<slug>.md`. Path→identity (`docs/specs/auth-flow.md → spec:auth-flow`) assumes a lowercase slug under a location dir; a literal uppercase root file would reverse-map `VISION.md → vision:VISION`, never round-tripping the lowercase forward path. So a `placement` doctype **carries its fixed slug** (the singleton's type id — address `vision:vision`, `changelog:changelog`, unchanged) and its case-preserved `file:` independently, and every path↔identity site matches **that exact literal path is this doctype's one instance**, never a dir-glob.

**The census — every `schema.location` consumer needs a placement branch (the decompose cut-list).** Because `location` is `None` for a placement doctype, a site that reads `schema.location` **drops it through the transient arm** (never promoted / read / reconciled / detected) unless taught the placement case. The census is **every production read of `schema.location` / `schema.placement`**, bounded by the grep below (§Census completeness) and one row per site — each either *carries a placement branch* or is *latent, with the reason stated*. The **⚠** rows are silent data-loss / broken-guarantee, not cosmetic.

**Declared or resolved — the census's second axis (M49).** Every row below was written while a placement home was a **constant**, the literal its schema declares. A site reading that literal off a raw pack read and one reading it off the cascade were then indistinguishable, so the census never had to ask *which home?*; `placement-root` makes them able to disagree, and a site that reads the **declared** home where the resolved one is meant now silently addresses a file no other door touches — the axis's own failure mode, and a new member of the ⚠ class. So the rule, and the default every row inherits: **a site resolves the home through the cascade.** Production schemas reach every door through `cli::start::CascadeDefs`, which applies `apply_docs_root` **and** `apply_placement_root` at one seam, so *resolved* is what a row means unless it says otherwise. The **declared** home is read by exactly four kinds of site, each saying so in its own row: the **freeze/manifest** surfaces (which hash what a pack *ships*), the **migration diff** (which compares two pack-shipped shapes), the **re-point floor** and the **orphan sweep** (which both need the pre-image the knob replaces). **The M49 rows — the three sites a re-rootable home creates, added in the same pass that creates them.** Each reads *both* homes, and the pairing is the point:
- `cli::start::apply_placement_root` (`start.rs`) — the seam itself, the twin of `apply_docs_root`. Takes the **declared** `placement.file` and writes the **resolved** one onto the schema every other row then reads; a located or transient doctype falls straight through. ### Store provenance — the binary-provenance stamp (M36)

A committed record of **which `jigc` binary produced this store**, so an adopter on a different machine is told when the store was written by a different build than the one now reading it. This hardens "same resolved cascade in → same workflow out" *across machines*: two developers on divergent binaries get a surfaced advisory rather than silent behavioural drift.

**Home — a dedicated committed file under `.jigc/`, never `.jigc/state/`.** The cross-machine claim *requires the record travel with the repo*, so it must be **committed** — the gitignored `.jigc/state/` (file↔CLI-state hashes) would never reach a clone. The recommended home is a new committed **`.jigc/version`** (a one-line record, e.g. `jigc-version: <semver>`; the exact filename is an increment detail). It is **not** a new field in `.jigc/config/packs.yaml`: the cascade loader treats each config file as a closed surface and rejects unknown keys ([overrides.md](overrides.md)), so a field there risks a load-time rejection — a dedicated file is the safer shape and keeps config (cascade *input*) and provenance (a written *fact about* the store) one-file-one-purpose. The value is the engine's `CARGO_PKG_VERSION` at write time; `jigc setup` writes it and store-writing ops refresh it.

**The check — a store-scope advisory.** The store-scope `jigc validate` sweep compares the recorded stamp to the running binary's `CARGO_PKG_VERSION` and, on mismatch, emits **`store-version.binary-mismatch`** (advisory severity, store scope, report-only — an un-keyed advisory, [validation.md](validation.md) → un-keyed findings; its `target` is `null`, the declared **singleton** exception — [command-output-contract.md](command-output-contract.md) → the declared non-unique exceptions). It **never** gates a transaction or `finalize` — honoring the report-only store-scope invariant ([validation.md](validation.md) → Exit semantics). The message is informational ("store last written by jigc `<x>`; you are running `<y>`"); a version delta is a *heads-up* that two builds may resolve the cascade differently, not by itself corruption.

**Its route is schema-version-aware (M42, corrected).** The original route — *"align versions / re-run `jigc setup`"* — is a **false all-clear** whenever the corpus is stale too: `jigc setup` re-stamps `.jigc/version`, which **self-clears this very advisory** while the committed docs stay on the old schema, so the next `jigc validate` reads as progress and the *actual* fix was never named. The route therefore splits on **whether the same sweep found the corpus stale** — keyed on the fifth family's machine handle, a `schema-conformance.schema-version-current` break in the report ([validation.md](validation.md) → Version-currency is itself a surfaced break), **never** on a route-string prefix:

- **stale corpus** → the route names **`jigc migrate-corpus` first** (the verb that upgrades the committed docs), the re-stamp only after it;
- **current corpus** (a divergent binary, nothing else) → the plain align-or-re-stamp route stands — naming `migrate-corpus` here would command a verb with nothing to do (`0 migrated, 1 already current`), the same false-route failure the [managed-vs-foreign discriminator](validation.md) deletes on the other side.

The split is a CLI concern (`.jigc/version` is a store-level fact the engine, empty by invariant, never reads); the handle it keys on is engine-minted.

**Three senses of "stamp" — keep them distinct.** [corpus-migration.md](corpus-migration.md) already separates two: the per-doc **schema-version stamp** (an in-doc front-matter field recording the doctype schema version a doc was authored against) and the edge-index **cache-stamp** (the rebuildable-cache HEAD-sha freshness marker, [Derived caches](#derived-caches) below). This adds a **third** — the **binary-provenance stamp**, a *committed* store-level fact recording which `jigc` built the store. It sits on a distinct axis from both: neither per-doc nor a rebuildable cache.

### The per-task working area (staging)

A task's staging area is a **gitignored scratch dir of working copies**, in the same Markdown format. It realizes the locked concurrency primitive directly: fan-out sub-agents each write their **managed docs** to their own `tasks/<task-id>/` subdir (isolation by directory), and the CLI merges at the join **by task-id order** ([structural-grammar.md](structural-grammar.md#repetition), [VISION.md](../VISION.md) → Parallelism). This managed-doc recombination is *not* git worktrees and is never git-merged — git's text-merge is not our deterministic by-task-id join. (Fan-out **code** *does* isolate by worktree, recombined by deterministic disjoint-apply — see [CLI and git](#cli-and-git) below; the **docs** always stay on this directory-isolated by-task-id join.)

A task is **pinned to its base** (the commit it started against). Operating a task whose base ≠ the current checkout is detected and routed, the same divergence philosophy as out-of-band detection. *Rebasing* a task onto a new base is deferred (parallels three-way merge).

**The pin is one rule, tested identically at every per-task door (M47, N7).** The divergence test is the overlap-aware decision [finalize.md](finalize.md) → Parallel hand-editing states (the 2026-06-12 M17 amendment): re-pin to the new HEAD iff the moved history is **disjoint** from the task's footprint (dirty working-tree paths ∪ its promote destinations), block naming the overlapping paths otherwise. Originally this paragraph read as a blanket *"switch back or discard"* and `jigc start --task <id>` implemented it literally, which made the **read-only resume door stricter than the commit door** — verified in one repo state: resume refused, `jigc task validate` exited 0, `jigc task finalize` **landed**. Resume now makes the identical decision over the identical facts, so an agent who commits groundwork in a separate task and re-composes is carried through rather than dead-ended into a destructive-only route. The M17 amendment's rationale — *"the unconditional rejection proved wrong for serial-task shapes the methodology itself mandates"* — applies to this door verbatim; it was drawn against the *milestone* sibling and the resume sibling was simply never enumerated. Two bounds, recorded rather than discovered: a re-pin is **in-memory only** (`base.json` is never rewritten — durable task state is a landed finalize's alone, so the next invocation re-derives the decision), and the rule is keyed on the task's **unit kind**, so a **milestone sub-task** keeps the blanket refusal at **every** per-task read door — both `jigc workflow <W> --task <sub>` (sub-agent re-entry) *and* `jigc start --task <sub>` (resume, the door the sub-task's own composed footer advertises) — by design, because its commit boundary is not `jigc task finalize` at all (that refuses outright with `finalize.milestone-sub-task`) but the consciously-strict milestone finalize, which blocks on *any* moved history since the sub-agent worktrees were cut from the shared pin. Relaxing either would make a read door looser than its own commit door, the inverse of the defect. The membership test is `owning_milestone` — the same one the sub-task finalize refusal is minted from, never a second rule. *(Naming only the re-entry door here is what let the resume door be relaxed unconditionally: the bound is over the door × unit-kind axis, and it is pinned by iterating that axis.)* ([DECISIONS.md](../DECISIONS.md) → 2026-07-26 the M47 Settle, Decision 10.)

Only `finalize` produces committed changes; the working area itself is never committed (it persists on disk across sessions, so work resumes, but is lost on a clean/clone — acceptable for staging).

**A task is an area that carries its base pin (M53).** `base.json` is not only the divergence test's input — its presence is what makes a directory under `tasks/` a task at all, and the same rule keys `milestones/<id>/`. One predicate answers it everywhere: `symlink_metadata(<area>/base.json).is_file()`, read off the writer registry's own **first** member ([team-ready-state.md](team-ready-state.md) → The working area's two populations) rather than a spelled-out filename, so it cannot drift from the unwind that removes that file first. A directory holding no pin is a **residual** — a leftover a faulted teardown left standing, or a directory somebody made — and it is a work unit at no door: listed by no roster, rendered as work in progress by no orientation, named in no `also open:` block, resolved by no by-id door, and blocking no `jigc rename`, which guards against a rename invalidating a live fan-out's by-task-id join key and a residual has no join to invalidate. Clearing one is a human act, by decision: no jigc verb resolves a residual, and the refusals name the path.

Two properties make that rule safe rather than merely tidy. **Existence, never a parse** — `mint_task` writes the pin with a plain non-atomic write, so a contents-keyed predicate would have a torn-read window the atomically-persisted milestone side does not, and a legitimate area whose pin is torn, corrupt or unreadable must still reach the producers that *say so* instead of being disowned as a leftover. And **the converse is fenced, not assumed**: every production mint door writes the pin as its first content write, immediately after opening the directory, so no legitimate area is pin-less at a moment a door can observe it — checked per `MINT_DOORS` row rather than argued, because a predicate whose converse fails answers *no such task* over live work. The remaining window is the two syscalls between opening the area and writing the pin; it narrows the pre-M53 window rather than closing it, and flickers in the safe direction (a just-minted area is briefly absent from the roster, never a settled one briefly present).

**The teardown keeps what jigc did not write (M52).** A landed `finalize` removes the working area, and that area is an ordinary directory an agent working in the repo also writes into — gitignored, so no commit has a copy of what it puts there and `git status` never mentions it. Which bytes are jigc's own is [team-ready-state.md](team-ready-state.md) → The working area's two populations, once, for every door; what *this* door does with the complement is keep it: each entry moves to `.jigc/displaced/<task-id>/<relative>` before the removal, with its relative path preserved and a foreign directory moved whole, and the landed surface names every move — on stderr, and as the envelope's `committed.displaced` ([command-output-contract.md](command-output-contract.md)). It is the one disposition available here: the door takes no consent flag, and it cannot narrate the loss on the *landed-boundary* warrant its siblings use, because the commit carries the promoted docs and the index and takes nothing at all out of the working area.

**The teardown is never skipped for what jigc wrote, and never taken for what it could not move (M53).** Those are two halves of one rule, and until M53 only the first half was implemented: the removal was a `remove_dir_all`, so an entry whose move failed was destroyed a statement later by the very teardown the move existed to spare it from — at exit 0, out of a gitignored tree with no second copy, under a sentence that said the area *held one entry* when it had held two. The removal is now the registry-keyed unwind: jigc's own members go, and the directory goes through a non-recursive `remove_dir`, which refuses a non-empty directory. So a third party's bytes survive **by construction** rather than by a check — nothing is enumerated and then deleted, so even a byte written *after* the walk read the directory is safe, and a byte the walk could not enumerate at all is safe too. A succeeding `pre-commit` hook writes into this area during the commit, which is squarely inside the interval the teardown then runs over. An area left standing is then **named**: one advisory `finalize.foreign-bytes` per area, keyed at its work unit, listing what is in it and carrying a `Human` route, at **exit 0** — the commit is truth, and a kept byte is not a failure ([command-output-contract.md](command-output-contract.md) → the `finalize.*` sub-table, which also states the two doors' channel asymmetry). The subject is a re-read of the area taken *after* the unwind, never the move's failure set: the motivating cell reports zero move failures. The cost the old sentence named is unchanged and is carried on the advisory's route — a left-over area whose base pin survives makes `jigc task list` report an active task that finalized, truthfully, because it is a task jigc could not tear down.

**The milestone boundary tears down two kinds of area, and answers for both (M53).** A landed `jigc milestone finalize` removes each sub-task's `tasks/<sub-id>/` *and* the milestone's own `milestones/<id>/` — the second through the very transaction that removes a per-task area at the sibling door, so it is one primitive with two subjects. Both keep their complement, to `.jigc/displaced/<unit-id>/<relative>`, and the landed envelope's `committed.displaced` is the **union** over every area the boundary settled, sorted by `from`; the stderr narration stays per area, where each move's origin is legible in its path. Until M53 the milestone's own area was the one area nothing answered for — the boundary passed no subject for the directory it was itself deleting — so an operator's bytes anywhere under it, the join's `merged/` staging tree included, died at exit 0 with an empty stderr while the envelope printed `displaced: []`. **Which** bytes are jigc's own inside a milestone area is again [team-ready-state.md](team-ready-state.md) → The working area's two populations, and the `merged/` tree's own rule is the join's: jigc writes the `docs/` directory there and, inside it, the materialized `<type>:<slug>.md` bodies, and nothing else.

**One parking home, two kinds of unit id — a stated provenance ambiguity, never a loss.** `.jigc/displaced/` is keyed by unit id, and task ids and milestone ids are minted from intents into the same slug space, so a milestone and a task can share one. The consequence is only that a reader cannot tell from the directory name alone which unit's teardown parked a given entry; the **bytes** are safe, because a parking path that is already occupied is never overwritten — the move lands at `<name>.2`, `<name>.3`, … and the `to` the surface names says where it actually went. Keying the home by kind as well would end the ambiguity and is deliberately not done here: nothing cleans this directory, so its paths are ones a human has already been told to look at, and renaming the home is a change to a surface that has shipped.

**The working area stages managed docs; the git index stages the code.** This scratch dir is the *managed-doc* staging surface — its working copies promote at finalize. A task's **code** is staged on a separate surface, the **git index**: under the agent-stage contract the agent `git add`s its own code edits as it works, and per-task `finalize` commits that index together with the docs it promotes ([finalize.md](finalize.md) → Dirty-tree policy). So a per-task commit set has two stages with two owners — the agent's index (code, plus any agent-written owner-artifact) and jigc's promotion (docs + first-commit config) — and finalize unions exactly those, never sweeping unstaged/untracked working-tree WIP. (The milestone fan-out combines each sub-agent's **worktree-isolated** code — never a whole-tree sweep of the shared checkout — and joins the managed docs by task-id; see the [three combine modes](#cli-and-git) below and [finalize.md](finalize.md#fan-out-finalize) → fan-out finalize.)

### Derived caches

The edge index and the file↔state hashes are **rebuildable from the committed docs**, so they are gitignored, never committed: committing them would churn diffs *and* reintroduce the dual-source-of-truth we eliminated with derived inverses.

**Staleness is handled per cache, and the two are not handled alike.** The **edge index** is **stamped with the HEAD it was built against** (`index.rs`, `EdgeIndex { stamp, edges }`); a branch switch, pull, or rebase changes the docs underneath it, so `load_committed` sees the stamp mismatch and rebuilds. The **file↔state hashes** carry **no stamp and no rebuild path** — `FileStateRecord` is a bare `{ hashes }` map, and the same operations leave a recorded baseline pointing at a path that no longer exists in the working tree, which the drift probe reads as a blocking dangling baseline ([validation.md](validation.md) → Probes, the `file-state` probe). The stamp-and-rebuild sentence was written once for both and built only for the index.

M45 does **not** retro-fit the stamp; it makes the failure mode survivable where the record proves the loss is not a deletion. A dangling baseline **downgrades to advisory, with a prune route to the existing `jigc unmanage`, only when `git log HEAD -1 -- <path>` is empty** — i.e. HEAD has no history for the path at all, so nothing was deleted, the baseline is an artifact of the checkout moving underneath the cache. Every genuine-deletion case (the path *has* history and is now gone) keeps blocking, and the prune is never automatic: silently forgetting a genuinely deleted managed doc would be a regression against *"detected and routed, never silently absorbed."* Two bounds, recorded rather than discovered: the predicate is history-gated, not a stamp — a stale-but-present baseline is still trusted — and a working copy truncated to a shallow clone can false-prune (the deleting commit reads as a root, so its deletion diff never materializes), which under-blocks and never over-blocks ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle, Decision 7). (The hash baseline's first-run edge case is noted in [write-commands.md](write-commands.md) → reconciliation.)

**The prune route carries one carve-out (M52).** The downgrade above is unchanged — the history gate still decides advisory-vs-block — but the *route* on the advisory arm is not universal. A sub-task is pinned to its milestone's **base**, which by construction predates the commit `jigc milestone create` lands the record in, so wherever the checkout stands at that pin — the provisioned worktree does by construction, the shared checkout whenever it is put there — the milestone's **own** record reads absent-and-history-less: the dangling-baseline cell exactly, whose route, followed, runs `jigc unmanage` over the record the milestone is run from. Recorded against the installed `1.0.0-rc.15` in the M52 per-axis review (`completions/artifacts/M52/baseline-surfaces.md` §4.3) and re-driven at HEAD before the fix, where `jigc task validate <sub>` printed that route for a live milestone from both the shared checkout and the provisioned worktree. So the task-scope sweep's caller — the only party that can see which work unit owns the task — names that one path (`engine::file_state::LiveRecord`), and the arm keeps the same check id and the same advisory severity while stating what the path is and routing at no verb. It is **path-keyed**: another milestone's record, and every other managed doc, keep the prune route byte-identically, and a record with HEAD history is still a genuine deletion that blocks.

### Concurrent writers

**Isolation-by-task-id is a property of the working areas, never of the derived caches.** A provisioned worktree binds to the **main checkout's** `.jigc`, so under a fan-out each sub-agent isolates its doc area (`tasks/<sub>/`) and its code worktree while **all N share one `state/file-state.json`, one `index/edges.json`, and one `milestones/<id>/tasks.json`** — the split is stated in [team-ready-state.md](team-ready-state.md) → What a fan-out worktree isolates. This section owns the other half: what those shared writers do when two of them run at once. It is the carve-out [VISION.md](../VISION.md) → principle 3 / Parallelism and [CLAUDE.md](../CLAUDE.md) → Concurrency point at, so that the isolation sentence there is not read as a universal.

**Every writer of the three shared files persists through `state::persist`** — write a process-unique temp sibling, then `rename` — so no reader ever sees a half-written file. That is the *corruption* half, closed for the two caches at M45 and for `tasks.json` at M46 Increment 1 (its four writers — `mint_milestone`, `add_task`, `drop_sub_tasks`, `reseed_cache_from_record` — were a plain truncating `fs::write`, which a concurrent reader observed as `EOF while parsing a value at line 1 column 0`). The *lost-update* half is decided per file, and the three answer it differently on purpose (M46 Increment 1; [DECISIONS.md](../DECISIONS.md) → 2026-08-18):

- **`file-state.json` — merged, base-relative.** `FileStateRecord::load` stashes the loaded map as a merge **base** (a `#[serde(skip)]` field, so the golden-locked byte form is untouched, and record identity stays the `hashes` map alone). `save` re-reads the on-disk map as *theirs* and merges over `base ∪ ours ∪ theirs`, per key: **`ours == base`** (including *both absent*) ⇒ take **theirs**, value or absence — we never touched this key, so the other writer's `record` or `forget` stands; **otherwise** ⇒ take **ours**, value or absence — including our own deletion against a concurrent re-record. Both sides touching one key is the conflict cell and resolves to the **later saver**: a path has exactly one last-known-good hash, so "combine two hashes" has no meaning to reach for.
- **`index/edges.json` — locked, not merged.** A decision, not an omission: the index is **stamp-rebuildable by construction** (a stamp mismatch rebuilds it from the committed `.md`s, per Derived caches above), so a lost delta costs one rebuild and never a wrong answer. Merge semantics here would be gold-plating.
- **`tasks.json` — persisted atomically, deliberately not merged.** Excluded on evidence rather than by omission: every production caller of the four writers is an **orchestrator door** (`milestone create` / `add-task` / `add-from-spec` and its rollback, and the cache re-seed the eight `milestone <verb>` doors share), and no sub-agent-time verb reaches one; the single door a live fan-out can still run re-seeds **byte-idempotently** (early return when both cache files exist, record-derived bytes otherwise). And the per-key rule above has nothing to key on — a `TaskList` is a registry, not a flat map, so a set-union would resurrect exactly the ids `drop_sub_tasks` exists to retire.

**The save-scoped lock closes the window the merge alone leaves open — with a declared weakening.** A base-relative merge fixes the *sequential* interleave; under true concurrency the gap between `save`'s re-read of *theirs* and its `rename` is still open, and a sibling landing inside it is overwritten by a save that returned `Ok`. `engine::state::with_save_lock` runs the whole critical section under an advisory lock — taken on a **stable `<filename>.lock` sibling**, never the target's own fd, because `write_atomic` replaces the target inode on every `rename` and a lock there would guard an inode the next persist orphans. Three properties are load-bearing and stated rather than assumed: the lock is **save-scoped** (acquired and released inside `save`, never held across a verb); the critical section **spawns no subprocess**, which is what keeps jigc's own `pre-commit` hook — a nested `jigc validate` process — from waiting on a parent that waits on it; and the spin is **bounded** (~1 s) and then **degrades to running unlocked rather than blocking**, because a rebuildable cache must never wedge a command behind a lock a crashed sibling still holds. The degrade is exactly the pre-lock behaviour: the merge still runs, only the narrow window reopens. **What *spawns no subprocess* forbids, and what it does not (M52).** It is a rule about **this critical section** and about **jigc's own processes**: jigc's `pre-commit` hook is a nested `jigc` process, so a subprocess started while the lock is held can end up waiting on a parent that is waiting on it. It says nothing about the far wider windows a *transaction* opens elsewhere, and in particular it does **not** forbid capture-and-compare across a subprocess — which is exactly what every `FileCas` row of `cli::rollback::ROLLBACK_POPULATIONS` does: jigc writes a file, the user's hook and the whole fan-out boundary run in between, and the restore compares the file against the bytes jigc left before it puts anything back ([finalize.md](finalize.md) → Rollback discipline). Both windows are at HEAD today, which is why that discipline exists at all. The two rules point the same way: the lock is short *because* nothing may interrupt it, and the rollback compares *because* its window is full of things that do.

**The base travels with the moved value, never a fresh load at save time.** The finalize hand-off is the path this matters most on: the record loaded in `Task::validate` is carried **by value** through staging, the `git commit`, and the pre-commit hook's whole separate `jigc` process, and is saved only in finalize phase 7. Re-loading it there would compute our delta against a base that already contains the hook's writes — our copy would read as *unchanged* for the hook's keys and, worse, as a *deliberate* delta for keys the hook retired. A refactor that swaps a carried record for a fresh `load` voids the merge without breaking a type, which is why the fact is written at both ends of the hand-off in code as well as here.

**What none of this buys — and the pair that makes the cost observable.** *"Out-of-band edits are detected and routed, never silently merged"* ([CLAUDE.md](../CLAUDE.md) → Architectural invariants) is a property of the reconciliation state machine **plus a recorded baseline**: the `DRIFTED + TOUCHED → conflict-block` arm is reachable only from a recorded hash, and the same bytes with no recorded hash take the `UNKNOWN → baseline-adopt` arm, which is an *advisory*. A lost baseline therefore does not degrade the guarantee, it switches it off — silently, at exit 0, with both sides' bytes merged into one commit. That contrast is pinned as a standing pair in `crates/cli/tests/reconciliation_baseline_contrast.rs`: one repo, one out-of-band edit, one in-task write, and one input difference. It is not only a concurrency statement — the baseline is legitimately absent on a teammate's fresh clone (`.jigc/` is gitignored), after `jigc unmanage`, and after the sanctioned "delete the caches, rebuild from `.md`s" — so the cost is a standing property of the cache, and the merge above is what stops a *concurrent writer* from producing it.

### Edge index lifecycle

The edge index ([document-type-schema.md](document-type-schema.md) → Bidirectional, but the inverse is derived) is a derived map of every cross-reference edge across the committed store. Its lifecycle has **five sites**, all deterministic:

| site | action | persistence |
|---|---|---|
| **committed rebuild** | first read after a stamp mismatch (branch switch, pull, rebase) — rebuild from committed `.md`s | atomic; persists in `.jigc/index/` with the new stamp |
| **working overlay** | `validate(task)` overlays the task's pending writes on the committed index for the scope of the run ([validation.md](validation.md) → Scope = effective state) | derived per-call, never persisted |
| **OOB absorb** | reconciliation's clean-absorb path incrementally updates the committed index for the absorbed doc's edges ([reconciliation.md](reconciliation.md) → Parse classifier) | atomic, in-place |
| **fan-out join** | at `join`, sub-task working overlays merge into the parent's working overlay by task-id order ([workflow-dialect.md](workflow-dialect.md#fan-out--join)) | derived, in-memory, never persisted |
| **finalize commit** | phase 7 invalidates the stamp; next read rebuilds against the new HEAD ([finalize.md](finalize.md)) | best-effort; cache-stamp absorbs failure |

One rule keeps the model honest: **the index is never persisted with task deltas in it.** Task overlays live in-memory for the scope of a `validate` or `finalize` run; only `finalize` writes them through (indirectly, via stamp invalidation → next read rebuilds against the new HEAD). This is what makes "delete `.jigc/`'s gitignored caches, rebuild from `.md`s, nothing lost" hold for the index too — committed `.md`s + the cascade (now including committed `.jigc/config/`) are the only source of truth.

The **working-overlay derivation**: walk the task's working area, parse each `.md` per the schema, emit the same `(source, relation, target)` edges the committed-rebuild path would emit, layer them over the committed index. Forward-ref integrity (the `finalize` gate) walks the *overlaid* graph; inverse-cardinality (completeness, store-scope) walks the *committed* graph. No expensive merge — overlay is read-side only.

**M45 defines the layering: the overlay shadows by `from`.** Today the walk unions committed ∪ staged with neither dedup nor shadowing — *"layer them over"* settled nothing. The rule M45 builds: if the task touched a `from` identity, that doc's **staged edge set replaces** the committed one for that identity; every untouched identity keeps its committed edges. Union-without-shadowing was the unwritten default and is wrong in both directions — it double-renders an edge that exists on both sides, and it keeps rendering an edge the task **removed**, under prose promising the reader *all* of a doc's grounding. Dedup-only was declined as the discount: it hides the double-render on one consumer and leaves the removed-edge lie intact. The rule's precondition is that a staged doc is authoritative for its own identity, which holds because **every staging path produces a complete doc** — `copy_in` is a whole-file copy, and `create` copies the committed body in for singleton and non-singleton alike (M43). The discriminator already exists (`task_froms`, computed in `overlay_working` and read by `ref-resolves`); shadowing extends it to the edge walk.

**Two precondition violators, recorded here rather than discovered later.** (1) The **migration-squatter branch** seeds a **blank** staged doc while a committed instance exists at the same slug, so its empty edge set shadows the committed one — arguably correct (the committed body *is* the foreign file being replaced), but a real behavior change on a shipped path, accepted deliberately. (2) **`task_froms` is populated *before* the doc is read and parsed**, and a parse failure `continue`s — so an unparseable staged doc sits in `task_froms` carrying **zero** edges. Under shadowing its empty set would hide the committed edges and a relation slice would render **nothing**, under the same prose promising *all* of a doc's grounding (today's union still renders the committed ones — so this is a regression the rule would introduce, not a defect it inherits). The fix ships with the rule: **populate `task_froms` only after a successful parse**, so a doc that failed to parse never claims authority over its own identity ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle, Decision 3 and its pre-decompose review).

## CLI and git

**The CLI orchestrates; git executes the VCS mechanics.** The CLI never reimplements branch / worktree / merge — it shells out to `git`. A *workflow* may trigger git deterministically (e.g. `finalize` staging + committing) exactly as it triggers any other structural command; git is deterministic, so the CLI core still makes no LLM calls. (`milestone-execution`'s fan-out **isolates sub-agent code by worktree** — each sub-task `git add`s its own edits in its own worktree — while its **managed docs** stay directory-isolated in `tasks/<sub>/` areas recombined by the by-task-id join; the worktree decision was *reopened and revised in M31*, see the three combine modes below and [Open questions](#open-questions).)

**git merges code; the CLI merges managed docs — never the reverse.** Letting `git merge` reconcile two edits to the same `.md` would *blind text-merge* the structured, anchored format — corrupting `{#id}` anchors and section structure and reintroducing non-determinism. **This 2026-06-04 rationale stays binding** — and M31 honors it: only *code* (never a managed doc) ever rides a worktree, and even code is never `git merge`d. So **three** combine modes, not two:

- **Overlapping writes to the same managed doc → always the CLI's deterministic by-task-id join** (one checkout, resolved against jigc_home). This is the single *managed-doc* merge primitive; git gains no second one. **The `fan-out` primitive's *docs* are exactly this case**: sub-tasks write managed docs into directory-isolated `tasks/<sub>/` areas, recombined by the join — never `git merge`. The algorithm is [The by-task-id join](#the-by-task-id-join-m7) below.
- **`fan-out` *code* → worktrees + deterministic disjoint-apply with block-on-collision** (the **third combine mode**, M31). Each sub-agent runs in its **own git worktree** (own index/HEAD) and `git add`s its code there; `finalize` combines the N attributable staged code-sets by **applying them in task-id order**, blocking + routing the named colliding paths on a same-file collision. This is **neither** the doc join (it operates on code, off the by-task-id overlay) **nor** ordinary `git merge` (no three-way text-merge — it is disjoint-apply, or block). It is the worktree-isolation the locked concurrency invariant already mandates ("each sub-agent writes to an isolated working area keyed by task ID … merged by task ID"), applied to code.
- **Disjoint *code-only* coarse work with no shared managed doc → may run in separate worktrees + `git merge`** — ordinary VCS, nothing for the CLI to mangle. This is a general capability of "the CLI shells out to git," distinct from the deterministic fan-out code-combine above.

**Why the CLI owns placement — the same rationale as owning the merge.** That the CLI, not `git`, merges managed docs is one face of a single rule: **the LLM places nothing, so it can misplace nothing.** Where every write lands is computed deterministically — a doctype's `location:` prefixed by the resolved `docs-root` (above), a section/item address resolved against the schema — never chosen by the model. This is the write-side of the determinism boundary ([CLAUDE.md](../CLAUDE.md) → "The LLM writes only through the CLI"): the agent hands prose for a *named slot*, and placement, cross-ref wiring, and merge are all CLI-owned. A hand-placed file bypasses this and is simply unmanaged — outside the store, the index, and reconciliation.

**Code resolves against the worktree; the doc-store + `.jigc/` resolve against jigc_home.** During a fan-out, a sub-agent's **code, git index, and HEAD** resolve against its **worktree** (`repo_root`), while the committed **doc-store** and the shared **`.jigc/`** (config, task areas, caches) resolve against **jigc_home** — the main checkout (`dirname(git rev-parse --git-common-dir)`). The committed doc-store has one canonical home (the main checkout); resolving it against a worktree would be the worktree-doc-bleed the merge invariant above forbids. So the two seams split cleanly: worktrees carry code, jigc_home carries docs and state.

A fresh worktree **rebuilds** the derived caches (per the stamp rule) and copies nothing else: every cascade layer is already reachable — the project layer is in-repo, the team layer is external, pack-default ships with the pack — and the per-developer `local` layer is deferred ([overrides.md](overrides.md)).

## The by-task-id join (M7)

The deterministic merge primitive (edge-index lifecycle **site 4**). A milestone fans out over its task list ([structural-grammar.md](structural-grammar.md#work-units-and-runtime-identity) → work-units); the milestone pins **one shared base** at `jigc milestone create` and every sub-task inherits it, so "present at the milestone base" is a deterministic lookup against a frozen commit, never a live-filesystem race. Each sub-task stages writes in its **own isolated `tasks/<sub-task-id>/` area** (isolation by directory). At the `join` the CLI recombines those areas into the parent's working overlay. The merge is a **pure function of the set of sub-task areas** — same set in, byte-identical result out, regardless of completion order — which is the property M7 exists to prove.

> **Isolation in M7 is structural + join-checked; the write-time barrier is M8.** "Each sub-agent writes only to its own area keyed by task id" is the locked invariant, but the *write-time* mechanism that enforces it depends on the `jigc workflow W --task <id>` re-entry that scopes a write to the acting sub-task — which is **M8** (control plane). In M7 the sub-areas are separate directories and are populated as fixtures; isolation is enforced at the **join**: a staged doc that is not attributable to its own sub-area is a blocking finding. The write-time barrier (rejecting a misdirected `--task`-scoped write) lands in M8 with the real sub-agent write path.

The algorithm:

1. **Order by task id, never by anything else.** Enumerate the sub-task areas by their **sorted task id** (an ordered key, never `read_dir`/filesystem order, never completion order). Every accumulator the merge touches (staged-doc set, edge overlay, finding list) is order-keyed (a sorted map / sorted vec), so iteration order cannot leak into the output.
2. **Disjoint union of staged docs, classified by provenance.** Each sub-area's staged docs are folded into the parent overlay in that order. The classification depends on a bit recorded at stage time — **`created`** (the doc was minted in this sub-task) vs **`edited-from-base`** (the doc existed in the committed store at the milestone base and was copied in for editing). This discriminator is what makes the next two rules decidable; without it the join could not tell a clash from a coincidental slug collision.
3. **Same-doc clash → blocking, never a blind merge.** Two sub-areas staging **`edited-from-base`** writes to the **same committed-at-base slug** is a partition violation: a blocking **`join.same-doc-clash`** finding, routed to a human. The CLI does not section-merge or last-writer-win — overlap of a shared target is an error, not a merge case (a section-level union was considered and rejected; see [DECISIONS.md](../DECISIONS.md) 2026-06-04). The **mixed case** — one sub-area `created` a slug the other `edited-from-base` (same slug) — is *also* a blocking clash, not a suffix.
4. **Colliding *new* instances → deterministic suffix.** Two sub-areas each staging a **`created`** instance whose minted id slugs the same (e.g. two coincidental `adr:cache-strategy`) are *distinct docs*, not a clash. The lower-task-id instance keeps the bare slug; each higher one takes the deterministic numeric suffix (`-2`, `-3`, … in task-id order) per [structural-grammar.md](structural-grammar.md#ids-provenance-and-minting). The join then **rewrites that instance's intra-document self-references** to the suffixed id in lockstep, so the renamed doc never dangles or points at its sibling. (A ref to *another* colliding doc cannot arise here: it would be a cross-area ref, rejected by rule 5 — one area is one sub-task.)
5. **Cross-area refs → blocking, checked per sub-area.** A staged ref that resolves only inside a *sibling* sub-area is rejected — see [validation.md](validation.md) → the cross-area rule. Mechanism: the join runs the forward-ref check **once per sub-area**, resolving that area's outgoing edges against `committed ∪ that one area` (reusing the single-area `ref_resolves` walk unchanged), **never** against a merged multi-area overlay — a naïve union of all sub-areas' `docs/` would silently resolve cross-area refs by mere path-existence.

The result is the parent working overlay, already **suffix-resolved**: every colliding `created` slug has its final (possibly suffixed) id before `finalize` sees it, so `finalize`'s destination-path sort never sees two docs competing for one path. `finalize` then commits the overlay (the commit-shaping — one aggregate commit vs per-sub-task commits — is the **`finalize.fan-out.squash`** cascade knob, M8; [finalize.md](finalize.md#fan-out-finalize)). The overlay is derived in-memory for the run, never persisted with task deltas in it (the edge-index invariant above).
