# Assistant adapter

The thin, per-assistant shim between the neutral CLI and a specific coding assistant (Claude Code, Cursor, Codex). It is the *entire* integration surface — kept tiny and **CLI-generated** so it can never become the next bloated rules-pile.

Builds on [VISION.md](../VISION.md) (assistant-neutral core + thin adapter; the sub-agent seam), [bootstrap.md](bootstrap.md) (the sentence it injects), [workflow-dialect.md](workflow-dialect.md) (the fan-out dispatch it binds), and [overrides.md](overrides.md) (config-family YAML). For the *why*, see [DECISIONS.md](../DECISIONS.md). Notation is **illustrative**.

## Neutral core, per-assistant profile

The core CLI knows nothing about any assistant. **All** assistant-specific knowledge lives in a small **adapter profile** — *how to inject* the bootstrap, *how to allowlist* `jigc`, *how to spawn* sub-agents. Swap the profile → new assistant, zero core changes.

This is the second of two **orthogonal extension axes**, the core neutral to both:

- **domain** → a **pack** (development is the first).
- **assistant** → an **adapter profile** (Claude Code is the first).

The profile is a **config-family artifact** (YAML, like schemas and manifests): config is YAML, content is its native format.

## Generated, minimal, regenerated

`jigc setup` (or `jigc adapter install --assistant claude-code`) **generates** the adapter from the profile and **regenerates it on upgrade**, so the integration stays current and can't rot — the thesis applied to integration itself: structure is CLI-owned, not hand-maintained. *(Built today: `jigc setup`, single embedded profile. The `jigc adapter install --assistant <X>` / `adapter regenerate` verb surface + multi-assistant selection is the designed shape, not yet built — it lands with profiles-beyond-Claude-Code, [Open questions](#open-questions).)*

`jigc setup` also **initializes the in-repo project layer** (`.jigc/config/`) when absent — so the project resolves as *set up* (orientation's clean state, [bootstrap.md](bootstrap.md) → Orientation output examples — keyed on the project layer's presence) and the cascade has a committed project layer to record deltas into ([overrides.md](overrides.md)). A fresh layer is empty (no customizations yet); it exists so the project reads as configured and is ready to carry deltas.

### The adapter's owned artifacts (M48)

VISION commits the adapter to *"a one-line pointer in root `CLAUDE.md` plus **a small set of skill/command files that each just call the CLI**"* — and until M48 the install commit carried the pointer and none of the files. The pointer half shipped at M9; this half did not, so an adopter had **no version-matched path to jigc's own guides at all** (the pre-1.0.0 trial had to seed `QUICKSTART.md`/`MIGRATING.md` into a sibling directory by hand and declare it operator seeding). The first one lands here: **the guides, as an adapter-owned artifact**.

**The principle it establishes, which is the load-bearing part — not the prose.** Guidance jigc owns ships as an **artifact jigc stamps and replaces on update**, never as repo prose copied into the user's tree (which would make the user's repo the owner of content jigc should own). Concretely the artifact is:

- **profile-declared.** *Where* it goes and *what header it opens with* are assistant knowledge — `.claude/skills/jigc/SKILL.md` is Claude Code's skill convention, not jigc's — so both live in the profile's `guide:` target and the neutral core only copies them. The target is **optional**: an assistant with no place to put a guide declares none, and the install is **inert** there, never an error.
- **generated from the one copy of its content.** The body is the repo's own `QUICKSTART.md` + `MIGRATING.md`, embedded at compile time (the same move as the pack's `include_dir!` of `packs/methodology/` from the workspace root), so there is no second authored copy to drift behind them. Their **in-repo relative links are resolved away** in the shipped bytes — every one points at a file of the *jigc* repository and dangles from an adopter's tree, and a guide that strands its reader on a followed link would author a law-1 defect in the same motion that fixes one. The label survives; only the link does.
- **self-describing.** A front matter carrying the profile's own keys, then jigc's two: the `jigc-version: <the build that wrote it>` stamp convention `.jigc/version` already uses, and `jigc-body-blake3:` — the digest of the artifact's **own body**. No side record is kept: the file says which build wrote it and what jigc wrote, which is what makes ownership decidable later by reading the file alone. Neither key may be declared by a profile.
- **rewritten whole on every `setup`**, the `.jigc/AGENT.md` mold — so a re-run on the same binary is byte-identical (no in-file idempotency markers), and a copy stamped at an older version is **replaced and re-stamped**. That is what *"regenerated on upgrade"* means for a file only `setup` writes: `jigc upgrade` reads and routes, it does not write, so the replacement door is the post-upgrade `jigc setup` re-run.
- **committed with the rest of the install**, so a clone gets the guides that match the binary that wrote them — its path is an ordinary member of the install commit's enumerated pathspec above.

### `jigc setup` has assistant-*neutral* install responsibilities too

The adapter profile is the *assistant-specific* half of setup; setup also performs installs that are **not tied to any assistant** — the project-layer init above is one, and the **M19 doc↔code backstop** is another. These are not adapter-profile content (a Cursor or Codex project wants them identically), so they live in `setup`'s neutral install path, **distinct from the per-assistant profile**.

- **The doc↔code backstop (M19) — an assistant-neutral git `pre-commit` hook.** `jigc setup` installs a `pre-commit` hook (into the hooks dir git resolves — usually `.git/hooks/`, see the install discipline below) that runs `jigc validate` (the store-wide doc↔code sweep, [validation.md](validation.md) → Store-scope re-validation) so committed-doc drift is surfaced **automatically, without the agent remembering to run it** — the M18 finding was that the on-demand detector never fired, so the over-time advantage went untested. It is **warn-only**: the hook always exits `0`, surfacing stale-anchor findings to the committer but **never rejecting the commit** (a *blocking* store-sweep would reject commits for unrelated pre-existing drift — the masking-trap M18 avoided — and would self-gate `jigc finalize`, which commits without `--no-verify`; see [finalize.md](finalize.md) → 6. Commit). Because the hook fires inside `finalize`'s own commit, its warning reaches the agent through finalize's **success-relay** of hook output ([finalize.md](finalize.md)). **The hook's output discipline is the load-bearing contract (M19 review B2)** — it is what separates a useful backstop from a per-commit annoyance, so it is spec, not prose. The hook **keys on content findings, not on the exit code** (the exit code is wrong-way-round — `jigc validate` exits 0 on *found drift* but non-zero on not-a-project / probe-missing / probe-integrity, [validation.md](validation.md) → Auto-firing the sweep). Concretely: the hook runs `jigc validate --format json` and surfaces a human-readable warning to the committer **only when the report names `doc-code` in its top-level `blocking_probes` array** — since M47 the keyed surface, so an *advisory-only* `doc-code` finding no longer warns ([validation.md](validation.md) → Auto-firing the sweep; [command-output-contract.md](command-output-contract.md) → The store sweep's envelope); on (i) a clean store, (ii) a store whose only `doc-code` finding is advisory, (iii) not-a-jigc-project, (iv) the `doc-code` probe missing, (v) any `pack-probe-integrity` meta-finding, it **prints nothing and exits 0**. So a clean commit is never noised, an unconfigured or probe-less repo never breaks a commit, and the warning fires only on real drift.

Install discipline mirrors the profile injectors: **idempotent** (a sentinel-marked block, re-runnable, and **regenerated on every `setup`** like the managed `.jigc/AGENT.md`), **non-destructive** (preserves/wraps any existing `pre-commit` hook), and it must resolve the real hooks dir (honoring `core.hooksPath` and the git-worktree `.git`-is-a-file case) — **and the success summary names the dir that resolution returned**, never a `.git/hooks` literal (M47/D4: under `core.hooksPath`, and from a linked worktree whose hooks live in the main checkout's common dir, the literal names a file that does not exist; the summary renders it repo-root-relative when the hook lives inside the repo and absolute when it does not, so the printed path is followable from where `setup` was run). The **PATH-vs-absolute-`jigc`** choice is a real hazard (a hook calling bare `jigc` runs whatever is on PATH at commit time — possibly a stale binary); the silent-exit-0 guard above also covers a hook whose `jigc` has since been removed (it no-ops cleanly rather than breaking every commit). Being a git hook (a VCS-event install), it is assistant-neutral by nature — the same hook serves every assistant.

**The install commit's pathspec — `setup` commits its own install, and only its own install (M48).** `jigc setup` lands its footprint as a dedicated `chore(jigc): install jigc workspace config` commit so the scaffolding never rides the user's first `finalize` ([project-setup.md](project-setup.md) → Idempotency & irreversibility). The pathspec is **enumerated, never a blanket `git add -A`**: the always-loaded host file (`CLAUDE.md`), the settings file (`.claude/settings.json`), the managed `.jigc/AGENT.md`, `.jigc/.gitignore`, the `.jigc/version` provenance stamp, the project layer (`.jigc/config/`), **the adapter's owned guide artifact** (below), the root `.gitignore` **only** when setup itself seeded the secrets floor on a fresh repo, and the `pre-commit` hook **iff the hooks dir git resolved puts it inside the working tree** — each filtered to present-and-not-gitignored. Two things setup writes are deliberately *not* in it: the transient `.jigc/` working area (gitignored by setup's own `.jigc/.gitignore`) and the machine-global `doc-code` probe (it lives beside the binary, not in the repo). **The hook's membership is a rule, not a fixed answer**, because the hooks dir is not fixed: the usual `.git/hooks/pre-commit` is not a trackable file, but an in-repo `core.hooksPath` makes the same hook an ordinary working-tree file that must be committed like any other install file — so the pathspec is derived from where the hook *landed* (under the canonicalized repo root, outside git's own `--git-dir`/`--git-common-dir`, **and owned by this repository** — the hook's own directory must answer this root when asked `rev-parse --show-toplevel`), naming the hook **file** and never the hooks **dir**, which may hold the user's other hooks. **Location is not trackability:** a hooks dir under the root can belong to *another* repo — shared hooks vendored as a submodule, or a plain embedded repo — and naming such a path takes the *whole* install commit down in opposite ways (inside a submodule `git add` refuses fatally; inside an embedded repo it stages nothing at exit 0 and the pathspec-limited `git commit` then dies on a path git does not know), which is why the ownership question is asked of git rather than a shape enumerated. **And the filesystem is not the only place that question has an answer:** a submodule that is *registered but not checked out* — what a plain `git clone` without `--recursive` leaves, i.e. the default clone — is an empty directory with no `.git` inside, so `rev-parse --show-toplevel` from the hook's dir answers *this* root while the index still holds the `160000` gitlink and `git add` refuses just as fatally. So the ownership question is asked of **both** sides: git's answer from the hook's own directory, *and* whether the index holds a gitlink at any ancestor of the hook's path. Deriving it from the *printed* path would not work either: the summary renders `.git/hooks/pre-commit` repo-root-relative, and a `.git`-internal pathspec entry is inert (`git add` on it stages nothing and exits 0), so a relative-path rule would look green while committing nothing.

**And because no test can promise git will accept a path, the hook is a *soft* member of the pathspec.** Seven of the eight entries are files setup wrote at paths setup chose; the eighth sits wherever the user's `core.hooksPath` put it — and a sparse-checkout that excludes that dir refuses the hook while every location and ownership test above says "committable". So a `git add` refusal **the hook entry is responsible for** costs the hook's membership and nothing else: the hook is dropped from the pathspec and git is asked again, which falls back to the already-declared bound (the hook is installed and reported, and left as the containing repo's file) instead of an install that cannot be completed at all. Attribution is **behavioural, never a match on git's message** — if the retry succeeds the hook was the cause, and if it refuses again it was not. A refusal that survives the retry, and every refusal on a pathspec that never carried the hook, is **loud on both halves** — a rejected `git add` is as fatal to the install commit as a rejected `git commit`, so it surfaces the same blocking `setup.install-commit` finding, routed on git's own cause rather than the git identity it was first written for.

**Declared bound — "a clone gets the backstop" is conditional, on two independent axes.** (i) **The hook is not always committable at all.** A `core.hooksPath` pointing outside the repo, and the **common** hooks dir a linked worktree resolves to, are outside the tree git commits from; there the backstop is a purely local install and a clone gets none of it. (ii) **Even committed, it is machine-specific.** The body embeds the **installing machine's absolute `jigc` path** (the PATH-vs-absolute hazard above), and its own guard makes a missing binary a silent exit 0 — so on another clone the tracked hook no-ops until that developer's own `jigc setup` rewrites it to their path (which setup then commits). Both halves are stated rather than engineered around: a PATH-relative hook would trade this bound for the stale-binary hazard, and the silent no-op is the correct failure for a warn-only backstop.

**It is an install artifact, not a managed document (M19 review N2).** The `pre-commit` script is a peer of `.claude/settings.json` and `.jigc/AGENT.md` — written by `jigc setup` (the deterministic CLI, no LLM), living wherever git's hooks dir resolves (usually git's control dir, but an in-repo `core.hooksPath` puts it in the working tree — see the install commit's pathspec above), **outside** the managed-doc store, the `file-state` hash set, and the reconciliation/edge-index machinery. It is never reconciled or treated as a doc; it is regenerated by `setup`. (No determinism-boundary or "LLM-writes-only-through-the-CLI" tension: `setup` is the CLI writing an install artifact, exactly as it writes the adapter host files today.) ([roadmap.md](../implementation/roadmap.md) → M19.)

There are **no per-command wrappers**. The agent shell-calls `jigc` and learns each command just-in-time from composed output (command-refs); a wrapper-per-command would be a static, partial surface that undercuts the "one entrypoint" promise. What the adapter *does* generate is a small, **catalog-derived** set of **human-facing workflow launchers** (e.g. a Claude Code slash-command per workflow), each just calling `jigc start --workflow <X>` — the *human's* path to kick off a specific workflow directly. That stays consistent with the rule: it's bounded and **regenerated from the workflow catalog** (not a hand-maintained pile), and it's not the agent's path (the agent still shell-calls the front door).

## The three responsibilities

### 1. Inject the bootstrap — hook (primary) + line (floor)

The bootstrap reaches the agent by the assistant's *best available* mechanism, declared in the profile:

- **A hook that calls the CLI** — injects the bootstrap plus a *thin live nudge* at session start (e.g. Claude Code's `SessionStart` running the front door). Fresher and higher-salience than a buried rules line, and it makes the bootstrap's "advertise *and* demonstrate" automatic: the agent's first context already shows live orientation. **Primary** where supported.
- **A static reference** in the always-loaded file (`CLAUDE.md` / `AGENT.md` / Cursor rules) — the **universal floor**: works where there's no hook system, and cheap insurance if the hook fails. The reference is *not the sentence inlined* — it is a stable one-line pointer (Claude Code: an `@.jigc/AGENT.md` import) to a **managed bootstrap file** the adapter writes under `.jigc/` and **regenerates on every `setup`**. This keeps the always-loaded file clean (a single pointer line, no marker-fenced block of content) and keeps the bootstrap text CLI-owned and rot-proof — the *structure is generated, not hand-maintained* discipline applied to the floor itself. The always-loaded file is touched only to ensure the pointer is present (idempotent on the exact reference line); the content lives in the managed file. (An assistant with no import mechanism falls back to inlining the sentence; the profile declares which.)
- **A resume / post-compaction hook** (capability-dependent) — *if* the assistant exposes a "context resumed" or "compaction completed" event, the adapter re-injects the bootstrap on that event so a mid-task compaction doesn't lose the routing pointer. The profile's `resume` event slot declares whether the assistant supports it; Claude Code ships this when the API exposes such an event. The universal compaction baseline (independent of any hook capability) is the routing footer the CLI appends to every agent-facing output ([workflow-dialect.md](workflow-dialect.md#emitted-format) → Routing footer; [bootstrap.md](bootstrap.md) → Context compaction resilience).

**Discipline:** the hook obeys the same *routing, not content* rule — it injects the bootstrap + at most a one-line current-state nudge, **never a content dump**. Its value is freshness and salience, not volume; the agent still *pulls* real context JIT via `jigc`. (Capability-dependent: the profile declares which mechanisms the assistant supports; the line is the floor.)

**The managed bootstrap body** (`.jigc/AGENT.md`) is five paragraphs, all stable: the canonical routing sentence ([bootstrap.md](bootstrap.md) → The sentence, verbatim); the **read rule** (managed = exactly the `jigc doc list` set — **the committed set** — read via `jigc doc show`; everything else — source, tests, any file not in that set — is read freely: the crisp discriminator the never-read-directly prohibition depends on, naming only stable verbs so it cannot rot; added 2026-07-17 from the RC lacon trial, B17 — and extended the same day by the surface-comprehension review, B4, with the two edges the flat rule did not compose with: a doc **staged in the open task** is not yet in the committed set, so its sanctioned read is `jigc doc show <doc> --task <id>`, never the file; an **`unregistered`** row is not yet managed — directly readable until adopted; and amended 2026-07-21, M44 Inc 4 change 2, from the rc.7 discoverability rerun with the **binary-derived-behavior** clause: project source stays freely readable, but how `jigc` *itself* behaves is learned from the installed binary — `jigc --help`, `jigc describe`, `jigc doc schema` — never a checked-out jigc or pack source tree, which need not match the binary in use; this closes the stale-source reach the flat "read source freely" clause otherwise licensed, scoping the freedom to *project* source without contradicting it); a one-line **context-compiler framing** (what `jigc` *is* and the division of labor — the mental model behind the never-read-directly rule; added 2026-07-06 from the RC greenfield trial, and its doc-slices promise scoped **per-tier** 2026-07-17, B2: a workflow pulls the slices *it declares*, and a quick fix legitimately declares none — the unscoped "slices your task needs" read as broken on the zero-slice tier); the **output contract** (stop on a non-zero exit, follow the output, never retry blindly — M36, narrowed 2026-07-06: the per-exit-code *meanings enumeration* is retired because each outcome's meaning rides in the command's own output — **every finding carries a route** (the advisory-route floor, [validation.md](validation.md) → The advisory-route floor; never `null`): a blocking finding or a repairable advisory names the action to take, an informational advisory says "no action needed" — plus, reinstated 2026-07-17 by the surface-comprehension review (B4), the **one-line exit-code taxonomy** — amended 2026-07-23 (M45 Settle, Decision 6) to `1 error · 2 usage · 3 blocking findings at a task-scope gate · 4 migration review hold` — the added qualifier is *at a task-scope gate*, because the unqualified *"3 = blocking findings"* was true of the gate that minted it and false as a general claim: a store-scope `jigc validate` reports blocking content findings at **exit 0**, and a rejected write blocks at **exit 1**. **That store-scope clause carries its own exception since M47** (the rc.10 wave, RC-alpha4 A3): it shipped *unqualified*, and four days later the 2026-07-24 confidence-audit fix minted `schema-conformance.schema-version-ahead`, whose exit **flips** — so the preloaded contract claimed exit 0 while the sweep's own trailer said "exits non-zero", and the trial planted exactly that state and read the preload as the lie it was. The stance is now scoped to the real predicate (`render.rs` → `validation_store_exit_flips`), stated as **the class, not a list** — four conditions flip it (an unreliable pack probe · an out-of-band rename · an unmigrated corpus · an above-current stamp) and enumerating them in a preloaded paragraph is content that rots, exactly like the retired meanings table. **The class is the flip itself, not a cause** (the M47 completion-audit correction): the clause first shipped as *unless the sweep itself could not be trusted*, which is true of three of the four and **false** of the out-of-band rename — that sweep worked and is reporting a real structural-identity change it found (its own trailer says so) — so the stated class excluded a real member, the same law-1 lie one tier down. The clause now claims only what holds over the whole axis: *a few conditions flip that exit*, and then the sweep **exits non-zero and its closing line names the condition and why**. The one an agent actually meets is still **named** — a doc stamped above this build's schema-version — in the store trailer's own words (`render.rs` → `AHEAD_STAMP_PHRASE`), and the surfaces are asserted to agree ([validation.md](validation.md) → Exit semantics owns the exception list itself; this tier names one instance and points at the closing line for the rest). The agreement is asserted **over the axis, not over one member**: the conditions live in one enumerable table (`render.rs` → `STORE_EXIT_FLIPS`, the same table the predicate, the `report_only` field and the trailer key on), each member carrying the witness finding, the closing line it renders, and whether its flip means an untrustworthy sweep — so `bootstrap_clause_covers_every_store_exit_flip` drives **every** condition through the real renderer and reddens when a fifth one would falsify the clause. The line carries the stable numeric key alone, which both independent readers otherwise had to reverse-engineer; the meanings stay in the output, and the taxonomy itself — every code, its meaning, and its scope qualifier — is owned by [command-output-contract.md](command-output-contract.md) → The exit-code taxonomy, **not** restated here. *(The earlier clause "the four numbers are frozen CLI constants, so the line cannot rot" was aspirational: at rc.8 only 3 and 4 are named constants and both are `pub(crate)` in the binary crate. M45 mints the one table constant and asserts **this line against it** — statement == constant — which is what actually makes the line unrottable.)*); and the **machine-output contract** (added 2026-07-21, M44 Inc 4 change 1, from the rc.7 discoverability rerun — the driver-facing facts the model otherwise reverse-engineered by scraping text: **every verb speaks `--format json` on a successful or validation outcome** — the scope is deliberate, the N4 carve-out, since a usage error rejected by clap *before* the JSON funnel prints plain text — and the **composed producers** `jigc start`/`jigc workflow`/`jigc migrate` **return the minted task id at `.task`**, read there and never scraped from the human line (`migrate` rides the same pinned `{task, text}` compose shape because it composes the `migrate-<type>` workflow over the minted task; the rc.7 baseline refuted "migrate lacks `.task`"); it names only the global `--format` flag and the stable `.task` key, never a per-verb enumeration, so it cannot rot).

### 2. Make `jigc` frictionless

Allowlist `jigc` in the assistant's permission/settings so the agent runs it without friction. This is the **path-of-least-resistance** the bootstrap *depends on* — if `jigc` prompts every time, the agent routes around it and the whole bet fails. Generating this makes it a guaranteed setup step, not something a human must remember.

*Honest boundary: this is enforcement by **ergonomics**, not by sandbox.* A non-compliant agent that decides to ignore the adapter and edit files directly bypasses us — there is no kernel-level block, and the architecture explicitly does not promise one ([VISION.md](../VISION.md) principle #3). The bet: frictionless `jigc` access + bootstrap *advertise+demonstrate* + "the CLI is the only path that knows the wiring" make compliance the cheaper path. Out-of-band edits, when they happen, are detected and reconciled via the engine-native `file-state` probe ([write-commands.md](write-commands.md) → Out-of-band reconciliation), not prevented.

**The `deny` safety floor — a bounded blocklist, not workflow enforcement (M36).** Alongside the `permit` allowlist, the profile carries a small, **enumerable `deny` list** that the same install path merges into the settings file's `permissions.deny`. It is a **safety floor against catastrophic/exfil actions**, deliberately *orthogonal* to the managed-doc boundary: it does **not** police whether the agent writes docs through `jigc` (that stays the ergonomics bet above, never a hard block), and it is **not** the deferred `PreToolUse` managed-write enforcement hook ([Open questions](#open-questions); [VISION.md](../VISION.md) principle #3) — conflating the two would install a sandbox where the architecture promises none. The floor is fixed and small enough to state as the design:

- **Destructive / exfil shell** — `Bash(rm -rf:*)`, `Bash(curl:*)`, `Bash(wget:*)`, `Bash(git push --force:*)`.
- **Secret-file reads — each pattern denied on *both* surfaces.** A `Read`-tool deny (`Read(./.env)`, `Read(./.env.*)`, `Read(./**/*.pem)`, `Read(./**/id_rsa*)`, `Read(./**/*.key)`, the common credential files) blocks the `Read` tool — **but a `Read`-rule deny does not stop `cat .env`**: a shell read reaches the same bytes through Bash, which `Read` rules never see. So each secret pattern also carries a **Bash-command twin** scoped to that path (`Bash(cat ./.env:*)`, `Bash(cat ./.env.*:*)`, …) — the reason the list carries paired entries, not one per file. The twin is a **floor, not a seal** — `less`/`grep`/a Python `open()` still read the file — and that honest gap *is* the *ergonomics-not-sandbox* posture: the floor stops the obvious footgun, not a determined agent. (The secret **set** is the same one the fresh-repo `.gitignore` floor seeds — [project-setup.md](project-setup.md) → the secrets-floor `.gitignore` — one list, two enforcement points.)

**Merged, never clobbered — mirror `inject_allowlist`.** Adding the floor to a `.claude/settings.json` that *already* carries a user `deny` array is the **same structure-aware merge** as the `permit` path ([Generated, minimal, regenerated](#generated-minimal-regenerated) idempotency; [project-setup.md](project-setup.md) → Idempotency & irreversibility): navigate/create `permissions.deny`, ensure each floor pattern is present (append-if-absent), preserve every user entry and unrelated key, write back — a re-run is a byte-stable no-op. It never replaces a user `deny`.

**No self-collision.** The floor's `git push --force` / `rm -rf` denies target the *agent's* Bash tool; `jigc` itself shells `git add`/`git commit`/`mv` as a **binary it invokes directly** (never routed through the agent's denied Bash surface — [CLAUDE.md](../CLAUDE.md) "CLI orchestrates, git executes"), so `finalize`'s own commit is unaffected. The floor constrains the agent, not the CLI.

### 3. Bind the spawn mechanism

The profile carries a **launch template**. The CLI renders its fan-out dispatch (`task_id` + entrypoint) *through* the template into the assistant's launch primitive — for Claude Code, a Task-tool invocation running `jigc workflow W --task <sub>`. The locked seam holds: **CLI owns the payload; the adapter owns the launch** — and the template is the *only* assistant-specific bit.

**Launch templates are typed-schema validated at install.** The template is the actual surface that decides whether the sub-agent ever sees the CLI's payload, so an unvalidated template is a determinism-boundary leak: a stale profile could omit the `{{task_id}}` placeholder, paraphrase inline instructions, or fail to invoke `jigc workflow` — and the sub-agent's writes would never reach the working area the join expects. The profile's launch template carries a schema declaring:

- **required placeholders** the CLI fills — the template must contain both `{{task_id}}` and `{{workflow}}` literally (a missing one is a hard install error);
- **the required invocation pattern** — the template must contain a `jigc workflow … --task …` invocation (the rendered command, however the assistant primitive surfaces it, must shell out to the CLI; no inline-paraphrased instructions to the sub-agent);
- **forbidden patterns — a *decidable* rule, not a heuristic** (M8): the check operates on the **whole rendered template** and asserts it contains **at most one newline total**, **exactly one backticked span** (the `jigc workflow … --task …` invocation), and **no** slot-author marker (`<<author:`), ATX heading (`#`/`##` at line-start), or `Run:`/`Spawn:`/`> ` directive marker anywhere — any of which signals re-authored workflow-body prose rather than a launch line. Free prose around the backticked invocation is fine. The rule is purely lexical (decidable at install with no judgement) and rejects the determinism-boundary leak — an inline paraphrase of the sub-agent's instructions — without a vague "looks like prose" test.
- **the backticked span's shape — a structural rule** (M31, the WF4 worktree binding): the span itself must be **either** the bare `jigc workflow … --task …` invocation **or** that invocation prefixed by a single `cd <worktree> &&` — exactly one whitespace-delimited token after `cd` (it is the CLI-filled `{{worktree}}` placeholder, validated *structurally*, never matched against a value, so the determinism rationale holds), and **no other shell** (a non-`cd` prefix like `rm -rf x &&`, a multi-token `cd` argument, or any trailing `&&`-chaining is rejected). This directs each fanned sub-agent into its own detached worktree (`design/storage.md` → the third combine-mode) without reopening the door to arbitrary shell. The shipped Claude Code template is one line: `` Use your Task tool to run: `cd {{worktree}} && jigc workflow {{workflow}} --task {{task_id}}` `` — the CLI fills `{{worktree}}` with the deterministic `.jigc/worktrees/<task_id>` path (the same `worktree_path` convention the fan-out `Spawn:` emit uses).

Validation runs at `jigc setup` / `jigc adapter install` / `jigc adapter regenerate`. **A broken template is an install-time error** with a precise pointer to the schema violation; the install does not complete. The intended *runtime* complement — the join's **never-started detection** ([workflow-dialect.md](workflow-dialect.md) → `fan-out` / `join`), which would catch a template that *passes* schema but still fails to reach the CLI at runtime — is **deferred past M8** ([DECISIONS.md](../DECISIONS.md) 2026-06-04). So in M8 the install-time schema check stands alone: it catches the broken template before any sub-agent runs, but a schema-valid template that misfires at runtime is an accepted, unsurfaced gap (a never-started sub-area contributes nothing to the join rather than surfacing as a routed outcome).

## The adapter profile

A small YAML spec of "how to wire into assistant X" (illustrative):

```yaml
# adapters/claude-code.yaml
assistant: claude-code
inject:
  - reference: { file: CLAUDE.md, to: .jigc/AGENT.md, syntax: at-import }  # floor: a managed bootstrap file + an `@`-import pointer (no inlined block)
  - hook: { event: SessionStart, run: "jigc start" }          # primary; calls the CLI — bare `jigc start` is read-only orientation
  - hook: { event: Resume, run: "jigc start", when: supports(resume) }  # post-compaction re-injection (ships when the assistant API exposes the event)
allowlist:
  file: .claude/settings.json
  permit: ["Bash(jigc:*)"]          # allow rules must name the tool scope (`Bash(…)`) — a bare `jigc *` glob is rejected by the harness
  deny:                               # safety floor — merged into permissions.deny, never clobbered (see § Make jigc frictionless)
    - "Bash(rm -rf:*)"
    - "Bash(curl:*)"
    - "Bash(wget:*)"
    - "Bash(git push --force:*)"
    - "Read(./.env)"                  # each secret pattern pairs a Read deny with a Bash twin (Bash(cat ./.env:*), …)
    # …secret-file set + its Bash twins — full list in the prose above
spawn:
  template: "Use your Task tool to run: `cd {{worktree}} && jigc workflow {{workflow}} --task {{task_id}}`"
guide:                                  # optional — the adapter's owned artifact (M48)
  file: .claude/skills/jigc/SKILL.md    # assistant-specific path; jigc writes and commits it
  front-matter:                         # the assistant's own header keys, emitted verbatim
    name: jigc                          # above jigc's `jigc-version:` + `jigc-body-blake3:`
    description: How to work in a jigc-managed repository — …   # stamp lines, which no profile may declare
```

Profiles for known assistants **ship with the CLI** (Claude Code first); additional profiles are **installable** later — a swappable layer parallel to packs.
