# Assistant adapter

The thin, per-assistant shim between the neutral CLI and a specific coding assistant (Claude Code, Cursor, Codex). It is the *entire* integration surface — kept tiny and **CLI-generated** so it can never become the next bloated rules-pile.

Builds on [VISION.md](../VISION.md) (assistant-neutral core + thin adapter; the sub-agent seam), [bootstrap.md](bootstrap.md) (the sentence it injects), [workflow-dialect.md](workflow-dialect.md) (the fan-out dispatch it binds), and [overrides.md](overrides.md) (config-family YAML). For the *why*, see [DECISIONS.md](../DECISIONS.md). Notation is **illustrative** ([what that disclaims](../CLAUDE.md#how-we-work-together)).

## Neutral core, per-assistant profile

The core CLI knows nothing about any assistant. **All** assistant-specific knowledge lives in a small **adapter profile** — *how to inject* the bootstrap, *how to allowlist* `jigc`, *how to spawn* sub-agents. Swap the profile → new assistant, zero core changes.

This is the second of two **orthogonal extension axes**, the core neutral to both:

- **domain** → a **pack** (development is the first).
- **assistant** → an **adapter profile** (Claude Code is the first).

The profile is a **config-family artifact** (YAML, like schemas and manifests): config is YAML, content is its native format.

## Generated, minimal, regenerated

`jigc setup` (or `jigc adapter install --assistant claude-code`) **generates** the adapter from the profile and **regenerates it on upgrade**, so the integration stays current and can't rot — the thesis applied to integration itself: structure is CLI-owned, not hand-maintained. *(Built today: `jigc setup`, single embedded profile. The `jigc adapter install --assistant <X>` / `adapter regenerate` verb surface + multi-assistant selection is the designed shape, not yet built — it lands with profiles-beyond-Claude-Code, [Open questions](#open-questions).)*

**Where it installs: jigc_home, from every cwd (M53).** The install is one per **repository**, not one per checkout — the pack loader reads `<jigc_home>/.jigc/config/`, `jigc config set` writes its delta there, the `.jigc/` workbench and committed doc-store bind to it ([storage.md](storage.md)), and the `pre-commit` hook lives in the repository-wide common hooks dir whichever checkout installed it. So `jigc setup` and `jigc uninstall` resolve their subject through **jigc_home** (the main checkout, which outside a linked worktree is simply the repo root), and from a linked or fan-out worktree they act on the main checkout's install and **say so** in the ack — text-only, the same declared bound `jigc task finalize`'s commit-site line carries ([command-output-contract.md](command-output-contract.md) → Evolution posture). Driven before this was true: `setup` in a linked worktree installed a worktree-local `.jigc/` that nothing read, and `uninstall` in a fan-out worktree removed the repository-wide hook at exit 0 while reporting a teardown of an install it left entirely standing, with all four of its refusal guards inert because they were pointed at a checkout whose `.jigc/worktrees/` and `.jigc/tasks/` do not exist ([DECISIONS.md](../DECISIONS.md) → 2026-09-23 setup and uninstall bind jigc_home). `jigc upgrade`, the artifact's reading door, asks about the same home.

`jigc setup` also **initializes the in-repo project layer** (`.jigc/config/`) when absent — so the project resolves as *set up* (orientation's clean state, [bootstrap.md](bootstrap.md) → Orientation output examples — keyed on the project layer's presence) and the cascade has a committed project layer to record deltas into ([overrides.md](overrides.md)). A fresh layer is empty (no customizations yet); it exists so the project reads as configured and is ready to carry deltas.

### The adapter's owned artifacts (M48)

VISION commits the adapter to *"a one-line pointer in root `CLAUDE.md` plus **a small set of skill/command files that each just call the CLI**"* — and until M48 the install commit carried the pointer and none of the files. The pointer half shipped at M9; this half did not, so an adopter had **no version-matched path to jigc's own guides at all** (the pre-1.0.0 trial had to seed `QUICKSTART.md`/`MIGRATING.md` into a sibling directory by hand and declare it operator seeding). The first one lands here: **the guides, as an adapter-owned artifact**.

**The principle it establishes, which is the load-bearing part — not the prose.** Guidance jigc owns ships as an **artifact jigc stamps and replaces on update**, never as repo prose copied into the user's tree (which would make the user's repo the owner of content jigc should own). Concretely the artifact is:

- **profile-declared.** *Where* it goes and *what header it opens with* are assistant knowledge — `.claude/skills/jigc/SKILL.md` is Claude Code's skill convention, not jigc's — so both live in the profile's `guide:` target and the neutral core only copies them. The target is **optional**: an assistant with no place to put a guide declares none, and the install is **inert** there, never an error.
- **generated from the one copy of its content.** The body is the crate's own [`crates/cli/guides/QUICKSTART.md`](../crates/cli/guides/QUICKSTART.md) + [`crates/cli/guides/MIGRATING.md`](../crates/cli/guides/MIGRATING.md), embedded at compile time (the same move as the seam's `include_dir!` of both packs under `crates/cli/packs/`), so there is no second authored copy to drift behind them. Both guides and both packs live **inside** the `jigc` crate since M54 (settled 2026-09-28), because a published crate carries only its own directory, and there is no root copy of either guide ([release.md](../implementation/release.md) → What the package carries). Their **in-repo relative links are resolved away** in the shipped bytes — every one points at a file of the *jigc* repository and dangles from an adopter's tree, and a guide that strands its reader on a followed link would author a law-1 defect in the same motion that fixes one. The label survives; only the link does.
- **self-describing.** A front matter carrying the profile's own keys, then jigc's two: the `jigc-version: <the build that wrote it>` stamp convention `.jigc/version` already uses, and `jigc-body-blake3:` — the digest of the artifact's **own body**. No side record is kept: the file says which build wrote it and what jigc wrote, which is what makes ownership decidable later by reading the file alone. Neither key may be declared by a profile.
- **rewritten whole on every `setup`**, the `.jigc/AGENT.md` mold — so a re-run on the same binary is byte-identical (no in-file idempotency markers), and a copy stamped at an older version is **replaced and re-stamped**. That is what *"regenerated on upgrade"* means for a file only `setup` writes: `jigc upgrade` reads and routes, it does not write, so the replacement door is the post-upgrade `jigc setup` re-run.
- **committed with the rest of the install**, so a clone gets the guides that match the binary that wrote them — its path is an ordinary member of the install commit's enumerated pathspec above.

**But jigc replaces only what jigc wrote.** The stamp is what makes ownership decidable from the file alone, so before any write `setup` recomputes the body's digest, compares it to the recorded one, and **re-assembles the whole file around it** to compare with what is on disk. Three states, and only two of them are jigc's: **absent** (the first install) and **owned** (every byte is what jigc assembles — a re-run, or a copy from an older build, both replaced). Everything else is the user's — a body edited under jigc's own header, **an edit anywhere in the front matter**, a file carrying no front matter at all, a front matter without jigc's stamp — and is left **byte-identical**, by `setup` and by `uninstall` alike.

**The oracle answers for the whole file, not the body (the rc.24 fix pass's completion audit).** It first compared the digest with the body and never read the front matter — and the front matter is where the assistant's own keys live. Driven on `1.0.0-rc.24`: a rewritten `description:` and an added `allowed-tools:` line were replaced by `jigc setup` at exit 0 with no finding, and the file deleted by `jigc uninstall`, the bytes in no git object, under a first sentence that says *edit it and it becomes yours*. Three checks now leave no byte out: the body hashes to the recorded digest; the body's opening sentence names the same version the `jigc-version:` line records (the one front-matter value jigc cannot predict, since any build may have written the copy, so it is tied to the digest through the sentence that repeats it); and the file equals the artifact assembled from this profile's front-matter keys, that version, that digest and that body — one assembly function, used to write and to check. **The stated bound is across builds and fails closed:** a copy written by a build whose profile front matter or opening sentence differs from the running build's is jigc's own and reads as the adopter's — left alone and reported, and reinstalled by deleting it and re-running `setup`. No published build differs in either, so no existing install meets it. **A second bound, older than this one:** the digest is of the bytes on disk, so in a fresh clone whose checkout git converted to CRLF the copy reads as edited and is left alone, at both doors; nothing is lost there.

Left alone, and *said*: a refusal raises the un-keyed `adapter-guide.user-modified` **advisory** carrying a route, never a block. Blocking an install because one guide file was edited would be hostile, and an install that stops there is worse than one that leaves the file alone and names it. The route states **both** admissible answers — keep your copy, or delete it and re-run `jigc setup` for jigc's own — because keeping the edit is a legitimate choice, not a defect to repair. A refused artifact also drops out of the summary's installed list *and* the install commit's pathspec: the line it would print says "stamped with this build", which of a user's copy is a lie, and the user's edit stays their business, unstaged.

**One batch, one hash move — the rule every guide edit obeys, stated here because the digest is what makes it cost something.** The artifact's body is the crate's own `QUICKSTART.md` + `MIGRATING.md` (`crates/cli/guides/`), so **any** byte changed in either file — a typo, a re-worded clause, a whole new paragraph — recomputes `jigc-body-blake3:` and produces a *different* artifact. For an adopter whose copy is still jigc's own that is free (the next `setup` rewrites it). For every adopter who has edited theirs it is not: each move re-raises `adapter-guide.user-modified`, and a wave that touches the guides in five commits hands that adopter the same advisory five times while their copy falls five builds behind, one build at a time. So **a wave lands every guide byte it owes in one commit** — the two source files and `guide_preamble`'s generated paragraph together, since all three feed `guide_body()` — and the reviewable consequence is one digest move per wave, not one per fix.

*Its second datum is F-10, and it is the same shape one size down:* **a four-task feature moved it twice.** Task 2 corrected `MIGRATING.md`'s committing-door count — a numeral the count fence requires to move with the registry, in the commit that moved the registry — and task 4 then landed the feature's owed guide paragraph, so the batch commit was again the **second** move. The rule's unit is *a wave*, and the commits inside one are where it is actually broken: a fence-driven numeral and a feature paragraph are both guide bytes, and what would have obeyed the rule is deferring the numeral to the batch, which is exactly the practical consequence the paragraph above already states. It is recorded rather than glossed for the same reason M52's is — the check is `git log --oneline <base>..HEAD -- crates/cli/guides/ crates/cli/src/setup.rs` (a range reaching back past M54 adds the guides' pre-move root paths, `QUICKSTART.md MIGRATING.md`), and a rule whose violations are quietly dropped from its own history is a rule nobody can run that check against.

*Its first datum is this repo's own violation, kept rather than glossed:* **M52 moved it twice.** The wave's decomposition put every guide byte in one late increment, and Increment 3 then corrected a `jigc task validate` sentence that happened to live in `QUICKSTART.md` — the settle record had even said that sentence *"lands in the guide batch"* — so the batch increment became the **second** move. What makes the rule checkable rather than a good intention is that a wave can be asked, at its close, for `git log --oneline <base>..HEAD -- QUICKSTART.md MIGRATING.md crates/cli/src/setup.rs` and read the guide-hash-moving commits off it. The practical consequence for a fix whose surface is a guide sentence: **defer the sentence to the batch**, and note it there — never edit the guide in passing.

**Every door asks, each in its own register.** `jigc setup` is the **writing** door — it replaces or refuses. `jigc upgrade` is the **reading** door: it is a read verb that writes nothing, so it reports the same advisory with the same route and replaces nothing, and its clean line names the artifact it read (a sweep that widened in silence would understate its own scope). **`jigc uninstall` is the closing door** — jigc wrote the file, so jigc takes it back out, and it is an ordinary member of the teardown's enumerated set ([project-setup.md](project-setup.md) → Teardown / cleanup (G5)). It asks the *same* ownership question: jigc's own copy is removed (with the directories jigc created for it, once they empty — never the user's own `.claude/`, which houses their settings), a user-modified one is left standing and reported with a route to this door's own exits. `--force`, the teardown's already-shipped operator-consent hatch, removes it either way — the deletion is asked for rather than assumed.

**Declared deviation from principle #5**, recorded rather than glossed: *every customization is a recorded delta against a known base version, never an untracked fork* — and refuse-to-clobber is an untracked-fork **detector with no delta**. It detects the fork and routes; it does not record, re-apply, or reconcile one. That is deliberate for a single artifact, where the whole file is the unit and "keep yours" is a complete answer. The delta discipline is **owed when a second adapter-owned artifact appears** — the trigger, filed in [decisions-pending.md](../implementation/decisions-pending.md) → *No firm trigger yet*.

### `jigc setup` has assistant-*neutral* install responsibilities too

The adapter profile is the *assistant-specific* half of setup; setup also performs installs that are **not tied to any assistant** — the project-layer init above is one, and the **M19 doc↔code backstop** is another. These are not adapter-profile content (a Cursor or Codex project wants them identically), so they live in `setup`'s neutral install path, **distinct from the per-assistant profile**.

- **The doc↔code backstop (M19) — an assistant-neutral git `pre-commit` hook.** `jigc setup` installs a `pre-commit` hook (into the hooks dir git resolves — usually `.git/hooks/`, see the install discipline below) that runs `jigc validate` (the store-wide doc↔code sweep, [validation.md](validation.md) → Store-scope re-validation) so committed-doc drift is surfaced **automatically, without the agent remembering to run it** — the M18 finding was that the on-demand detector never fired, so the over-time advantage went untested. It is **warn-only**: the hook always exits `0`, surfacing stale-anchor findings to the committer but **never rejecting the commit** (a *blocking* store-sweep would reject commits for unrelated pre-existing drift — the masking-trap M18 avoided — and would self-gate `jigc finalize`, which commits without `--no-verify`; see [finalize.md](finalize.md) → 6. Commit). Because the hook fires inside `finalize`'s own commit, its warning reaches the agent through finalize's **success-relay** of hook output ([finalize.md](finalize.md)). **The hook's output discipline is the load-bearing contract (M19 review B2)** — it is what separates a useful backstop from a per-commit annoyance, so it is spec, not prose. The hook **keys on content findings, not on the exit code** (the exit code is wrong-way-round — `jigc validate` exits 0 on *found drift* but non-zero on not-a-project / probe-missing / probe-integrity, [validation.md](validation.md) → Auto-firing the sweep). Concretely: the hook runs `jigc validate --format json` and surfaces a human-readable warning to the committer **only when the report names `doc-code` in its top-level `blocking_probes` array** — since M47 the keyed surface, so an *advisory-only* `doc-code` finding no longer warns ([validation.md](validation.md) → Auto-firing the sweep; [command-output-contract.md](command-output-contract.md) → The store sweep's envelope); on (i) a clean store, (ii) a store whose only `doc-code` finding is advisory, (iii) not-a-jigc-project, (iv) the `doc-code` probe missing, (v) any `pack-probe-integrity` meta-finding, it **prints nothing and exits 0**. *(Case (iv) is the one silent pass that hid a real fault — the M54 baseline drove a probe-less install committing through the hook with nothing said — and M54 removed it by construction rather than by a hook change (landed 2026-09-29, Increment 2): the probe runs inside `jigc`, so a `jigc` that runs at all has its probe ([module-layout.md](../implementation/module-layout.md) → Probe boundary). Case (iv) survives only on the override path, a `JIGC_DOC_CODE_PROBE` naming no file. A self-exec child that cannot start, or a build-id skew between `jigc` and its probe child, is case (v), loud at every other door.)* So a clean commit is never noised, an unconfigured or probe-less repo never breaks a commit, and the warning fires only on real drift.

Install discipline mirrors the profile injectors: **idempotent** (a sentinel-marked block, re-runnable, and **regenerated on every `setup`** like the managed `.jigc/AGENT.md`), **non-destructive** (preserves/wraps any existing `pre-commit` hook), and it must resolve the real hooks dir (honoring `core.hooksPath` and the git-worktree `.git`-is-a-file case) — **and the success summary names the dir that resolution returned**, never a `.git/hooks` literal (M47/D4: under `core.hooksPath`, and from a linked worktree whose hooks live in the main checkout's common dir, the literal names a file that does not exist; the summary renders it repo-root-relative when the hook lives inside the repo and absolute when it does not — ~~so the printed path is followable from where `setup` was run~~ **[amended 2026-09-23 (the cwd fixes' review, LOW 5):** the root is **jigc_home**, not the cwd, so from a linked worktree the common hooks dir is *inside* the root and prints `.git/hooks/pre-commit` where it used to print an absolute. Falsifying datum: the same hook, the same file, two spellings across the two bindings. What makes the relative spelling followable for a reader standing elsewhere is the ack's own site line, which names the root — law 1's rule unchanged, applied to the root the install actually used**]**). The **PATH-vs-absolute-`jigc`** choice is a real hazard (a hook calling bare `jigc` runs whatever is on PATH at commit time — possibly a stale binary); the silent-exit-0 guard above also covers a hook whose `jigc` has since been removed (it no-ops cleanly rather than breaking every commit). Being a git hook (a VCS-event install), it is assistant-neutral by nature — the same hook serves every assistant.

**The block is delimited by two marker comments in every hook `setup` writes (2026-10-06, the human's ruling on the rc.24 fix pass's item 19 — [DECISIONS.md](../DECISIONS.md) → *The `pre-commit` hook's block carries an end marker*).** A start sentinel and an end marker, around the same bytes whether the block is spliced into a foreign hook or stands in the hook jigc writes whole (the shebang, the block, `exit 0`). Until then only the spliced block carried the end marker, and the hook jigc wrote whole was recognised by being *this* build's body byte for byte — so a hook another build had written, or one edited inside jigc's lines, could not be told from anybody else's, a re-install spliced a second block in ahead of it, and the teardown had to leave it. Delimited, the block is found by its markers whatever is between them: a re-install replaces it and `jigc uninstall` removes exactly it ([project-setup.md](project-setup.md) → Teardown / cleanup (G5)). **A hook without the end marker is the upgrade case:** where jigc's block is in it exactly as jigc wrote it — rendered again from the hook's own `jigc='…'` line, which is the text every release through `1.0.0-rc.24` wrote — `setup` replaces that block with the delimited one and keeps every other line; where it is not (edited inside jigc's lines, or written from a text this build does not know), the file is somebody's, kept verbatim and wrapped, as before.

**The install commit's pathspec — `setup` commits its own install, and since M51 only the *bytes* it wrote (M48 / M51).** `jigc setup` lands its footprint as a dedicated `chore(jigc): install jigc workspace config` commit so the scaffolding never rides the user's first `finalize` ([project-setup.md](project-setup.md) → Idempotency & irreversibility). The pathspec is **enumerated, never a blanket `git add -A`**: the always-loaded host file (`CLAUDE.md`), the settings file (`.claude/settings.json`), the managed `.jigc/AGENT.md`, `.jigc/.gitignore`, the `.jigc/version` provenance stamp, the project layer (`.jigc/config/`), the settings record `.jigc/settings-entries.json` where the run keeps one (→ *Taken back by a record, never by resemblance*, below), **the adapter's owned guide artifact** (below), the root `.gitignore` **only** when setup itself seeded the secrets floor on a fresh repo, and the `pre-commit` hook **iff the hooks dir git resolved puts it inside the working tree** — each filtered to present-and-not-gitignored. One thing setup writes is deliberately *not* in it: the transient `.jigc/` working area (gitignored by setup's own `.jigc/.gitignore`). *(Until M54 there was a second, the machine-global `doc-code` probe `setup` extracted beside the binary; since M54 Increment 2 (2026-09-29) the probe ships inside `jigc` and `setup` writes nothing outside the repository.)* **The hook's membership is a rule, not a fixed answer**, because the hooks dir is not fixed: the usual `.git/hooks/pre-commit` is not a trackable file, but an in-repo `core.hooksPath` makes the same hook an ordinary working-tree file that must be committed like any other install file — so the pathspec is derived from where the hook *landed* (under the canonicalized repo root, outside git's own `--git-dir`/`--git-common-dir`, **and owned by this repository** — the hook's own directory must answer this root when asked `rev-parse --show-toplevel`), naming the hook **file** and never the hooks **dir**, which may hold the user's other hooks. **Location is not trackability:** a hooks dir under the root can belong to *another* repo — shared hooks vendored as a submodule, or a plain embedded repo — and naming such a path takes the *whole* install commit down in opposite ways (inside a submodule `git add` refuses fatally; inside an embedded repo it stages nothing at exit 0 and the pathspec-limited `git commit` then dies on a path git does not know), which is why the ownership question is asked of git rather than a shape enumerated. **And the filesystem is not the only place that question has an answer:** a submodule that is *registered but not checked out* — what a plain `git clone` without `--recursive` leaves, i.e. the default clone — is an empty directory with no `.git` inside, so `rev-parse --show-toplevel` from the hook's dir answers *this* root while the index still holds the `160000` gitlink and `git add` refuses just as fatally. So the ownership question is asked of **both** sides: git's answer from the hook's own directory, *and* whether the index holds a gitlink at any ancestor of the hook's path. Deriving it from the *printed* path would not work either: the summary renders `.git/hooks/pre-commit` repo-root-relative, and a `.git`-internal pathspec entry is inert (`git add` on it stages nothing and exits 0), so a relative-path rule would look green while committing nothing. **A pathspec bounds *paths*, never authorship — which is why the M48 half of this rule was true and incomplete.** *"Only its own install"* is a claim about the eight paths, and it held; what it does not settle is whose **bytes** sit at them when the commit is made. Driven at the M51 baseline: a committed `CLAUDE.md` edited and **never staged** was committed into `chore(jigc): install jigc workspace config` at **exit 0**, and `git status --short` then came back **empty**, so nothing was left to prompt recovery. So the pathspec question is joined by a **bytes** question, asked over that same enumerated pathspec (M51 Increment 3; [surface-contract.md](surface-contract.md) → The carryover gate, whose second member this door is): a path whose index *or* worktree bytes differ from `HEAD` **before the install writes anything** refuses — one blocking routed `setup.dirty-install-path` over the whole sorted set, with **`jigc setup --force`** the single consent ([validation.md](validation.md) → The M51 registrations — Increment 3). **One stated exemption, and it is per member:** on an unborn `HEAD` an *untracked* file at a path the install **merges into** rides the repository's first commit instead of refusing — the on-ramp — while a path it **replaces** refuses there too, which is why each member of the pathspec states what its writer does to bytes it finds (the same row).

**The question is asked once, before the first write, and acted on there** — which is a correction, with the datum that forced it. The rule shipped as a **conjunction**: dirty before the install *and* still dirty once it has, on the reasoning that where `setup` rewrites an artifact whole the commit carries only jigc's canonical bytes, so refusing would block an upgrade over jigc's own file. Driven at `da5173a1`, that second leg is structurally blind to exactly the class it reasons about: an adopter's uncommitted `.jigc/AGENT.md` prose is *gone* by the time the second ask runs — the unconditional rewrite is what made the path clean again — so the set came back **empty**, `setup` exited 0, `git status --short` was empty and `git log --all -S` found the bytes in no object. *"The commit carries jigc's bytes"* was true and beside the point. The **whole-rewrite carve-out is therefore withdrawn**, and the sentence that stated it is struck on two counts besides: it named **the guide**, which M48's refuse-to-clobber already preserves and drops from the pathspec, and it omitted **`.jigc/config/packs.yaml`**, whose parse-mutate-serialize round-trip drops an adopter's comment for the same structural reason.

**What survives the withdrawal is an ownership question, defaulting to refuse.** An install path is exempt only when an oracle can read the file and say *these bytes are jigc's own*: the guide's recorded body digest, and `.jigc/version`'s one-line `jigc-version:` shape (nobody authors prose into a machine stamp, and its re-stamp *is* the documented `store-version.binary-mismatch` recovery). Every other member of the pathspec — merged-into or rewritten whole — refuses. The old derivation classified a path nobody had thought about as **exempt**, which is how two of the ten swept authored bytes; this one classifies it as a **refusal**, so forgetting costs a loud false alarm `--force` clears and never a loss.

**The bytes question is asked of the files where `git status` cannot answer it (the rc.24 fix pass).** *Present-and-not-gitignored* is the right filter for the **pathspec** — git will not add an ignored path — and it was the wrong filter for the **question**, because the question is whose bytes the install is about to run over and an ignored file has bytes like any other. Driven on the release binary at `104a7d4b`: `.jigc/AGENT.md` listed in `.gitignore`, a team's notes in the file, and `jigc setup` exited 0 with no finding and the notes in no git object, on a born `HEAD` and an unborn one. A tracked path whose index entry is flagged assume-unchanged or skip-worktree is the same blindness from the other side — status reports it clean whatever the file holds. So the pathspec keeps its filter, and the question no longer shares it: every member present on disk that status did not name is asked about, and **the asking is git's** — which of them git tracks and which index entries carry a flag is read from `git ls-files -v`, an unflagged tracked path is `git status`'s to call clean, and a flagged one is put to git's own status again with the flag out of the way. A tracked file git then calls modified is dirty at **every** member, as if status had said so. (It first compared blob ids by hand, which refused a clean `CLAUDE.md` whose blob held CRLF under `core.autocrlf=input`; [validation.md](validation.md) → the `setup.dirty-install-path` row carries the datum.) An ignored file is a subject **only at a member whose writer replaces** — one the install merges into keeps its bytes and joins no commit, so nothing about it changes — and there the ownership question above is asked of **every** replacing member rather than of two, because no commit can ever make an ignored path clean and *refuse while dirty* would refuse every re-run over jigc's own output. Each replacing member therefore declares how its own bytes are recognised, where it declares its writer: the stamp's shape, the empty project-layer marker and the guide's digest read something no build changes; the bootstrap file and `packs.yaml` are recognised by *this run's write would leave the file byte-identical*, which an older build's copy satisfies only while the generated content has not moved. For the upgrade that moves it, the provenance is kept where M51 already keeps it for an uncommitted install — the install footprint record gains the hash of every ignored file a run replaced, and the pre-write ask subtracts a path whose bytes still hash to it — so a repository that ignores a jigc install path and never edited the file re-runs `setup` at exit 0 across upgrades, and an edit re-arms the refusal for exactly that path. `--force` names an ignored path it replaced like any other ([validation.md](validation.md) → the `setup.dirty-install-path` row carries the route arms and the one stated bound).

**And where git cannot answer at all, nothing is installed (the rc.24 fix pass's completion audit).** The pre-write ask had a third outcome — git did not answer — under which the install ran and only its commit was skipped. With a corrupt index, a submodule whose gitdir is gone, no `git` on `PATH`, an ownership refusal or an unreadable `HEAD`, that regenerated `.jigc/AGENT.md` over an uncommitted edit, at exit 0 in the first two. The door now refuses there before its first write, quoting git and naming the install paths that exist; `--force` does not pass it, because the consent is spent on paths git named. **Its code is its own, `setup.unverified-install-path` (2026-10-06, the human's ruling on the fix pass's item 17):** it was built under `setup.dirty-install-path`, whose usual remedy is exactly the `--force` this refusal does not honour, so one code named two states with two different next acts ([validation.md](validation.md) → the `setup.unverified-install-path` row). What it does **not** refuse is a home git says is no work tree — the three layouts where the resolved home is the parent of a git directory rather than a checkout (a bare repository's worktree, `--separate-git-dir`, a submodule): git is asked `rev-parse --is-inside-work-tree` before the dirty question so the two kinds of `git status` failure are never confused, and there the install runs with its commit skipped, as it always has ([validation.md](validation.md) → the `setup.dirty-install-path` row).

**And because the ask is pre-write, the refusal installs nothing** — which is what makes its own sentence (*every path listed above still has its pre-run bytes there*) true at a path the install rewrites whole. The same predicate is asked again over the settled pathspec immediately before the commit, as the **backstop** for the one member the pre-write enumeration cannot name (the hook, whose home the install itself resolves and whose writer preserves a foreign hook verbatim); where *that* ask fires the install is written and staged, and it holds back exactly the paths it names, because `git add` on an index-only difference would replace the adopter's staged blob with the worktree's bytes and re-enact the loss one step earlier. **`--force` is consent, not preservation:** it lets the install run, so at a whole-rewrite path the adopter's bytes are replaced on the way to the commit — which the install then **says**, as an advisory `setup.forced-install-path` naming every path the consent was spent on, rather than letting a silent exit 0 stand over bytes that are gone.

**A file the install replaces is written as a regular file at exactly its path, never through a link (the rc.24 fix pass).** The ownership question above is asked of a path that differs from `HEAD`, and a **committed** symlink does not: driven on `1.0.0-rc.24`, a link at `.jigc/AGENT.md`, `.jigc/version`, `.jigc/config/.gitkeep` or `.jigc/config/packs.yaml` whose target no git object held — untracked, gitignored, or outside the repository — had that target regenerated at exit 0 with no finding, `--force` did the same and named nothing, and the dirty-install route's own *commit them* arm turned an uncommitted link into that cell, because committing a link commits the link. So before the first write, and before the dirty question, every member whose writer **replaces** is asked what its entry is **without following a link** — and so is every directory on the way to it below the checkout root, since a linked `.jigc` or `.jigc/config` carries a write into another directory exactly as a link at the leaf does (driven: the target was regenerated and the run then failed at its own `git add`, *beyond a symbolic link*). Anything but a regular file or an absent one **refuses under the member's existing write-failure code** — `setup.write-bootstrap`, `setup.version-stamp`, `setup.init-project-layer`, `setup.compose-marker`, and `setup.write-guide` for a link on the way to the guide — as one finding that names every blocked path, with nothing written. It is the rule the same door already applied to `.jigc/.gitignore` (a symlinked ignore file has refused since M51), now stated once for the class: each replacing member declares the code its refusal rides where the member is enumerated, so a new one cannot be declared without it. **`--force` does not override it** — the consent is to replace a file, not to follow one — and the route is to remove the entry, committing the removal where git tracks it. **The commit is no longer what makes the re-run land (2026-10-06, the human's ruling on the fix pass's item 1 — [DECISIONS.md](../DECISIONS.md) → *`jigc setup` completes after a tracked install file was deleted*).** Left uncommitted, the deleted path is a difference from `HEAD`; the pre-write gate asks only about paths that exist, so the install was written, and the backstop before the commit then refused over the file the install had just put there — on every run wherever the restored bytes differ from `HEAD`'s, which a regular file in a committed link's place always does. A path that was **absent from the working tree before the run, with nothing in the index that `HEAD` does not hold**, is not the adopter's uncommitted work: the install restores it and commits it, at every member — the hook under an in-repo `core.hooksPath` included — whether the deletion was staged or not, and a run that fails after writing it records it as its own. What still refuses is the path absent from the working tree whose **index** entry holds bytes of the adopter's (staged, then deleted): the install commit would replace that entry, so the backstop names it and leaves the staged blob as it was. A **link at the guide's own path** is answered earlier by the guide's oracle: it is an entry jigc did not write, so it is left alone and reported under `adapter-guide.user-modified` like an edited copy. The members whose writer **merges into** what it finds are asked a different question, because a merge through a link changes its target by exactly what it would have changed in a regular file, and a `CLAUDE.md` that links to `AGENTS.md` is an ordinary thing for a repository to have: **a link there is followed — to a regular file inside the checkout, and nowhere else (the rc.24 fix pass's completion audit; *that git does not ignore* stood here until 2026-10-06 and is struck by the human's ruling on the fix pass's item 18, below).** This paragraph first said those members *are not asked*, and that was the defect: driven on `1.0.0-rc.24`, a committed `CLAUDE.md` or `.claude/settings.json` link to a file **outside the repository** had that file rewritten at exit 0 with `git status` empty and an ack naming an install no commit carried; a **dangling** one created the file wherever it pointed; and a link to a **tracked file in the repository** merged there and left that file modified and uncommitted beside an install commit that did not name it. So, before the first write: where the link leads to a file the repository can commit, **that file becomes an install member** — asked about by the dirty gate like any other (an untracked or edited one refuses by name on a born `HEAD`; on an unborn one it rides the first commit with the link), named in the install commit, and named in a `note:` on stderr that says which file was merged into, since the summary's `line_file` stays the path the assistant reads. **Where the link leads to a file inside the checkout that git ignores, the link is followed and that file is treated as an ignored ordinary file at the member's own path is (2026-10-06 — [DECISIONS.md](../DECISIONS.md) → *`jigc setup` follows a `CLAUDE.md` or settings link to an ignored file*):** jigc's section is merged in, the file joins no commit and no index entry, the dirty gate does not ask about it, and the `note:` says *git ignores that file, so no commit carries it*. The fix pass refused this end, on the reasoning that a link is followed only to a file a commit can carry; `1.0.0-rc.24` followed it and merged, an ignored ordinary `CLAUDE.md` has always been merged into at exit 0, and a merge loses nothing either way — so the refusal was new and protected nothing. The file reaches that treatment by the road an ordinary one takes: it is a member of the install's path class, and the two filters that drop an ignored path the install merges into — the dirty gate's candidates and the install commit's pathspec — drop it. **The link itself is still asked about like any install path**: committed, it is clean; untracked on a born `HEAD` it refuses by name under `setup.dirty-install-path`, as an untracked ordinary `CLAUDE.md` does; on an unborn one it rides the first commit and the ignored file behind it does not. Every other end — out of the repository, nowhere, a directory, inside git's own directory (which `git check-ignore` does not call ignored and which is no working file of the repository) — refuses under the member's own write-failure code (`setup.inject-reference` · `setup.inject-allowlist` · `setup.secrets-gitignore`), `--force` or not, with the route *remove the link, or point it at a regular file inside this repository*. `.jigc/.gitignore` is the one merged-into member a link is never followed at — its writer amends in place and refused a symlink already, but after the bootstrap file had been written; it refuses here instead (`setup.init-project-layer`), with nothing written. The `pre-commit` hook is asked the same way where it is itself a link: followed to a script in the repository or in its own hooks directory, refused (`setup.install-hook`) where it leads anywhere else or nowhere. **Not this rule's subject:** a directory or special file at a merged-into path, which the writer fails on loudly as before, and a `core.hooksPath` that itself points outside the repository — a hooks directory the adopter configured, not a link the install followed. The writers keep the rule themselves as well — each opens its destination with `O_NOFOLLOW` and asks the open handle what it is — so a link that appears after the question was asked fails the write instead of redirecting it.

**And because no test can promise git will accept a path, the hook is a *soft* member of the pathspec.** Seven of the eight entries are files setup wrote at paths setup chose; the eighth sits wherever the user's `core.hooksPath` put it — and a sparse-checkout that excludes that dir refuses the hook while every location and ownership test above says "committable". So a `git add` refusal **the hook entry is responsible for** costs the hook's membership and nothing else: the hook is dropped from the pathspec and git is asked again, which falls back to the already-declared bound (the hook is installed and reported, and left as the containing repo's file) instead of an install that cannot be completed at all. Attribution is **behavioural, never a match on git's message** — if the retry succeeds the hook was the cause, and if it refuses again it was not. A refusal that survives the retry, and every refusal on a pathspec that never carried the hook, is **loud on both halves** — a rejected `git add` is as fatal to the install commit as a rejected `git commit`, so it surfaces the same blocking `setup.install-commit` finding, routed on git's own cause rather than the git identity it was first written for.

**Declared bound — "a clone gets the backstop" is conditional, on two independent axes.** (i) **The hook is not always committable at all — and on the default hooks dir it never is.** `.git/hooks/pre-commit` is *under* the repo root and inside git's own control dir, so git cannot track it; a `core.hooksPath` pointing outside the repo, and the **common** hooks dir a linked worktree resolves to, are outside the tree git commits from entirely. On all of them the backstop is a purely local install and a clone gets none of it — which, because the default shape is the one almost every adopter is on, the **install summary says at the door**: the hook line gains a clause naming the consequence (in no commit; a clone has no backstop until `jigc setup` runs there), and the `--format json` install envelope carries the same fact — the key and its declaration live with the rest of that envelope's keys in [command-output-contract.md](command-output-contract.md) → *Every other envelope*, which is the doc that pins the wire (M51: it was declared here, in an adapter bound, and a wire key declared in a doc that pins no wire is a key a driver has no path to; the bound is this paragraph's and stays here, the key's declaration moved). The clause is keyed on the pathspec the install commit was made from, so the sentence and the commit cannot disagree (M48; the first sweep fixed the pathspec on every shape and left the surface silent on the dominant one). (ii) **Even committed, it is machine-specific.** The body embeds the **installing machine's absolute `jigc` path** (the PATH-vs-absolute hazard above), and its own guard makes a missing binary a silent exit 0 — so on another clone the tracked hook no-ops until that developer's own `jigc setup` rewrites it to their path (which setup then commits). Both halves are stated rather than engineered around: a PATH-relative hook would trade this bound for the stale-binary hazard, and the silent no-op is the correct failure for a warn-only backstop.

**It is an install artifact, not a managed document (M19 review N2).** The `pre-commit` script is a peer of `.claude/settings.json` and `.jigc/AGENT.md` — written by `jigc setup` (the deterministic CLI, no LLM), living wherever git's hooks dir resolves (usually git's control dir, but an in-repo `core.hooksPath` puts it in the working tree — see the install commit's pathspec above), **outside** the managed-doc store, the `file-state` hash set, and the reconciliation/edge-index machinery. It is never reconciled or treated as a doc; it is regenerated by `setup`. (No determinism-boundary or "LLM-writes-only-through-the-CLI" tension: `setup` is the CLI writing an install artifact, exactly as it writes the adapter host files today.) ([roadmap.md](../implementation/roadmap.md) → M19.)

There are **no per-command wrappers**. The agent shell-calls `jigc` and learns each command just-in-time from composed output (command-refs); a wrapper-per-command would be a static, partial surface that undercuts the "one entrypoint" promise. What the adapter *does* generate is a small, **catalog-derived** set of **human-facing workflow launchers** (e.g. a Claude Code slash-command per workflow), each just calling `jigc start --workflow <X>` — the *human's* path to kick off a specific workflow directly. That stays consistent with the rule: it's bounded and **regenerated from the workflow catalog** (not a hand-maintained pile), and it's not the agent's path (the agent still shell-calls the front door).

## The three responsibilities

### 1. Inject the bootstrap — hook (primary) + line (floor)

The bootstrap reaches the agent by the assistant's *best available* mechanism, declared in the profile:

- **A hook that calls the CLI** — injects the bootstrap plus a *thin live nudge* at session start (e.g. Claude Code's `SessionStart` running the front door). Fresher and higher-salience than a buried rules line, and it makes the bootstrap's "advertise *and* demonstrate" automatic: the agent's first context already shows live orientation. **Primary** where supported.
- **A static reference** in the always-loaded file (`CLAUDE.md` / `AGENT.md` / Cursor rules) — the **universal floor**: works where there's no hook system, and cheap insurance if the hook fails. The reference is *not the sentence inlined* — it is a stable one-line pointer (Claude Code: an `@.jigc/AGENT.md` import) to a **managed bootstrap file** the adapter writes under `.jigc/` and **regenerates on every `setup`**. This keeps the always-loaded file clean (a single pointer line, no marker-fenced block of content) and keeps the bootstrap text CLI-owned and rot-proof — the *structure is generated, not hand-maintained* discipline applied to the floor itself. The always-loaded file is touched only to ensure the pointer is present (idempotent on the exact reference line); the content lives in the managed file. (An assistant with no import mechanism falls back to inlining the sentence; the profile declares which.)
- **A resume / post-compaction hook** (capability-dependent) — *if* the assistant exposes a "context resumed" or "compaction completed" event, the adapter re-injects the bootstrap on that event so a mid-task compaction doesn't lose the routing pointer. The profile's `resume` event slot declares whether the assistant supports it; Claude Code ships this when the API exposes such an event. The universal compaction baseline (independent of any hook capability) is the routing footer the CLI appends to every agent-facing output ([workflow-dialect.md](workflow-dialect.md#emitted-format) → Routing footer; [bootstrap.md](bootstrap.md) → Context compaction resilience).

**Discipline:** the hook obeys the same *routing, not content* rule — it injects the bootstrap + at most a one-line current-state nudge, **never a content dump**. Its value is freshness and salience, not volume; the agent still *pulls* real context JIT via `jigc`. (Capability-dependent: the profile declares which mechanisms the assistant supports; the line is the floor.)

**The managed bootstrap body** (`.jigc/AGENT.md`) is five paragraphs, all stable: the canonical routing sentence ([bootstrap.md](bootstrap.md) → The sentence, verbatim); the **read rule** (managed = exactly the `jigc doc list` set — **the committed set** — read via `jigc doc show`; everything else — source, tests, any file not in that set — is read freely: the crisp discriminator the never-read-directly prohibition depends on, naming only stable verbs so it cannot rot; added 2026-07-17 from the RC lacon trial, B17 — and extended the same day by the surface-comprehension review, B4, with the two edges the flat rule did not compose with: a doc **staged in the open task** is not yet in the committed set, so its sanctioned read is `jigc doc show <doc> --task <id>`, never the file; an **`unregistered`** row is not yet managed — directly readable until adopted; and amended 2026-07-21, M44 Inc 4 change 2, from the rc.7 discoverability rerun with the **binary-derived-behavior** clause: project source stays freely readable, but how `jigc` *itself* behaves is learned from the installed binary — `jigc --help`, `jigc describe`, `jigc doc schema` — never a checked-out jigc or pack source tree, which need not match the binary in use; this closes the stale-source reach the flat "read source freely" clause otherwise licensed, scoping the freedom to *project* source without contradicting it); a one-line **context-compiler framing** (what `jigc` *is* and the division of labor — the mental model behind the never-read-directly rule; added 2026-07-06 from the RC greenfield trial, and its doc-slices promise scoped **per-tier** 2026-07-17, B2: a workflow pulls the slices *it declares*, and a quick fix legitimately declares none — the unscoped "slices your task needs" read as broken on the zero-slice tier); the **output contract** (stop on a non-zero exit, follow the output, never retry blindly — M36, narrowed 2026-07-06: the per-exit-code *meanings enumeration* is retired because each outcome's meaning rides in the command's own output — **every finding carries a route** (the advisory-route floor, [validation.md](validation.md) → The advisory-route floor; The stance is now scoped to the real predicate (`render.rs` → `validation_store_exit_flips`), stated as **the class, not a list** — a handful of conditions flip it, and enumerating them in a preloaded paragraph is content that rots, exactly like the retired meanings table — a claim this parenthetical then falsified inside the very sentence making it, by listing members of a table that had already outgrown the list (`render::STORE_EXIT_FLIPS`; retired M49 Increment 8 / T6, under the settled *point at the table, do not re-count* rule — [validation.md](validation.md) → Exit semantics). **The class is the flip itself, not a cause** (the M47 completion-audit correction): the clause first shipped as *unless the sweep itself could not be trusted*, which each member's own `sweep_untrustworthy` verdict decides, and which is **false** of the out-of-band rename — that sweep worked and is reporting a real structural-identity change it found (its own trailer says so) — so the stated class excluded a real member, the same law-1 lie one tier down. The clause now claims only what holds over the whole axis: *a few conditions flip that exit*, and then the sweep **exits non-zero and its closing line names the condition and why**. ### 2. Make `jigc` frictionless

Allowlist `jigc` in the assistant's permission/settings so the agent runs it without friction. This is the **path-of-least-resistance** the bootstrap *depends on* — if `jigc` prompts every time, the agent routes around it and the whole bet fails. Generating this makes it a guaranteed setup step, not something a human must remember.

*Honest boundary: this is enforcement by **ergonomics**, not by sandbox.* A non-compliant agent that decides to ignore the adapter and edit files directly bypasses us — there is no kernel-level block, and the architecture explicitly does not promise one ([VISION.md](../VISION.md) principle #3). The bet: frictionless `jigc` access + bootstrap *advertise+demonstrate* + "the CLI is the only path that knows the wiring" make compliance the cheaper path. Out-of-band edits, when they happen, are detected and reconciled via the engine-native `file-state` probe ([write-commands.md](write-commands.md) → Out-of-band reconciliation), not prevented.

**The `deny` safety floor — a bounded blocklist, not workflow enforcement (M36).** Alongside the `permit` allowlist, the profile carries a small, **enumerable `deny` list** that the same install path merges into the settings file's `permissions.deny`. It is a **safety floor against catastrophic/exfil actions**, deliberately *orthogonal* to the managed-doc boundary: it does **not** police whether the agent writes docs through `jigc` (that stays the ergonomics bet above, never a hard block), and it is **not** the deferred `PreToolUse` managed-write enforcement hook ([Open questions](#open-questions); [VISION.md](../VISION.md) principle #3) — conflating the two would install a sandbox where the architecture promises none. The floor is fixed and small enough to state as the design:

- **Destructive / exfil shell** — `Bash(rm -rf:*)`, `Bash(curl:*)`, `Bash(wget:*)`, `Bash(git push --force:*)`.
- **Secret-file reads — each pattern denied on *both* surfaces.** A `Read`-tool deny (`Read(./.env)`, `Read(./.env.*)`, `Read(./**/*.pem)`, `Read(./**/id_rsa*)`, `Read(./**/*.key)`, the common credential files) blocks the `Read` tool — **but a `Read`-rule deny does not stop `cat .env`**: a shell read reaches the same bytes through Bash, which `Read` rules never see. So each secret pattern also carries a **Bash-command twin** scoped to that path (`Bash(cat ./.env:*)`, `Bash(cat ./.env.*:*)`, …) — the reason the list carries paired entries, not one per file. The twin is a **floor, not a seal** — `less`/`grep`/a Python `open()` still read the file — and that honest gap *is* the *ergonomics-not-sandbox* posture: the floor stops the obvious footgun, not a determined agent. (The secret **set** is the same one the fresh-repo `.gitignore` floor seeds — [project-setup.md](project-setup.md) → the secrets-floor `.gitignore` — one list, two enforcement points.)
- **jigc's own human-owned destroying doors (M50)** — `Bash(jigc uninstall:*)` and `Bash(jigc milestone discard:*)`. These are neither destructive *shell* nor a secret read, which is why they are their own bullet rather than an addition to either: they are `jigc` verbs, permitted by the `Bash(jigc:*)` prefix permit like every other verb, that delete bytes existing in **no object DB** — a task's staged prose, a worktree's uncommitted work. Each already refuses that state and names `--force` as the exit ([project-setup.md](project-setup.md) → Teardown; [team-ready-state.md](team-ready-state.md) → Abandon refuses on a dirty worktree), but `--force` is an *operator's* consent, and an agent holding a blanket `jigc` permit can spend it without one. Denying blocks — the profile has no prompt to express — and the deny merge is append-if-absent, so this reaches **already-installed** repos on their next `setup`; narrowing the `permit` instead would have reached none of them, the permit being a prefix pattern injected purely additively and never pruned. `jigc milestone provision` is deliberately **not** on the floor: its destruction sits behind the same `--force` under M48's fail-closed leftover classifier, and blocking the verb an unattended fan-out runs would park that fan-out on a decision nobody is watching.

**Merged, never clobbered — mirror `inject_allowlist`.** Adding the floor to a `.claude/settings.json` that *already* carries a user `deny` array is the **same structure-aware merge** as the `permit` path ([Generated, minimal, regenerated](#generated-minimal-regenerated) idempotency; [project-setup.md](project-setup.md) → Idempotency & irreversibility): navigate/create `permissions.deny`, ensure each floor pattern is present (append-if-absent), preserve every user entry and unrelated key, write back — a re-run is a byte-stable no-op. It never replaces a user `deny`.

**Taken back by a record, never by resemblance (2026-10-06, the human's ruling on the rc.24 fix pass's item 21 — [DECISIONS.md](../DECISIONS.md) → *`jigc setup` records the settings entries it adds*).** The three merges into the settings file — the permits, this floor, the `SessionStart` hook command — each add an entry only where none stands, so afterwards an entry the adopter already had and one jigc added are the same entry. `jigc uninstall` used to remove every entry *equal* to one jigc installs: driven on `1.0.0-rc.24`, an adopter's own `Bash(rm -rf:*)` deny rule, their `Bash(git add:*)` permit and their own `jigc start` hook were gone at exit 0 — from a file no git object held, where the settings file is ignored. Which entries a run added is known only to that run, so `setup` writes it down, in **one small committed file, `.jigc/settings-entries.json`**, a member of the install commit: a JSON object carrying `format` (a number a later build can branch on; this one writes and reads `1`), `file` (the settings file it describes) and `added` (`allow`, `deny`, `hooks`, each hook an `event` and a `command`). Four rules hold it:

- **It is consulted only where git tracks the settings file — and the record with it.** The record and the file it describes then travel together, clone by clone. Trusted wherever it is found, it would be read against a settings file that is private to each clone and say of one clone's own entries that jigc added them. *Tracked* is asked of the file the settings path leads to: behind a committed link to an ignored file, the entries are in a file git does not track.
- **Where it is not consulted, `uninstall` removes none of the three kinds and names what it left** — a settings file git ignores or does not track, and an install with no record. Every entry identical to one jigc installs is printed, by the key it sits under, so it can be removed by hand. `--force` is the operator's consent, as at this door's other guards, and removes every such entry, the adopter's included.
- **It never claims an entry no run of `setup` added.** A run records the entries it is about to add, plus the earlier record's entries that are still in the file. So over an install that predates the record a later `setup` adds nothing and records nothing: that install's entries stay unclaimed, and are left and named by the teardown. Reading them back out of git history, or assuming that what equals jigc's is jigc's, is the inference the record replaces.
- **It is absent where there is nothing to record.** `setup` writes it only where its install commit can carry the settings file, and removes a record that stands where it cannot — the install commit carrying the removal, the run saying so — so that no stale claim waits to be read against a later file. One occurrence of a recorded entry is removed, not every one: jigc added one, and a twin written beside it afterwards is the adopter's.

As an install member it is a file `setup` replaces whole, refused like the others when an uncommitted edit or a link stands at its path (→ *The install commit's pathspec*, above); its write failure rides the settings merge's own `setup.inject-allowlist`, and no finding code was minted for it. **Outside the record, with their reasons:** the `CLAUDE.md` section and the `pre-commit` block are also removed from files jigc merges into, and each is recognised by content that names jigc itself — the import of jigc's own bootstrap file, jigc's two marker comments — and stops working once the install is gone.

**No self-collision — and the reach that claim never had (corrected M50).** The floor's `git push --force` / `rm -rf` denies target the *agent's* Bash tool; `jigc` itself shells `git add`/`git commit`/`mv` as a **binary it invokes directly** (never routed through the agent's denied Bash surface — [CLAUDE.md](../CLAUDE.md) "CLI orchestrates, git executes"), so `finalize`'s own commit is unaffected. But the closing sentence this paragraph carried — *"the floor constrains the agent, not the CLI"* — was a claim about **who the floor reaches**, and it was drawn from a survey of jigc's own `git` shell-outs alone. It never contemplated the third case: the agent asking jigc to perform the deletion, where the destroying bytes are the *agent's* request and the *CLI's* hands. That case is exactly the two verbs above, so the honest statement is narrower and is the one that holds: the floor never blocks jigc's **internal** shell-outs, because those are not the agent's Bash tool — and where jigc's own **surface** is the destroying door, the floor does reach it, deliberately.

### 3. Bind the spawn mechanism

The profile carries a **launch template**. The CLI renders its fan-out dispatch (`task_id` + entrypoint) *through* the template into the assistant's launch primitive — for Claude Code, a Task-tool invocation running `jigc workflow W --task <sub>`. The locked seam holds: **CLI owns the payload; the adapter owns the launch** — and the template is the *only* assistant-specific bit.

**Launch templates are typed-schema validated at install.** The template is the actual surface that decides whether the sub-agent ever sees the CLI's payload, so an unvalidated template is a determinism-boundary leak: a stale profile could omit the `{{task_id}}` placeholder, paraphrase inline instructions, or fail to invoke `jigc workflow` — and the sub-agent's writes would never reach the working area the join expects. The profile's launch template carries a schema declaring:

- **required placeholders** the CLI fills — the template must contain both `{{task_id}}` and `{{workflow}}` literally (a missing one is a hard install error);
- **the required invocation pattern** — the template must contain a `jigc workflow … --task …` invocation (the rendered command, however the assistant primitive surfaces it, must shell out to the CLI; no inline-paraphrased instructions to the sub-agent);
- **forbidden patterns — a *decidable* rule, not a heuristic** (M8): the check operates on the **whole rendered template** and asserts it contains **at most one newline total**, **exactly one backticked span** (the `jigc workflow … --task …` invocation), and **no** slot-author marker (`<<author:`), ATX heading (`#`/`##` at line-start), or `Run:`/`Spawn:`/`> ` directive marker anywhere — any of which signals re-authored workflow-body prose rather than a launch line. Free prose around the backticked invocation is fine. The rule is purely lexical (decidable at install with no judgement) and rejects the determinism-boundary leak — an inline paraphrase of the sub-agent's instructions — without a vague "looks like prose" test.
- **the backticked span's shape — a structural rule** (M31, the WF4 worktree binding): the span itself must be **either** the bare `jigc workflow … --task …` invocation **or** that invocation prefixed by a single `cd <worktree> &&` — exactly one whitespace-delimited token after `cd` (it is the CLI-filled `{{worktree}}` placeholder, validated *structurally*, never matched against a value, so the determinism rationale holds), and **no other shell** (a non-`cd` prefix like `rm -rf x &&`, a multi-token `cd` argument, or any trailing `&&`-chaining is rejected). This directs each fanned sub-agent into its own detached worktree (`design/storage.md` → the third combine-mode) without reopening the door to arbitrary shell. The shipped Claude Code template is one line: `` Use your Task tool to run: `cd {{worktree}} && jigc workflow {{workflow}} --task {{task_id}}` `` — the CLI fills `{{worktree}}` with the deterministic `.jigc/worktrees/<task_id>` path (the same `worktree_path` convention the fan-out `Spawn:` emit uses).

Validation runs at `jigc setup` / `jigc adapter install` / `jigc adapter regenerate`. **A broken template is an install-time error** with a precise pointer to the schema violation; the install does not complete. The intended *runtime* complement — the join's **never-started detection** ([workflow-dialect.md](workflow-dialect.md) → `fan-out` / `join`), which would catch a template that *passes* schema but still fails to reach the CLI at runtime — is **deferred past M8** ([DECISIONS.md](../DECISIONS.md) 2026-06-04). So in M8 the install-time schema check stands alone: it catches the broken template before any sub-agent runs, but a schema-valid template that misfires at runtime is an accepted, unsurfaced gap (a never-started sub-area contributes nothing to the join rather than surfacing as a routed outcome).

## The adapter profile

A small YAML spec of "how to wire into assistant X" (illustrative):

```yaml
# adapters/claude-code.yaml
assistant: claude-code
inject:
  - reference: { file: CLAUDE.md, to: .jigc/AGENT.md, syntax: at-import }  # floor: a managed bootstrap file + an `@`-import pointer (no inlined block)
  - hook: { event: SessionStart, run: "jigc start" }          # primary; calls the CLI — bare `jigc start` is read-only orientation
  - hook: { event: Resume, run: "jigc start", when: supports(resume) }  # post-compaction re-injection (ships when the assistant API exposes the event)
allowlist:
  file: .claude/settings.json
  permit: ["Bash(jigc:*)"]          # allow rules must name the tool scope (`Bash(…)`) — a bare `jigc *` glob is rejected by the harness
  deny:                               # safety floor — merged into permissions.deny, never clobbered (see § Make jigc frictionless)
    - "Bash(rm -rf:*)"
    - "Bash(curl:*)"
    - "Bash(wget:*)"
    - "Bash(git push --force:*)"
    - "Read(./.env)"                  # each secret pattern pairs a Read deny with a Bash twin (Bash(cat ./.env:*), …)
    # …secret-file set + its Bash twins — full list in the prose above
    - "Bash(jigc uninstall:*)"        # the two human-owned destroying doors (M50) — `--force` is the operator's consent
    - "Bash(jigc milestone discard:*)"
spawn:
  template: "Use your Task tool to run: `cd {{worktree}} && jigc workflow {{workflow}} --task {{task_id}}`"
guide:                                  # optional — the adapter's owned artifact (M48)
  file: .claude/skills/jigc/SKILL.md    # assistant-specific path; jigc writes and commits it
  front-matter:                         # the assistant's own header keys, emitted verbatim
    name: jigc                          # above jigc's `jigc-version:` + `jigc-body-blake3:`
    description: How to work in a jigc-managed repository — …   # stamp lines, which no profile may declare
co-author:                              # optional — the agent's commit trailer (2026-10-03)
  name: Claude                          # renders `Co-Authored-By: Claude <noreply@anthropic.com>`
  email: noreply@anthropic.com          # the co-author's identity, for de-duplication
  when-env: CLAUDECODE                  # set, non-empty, in the agent's processes — and only there
```

Profiles for known assistants **ship with the CLI** (Claude Code first); additional profiles are **installable** later — a swappable layer parallel to packs.

### The co-author trailer (2026-10-03)

A profile may declare the **co-author** its agent signs commits with, and every commit jigc makes **while running under that agent** carries exactly one `Co-Authored-By: <name> <<email>>` git trailer — every member of the committing-door axis (`cli::invocation_log::COMMITTING_DOORS`: both `jigc task finalize` arms and the path-scoped doc-only commit, both `milestone finalize` arms including each per-sub-task commit, `rename`, `migrate-corpus`, the four record-only milestone doors and the sub-task `task discard`) and `jigc setup`'s install commit. The `commit` doctype is untouched: the trailer is the adapter's, applied when the message is handed to git, never a schema item.

- **Which profile.** The one `jigc setup` installs — `cli::setup::SETUP_ASSISTANT`. Setup is single-assistant today, so no per-repo record of the choice exists to read; `jigc upgrade` and the installed-artifact roots read the same constant, and when a `--assistant` selector lands ([Open questions](#open-questions)) the recorded choice becomes all three readers' input.
- **When — and why not always.** The trailer is added only while the profile's `when-env` variable is **set and non-empty in jigc's own environment** — the variable the assistant sets for the processes its agent runs (`CLAUDECODE` for Claude Code). The trailer *claims* the agent co-authored the commit; a human running `jigc task finalize` by hand made that commit alone, and a static trailer would put a false co-author on it — a law-1 lie ([surface-contract.md](surface-contract.md)). The variable's *name* is assistant knowledge, so the profile declares it and the neutral core reads only the name it is given; the engine is never consulted. The value is a static string because Claude Code exposes `CLAUDECODE=1` and `AI_AGENT=claude-code_<version>_agent` to its agent but **no model name**.
- **Where it is applied.** At the one hook-capable commit seam (`cli::task::git_commit_capture`), which owns the message flag and signs the message every door hands it — so the axis is covered by construction and a door that joins the seam is signed by joining it. The install commit, the seam's one recorded exclusion (`--no-verify`), signs its own message with the same function.
- **Placement and de-duplication.** jigc renders the trailer itself rather than asking git to (`--trailer` would run `git interpret-trailers` under the user's ambient `trailer.*` config): appended to the message's trailer block when its last paragraph is one, else as a new block after one blank line — the place `git interpret-trailers` gives a trailer added at the end, and git's own `%(trailers)` parser is what the acceptance suite counts with. A trailer block that already names the **same address** — whatever name it spells, the key compared case-insensitively — is left byte-identical, because the composed `step:author-commit` still invites an agent to record a co-author in the commit doc's `#trailers` itself.
- **The amend arm.** It re-authors the message from scratch, so the trailer is re-derived — and **carried over** when `HEAD`'s message already carries the profile's trailer, because the tree that claim was made for does not move: a human repairing an agent's message keeps the agent's credit, and an agent amending its own commit lands it once.
- **No key, no trailer.** A profile without `co-author` adds nothing to any commit, so an adopter on another assistant is unaffected. A malformed declaration fails the profile load — `setup.profile-load` at install, no trailer at a commit — rather than ever rendering a line git would not read as a trailer.

**Declared bounds.** A human who finalizes work agents did — a `jigc milestone finalize` run by hand over sub-agents' code — lands no trailer: an omission, never a false claim, and the commit doc's `#trailers` is the route to record it. A command a human types *into* an agent's session inherits that session's environment and is signed as the agent's; jigc cannot tell the two apart and does not try (not driven). No pinned `--format json` key carries the full message — `subject` and `committed.subject` are its first line, which the trailer never touches, and the Conventional-Commits header release tooling reads is unchanged. The test suite runs every process under an empty `CLAUDECODE` (`.cargo/config.toml`), so a run inside an agent session matches a CI runner, and `crates/cli/tests/agent_co_author.rs` sets the variable per cell.
