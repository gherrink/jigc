# Methodology docs — encode planning/completion, graduate the working-docs they drive

**Status: settled at M16 planning (2026-06-09); the locked spec M16 decomposes against.** This is the close of the self-hosting loop: jigc composes its *own* milestone-planning and milestone-completion workflows **and** manages the working documents those workflows author (roadmap, deferral-ledger, decisions-log, completion-record) as managed doctypes. It is the second adoption-arc prerequisite ([roadmap.md](../implementation/roadmap.md) → M16), built on M15's `checkpoint` step kind and M13's `arch-doc` create→author→finalize→promote spine.

Reading-order note: this reads after [self-hosting.md](self-hosting.md) (it completes the loop that doc opens — M12 encoded the dev-workflow, M15 the increment-workflow, M16 the planning/completion workflows + their docs) and before [multi-pack.md](multi-pack.md) (the terminus, which composes the methodology pack this milestone completes *with* the dev pack).

## What M16 proves, and what it does not

**Proves:** jigc composes its full planning/completion workflows as methodology-pack definitions, and the methodology pack can **manage fresh instances** of its own working-doc doctypes (author + validate them) — closing the self-hosting *machinery* loop. (Not "fully closed" unqualified: the hardest case — jigc managing its *own* real, historical, two-level files — stays for the v1 migration; see the fresh-instance bound below.) The forcing-function sort ([self-hosting.md](self-hosting.md) → the three-way determinism cut) lands its last bucket here: M16 builds the **owner-assigned-artifact gate** (bucket 3 — the genuine-audit recording a headless gate can't author, only assert-present).

**Does not prove (the honest bounds, recorded so the completion audit can't charge them as findings):**
- **The single-agent-spine bound (sharper than M15).** The planning/completion workflows are multi-agent orchestration loops — planning fans out `capability-auditor`/`gap-detector`/`design-reviewer`; completion runs parallel `milestone-code-reviewer`/`milestone-e2e-tester` audits + per-finding fix agents. jigc composes the **single-agent linear spine** — the phases one agent walks, with the checkpoints and the #5 presence-gate made structural. The fanned recon, the independent design review, and the **completion audit verdict** stay orchestration-level (the build harness) and irreducible judgment — *never* jigc-composable. This bound is bigger than the increment-workflow's and is recorded, not inherited ([self-hosting.md](self-hosting.md#the-honest-encode-bound), [workflow-dialect.md](workflow-dialect.md) → checkpoint honest-encode bound). **Build-time honesty watch (review finding A-3):** the encoded planning/completion steps must keep their gap-detection / settle / verdict phases as *pure agent-judgment prose* — a step that emits a `gap-count ≥ N` lint or a structured checklist the agent must satisfy has *hollowed* the judgment (the `methodology_honesty_artifact` FAIL exemplar). The checkpoints halt; they never score.
- **Fresh-instance, not in-place migration.** M16 ships the doctypes + authoring workflows in the **methodology pack**, proven on **fresh instances** (the M12/M17 separate-project dogfood model). jigc's *own* `roadmap.md`/`DECISIONS.md`/`decisions-pending.md` stay plain markdown until a later v1 migration — graduating the real 800-line artifacts in place is a migration project that also trips the deferred multi-level-repetition limit. Honest consequence: M16 proves the *machinery*, exercised on fresh docs, not jigc's own historical files reborn as doctypes. **The hardest case stays unproven (review finding A-4):** jigc managing its *own* real, large, two-level roadmap is exactly what the one-level bound + the migration deferral leave for v1 — so "the self-hosting loop is fully closed" means *the machinery is built and exercised on fresh docs*, not *jigc's historical docs are self-managed*. M17's dogfood must not over-read this.

## The authoring spine — `creates-task: true, selectable: false` (the sub-task precedent)

The crux the gap pass surfaced: a managed doctype is authored only through the **task-scoped** create-gate (`jigc doc create`/`set-slot`/`set-field`/`add-item` all resolve an active `.jigc/tasks/<id>/` area; promotion is at finalize). The increment-workflow M15 shipped is `creates-task: false` and authors **nothing** managed — so "graduate the working docs" has no path *if* planning/completion copy that shape.

They do not. Planning and completion are **`creates-task: true, selectable: false`** — the exact front-matter of the shipped `sub-task` workflow ([crates/cli/packs/dev/workflows/sub-task.yaml](../crates/cli/packs/dev/workflows/sub-task.yaml)): they **mint a task** (so authoring rides the *proven* create-gate + finalize-promote spine, zero new authoring engine work), but ship **no `when`** and stay off the router catalog (`selectable_workflows` filters on `creates_task && selectable`). Spiked against the real binary (2026-06-09): `jigc start --workflow sub-task "..."` composes **and** mints a task dir, and the existing `selectable_catalog_excludes_the_non_selectable_sub_task` test pins it off-router. So planning/completion are invoked directly via `jigc start --workflow planning "<milestone>"` / `--workflow completion "<milestone>"`, mint a task, author their docs, finalize. The catalog-leak discipline ([self-hosting.md](self-hosting.md) build-note) holds: both stay out of the methodology pack's `default-workflow.of` enum.

A task authoring **multiple** managed docs in one pass is already proven (`single-task` authors `commit` + `adr`). Re-authoring a **committed** running doc is proven via `read_or_copy_in`/`copy_in` (the baseline exercised it end-to-end). What M16 adds to the spine is small and named below.

## The four doctypes (earned from their drivers)

All schemas live in the **methodology pack** (`crates/cli/packs/methodology/schemas/`) — the pack composes alone (the M12 subsume model; co-composition with dev is M14, not M16). All use **single-word section ids** (the multi-word-section-id reparse defect is unfixed — [decisions-pending.md](../implementation/decisions-pending.md) — and these route around it as `arch-doc`/`prd` did). Three are **running** (cross-milestone, append-maintained); one is **per-milestone** (create-fresh instance).

| Doctype | Driver | Persistence | Lifecycle | One-line shape |
|---|---|---|---|---|
| `roadmap` | planning · Decompose | running singleton, `placement: { file: docs/roadmap.md }` | idempotent-create + maintain | one repeatable `milestones` section; entry = title + `proves` slot + `decomposition` slot |
| `deferral-ledger` | planning · Settle (+ every deferral write) | running singleton, `placement: { file: docs/deferral-ledger.md }` | idempotent-create + append | one repeatable `entries` section; entry = title + `kind`(enum D/I) + `trigger`(string) + `date` + `body` slot |
| `decisions-log` | planning · Settle **+** completion · triage | running singleton, `placement: { file: docs/decisions-log.md }` | idempotent-create + append | one repeatable `entries` section; entry = title + `date` + `why` slot |
| `completion-record` | completion · Audit→triage→re-verify | per-milestone, `location: completions/` | create-fresh per milestone | `meta` header (`verdict` enum green/red + `owner-artifact` *owned-location path* field, the #5 gate target) + repeatable `findings`; finding = title + `severity` + `disposition`(enum fixed/deferred/contested) + `evidence` *string* (not a managed ref — see Relations) + an **optional `detail` prose slot** (M49: the paragraph the one-line `evidence` cannot hold) |

**Each persisted doctype gets its OWN `location:` subdir** (review finding B-1) — never a shared root location. A root `location: ./` would make the reconciliation sweep (`file_state.rs` `reconcile_committed_store` globs `<repo>/<location>/*.md`) vacuum every root markdown (`README.md`, `CLAUDE.md`, `VISION.md`) as a doctype instance, and three doctypes sharing one location breaks `identity_of` (first-prefix-wins). Dedicated subdirs mirror the shipped `decisions/`/`specs/`/`architecture/` pattern and are correct because M16 proves on **fresh instances** (the `location:` need not match jigc's own root-file layout — that is the v1-migration concern). **B-1's *dir-glob* premise is rebutted at M38** (2026-07-04): the objection is sound only because the sweep matched a `<location>/*.md` **glob**. M38's placement convention gives a singleton a **literal-file home matched by exact path** (`VISION.md` is the managed vision; every other root `.md` stays unmanaged), so a root home no longer vacuums `README.md`/`CLAUDE.md` — the glob-vs-literal distinction is the fix. So `vision` moves to root `VISION.md` and the internal singletons to direct `docs/*.md` under the new model ([storage.md](storage.md) → Placement; [DECISIONS.md](../DECISIONS.md) → 2026-07-04 M38 planned); B-1's *dedicated-subdir* conclusion stands only for **multi-instance** doctypes.

**The three running docs are SINGLETONS with a fixed slug** (review finding B-2) — the slug is **the doctype id** (always `docs/roadmap.md`, `docs/deferral-ledger.md`, `docs/decisions-log.md` — the placement homes the table above states), *not* `id-from: title`. This is the one net-new schema concept the running docs need: a `singleton: true` declaration that fixes the slug to the type id, so a re-`create` deterministically targets the same committed file (the premise idempotent-create rests on — without it, an `id-from: title` slug drifts with the authored H1 and the "running" doc forks into many). `completion-record` is **not** a singleton — it is `id-from: title` per-milestone (`<repo>/completions/m16.md`), create-fresh, the proven pattern.

**Earn-from-driver, at build.** These are intent-level shapes; each schema's exact fields/slots are authored **with its driving workflow** in the build increment that ships that workflow (the M3-`spec` / M13-`arch-doc` discipline) — not pre-defined here. The shapes above are the bar the gap pass validated, not the YAML.

**The one-level bound (roadmap).** The real roadmap is two-level (milestone spine → per-milestone increment decompositions), and the roadmap doctype is nonetheless **one level**: a milestone entry carries its increment decomposition as **prose in a `decomposition` slot**, not as structured sub-items. **The bound is a deferral, not a limit — and it was written here as a limit until M49.** Repeatable-inside-repeatable shipped at **M22** as `Leaf::Repeatable` (`changelog`'s release → change-group is the consuming target), and the increment tier would sit at nesting depth 2, inside the addressable cap — a claim the M49 baseline drove and **refuted** as a blocker ([structural-grammar.md](structural-grammar.md) → Repetition). What defers the tier is leg 0 of the M49 razor: no door and no declared hole needs it, the migration writes decomposition prose into the slot exactly as `planning-finalize.yaml` already states, and the bump that would ship the tier is itself the one nested shape no kind classifies: adding a nested repeatable block to an existing item block rides the backstop, so `roadmap` could not be migrated to the version that introduced the tier at all (`AddedNestedRepeatable`, still deferred with its trigger — [decisions-pending.md](../implementation/decisions-pending.md)). *(This clause named the wrong arm until M50. The worry it stated — that the tier, once shipped, would be stuck at its birth shape because the classifier could not see one level down — was real when written and is **retired**: `diff_item_fields` recurses, and a leaf edit one level down classifies with its own kind, driven by `crates/cli/tests/migrate_locus_axis.rs` ([corpus-migration.md](corpus-migration.md) → The third locus). What blocks the tier is the **add**, not the reshape.)* *Trigger:* a **second** independent driver that is not this repo's own planning convenience — an adopter's decomposition needing per-increment identity, status or addressability, **or** `add-from-spec` being asked to seed from a roadmap entry ([decisions-pending.md](../implementation/decisions-pending.md); [DECISIONS.md](../DECISIONS.md) → 2026-08-28 M49 Settle → D3).

**Relations (edges) — none managed, by deliberate bound (Codex finding 3).** **No M16 doctype carries a per-entry *managed* `ref`.** The tempting case — a `completion-record` finding referencing the `adr`/`spec` it concerns — is **downgraded to a plain `string` `evidence` field**, because `adr`/`spec` are **dev-pack** doctypes and the methodology pack **composes alone** (the M12 subsume model): a managed `ref: {to: adr}` would point at a doctype outside the composed schema universe, so `ref-resolves` could not walk it without pulling in dev (which is M14 co-composition, not M16). Likewise `deferral-ledger.trigger` is a milestone work-unit (`string`, not a doctype), and roadmap/decisions-log entries cross-reference in prose. **Consequence — B4 shrinks to conformance-only:** with no per-entry managed ref, the `index.rs` repeatable-ref-edge lift and the per-item edge-identity question (former finding I-3) are **not needed for M16** — they defer to the first milestone that puts a managed ref inside a repeatable item under co-composition. M16's "validate against reality" rests on **repeatable-section conformance** (every entry is well-formed), not per-entry ref-resolution. **Honest consequence:** an `evidence`/`trigger` string naming a non-existent artifact or milestone is *not* caught by any check — acceptable for M16, stated so the completion audit can't charge it.

***The universe rule is now mechanically held (M50).*** The rule above — no managed `ref` pointing at a doctype outside the composed schema universe — was a convention nothing enforced, and M50 tested it by proposing exactly the edge it forbids (`adr —supersedes→ research`, a dev-pack ref to a methodology doctype). The rule was **kept and the edge refused**, on this same rationale read symmetrically: the dev pack composes alone too, so such a ref would be *unloadable* in every dev-alone composition. The refusal exposed two defects the rule had been hiding, and the first ships with it: the pack-load [ref-target fence](multi-pack.md#a-ref-target-is-composition-scoped), which makes the rule checkable at **every** door instead of asking a future author to remember it. (The second is that `jigc doc schema`'s ref projection named no target at all — [doc-read-surface.md](doc-read-surface.md).)

**First intra-pack managed ref (M37 update).** The bound above is "no ref that points *outside* the composed schema universe" — its rationale is the dev-pack target (`adr`/`spec`) unreachable under methodology-alone composition, *not* a blanket ban on managed refs. M37's `vision —grounded-in→ research` ([design-altitude-doctypes.md](design-altitude-doctypes.md)) is the pack's **first internal managed ref**, and it **honors, not reopens, this bound**: both ends are methodology doctypes (intra-pack, so the target is inside the universe) and it is a **doc-level** header field, not a per-repeatable-item ref — so it neither points outside nor needs the still-deferred `index.rs` repeatable-ref-edge lift. `ref-resolves` walks it unchanged (the edge index is schema-driven and pack-agnostic).

## The milestone-record (M39) — work-unit state graduates to a managed doctype

M39 adds a fifth methodology-pack work-doc doctype, **`milestone-record`** (per-milestone, `location: milestone-records/`), graduating a milestone's *in-flight* state — the base-SHA pin + the ordered sub-task list with each sub-task's `intent`/`status` — out of the gitignored `.jigc/` workbench into a committed, `jigc doc show`-able record a teammate on a fresh clone continues from (the settled **`.jigc`-is-the-workbench, the repo is the record** principle). It is the symmetric sibling of `completion-record` — where that captures milestone-*close* state, this captures milestone-*in-flight* state — and, like it, carries **no LLM-authored prose slot**: it is a purely machine-maintained structural record (a base `field` + a repeatable `tasks` section), which is the shape the M16 vocabulary above did not yet express (every leaf here was an LLM-`slot` or author-`field`). It rides the proven repeatable-section + `add-item` + singleton-slug primitives and earns exactly **two** new engine capabilities — the `set: on-transition` CLI-materialization seam (extending M22's `on-create`) and the committed-record-as-operational-source read-back (the `.jigc/milestones/<id>/{base,tasks}.json` demotion to a rebuildable cache). It carries **no managed edge** (task-ids stay plain strings — a `task` is a work-unit `ref-resolves` cannot walk, the `deferral-ledger.trigger` precedent — so the M16 "no per-entry managed ref until a driver earns it" bound holds). The full design of record — the doctype shape, the two write arms (`add-task` append / `join` in-place mutate), the no-silent-overwrite reconcile preflight, the path-scoped per-op commit model, and the fresh-clone continuation semantics — is in [team-ready-state.md](team-ready-state.md); it is the conformance witness for the `jigc doc show --format json` pin ([doc-read-surface.md](doc-read-surface.md)).

## The planning gate-record (post-M16 design addition, 2026-06-21 — the pack-shape of the plan-time forcing-functions)

**Status: shipped at M49** — the `planning-record` doctype (one required slot per gate row) and the `planning` workflow's authoring step; designed 2026-06-21 and deferred at M16 ([DECISIONS.md](../DECISIONS.md) → 2026-06-21 Direction). This is **D** from the M31 retrospective, authored pack-shaped: the recurring plan-time failure-classes the methodology has accreted as prose lessons (spread across [milestone-planning-workflow.md](../implementation/milestone-planning-workflow.md) / [increment-workflow.md](../implementation/increment-workflow.md)) consolidated into a **single required gate-record** the planning workflow authors — so each is a forcing function (a slot that blocks `finalize` until filled) instead of prose an agent skims.

**The consolidated gates — and this table is their single home** (each cites the prose lesson that is its rationale — *index, not replace*: the worked instances stay where they are; this is the checklist that points at them). The set is stated here and **nowhere else**: the shipped `planning-record` carries one required slot per row below, and `crates/cli/tests/planning_gate_home.rs` derives the gates from that schema to hold this table equal to them and to refuse any paragraph under `design/`, `implementation/` or `.claude/` that restates a majority of the set. **The independent robust-case advocate — the `cheap-vs-robust` fork is never self-framed (M34).** The gate failed at M34 not for being absent — it existed and cited M33 — but because the **proposer administered *and framed* it**: the orchestrator recommended the cheap cut, strawmanned the robust path as "premature generality against a hypothetical," and the human gate decided on that biased framing. A gate the biased party both runs and frames does not bind. So a `cheap-vs-robust` fork (at plan-time **Settle** or completion-**triage**) is **adjudicated independently, not self-resolved**: before surfacing the fork, the orchestrator spawns a **separate read-only agent** (the sibling of the gap-detector / design-reviewer recon agents) whose sole charter is to argue the **vision-robust case at full strength** — the hole / one-way-door the cheap cut leaves, why the capability is on the committed trajectory (not premature), and how it is provable **now** (incl. on a reconstructed/synthetic case). The human then decides between **two honestly-argued cases**, never the proposer's lone cheap recommendation; the orchestrator may not surface a `defer` recommendation for anything that trips a cheap-vs-robust tell without the advocate's case beside it. **The advocate exercises its claims — spike, don't orate (M43, 2026-07-17):** the advocate carries the same exercise-don't-infer discipline as the recon auditors — a compiled spike, a live repro, a driven flow — because executed evidence is what decides forks (every decisive M43 advocate case rested on a spike, and two charter fears dissolved under one: a serialization golden proven byte-identical, a "second gate" proven a non-issue). An advocate case that only argues is a weaker instrument than the fork deserves. (Run by hand today — a spawned subagent, like the existing delegated recon — and pack-encoded with the planning workflow. **Bound against gilding:** it fires on a *genuine* fork — a deferral/cheap-cut of something the milestone *touches* — not on every trivial disposition; a clearly trajectory-uncommitted extension still defers, but the advocate is what **tests** that claim instead of letting the proposer assert it.)

**A deferral trigger is a claim about the code — and a claim gets a test (M42, 2026-07-14).** The `deferral-ledger` entry's **`trigger` is a plain `string`** — *"revisit when X happens"* — i.e. a condition someone must **remember to re-evaluate**. That is the rotting-prose shape again, and it rotted: the freeze-assert hole was deferred with the trigger *"if packs are ever loaded from the filesystem in production"*; **multi-pack shipped at M14, the trigger fired, and nothing noticed** — the hole was found two milestones and one RC trial later. **Pack-shape:** the entry block gains an **optional `trigger-test: code-anchor`** field with `check: symbol-exists` — so a deferral whose trigger is a *checkable claim about the code* **names a test that asserts the condition has not yet arrived**, the `doc-code` probe **verifies the test exists**, and the test **goes red on the commit that makes the trigger true.** *The trigger fires itself; nobody has to remember it.* Triggers that are genuinely judgment (*"when an adopter corpus surfaces a measured floor"*) keep the prose field and stay `N/A` — the field is **optional by design**, and that boundary is the A-3 bound doing its job. **Cost note:** an added optional field on a repeatable item block was *unclassifiable* by the corpus-migration classifier until three days ago; **M42 built `AddedItemField`**, so this is now a routine `deferral-ledger` bump rather than a corpus strand. Lands with the self-hosting encode.

**The M42 rows are the pack shape, not a description of it.** The `census` and `reuse-exercised` cells sharpened at M42 (2026-07-14) are written as the **slot hints** the `planning-record` schema will carry — *"name where the property is enforced, or state honestly that it is list-enforced and will rot"*, *"a cell that cites a type, a parameter or a call site rather than a behaviour you observed is not filled"*. When the encode lands, those sentences move **verbatim** into the schema's `hint:`; nothing is redesigned. That is the 2026-06-21 rule working as intended — and it is worth recording that the rule **had not been followed once** in the three weeks before M42 (M41's two dev-workflow fold-backs were plain prose; so was M42's first draft), which is the same failure the rules themselves describe: *a rule you must remember to read is not a fence.*

**The pack form — presence-conformance, never content-scoring (the A-3 bound is load-bearing here).** A per-milestone **`planning-record`** doctype (intent-level; the symmetric sibling of `completion-record` — planning produces a gate-record, completion produces an audit-record), one **required slot per gate**, each answered with the agent's authored **evidence-or-`N/A`-with-why**. The forcing function is the *already-built* `required-slot-present` conformance (M16 engine work #1): an empty gate-slot **blocks** `finalize` on the planning task. jigc enforces the slot is **filled** — it **never reads or grades the judgment inside it** (the #5 owner-artifact "presence, not content" precedent). This is exactly the line A-3 draws: a composed step that emitted a `gap-count ≥ N` lint or auto-checked the gates would *hollow* the judgment (the `methodology_honesty_artifact` FAIL) — **barred**. The checkpoints halt; they never score; the agent writes the property census / the cheap-vs-robust fork / the spike evidence *as prose into the slot*, the same way `completion-record.findings` are agent-authored and jigc only checks the section conforms.

**Why this caps the prose accretion (the other half of D).** Today a new lesson appends a paragraph to an already-long workflow doc that the next agent skims. Pack-shaped, a new lesson is a **new gate-row** (+ a one-line rationale pointer to its worked instance), and the workflow docs **stop growing inline prose** — [milestone-planning-workflow.md](../implementation/milestone-planning-workflow.md) points *here* for the gate-record and keeps only the worked instances as the *why*. (Lighter alternative if a fifth doctype is unwanted at encode-time: fold the gate-slots onto the existing roadmap milestone-entry — co-located but mixes "the plan" with "the plan's gate-record"; the separate `planning-record` is recommended for the completion-record symmetry. **Earn-at-build:** the exact slots/YAML are authored with the planning-workflow encode, the M3-`spec`/M13-`arch-doc` discipline — the table above is the bar, not the schema.)

## The engine work (bounded; risk-first)

Three engine deltas, each with the M13 cold-start discipline (spike the **empty/cold** state, not a populated fixture) and the forward-review red obligation (every gate must **fire-and-block** on deliberately-malformed input before its green test — the *vacuously-green managed-doc gate* failure class):

1. **Repeatable-section conformance (the B4 lift, conformance-only).** `validate.rs` skips conformance over repeatable sections (an unconditional `continue` past non-`Simple` bodies). Lift it: per item, run `required-slot-present`/`required-field-present`/`field-value-conformant` over the block's leaves (exempting the `id-from` heading field). Validate-layer-only — the parser already records per-item slot spans + fields; the `#section/item/leaf` address vocabulary (M13) already addresses a finding inside an item. **The ref-edge half is OUT of M16** (Codex finding 3): no M16 doctype carries a per-entry managed ref (the completion-record's per-finding reference is a `string`, not a `ref`, because its `adr`/`spec` targets live in the dev pack and the methodology pack composes alone), so the `index.rs` repeatable-edge lift and the per-item edge-identity question defer to the first co-composition milestone that needs them. **Red obligation:** a hand-malformed repeatable entry (empty required slot; malformed required field value) must produce a blocking finding — proving the loop fires, not just that good input passes. This updates the `schema-conformance.*` scope in [validation.md](validation.md) and [document-type-schema.md](document-type-schema.md) (which states the MVP limit being lifted).

2. **Idempotent create (the B5 fix + the create-or-update mechanism).** `create` today checks only the *working-area* path, so `create` on an already-committed slug mints a **blank** and finalize **clobbers** the committed file (silent data loss). Fix: `create` on an existing committed slug **copies-in** the committed doc (the `read_or_copy_in` path) instead of minting blank. This (a) kills the clobber landmine and (b) gives **create-or-update** — the running-doc workflows always say "create the ledger," safe whether or not it exists, then `add-item` appends. **No *workflow* conditional and no agent branch-judgment** (Codex finding 5): `create` is a deterministic state-dependent *write command* (singleton + committed-path-exists → copy-in; else mint), exactly as every write command acts over current store state — the barred thing is conditional *composition* / agent branching, not deterministic command behavior. **Gate the committed-copy-in to the singleton/create-or-update doctypes (review finding I-2)** — `create` is a *shared* primitive (the MVP `single-task` ADR flow uses it and expects a fresh mint / collision-reject). Changing it globally would silently make a committed-ADR slug collision copy-in the old ADR instead of rejecting — a behavior change to the acceptance-pinned superseding-decision flow. So the copy-in branch keys on the `singleton: true` schema flag (or an explicit create-or-update marker); non-singleton `create` keeps its mint-or-reject semantics unchanged, with a regression obligation that the `single-task` ADR-create + superseding flow still pass. **Copy-in does not itself reconcile (review finding I-1):** `read_or_copy_in` reads the committed doc directly; OOB drift over it is caught at **finalize-preflight** (`reconcile_committed_store` → DRIFTED+TOUCHED conflict-block), not at copy-in. **Red obligation + cold/warm spike:** `create` cold (fresh) round-trips byte-stable; `create` warm (existing) preserves prior content and re-promotes byte-stable — and the warm-drift spike must **record the baseline first**, then OOB-edit, then assert finalize *conflict-blocks* (an unrecorded-baseline drift silently baseline-*adopts*, a vacuously-green pass; confirm `first_touch_canonicalize` is a no-op on an already-canonical committed doc so the first warm edit doesn't perturb bytes). **Revised at M43 inc-7 T1** ([DECISIONS.md](../DECISIONS.md) → 2026-07-16 M43 planning: the Settle, review-baked): the I-2 singleton gate is **dropped** — the copy-in is doctype-blind, extending create-or-update to every persisted doctype (the blank-Created finalize clobber ambush on non-singletons was a defect against this record's intent). The superseding flow I-2 protected is unaffected in substance: a *fresh-slug* ADR still mints fresh, a working-area collision still serial-rejects, and a committed-slug create now updates instead of ambushing; the ack carries the `existed` discriminator ([command-output-contract.md](command-output-contract.md) §2).

3. **The #5 owner-assigned-artifact gate (the completion-half primitive).** The third determinism-bucket: the milestone-completion audit produces a **recorded owner-artifact** — the genuine live-agent audit run (the Half-B recording a headless gate cannot author, the sibling of M8's genuine-spawn). The #5 gate is a **finalize-time presence check** on the completion task: `exists(path)` for the named owner-artifact, **pure presence, zero content inspection** (a check that reads the artifact's bytes has crossed into judgment — the determinism boundary; that is the FAIL exemplar). It emits a blocking finding when absent, never an opinion on quality. It is an **intrinsic** check (the milestone is not shippable without the artifact — floored blocking), so it adds one row across the severity lists: `INTRINSIC_CHECK_KEYS` (17→18), both packs' `knobs.yaml` (26→27), `CHECK_INVENTORY` (it is a task-validate/finalize check, unlike the compose-time marker checks), and the [validation.md](validation.md) Severity inventory.

   **The recording surface (review finding B-3 + Codex blocking-1 — was undesigned and, once designed, was vacuous).** The path the gate checks is the **`owner-artifact` field on the `completion-record`'s `meta` header**, but it is **not an arbitrary path** — a bare `exists(path)` would pass with `owner-artifact: README.md` or any pre-existing/untracked file, proving "some path exists," not "a durable owner-artifact was recorded" (the source workflow's bar: *"not shippable until this artifact exists"*). So the field is constrained to a **repo-relative path under an owned artifact home** (`completions/artifacts/<milestone>/…`), and finalize **stages that file in the same transaction** as the `completion-record` (the writes-are-transactional-at-finalize invariant). *(It is a **stage**, not a doc promotion: the artifact is not a managed instance, so it never passes through `plan_promotions` — finalize stages the recorded `owned-location` path into the index the commit carries, [finalize.md](finalize.md) → 5. Stage.)* The gate **rejects** absolute paths, `..`, symlink escapes, and untracked/out-of-repo targets, and asserts the artifact is **durably present in the committed artifact home**. It reads the field string + checks the file is staged/committed — never the artifact's bytes (presence, not content). The read site is finalize/validate on the completion task; the existing machinery has no owner-artifact concept, so the field-validation + same-transaction staging + `exists()` is the net-new surface (real, not assumed-reusable).

   **Amended at M17 planning (2026-06-12) — the omission bypass is closed.** The M16 shape left the *field itself* optional (`owned-location` exempt from `required-field-present` — "presence is the agent's choice"), which made the backstop bypassable by omission: a completion-record that never sets `owner-artifact:` finalized clean with **no finding anywhere** — and omission is the default state of a fresh mint, so the bypass was the path of least resistance (verified by exercise). M17 reverses the exemption: a **declared** owned-location field is required like any other field — *conformance* owns field-**absence**; the **#5 gate** keeps owning the named *file's* presence/safety/trackedness. Chosen over teaching the gate to block on field-absence, to keep conformance uniform (field-absence is ordinary schema conformance, not artifact adjudication). The `validate.rs` exemption comment flips in the same increment. ([DECISIONS.md](../DECISIONS.md) 2026-06-12; the M17 pre-fix set.)

   **What it proves, and the honest bound (the anti-vacuity statement).** The gate proves **"an artifact is present at the path the completion-record names"** — it does **not** prove the genuine audit happened. Unlike M8's genuine-spawn (a capability a headless agent *structurally cannot* fake), a path-existence check has no such teeth: the orchestrator writes both the path-field and the file. So genuineness stays an **orchestration-level recorded responsibility** (the M8 analogue — the completion e2e-tester, being headless, flags the owner-artifact as the half it did *not* run; [milestone-completion-workflow.md](../implementation/milestone-completion-workflow.md) → the spawn-class third audit artifact). The gate is a **backstop** — you cannot finalize a completion without recording *something* at the named path — not a proof of the audit's authenticity. Stated plainly so the gate can't be over-read as mechanizing the judgment it only brackets. **Red obligation:** the gate **blocks** when the named path is absent and **passes** when present — proving it fires, not a vacuous always-pass.

**Why a check, not a step kind.** A step kind only *emits* a deterministic directive from compose-time data — it cannot verify anything at finalize (no runtime). A presence *assertion* is a finding-emitter, so it is a validation check, not a `StepKind` variant. (A checkpoint-flavored halt was considered and rejected: it asserts nothing, it only halts — presence would be trusted, not checked.)
