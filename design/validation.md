# Validation engine

**One deterministic engine runs read-only probes over a scope and reports severity-classified findings.** It is the *validate* stage of the loop and the gate behind `finalize`.

Builds on [VISION.md](../VISION.md) principle #6, [structural-grammar.md](structural-grammar.md) (the edge index, the validation framing, override), [document-type-schema.md](document-type-schema.md) (the relations probes walk), [write-commands.md](write-commands.md) (`finalize ≡ validate + commit`, severity-as-cascade, the `reconcile` route), [storage.md](storage.md) (edge index, effective state), and [workflow-dialect.md](workflow-dialect.md) (findings feed composition; the `workflow-refs` probe). For the *why*, see [DECISIONS.md](../DECISIONS.md). Scope: the framework + the two engine-native MVP probes; `doc-code` is pinned at contract level only (`override-default` is fully specified in [overrides.md](overrides.md)). Notation is **illustrative** ([what that disclaims](../CLAUDE.md#how-we-work-together)).

## What validation is — and isn't

Validation is **the determinism boundary applied to correctness**: the CLI-owned half of a project (references, structure, state) can be *mechanically verified*; the LLM-owned half (prose) cannot. So the engine checks exactly the structured half and **never judges the prose**.

- **Mechanical, never semantic** — deterministic predicates, no LLM in the engine (it makes no model calls). There is no "is this spec well-written?" probe. The integration advantage is *guaranteed referential integrity*, not content quality.
- **Detect & route, never auto-fix** — the engine reports what's wrong and a direction to repair; it never authors the fix.
- **Read-only & deterministic** — probes never mutate; same effective state → same findings.

*Honest boundary* ([VISION.md](../VISION.md) principle #6): this catches **structural/syntactic** breakage (dangling refs, missing coverage mappings, drift), not **semantic** drift (upstream changing the meaning around an untouched reference). "Always knowing what's stale" is the achievable, valuable promise.

**Where it sits:** the engine runs at **`validate` / `finalize`**. The per-write field-type / enum / slug checks are the schema's *local adjudication* — a separate fast path at write-time, not the validation engine ([write-commands.md](write-commands.md): write-time vs finalize-time checks).

## The engine / probe boundary

**Fat engine, thin probes.** The engine owns everything reusable; a probe is the narrowest domain predicate.

| the **engine** provides | a **probe** declares / implements |
|---|---|
| scope → target resolution (task / doc / store) | an **id** (`workflow-refs`, `file-state`, `doc-code`, …) |
| the read-only **effective-state graph + edge index** | a **target-type** (any-doc / a doc-type / workflow / file / override) |
| **scheduling** probes over targets (independent, parallelizable) | a **default severity** (blocking / warning / advisory) |
| **severity assignment via the cascade** (the M6 post-pass below), aggregation, report | a read-only **`check(target, ctx) → [finding]`** |
| the **`finalize` gate** | — |

**Severity is engine-owned, via the cascade.** A probe returns a finding with a *suggested default*; the engine assigns the **final** severity from `project > team > pack-default`. This is the only design that honors the locked "severity is a cascade setting" — a project promotes or demotes a check (e.g. `doc-code.missing-test: advisory`) as a recorded override delta, never a code change. Self-classify (severity baked into probe code) is rejected for exactly that reason. **Wired in M6** ([Severity assignment — the M6 post-pass](#severity-assignment--the-m6-post-pass)); pre-M6 every finding carries its hardcoded default and no cascade read happens.

## Findings

A finding is `{ target, probe, severity, message, route }`:

- **target** — the address it concerns (`spec:auth-flow#criteria/rate-limit`)
- **probe** — who raised it · **severity** — engine-assigned via cascade · **message** — human-readable (always present)
- **route** — a repair direction the engine **never executes**, **always present** (the route floor below — never `null`). **On the wire, `route` is a `String`** (a human-readable prose direction; the pinned `Finding` JSON envelope — as built, unchanged at M43). Internally (M43) every route is constructed as a typed `Route` value — the **kind taxonomy**: **`Mechanical { argv, tail }`** (a copy-runnable `jigc` command, parse-asserted against the real CLI) · **`Human(String)`** (a real fix jigc cannot execute) · **`Informational(String)`** (a genuine no-op) — serializing byte-identical to the string form ([surface-contract.md](surface-contract.md) → The route fence). That taxonomy is also the **future wire tagged-union**; promoting the wire shape stays a deferred cross-cutting result-contract change (it would re-shape the pinned golden and every route producer — [decisions-pending.md](../implementation/decisions-pending.md)). It supersedes the earlier `fill-leaf`/`run-command`/`reconcile` union sketched here (retired at the M43 fold-back, rationale engaged: a driver's real need is **act-vs-inform** — `Mechanical{argv}` subsumes `run-command`, and `fill-leaf`/`reconcile` were mechanical routes to *specific verbs*, not kinds; [DECISIONS.md](../DECISIONS.md) → 2026-07-16 M43 planning: the Settle).

```text
{ target:   spec:auth-flow#criteria/rate-limit,
  probe:    doc-code,
  severity: blocking,                          # from cascade; probe default was blocking
  message:  "criterion maps to no test",
  route:    "point the criterion at a real test, or correct the cited symbol" }
```

Because findings are **navigable state**, a `fix-drift` workflow can `fan-out` over `{{store.findings}}` and route each to its repair — *validate → compose a repair workflow → agent authors the fix → re-validate*. The loop closes while the engine still only **detects and routes**. The route is a *direction*, not a guarantee the repair is correct or complete — the agent still reasons and authors.

### The route floor

**Every finding carries a route — two kinds, never `null`** (M41 Fork 2 / V15 established the floor over advisories, under this section's pre-M43 name *the advisory-route floor* — the name inbound pointers from that era still carry; **M43 widens it to blocking validation/gate findings** — [surface-contract.md](surface-contract.md) → The route fence; the contract owner is [command-output-contract.md](command-output-contract.md) → §route). This **supersedes** the earlier "route is optional / `none` is fine where there's no mechanical route" model: the no-op case is reified as an explicit route *value*, not a null.

- A **repair route** names an action — **mechanical** (`run jigc …`) *or* a **non-mechanical human** one (`correct or drop the mention`, `author a referrer` — a real fix jigc cannot execute). The two route-less advisories the engine emitted — `schema-conformance.mention-resolves` (a dangling in-prose mention) and `schema-completeness.inverse-cardinality` (a below-minimum completeness obligation) — carry human repair routes, not the no-op.
- An **informational route** (`no action needed …`) marks a genuine no-op — an uncheckable-by-design outcome (e.g. `doc-code.unsupported-language`) or a pure routing note (a `file-state` baseline-adopt / absorb).

The floor rule is "every finding **routes**," **not** "every route is 'no action needed'" — flattening the two would tell an agent a dangling mention needs no action, a regression. This honors the earlier rationale (a null was tolerated only where there is no *mechanical* route) by reifying that case as an explicit informational route rather than an absence.

**Blocking joins the floor (M43).** A blocked finalize is the highest-stakes surface, and under the advisory-only scoping it printed no recovery: every gate `schema-conformance.*` block was minted route-less ("the agent fills the slot directly" — assumed, never said). Now the gate blocks name their repair verb (`required-slot-present` → `jigc doc set-slot`, `required-field-present`/`field-value-conformant` → `jigc doc set-field`, and the task-sweep `unknown-type` block — a staged doc whose type the resolved cascade does not define — carries a human route: check the type against `jigc describe`, then restore the doctype's cascade entry or remove/re-type the stray staged file), the write-time `write.*` rejects route their fix-and-re-run direction (**which miss earns which code, and which route each code carries, is *The `write.*` route split* below** — a route is a function of the miss, so the code has to name the miss correctly first), and every `workflow-refs.*` break carries the family's fix-the-definition route. The cascade delta-target parse errors (`structural-target.*` / `slot-fill-target.*`) and the project-owned-step read fault (`overrides.project-step-missing`) carry human routes too — correct the target string in the `jigc config` argument or the recorded `deltas:` entry; restore the owned step file or drop the project layer's claim — closed at the M43 completion audit: they had passed the floor only by the accident of every caller rendering through `finding_to_err` rather than the seam, and are now seam-admissible by decision (routed + declared singletons, [command-output-contract.md](command-output-contract.md) → The declared singleton exception). **The floor's presence half is asserted at the seam** — `blocking ⇒ route present` rides `Finding`'s own `Serialize` (the third assert on the M42 finding-key seam, debug posture: enforced by the suite exercising the seam, never a release panic), so a route-less non-exempt blocking finding cannot be serialized at all and there is no producer census to keep current.

**P6 — route-followability (M47): presence is not followability, and the second property lands at the same seam.** The M43 CLI-seam fence proves a mechanical route **parses**; it sits on `Route::mechanical` and never sees the finding, so a route reaching an agent still carrying `<doctype>` or `<address>` passed every fence above and was still unrunnable — law 2's *nothing hides* failing at the last inch ([surface-contract.md](surface-contract.md) → The route fence). So a second, **finding-side** property, asserted where the presence half is: *a placeholder whose value is derivable from the finding's own `key.target` must be substituted before the finding is projected* — `Finding::route_placeholders_are_substituted`, the fourth assert on the finding-serialization seam, same debug posture as its three siblings. Derivability is **declared, never inferred**: `ROUTE_PLACEHOLDERS` in [finding.rs](../crates/engine/src/finding.rs) carries one row per member of the CLI-seam `DUMMY_SUBSTITUTIONS` table — a verdict **and its reason** — beside `is_route_exempt`/`is_declared_singleton`, with a test asserting the two tables declare the same set in the same order (a token in one and not the other is either a placeholder with no verdict or a verdict about a placeholder no route may carry). Exactly two are derivable: **`<address>`** (the target itself — *narrowed to the top showable hop on a `jigc doc show` route*, since a read verb resolves a doc or a section and never the absent item a `write.not-present` names, so echoing the target verbatim would mint a concrete dead end, worse than the placeholder it replaced) and **`<doctype>`** (the target's `<type>` head). **`<task-id>` is the carve-out, declared non-derivable rather than faked**: one doc is written from many tasks, so no rule derives a task from an address — it needs a *different* source (the CLI dispatch that resolved the task, which is exactly what the write-verb enrichment below supplies) and stays outside the property. Human-route prose spans are outside it too: the property reads an argv, which only a mechanical route has. **Statement == fence** — this paragraph names the table, and the table *is* the enforcement.

**The boundary-door selector (M49): a route must run at the door that printed it.** Presence, parseability and placeholder-substitution are all properties of the route *in isolation*; a route can hold all three and still exit 1 at the door that emitted it. It did: every gate block's `jigc doc` write carried no `--task` selector, so at each of the three boundary doors — the registry `render::BOUNDARY_DOORS`, the doors the shared `validate_task` entry stands behind — the emitted argv failed with *"more than one active task"* the moment a second task was open, which a fan-out always is. This is not a counter-example to `<task-id>`'s declared non-derivability above: that verdict is about the *address*, and the second source it names — the CLI dispatch that resolved the task — is precisely what these doors hold (the two task doors take the id as their own argument; the milestone door reads the contributing sub-task off `MaterializeOutcome::sources`). So the selector is supplied by the same CLI-side post-pass the write verbs use, keyed on the route's **shape** — a mechanical argv naming a `jigc doc` verb `VERB_KINDS` classifies `Write` — and re-checked through the fence's own predicate before it is adopted, so the pass can only emit a route that runs. It is **door-scoped**: the store sweep resolves no task and its routes stay task-free. The property is proven the only way it can be, by **running the emitted bytes**: `crates/cli/tests/route_followability.rs` crosses `engine::validate::conformance_repair_codes()` with that door registry, reading both sides from code and panicking on a door it has no arm for.

**One exemption, re-affirmed on its own rationale — and one that used to be listed beside it** (the one-home exemption fn `is_route_exempt` in [finding.rs](../crates/engine/src/finding.rs) — the `is_declared_singleton` pattern, a list of exceptions checkable from the code alone):

- A **purely-positional parser `conformance.*` diagnostic** — a `Severity::Blocking` finding raised at a source coordinate — *may* stay route-less: the located message **is** the repair (fix the named line; no CLI verb repairs a hand-broken byte, and an at-parse route would be a guess). **The rationale became true of the surface it is about at M49** (Increment 8 / T4): until then the located half reached only the `--format json` envelope — the agent text rendered `severity · code — message` and nothing else, so an exemption justified by *the located message* named no line and no address to the reader it exempted. Every text render of a `Finding` now carries an indented **`at: <address> · line <n>`** between the message and the route, from one renderer (`cli::render::finding_locus`), and the axis is held from source: `crates/cli/tests/located_finding_text.rs` sweeps every production read of a finding's `message` in `crates/cli/src` and requires a verdict with a reason per site, a `Carries` verdict checked against the enclosing function rather than believed. **Line 1 is this codebase's *no coordinate known*** — every producer that synthesizes a location purely to carry an address stamps `1:1` (`readdress_to_uri`, `compose::at_resource`, `doc::stamp_target`, `migrate_corpus::blocked_finding`) — so a line-1 location contributes its address alone, and a location-less finding renders byte-identically to before. Exemption means *may*, not *must*: a parse failure that does know a direction (a below-version doc's findings routed `migrate`) still carries it. **M49 adds the second such carrier**, and it is a `conformance.*` code proper: `conformance.duplicate-field` — a declared key repeated in one field group is repaired by deleting the stray line, which is a direction rather than a guess, so it carries the shipped hand-repair sanction ([The M49 registration](#the-m49-registration)). The pinned envelope in [finding.rs](../crates/engine/src/finding.rs) keeps its `route: null` for exactly this shape.

  **And the exemption is a list, not a namespace** (M49, Increment 8 / D5). `is_route_exempt` was `starts_with("conformance.")`, so a code *no producer emits* was exempt by its **spelling** — a route-less blocking finding could be admitted at the seam by being named into the family, which is the same shape as a fence that cannot refuse. It is now `CONFORMANCE_PARSE_DIAGNOSTICS` in [finding.rs](../crates/engine/src/finding.rs): thirteen rows in the order the parser raises them (frame → field group → item identity → slot prose), the shared reason stated once and what each message leaves the reader stated per row. **The shared reason is stronger than *the located message is the repair*, and it is checkable**: every member is raised by `parse::parse_sections`, which returns `Err` on *any* finding, so a document carrying one **does not parse** — and every `jigc doc` write verb resolves its address through that same parse, so a mechanical repair route here would name a command that cannot run on the document it is printed about. Completeness needs no new census: the shipped seam-sweep (`every_production_blocking_finding_is_routed_or_exempt`) scans engine production source for route-less blocking constructors and asserts each code is enumerated — an applied mutant (a new route-less blocking `conformance.*` producer) reddens it, where the prefix predicate admitted the same mutant silently — and a **disposal arm** beside it asserts the reverse direction over engine source: every `conformance.*` code *name* has a producer. That is how the two dead names went — `item-anchor-missing`, retired by M45's rename and alive only in a negative assertion nothing could ever falsify, and a synthetic `heading-missing` standing in for the real `section-missing` in the engine's own pinned-envelope golden. A retired code is now written without its family head, because a name spelled in full is a name with no producer.
- **The hook-rejection identities were the second exemption, and M52 retired the need for one.** Through rc.15 `finalize.commit-rejected` and its nine per-door siblings were an anyhow error path and never a `Finding`, so the floor never saw them and the exemption fn needed no entry. Since M52 Increment 1 a reject that carries a finding is emitted on the findings envelope ([command-output-contract.md](command-output-contract.md) → The two reject arms), so each identity **does** reach the seam — as a blocking `Finding` **carrying a route**: the frame's own recovery sentence, naming what survived and this door's re-run. It satisfies the floor rather than being excused from it, and `is_route_exempt` still has exactly one family in it. git's verbatim stderr is unchanged — it is the finding's `message`, escaped by the envelope like every other value, never wrapped ([finalize.md](finalize.md)).

### The `write.*` route split

**Established M43; the taxonomy revised at M47** ([DECISIONS.md](../DECISIONS.md) → 2026-07-26 M47 Settle, Decisions 8 and 9). The write-time rejects are the one family whose route depends on *which kind of miss* the address made, so the wave that swept the routes had to fix the codes first: four of the eight cells of the write-verb × miss-shape matrix named an **item-id miss** a shape question and routed it at the schema — a dead end, because the schema names the declared shape and never the corpus's real item ids — and once the codes were corrected, **six** cells still handed back the engine's *literal* fallback (`jigc doc show <address> --task <task-id>`, both placeholders unfilled) until the enrichment reached every dispatch site. Both matrices are swept as data, one row per cell (`crates/cli/tests/write_miss_shape_axis.rs`, `crates/cli/tests/undeclared_address_writes.rs`), which is what makes a tenth verb a row rather than a rediscovery. The **address-miss** taxonomy — the four codes an address that *names nothing* can earn (the payload rejects and the write-time guards answer a different question and carry their own routes: `write.malformed-value` · `write.already-present` · `write.unslugable-title` · `write.list-overwrite` through `write_route`'s declared per-code map, `write.id-from-field` · `write.machine-maintained` · `write.unset-ineligible` · `write.area-barrier` · `write.identity-change` · `write.title-ignored` at their own construction sites — the second-to-last produced at `jigc doc retitle-item`'s enum-`id-from` refusal, at `jigc doc rename`'s two identity refusals, at the `create`/`author` title pre-check's divergence arm, and — since M49 — at `jigc rename`'s own two fixed-identity refusals (a placement singleton's and a milestone-record's reslug), whose whole shipped defect was carrying **neither** code nor route while that in-task sibling one argument away carried both; the last **only** at that pre-check, for the *silent no-op* shape a same-slug re-author or a fixed-title singleton makes, M48 — and note that the `write_route` half of the split is **write-verb-scoped**: `jigc rename` reaches no engine write, so where it raises `write.already-present` / `write.unslugable-title` it composes the route for the state it is actually in, its occupancy arm naming both the free-id re-run and the incumbent the caller may have meant):

- **`write.unknown-section`** — the address names a section **the schema does not declare** (`SpliceError::UndeclaredSection`, and `GenerateError::UnknownSection` on the generation half). **At any hop, not only the first (M49):** a *nested*-section segment declared nowhere in the item block it is addressed under (`#releases/1-3-0/bogus/xyz`) is the same miss one level down, and earns the same code at all six item-addressing verbs plus the `add-item` whose destination is that segment — one predicate (`engine::write::nested_section_undeclared`, the ranked sibling of `section_undeclared`), converging the four codes the doors used to disagree on ([command-output-contract.md](command-output-contract.md) → Evolution posture, the M49 code flip). The bound is the segment declared **nowhere**: one declared as a field or slot stays `write.wrong-shape`, and a trailing **leaf** name is not a section hop at all. **And at the *section-level* forms, which reach no write door at all (M49):** `jigc doc set-slot` at `#<undeclared-section>` and `jigc doc set-field` at `#<undeclared-section>/<leaf>` bottom out in the CLI's own target resolvers — searching the schema for a slot or a field, finding neither because the section they would live in does not exist, and refusing with a bare `{"error": "no slot addressed by …"}`: code-less, route-less, **outside the finding envelope**, so a driver keying on `(code, target)` saw nothing and the agent was handed no recovery. `jigc doc author` reaches both resolvers through its batch lowering — a payload section's `set:` key is a field hop, the section's own id is its slot, key-less — so the same bare form answered at two more doors. The sentence above was therefore a **universal with four exceptions**, declared only in a test comment and a commit message (M47 increment 6, advisory 2). It is no longer stated as a universal a reader has to take on trust: it is **held by a named fence** (M50) — `every_doc_write_verb_answers_its_address_shape_and_declaredness_cells` in [write_miss_shape_axis.rs](../crates/cli/tests/write_miss_shape_axis.rs) crosses the write-verb surface it derives from `VERB_KINDS ▸ doc ▸ Write` with a **manufactured** address-shape × leading-hop-declaredness space (`engine::address::Fragment` supplies hop counts and no verdicts, and declaredness is a property of a fixture, not of any registry), carries the code each cell must earn, and totals the table against the driven cells **in both directions** — no row may claim a cell nothing drives, and no driven cell may sit outside the table. Every `doc` write verb is dispositioned exactly once: it carries rows, or it takes no address at all (`doc create`; `doc rename`, whose own fragment refusal is routed but still code-less and outside the finding envelope — the last bare-sentence reject on the surface, and not this cross's), or its cells are reached **by lowering** (`doc author`, whose payload keys land on the five addressed verbs' own resolvers). The resolvers ask the engine's own rank-1 predicate (`engine::write::undeclared_section_splice`, `pub` for exactly this) instead of inferring the miss from the absent leaf below, so *undeclared section* is one predicate, one code, one sentence and one `jigc doc schema <doctype>` read whichever side of the seam adjudicates it. **The bound that remains is narrower than it was (M50).** The single-hop `#<name>` at `set-field` names no section at *any* hop — it is a field-id search across every declared section — so `write.unknown-section` is still not what it got wrong, and minting one there would be a law-1 lie about sections that all exist (driven: `jigc doc set-field <adr>#status` resolves, through the **declared** header section that carries a field of that id). What is no longer true is the second half of that sentence: an unmatched single hop does **not** keep the resolver's own *no field addressed by* sentence. It named an undeclared **leaf**, which is `write.unknown-field` at every write verb, and it earns it at both `--value` and `--unset` — with the miss's `at` naming the search the form performs rather than a section it never addressed. The two section-level resolvers' **remaining** bare arms go with it: an address with no fragment at all at either verb, and — at `set-slot` — a declared section that hosts no prose slot (repeatable, or simple and slotless) and an item address with no slot leaf hop, each a genuine declared-shape defect and so `write.wrong-shape`, ranked behind the same rank-1 undeclared-section question. `jigc doc author` inherits every one of them through its batch lowering, by construction rather than by a second guard ([write-commands.md](write-commands.md) → Every write resolves its address before it moves bytes). What survives as a bound is a **type**, not a promise: both resolvers and the shared undeclared-section guard now carry `Finding` as their error, which is what a bare `anyhow` cannot inhabit — the escape `DocFailure`'s blanket `From<anyhow::Error>` opens is closed at the type level rather than by a later grep.
- **`write.unknown-field`** — the address names an undeclared **leaf**, *field or slot alike*: **one contract member** for "the schema declares no such leaf here", whichever leaf kind it named (`GenerateError::UnknownField` for a field, `SpliceError::UnknownLeaf` for a slot — two variants for the **sentence**, one code and one route, because a `set-slot` reject must say *slot*: that is what the agent addressed). M47 T4/T5; [write-commands.md](write-commands.md) → Every write resolves its address before it moves bytes.
- **`write.wrong-shape`** — a **genuine declared-shape defect**, and only that: the declared shape cannot host the write (an `add-item` into a simple section, an item address under a non-repeatable one), or the staged source no longer parses against the schema at all (`GenerateError::WrongShape`). At M47 it **retreats** to that set — it is no longer what an item-id miss reports.
- **`write.not-present`** — an **item-id miss at every item-addressing write verb**: the addressed item was never minted, or names no item under the addressed parent. `GenerateError::NotPresent` and `SpliceError::NotPresent` mint the same code from the two halves of the write path, so the same miss reads the same whichever half adjudicated it.

The first three are answerable **from the schema** and route the mechanical `jigc doc schema <doctype>` read. The fourth is not: it routes the **followable containing section** — `jigc doc show <type>:<slug>#<section> --task <id>`, whose live item ids reveal the right address — and the N2 pin strips a nested / field-leaf address to the top **showable** section, never an unshowable field-leaf (M44 Inc 2).

**That last route is overridden at the write-verb dispatch — at six sites, not universally.** The engine's `write_route` map holds no URI and no task id, so its `write.not-present` arm is a **defensive fallback**; the concrete route is built by `enrich_not_present_route` ([doc.rs](../crates/cli/src/doc.rs)) as a post-pass at the **six write-verb dispatch sites** that can produce the code — `run_set_field` · `run_unset_field` · `run_set_slot` · `run_add_item` · `run_remove_item` · `run_retitle_item`, i.e. the five verbs `jigc doc set-field` (both `--value` and `--unset`), `set-slot`, `add-item`, `remove-item`, `retitle-item` — where the real URI and the resolved task id are in scope (M44 wired two; M47 T2 wired the other four, two of which T1 had just turned into producers). **The batch `jigc doc author` path is the declared exception**: it lowers every leaf through the shared `apply_slot_target`/`apply_field_target` seam rather than a per-verb dispatch, so it keeps the engine's fallback — whose `<address>` half P6's substitution now fills, leaving only the non-derivable `<task-id>`. The exception therefore costs a route *shape*, never a literal placeholder pair, and it has **no binary-reachable producer today** (the batch path mints every item hop with the same slugify the engine mints ids with, so it cannot address an item it did not just add) — recorded rather than glossed, so a future batch producer is a known trigger instead of a discovery.

**The two dead-end rejects keep their M45 shape.** `write.non-reparseable` / `write.target-escape`: "re-run the same write" is the recovery only when the *payload* is what broke, never when the **staged source** is, so both keep re-run as their first branch and name the escape hatch after it — `jigc task discard <task-id> --force`, the shipped whole-task discard, carried as a fence-checked span with the declared placeholder because the engine holds no task id at this seam (M45 Inc 2). The span carries the **consent** since M50: the state that reaches either reject is one whose task stages a doc, so the bare form would be a route this wave's own guard blocks ([write-commands.md](write-commands.md) → Abandoning a task).

## Scope = effective state

`validate` runs over a scope, and it checks the **effective state**, not committed-only:

- **task** (what `finalize` gates on) — `committed + the task's working deltas + the referential blast radius`. The engine overlays the task's deltas on the committed edge index and runs probes over the prospective merged graph. **Blast-radius is required**: if a task removes a ref target, the now-dangling referrers it didn't directly edit are flagged too (cheap — walk inbound edges), so a task can't commit breakage elsewhere. **The blast radius covers code anchors, not just doc→doc refs (the universal `finalize` floor).** A task that changes code can dangle a `code-anchor` in a **committed** doc it never opened — the symmetric `doc→code` case of "breakage elsewhere". So `finalize` re-resolves every committed `code-anchor` whose **target file is in the task's staged code change-set** (`git diff --cached --name-only`, against the materialized index of [The `doc-code` probe](#the-doc-code-probe-m10) → What the probe reads), and **blocks** on one that *newly* dangles — the same integrity gate as a dangling forward-ref, on the code surface. This is workflow-agnostic: a `quick-fix` task that authors no doc is gated identically, so a lighter workflow cannot opt out of doc↔code integrity. **Two properties make the scoping honest** rather than a sampling shortcut, and both are *implemented*, not merely asserted:

  - **Newly-dangled, not merely dangling — no cross-task false attribution.** A blast anchor blocks only if it **resolved against `HEAD` *and* dangles against the staged index**. The CLI materializes the changed files' `HEAD` versions (`base_code_tree_root`) and the engine re-resolves the blast set against both. So pre-existing drift (a stale committed citation already broken at `HEAD`, e.g. from a prior out-of-band edit) in a file the task merely *touches* is **not** attributed to it — the task is gated only on drift its own change introduced. Without this, scoping-by-file alone would wedge an unrelated task on drift it did not cause, re-introducing the cross-task coupling the integrity/completeness split forbids. (Task-surface anchors — the task's own authored/edited docs — are *not* given this grace: a dangling anchor there is always the task's own integrity to fix.)
  - **Path-local, with named bounds.** The scoping covers the right committed anchors because `code-anchor` resolution is **path-local** — `p#s` is a pure function of `p`'s bytes for every shipped grammar (and the reserved `#kind:name` qualifier stays path-local). Both the anchor path and the change-set are **lexically normalized** before comparison, so a non-canonical anchor (`./src/foo.rs`) does not escape. Two honest bounds: a future **non-local** resolver (imports / re-exports / build config, so changing file B could dangle an anchor into file A) would under-cover — guarded by `path_locality_*` so the model change fails loud rather than leaking; and a tracked **symlink** anchor file breaks path-locality (its bytes are the link, not the target), so the probe emits a `doc-code.symlink-anchor` **advisory** rather than silently following it. The multi-valued-anchor guard for *committed* docs is store-scoped (`jigc validate`), not re-attributed per task — no shipped doctype declares a list-valued `code-anchor`.

  **Cost:** the blast radius enumerates every committed managed doc on a finalize that stages any code (then filters by changed file), plus one extra `doc-code` invocation over the blast set for the base comparison. Acceptable at present store sizes; a persisted `code-path → committed-anchor` index (invalidated with the edge-index/file-state machinery) is the scaling path if a large store makes the per-finalize walk bite — not built speculatively. (Store-scope `jigc validate` stays the un-scoped health check — it re-resolves *all* committed anchors regardless of attribution.)
- **doc** — a single doc and its immediate references.
- **store** — the whole committed state (a health check).

**Integrity vs completeness.** The per-task `finalize` gate blocks only on **integrity the task can fix** — forward-ref resolution, required slots, malformed values. **Completeness obligations** (inverse/minimum-cardinality — "every PRD needs a SPEC") depend on *other* tasks, so they are **advisory by default, surfaced at `store`/milestone scope** (report-only there — the "hard-enforced at store" aspiration was never built; see the severity inventory), never the per-task gate — otherwise legitimate PRD-first / SPEC-later authoring would deadlock. (Severity and scope are cascade-tunable as usual.)

**Forward-ref resolution — the two reachable surfaces.** "Forward-ref resolution" covers refs whose targets sit in *exactly* two places: (a) the **committed store** (already on disk), or (b) the **same task's working area** (created by deltas in the same task — resolved against the working overlay, [storage.md](storage.md) → Edge index lifecycle). A ref whose target is in *neither* — that is, a ref to a doc that doesn't exist anywhere reachable at finalize time — is a **blocking integrity error**. **Cross-task forward-refs are not supported in MVP** (or post-MVP without an explicit provisional-ref feature): a ref to a doc *another* task plans to create cannot be resolved by *this* task's finalize, so it fails. The failure is the design — the deadlock Codex's review walked (T1 authors `supersedes: adr:b` where B will be created in T2) is rejected at its source: the agent never authors a cross-task forward-ref; if it does, finalize blocks. The error message names the three routing options: **(i)** order the tasks so the target exists first (T2 before T1); **(ii)** move the target's creation into this task; **(iii)** drop the ref. No new syntax (no `?` provisional marker), no new state machine — easier to relax later if a real cross-task pattern needs it than to ship speculative grammar now. The integration-advantage's mechanical floor (forward-ref resolution at finalize) holds without exception.

**Fan-out cross-area refs follow the same policy.** A sub-agent in sub-task B authoring a ref into sub-task A's working area (e.g. typing `supersedes: adr:cache` while guessing A's slug) is the *fan-out variant* of the cross-task forward-ref case. Same rule, different surface: each sub-task's outgoing refs are validated at **`join`** against `(committed store ∪ this sub-task's own working area)` only; cross-area refs are rejected as blocking integrity errors ([workflow-dialect.md](workflow-dialect.md) → `fan-out` / `join`). The two surfaces — cross-task at finalize, cross-area at join — close the boundary against the same failure mode with symmetric rules.

> **Enforcement is a *narrowing*, not the existing walk re-pointed (M7).** The join validation entry point is built in M7 ([storage.md](storage.md#the-by-task-id-join-m7)). The danger: forward-ref resolution today keys on **filesystem-path existence** in the task's `docs/`, so once N sub-areas physically coexist on disk, a naïve overlay that unions every sub-area's `docs/` would make a cross-area ref *resolve clean* — silently defeating this rule. So resolution must be scoped **per-`from`**: each outgoing ref resolves only against `committed ∪ the area that authored that `from`*, never the flattened multi-area view. **Mechanism:** the join invokes the existing single-area forward-ref walk **once per sub-area**, passing that area's own `task_dir` — so the narrowing is simply "call per area," sibling areas are never in any single call's surface, and the single-area walk stays authoritative and unchanged. At finalize the sibling areas aren't reachable; at join they are — so this is the one case where the surface must be *actively excluded*, not merely "not added." The check is **intrinsic** (floored at `blocking`, M6 floor machinery — [Severity inventory](#mvp-check-inventory)).

### The milestone-boundary gate (M45)

The two rules above scope **authoring** at the fan-out boundary — which area a sub-task's outgoing refs may resolve against. Neither adjudicates whether the **merged** state conforms, and until M45 nothing did: `milestone finalize` ran no validate at all ([finalize.md](finalize.md) → 2. Validate, where that divergence is recorded against this doc's own *"one engine, two entry points"*). Two classes committed at exit 0, live-reproduced at the M45 baseline — a sub-area doc carrying three blocking conformance findings, and a code-anchor dangling **across** two worktrees, which no per-area check can see by construction ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle, Decision 2). The gate that closes it:

- **Scope — the merged effective state, once.** Not N per-area runs: the by-task-id merged doc set overlaid on the committed store, plus the merged code tree `combine_worktree_trees` returns. This is the [task-scope effective-state model](#scope--effective-state) with *"the task's working deltas"* read as *"the merged sub-areas"* — including its blast radius, which is what reaches the cross-worktree anchor.
- **Families — the per-task gate's, unchanged.** The `schema-conformance.*` presence/value trio + `ref-resolves` over the merged doc set, and the `doc-code` code-anchor re-resolution over the merged code tree. **No new check ids:** a milestone-boundary block is an ordinary blocking finding whose subject happens to be merged state. The `doc-code` arm reads anchors by filesystem path, so the merged *tree SHA* has to become a tree on disk before the probe can see it — the checkout mechanism, its teardown obligation, and its cost are the transaction's, [finalize.md](finalize.md) → 2. Validate.
- **Position and exit — owned by the transaction.** Where the gate sits in `run_milestone_finalize` (and why it is never inside engine `join`), and that it exits through the existing `blocked()` path with a real `ValidationReport`, are [finalize.md](finalize.md) → 2. Validate. Nothing new is minted for it here.

**The subject is every doc the boundary commits — including the transient ones (M49).** The gate's doc set was first written as *the merged docs with a committed home* (`location:`/`placement:`), which is the promote plan's subject, not the boundary's. A fan-out's **`commit:<sub-id>`** docs declare neither home, and under **`squash: false`** each code-carrying sub-task's is rendered into that sub-task's commit message — it is committed bytes, exactly as a task's commit doc is at `jigc task finalize`. So the door-list claim below was **false when it was written**: an author-required leaf left unfilled (`type` and `summary` are the doctype's whole author-required set) blocked `jigc task validate <sub-id>` at exit 3 and landed a `: <subject>` commit through this door at exit 0. The subject now reads *"everything this boundary commits"*: the persisted merged docs **plus** the transient docs the boundary will render into a commit message. The predicate is untouched — the same `validate_task` entry over the same families; only the set it is handed grew.

**The two `squash` modes differ, and the reason is what the boundary reads.** Under **`squash: true`** the aggregate message is CLI-synthesized (*"a milestone has no commit doc to render"*) and **no** commit doc is read at all, so a sub-task's is not part of the committed state and gating it would refuse a milestone whose committed output is entirely correct. Under **`squash: false`** only the **code-carrying** sub-tasks get a commit, so only their commit docs are read. The gate therefore keys its transient subject on the *very set the render uses* (`code_carrying_worktrees`, one producer for both callers) rather than on a parallel derivation — a gate keyed on a different set than the render would either skip a doc that lands or block one that does not. This makes the knob an **input** to the gate rather than something it is independent of: which docs the boundary commits is exactly what the knob decides.

**`jigc milestone join` is not a third conformance door, by design.** It is a report-only pre-check that commits nothing: it runs the engine's by-task-id join — the same-doc clash and the per-sub-area cross-area ref walk — and no conformance pass. Its ref walk *does* see a transient doc's outgoing refs (a sub-task commit's dangling `implements` blocks there and again at finalize), which is why the un-gated class was the presence/value families and not `ref-resolves`.

## Probes

One uniform interface (`check(target, ctx) → [finding]`), two implementations:

- **Engine-native** — built in, in-process. **The MVP ships two:**
  - **`workflow-refs`** (target: workflow) — every `placeholder` / `include` / `command-ref` resolves, no include cycles, no `@` on a scalar-resolving path, no step's instruction prose shadows the composer-reserved `Run: ` / `Spawn: ` / `Checkpoint: ` line-start ([workflow-dialect.md](workflow-dialect.md#emitted-format)), every `fan-out` step has a matching later `join` step (and vice-versa), and workflow bodies contain only `{{include}}` lines / blank lines / HTML comments at top level ([workflow-dialect.md](workflow-dialect.md#on-disk-definition-format)).
  - **`file-state`** (target: file) — the on-disk content hash matches the recorded state; drift → a `reconcile` finding consumed by the reconciliation classifier ([reconciliation.md](reconciliation.md)). With no recorded hash (first run / fresh checkout), the current on-disk content is adopted as the baseline — absent-hash is not drift. **Committed docs only (M43 A14):** a task's *staged working-area copy* is never keyed against the record — a persisted staged instance is reported as the informational `file-state.staged-copy` advisory at its repo-real committed destination (an in-flight edit of a copied-in doc legitimately differs from the committed baseline, so hashing it would mint false drift), and a transient-sink instance (no committed home) yields no `file-state.*` finding at all.

  **Engine-native, full logic in M5:**
  - **`override-default`** (target: override) — per-delta `clean / conflict / orphaned / needs-rebasing` reconciliation, run by `jigc upgrade`. **M5** shipped it via a **bespoke upgrade-time path** (a direct `classify(deltas, pack)` call, not `validate_task`) with **blocking-by-default** hardcoded severities. **M6** moves it onto the **non-task `Probe` seam** ([The non-task `Probe` seam](#the-non-task-probe-seam-m6)) and makes its three checks **cascade-tunable** via the M6 post-pass — it is the seam's first (and this milestone's only) real consumer, the proof the seam is non-hollow. Findings carry a **human-readable `String` route** (not the tagged union below). Full logic in [overrides.md](overrides.md) → Upgrade reconciliation.
- **Pack probes** — **built in M10** (the first one — `doc-code`), still behind the "not a public API yet" line (we compose only our own pack — the **trusted-pack** model). An **invoked subprocess** with a JSON-in / JSON-out contract: language-neutral, **read-only and deterministic by contract** (`doc-code` must parse real code, so it can't be declarative). The development pack's **`doc-code`** (does this symbol/file exist? does a `spec` criterion map to a real test?) lands here; *staleness* — did referenced code change after the doc? — is a stretch deferred past M10 ([Open questions](#open-questions)). **"Deterministic by contract" is locked, not aspirational** — see [Pack-probe determinism contract](#pack-probe-determinism-contract) for the six rules the subprocess implementation satisfies and the four meta-finding modes that surface every misbehavior; M10 enforces the contract + the timeout/crash/malformed-output meta-findings, deferring only **OS-level sandboxing** (seccomp/Landlock) + the `sandbox-violation` meta-finding it backs. The probe spec is [The `doc-code` probe](#the-doc-code-probe-m10) below.

## Pack-probe determinism contract

Pack probes are subprocess invocations behind a JSON-in / JSON-out contract; their findings feed `validate` and `finalize`, so they must satisfy the determinism boundary the engine itself satisfies. **"Deterministic by contract" is locked, not aspirational** — when subprocess probes ship post-MVP, the implementation must satisfy the rules below. Implementation (OS-level sandboxing — seccomp, Landlock, or equivalents) is deferred, but cannot ship without satisfying the contract. Codex's Pass 3 invariant attack is closed by making the rules explicit and forward-binding.

### The six rules

A subprocess pack probe must:

1. **No network access** — no TCP/UDP/Unix sockets to external endpoints. The probe runs against the local repo and its scratch dir; nothing else.
2. **No model calls** — no LLM, local or remote. The engine's no-LLM rule ([VISION.md](../VISION.md) principle #1) extends to its probe interface; a probe that calls a model is an engine-extension that bypasses the determinism boundary.
3. **No time / random reads** — no `time()`, `/dev/urandom`, `random()`, etc. Same input + same repo → same output, always. Deterministic randomness seeded by the probe input (e.g. a hash-derived seed) is allowed.
4. **Read-only filesystem outside scratch** — may read the repo and the cascade-resolved schema; may write only to a probe-supplied scratch dir; the engine cleans the scratch dir between invocations. No persistent state across runs.
5. **Bounded resources** — engine-set CPU-time, memory, and output-size limits. A runaway probe is killed and surfaces as a `timeout` failure.
6. **JSON-in / JSON-out, nothing else** — stdin = JSON request; stdout = JSON findings; stderr = diagnostic logging only (for human debugging). No shelling out to other processes — each shell-out would be a separate determinism review that the contract intentionally precludes.

### The wire contract — request / response

> **M10 reshapes the seam (the "zero engine change" claim was aspirational, not built).** The M6 `Probe` seam shipped only the **non-task** ctx shape (`OverrideCtx { deltas, pack: &dyn PackSource }` — a *live, non-serializable* handle) and a `check(&self, ctx)` signature with **no `target`** ([module-layout.md](../implementation/module-layout.md) → Probe boundary; the M10 planning audit, [DECISIONS.md](../DECISIONS.md) 2026-06-06). So admitting `doc-code` is **not** zero-engine-change: M10 builds the serializable effective-state ctx + a `target` the seam previously lacked. This is real engine work, scoped into M10 — not a free reuse. The paragraph below states the *target* shape the reshape lands on.

The wire shape below was **illustrative**; **M10 concretizes it** (the request/response envelope + the snapshot format), since this is the milestone that ships the first subprocess probe. What makes a subprocess impl consume the *same* logical input as an in-process one is that **`ctx` is effective-state the engine can serialize** — a live graph in-process, its serialized read-only projection + a path-ref out-of-process. A `ctx` defined as a live in-memory handle (what M6 built) forecloses the subprocess path, which is exactly why M10 reshapes it before wiring `doc-code`.

**Effective-state access falls out of the six rules.** A subprocess can hold no live graph handle (no callbacks, rule 6) and reach the engine over no socket (no network, rule 1), so the engine **materializes a read-only effective-state snapshot** in the probe's read scope (rule 4 permits read-only fs) and the request carries a **path-ref** to it. The probe reads the snapshot; it never calls back.

**What the snapshot must carry for `doc-code` (M10).** So increment-cutting doesn't fork on snapshot content, the `doc-code` snapshot itemizes: the **`(target-address, code-anchor-value)` pairs** to adjudicate (enumerated by the engine over the task's effective-state docs — [Target surface](#the-doc-code-probe-m10)), each pair's **check id** (`symbol-exists` vs `criterion-maps-to-test`, so the probe applies the test predicate only to the latter), and the **working-tree root** the anchors resolve against (the code is read directly from the repo per rule 4, not copied into the snapshot). The probe needs no live doc parse — the engine has already extracted the anchor values; the probe's job is purely *resolve `path#symbol` against real code*.

```
request:   { probe_id, target: <address>, effective_state: { snapshot_path }, config: { … }, schema_version }
response:  { findings: [ { target: <address>, severity?, message, route? } ], schema_version }
```

- **`target`** (request and each finding) uses the one address grammar ([structural-grammar.md](structural-grammar.md#addressing)).
- **`severity?`** is advisory and usually omitted — the engine assigns the final severity via the cascade (severity is engine-owned, never baked into a probe). Each finding is the engine's one `finding` shape ([Findings](#findings)).
- **`schema_version`** on both sides is present *as a field* now so the contract can evolve without silently breaking a probe built against an older engine; the *versioning policy* itself is deferred (below).
- **A no-findings adjudication MUST emit `{ findings: [], schema_version }`** — a clean run is an *empty findings array*, never empty stdout. On a zero exit, **empty or unparseable stdout is treated as `malformed-output`** (a blocking meta-finding), not as "no findings": an empty stream is indistinguishable from a probe that silently did nothing, so the contract fails safe rather than masking a non-adjudication. The dev pack's `doc-code` always prints a response; a third-party probe must too.

### Failure semantics — meta-findings

A probe that misbehaves surfaces its failure as a **meta-finding**; the engine never crashes. Every meta-finding is **intrinsic blocking** — a probe that timed out, crashed, returned malformed output, or violated its sandbox can't be trusted to have validated anything, and a missing finding could mask a real integrity error:

| failure | meta-finding |
|---|---|
| **timeout** (probe exceeded the time budget) | `probe-failure { probe, reason: timeout }` |
| **crash** (non-zero exit, no JSON output) | `probe-failure { probe, reason: crash, exit-code }` |
| **malformed JSON output** | `probe-failure { probe, reason: malformed-output, parse-error }` |
| **sandbox violation** (blocked network call, fs write outside scratch, etc.) | `probe-failure { probe, reason: sandbox-violation, detail }` |

The engine surfaces every meta-finding through the same `finding` shape ([Findings](#findings)) — the probe's user-facing failure looks like any other finding to the agent.

### Scope — what M10 enforces vs. defers

**M10 ships the first subprocess pack probe (`doc-code`) and enforces the contract** — the six rules and the **timeout / crash / malformed-output** meta-findings are wired (the severity inventory gains the `pack-probe-integrity.*` category, each intrinsic blocking). What **defers** is **OS-level sandboxing** (seccomp / Landlock / equivalents) and the **`sandbox-violation`** meta-finding it backs — justified by the **trusted-pack** model (the only pack composed is our own; safely running an *untrusted* third-party probe is the post-MVP "not a public API yet" line). The three enforced meta-findings need no OS isolation — they are observable from the subprocess boundary itself: a wall-clock budget the CLI invoker enforces (timeout), a non-zero exit / absent JSON (crash), and an unparseable stdout (malformed-output). The deferred `sandbox-violation` is the one that *requires* OS isolation to detect (a blocked network call, an fs write outside scratch) — hence it travels with the sandboxing implementation. The contract is **satisfied, not waived**: M10 cannot ship `doc-code` without the rules holding and the three meta-findings firing.

Still deferred with the OS-sandboxing implementation: sandbox tech + exact resource limits, and the *versioning policy* over the now-concretized request/response schema.

## The `doc-code` probe (M10)

The development pack's first probe, and the milestone that makes VISION principle #6's headline real: *documentation drift caught deterministically at the task boundary*. It is the adjudicator behind the **`code-anchor`** field type — the first **pack-declared** field type ([document-type-schema.md](document-type-schema.md) → Pack-declared field types). Settled at M10 planning ([DECISIONS.md](../DECISIONS.md) 2026-06-06).

### What it checks

A `code-anchor` is a structured reference from a doc into the codebase. M10 shipped the first two persisted-doctype targets; **M13 adds `arch-doc` as the third** ([architecture-documentation.md](architecture-documentation.md); [roadmap.md](../implementation/roadmap.md) → M13 Increment 5):

- **`adr.cites-code`** (an optional `code-anchor` in the `status` header section) — the **floor**: *does the cited code still exist?*
- **`spec` `criteria/<id>/maps-to-test`** (an optional `code-anchor` in the `criteria` repeatable block) — the **headline**, the VISION worked example (`⚠ SPEC criterion 'limit=100/min' maps to no test`): *does the criterion map to a real test?*
- **`arch-doc` `components/<id>/implemented-by`** (a `code-anchor` in the `components` repeatable block — M13) — the **richest** case: a **per-component `symbol-exists`** anchor, *does the documented component still resolve to its implementing symbol?* ([architecture-documentation.md](architecture-documentation.md) → flow 16.)

Two checks (both blocking-default, tunable — they tune through the [M6 post-pass](#severity-assignment--the-m6-post-pass) for free):

- **`doc-code.symbol-exists`** — the `code-anchor` resolves to a real file (and, if a symbol is named, a real symbol).
- **`doc-code.criterion-maps-to-test`** — the criterion's `maps-to-test` anchor resolves to a real *test* (symbol existence + a test predicate).

**Which check runs (the M13 `check:` predicate selector).** M10 chose the predicate **by position** — a Simple-section anchor got `symbol-exists`, a repeatable-block anchor got `criterion-maps-to-test`. arch-doc broke that coincidence: its repeatable `components/implemented-by` cites *implementation* code and wants `symbol-exists`, so position no longer discriminates. M13 makes the predicate **pack-declared**: the resolution is **`field.check ?? field_type.check`** — a schema field's optional `check:` overrides the field-type's declared `check:`. So bare `code-anchor`s (`adr.cites-code`, `arch-doc.components/implemented-by`) inherit `symbol-exists`, and `spec.criteria/maps-to-test` carries an explicit `check: criterion-maps-to-test` to keep its shipped predicate. The positional constants are deleted ([architecture-documentation.md](architecture-documentation.md) → The per-field-type predicate selector; [document-type-schema.md](document-type-schema.md) → Pack-declared field types).

**`doc-code.title-names-symbol` — the stale-heading guard (design home minted at M40 Settle).** A third check under the `doc-code` namespace, **engine-emitted** (a pure string check at the task gate — no code resolution, not the subprocess probe; it wears the `doc-code.*` id so the floor/hook machinery catches it): on a `code-anchor` field declaring `title-names-symbol: true` (arch-doc `components/implemented-by`), an item title carrying a **compound code-identifier** (a camelCase/PascalCase token) that is *not* the anchored symbol is flagged — the heading still names a renamed/removed symbol (the long-horizon study's observed failure: the agent fixes the anchor and leaves the heading stale). It shipped with the long-horizon-study fix carrying **no inventory row and no `knobs.yaml` key** — a violation of this doc's own "only keyed checks tune" discipline, repaired here. **M40 mints its cascade knob and demotes the default blocking → advisory** ([DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 planning: Settle): the check's known false-positive class — **brand-name compound identifiers** (`WordPress`, `PostgreSQL`) in a legitimately descriptive title — has no valid remedy under blocking (renaming the heading would be *wrong*), which wedges the agent; the knob makes calibration config, not code. Conscious cost, recorded: the long-horizon study re-tested with this check *blocking*; a strict project re-promotes it with one cascade line. The route text names the **minting step** (`jigc start "<intent>"`) followed by **`jigc doc retitle-item`** (M41, V8) — the check fires task-less on the store-scope `jigc validate` surface while `retitle-item` resolves an active task first, so a route naming `retitle-item` *alone* commanded a verb no task-less context could run (observed live in the rc.4 rerun); the earlier route before M40 omitted the retitle verb entirely, commanding a repair no verb could perform.

**M47 — the message states the comparison, never the rename** (surface-contract law 1; the project-alpha-4.0 D3 row). The design *intent* recorded above is a rename the agent forgot to mirror; the **check** is a string scan of the title's compound identifiers against the anchored symbol, reading no git history and resolving no code. Its message nevertheless asserted *"the heading still names a **renamed/removed** symbol; update the title to match the code"* — an event it never observed, on docs whose code never moved, and it sent a trial worker hunting a phantom change. It now names both sides of the comparison it actually made and labels it as one; the route is unchanged apart from dropping the same "stale symbol" framing from its parenthetical.

### The anchor grammar + resolution

A `code-anchor` value is **`<repo-relative-path>#<symbol>`** (e.g. `crates/engine/src/validate.rs#validate_task`) — the shape the codebase's own fixtures already use. A bare `<repo-relative-path>` (no `#symbol`) degrades to a **file-existence** check. `<symbol>` resolves against the file's **named items at any nesting** — top level, inside a `mod` body (incl. the dominant `#[cfg(test)] mod tests`), or as an `impl` method — not top-level items only; matching is over real AST named items, so a name appearing only in a string or comment never false-resolves, and a genuinely-absent symbol still blocks. The **is-a-test** predicate likewise counts a `#[test]`-attributed `fn` at any nesting (the dominant unit-test layout). (Those are the **Rust** named-item / test shapes; `symbol-exists` generalizes to five more languages via a per-language node-kind allowlist — see [Multi-language resolution](#multi-language-resolution-m27) below — while the is-a-test predicate stays Rust-only.)

**M50 — the grammar is stated where the type is named, and the pack is its one home** (RC-m50 → F-1). Until M50 the paragraph above was the *only* place the anchor form was written down: `jigc doc schema adr` printed `cites-code: code-anchor`, the `{{schema:<doctype>}}` authoring projection printed `code-anchor`, `jigc doc set-field --help` never said *anchor*, and the shipped guide named the type once in a sentence about probes — so a blind worker reverse-engineered `path#Symbol` from two rejected writes. The grammar now rides the pack's field-type declaration as an optional **`hint:`** (`config/field-types.yaml`), because the engine cannot state a pack-declared type's value shape — a probe adjudicates it, and the engine ships empty of content — and every surface that names the type renders that one string verbatim: the `doc schema` listing, the `{{schema:}}` projection, and a generated `doc set-field --help`, with the shipped guide stating it in prose. It is presentation only: a field type serializes to its bare spelling, so the `hint:` rides no `schema-hash` and no pinned json key, and `doc schema`'s `contract-version` does not move ([doc-read-surface.md](doc-read-surface.md) → the plain listing's value grammar). The spelling above is this document's normative one; the pack's own is fenced, in both directions, by `crates/cli/tests/code_anchor_grammar_sites.rs`.

**M50 — and a value that is not an anchor says so, instead of being reported as an absent file** (RC-m50 → F-2; the same law-1 class as the two repairs above, at the *file* half of the grammar). The bare-path branch reads the whole literal as a filename, which is right when the literal is one. It is not when the worker typed another tool's address convention — an editor's `file:line`, a compiler's `file:line:col` — over a path that exists: *“`src/pad.ts:5` is absent from the staged index”* is then true of a reading nobody meant and false about the file actually cited, so the finding cannot distinguish a wrong line number from an unsupported scheme. The split is made on **evidence the probe already holds**, exactly as the symbol-side split above is: the value takes the grammar sentence only when a `:`-cut prefix of it *names a file in the root the finding names* — the first such prefix, not the first colon, so a path legitimately carrying a `:` is named whole, and a *file*, not any entry, because the sentence claims one. Where no prefix does, the absence claim is true of every reading and the shipped sentence and repairs stand, un-named by the grammar. **The verdict does not move** — same severity, `code`, `check` and location — and the route carries **no staging clause**, because the cited file is present in the root read. The probe re-declares the grammar token rather than sharing a `const`: it cannot depend on `engine` (its `Cargo.toml` declares an empty `[workspace]` to keep the tree-sitter grammars out of the lock graph), so it joins `code_anchor_grammar_sites.rs`'s site table, which is total in both directions.

Resolution is **static parsing via tree-sitter** (the grammar chosen by file extension) — picked *so that* additional languages are a **fixture-add, not a rewrite**. This is forced by the determinism contract: `cargo test --list` (or any build-driven enumeration) compiles → reads wall-clock, may hit the network on a cold cache, and shells out — violating rules 1/3/5/6. Static parse of the file's AST is deterministic and language-neutral. **M10 shipped and *proved* the Rust grammar** — symbol existence + the **"is-a-test" predicate** (`#[test]`-attributed fn). **M27 cashes in the fixture-add design**, generalizing `symbol-exists` to five more languages (TypeScript, JavaScript, Python, PHP, bash). The generalization is **per-predicate**: `symbol-exists` resolves across all six languages; the **is-a-test predicate (`criterion-maps-to-test`) stays Rust-only** — `#[test]` has no portable cross-language signature (pytest naming, Jest/Vitest calls, PHPUnit attributes all differ), so porting it is a separate per-language predicate, deferred. See [Multi-language resolution](#multi-language-resolution-m27).

**M46 — the non-resolution diagnosis states the comparison, never an absence** (surface-contract law 1; the M47 `title-names-symbol` repair one check over — the same class of lie, at the probe rather than in the engine). A `#symbol` that resolves to none of the units above has **two causes**, and the finding stated only one of them: it said *"`X` is absent from `f` in the staged index"* of a file whose bytes the probe had just parsed and whose **indexed blob carries that name**. That is the closure-framework case — a test registered as a *string argument to a call*, the shape PHP/Pest, TypeScript/vitest and `node:test` share, reproduced on three frameworks by three parties — and every repair the route then offered (`git add` it; re-cite the renamed/moved code; restore the deleted symbol) repairs a change that never happened, so an agent following it **corrupts a correct citation**. The split is made on evidence the probe already holds: the bytes it parsed, under the root the finding names (task scope reads the materialized index, store scope the working tree — *What the probe reads, and when*, below), so *"the text occurs here and declares nothing"* is a fact about that root rather than an inference. The reading is a **raw substring**, deliberately: under a word-boundary reading a name occurring only inside a longer identifier (`burst` inside `burst_rejected`) would take the absence sentence its own bytes contradict, which is the lie the split exists to end. So — text **absent**: the shipped sentence and the shipped rename/restore repairs stand. Text **present**: the message says the name occurs in the file and declares nothing there (a name inside a string, a comment or a framework registration is not a declared unit), and the route leads with the file-only fallback below. The two roots differ by exactly one clause — the staged-index rendering adds *"if a declaration by that name is on disk but unstaged, `git add` it"*, because the probe reads the index and cannot see the working tree; the working-tree rendering has no such gap and does not. **The verdict does not move**: the sanction above (a name living only in a string or a comment must never false-resolve) keeps both cells blocking, with the same `code`, `check`, severity and location. The repair is **probe-side** by decision and by fence — the schema-side alternative would edit `spec`'s `check:` key, which sits inside the frozen `schema-hash`, turning a message repair into an adopter-facing frozen-doctype event ([corpus-migration.md](corpus-migration.md) → the freeze assert).

**The file-only fallback is what that route leads with — and what it buys is stated, because the finding now recommends it.** A bare `<repo-relative-path>` degrades to a file-existence check (above) under **every** predicate, `criterion-maps-to-test` included: the anchor then asserts the file's presence and *not* that a test exists, and — measured on a `maps-to-test` anchor with no `#symbol` — it produces **no finding at all**, since the bare-path branch never reads the check id. Under a check whose *name* promises a test, that is a real bound — so it rides in the route text rather than waiting for an adopter to discover it. **The arm not taken is recorded rather than left as a silence:** the alternative was to mint an advisory on the [`unsupported-language` mould](#multi-language-resolution-m27), surfacing a file-only `maps-to-test` as checked-at-a-coarser-predicate. It is refused on the **rule**, not on cost — that mould's *"an uncheckable citation is surfaced as uncheckable"* is quantified over *no grammar exists*, while a file-only anchor is a citation checked at the coarser predicate its own author chose, so stretching the rule to this cell would be analogy rather than citation. *Re-opening condition:* a trial or adopter reports a criterion whose `maps-to-test` points at a file containing no test, unnoticed at exit 0 — a one-cell add at the probe's bare-path branch, and no new check id, knob or inventory row until then.

**The pack-side caveat that stops the shape being authored at all is owed by the field's resolved `check:`, never a list of step names.** A step soliciting a `maps-to-test` write states that a closure-based framework registers its tests with no named symbol, so the `#<test-fn>` is dropped and the `<path>` given alone. That obligation is **derived** — it falls on every step soliciting a write to a field whose *resolved* predicate (`field.check ?? field_type.check`, the M13 `check:` selector above) is `criterion-maps-to-test` — because stating it as two step names is what failed: M45's rider reached one of the two and the second went unswept for a wave, manufacturing the finding above on exactly the corpora it was written for. `arch-doc`'s `implemented-by` is outside the set **at the predicate**, its resolved check being `symbol-exists`, where a named declaration is the normal case. (`crates/cli/tests/maps_to_test_caveat_fence.rs` derives the owe-set from both shipped packs and is the fence; declared bound: it reads shipped bytes, so a step soliciting the write without naming the field carries no signal to derive from.)

### Multi-language resolution (M27)

M27 generalizes the probe from one grammar to six, closing the **non-Rust silent-pass**: a `#symbol` on a non-`.rs` file used to return *no finding*, so a polyglot citation looked validated when it never was. All multi-language logic stays **probe-internal** — no engine, CLI, or pack-schema change (the `code-anchor` field type, the three code-anchor doctypes, and the wire contract are all language-blind; the grammar deps stay out of the engine/cli lock graph by the probe's detached-workspace invariant). Settled at M27 planning ([DECISIONS.md](../DECISIONS.md) 2026-06-19).

**The dispatch — an extension→grammar map (the generalization of M10's `is_rust_file`).** `.rs`→Rust; `.ts`/`.mts`/`.cts`→TypeScript; `.tsx`→**TSX** (a *distinct* grammar — the plain TypeScript grammar parses JSX with errors); `.js`/`.jsx`/`.mjs`/`.cjs`→JavaScript; `.py`/`.pyi`→Python; `.php`/`.phtml`→PHP; `.sh`/`.bash`→bash. Bash additionally **sniffs the shebang** (`#!…sh`) when a file has no recognized extension — the dominant real-world bash case, and reading only the file's own bytes keeps the static-parse determinism contract intact (no wall-clock, network, or build). **Extension dispatch is tried first; the shebang sniff fires only for a file whose extension maps to no grammar (or has none)** — extension always wins (a `.py` file with a bash shebang is Python). One accepted edge: a `.ts` file that *contains JSX* (non-conventional — `.tsx` is the JSX path) parses with errors under the plain TypeScript grammar and may not resolve all symbols; not worth a heuristic.

**What counts as a citable unit — a per-language allowlist of (node-kind → extractor), NOT the M10 field-driven walk.** M10 resolved any AST node exposing a `name` field; that is safe in Rust (only declarations carry `name`) but **over-matches** in the new grammars — bash `command` nodes, TS `import_specifier`/`variable_declarator`, PHP `simple_parameter`, and Python import statements all carry a `name`, so the field walk would *false-resolve a called-but-never-defined symbol* (the exact rot the probe exists to catch). So `symbol-exists` resolves against a **per-language allowlist of declaration node kinds, at any nesting** — mirroring Rust's any-nesting rule, visibility/export ignored (an internal function is as citable as an exported one). Two **value-position** kinds are the exception: a bare `variable_declarator` and a bare `method_definition` also appear in non-declaration positions (a function-local `let`, an object-literal method), so they are **constrained to a declaration position** rather than matched anywhere — else the over-match the model exists to close re-opens. **M28 generalized the resolution model itself** (the HD1 *addressable-unit* keystone, [ideas/multi-language-doc-code.md](../ideas/multi-language-doc-code.md) → HD1): an allowlist entry is a **node-kind paired with an *extractor* that yields the unit's name**, not a fixed `.name`-field read. The six programming-language grammars keep M10's single `.name`-child read as **one** extractor (behaviorally byte-identical); a grammar with **no `.name`-field declarations** — CSS, whose units are selectors / `@keyframes` / custom properties — supplies its own extractors ([CSS addressable units](#css-addressable-units-m28) below). **(M29 update:** YAML rides this same seam — its units are **mapping keys**, supplied by a YAML extractor ([YAML addressable units](#yaml-addressable-units-m29) below); it is the first language to *ride* the finished seam rather than force it, the proof the keystone generalizes cheaply.**) (M41 update:** **Vue** rides the seam *differently* — a `.vue` single-file component is an HTML-ish **envelope**, not a plain source tree, so its resolution is a **two-part union**: the `<script>`/`<script setup>` blocks are **string-extracted** (a plain scan, **no vendored Vue grammar** — the honest bound) and their symbols resolved under the TS allowlist, **unioned** with a **filename-component unit** ([Vue addressable units](#vue-addressable-units-m41) below); it is the first *envelope* target, and its SFC extract seam is authored **fresh** — no prior extractor covered an envelope format.**)** The address stays `path#name` over the richer unit set, so `symbol-exists` is now *addressable-unit-exists* with the **same check-id, the same `code-anchor` field type, zero schema change**. The allowlist, now with its extractor column:

| language | citable node kinds | extractor → unit name |
|---|---|---|
| Rust | any named item (the M10 field-driven path, unchanged) | read `.name` child |
| TypeScript / TSX | `function_declaration`, `class_declaration`, **`abstract_class_declaration`**, `interface_declaration`, `type_alias_declaration`, `enum_declaration`; `method_definition` *(class-body member only — not object-literal methods)*; `variable_declarator` *(module/export/top-level only — not a function-local `let`/`const`)* | read `.name` child |
| JavaScript / JSX | `function_declaration`, `class_declaration`; `method_definition` *(class-body member only)*; `variable_declarator` *(module/export/top-level only)* | read `.name` child |
| Python | `function_definition`, `class_definition` (methods + nested defs at any nesting — nested defs are idiomatic and citable in Python) | read `.name` child |
| PHP | `function_definition`, `class_declaration` (incl. abstract — an `abstract_modifier` child, same kind), `method_declaration`, `interface_declaration`, `trait_declaration`, `enum_declaration` | read `.name` child |
| bash | `function_definition` **only** — functions-only; non-function bash symbols (variables, aliases) stay unverified, stated so the name doesn't over-promise | read `.name` child |
| CSS *(M28)* | `class_selector`, `id_selector`, `keyframes_statement`; `declaration` *(custom-property only — its `property_name` must start `--`)* | the kind's name child — `class_name` *(under a `class_selector` only — not a `pseudo_class_selector`'s `class_name`)* / `id_name` / `keyframes_name` / `property_name` *(the `--` kept verbatim)*; sigils are already separate grammar tokens, so class/id/keyframe names need no stripping |
| YAML *(M29)* | `block_mapping_pair`, `flow_pair` *(both block- and flow-mapping keys)* | `child_by_field_name("key")`, **stripping a single pair of surrounding matched quotes** (`"web"`/`'web'`→`web` — the deliberate *opposite* of CSS's kept `--`: quotes are not part of the YAML identifier); anchors/aliases/tags/values/sequence-items are never a `key` child, so they never resolve |
| Vue SFC *(M41)* | the **TS allowlist over the string-extracted `<script>`/`<script setup>`** (parsed under the vendored `tree-sitter-typescript`), **unioned** with a **filename-component unit** *(not a grammar node)* | script half: the TS `.name`-child reads over the extracted script text; filename half: `file_stem() == symbol` (the idiomatic `AppLayout.vue` ⇒ `AppLayout` component name — it lives only as a `name:` string / is compiler-inferred, so it is *not* a citable script symbol) — see [Vue addressable units](#vue-addressable-units-m41) below |

(The table is the contract; the exact node-kind set per grammar is build-time-pinned against each grammar's `node-types`, and each new grammar carries the M10 panic-free-on-hostile-input property as its own fixture.)

**Unsupported extensions — a non-blocking advisory, never a silent pass.** A `#symbol` anchor on a present file whose extension (or shebang) maps to **no shipped grammar** — CSS, YAML/docker-compose, anything else — emits a **`doc-code.unsupported-language` advisory** ("anchor not validated — no grammar for `.xyz`"), replacing M10's silent `return None`. **(M28 update:** CSS is no longer un-grammared — it ships an addressable-unit extractor, [CSS addressable units](#css-addressable-units-m28) below, so a `.css#name` anchor now resolves rather than advises; YAML/docker-compose and every other un-grammared extension still take this advisory.**) (M29 update:** YAML is no longer un-grammared either — `.yaml`/`.yml` ship a mapping-key extractor ([YAML addressable units](#yaml-addressable-units-m29) below), so a `.yaml#name` anchor now resolves; every other un-grammared extension still takes this advisory.**) (M41 update:** `.vue` is grammared too — an SFC's extracted `<script>` symbols + its filename component resolve ([Vue addressable units](#vue-addressable-units-m41) below), so a `.vue#name` anchor now resolves rather than advises; every other un-grammared extension still advises.**)** This keeps a polyglot "all clean" honest: an uncheckable citation is surfaced *as uncheckable*, not hidden green. It is a **distinct check-id** (not a severity-demotion of `symbol-exists`), so tuning `symbol-exists` can never accidentally promote it to blocking; it is an **un-keyed informational advisory** (no `knobs.yaml` key, no inventory row — the [informational-outcome](#mvp-check-inventory) precedent), so it adds no tunable surface. (A project that later genuinely needs to *enforce* anchor-checkability can earn a keyed `unsupported-language.severity` then — not built speculatively.)

**`criterion-maps-to-test` on a non-Rust file — the symbol floor blocks, the test-predicate advises.** The is-a-test predicate is Rust-only, but the symbol *underneath* it resolves for the v1 languages — **exactly one finding per anchor**, depending on whether the symbol resolves:

| non-Rust `maps-to-test` | symbol **resolves to no declared unit** | symbol **resolves** |
|---|---|---|
| finding | one **blocking** `doc-code.criterion-maps-to-test` (the `symbol-exists` floor — nothing to advise about a name that declares nothing) | one **advisory** `doc-code.unsupported-language` (the is-a-test half is unverified); the symbol passes |

So a non-Rust test symbol that resolves to nothing never passes silently (it blocks, like `implemented-by`); only the "is it actually a test" assertion is deferred, and only when there is a present symbol to make the assertion about. The advisory never co-fires with the block.

**CSS + docker-compose are parked.** Their addressable units (CSS selectors, compose service keys) are not AST named items in the `path#symbol` sense — they need a distinct resolution semantics, deferred to a follow-on ([decisions-pending.md](../implementation/decisions-pending.md)). Until then they take the `unsupported-language` advisory like any other un-grammared extension. **(M28 update:** CSS shipped — its addressable units are now resolved by the extractor below; **docker-compose stays parked**, still taking the advisory.**) (M29 update:** docker-compose/YAML shipped too — `.yaml`/`.yml` mapping keys resolve via the [YAML addressable units](#yaml-addressable-units-m29) extractor, so a compose service key now validates rather than advises; both parked targets are now grammared.**) (M41 update:** the **Vue SFC** tier-1 slice of the [multi-language north-star](../ideas/multi-language-doc-code.md) shipped too — but *not* from this CSS/compose parked pair: its SFC extract seam is authored **fresh** (no prior HD tier covered an envelope format), resolving `.vue` script symbols + the filename component ([Vue addressable units](#vue-addressable-units-m41) below).**)**

#### CSS addressable units (M28)

M28 ships the **first breadth target** of the [multi-language north-star](../ideas/multi-language-doc-code.md) and proves the **HD1 addressable-unit keystone** on the most-different model: CSS has **no `.name`-field declarations**. A CSS `code-anchor` (`styles.css#btn`) resolves through the same `symbol-exists` check-id, the same `code-anchor` field type, and the same `path#name` address — the probe just gains a CSS extractor; **probe-internal, zero engine/CLI/pack-schema change**. Settled at M28 planning ([DECISIONS.md](../DECISIONS.md) 2026-06-20).

**The addressable units** = **class** / **id** / **`@keyframes`** / **custom-property** names. Selector sigils are already separate grammar tokens (a `class_selector`'s `class_name`.text is `"btn"`, not `".btn"`), so class/id/keyframe names need **no stripping**; a custom property **keeps its `--`** (`--color`→`#--color`) — the `--` is genuinely part of the CSS identifier (`var(--color)`), unlike the `.`/`#` sigils, and keeping it stays collision-safe (`.color`→`#color` and `--color`→`#--color` stay distinct). **Compound / chained / `@media`-nested selectors contribute all their class/id names** (`.card > .title` → both `card` and `title`), via the existing full-tree walk.

**Two over-match closures** (the M27 over-match shape — a `name`-bearing non-declaration node *false-passing* a citation, the exact rot the probe exists to catch): a pseudo-class (`:hover`, `:root`) parses as `pseudo_class_selector > class_name` — the *same* `class_name` kind a real `.class` uses — so the class extractor **parent-constrains** `class_name` to a `class_selector` child; and `--color: red` and `color: red` both parse as `declaration > property_name`, so the custom-property extractor **gates on `starts_with("--")`** (else every property — `color`/`display`/`margin` — false-resolves). This is why the extractor model is *node-kind + predicate*, not pure node-kind.

**Honest bounds the milestone originates** (HD1 is silent on these — CSS-specific):

- **Intentionally-unverified selectors.** Element/type (`div`), attribute (`[data-x]`), universal (`*`), and pseudo-class/pseudo-element selectors are **not** addressable units — either uncitable by intent or the over-match traps above; `@font-face` is an anonymous at-rule (nothing to cite).
- **`@import`ed stylesheets are not followed.** Single-file parse: a class living in an imported sheet **blocks**, by design — the same rule as Rust not following `use`. Cite the file that *defines* the unit.
- **Class / id / `@keyframes` names collide under existence-only `path#name`.** A class `.x`, an id `#x`, and a `@keyframes x` all resolve as `x` — the four arms feed **one flat name set** matched by equality, so a citation cannot distinguish them. A custom property stays distinct because it keeps its `--` (`--x` ≠ `x`). The typed `#kind:name` qualifier stays the **HD1-deferred escape hatch**, built only when real ambiguity bites.
- **One representative class per component.** `arch-doc.implemented-by` is a bare scalar `code-anchor` and the engine blocks list-valued anchors, so a multi-class component (`.card`/`.card--active`/`.card__title`) cites **one** representative class; multi-class-per-component is deferred engine work (a `0..*` code-anchor with list-element enumeration), **not** an M28 schema knob.
- **is-a-test is N/A.** CSS has no tests, so only `symbol-exists` (`implemented-by` / `cites-code`) applies — the `criterion-maps-to-test` predicate is never invoked on a CSS anchor.

#### YAML addressable units (M29)

M29 ships the **second breadth target** of the [multi-language north-star](../ideas/multi-language-doc-code.md) and is the **inverse of M28's reframe**: M28 *forced and built* the HD1 per-grammar extractor seam; M29 is the first language that **rides** the finished seam, so it is the proof the keystone *generalizes cheaply* — "support language N = one uniform move (define N's addressable units), not N special cases." A YAML `code-anchor` (`compose.yaml#web`) resolves through the same `symbol-exists` check-id, the same `code-anchor` field type, and the same `path#name` address — the probe just gains a YAML extractor; **probe-internal, zero engine/CLI/pack-schema change**. Settled at M29 planning ([DECISIONS.md](../DECISIONS.md) 2026-06-20).

**The addressable units** = **mapping keys** — both **block** (`block_mapping_pair`) and **flow** (`flow_pair`) mappings, at **any nesting** via the existing full-tree walk (`services: → web: → build: → context:` all resolve). A docker-compose service `web` is a mapping key under `services:`. Surrounding matched quotes are **stripped** (`"web":`/`'web':`→`#web`) — the deliberate **opposite of M28's kept `--`**: quotes are *not* part of the YAML identifier (`"web"` and `web` are the same key), whereas CSS's `--` genuinely is part of the identifier.

**The citable-node rule — the over-match census** (the M27/M28 over-match shape, plus two YAML-novel failure modes M28's gates do not cover): the rule is **admit a name iff `node.kind()` ∈ {`block_mapping_pair`, `flow_pair`}, take `child_by_field_name("key")`, strip a single pair of surrounding matched quotes.** The `[key]`-field constraint is the YAML analogue of CSS's `class_name`-under-`class_selector` parent-constraint — it **structurally excludes** every over-match negative: an **anchor** `&web`, an **alias** `*web`, a **tag** `!!str web`, a mapping **value** `WEB_HOST: web`, a **sequence item** `- web`, and `#`-comment text all live under the `[value]` field or as sequence children, never `[key]`. The two YAML-novel modes (false-*block*, not false-*pass*): **(B1)** flow mappings need a second arm — `{web: …}` parses as `flow_pair`, *not* `block_mapping_pair`; a single-arm extractor would silently drop flow-map keys and **false-block a valid anchor** (under-match); **(B2)** the `[key]` field returns the raw source span *including quotes*, so a quoted key needs stripping or it won't match `#web` (CSS's first-child-by-*kind* `css_child_text` is the wrong helper — the read is by *field* + quote-normalization).

**Honest bounds the milestone originates** (HD1 is silent on these — YAML-specific):

- **Flat-namespace collision — sharper than CSS's.** Generic keys (`image`, `ports`, `build`, `environment`) recur under *every* service, so `compose.yaml#image` resolves **trivially-true**; and a service key `web` is indistinguishable from a same-named key at *any other path*. Existence-only `path#name` cannot disambiguate by path. The typed `#kind:name` / **key-path `#services.web` qualifier** stays the deferred escape hatch, built only when a real citation must disambiguate a mapping key from a same-named key at a different path.
- **Compose-schema-blind.** The probe has **zero docker-compose knowledge** — `compose.yaml#web` means "a YAML key named `web` exists," **not** "a compose *service* named `web`." `grammar_for` is purely extension-keyed (`.yaml`/`.yml`, no `compose.yaml`/`docker-compose.yml` filename special-casing), so M29 resolves `#name` on **any** YAML (k8s manifests, GitHub Actions, app config), broader than docker-compose — the name must not over-promise.
- **Quote-strip bound.** The strip removes only the *surrounding* matched quotes — internal YAML escapes (`"a\"b"`, `'a''b'`) and decorated/complex/anchored keys (`? [a,b]`, `&k web:`) are **not** normalized and resolve only against their raw inner span (rare for compose keys; the same `#kind:name`/key-path qualifier is the deferred escape hatch).
- **Merge-key `<<` admitted-harmless.** A merge `<<: *anchor` parses as an ordinary `block_mapping_pair` whose `[key]` is the scalar `<<`, so the rule admits `<<` (only the aliased *value* `*anchor` is excluded). `compose.yaml#<<` is never a real citation; filtering it would be code for nothing, so it is left as-is.
- **Single-file parse.** No `extends:`/`!include`/cross-file anchors are followed — cite the file that *defines* the key (the Rust-`use` / CSS-`@import` rule). A multi-document `---` stream resolves **all** documents' keys.
- **One service key per component.** `arch-doc.implemented-by` is a bare scalar `code-anchor` and the engine **blocks list-valued anchors**, so a deployment component citing several services cites **one** representative service key; multi-service-per-component is deferred engine work (a `0..*` code-anchor with list-element enumeration), enforced-blocked (not silent), **not** an M29 schema knob.
- **is-a-test is N/A.** YAML has no tests, so only `symbol-exists` (`implemented-by` / `cites-code`) applies — the `criterion-maps-to-test` predicate is never invoked on a YAML anchor.

#### Vue addressable units (M41)

M41 ships the **tier-1 SFC slice** of the [multi-language north-star](../ideas/multi-language-doc-code.md) and is the seam's **first *envelope* target**: unlike CSS/YAML — plain source trees with a single vendored grammar and a pure extractor — a `.vue` **single-file component** is an HTML-ish envelope wrapping a `<script>`/`<script setup>` block, a `<template>`, and `<style>` blocks. So its resolution is authored **fresh** (no existing HD tier covered an envelope format — [decisions-pending.md](../implementation/decisions-pending.md) → the rc.5 wave, Settle fork 3): a **two-part union** rather than a pure per-grammar extractor. A Vue `code-anchor` (`AppLayout.vue#AppLayout`) resolves through the same `symbol-exists` check-id, the same `code-anchor` field type, and the same `path#name` address — **probe-internal, zero engine/CLI/pack-schema change**. The tier-1 trigger fired at the rc.4 rerun trial (9 symbol-blind `.vue` `implemented-by` anchors finalized clean); settled at M41 planning ([DECISIONS.md](../DECISIONS.md) 2026-07-11).

**The addressable units** = the **union** of two sources ([`symbol_exists_vue`](../crates/cli/probes/doc-code/src/resolve.rs)):

- **Script symbols** — the `<script>` / `<script setup>` block text is **extracted** and parsed under the **vendored `tree-sitter-typescript`** grammar, resolving `#symbol` against the **TS allowlist verbatim** (`function`/`class`/`interface`/`type`/`enum` declarations, class-body methods, module-level `variable_declarator`s — the M27 TS rule). Resolution is **existence-only** — a symbol *exists* in the script or it does not; the extracted-block offsets are irrelevant (the extract discards position, so no finding ever carries a line).
- **The filename-component unit** — a `.vue` whose **`file_stem()` equals the symbol** resolves (`AppLayout.vue#AppLayout`). The idiomatic SFC component name lives only as a `name:` *string* or is compiler-inferred from the filename, so it is **not** a citable script declaration; the filename unit is the addressable handle for it. This unit is **not a grammar node** — it is a filename equality, unioned in beside the script symbols.

**The extract seam — a string-scan, not an HTML/Vue parse (the honest bound).** There is **no vendored Vue grammar**; `extract_vue_script` is a plain, panic-free **string scan** that concatenates the inner text of every `<script …>…</script>` block (both plain `<script>` and `<script setup>`, in source order). A truncated / absent block is skipped, so empty or hostile input yields an empty extracted script and the script half resolves `false` without a crash (the M27 panic-free-on-hostile-input property, carried). Tag matching is ASCII-case-insensitive over ASCII delimiters, so every slice lands on a UTF-8 boundary and non-ASCII script bodies pass through untouched.

**Explicit exclusions — what is *not* an addressable unit** (stated so the scope line does not over-promise): **template refs** (`ref="foo"`, `<template>` bindings), **scoped-`<style>` classes** (`.btn` in a `<style scoped>`), and **SFC compiler macros** (`defineProps`, `defineEmits`, `defineExpose`, `withDefaults`) are **not** addressable. Template refs and style classes live outside the `<script>` block, so the extract never sees them; SFC macros are compiler intrinsics, not declared symbols the TS allowlist admits. The scope line is therefore **script declarations + the filename component**, nothing else.

**Honest bounds the milestone originates** (envelope-specific — HD1/HD2 are silent on these):

- **Script-language-blind — resolved under TS only.** The extracted `<script>` is always parsed under `tree-sitter-typescript`, regardless of a `lang="ts"` / `lang="js"` attribute. TS is a superset of JS for the allowlist's declaration kinds, so a plain-JS SFC still resolves; a `lang="jsx"`/`lang="tsx"` script containing JSX may parse with errors under the plain TS grammar (the same accepted edge as a `.ts` file containing JSX, [the dispatch](#multi-language-resolution-m27)). No per-`lang` dispatch is built until a real SFC needs it.
- **The filename unit resolves trivially for any `file_stem` match.** `AppLayout.vue#AppLayout` resolves purely because the stem equals the symbol — even if the component were renamed internally. This is intentional (the SFC component name *is* the filename by convention); the honest ceiling is "a file by this name exists and its stem matches," not "a component symbol named `X` is declared."
- **Single-block-envelope parse only.** Only literal `<script>` blocks are extracted — no template-compilation, no `<script>`-`src=` external file following (the Rust-`use` / CSS-`@import` single-file rule), no macro-hoisted binding synthesis. Cite the symbol the SFC's own script *declares*, or the filename component.
- **is-a-test is N/A.** Vue SFCs are components, not tests, so only `symbol-exists` (`implemented-by` / `cites-code`) applies — `criterion-maps-to-test` is never invoked on a `.vue` anchor.

**Reserved address syntax — the `#kind:name` qualifier (deferred; the `:` namespace is reserved now).** The `path#name` address resolves "any addressable unit named `name`" across a **flat namespace**, so the CSS class/id/`@keyframes` collision and the YAML same-name-at-any-path collision (both above) are by design. The typed `path#kind:name` disambiguation qualifier that would close them stays **deferred** — built only when a real citation resolves to the *wrong* unit, not merely *could* ([DECISIONS.md](../DECISIONS.md) 2026-06-20, dogfood-informed: the collision is real structurally but did not bite real authoring). To keep deferring free, the **`:` character in a code-anchor fragment is reserved for that qualifier now**: no shipped grammar's extractor emits a unit name containing `:`, so `#kind:name` remains an unambiguous future namespace rather than a current symbol meaning. The reservation is **guarded by a probe test** (`crates/cli/probes/doc-code/src/resolve.rs` → `no_extractor_yields_a_colon_bearing_unit_name`) that asserts every shipped grammar's addressable-unit extractor is `:`-free over its representative fixture — so a future grammar that emitted a `:`-bearing unit name trips the guard and forces a conscious decision instead of silently colliding with the reserve.

**What the probe reads, and when.** The probe runs at **`validate` / `finalize`** time and resolves a doc's anchors against a **code tree root**. Since the M30 change-set narrowing, per-task `finalize` commits the **git index** (the agent-staged code), not a working-tree sweep — so at task/finalize scope `self.validate()` **materializes the current index** into a temp tree and the probe reads **that materialized index**: exactly the bytes about to be committed (the "anchor resolved at compose but code changed before finalize" risk is still closed by construction, and a cited symbol the agent wrote but forgot to `git add` is now *caught* — it is absent from the index, so the citation dangles and `finalize` blocks). The store-scope sweep ([Store-scope re-validation](#store-scope-re-validation--jigc-validate-m18) below) keeps its root at the on-disk working tree — it is task-less, with no index to commit. Either way the probe combines doc + code — a combination no engine-native probe performs. ([finalize.md](finalize.md) → Dirty-tree policy; [DECISIONS.md](../DECISIONS.md) 2026-06-20 → M30 Increment 3.)

**The finding must name the root it read, and route to `git add` (M42).** The two roots above are **correct by design** — task scope reads the materialized index, store scope reads the working tree — and that asymmetry is not the defect. The defect is that the finding says neither. On the dominant case the two roots disagree about (a file **present on disk, never `git add`ed**), the task-scope finding's *message* is **factually false** — *"anchor `X` resolves to no file (`f` is absent from the working tree)"* (`crates/cli/probes/doc-code/src/main.rs:146-154`) — when the file is sitting right there in the working tree; and its hardcoded *route* — *"update the citation to match the renamed/moved code, or restore the cited symbol (e.g. revert the change)"* (`:253-271`) — commands **both of the wrong repairs**: the citation is correct and the code is correct, and the only correct action is **`git add`**. An agent that follows this route as written **corrupts a correct citation**. M42 repairs both halves: the message names the **staged index** as the root it read, and the route names **`git add`** for the present-but-unstaged case (the store-scope rendering names the working tree, so a reader can always tell which generation produced the verdict). This is the route floor's *quality* sibling — a route that names a repair which makes the doc *worse* is not a route, and the [floor](#the-route-floor) counts it as one.

**Target surface — task scope (the M10 wiring).** A `code-anchor` is **a probe-checked field, not an edge** ([doctype-map.md](../implementation/doctype-map.md)), so it is **not in the edge index** and the [blast-radius walk](#scope--effective-state) (which walks *inbound edges*) cannot reach a citing doc from changed code. `doc-code` therefore **enumerates `code-anchor` leaves directly over the task's effective-state docs** — the docs the task **created or edited** (working deltas) ∪ the docs **bound into the task's read roles** — and resolves each against the materialized index (the code tree root above). This is what makes both M10 targets reachable at task scope: the headline `spec` is a **bound** read-role doc; the floor `adr` is **created in-task** (a working delta) via the create-gate (flow 13). A *store-wide* audit — every committed doc's anchors with no task open — is the **M18 store-scope re-validation** ([Store-scope re-validation](#store-scope-re-validation--jigc-validate-m18) below), genuinely new machinery (a read-only committed-store walk), explicitly **not** in M10's slice. The per-task gate blocks only on **anchors the task's own effective state carries** (integrity the task can fix), never on pre-existing drift in unrelated committed docs.

### Store-scope re-validation — `jigc validate` (M18)

**The family set's code-side home is `engine::validate::STORE_FAMILIES` (M51).** The sections below are the taxonomy's *history* — each family stated where it landed, under the arrival-order ordinal it earned (*the fourth family*, *the fifth family*) — and history is not a set: the numbering had drifted (the sweep body labelled inverse-cardinality *Family 5* while this doc calls schema-conformance *the fifth family*), and nothing carried the whole list. `jigc validate --help` is where that cost landed — it named **one** family, doc↔code, and called it the verb, so the door under-stated its own report by six. The registry now carries the set in **sweep order with no ordinal at all**, the help is *generated* from it (`crates/cli/tests/help_truth.rs` compares the emitted bytes to the registry as an ordered equality), and a family added to the sweep reaches the door by joining the registry. The CLI-side advisories the verb appends after the engine sweep — store provenance (`store-version.binary-mismatch`) and the two orphan-strand tiers — are not content families and are not registry members; the strand walk is named inside the file↔CLI-state member's clause, which is where an agent reading the help meets it.

M10's task gate keeps a doc honest *at authoring time* — but a committed doc's anchor whose symbol the code later renames is caught **only** on deliberate re-author, never at an unrelated `finalize`, on doc-drift/absorb, or by any standing sweep. So a committed doc **silently rots** under moving code. M18 closes that gap: a **store-wide, on-demand, read-only** re-validation that re-checks every committed doc's `code-anchor` fields against current code — the passive over-time detector VISION principle #6's "living documentation that stays honest against the code" needs. Settled at M18 planning ([DECISIONS.md](../DECISIONS.md) 2026-06-13).

**The command.** A new top-level **`jigc validate`** — the realization of VISION's named-but-unbuilt `Validate loop` ([VISION.md](../VISION.md) → Primary flows, `jigc validate [target]` "across all four targets"). M18 builds it **scoped to doc↔code over the committed store**; the rest of the four-target breadth stays a **named-but-unbuilt envelope** the command grows into — **M20 completes two more targets** (workflow↔refs + read-only file↔CLI-state; [Completing the envelope](#completing-the-envelope--workflowrefs--read-only-filecli-state-m20) below), and **override↔default is consciously excluded** (it checks *recorded config deltas against the pack*, not the committed doc store — folding a config-cascade check into a doc-store sweep is a category mismatch; its home stays `jigc upgrade`). It is **task-less by construction** — there is no working area, so it does *not* hang off the `task` verb.

**Scope of the sweep.** Every committed doc of every active schema that carries a `code-anchor` field — today the three code-anchor doctypes, all of them `location:` doctypes: `adr.cites-code` (`decisions/`), `arch-doc.components/<id>/implemented-by` (`architecture/`), and `spec.criteria/<id>/maps-to-test` (`specs/`). Repeatable sections are walked **per item** (every component of every arch-doc, every criterion of every spec). Each anchor resolves through the same `field.check ?? field_type.check` predicate selector as the task gate, so `symbol-exists` and `criterion-maps-to-test` apply unchanged. (The store walk claims a location's files by `location:`, so it assumes **one doctype per location** — true today; a future pack sharing a `location:` across doctypes would need the walk to disambiguate by parsed type.)

**"Every active schema" includes the placement class (M42; landed Inc 2 T3).** As built the walk keyed on `schema.location` alone, so a **placement** doctype ([storage.md](storage.md) → Placement — `location: None`, homed at a literal `VISION.md`/`CHANGELOG.md`/`docs/roadmap.md`) dropped through the *transient* arm and contributed zero anchors: the family would report a **clean store over anchors it never read**. **Latent, not live** — no shipped placement doctype declares a `code-anchor` — but the hole opened on a *bare schema edit* (no version gate, no migration), so it is closed rather than recorded: a placement doctype's single committed instance is enumerated at its literal home through the shared placement-aware `index::committed_instances`, addressed by the fixed `<type>:<type>` singleton identity, and the shared projection carries the **multi-valued non-silent guard** to it unchanged ([storage.md](storage.md) → The census, where the site is recorded). The located glob deliberately keeps its own `read_dir` walk — it *propagates* a directory-read error where the shared enumerator swallows it, and an unreadable managed location must be loud, never a clean-looking empty.

**Mechanism — reuse below the enumeration, net-new at it.** The sweep reuses the proven spine wholesale: the lifted doc→anchor projection (`collect_from_source`), the serializable effective-state snapshot, the subprocess `doc-code` invoker, and finding ingestion. What is **new** is a **read-only committed-store enumeration**: its own deterministic, address-sorted walk of `<repo-root>/<location>/*.md` per schema, parsing each doc and collecting its `code-anchor` leaves. This walk **must not route through `reconcile_committed_store`** — that path mutates the file-state record and edge index (it re-baselines drifted-clean docs via *absorb*, keyed off a `task_dir` that a task-less sweep lacks), so reusing it would *silently re-baseline genuine drift* the sweep exists to surface. The store sweep opens **no `FileStateRecord` write**; it is pure read.

> **"Committed store" = the managed docs on disk under their `location:` dirs (the working tree), not git HEAD.** The walk globs `<repo-root>/<location>/*.md` off the filesystem — consistent with the engine's *files-are-truth* model and the `doc-code` probe, which resolves anchors against **working-tree** code ([What the probe reads](#the-doc-code-probe-m10)). So a just-authored, not-yet-committed doc under a `location:` is swept too, and it is checked against the *same* working-tree code the probe reads — the doc and the code it cites are always the same generation, never a HEAD-doc-vs-working-code mismatch. "Committed" here means *the persisted store as it exists on disk*, the unit a human reviews in a diff — not a `git` revision.

**Severity — report-only, with one exit-code exception (probe-integrity).** The sweep **detects and reports content drift; it never gates a transaction.** There is no task transaction to block, so a **content finding** — a stale `doc-code.symbol-exists` / `criterion-maps-to-test` anchor, *whatever its cascade severity* — is *listed*, and on a content-only run the command exits **0** (the `jigc ingest` detect-and-report precedent, not the exit-3 `task validate`/`finalize` gate). This keeps the load-bearing invariant intact *by construction*: "integrity holds at a `finalize`/commit boundary, not on every write" ([CLAUDE.md](../CLAUDE.md)) is untouched because `jigc validate` is a **read command, not a write path**.

**The one exception — the probe didn't run.** The `pack-probe-integrity.*` meta-findings (timeout / crash / malformed-output, [Failure semantics](#failure-semantics--meta-findings)) are **intrinsic-blocking and not cascade-tunable** for a load-bearing reason: a probe that crashed *cannot be trusted to have validated anything*, and a missing finding could mask real drift. So they are **not** content findings, and "exit 0" must **not** swallow them — a `doc-code` crash partway through a 40-doc sweep that still exits 0 would report a clean store the probe never checked. Rule: **if any `pack-probe-integrity.*` meta-finding is present, `jigc validate` exits non-zero** (the sweep could not produce a trustworthy result); a run with only content findings (or none) exits 0. This is the `ingest` precedent's one gap — `ingest` never invokes a probe, so it never had to distinguish a routed *content* finding from a probe that *failed to execute*. (Note: this is still **not** a transaction gate — it is the command honestly reporting it could not complete, not blocking a write.)

The report-only stance also inverts the masking-trap guard: at task scope the engine *deliberately excludes* unrelated committed docs (so a task can't be blocked by pre-existing drift it didn't cause — [the join narrowing](#scope--effective-state)); at store scope surfacing exactly that pre-existing drift across the whole store **is the command's entire purpose**. The inversion is intentional — a future reader must not "fix" the store walk to honor the task-gate exclusion. The guard lives in the task-scope *surface selection* (`enumerate_target_surface`), not in the per-doc anchor projection the store walk lifts, so store scope cannot weaken the task gate.

**Honest bounds — named, not papered over.** A perfect store sweep still covers only *half* of "honest against the code":

- **Structural drift only, never behavioral.** `symbol-exists` knows a symbol *exists*, not that the prose still *describes what the code does*. A renamed/deleted/moved symbol is caught; a component whose description has gone stale while its `implemented-by` symbol still exists is **not**. The sweep's claim is bounded to structural anchor drift.
- **Non-Rust `#symbol` resolves for supported languages; the rest advise (M27).** The `doc-code` probe resolves symbols for Rust + TypeScript/JavaScript/Python/PHP/bash (**M28** adds **CSS** — the first non-`.name`-field grammar, resolving selector / `@keyframes` / custom-property units, [CSS addressable units](#css-addressable-units-m28); **M29** adds **YAML** — mapping keys, the first language to ride the finished seam, [YAML addressable units](#yaml-addressable-units-m29); **M41** adds **Vue** — the SFC `<script>` symbols + the filename component, the first *envelope* target, [Vue addressable units](#vue-addressable-units-m41)); a `#symbol` anchor into a file of any *other* language no longer silently passes — it emits a non-blocking `doc-code.unsupported-language` advisory ([Multi-language resolution](#multi-language-resolution-m27)). So a store-wide "all clean" over a polyglot repo is now meaningful for the supported languages and *honestly flags* uncheckable citations for the rest, rather than hiding them green. (The `criterion-maps-to-test` is-a-test predicate stays Rust-only — a non-Rust test anchor blocks on a symbol that resolves to no declared unit but advises on the test-predicate.)
- **Multi-valued anchors get a non-silent guard.** No shipped `code-anchor` field is list-valued, so M18 builds **no** list-element enumeration (generality for a non-existent case). But the existing enumerator *silently drops* a list-valued anchor — which at store scope would be a false "all clear." M18 replaces the silent drop with a **loud guard finding** so a future `0..*` code-anchor can never pass unchecked-but-green.

**Distribution bound.** The command's whole job is to invoke the `doc-code` probe, which today is placed beside `jigc` in a **build tree / local release** but is **not** shipped by `cargo install` ([decisions-pending.md](../implementation/decisions-pending.md)). M18 targets that build-tree/local path (where the probe sits beside `jigc`); the `cargo install` embed-and-extract fix stays on its existing trigger, unfired. **The sweep pre-flights probe presence:** if the `doc-code` binary is not resolvable beside `jigc` (or via `JIGC_DOC_CODE_PROBE`), `jigc validate` exits non-zero with **one** operational error ("`doc-code` probe not found"), rather than emitting a `crash` meta-finding per anchor — a missing probe is a misconfiguration to report once, not N findings (and, with the exit rule above, never a falsely-green run).

**Auto-firing the sweep (M19).** The report-only stance is precisely what lets `jigc validate` be **fired automatically** without violating any boundary: M19 installs an assistant-neutral **warn-only git `pre-commit` hook** (via `jigc setup`) that runs the sweep on every commit, so committed-doc drift surfaces with no agent action ([assistant-adapter.md](assistant-adapter.md) → neutral install; [finalize.md](finalize.md) → 6. Commit). Because content findings exit 0, the hook only *warns* — it never blocks a commit, so it cannot re-introduce the masking-trap or gate `finalize`. A hook *driven by the exit code* would be wrong-way-round (operational-error and probe-integrity both exit non-zero while *found drift* exits 0), so the warn-only hook surfaces the report and always exits 0; the agent acts on the warning (it reaches them via finalize's success-relay of hook output). **M47 re-keys *what* warns onto severity:** the hook matches the store envelope's top-level **`blocking_probes`** array ([command-output-contract.md](command-output-contract.md) → The store sweep's envelope) instead of grepping the report for a `doc-code` finding at *any* severity — so an **advisory-only** `doc-code` finding (the stale-heading guard; a citation the probe cannot check) stops warning on every commit forever, while a **blocking** one still does. It is also the only shape a shell can bind soundly: a flat array of plain strings is a `]`-delimited region, so the match is bounded by the array's own `]` and structurally cannot reach into `findings`, where a finding-object grep had to bind a key to a member across nested `{}`.

### Completing the envelope — workflow↔refs + read-only file↔CLI-state (M20)

M18/M19 built the doc↔code target and its auto-fire. M20 completes the store-scope envelope to **three** targets — adding **workflow↔refs** and a **read-only file↔CLI-state** sweep — so `jigc validate` is the one read-only surface that re-checks every kind of *structural* integrity the store can carry. **override↔default is deliberately not a fourth target** (above): it operates on recorded config deltas against the pack, has no committed doc to walk, and already sweeps all deltas at `jigc upgrade`. Settled at M20 planning ([DECISIONS.md](../DECISIONS.md) 2026-06-14).

**workflow↔refs at store scope — the pack's own referential integrity.** Today `workflow-refs` fires only at `jigc start` compose-time, over the *one* workflow being composed (with task data in hand). The store-scope target is the **task-less** complement: a deterministic, address-sorted enumeration of **every workflow definition the resolved cascade provides** (`project > team > pack-default`), checking each definition's **task-independent referential integrity** against the current pack. This catches the workflow-side analogue of doc rot: a step file or command removed under a workflow that still includes/refers to it.

**Scope pin — the exact check set, and why command-refs are membership-only (the load-bearing line).** The store sweep runs only the checks that are *well-defined with no task in hand*: `include-resolves`, `include-cycle-absent`, `body-include-only`, the three composer-reserved marker-shadow checks (`run-` / `spawn-` / `checkpoint-marker-not-shadowed`), and `fan-out-join-paired`. The **task-data-dependent** checks — `placeholder-resolves` over `{{task.*}}`, `at-marker-on-non-scalar` — are inherently compose-time (there *is* no task at store scope) and **stay at `jigc start`**. The subtle one is **`command-ref-resolves`: at store scope it checks *catalog membership only*** (`catalog.get(id)` succeeds), **not** command-arg resolution — because resolving a command's args runs them against the context, and the dev pack's command catalog gives nearly every command-ref a `task.*` arg, so a task-less full resolution would emit `task-ref-in-no-task-workflow` for essentially every command-ref: **fabricated drift, not real**. So the store target needs a **membership-only command-ref path** (catalog `get` without `render_command`) — a small net-new code path, not a reuse of the compose-time `command-ref-resolves`. The remaining check logic is reused per-definition; the **net-new work is the store-wide enumeration + per-def driver + the membership-only command-ref path** (no task minted), none of which exists today (the only callers of `workflow_refs` are `jigc start`). **M43 adds `schema-ref-resolves` to the store set** — each lone `{{schema:<doctype>}}` generation-seam ref checked by membership against the **composed cascade's** doctype set, deliberately *not* the per-origin scope the command-ref path resolves against: a methodology step legitimately solicits a dev doctype ([surface-contract.md](surface-contract.md#the-schema-projection-law-1) — the composition model, not per-origin doctype scoping). Membership-only like the command-ref path (no rendering, no task), and the same check id fires at compose ([workflow-dialect.md](workflow-dialect.md) owns the grammar row).

**read-only file↔CLI-state at store scope — detect, never absorb.** A sweep that compares each committed managed doc's on-disk content hash to its recorded `FileStateRecord` and **reports drift** (`file-state.hash-matches`), opening **no record write**. It **must not route through `reconcile_committed_store`** — the same bar M18 drew for the doc↔code walk, and for the same reason: that path *absorbs* (re-baselines drifted-clean docs, mutating the record + edge index), so reusing it would silently re-baseline the very drift the sweep exists to surface. The mutating reconciliation path stays the **task-scope / finalize** concern; the store-scope file-state target is a **detect-without-absorb twin** — pure read, findings only. (This is the one genuinely net-new piece of logic in M20's envelope: a non-mutating variant of the committed-store file-state check.) **"Each committed managed doc" means `index::committed_instances` — located *and* placement (M42; landed Inc 2 T2).** As built, the twin walked only `location:`-bearing schemas while its *mutating* counterpart had carried a placement branch since M38 — so `jigc validate` could not see an out-of-band edit to a baselined `CHANGELOG.md`/`VISION.md` at all (silently clean, exit 0), and [CLAUDE.md](../CLAUDE.md)'s *"out-of-band edits are detected and routed"* invariant did not hold for the placement class ([storage.md](storage.md) → The census, where the site is recorded). It now shares the same placement-aware enumerator as families 3 and 5, keying each doc on its repo-relative path (a placement doc's literal `placement.file`) — **enumeration only**: the twin still takes the record by `&` and never routes through `reconcile_committed_store`, so detect-without-absorb is untouched. Acceptance: `crates/cli/tests/validate_envelope.rs` → `validate_detects_an_oob_edit_to_a_committed_placement_doc` (a baselined root `CHANGELOG.md`, hand-edited through git, on the real binary). Three edges the twin must pin, because the mutating path resolves them by *writing* and the read-only twin cannot:

- **UNKNOWN (un-baselined) ≠ clean.** The classifier's three states are clean / drifted / **unknown** (record has no entry); the mutating path *adopts a baseline* on unknown. The twin must **not** silently pass an untracked committed doc (a false "all clear") — it reports it as a distinct **un-baselined / not-yet-tracked** outcome, neither drift nor clean. (On a fresh clone or pre-baseline store this is informational, not an error — it does not flip the exit code.)
- **The reused `hash-matches` id carries a store-scope route, not `reconcile <path>`.** At task scope a drift finding routes to `reconcile`; at store scope there is no task and the mutating reconcile is barred, so that route is wrong. The twin reuses the **check id** `file-state.hash-matches` (no new check id, no severity-inventory growth) but emits a **store-scope route variant** (report-only — "review / re-author through the owning workflow"), never `reconcile`. The "no new finding surface" claim is precise to *check ids*, not the route string.
- **Content drift on *present* docs only (M20) — recorded-but-missing rename detection added at M35.** The M20 twin covered only a tracked doc whose on-disk content diverged; **recorded-but-now-missing** docs (rename / deletion) were out of scope, a task-scope concern. **M35 brings the strong/weak rename classifier into the store sweep** (Component A — [reconciliation.md](reconciliation.md) → Rename detection): the store walk now enumerates recorded-but-missing paths and runs the **pure, non-mutating** `detect_rename` (it classifies, it does not absorb — so the detect-without-absorb bar holds), firing **before** the fourth family (`ref-resolves`). **Dedup mechanism (so the two never emit competing diagnoses — pinned as scope-subtraction, not mere ordering):** when `detect_rename` claims a slug renamed/missing, that slug's **inbound edges are excluded from `ref_resolves_store` for this sweep** — so an OOB move-with-referrers surfaces **one** `reconciliation.rename` finding and **zero** `ref-resolves` findings for those edges, while `jigc validate` still reports every *other* dangling ref (it stays a report-all read command — no short-circuit). This is also the only detector that catches a **referrer-less** OOB `git mv` (no dangling ref exists to find). The route is the actionable "adopt as `jigc rename`" / revert.

**Orphan detection — committed docs outside the resolved roots (M36).** The twin above detects drift on docs the store *knows about* (a `FileStateRecord` exists); it cannot catch a doc that fell **outside** the resolved doctype roots — the `docs-root`-changed orphan ([storage.md](storage.md) → docs-root). M36 adds a store-scope advisory: **`file-state.orphaned-doc`** (advisory, store-scope, report-only, un-keyed like the informational outcomes in the [inventory](#mvp-check-inventory)) — a committed `.md` that looks like a managed doc stranded at a former root. **The match predicate (pinned — a bare extension match would brick):** doctypes have **no filename pattern** (`id-from: title` mints an arbitrary slug), so **when no prior home is in hand** the only self-discovery signal is the `location:` **directory** basename — *pinned at M36 over the only home shape a knob could then move, and the **"only"** does not stand at M49: a re-rootable `placement:` home contributes a second self-discovery key, keyed on a **filename** (below, The M49 placement arm). What the pin forbids — a bare extension match — still stands, and the M49 arm is not it.* The detector flags a committed `.md` whose path lies **under a directory whose basename equals some doctype's `location:` basename** (e.g. `decisions/`, `specs/`) **and** which is **not** under that doctype's *current* resolved root. This flags `<old-root>/decisions/foo.md` after a `docs-root` change while **excluding** `README.md` and ordinary prose (never under a doctype-location-named dir); matching by extension alone is explicitly wrong (it would flag every stray markdown file — a front-door false-positive). Route: re-point `docs-root` to cover it, or `jigc unmanage` it. Same detect-without-absorb bar as the twin — pure read, findings only.

**M39 re-key — the strand discriminator, not location-basename-only.** The pinned claim above ("the only stable discriminator is the `location:` directory") is scoped to the **found-stranded self-discovery** arm — where the sweep has *no* record of the doc's prior home and the dir basename is all it can key on. M39 generalizes the detector (`crates/cli/src/orphan.rs`) to a **prior-home / current-home strand predicate** (`is_stranded` over a `Home` = `location` dir **or** `placement` file): the self-discovery arm keeps the basename key — and the parenthetical M39 wrote beside it, *(a placement/root file has no dir pattern, so it is **not** self-discoverable)*, **does not stand at M49 and is struck rather than quietly reworded**: it was true only while a `placement.file` was a constant, which `placement-root` ended (below) — but the M39 relocation + `config set docs-root` fire-points supply a **recorded/confirmed prior home**, so a placement→root, root→`docs`, `location`-basename **rename**, or shape change (`location`↔`placement`) all become detectable — the relocations the location-dir-basename-only key was blind to. Freeze-exempt doctypes carry **no prior-home snapshot**, so their prior home is **human-supplied/confirmed** (auto-move stays unsafe). See [storage.md](storage.md) → Placement and the roadmap's M39 Increment 5.

- **Why `git ls-files`, not file-state keys (the coverage hole).** The obvious detector — "advise on any `file-state` key whose path lies outside the resolved roots" — has a **silent hole**: `file-state.json` is gitignored and written only at `finalize`, so on the **clone → `jigc config set docs-root` adoption path** there are *no* local file-state keys for the pre-existing committed docs, and the advisory never fires — a silent orphan, the exact regression against "detected and routed, never silent". So the detector enumerates **`git ls-files`** and flags committed `.md`s that match a self-discovery predicate above — the location-basename one, or (M49) a re-rootable placement home's declared remainder — but fall outside the resolved home: `git ls-files` is the committed truth that survives a fresh clone, where the finalize-gated file-state map does not.

**M40 two-tier route — discriminate on registration, never gate on it** ([DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 planning: Settle). The adoption trial proved the single route wrong for one arm: a never-adopted foreign doc under a doctype-basename dir (`research/notes.md`) took the same "stranded → `jigc unmanage`" route as a genuine strand — a proven no-op loop (`unmanage` on a never-registered doc is a clean no-op; the advisory re-emits, exit 0). The classify heuristic is **unchanged** *by M40* (parent-dir basename, as pinned above; M49 adds the second arm below, and the two tiers key on **registration**, never on which arm matched); the *finding* now discriminates on **`FileStateRecord` membership** (already loaded in the same fn — the threading is CLI-local): a **registered** path is a genuine strand → the existing "stranded → `jigc unmanage` / relocate" route; an **unregistered** basename-coincidence → a "looks-managed-but-unregistered" advisory whose route is **conditioned on the `migrate-<doctype>` workflow actually existing** (the same `migrate.rs` prefix scan): present → route to **`jigc migrate <path> --as <doctype>` or ignore**; absent (milestone-record, dogfood-record) → the route falls back to **"ignore, or route to a human"** — never command a verb that hard-errors. The migrate route is real for the seven doctypes whose `migrate-*` workflows land in the same wave ([auto-migration.md](auto-migration.md) → the methodology work docs), not for every methodology doctype. This is deliberately **not** a plain registration gate — that is the exact design the bullet above rejected, for the same reason: file-state is gitignored, so *gating* emission on membership would silence genuine strands on a fresh clone. Under two-tier the fresh-clone case **still fires** (as the unregistered arm, whose migrate-or-ignore route is still actionable) — only the ROUTE is tiered, never the emission — so the M36 "never silent" property survives intact.

**The M49 placement arm — the second self-discovery key, and the trade it buys** (`crates/cli/src/orphan.rs` → `orphaned_docs`' re-rootable tier; [storage.md](storage.md) → the M49 rows of the placement census). Until M49 a `placement.file` was a literal inside the doctype's frozen `schema-hash` — a constant no cascade could move — so the pin above was exhaustive *by construction*: there was no placement strand to detect, which is why M39 wrote the parenthetical it did. **`placement-root` ends that** ([overrides.md](overrides.md); [storage.md](storage.md) → Placement), and the detector follows the knob, keyed exactly as the `location:` arm is — on **the part the knob leaves invariant**:

- **The key is the declared home's remainder past its first path component.** `placement-root` replaces exactly that first component (`docs/roadmap.md` → `<root>/roadmap.md`), so `roadmap.md` is what survives every re-point, and it is read off the **declared** schema — the resolved one cannot serve, because under `placement-root: .` a nested-declared home and a root-declared one both resolve to a bare filename and are then indistinguishable.
- **The match is path-boundary anchored** (`orphan::at_remainder`): `<anything>/<remainder>`, or exactly `<remainder>` (the repo-root case `placement-root: .` produces) — never a bare suffix, so `docs/old-roadmap.md` is not a `roadmap.md`.
- **A home declared at the repo root contributes no arm at all.** `VISION.md` / `CHANGELOG.md` carry no leading component, so no `placement-root` value could ever have stranded their instances; a stray `docs/VISION.md` is therefore never called a strand (the unburiability of the ecosystem-idiomatic files is a derivation, not an allow-list). Only the recorded-prior-home arm sees a strand there.

**The trade this makes, owned rather than denied.** A declared-**filename** key is *narrower* than the extension match the M36 pin forbids — one declared remainder per re-rootable placement doctype (three ship today), not every `.md` — but it is **broader than** the location-dir key it joins: a filename matches at **any depth anywhere in the tree**, while a directory basename matches only under a directory that already names a home. The driven consequence, at the **pack-default** cascade (`placement-root` never set, no re-point anywhere): a committed `implementation/roadmap.md` or `packages/foo/roadmap.md` draws `file-state.unregistered-doc` — *"it carries `roadmap`'s home filename, whose resolved home is `docs/roadmap.md`"* — where pre-M49 no arm could reach it at all. That is a **filename coincidence**, and it is admitted here rather than hidden: the two-tier route above is precisely what makes it survivable — the unregistered tier says *coincidence or un-ingested foreign doc, not a tracked strand*, routes at `jigc migrate <path> --as <doctype>`-or-ignore, stays advisory, and is no `render::STORE_EXIT_FLIPS` member, so it neither gates nor flips the exit. The bar the pin actually set — *do not flag every stray markdown file at the front door* — still holds: `README.md`, and every `.md` whose name is not some re-rootable placement doctype's declared remainder, stay untouched. Both halves are pinned by `crates/cli/tests/placement_override.rs` → `the_orphan_predicate_of_record_states_the_placement_arm_that_shipped` (the binary driven at the unset knob, and this section asserted to describe what it did).

**Exit semantics — report-only, with the exit-flipping exceptions `render::STORE_EXIT_FLIPS` enumerates** (the count is deliberately **not** restated here — the hand-count in the code that carries it went stale three times; the table **is** the enumeration, and each exception below is admitted on its own recorded criterion)**.** The M18 report-only rule holds for **every content finding** — a stale `doc-code` anchor, a dangling `workflow-refs` reference, a `file-state` *content* drift, a dangling cross-doc `ref-resolves` edge (the fourth family, below), a per-instance `schema-conformance` break (the fifth family, M33/M34, below), *whatever its cascade severity* — *listed*, content-only run exits **0**. `jigc validate` stays a **read command that never gates a transaction** for content drift — the load-bearing invariant the doc↔code target honors. **The first two exceptions, as the rule was first written:** (1) a `pack-probe-integrity.*` meta-finding (the `doc-code` subprocess failing) or the probe-missing operational error — the sweep *could not produce a trustworthy result*; and (2) **a store-scope rename detection** (M35, Component B) — an out-of-band `git mv` is a **structural-identity event introduced by this commit**, not pre-existing content rot, so it joins the same exit-flipping exception class. *Engaging the report-only rationale (record-is-rebuttable):* report-only exists so the sweep never gates on **pre-existing, unrelated drift a commit didn't cause** (the masking-trap); a rename caused by the change in front of the sweep is not that case, so flipping its exit is *consistent with* the rationale, not a violation. (`schema-conformance.ref-resolves` is intrinsic-blocking, but *blocking* is a **finalize/task-scope** verdict; under the read-only store sweep the same *content* finding is *listed*, never a gate — which store-scope findings *do* flip the exit is one enumeration, `render::STORE_EXIT_FLIPS`, which this doc points at rather than re-lists.)

**The third exception (M42) — the unmigrated-corpus condition, admitted on the class's *existing* criterion.** The report-only rationale **stands in full and is conceded**: it exists so the sweep never gates on pre-existing, unrelated drift a commit didn't cause, and **nothing here touches it**. What changes is *which findings meet the exception class's own recorded criterion* — **"the sweep could not produce a trustworthy result"** (`crates/cli/src/render.rs:344-349`, whose predicate is today `pack-probe-integrity.*` + `reconciliation.rename`). **An unmigrated corpus meets that criterion more strongly than a failed probe does.** When the manifest says v2 and the corpus is v1, **every other family is parsing docs against a schema those docs do not conform to** — the anchors, the workflow refs, the hashes, the cross-doc edges, and the conformance verdicts are all computed against the wrong shape. A "clean" verdict there is not a clean corpus; it is an **untrustworthy sweep**, exactly the state a crashed probe leaves. So the **version-currency break flips the exit non-zero**, for the same reason and through the same predicate. *Why now and not 1.1:* an exit code is the first contract a pipeline binds — it carries no version field and no additive carve-out — and [decisions-pending.md](../implementation/decisions-pending.md) already promises `validate --format json` as a CI-gating contract. Ship 1.0 exiting **0** over an unmigrated corpus and every adopter encodes *unmigrated == green*; flipping it later turns green pipelines red on a minor upgrade. That is the one genuine one-way door in P1. ([DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 planning: the Settle.)

Two things the exception's own definition must pin, because getting either wrong turns this fix into the failure it exists to prevent:

- **The exit predicate keys on a *check id*, minted for this fact: `schema-conformance.schema-version-current`.** The M42 pass first wrote the version break as a reuse of `field-value-conformant` over the stamp field (*Version-mismatch is itself a surfaced break*, below — the pin is corrected there, with its rationale engaged). Under that reuse the exception has **no mechanism**: the predicate sees only `Vec<Finding>` (probe + code), so keying on `field-value-conformant` would flip the exit for **an invalid `status` enum or a malformed `date` on any ADR** — ordinary content drift, precisely the masking-trap the report-only rule exists to prevent — and keying on the *route string* instead would couple an exit code to prose. Neither is admissible. The break gets **its own code**, the predicate keys on **that code**, and every ordinary content finding keeps its code and stays report-only / exit-0.
- **The *managed*-arm condition is about which code fires — not about the exit, and that is a M46 revision of what M42 wrote here.** Since the fifth family now enumerates **placement** homes ([below](#store-scope-schema-conformance--the-fifth-family-m33m34)), it reaches a stock repo's real Keep-a-Changelog `CHANGELOG.md` — a file the user never handed to jigc (`index::committed_instances` returns a placement instance on **mere file existence**, `crates/engine/src/index.rs:718-733` — there is no registration test). It carries no stamp and parses against no known schema version. **That is the adoption case, not an unmigrated corpus:** it emits the **adoption advisory** (route: `jigc ingest` / `jigc migrate <path> --as <doctype>`), and `schema-version-current` fires **only** on a *stamped* committed instance whose stamp is **below** its manifest version (the discriminator: [The managed-vs-foreign discriminator](#store-scope-schema-conformance--the-fifth-family-m33m34), below). That half is untouched and still load-bearing: without it M42 would have **routed** the default brownfield first run at `migrate-corpus`, the same false-route failure the Settle caught for the *route* and would otherwise have carried straight into the *exit code* it minted in the same wave.

  **The other half M42 wrote — *and stays exit-0* — is withdrawn at M46, as a basis-has-changed revision rather than a silent swap.** Name what the exit-0 bought, because that is what decides whether it is still worth its price: it kept a stock brownfield first run from being sent at a verb with nothing to do — and at M42 `migrate-corpus` was that verb, blocking on the foreign file itself, which is where the noise was audible. M46 Increment 3 takes the foreign file out of that verb's blocking set entirely ([corpus-migration.md](corpus-migration.md) → The foreign arm), so the purchase is **spent**: the verb is now silent about the file, and the store sweep's exit is the only surface left that makes a squatter at a managed home audible at all. Reported at exit 0 that is a green a script chaining `jigc validate && deploy` reads as *the store is fine*, over a home whose occupant the sweep has just adjudicated foreign. So `schema-conformance.unadopted-instance` joins `render::STORE_EXIT_FLIPS` and the run **exits non-zero** — with the **finding untouched**: still advisory, still a `GATES_NOWHERE` member, still routed at `jigc ingest`. Flipping the *sweep's* exit is not granting the *finding* a gate, and the two claims are asserted separately over one report ([DECISIONS.md](../DECISIONS.md) → 2026-08-19 M46 Increment 3 / T1).

**The trailer must not claim a gate that does not exist (M42).** The report-only trailer prints *"these gate at `jigc task validate` / `jigc task finalize`"* (`store_trailer`, `crates/cli/src/render.rs`) — and for the **version-currency break that sentence is false**: at task scope a stale committed doc downgrades to `advisory · reconciliation.conformance-block`, and a finalize over a doubly-stale corpus was **proven to commit**. It has **no gate anywhere in the system** while the tool prints that it gates — the same class of lie as the false green above, one line further down the same report. M42 corrects the claim on both branches: `schema-conformance.schema-version-current` gets its **own** trailer case (it now flips the exit — above — and says so, naming `jigc migrate-corpus` as the route), and the report-only branch claims a gate only for the findings that **actually carry one at task scope**. *(This is why the papercut-batch item "render `blocking (gates at finalize)` per finding" is a **dependency** on this fix and not a papercut: per-finding labelling would print the falsehood more prominently, on every row.)*

**The criterion is *"a gate exists **and** would block, at a door the sentence names"* (M47, N10).** The M42 shape above left the trailer and the row on **two** criteria: the row labelled with `Blocking && gates_at_task`, the trailer *counted* with the bare `gates_at_task` — which consults `GATES_NOWHERE` and the un-baselined discriminator but **never severity**. So a store sweep whose only finding is the advisory-by-default `doc-code.title-names-symbol` (not a `GATES_NOWHERE` member, and rightly not — `doc-code` *is* a task-scope family) printed the row `advisory · doc-code.title-names-symbol …` and then *"these gate at `jigc task validate` / `jigc task finalize`"*: **the row and the trailer contradicting each other in the same report**, and the reader sent to a gate that reports the finding clean at exit 0. The trailer now counts on the **same** predicate the row labels with, so the two can no longer disagree. Two further corrections land on that one claim:

- **The door list is complete: it names `jigc milestone finalize` too.** The milestone-boundary gate ([above](#the-milestone-boundary-gate-m45)) drives the *same* `engine::validate::validate_task` entry, under the same resolved cascade, over the merged effective state, and blocks exit 3 on the same families — so for every finding the trailer counts, that door gates as hard as the two task doors. Naming only the task pair told a fan-out operator the boundary they were actually standing at could not stop them. *(The sentence was **not** true of the transient `commit:<sub-id>` docs a `squash: false` fan-out commits until M49 widened the gate's subject to them — [above](#the-milestone-boundary-gate-m45), where the rule and the `squash` carve-out are stated.)*
- **`workflow-refs.*` is scoped to the door it really has — compose.** The counted set had to be checked against the milestone gate's inputs rather than assumed, and one family fails the check: the workflow↔refs family (family 2 of the store sweep) is emitted at **compose** (`crate::start`) and by the store sweep, and by **no** task-scope path — `validate_task` runs staged-instance conformance, the committed-store reconciler, `ref-resolves`, and `doc-code`, and no workflow↔refs pass at all. So neither task door nor the milestone gate can ever see one, and the M42 sentence was already false for it (a blocking `workflow-refs.include-resolves` printed `blocking (gates at finalize) ·` and was counted into *"these gate at …"*). It is **not** a `GATES_NOWHERE` member — a hard gate does exist for it — so the claim is *scoped to the right door* (`jigc start`) rather than withdrawn: `gates_at_compose` in `crates/cli/src/render.rs`, derived from the emit sites exactly as `GATES_NOWHERE` is. The all/none/mixed shapes are unchanged; the mixed sentence gains a compose clause only when a compose-gated finding is present.

**The per-finding label, once the criterion is sound (M42, Inc 12).** On the corrected criterion the label ships: a **store**-view row whose finding a `finalize` would actually stop on renders `blocking (gates at finalize) · <code> — <message>`; every other row keeps the bare severity token and claims nothing. Its predicate is the trailer's `gates_at_task` **plus the finding's cascade severity** (**plus, since M47, the compose-scope exclusion above** — the label and the trailer share one predicate) — the row asserts a *finalize block*, which a `warning`/`advisory` never is (the cascade demotes non-intrinsic checks in the field), and which a compose-only family never is either. `schema-conformance.schema-version-current` joins `GATES_NOWHERE` for this reader: it gates nowhere, and unlike the trailer (whose unmigrated-corpus branch never reaches the report-only case) the row has no structural shortcut around it. **Task-scope rendering is untouched** — there the severity token *is* the verdict — and the JSON severity token is unchanged on both surfaces: the label is a text affordance, never a break of the machine contract ([command-output-contract.md](command-output-contract.md)).

**The criterion is per *finding*, not per *code*** (M42, T3 — `gates_at_task` in `crates/cli/src/render.rs`). The claim the trailer makes is *"a gate exists for **this finding**"*, so that — not the narrower *"some task-scope path can emit this **code**"* — is what must be established. Two conditions, both derived from the **emit sites, never from this prose**:

**(1) No gate blocks on the code** (the shipped set, `GATES_NOWHERE`). **The derivation is *"no gate blocks on it"*, not *"no task-scope path emits it"*** — a distinction that was inert until M48, and is stated in its stronger form because the weaker one is now **false of a member that still belongs**: since the [managed-vs-foreign discriminator reached the task-scope reconciler](#store-scope-schema-conformance--the-fifth-family-m33m34) (M48 Inc 4), `schema-conformance.unadopted-instance` *does* have a task-scope producer, mints **advisory** at every one of its emit sites, and the task-scope doors gate on `has_blocking()` — so it is reported there and blocks nowhere. Walk each code's producers; nine qualify:

- the store-only content families — `schema-conformance.mention-resolves` (in-prose mentions, store-scope by design), `schema-conformance.repeatable-populated` / `surplus-sections-absent` (the M40 hollow-and-surplus adoption advisories), and `schema-completeness.inverse-cardinality` (completeness depends on *other* tasks — never a per-task gate) — none of which the engine's `validate_task`, the shared body of `jigc task validate` and the `finalize` preflight, can produce under any workflow;
- `schema-conformance.unadopted-instance` — the foreign-squatter adoption advisory ([above](#store-scope-schema-conformance--the-fifth-family-m33m34)), emitted by the fifth family's foreign arm **and**, since M48, by the task-scope reconciler's `UNKNOWN` + non-conformant arm. Both mint it through the one advisory-severity producer, so no door gates on it;
- `file-state.un-baselined` — the read-only twin's UNKNOWN outcome; the task path *adopts* a baseline instead (`file-state.baseline-adopt`), so this code never reaches a gate;
- the CLI-minted, un-keyed store advisories — `file-state.orphaned-doc`, **`file-state.unregistered-doc`** (M40's second orphan tier — an earlier draft of this list omitted it, the un-enumerated-sibling failure this wave keeps finding: enumerate the emit sites, never a prose list), and `store-version.binary-mismatch`.

**(2) The finding is a per-doc conformance break over an *un-baselined* committed doc** — the condition a code-level list **cannot** express, and which the first shipped version of this fix therefore missed. The store sweep parses every committed instance *itself*, so it raises `conformance.*` (the `parse_sections` `Err` arm, [above](#store-scope-schema-conformance--the-fifth-family-m33m34)) and `schema-conformance.*` findings **directly over committed docs**. `validate_task` never does — it parses only the task's **staged** instances, and routes the *committed* store through `file_state::reconcile_committed_store`, which grades a nonconformant committed file by **`FileStateRecord` membership** (the same discriminator M40's [two-tier orphan route](#the-two-tier-rule) keys on):

- **baselined** and drifted → **blocking** `reconciliation.conformance-block`. The gate is real; the claim stands (withdrawing it here would be the opposite lie).
- **un-baselined** — no record entry → **advisory** `reconciliation.conformance-block` (*routed, not recorded*), or, where the [managed-vs-foreign discriminator](#store-scope-schema-conformance--the-fifth-family-m33m34) adjudicates the file **never adopted** (M48 Inc 4), the advisory `schema-conformance.unadopted-instance` — which condition (1) above already carries, so this condition never has to reach it. Nothing gates on either, **ever**. And un-baselined is not an edge case: `.jigc/state/` is gitignored, so it is the state of **every** committed doc in a fresh clone, in a brownfield adoption, and in any hand-authored corpus — i.e. the dominant `jigc validate` corpus. So the blanket sentence was false over exactly the population the sweep most often runs against: a `blocking · conformance.section-missing` on a committed ADR, printed with *"these gate at `jigc task validate` / `jigc task finalize`"*, over a finalize that was **proven to commit**.

So the CLI derives, alongside the report, the `<type>:<slug>` identities of the committed instances with no record entry (`unbaselined_identities`), and the trailer joins each per-doc finding to its doc on the identity part of the address `attribute_to_doc` gave it. The claim is only ever **withdrawn** on a proof that no gate exists, never granted on the absence of one.

The report-only branch then counts the findings that *do* gate — **blocking, gate-carrying, and boundary-scoped**, per the M47 criterion above: **all** → *"these gate at `jigc task validate` / `jigc task finalize` / `jigc milestone finalize`"*; **none** → no gate claim at all (a stock brownfield repo, whose sole finding is the adoption advisory — or any store whose findings are all advisory — is no longer sent looking for a gate that will never fire); **mixed** → how many gate, how many gate at compose when a `workflow-refs.*` break is among them, and that the rest gate nowhere. `schema-conformance.schema-version-current` gates nowhere either but never reaches this branch — it flips the exit and takes its own case. This corrects the **claim**, not the gate: the task-scope downgrade to `advisory · reconciliation.conformance-block` and finalize's behaviour over a stale corpus are untouched here.

**No new severity surface — check ids reused.** `workflow-refs.*` and `file-state.hash-matches` are already in the [severity inventory](#mvp-check-inventory); M20 invokes them at **store / read-only scope** instead of compose / task scope — **no new check id, no new knob, no severity-inventory growth** (the only deltas are a membership-only command-ref *path* and a store-scope *route* variant on `hash-matches`, neither a new id). workflow↔refs is engine-native in-process; file↔CLI-state likewise — neither is a subprocess probe, so neither can raise a `pack-probe-integrity` meta-finding; only the doc↔code target can.

**The M19 pre-commit backstop stays doc↔code-keyed for *content*; M35 adds a hard block on rename — scoped to *this commit's* moves.** The warn-only hook keys its *warning* on `doc-code.*` content findings — since M47, on the **blocking** ones only, via the sweep's `blocking_probes` array ([Auto-firing the sweep](#store-scope-re-validation--jigc-validate-m18) above) — and M20 did **not** broaden the warn set. **M35 (Component B)** makes the hook **block the commit** on a store-scope rename detection — but *only* on a rename **introduced by this commit**, never on pre-existing drift. **The scoping mechanism (load-bearing — without it the masking-trap returns):** the hook intersects the sweep's `reconciliation.rename` hits with **this commit's staged path-status set** (`git diff --cached --name-status`, the `R`/`D`/`A` entries); it **blocks** only when a detected rename's old *and* new paths are both in that staged set, and **reports (warn, exit 0)** any rename hit whose paths lie *outside* the staged set (a pre-existing OOB move left in the tree, an uncommitted earlier rename — drift this commit didn't cause). So `detect_rename` firing on its own never blocks an unrelated commit; only a rename *this commit is making* gates. This is the one case where the hook gates rather than warns, and it follows the exit-flipping exception above. Content drift (`doc-code`, `ref-resolves`, `file-state`) still only warns. *(Acceptance, flow 37: an unrelated commit with a pre-existing OOB-moved doc sitting in the tree must **not** block; a commit that itself stages a bare `git mv` of a managed doc **must** block.)*

### Store-wide forward-ref integrity — the fourth family (2026-06-23)

The store sweep gains a **fourth content family: cross-doc forward-ref integrity** — the **store-wide analog of the task-scope `ref-resolves` finalize gate**. Until now `schema-conformance.ref-resolves` fired *only* at `jigc task finalize`, scoped to the task-touched edges (`crate::index::ref_resolves`); the store sweep ran doc↔code, workflow↔refs, and file↔CLI-state but **not** ref-resolves. So a dangling `supersedes`/`cites` reference *already committed* in the store — a target deleted or renamed three docs away from where a later task works — was **invisible to `jigc validate`**, hence to anything keyed on its findings. The fourth family closes that asymmetry: `crate::index::ref_resolves_store` walks **every committed forward edge** in the rebuilt committed edge index and reports each whose target is not committed-reachable as the same blocking `schema-conformance.ref-resolves` finding the finalize gate raises.

- **Not the M20 "deliberately-not-a-fourth-target" case.** M20 ruled out *override↔default* as a target because it has **no committed doc to walk** (it operates on recorded config deltas, swept at `jigc upgrade`). Forward-ref integrity is the opposite: it walks the **committed edge index** — a real store surface, the same one the finalize gate consults — so it *does* have something to sweep. The M20 reasoning does not exclude it; it simply hadn't been wired store-wide yet.
- **No new severity surface — check id reused.** Exactly the M20 pattern: `schema-conformance.ref-resolves` is an existing [inventory](#mvp-check-inventory) check id (intrinsic, floored blocking). The fourth family **invokes it at store / read-only scope** over the committed index instead of the task overlay — **no new check id, no new knob, no severity-inventory growth.** Engine-native and in-process (an edge-index walk, like file↔CLI-state), so it raises no `pack-probe-integrity` meta-finding.
- **Reachability rule is shared, not forked.** The store walk reuses the *committed-store* half of the finalize gate's reachability test (`committed_reachable`, factored out of `target_reachable`): a `<type>:<slug>` edge resolves iff the target type's canonical `<location>/<slug>.md` exists. The store walk has **no task working area** (no surface b) and **no `task_froms` filter** — the committed store is closed, so *every* committed edge is in scope.
- **The pre-commit backstop is unchanged here.** Like M20, this increment does **not** broaden jigc's shipped warn-only hook (which stays `doc-code.*`-keyed); it only makes `jigc validate` *report* the dangling cross-doc ref on demand. (A study harness that keys a blocking hook on `schema-conformance.ref-resolves` findings is study configuration, not a jigc behavior change.)

### Store-scope schema-conformance — the fifth family (M33/M34)

The store sweep gains a **fifth content family: per-instance schema-conformance** — the **store-wide analog of the task-scope `finalize` conformance gate**, and the **detect-half the M34 migration turns on**. The baseline audit (2026-06-24, exercised) found the gap precisely: the first four families re-check *anchors*, *workflow refs*, *file-state hashes*, and *cross-doc edges*, but **none re-parses a committed doc against its schema**. So a doc made non-conformant by a *schema-shape change* with **bytes unchanged** is invisible to `jigc validate` (family 3 is hash-only; bytes match baseline ⇒ exit 0). The exact M34 case — a v1 corpus under a v2 schema — produces **zero findings** today. The fifth family closes that: it re-parses **every committed instance against the current resolved schema** and reports each `schema-conformance.{required-slot-present, required-field-present, field-value-conformant, ref-resolves}` break — **plus a version-currency break** on a *managed* instance below its doctype's manifest version, under its **own** check id **`schema-conformance.schema-version-current`** (M42), emitted even when the doc is otherwise structurally clean (Version-currency is itself a surfaced break, below).

- **Verified clean lift — pure function, no task context.** `conformance_for` / `schema_conformance` are **pure** over `(filename, schemas, rel_key, source)` — no working area, no `reconcile_committed_store`, no minted task (confirmed by spike). The fifth family feeds them the committed docs + the current schemas; the enumeration is the family's own committed-store doc-walk, **not** the anchor-scoped `enumerate_committed_surface` (which would under-walk — it visits only `code-anchor`-bearing docs). This is **wiring, not new check logic**. *(The doc-walk shipped keyed on `schema.location` alone, which under-walked in the other direction — see the placement bullet below; M42 re-points it at `index::committed_instances`.)*
- **One new check id — the version break, and only it (M42 correction).** The four structural checks are reused verbatim at **store / read-only scope** — no new id, knob, or inventory growth (the 2026-06-23 fourth-family pattern). The **version-currency** break is the one exception, and the M42 pass got it wrong the first time; see the pin's correction two bullets down.
- **Exit semantics — report-only for a structural break; exit-flipping for a version-currency break (M42 revision).** A *structural* `schema-conformance.*` break stays report-only at store scope (exit 0) like every content family: the intrinsic-blocking severity is a *finalize/task-scope* verdict, *listed* never gated under the read-only store sweep. **`schema-conformance.schema-version-current`** is the exception M42 admits: an unmigrated corpus means every other family is parsing against a schema its docs do not conform to, so the sweep *could not produce a trustworthy result* and the exit flips ([Exit semantics](#completing-the-envelope--workflowrefs--read-only-filecli-state-m20) → the third exception, whose two conditions — *this code*, and the *managed* arm only — are pinned there). Since 2026-07-24 the exception is a code **pair**: its above-current sibling **`schema-conformance.schema-version-ahead`** (a future/foreign stamp — the doc was written to a schema this binary does not know, so the sweep could not adjudicate it) flips the exit for the same reason through the same predicate. The report-only rationale is untouched: an invalid enum, a malformed date, a missing slot keep their codes and their exit-0. **And since M46 the *foreign* arm flips too** — `schema-conformance.unadopted-instance`, last in that table's precedence order: unlike the two version breaks the sweep there **worked** (it found the file and named it foreign, so `sweep_untrustworthy: false`), and the flip is its verdict on a standing fact about the corpus rather than a claim that it could not adjudicate. The withdrawal of M42's exit-0 for that arm, and what it bought, are recorded where M42 wrote it ([above](#completing-the-envelope--workflowrefs--read-only-filecli-state-m20) → the managed-arm bullet).
- **Version-currency is itself a surfaced break — emitted, not only routed (M34); and it gets its own check id (M42).** With the per-doc schema-version stamp ([corpus-migration.md](corpus-migration.md)), a **managed** committed instance whose stamp is **below** its doctype's manifest version — or **absent** on a doc that still parses against a known schema version (the v0 corpus state) — is **non-conformant by that fact alone**, and the fifth family **emits** a finding for it even when the doc is otherwise structurally clean. This is load-bearing: the headline detect case is the **pure-stamp v0 corpus** (the M34 dogfood), which carries *no other* non-conformance, so a labeler that only annotates pre-existing findings would leave it silent (exit 0) — breaking the detect-half for its own dogfood. Emission, not annotation, is what closes the silent-drift hole ([corpus-migration.md](corpus-migration.md) → property census).

  **The pin this bullet used to carry — *"No new check id: the version break reuses an existing `schema-conformance.*` id (e.g. `field-value-conformant` over the stamp field)"* — is retracted at M42, by engaging it rather than sidestepping it.** What it was right about: a version break needs no new **family**. It is a `schema-conformance` fact, it rides the existing store walk, and it earns no new probe. What it was **wrong** about is that it therefore needs no new **id** — because *a stale stamp and an invalid enum value are different facts with different consequences*. `field-value-conformant` also fires on an out-of-range `status` on any ADR; collapsing the two into one code makes the version break **indistinguishable to any machine consumer** — including the exit predicate, which sees only `(probe, code)` (`crates/cli/src/render.rs:344-349`). That is exactly the property M42 exists to add, so the reuse is precisely what blocks the fix. Named honestly: **reusing `field-value-conformant` for a version break was always a category error** (the stamp is not a field whose *value* the author got wrong — it is a fact about which schema the whole doc was written against); it merely cost nothing until something needed to **act** on the distinction. M42 mints **`schema-conformance.schema-version-current`** — **intrinsic + keyed** ([inventory](#mvp-check-inventory)) — fired when a *managed* committed instance's stamp is below its manifest version. **`is_author_required` is untouched** — the stamp stays author-exempt (engine-`set:`); version-currency is a *store-scope corpus* rule, not an authoring obligation.
- **"Every committed instance" also means the instances at a doctype's *prior* homes (M52 completion audit, fix 2).** `index::committed_instances` answers *where does this doctype live* in the **present tense**, so after a schema bump that also **moves a doctype's home** the committed document sits at a path no resolved schema names and the census yields nothing. Driven at `c80b3f8f`: with `changelog` bumped 2→3 and relocated off the repo-root `CHANGELOG.md`, `jigc validate` printed *"no findings — the committed store validates clean"* at **exit 0** and `jigc doc list` printed *"no committed docs"*, while `jigc migrate-corpus --dry-run` — reading the snapshot store — answered `1 would migrate` about the same file. That is the M42 false-green this family exists to close, reopened through the one axis M52 Increment 7 widened on the **migrate** side alone ([corpus-migration.md](corpus-migration.md) → The corpus walk keys on the `from` home). The fix is the same key: the CLI reads every home the doctype declared below its current version out of the versioned snapshot store, re-roots each through `docs-root` / `placement-root` (`cli::migrate_corpus::prior_homes` — the **one** derivation, shared with the migration walk), enumerates the committed instances there (`cli::orphan::prior_home_instances`) and hands them to this family beside the census (`engine::validate::PriorHomeInstance`). Three consequences, each a property rather than a coincidence: **the subject is the *unmigrated* instances at those homes**, so `schema-version-current` is the true statement about each and no new code is minted — the premise *a document at a prior home was written by a prior version* is true under the freeze (a home is inside the doctype's frozen `schema-hash`, so it cannot move without a bump) and **not universally**, because a pack author may reshape a home and re-pin the hash at the same version, and the instance left behind is then **at** version; the three stamp readings are therefore answered separately (below current ⇒ this family's; at or above ⇒ the strand advisory's and the orphaned-instance break's, both untouched; **unstamped** ⇒ this family's iff the shipped managed-vs-foreign discriminator calls the bytes jigc's — the v0-era document — and the adoption door's otherwise). That narrowing is a correction with a datum: widening to the at-version cell took a file `schema-conformance.orphaned-instance` reports today and made it silent at exit 0, which `crates/cli/tests/unclaimed_file_family.rs` caught by going red; the document **joins `jigc doc list`** as `managed` at the home it is actually at, because the listing and the sweep read one enumerator; and its path joins the orphaned-instance walk's *claimed* set, so one stranded document draws **one** finding (below). Best-effort over the snapshot store, unlike the migration walk which fails closed — the posture and its reason are stated once, at [corpus-migration.md](corpus-migration.md) → Prior-schema sourcing. Acceptance: `crates/cli/tests/migrate_corpus_home_pairs.rs` → the eight `{location, placement}² × {relocation-only, with-content}` cells, each asserting the pre-migration `validate` + `doc list` state before the migration lands it.
- **Version-aware routing (M34; re-pointed at M42).** A version-currency break routes to **`jigc migrate-corpus`** (a known-old-version *managed* doc the transform can upgrade) — and, since M42, to a verb that can actually *see* the doc ([corpus-migration.md](corpus-migration.md) → The corpus walk). A doc **at** the current version that still does not conform routes as *corrupt* (review). A doc stamped **above** the current version routes *ahead* (2026-07-24): a future/foreign stamp no verb can fix — upgrade jigc, or restore the stamp from git history — never *migrate* (`migrate-corpus` **blocks** it as `migrate-corpus.schema-version-ahead`, not a silent already-current) and never the at-current *corrupt* lie. An in-flight doc mid-migration always reads `below-version ⇒ migrate`, never `corrupt` ([corpus-migration.md](corpus-migration.md) → stamp-flips-last). A **never-adopted foreign** file at a managed home takes neither route — it is an adoption case, below. Since **M48 Inc 4** the *task-scope* reconciler's un-baselined advisory labels itself through this same routing, so *stale* reads *stale* at both doors — with one difference the store side has no equivalent of: an **at-version** managed doc there takes the reconciler's hand-repair **sanction**, the same words its blocking twin uses, rather than this labeler's bare *corrupt* token ([below](#store-scope-schema-conformance--the-fifth-family-m33m34)). The **blocking** counterpart is the migration-upgrade gate at the transform transaction boundary — not this read-only sweep.
- **"Every committed instance" means `index::committed_instances` — located *and* placement (M42; landed Inc 2 T1).** As built through rc.5 the family enumerated only `location:`-bearing schemas (`crates/engine/src/validate.rs`, whose guard comment — *"a transient (location-less) type has no committed docs"* — was true pre-M38 and **false since**), so it silently dropped every **placement** doctype ([storage.md](storage.md) → The census, where the site is now recorded). The stale-able population is exactly the doctypes past schema-version 1, and **the skip dropped its placement half wholesale**: of the three doctypes at schema-version 2, `adr` is a `location:` doctype and was walked (the M34 dogfood rides it — which is *why* the hole read as covered), while the two **placement** ones, `changelog` and `deferral-ledger`, were invisible. So the detect-half was blind over exactly the corpus the migration exists to upgrade — `jigc validate` exited **0** over an unmigrated corpus while `migrate-corpus` could migrate it perfectly well (the fixing half outrunning the detecting half). *(The first statement of this bullet — "both doctypes at schema-version 2 in either pack are placement doctypes" — was **false**; `adr` is the counterexample. Corrected here rather than quietly dropped: the claim was load-bearing for the row's severity, and it is still true where it counts.)* M42 re-points the family's **enumeration** at **`index::committed_instances`** — the placement-aware enumerator (located `<location>/*.md` **and** a placement type's single literal file, each addressed by its `<type>:<slug>` identity, a placement singleton's `<type>:<type>`) that the hollow/surplus walk below already uses. The presence/value checks, the stamp read, and the version-aware route are then reached by every persisted doctype, with **no new check logic** — the M33/M34 "wiring, not new checks" property, again. Acceptance: `crates/cli/tests/corpus_migration.rs` → `validate_detects_the_stale_placement_changelog_then_migrate_clears_it` (detect → migrate → re-validate clean, on the real binary).
- **Extend the enumeration; never merge the two walks (load-bearing).** The hollow/surplus advisories run a **separate** store walk, and `crates/engine/src/validate.rs:645-655` records why: *"Family 5 surfaces the pure-stamp v0 case only when a doc has no other findings; an advisory folded into its per-doc `doc_findings` would silently swallow that break."* The pure-stamp v0 corpus is the **headline** case this family exists for (*Version-mismatch is itself a surfaced break — emitted, not only routed*, above), so folding the walks together would break the very detect-half P1 is fixing. P1 shares the **enumerator**, not the walk. A build that "simplifies" the two into one is a regression, not a cleanup.
- **The managed-vs-foreign discriminator — the stamp, with a declared bound (M42, corrected).** Extending the family to placement homes puts it over root `CHANGELOG.md`, which in a brownfield repo is very often a **never-adopted foreign file** sitting at the canonical destination. That doc is not an unmigrated *managed* doc: it is the **in-location-squatter adoption case** [storage.md](storage.md) → Placement already adjudicated (`source-path == promote-destination` → seed/adopt in place), so it routes to **`jigc ingest`** / **`jigc migrate <path> --as <doctype>`** — *never* to `migrate-corpus`, a verb that would do nothing for it. **Since M46 that is true of the verb, not only of this route**: `migrate-corpus` asks this same shipped discriminator before its fold and reports this same advisory verbatim from the one producer, so the two doors can no longer tell two stories about one file ([corpus-migration.md](corpus-migration.md) → The foreign arm). Three arms, keyed on **the doc's own committed bytes**:

  | the committed instance | verdict | finding | route | exit |
  |---|---|---|---|---|
  | **stamped**, stamp **below** the manifest version | **managed**, stale | `schema-conformance.schema-version-current` (blocking) | `jigc migrate-corpus` | **flips** |
  | **stamped**, stamp **above** the manifest version (2026-07-24 — the confidence-audit sibling-hunt item 1) | **managed**, future/foreign stamp (OOB-planted, or written by a newer jigc) | `schema-conformance.schema-version-ahead` (blocking, its own code — a future stamp **cannot** be fixed by `migrate-corpus`, so folding it into the below code would route an unfixable doc at a verb that blocks it) | human: upgrade jigc, or restore the stamp from git history | **flips** |
  | **unstamped**, but **parses** against a known schema version | **managed**, v0-era (the M34 headline case) | `schema-conformance.schema-version-current` (blocking) | `jigc migrate-corpus` | **flips** |
  | **unstamped**, and parses against **no** known schema version | **foreign**, never adopted | `schema-conformance.unadopted-instance` (advisory) | `jigc ingest` / `jigc migrate <path> --as <doctype>` | **flips** (M46) |

  The foreign arm's advisory is **un-keyed** — the `file-state.orphaned-doc` / `store-version.binary-mismatch` class ([Inventory = the keyed surface](#mvp-check-inventory)): a report-only heads-up, not a pass/fail gate, so it earns no inventory row and no `knobs.yaml` key (earnable later if a project needs to enforce adoption). *Un-keyed* and *advisory* are claims about the **finding** — its severity, its tunability, and the gate it does not carry, all three unchanged at M46. The **run's** exit is a separate claim, and it is the one that moved: the sweep refuses to report a green over a home whose occupant it has just adjudicated foreign (the managed-arm bullet above). Its route is **conditioned on the `migrate-<doctype>` workflow existing**, exactly as [the M40 two-tier route](#completing-the-envelope--workflowrefs--read-only-filecli-state-m20) already pins for its unregistered arm — never command a verb that hard-errors.

  **The classifier's precondition: it runs only where a stamp can exist (M42 T1, as built).** Stamp-absence is the discriminator's first signal, and it is only *evidence* for a doctype the CLI actually stamps — the **versioned** set (a governing `schema-manifest.yaml` entry; the stamp is injected exactly there — `crates/cli/src/pack.rs` → `load_pack_schema`). For an **unversioned** doctype (freeze-exempt, or a project-defined type) **no** instance ever carries a stamp, so "unstamped" carries no information at all, and calling one of its docs *"never adopted by jigc"* on the strength of a failed parse would be an unfounded claim of exactly the kind this discriminator exists to remove — a corrupt *managed* doc routed at adoption instead of surfacing its break. So an unversioned doctype is **never** classified: it keeps the pre-M42 behavior (its structural findings, un-routed — `route_schema_conformance` already returns early with no manifest version). Both shipped packs are fully versioned, so the production surface is fully covered; the precondition only narrows what the classifier is willing to *assert*. The parse arms then read against the doctype's **current** shape **and every shipped prior snapshot** (`schema-snapshots/<ty>.v<k>.yaml`, `1..current`) — load-bearing, not belt-and-braces: a v0-era ADR does **not** parse against the current (v2) `adr` (the optional `## Options` slot makes `## Decision` read as a renamed section) but **does** parse against `adr.v1`, so a current-shape-only test would route the M34 headline case at adoption.

  **The M42 pass first settled this on `FileStateRecord` membership** (`record.get(&rel).is_some()`, reusing M40's two-tier orphan test) **and that is broken** — recorded here rather than quietly swapped, because the reasoning is the instructive part. The file-state record lives in **gitignored, rebuildable `.jigc/state/`** ([storage.md](storage.md) → Derived caches: *"rebuildable from the committed docs, so they are gitignored, never committed"*), and this very doc already says what an absent entry means — *"On a fresh clone or pre-baseline store this is informational"* ([the `UNKNOWN` bullet](#completing-the-envelope--workflowrefs--read-only-filecli-state-m20), above). **So on a fresh clone of a managed repo the record is empty and every managed doc reads as foreign** — the tool would tell a teammate to `ingest` their own committed corpus. A discriminator for a fact about the *committed store* cannot key on a *gitignored cache*; it must key on something that survives a clone. **The stamp does.** (The two other rejections from that pass still stand: CLI-side post-filtering is dishonest — `validate_store_families` is a `pub fn`, so a knowingly-wrong finding is one call away from a driver — and the engine-empty invariant is untouched either way.)

  **The bound the stamp carries, declared with its expiry — not assumed away.** The objection that sank the stamp in the first pass is **real**: stamp-absent means *both* "never adopted" *and* "a v0-era managed doc," and the v0 case is the headline case the detect-half exists for. The **parse test** separates them in the ordinary case (a foreign `CHANGELOG.md` does not parse against a known schema version; a v0-era managed doc does), and what remains is **bounded, not eliminated**: a foreign file that happens to parse clean would be routed `migrate-corpus`, and a v0-era managed doc corrupted past parsing would be routed `ingest`. The residual population is enumerable: **M34 shipped the v0→v1 stamp migration for every dev doctype and M40 for every methodology one**, so an unstamped *managed* doc exists only in a corpus that has never run that migration — a set that is finite pre-1.0 and **empty at the 1.0 pin**, after which stamp-absent means foreign, full stop. This is a **declared bound with an expiry**, on the record, revisited at the 1.0 call — not a silent assumption. **The same discriminator applies to family 3's `un-baselined` advisory** (above): an unstamped, unparseable committed doc at a placement home is a foreign file to *adopt*, not an un-baselined *managed* one.

  **The discriminator's third consumer: the task-scope reconciler (M48 Inc 4).** M42 swept the discriminator through the surfaces that adjudicate the committed store *at store scope* — this fifth family, family 3's `un-baselined` advisory, and `jigc doc list`'s registration state — and **stopped there**. `engine::file_state::reconcile_committed`'s `UNKNOWN` + non-conformant arm, the primitive **every** task-scope door routes committed docs through (`jigc task validate`, the `finalize` preflight, the milestone-boundary gate, the `milestone-record` overwrite preflight), was never reached: it graded **every** non-conformant committed file `reconciliation.conformance-block`, foreign and managed alike. So one file answered **two codes** depending on which door asked, and the stable `(code, target)` key — the thing a driver joins on ([command-output-contract.md](command-output-contract.md)) — was not stable across the doors of one binary. The arm now asks the same question through the same seam: **foreign** ⇒ `schema-conformance.unadopted-instance` with `adoption_route`'s route, byte-identical to the store door's; **managed** ⇒ `reconciliation.conformance-block`, routed on its stamp (below). **Neither branch records**, so the routed-but-not-recorded recurrence the G4 gate exists for is untouched ([project-setup.md](project-setup.md) → Flow 2 hardening). The three inputs the discriminator needs (the manifest version map, the shipped prior shapes, and the `migrate-<ty>`-bearing doctypes the M40 two-tier route conditions on) are **pack facts the engine cannot produce**, so the CLI threads them in at each door exactly as it threads the caller-supplied conflict presentation. **No new check id** — the M21 *"no new check ids"* invariant stands; what moves is which of two shipped codes a foreign file draws. It is a **breaking change to the stable key for the foreign cell only**, which is why it lands pre-1.0.

  **And the managed cell routes on its stamp (M48 Inc 4, T2).** Splitting the *code* fixed half of it. The advisory's **route** — *"ingest, migrate, or move `<path>` out of the managed location to resolve it"* — was written when this arm served foreign ∪ managed, where adoption-or-removal advice was right for the foreign majority. With the foreign half gone it is wrong for **100%** of what remains: every clause tells the operator to adopt or remove **a doc jigc wrote and owns**. What is right depends on exactly one fact — which schema the doc was written against — and both answers are strings this repo already ships, so the fix mints no mechanism and no check id, only a branch on the doc's own [schema-version stamp](#store-scope-schema-conformance--the-fifth-family-m33m34) (read from the raw front matter, as the discriminator reads it — a below-version doc of a structurally-changed doctype is *in* this arm precisely because it does not parse):

  - **at-version** ⇒ the **blocking twin's hand-repair sanction** (*"this is the one case a managed file is yours to hand-edit"*), lifted into one shared source both producers read, so the advisory and its `DRIFTED` twin cannot drift apart. Nothing to migrate; the file really is yours to repair.
  - **below-version**, **stamp-absent** (the v0-era corpus) or **above-current** ⇒ the **[version-aware route](#store-scope-schema-conformance--the-fifth-family-m33m34)** the store door already labels this same doc's findings with. This split is load-bearing rather than decorative: hand-repair advice over a **stale** doc tells the operator to hand-fix what `jigc migrate-corpus` must rewrite, and over an **ahead** one it hides that no verb in this binary can fix a future stamp.

  The sanction is the **default** and the stamp overrides it, so an **unversioned** doctype — where the version-aware labeler returns early, and which the discriminator [never classifies](#store-scope-schema-conformance--the-fifth-family-m33m34) at all — keeps the pre-M48 wording **by construction**, not by a second branch. The four stamp states are the class axis, and the acceptance iterates all four end to end through the real binary over one un-baselined non-conformant managed ADR each (`crates/cli/tests/foreign_at_both_doors.rs`), lifting the at-version route from a `DRIFTED`-arm finding produced in the same run rather than re-typing it.

### In-prose mention integrity — `schema-conformance.mention-resolves` (M33)

A **new check id**, `schema-conformance.mention-resolves` — the lighter, prose-embedded sibling of `ref-resolves`. The store sweep scans each committed doc's **slot prose** for **managed mentions** (`#<type>:<slug>`, `<type>` a known managed doctype — the `:`-plus-known-doctype discriminator means a bare external `#issue-42` is *not* a mention and is never flagged) and reports each whose `<type>:<slug>` names no committed doc, by the same `committed_reachable` rule the `ref-resolves` families use ([document-type-schema.md](document-type-schema.md) → In-prose mentions). Unlike the other store-scope families, it is **genuinely new** (a prose scan, not one of the structural families), so it earns **one new check id** — default severity **advisory** (a cascade knob), **store-scope only** (the cross-doc backstop — a mention dangles when *another* doc is renamed/deleted), **never a per-task finalize gate**. That advisory, store-scope-only placement is exactly what "lighter than `field`-refs" means: field-refs (`ref-resolves`) block at finalize; mentions advise at store scope. Doc-level only in v1 (section-anchor mentions deferred).

### Blocking semantics — the proof is the *blocking* case

`code-anchor` fields are **optional**. The probe **blocks** when an anchor is *present but unresolvable* (points at a file/symbol/test that does not exist) — the exact mirror of the proven `ref-resolves` "blocks when it dangles" pattern (M1 `supersedes`, M3 `implements`). A doc with *no* anchor is not a `doc-code` block (an "uncovered criterion" advisory is a deferred stretch). The acceptance proof ([worked-examples.md](worked-examples.md) → flow 13) is therefore the **blocking** walk: a `maps-to-test` pointing at a deleted test → `finalize` blocks; pointing at a real test → passes. A happy-path-only acceptance would be a masking test.

### Architecture — subprocess from the start, engine stays shell-free

M10 ships `doc-code` as a **subprocess** (not an in-process prototype) — the only path that genuinely satisfies the determinism contract, since the timeout/crash/malformed-output meta-findings are *defined over the subprocess wire* (an in-process fn has no exit code, no JSON to malform, no clean timeout — it would *waive* them). The split respects the engine's shell-free invariant ([module-layout.md](../implementation/module-layout.md) → Probe boundary):

- **The engine owns** the reshaped `Probe` seam (a `target` + a *serializable* effective-state ctx), the effective-state snapshot it materializes in the probe's read scope, ingestion of the probe's findings into the `ValidationReport`, and synthesis of the meta-findings.
- **The CLI owns** the subprocess invoker (`std::process::Command` + a wait-timeout) — so no engine module shells out. The `doc-code` executable is a **separate program** (tree-sitter-based), wired in because the schema's `code-anchor` leaf implies it (`code-anchor ⇒ doc-code`).

## Severity inventory

Every MVP check ships with a **declared default severity** and an **intrinsic-or-tunable** classification. The cascade can promote or demote a *tunable* check's severity; it cannot demote an *intrinsic* check below `blocking`.

### The two-tier rule

- **Intrinsic** — the determinism boundary cannot survive demotion. Locked at `blocking`. **Mechanically (M6): the check's knob carries `floor: blocking`** ([overrides.md](overrides.md) → Locked keys; the per-key floor is a `KnobDecl` field). The floor *value* and severity *assignment* are pack/cascade-driven, but the engine **also asserts at pack-load that its known intrinsic check-id set each carries `floor: blocking`** — a mis-declared pack (an intrinsic check left unfloored) fails loudly at load rather than silently un-locking. (The asserted set is the **live-keyed** intrinsic checks; a documented-but-deferred row carrying no `knobs.yaml` key — `pack-probe-integrity.sandbox-violation` until OS-level sandboxing ships — is not in the asserted set, since it has no knob to floor.) This is legitimately engine knowledge: the intrinsic checks *are* the engine's own load-bearing invariants ([What "intrinsic" means mechanically](#what-intrinsic-means-mechanically)), and the assertion is *assertion-only* — it never assigns severity or ships pack content, so the engine-empty invariant holds. A `scalar-set` attempting to set the key below its floor is **soft-rejected at cascade resolution** (the offending delta is dropped, not applied; resolution continues; visible via `--explain`). This is distinct from setting an *undeclared* key, which stays a hard resolution error.
- **Tunable** — cascade can promote or demote freely (its knob declares no `floor`, or a floor it sits above). Use a `scalar-set` keyed `validation.<probe>.<check>.severity: <level>` for per-check tuning, or `validation.<probe>.severity: <level>` to set a default for every check under a probe. **Per-check wins** via a deliberate three-step lookup (M6): the post-pass resolves a finding's severity by trying its per-check key, then the per-probe key, then the knob's declared default — *not* plain exact-key resolution (which has no prefix fallback).

### What "intrinsic" means mechanically

An intrinsic check is one whose demotion would break a load-bearing invariant of the system itself:

- **`workflow-refs.*`** — composition would emit broken / ambiguous / cyclic output to the agent. The structural-determinism bet fails at the surface where compliance actually happens.
- **`schema-conformance.*`** — the four schema-driven integrity checks at finalize, **plus `schema-version-current` (M42)**. Forward-ref resolution is the integration advantage's mechanical floor; required-slot / required-field presence is what makes a schema meaningful at all; field-value conformance is the field-type adjudication that distinguishes structured values from prose. `schema-version-current` is intrinsic on a different axis, and it is the one intrinsic check whose bite is **store-scope**: a corpus below its manifest version means *every other check in this sweep is adjudicating docs against a schema they were never written to*, so demoting it would let a project silently opt out of knowing that its own validation results are meaningless — the trustworthiness floor, the `pack-probe-integrity.*` rationale applied to the schema rather than the probe. (It is also what the store-scope exit flip keys on, so a demotion would silently disarm that too.) The three presence/value checks (`required-slot-present`, `required-field-present`, `field-value-conformant`) adjudicate **both simple and repeatable** sections — **per item** over a repeatable block's leaves, the `id-from` heading field exempted (it is the heading text, never a trailing bullet), findings addressed at `#section/item/leaf` (M16; [Repeatable-section conformance](#repeatable-section-conformance-m16) below).
- **`pack-probe-integrity.*`** (M10) — a probe that timed out, crashed, or returned malformed output **cannot be trusted to have validated anything**, and a missing finding could mask a real integrity error. Demoting these would let a misbehaving probe pass silently — the determinism boundary applied to the probe interface itself. (`sandbox-violation` joins them when OS-level sandboxing ships.)
- **`owner-artifact.present`** (M16) — a `completion-record` whose owner-assigned artifact is absent would let a milestone finalize with no recorded audit artifact (the source workflow's bar: *"not shippable until this artifact exists"*). Demoting the gate would defeat the completion-half backstop. It asserts **presence** at a safe owned-location path, **never** the artifact's bytes — the determinism boundary holds (it brackets the genuine-audit judgment, never mechanizes it; [methodology-docs.md](methodology-docs.md) → the honest bound).

Tunable checks protect themselves with their *route* and *default severity*, not with lock semantics: `file-state` drift routes to reconciliation (so demotion just means "absorb silently" — still safe); `inverse-cardinality` is advisory at task scope by design (because completeness depends on other tasks); commit line-limits are conventional and a project may rationally not want them enforced.

### Synthetic categories

`schema-conformance`, `schema-completeness`, `commit-rendering`, and `changelog-recording` (M42) are **synthetic probe categories** — not literal probes with a `check(target, ctx) → [finding]` implementation, but namespaces for cascade-key consistency. The engine runs these checks as part of other pipelines (the parse + schema-validate path for `schema-conformance`, the edge-index walk for `schema-completeness`, the commit-doc renderer for `commit-rendering`, the finalize-time create-gate tabulation for `changelog-recording`). The cascade key naming is uniform regardless of whether a check sits in a literal probe or a synthetic category — a project tuning severity doesn't need to know the implementation detail. **This is exactly why severity assignment is a post-pass** (below): a synthetic check has no `check()` site to thread a cascade read into, but it still produces a `Finding` carrying a `(probe, check)`, so the engine's aggregate post-pass tunes it identically to a real probe's finding.

### Repeatable-section conformance (M16)

`schema-conformance`'s three presence/value checks adjudicate **every item of a repeatable section**, not just simple sections. The MVP path validated only `Simple` bodies (an unconditional skip past non-`Simple` section bodies); **M16 lifts that limit** so each repeatable item is conformance-checked over its block leaves:

- **`required-slot-present`** — every required slot of the item is non-empty;
- **`required-field-present`** — every required field of the item carries a value, **except the `id-from` source field**, which renders as the item's `###` heading rather than a trailing bullet (mirroring the parser's heading-field exclusion — [document-type-schema.md](document-type-schema.md#sections-and-repetition)); checking its presence as a bullet would false-fail every conformant item;
- **`field-value-conformant`** — every present item field's value conforms to its declared type (date / enum / string-shape).

Findings address at **`#section/item/leaf`** (the M13 fragment vocabulary), so a malformed entry is located precisely inside the document. The checks stay **intrinsic blocking** (above) and share the simple-section `schema-conformance.*` cascade keys — no new inventory rows.

**Conformance-only — ref-edges are out of M16.** No M16 doctype carries a *per-entry managed `ref`* ([methodology-docs.md](methodology-docs.md) → Relations), so this lift covers only presence/value conformance. The `ref-resolves` walk over a *repeatable-item* edge — and the per-item edge-identity question it raises — stays **deferred** to the first co-composition milestone that puts a managed ref inside a repeatable item; M16's "validate against reality" rests on per-item conformance (every entry well-formed), not per-entry ref-resolution.

### The changelog-gate advisory (M42)

**Settled at M42 planning (2026-07-13; [DECISIONS.md](../DECISIONS.md) → the Settle, fork 6).** The adoption trial finalized an unambiguously user-facing fix bundle with **no changelog entry**, and asked for the call to be made: *"if it's optional, I'll skip it; if it matters, gate it."* The answer is a **finalize-scope advisory**, `changelog-recording.gate-granted-unused` — it **surfaces without refusing**.

- **It keys on the *gate*, never on the diff.** The finding fires when the task's workflow **grants** the `changelog` create-gate (`allows-create`) and the task recorded **no** entry against it. It does **not** fire on "the CLI thinks this change is user-facing" — that is judgment, and the determinism boundary forbids the CLI from making it ([VISION.md](../VISION.md) → the determinism boundary). The pack decides which workflows record a changelog by granting the gate; the check only reports that a granted gate went unused.
- **"Recorded an entry" is a *write-touch*, not an item count (M46).** The check keys on the **write-touch**: the task's staged changelog is compared against its **un-authored baseline** — the bytes the staging primitive materialized at first touch, discriminated on the *recorded provenance* rather than on what is on disk (a doc this task **created** → the pristine skeleton, rebuilt through the mint's own renderer; otherwise → the committed bytes under the one canonicalization the copy-in applies) — and **any** staged write that lands bytes over that baseline is the entry: a new change-group, a retracted one, a retitled release, a corrected `date`, rewritten `notes`. The predicate this replaces compared repeatable-**item counts**, so every write that leaves the count standing still recorded an entry the check refused to see (the trial's F-1, [findings-verification.md](../completions/artifacts/RC-1.0-gate/findings-verification.md) §1) — which is the check adjudicating the *diff* by proxy, the one thing the bullet above says it never does. Two cases read as *no* entry and are meant to: a bare `jigc doc create changelog` materializes exactly that baseline (create-and-abandon is the silent skip this check exists to surface), and a **refused** write leaves the same copied-in bytes behind. An unresolvable baseline (a vanished committed source) keeps the advisory **on** — an unprovable write is not a recorded entry, and this is an advisory either way.
- **Reported at both doors, computed at both entry points (M46).** It is a member of the previewed set, so `jigc task validate` computes it at phase 2 and `finalize` computes it again at its own position — the same check at the same severity, reported twice and never merged twice ([finalize.md](finalize.md) → 2. Validate). It ran on the committing path only until then, which left the surface that promises *"see what's left before committing"* one member short of the truth — and, under the one cascade line that promotes this row to `blocking`, left a project reading a clean `task validate` over a state `finalize` was about to refuse. The **route** is the door's, because which verbs are alive differs by door: the preview door leads with the in-task verbs (the working area is open there), the landing `finalize` door prints the landed-state form alone (`.jigc/tasks/<id>/` is gone by then), and a promoted gate — which refuses, and so leaves the task open — names the in-task verbs plus the one exit a change that is *not* user-facing has, since an advisory's *"no action is needed"* clears no blocking finding.
- **Advisory, and tunable *upward*.** The default is advisory (surfaced at both doors, never blocking) — but it is a **keyed** row, so a project that means it (the trial's *"if it matters, gate it"*) promotes it to `blocking` with **one cascade line**, not a code change. That is the same *calibration-is-config* posture M40 used to demote `title-names-symbol`, run in the other direction.
- **It is separable from the discoverability bug it was found alongside, and it does not subsume it.** The pack fix — splitting the changelog paragraph into a step included **only** by gate-granting workflows — repairs a genuine defect on its own (`step:implement` instructs a `jigc doc create changelog` that `implement-from-spec` and `sub-task` *refuse*, since neither grants the gate). That fix makes the prompt *disappear* where the gate is absent; this advisory makes the *skip* visible where the gate is present. Neither replaces the other.
- **Its `target` is the *task id* — declared, because the default would be a degenerate key.** The finding's **subject is a work unit, not a doc**: it says *this task's granted gate went unused*. So it fits neither the `<type>:<slug>#<fragment>` URI normal form nor the `file-state` path exception — and a finding with no declared address ships as `target: null`, which under the stable `(code, target)` key would collapse **every skipped changelog in the corpus onto one key** ([command-output-contract.md](command-output-contract.md) → The stable finding key). Shipping that in the same wave that *fixes* exactly this defect for the `write.*` family would be self-refuting, so it is pinned here at its mint: **`target` = the task id** — the work-unit identity, stable and opaque, the same value the composed-output `task` key and the task-verb acks carry (that doc's normalization table owns the doc-subject families and the *task*-subject form; this check's row is its data, not a second table).

## Severity assignment — the M6 post-pass

Severity is assigned in **one engine-owned pass over the aggregated findings**, *after* every probe and synthetic pipeline has run — never threaded into each probe site. This is what "the engine assigns, the probe suggests" means concretely, and it is the design that makes the synthetic categories, the inline `workflow-refs`/`schema-conformance` emissions, and the non-task `override-default` all tune through one mechanism.

- **A `Finding` carries `(probe, check)` as structured fields** (M6 — alongside the existing `code`/`message`/`route`; the dotted `code` is retained for rendering but is no longer the severity handle). The pre-M6 finding had only a dotted `code`, and the built codes did **not** all parse to a clean `<probe>.<check>` (e.g. `override-default.content-changed` vs the inventory's `target-unchanged`; `file-state` emitting `reconciliation.*`), so the handle is made explicit rather than parsed.
- **Override-only-on-explicit-delta.** The post-pass overrides a finding's severity **only when the resolved cascade actually carries a `scalar-set` for that finding's key** (per-check, then per-probe — the three-step lookup above). Absent any delta, the finding keeps the **hardcoded default** the probe emitted. This makes the **no-override path byte-identical** to pre-M6 output *automatically* — the determinism boundary's #1 risk for this milestone — and sidesteps any need for `knobs.yaml` defaults to exactly mirror the code's literals (the knob `default` exists for `check_value`, the floor, and `--explain`, not the hot path).
- **Matched by inventory `(probe, check)` membership, never by code-prefix.** A finding is tuned only if its `(probe, check)` is an inventory row. The per-probe fallback step applies *only* to findings whose check has a row — so an unkeyed sibling carrying a category-prefixed code (e.g. `schema-conformance.unknown-type`, or the parser's `conformance.*` codes — neither in the inventory) is **exempt from the post-pass entirely** and keeps its emitted (blocking) severity. A per-probe key never accidentally catches a determinism-boundary code that has no row.
- **Assigned once, at report construction — before the gate.** Severity assignment runs as the single construction point of the `ValidationReport` (`ValidationReport::new(findings, &resolved)` — or an explicit assignment the contract requires before any read), so `has_blocking()` and every downstream consumer see *post-pass* severities. There is no window where a caller reads a finding's pre-assignment severity. A test pins that `has_blocking()` reflects the assigned severities (a demoted blocking check stops gating; a promoted advisory one starts).
- **The gate itself is unchanged.** `finalize` still blocks on `severity == blocking` ([How it gates `finalize`](#how-it-gates-finalize)); once severity is cascade-assigned at construction, a demoted check simply stops being blocking with no change to the gate predicate.
- **Every finding-emitting entry point must resolve the cascade.** Compose already builds a `Resolved`; **`task validate` / `finalize` and `jigc upgrade` do not today** and must gain one to feed the post-pass. Building a `Resolved` at those entry points is itself behaviour that must not perturb the no-override path, so the **byte-identical golden must cover the validate and upgrade paths**, not only `start_compose` — the determinism guard's real surface this milestone.

**`warning` is a live third tier (M6).** Pre-M6 only `blocking`/`advisory` were ever produced. M6 makes `warning` a settable, produced severity: it is **surfaced but non-blocking** (the gate keys on `blocking` only), rendered distinctly from `advisory`. A check demoted `blocking → warning` still appears in every report and `--explain`, but does not stop `finalize`/`upgrade`.

## The non-task `Probe` seam (M6)

M6 stands up the `Probe` seam (`probe.rs` is a stub today) **minimally** — shaped to fit `override-default`, not as a universal trait forced over every existing probe. `validate_task`'s proven inline probes (`file-state`, `schema-conformance`, `ref-resolves`) stay wired as they are; they become severity-tunable purely via the post-pass above, with **no rewrite of the byte-stable task path**. The seam's job is narrower: give a **non-task-scoped** probe (one whose ctx is `(recorded deltas, pack)`, not a task working area) a first-class entry point so it participates in aggregation + the post-pass.

- **`override-default` is the retrofit.** M5 ran it as a bespoke `classify(deltas, pack)` call inside `jigc upgrade`; M6 routes it through the seam and threads the resolved severity lookup into it, so its three checks tune via `validation.override-default.*.severity` like any other. `upgrade_in_repo` is the only production caller, so the retrofit touches one CLI seam.
- **Two ctx shapes, not one trait over both.** Task-scoped and override-scoped probes consume structurally different inputs; the seam admits the non-task shape rather than coercing both into a single generic ctx (the over-generalization trap M3 paid for). A future store-scoped probe extends the seam then, when a real consumer exists.

## How it gates `finalize`

`finalize` ≡ `validate(task) + the commit-time gates + commit`: one engine, two entry points, so every check `validate` runs is a check `finalize` blocks on — `jigc task validate` **previews the finalize gate up to the commit** (M47). It is a preview of that much, not a prediction of the commit: the preflight *before* it (the base pin) and the phases *after* it adjudicate their own failures — the staged set, render and promote, staging itself, and the commit (the hook) — at a **different position in the same transaction, not under a different scope** ([finalize.md](finalize.md) → 2. Validate; [command-output-contract.md](command-output-contract.md) → The exit-code taxonomy). `finalize` blocks on **blocking-class findings within the task scope**; advisory findings are surfaced but don't stop the commit. `finalize` defaults to autonomous (a cascade-settable confirm-gate aside), with git/PR as the durable correction point.
