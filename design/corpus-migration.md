# Schema freeze & managed-corpus migration (M33 + M34)

The **productive-readiness pair**. M33 declares the doctype set + schema-definition format a **frozen v1** and makes the freeze *enforced, not asserted*; M34 builds the **automated path to migrate a managed-document corpus** across a v1→v2 schema change, so the lock-in cost a productive adopter inherits is *bounded* rather than open-ended. They are planned together because they are coupled at the seam: M34's transform migrates *onto* the v1 shape M33 declares. They **build as two sequential milestones, M33 first**: M33 completes + freezes the v1 shape and enforces it **dev-side** (a schema change can't silently ship — the manifest + pack-load assertion, self-contained); M34 then builds the **corpus-side** machinery (detector + transform + stamp) that lets a *blocked* change be migrated rather than only blocked ([DECISIONS.md](../DECISIONS.md) → 2026-06-24 M33 + M34; charter [roadmap.md](../implementation/roadmap.md) → M33/M34).

This doc owns the **version stamp**, the **store-scope conformance detector**, the **deterministic transform**, and the **freeze declaration + discipline**. It is the managed-corpus sibling of [auto-migration.md](auto-migration.md) (foreign-doc *adoption*) — and the distinction is load-bearing, below.

## Why this is net-new, not a reuse (the baseline audit's correction)

The original M34 charter assumed *"reconciliation already provides the detect half; M34 adds the transform arm."* The baseline audit (2026-06-24, exercised on the real binary) **refuted that**: store-scope `jigc validate` runs four integrity families — doc↔code, workflow↔refs, file↔CLI-state (**hash-only**), cross-doc ref-resolves — and **none re-parses a committed doc against its schema**. M33 has since added two more store checks — `schema-completeness.inverse-cardinality` (completeness) and `schema-conformance.mention-resolves` (a prose scan) — but neither closes the gap: `mention-resolves` only **scans slot prose for managed mentions**, it does **not** run `schema_conformance` (required-slot / required-field / field-value / ref-resolves) over each committed doc (verified: `conformance_for` is wired at task scope only). So no store family re-parses a doc against its full schema. A doc made non-conformant by a *schema* change while its **bytes are unchanged** still passes `validate` clean (exit 0, verified). Full schema-conformance runs only at **task scope** (`finalize` / `jigc task validate`), only over docs a task touches.

So the genuine value-flow — *a managed corpus at v1 → a schema-shape change ships → the now-non-conformant corpus is detected, blocked, and migrated* — is broken at **step one** today. Both halves are net-new:

| Piece | State today | M33/M34 builds |
|---|---|---|
| Store-scope **schema-conformance detector** | absent (`mention-resolves` scans prose only; no store family runs full `schema_conformance` per doc) | the **fifth content family** ([validation.md](validation.md)) |
| Per-doc **schema-version stamp** | absent (only result-JSON `schema_version`) | a schema-declared, engine-valued front-matter field |
| **Schema-diff** | absent (`Schema` derives `PartialEq` only) | a v1→v2 delta classifier |
| Deterministic **transform producer** | absent (`migrate` is LLM foreign-adoption) | schema-diff-driven byte-stable splices |

## The determinism boundary holds (the auto-migration distinction)

[auto-migration.md](auto-migration.md) (`jigc migrate`) adopts a **foreign** document into a **fresh** managed doc: the LLM rewrites un-CLI-verifiable prose, the CLI strict-parses + conformance-gates + adopts, with a human fidelity gate. It is one-file-one-`--as`, never re-opening a managed doc.

M34's corpus migration is the **opposite shape**: a *conformant managed v1 doc* → a *structurally re-rendered v2 doc*, over **N instances of a type at once**. Its source is already canonical (no fidelity gate needed), and the transform is **largely deterministic and CLI-owned**:

- **Structural changes are CLI-owned, no LLM** — *add optional field*, *widen cardinality* (`0..1`→`0..*`), *fixed-slot→repeatable-with-default*. These are computed from the schema-diff and applied as **byte-stable splices** over the proven `write.rs` primitives. The prose is **unchanged**; routing a structural-only bump through an LLM would be lossy, non-deterministic, *and a determinism-boundary breach* (the CLI owns structure — [VISION.md](../VISION.md) → the determinism boundary). This is why reusing `migrate`'s re-author path was **rejected**.
- **Prose-needing changes route to the agent** (Framing A) — a *new required slot* has no deterministic default; the CLI mints the empty slot and the migration workflow routes it to the agent to author, exactly as a `create` flow does. The CLI never authors the prose; it owns only placement and the conformance gate.

The boundary is the same one [auto-migration.md](auto-migration.md) draws; only the *source* (managed-canonical vs foreign) and the *deterministic fraction* (high vs low) differ.

## The schema-version stamp — schema-declared, engine-valued

A managed doc must record **which schema version it was authored against**, so the detector can tell a *known-old-version* doc (migrate it) from a *genuinely-corrupt* one, and so the transform knows its starting point. The stamp is **per-doc, recording the doc's *own doctype* version** (not a global doctype-set version), matched against that doctype's entry in the manifest.

**Shape: a field declared in each doctype's schema, with an engine-supplied value** — the `status`/`date` model (in-schema field, engine-set value). The engine injects the declaration uniformly across all doctypes (no N hand-edits), and a new **"current active schema version" deriver** supplies the value at create time. The crucial reason it is **in-schema, not out-of-schema** (review Finding 1): the migration transform is driven by a **schema-diff over two `Schema` values**, so an out-of-schema engine/manifest field would produce *no* `added-field` classification and the schema-diff classifier — the riskiest net-new code — would get only synthetic coverage. In-schema makes the stamp a *real* `added-field` migration — and **the one genuinely live add-field case** (no post-freeze shape change is pending; everything else is already v1), so the stamp dogfood is where the transform's **`add-field` branch earns its end-to-end proof** (the branch-split — [DECISIONS.md](../DECISIONS.md) → 2026-06-25 reconciliation). The spike that shaped the rest: **`prd` and `changelog` render zero front-matter** (no `header:` section), so the stamp **introduces a `---` block that never existed** for those two — a real v0→v1 shape change; **`spec` already carries a `meta` header** (M33's `derived-from` field, commit `3c859c6`), so its stamp adds a field to an *existing* `---` block.

> **Two senses of "stamp" — keep them distinct.** This **schema-version stamp** is a durable, in-doc front-matter field. It is *not* the edge-index **cache-stamp** (`storage.md` → the index's HEAD-sha marker), which is a rebuildable-cache freshness marker carrying no schema version. The migration reads and writes the former; the latter stays a cache concern.

Two consequences the build must carry:

- **The deriver is net-new.** Today the on-create deriver produces a value only for `Date + set:on-create` (the clock) else a literal `default`; there is no "live schema version" deriver. ([storage.md](storage.md) → front-matter; [document-type-schema.md](document-type-schema.md) → the stamp field.)
- **Stamping a committed corpus is the first migration — and a genuine one.** Adding the in-schema field is an `added-field` schema-diff the transform classifies and applies; it churns every doc's `file-state` hash and *introduces front-matter* to the header-less two (`prd`/`changelog`; `spec` already has a `meta` header). **Run as the dogfood case of M34's own add-field transform** (build-order: the transform exists before the stamp lands), so the first real migration proves the transform's `add-field` branch on a real case (the cold-start spike discipline — [milestone-planning-workflow.md](../implementation/milestone-planning-workflow.md) → cold-start state). *(This dev repo carries no committed dev-pack-6 corpus — only methodology doctypes, out of the frozen set — so the dogfood/worked-example runs over a committed dev-pack corpus in a fixture repo, as the e2e flows already do.)*

**The stamp flips *last*, never mid-migration (review Finding 2).** A migration that includes a *prose-needing* change mints an empty required slot and routes it to the agent; if the stamp were bumped to v2 *before* that slot is authored, the conformance detector would read the in-flight doc as `at-version + missing-required-slot` ⇒ **corrupt**. So the stamp flips to the new version **only after** every structural splice *and* every prose-pending slot is authored and the migration-upgrade gate passes the doc as conformant. An in-flight doc therefore always reads `below-version ⇒ migrate`, never `corrupt`.

## The store-scope conformance detector — the 5th `validate` family

The detect-half. The **fifth content family** that re-parses **every committed doc against the current resolved schema** and reports each non-conformant instance — the full-`schema_conformance` analog the four integrity families never covered for *schema* shape (M33's `mention-resolves` is store-scope `schema-conformance` but prose-scan only, not a per-doc re-parse). Designed in [validation.md](validation.md) → Store-scope schema-conformance (the fifth family). Key properties, pinned:

- **Verified clean lift.** `conformance_for` / `schema_conformance` (`validate.rs`) are **pure functions** over `(filename, schemas, rel_key, source)` — no working-area, no `reconcile_committed_store`, no task context (confirmed by spike). Fed the committed docs + the current schemas, they fire `schema-conformance.{required-slot,required-field,field-value,ref-resolves}` over stale docs. The committed-doc walk already exists (`file_state::detect_committed_store`); the family reuses **that** doc-walk, *not* the anchor-scoped `enumerate_committed_surface`.
- **Scope pin (M4 lesson — state the surface the check fires against).** The family fires over the **whole committed store, every instance**, and is **report-only at store scope** (exit 0), exactly like the other store-scope content families — `jigc validate` stays a read command that never gates a transaction ([validation.md](validation.md) → Exit semantics). A version-mismatch (doc stamped < manifest v1) is surfaced as the *migrate* route; a conformance break with no version explanation is surfaced as *corrupt*.
- **No new severity surface** — `schema-conformance.*` check ids already exist (the M20/2026-06-23 pattern: same id, store/read-only scope, no knob growth).

The **blocking** counterpart is the **migration-upgrade gate** (below), which fires at the *transform transaction boundary*, not at `validate`.

## The deterministic transform — schema-diff → byte-stable splice

1. **Schema-diff.** A v1→v2 delta classifier over two `Schema` values, classifying each change by kind: `added-optional-field`, `widened-cardinality`, `fixed-slot→repeatable-with-default`, and **`prose-needing`** (a new *required* slot/field with no deterministic default — the Framing-A escape hatch). Net-new (`Schema` derives `PartialEq` only; no comparison code exists).
2. **Transform driver.** Consumes the classified diff and emits a sequence of byte-stable splices over `write.rs` primitives (`splice`, `set_field`, `add_item`, `nested_repeatable`). The one **net-new primitive** is **fixed-slot→repeatable-with-default**: promote a physical `<<slot>>` into a repeatable item-block carrying the old slot content as the default first item (`add_item` assumes the section is *already* repeatable; the promotion is unexercised today).
3. **Prose routing.** A `prose-needing` change mints the empty slot and routes it to the migration workflow's agent step (Framing A); the CLI conformance-gates the result.

## Prior-schema sourcing — the versioned snapshot store (Inc 4)

The schema-diff needs **two real `Schema` values**. For the v0→v1 stamp (Inc 3) the prior shape is derivable in-process (`from = strip_stamp(current)` — the stamp is the only v0→v1 change). But a genuine v1→v2 **structural** change cannot be derived from the current schema: the verb needs the *actual prior shape*. So the pack **stores prior schema shapes as versioned snapshots**, and the verb sources `from` keyed on each committed doc's stamp. This is what makes the structural transform branches (built + unit-proven since Inc 2) reachable through the shipped `jigc migrate-corpus` verb — without it they are engine-substrate-only ([DECISIONS.md](../DECISIONS.md) → 2026-06-25 M34 audit Finding 1).

- **Storage (settled):** a dedicated **`schema-snapshots/<type>.v<N>.yaml`** pack resource kind — each snapshot a *full, real, reviewable schema file* (honoring the "plain, diff-friendly files" invariant; the determinism boundary in its strongest form — the diff is over two genuine declared schemas, never a hand-written migration recipe). It lives **outside `schemas/`** by necessity: the freeze gate enumerates `schemas/` and keys by doctype, so a snapshot there would collide on `type` and break the 6-doctype freeze assertion. The freeze manifest stays the `type → version + hash` declaration, untouched; snapshots are a separate kind, invisible to it.
- **`from`-selection (per committed doc, by stamp):** stamp **absent** → `strip_stamp(current)` (the unchanged v0→v1 pre-stamp path — keeps the Inc-3 dogfood green); stamp **`k`, `1 ≤ k < current`** → load `schema-snapshots/<type>.v<k>.yaml`; a **missing** snapshot **blocks** that doc with a route (never a silent `already-current`).
- **The stamp value-bump (the v1→v2 transition, distinct from the v0→v1 add).** A present-but-below stamp is *updated* to the current version via `write::set_field` (the field already exists — `added-field` only covers the absent case). This closes the Inc-3 detector/verb divergence ([DECISIONS.md](../DECISIONS.md) → Finding 2): a doc the detector routes `migrate` (stamp absent **or** below) is migrated by the verb, never reported `already-current`.
- **Snapshot integrity (deferred, bounded).** Prior-version snapshot hashes are **not** frozen in the manifest in v1: a drifted snapshot fails the migration transform/round-trip loudly (the acceptance catches it), so a second hash gate is premature. Revisit when a real v1→v2 migration ships and the snapshot set grows.

## Completing v1 — the five schema-engine opens

The freeze is a **one-way door**: anything not in v1 returns only through a breaking migration. So the robust cut is a *complete, correct* v1 — all five deferred schema-engine opens are **built into v1**, not deferred past the freeze (the cheap path that guarantees a future migration). The one genuine *schema-shape* change among them, the `spec.derived-from` ref, **shipped in M33** (commit `3c859c6`) and is now part of frozen v1 — so it is **not** an M34 transform case (the change already happened pre-freeze; [DECISIONS.md](../DECISIONS.md) → 2026-06-25 reconciliation). Because no post-freeze shape change is yet pending (the freeze working as intended), M34's transform earns its end-to-end proof on **reconstructed historical** shape changes plus the one live add-field (the stamp); see [the increments](../implementation/roadmap.md) (M34 Inc-2/Inc-3) for the branch-split.

| Open | What v1 gains | Migration case |
|---|---|---|
| **prd→spec — stored spec-side as `spec.derived-from → prd`** | the doctype-graph edge the [doctype-map](../implementation/doctype-map.md) intends, modeled the way it was **settled at M9** ([project-setup.md](project-setup.md) → the spec-side `derived-from`, inverse derived never stored; [document-type-schema.md](document-type-schema.md) → `spec.derived-from → prd, card, inverse: has-specs, inverse-card: "1..*"`). The ref lives on the **spec** (a new spec header field — introduced a `---` block to `spec` in M33); the PRD's `has-specs` is the **derived inverse**, never stored, so PRD-first authoring never deadlocks | **shipped in M33** (commit `3c859c6`) — now frozen v1, **not** an M34 transform case; the M34 headline is the reconstructed `prd.requirements` fixed-slot→repeatable reshape instead (the riskiest net-new primitive) |
| **repeatable-item managed-ref edges** | a `ref` field on a repeatable item resolves through the edge index (today `index.rs` skips non-simple sections — silently inert); a **general edge-extractor completion** (no longer prd→spec's substrate — that edge is doc-level, spec-side) | byte-neutral to build (one edge-extractor branch); no instance-byte change, no migration penalty |
| **inverse/min-cardinality** | enforced completeness ("a PRD must have ≥1 spec"), realized as the **inverse-card `1..*` on `has-specs`** — counting each PRD's *inbound* `derived-from` edges at store scope (the `schema-completeness.inverse-cardinality` check, store-scope advisory, never a per-task finalize gate — [document-type-schema.md](document-type-schema.md) → :128) | settles the v1 schema metadata (`inverse-card` declarations — a schema-hash change, byte-neutral to instances) |
| **in-prose mentions** | the `schema-conformance.mention-resolves` check — a managed mention `#<type>:<slug>` in slot prose that names no committed doc is reported (advisory, store-scope; external `#issue-42` never flagged). Settled M33 ([document-type-schema.md](document-type-schema.md) → In-prose mentions) | additive validation feature — no instance-byte change; in v1 for completeness |
| **schema-fragment `include`** | de-duplicates the `changelog` change-group block; a clean frozen schema-definition format | additive format feature — no instance-byte change; in v1 so the frozen format is clean |

Only the **`spec.derived-from` ref** is a schema-shape change (it adds a field to `spec`), and it genuinely belonged *before* the freeze; the other four are byte-neutral engine/format/validation completions (no migration penalty to defer) built into v1 anyway for a complete frozen baseline ([DECISIONS.md](../DECISIONS.md) → 2026-06-24 M33 + M34). **Forward `card` of `derived-from` shipped at `0..1`** (M33 Inc-2, commit `3c859c6`) — the deadlock guard: it is never author-required, so a legitimately PRD-less spec stays valid; the "PRD ≥1 spec" obligation rides the *inverse-card*, store-scope, not the forward card.

## The freeze — declared *and* enforced

M33's deliverable is **declaration + enforcement**, not prose discipline:

- **Declare the doctype set + schema-definition format v1-complete.** The format (`id-from`/`card`/`set`/`of`/`header`/`to`/`inverse`/`inverse-card`) is already **shipped + golden-locked** ([document-type-schema.md](document-type-schema.md)) — M33 *formalizes* it, and corrects the stale "placeholders pending implementation" line as the act of declaring. The frozen *set* is the persisted doctypes enumerated in [doctype-map.md](../implementation/doctype-map.md).
- **A versioned, hashed doctype-set manifest.** An enumerated `doctype → schema-version + schema-hash` artifact, so the freeze can *self-enforce*: a schema-shape change that bumps no version + ships no M34 migration is **blocked**, rather than caught by review. This is the net-new artifact that makes the discipline mechanical.
- **The enforcement gate fires at pack-load / build time, not at `validate` (review Finding 3 — scope pin).** It is an **engine assertion** that recomputes each shipped doctype's `schema-hash` and compares it to the manifest, failing **loudly** on a mismatch — the sibling of the existing intrinsic-floor assertion ([validation.md](validation.md) → Severity inventory), *not* the report-only `validate` store sweep (which exits 0 and would never gate). A hash mismatch with no bumped manifest version is the un-migrated schema change the freeze forbids; the fix is to bump the version + ship the M34 migration (or revert). This firing surface is **pinned now** even though the manifest's on-disk home/format is settled at the increment that builds it.
- **Convergence is evidence, not a promise.** Beyond the gate, the freeze is *proven* by a defined run of milestones with zero schema-shape commits — tracked after the declaration, not gated inside M33.

## Acceptance flows (spiked against the real binary)

The engine-behaviour claims these flows encode were **exercised at Scope** (the baseline audit drove the real binary): store-scope `validate` runs four families exit 0; `conformance_for` is a pure task-less function; `write.rs` primitives are byte-stable; `migrate` is foreign-adoption (not corpus-upgrade). The acceptance flows therefore rest on verified, not assumed, behaviour.

- **The detect flow** — a committed corpus at v1; a schema-shape change ships; `jigc validate` now **reports** every stranded instance at store scope (today: silent, exit 0). The headline regression-retirement.
- **The migrate flow** — the same stranded corpus run through `jigc migrate-corpus`: the **add-field stamp** (v0→v1) applied deterministically byte-stable (Inc 3, proven live); the **structural kinds** (widen-card / slot→repeatable / prose-needing) applied byte-stable for a **v1→v2** change once the verb sources the prior shape from the versioned snapshot store (Inc 4 — proven on the reconstructed M25 `prd.requirements` reshape through the real binary); a prose-needing change routed to the agent; the result conformance-gated and adopted; the stamp value-bumped to the new version.
- **The dogfood flow** — the v0→v1 stamp migration *is* the first add-field transform over the existing corpus.
- **The freeze-enforcement flow** — a schema edit with no version bump is blocked by the manifest check.

These land in [worked-examples.md](worked-examples.md) when the increments build them.

## Open questions

- **Manifest home + format** — *settled (Inc 4).* The freeze manifest stays the pack-shipped `type → version + hash` declaration (`config/schema-manifest.yaml`); **prior schema shapes live as per-version snapshots in `schema-snapshots/<type>.v<N>.yaml`** (a dedicated pack resource kind), sourced by the verb keyed on each committed doc's stamp (Prior-schema sourcing, above). Snapshot hashing is a deferred, bounded robustness option. How `jigc upgrade` relates remains future work.
- **Layout/dialect changes** — this pair scopes *schema-shape* migration; a *directory-layout* or *workflow-dialect* breaking change is a sibling migration class, deferred until a real driver forces it (the `docs-root` move showed layout can shift, but a pinned `docs-root` already mitigates it — [READINESS-ASSESSMENT.md](../READINESS-ASSESSMENT.md)).
