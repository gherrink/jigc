# Schema freeze & managed-corpus migration (M33 + M34)

The **productive-readiness pair**. M33 declares the doctype set + schema-definition format a **frozen v1** and makes the freeze *enforced, not asserted*; M34 builds the **automated path to migrate a managed-document corpus** across a v1→v2 schema change, so the lock-in cost a productive adopter inherits is *bounded* rather than open-ended. They are planned together because they are coupled at the seam: M34's transform migrates *onto* the v1 shape M33 declares. They **build as two sequential milestones, M33 first**: M33 completes + freezes the v1 shape and enforces it **dev-side** (a schema change can't silently ship — the manifest + pack-load assertion, self-contained); M34 then builds the **corpus-side** machinery (detector + transform + stamp) that lets a *blocked* change be migrated rather than only blocked ([DECISIONS.md](../DECISIONS.md) → 2026-06-24 M33 + M34; charter [roadmap.md](../implementation/roadmap.md) → M33/M34).

This doc owns the **version stamp**, the **store-scope conformance detector**, the **deterministic transform**, and the **freeze declaration + discipline**. It is the managed-corpus sibling of [auto-migration.md](auto-migration.md) (foreign-doc *adoption*) — and the distinction is load-bearing, below.

## Why this is net-new, not a reuse (the baseline audit's correction)

The original M34 charter assumed *"reconciliation already provides the detect half; M34 adds the transform arm."* The baseline audit (2026-06-24, exercised on the real binary) **refuted that**: store-scope `jigc validate` runs four integrity families — doc↔code, workflow↔refs, file↔CLI-state (**hash-only**), cross-doc ref-resolves — and **none re-parses a committed doc against its schema**. M33 has since added two more store checks — `schema-completeness.inverse-cardinality` (completeness) and `schema-conformance.mention-resolves` (a prose scan) — but neither closes the gap: `mention-resolves` only **scans slot prose for managed mentions**, it does **not** run `schema_conformance` (required-slot / required-field / field-value / ref-resolves) over each committed doc (verified: `conformance_for` is wired at task scope only). So no store family re-parses a doc against its full schema. A doc made non-conformant by a *schema* change while its **bytes are unchanged** still passes `validate` clean (exit 0, verified). Full schema-conformance runs only at **task scope** (`finalize` / `jigc task validate`), only over docs a task touches.

So the genuine value-flow — *a managed corpus at v1 → a schema-shape change ships → the now-non-conformant corpus is detected, blocked, and migrated* — is broken at **step one** today. Both halves are net-new:

| Piece | State today | M33/M34 builds |
|---|---|---|
| Store-scope **schema-conformance detector** | absent (`mention-resolves` scans prose only; no store family runs full `schema_conformance` per doc) | the **fifth content family** ([validation.md](validation.md)) |
| Per-doc **schema-version stamp** | absent (only result-JSON `schema_version`) | a schema-declared, engine-valued front-matter field |
| **Schema-diff** | absent (`Schema` derives `PartialEq` only) | a v1→v2 delta classifier |
| Deterministic **transform producer** | absent (`migrate` is LLM foreign-adoption) | schema-diff-driven byte-stable splices |

## The determinism boundary holds (the auto-migration distinction)

[auto-migration.md](auto-migration.md) (`jigc migrate`) adopts a **foreign** document into a **fresh** managed doc: the LLM rewrites un-CLI-verifiable prose, the CLI strict-parses + conformance-gates + adopts, with a human fidelity gate. It is one-file-one-`--as`, never re-opening a managed doc.

M34's corpus migration is the **opposite shape**: a *conformant managed v1 doc* → a *structurally re-rendered v2 doc*, over **N instances of a type at once**. Its source is already canonical (no fidelity gate needed), and the transform is **largely deterministic and CLI-owned**:

- **Structural changes are CLI-owned, no LLM** — *add optional field*, *add optional section*, *widen cardinality* (`0..1`→`0..*`), *fixed-slot→repeatable-with-default*. These are computed from the schema-diff and applied as **byte-stable splices** over the proven `write.rs` primitives. The prose is **unchanged**; routing a structural-only bump through an LLM would be lossy, non-deterministic, *and a determinism-boundary breach* (the CLI owns structure — [VISION.md](../VISION.md) → the determinism boundary). This is why reusing `migrate`'s re-author path was **rejected**.
- **Prose-needing changes route to the agent** (Framing A) — a *new required slot* has no deterministic default; the CLI mints the empty slot and the migration workflow routes it to the agent to author, exactly as a `create` flow does. The CLI never authors the prose; it owns only placement and the conformance gate.

The boundary is the same one [auto-migration.md](auto-migration.md) draws; only the *source* (managed-canonical vs foreign) and the *deterministic fraction* (high vs low) differ.

## The schema-version stamp — schema-declared, engine-valued

A managed doc must record **which schema version it was authored against**, so the detector can tell a *known-old-version* doc (migrate it) from a *genuinely-corrupt* one, and so the transform knows its starting point. The stamp is **per-doc, recording the doc's *own doctype* version** (not a global doctype-set version), matched against that doctype's entry in the manifest.

**Shape: a field declared in each doctype's schema, with an engine-supplied value** — the `status`/`date` model (in-schema field, engine-set value). The engine injects the declaration uniformly across all doctypes (no N hand-edits), and a new **"current active schema version" deriver** supplies the value at create time. The crucial reason it is **in-schema, not out-of-schema** (review Finding 1): the migration transform is driven by a **schema-diff over two `Schema` values**, so an out-of-schema engine/manifest field would produce *no* `added-field` classification and the schema-diff classifier — the riskiest net-new code — would get only synthetic coverage. In-schema makes the stamp a *real* `added-field` migration — and **the one genuinely live add-field case** (no post-freeze shape change is pending; everything else is already v1), so the stamp dogfood is where the transform's **`add-field` branch earns its end-to-end proof** (the branch-split — [DECISIONS.md](../DECISIONS.md) → 2026-06-25 reconciliation). The spike that shaped the rest: **`prd` and `changelog` render zero front-matter** (no `header:` section), so the stamp **introduces a `---` block that never existed** for those two — a real v0→v1 shape change; **`spec` already carries a `meta` header** (M33's `derived-from` field, commit `3c859c6`), so its stamp adds a field to an *existing* `---` block.

> **Two senses of "stamp" — keep them distinct.** This **schema-version stamp** is a durable, in-doc front-matter field. It is *not* the edge-index **cache-stamp** (`storage.md` → the index's HEAD-sha marker), which is a rebuildable-cache freshness marker carrying no schema version. The migration reads and writes the former; the latter stays a cache concern.

Two consequences the build must carry:

- **The deriver is net-new.** Today the on-create deriver produces a value only for `Date + set:on-create` (the clock) else a literal `default`; there is no "live schema version" deriver. ([storage.md](storage.md) → front-matter; [document-type-schema.md](document-type-schema.md) → the stamp field.)
- **Stamping a committed corpus is the first migration — and a genuine one.** Adding the in-schema field is an `added-field` schema-diff the transform classifies and applies; it churns every doc's `file-state` hash and *introduces front-matter* to the header-less two (`prd`/`changelog`; `spec` already has a `meta` header). **Run as the dogfood case of M34's own add-field transform** (build-order: the transform exists before the stamp lands), so the first real migration proves the transform's `add-field` branch on a real case (the cold-start spike discipline — [milestone-planning-workflow.md](../implementation/milestone-planning-workflow.md) → cold-start state). *(This dev repo carries no committed dev-pack-6 corpus — only methodology doctypes, out of the frozen set — so the dogfood/worked-example runs over a committed dev-pack corpus in a fixture repo, as the e2e flows already do.)*

**The stamp flips *last*, never mid-migration (review Finding 2).** A migration that includes a *prose-needing* change mints an empty required slot and routes it to the agent; if the stamp were bumped to v2 *before* that slot is authored, the conformance detector would read the in-flight doc as `at-version + missing-required-slot` ⇒ **corrupt**. So the stamp flips to the new version **only after** every structural splice *and* every prose-pending slot is authored and the migration-upgrade gate passes the doc as conformant. An in-flight doc therefore always reads `below-version ⇒ migrate`, never `corrupt`.

## The store-scope conformance detector — the 5th `validate` family

The detect-half. The **fifth content family** that re-parses **every committed doc against the current resolved schema** and reports each non-conformant instance — the full-`schema_conformance` analog the four integrity families never covered for *schema* shape (M33's `mention-resolves` is store-scope `schema-conformance` but prose-scan only, not a per-doc re-parse). Designed in [validation.md](validation.md) → Store-scope schema-conformance (the fifth family). Key properties, pinned:

- **Verified clean lift.** `conformance_for` / `schema_conformance` (`validate.rs`) are **pure functions** over `(filename, schemas, rel_key, source)` — no working-area, no `reconcile_committed_store`, no task context (confirmed by spike). Fed the committed docs + the current schemas, they fire `schema-conformance.{required-slot,required-field,field-value,ref-resolves}` over stale docs. The committed-doc walk already exists (`file_state::detect_committed_store`); the family reuses **that** doc-walk, *not* the anchor-scoped `enumerate_committed_surface`. *(M42: that walk enumerated only `location:`-bearing schemas, so the family silently skipped every **placement** doctype — i.e. exactly the population that can be stale, since both doctypes at schema-version 2 are placement ones — and `jigc validate` exited 0 over an unmigrated corpus. The census is finished and the enumeration is placement-aware; the fix and its discriminator — managed-stale → `migrate-corpus` vs never-adopted-foreign → `ingest` — are owned by [validation.md](validation.md) → Store-scope schema-conformance, the placement sites by [storage.md](storage.md) → Placement.)*
- **Scope pin (M4 lesson — state the surface the check fires against; revised at M42).** The family fires over the **whole committed store, every instance** — since M42 that means *every home*, `location:` **and** `placement:` (above). A **structural / content** break (missing slot, missing field, malformed value, dangling ref) is **report-only at store scope** (exit 0), exactly like the other store-scope content families — for those, `jigc validate` stays a read command that never gates a transaction. **The version-currency break is the exception, and it flips the exit non-zero** ([validation.md](validation.md) → Exit semantics → the third exception; the check id is `schema-conformance.schema-version-current`, minted at M42 precisely so the exit predicate can tell a stale corpus from an invalid enum). *This bullet asserted the opposite until M42 — "**A version-mismatch … is surfaced as the *migrate* route**" under a blanket report-only — and the M42 pass edited the bullet above it while leaving this one, the one that actually **owns** the property, contradicting the new rule.* Recorded rather than silently overwritten: a schema/format doc that contradicts its sibling on the property it owns is the M33 `prd→spec` shape that halted a build. The **routes** are unchanged in kind and re-pointed in detail: a **managed** doc below its manifest version routes *migrate*; a **never-adopted foreign** file at a managed home routes *adopt* (`ingest` / `migrate --as`), gates no door, and — since M46 — **flips the sweep's own exit** (the exit-flipping codes are enumerated by `render::STORE_EXIT_FLIPS`, which prose points at rather than re-counts; M42's exit-0 for this arm is withdrawn where M42 wrote it, [validation.md](validation.md) → the managed-arm bullet); a doc **at** the current version that still does not conform routes *corrupt*. The discriminator (and its declared bound) is owned by [validation.md](validation.md) → the managed-vs-foreign discriminator.
- **No new severity surface** — `schema-conformance.*` check ids already exist (the M20/2026-06-23 pattern: same id, store/read-only scope, no knob growth).

The **blocking** counterpart is the **migration-upgrade gate** (below), which fires at the *transform transaction boundary*, not at `validate`.

## The deterministic transform — schema-diff → byte-stable splice

1. **Schema-diff.** A v1→v2 delta classifier over two `Schema` values, classifying each change by kind: `added-optional-field`, **`added-optional-section`**, `widened-cardinality`, `fixed-slot→repeatable-with-default`, and **`prose-needing`** (a new *required* slot/field with no deterministic default — the Framing-A escape hatch). Net-new (`Schema` derives `PartialEq` only; no comparison code exists). **Two doctype-level kinds added at M38 — `relocated` and `display-title-changed`** (below); these are classified *outside* the per-section loop, because `location`/`placement`/`display-title` are `Schema`-level fields the section-diff never inspects (a pure relocation would otherwise diff to `[]` and silently no-op).
2. **Transform driver.** Consumes the classified diff and emits a sequence of byte-stable splices over `write.rs` primitives (`splice`, `set_field`, `add_item`, `nested_repeatable`). Two **net-new primitives**: **fixed-slot→repeatable-with-default** (promote a physical `<<slot>>` into a repeatable item-block carrying the old slot content as the default first item — `add_item` assumes the section is *already* repeatable) and **added-optional-section** (splice an empty `## <Heading>` slot-section block at the section's schema-ordered offset into each committed doc). The second is the **direct analog of the stamp migration's already-shipped block-insert** (which splices a `---` front-matter block into a header-less doctype, byte-stable — [DECISIONS.md](../DECISIONS.md) → 2026-06-25 M34 Inc-4): same insert-a-canonical-block-at-a-computed-offset pattern, one splice, prose of every other section byte-preserved.

   **Why `added-optional-section` is a transform, not a no-op (M36 planning correction).** In the doctype-schema model a prose *slot is a section* (adr's `context`/`decision`/`consequences` are each a `- id: X, slot: {…}` body section), so shipping the adr `options` **optional slot** adds a whole `## Options` section. The parser matches body sections **strictly by index** ([parse.rs](../crates/engine/src/parse.rs) → `body_sections` `enumerate` over `headings.get(i)`, no optional-section skip), and the canonical writer emits every schema section's heading **unconditionally** even when the optional slot is empty ([write.rs](../crates/engine/src/write.rs) → `render_section`; optionality governs *prose presence*, not *heading presence*). So under v2 the single canonical byte form of every ADR carries `## Options`, and a historical v1 ADR (three headings) is **non-canonical** — re-parsing it against v2 fails `[section-renamed…, section-missing]` before conformance runs. An added *optional* section therefore is **not** a byte-identical no-op: without the transform, `migrate-corpus` stamp-bumps then re-gates and **strands the whole corpus** (stamped v2, failing its own gate). The transform inserts the empty heading so each historical doc canonicalizes to exactly the v2 writer's shape; an empty optional slot then conforms ([validation.md](validation.md) → the optional flag exempts an absent prose slot). **Chosen over parser-tolerance** (making the parser skip an absent optional section): tolerance would create *two* valid byte forms for one schema — forking the frozen canonical form and touching the byte-stable parse core, the #1-retired risk — whereas migration canonicalizes cleanly and leaves the parser untouched. **Over-build line (written at M36; the clause expired at M42).** As written: *this covers inserting **one** optional slot section at its schema-ordered offset; general section insert-anywhere / field-group sections / section reorder / removal are **not** built* — on the stated basis that **"no frozen doctype needs them."** That basis was true when written, and **M42 falsified it**: fork 3's `milestone-record` enum widening and the deferred spec lifecycle's real shapes (a wholly-new *repeatable* section; fields on an *item block*) all land in changes the classifier cannot express, and — the rule both waves paid for — **a bump without a kind strands the corpus** ([DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 Settle). The kinds those drivers need are built: *The classifier's holes* below. **The guardrail stands for what still has no driver**, and these remain **unbuilt**: a nested repeatable **block** added, dropped or `id-from`-re-keyed (e.g. `changelog.releases.changes` itself), section **removal**, section **reorder**, and general **insert-anywhere**. *(An **edit to a leaf inside** an existing nested block left this list at M50 Increment 6, which made the third locus reachable — it classifies with the leaf's own kind: *The third locus*, below. The **per-item Framing-A prose handoff** left it at M49, when `AddedItemSlot` shipped — an item block gaining prose was a hard brick at every arity, and its only route named a file in the jigc source tree: *The item locus's other leaf*, below.)* What M42 adds is that they are unbuilt *out loud* — named as such where the author who would need one actually reads ([doctype-authoring.md](../implementation/doctype-authoring.md) → the transform-kind coverage matrix), so the kind gets built **before** the bump ships, never after. The over-build principle is unchanged: a need the trajectory does not commit to is still premature generality — but a need it *does* commit to is not a saving to defer. The residual parser defect (`section-missing` fires unconditionally for a genuinely-absent optional section) is out of scope — the frozen-v1 canonical corpus always renders the heading, so it is never exercised; parked in [decisions-pending.md](../implementation/decisions-pending.md).
3. **Prose routing.** A `prose-needing` change mints the empty slot and routes it to the migration workflow's agent step (Framing A); the CLI conformance-gates the result.

## Relocation — the file-move + display-title transform (M38)

The five kinds above are **in-content splices at a fixed `<location>/<slug>.md` path**. M38's `changelog` relocation (`docs/changelog/changelog.md` → root `CHANGELOG.md`, and `# changelog` → `# Changelog`) needs two kinds the splice model can't express, so they run as a **parallel arm** in the migrate-corpus driver, detected from the doctype-level diff before the per-doc content fold:

- **`relocated { from, to }`** — the committed instance's home changed ([storage.md](storage.md) → Placement). This is a **file move, not a content edit**, and it is **git-free** (like the rest of `migrate-corpus`): `std::fs::rename(from, to)` (or `persist(new) + remove(old)`) at the filesystem, with the file-state record re-keyed `from → to`; staging is left to the caller's later `git add`/commit, whose rename-detection collapses the delete+add into a clean `R` in the diff. *(No `git mv` — that would stage mid-verb, breaking migrate-corpus's git-free model; `rename.rs`'s git-mv verb is **not** reused. The M39 detect+route floor, which offers a resolution op to a human, is where an atomic git-mv belongs — not this batch transform.)* It sources `from`/`to` from the two schemas' resolved homes (the v1 snapshot carries the old `location`, v2 the new `placement`), so it is **auto-derived from the declared schemas** — the determinism boundary holds (no hand-written move recipe). The corpus walk keys on the **`from`** home (where the instances actually sit), not the empty `to`.
- **`display-title-changed { to }`** — a `display-title:` add/change ([document-type-schema.md](document-type-schema.md)) rewrites the doc's H1 line (`# changelog` → `# Changelog`). A one-line H1 splice, byte-stable otherwise; needs its own kind because `schema_diff` does not inspect `display-title` either.

For `changelog` the two kinds **combine** with the schema-version stamp bump into one v1→v2 migration, applied as **one atomic per-doc unit in a fixed order** (so the move and the content splices can't race): read the instance from `from` → apply the H1 re-title + stamp field to the in-memory doc → **write once to `to`** → `remove(from)` → re-key file-state `from → to`. Write-before-remove (never `remove(from)` before `to` exists) so an abort between strands neither copy — the no-data-loss ordering the census below pins. **First location-only frozen migration** — it exists to prove the freeze machinery can perform the relocation the freeze *forces* (a `location` change is in the schema-hash, so it version-gates).

### The freeze-exempt sibling — the parallel relocation path (M39 inc-5)

The transform above gates to the **frozen manifest set** (`frozen_doctype_versions`): a frozen doctype's relocation is version-gated, and its prior home is *derived* from the versioned snapshot (`candidate_docs` in `migrate_corpus.rs`), so it auto-moves safely. A **freeze-exempt** doctype (**pre-M40** the methodology singletons — `vision`, the roadmap, the milestone-record — no `schema-manifest.yaml` entry until they join the methodology manifest at M40, below) relocates by a **bare schema edit**: no version bump, no snapshot, so *no derivable prior home*. Migrate-corpus therefore skips it (the `versions.get(&ty)` gate), and it relocates through a **parallel path** — `crate::relocate::relocate_freeze_exempt`, the sibling exposed as `jigc relocate <type> --from <prior-home>`:

- The prior home is **human-supplied/confirmed** (the `--from` arg — a directory `docs/vision/` or a literal file `docs/vision.md`), because there is no snapshot to record it; **auto-derivation stays unsafe** for a freeze-exempt doctype (nothing pins where the instance *was*). This is the deliberate asymmetry with the frozen arm.
- The move is the **T1 standalone move primitive** (`relocate::move_doc` — `git mv old→new` + file-state re-key), *decoupled* from `rename.rs`'s referrer-repoint/H1/dangling-gate. Unlike the git-free batch transform above, this offers an atomic **`git mv`** to a human as a **detect+route+offer-move** resolution — exactly the "where an atomic git-mv belongs" the batch-transform note reserves for the M39 floor. The bytes are preserved (a pure relocation), so the re-keyed hash is the current file's.
- The two paths are **reconciled**: `relocate_freeze_exempt` **refuses** a doctype in the frozen manifest set (routing it back to `jigc migrate-corpus`), and migrate-corpus's frozen gate skips the freeze-exempt complement — so every persisted doctype relocates through exactly one path, keyed on frozen-vs-exempt.

**Scope M39 inc-5 T4 closes (storage.md → Freeze + relocation, the `storage.md:148` obligation):** the *freeze-exempt relocation floor itself* — detect + route + move a freeze-exempt doctype's pre-existing committed instance from a supplied prior home to its current home, never silently stranding it. **Still owed / not claimed here:** an *automatic* prior-home record for freeze-exempt doctypes (there is none by construction — the human supplies it); and the changelog's bump-computation-from-commit-tokens facet ([ideas/root-changelog-render.md](../ideas/root-changelog-render.md)).

**M40 revises the dichotomy — the methodology doctypes leave the freeze-exempt set.** The methodology pack now ships its **own** `schema-manifest.yaml` — listing all **ten** shipped schemas, the transient `commit` shadow included (the freeze assert is strict set-equality; the dev precedent lists its transient `commit`, stamp-excluded) — ([DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 Settle): its persisted doctypes are stamp-injected, freeze-asserted, and **migrate-corpus-owned** — the v0 stamp-absent arm above recovers the existing unstamped corpora, exactly the recovery precedent it was kept open for. `jigc relocate` consequently **refuses** them (the frozen-manifest-set refusal keys per-origin pack), so the exempt relocation path covers only *genuinely manifest-less* doctypes. The original exemption's rationale is engaged, not overridden: the recorded precondition — hash-freezing a shape never proven byte-stable would be premature ([doctype-map.md](../implementation/doctype-map.md) → the scope pin) — is **discharged by the M40 methodology `arb_doc()` byte-stability census before the manifest lands** (the M33 census covered only the six dev doctypes). Manifest resolution is **unified per-origin-pack** in the same motion, closing the split-brain (per-origin at `all_schemas` vs composite→dev at the mint/task/ingest/milestone call sites) under which a methodology manifest alone would have validate demand a stamp mint never writes — a doctype's governing manifest entry is the one from `origin_pack(Schemas, ty)`, the pack whose schema definition wins (both packs carry a `commit` entry with different hashes). `schema-snapshots/` starts **absent at v1** (the dev precedent ships snapshots only for migrated doctypes; first populated at the first methodology v1→v2 bump). One walk arm the manifest forced (M40 inc-5 T5): a **placement-born** frozen doctype — placement at v1, so *no* location-bearing prior snapshot exists (the four methodology singletons: `vision`/`roadmap`/`decisions-log`/`deferral-ledger`) — migrates its **literal placement file in place**; pre-fix the walk treated every placement doctype as *relocated* and silently skipped one with no prior snapshot, so an unstamped committed roadmap never migrated. *(The **known bound** recorded here — that the detect-half's family-5 sweep still walked only `location:`-bearing schemas, so an unstamped **placement** doc was verb-migratable but never detector-routed `migrate` — **is closed at M42**: the sweep enumerates placement instances too, over the same placement-aware `committed_instances` walk the hollow/surplus advisories always used. See the detector section above and [validation.md](validation.md) → Store-scope schema-conformance. The verb's own placement walk was **also** broken, and in the opposite direction — *The corpus walk*, below.)*

## Prior-schema sourcing — the versioned snapshot store (Inc 4)

The schema-diff needs **two real `Schema` values**. For the v0→v1 stamp (Inc 3) the prior shape looked derivable in-process (`from = strip_stamp(current)` — the stamp is the only v0→v1 change; that derivation held only while the doctype had not bumped past v1, and M42 replaced it — the bound below). But a genuine v1→v2 **structural** change cannot be derived from the current schema: the verb needs the *actual prior shape*. So the pack **stores prior schema shapes as versioned snapshots**, and the verb sources `from` keyed on each committed doc's stamp. This is what makes the structural transform branches (built + unit-proven since Inc 2) reachable through the shipped `jigc migrate-corpus` verb — without it they are engine-substrate-only ([DECISIONS.md](../DECISIONS.md) → 2026-06-25 M34 audit Finding 1).

- **Storage (settled):** a dedicated **`schema-snapshots/<type>.v<N>.yaml`** pack resource kind — each snapshot a *full, real, reviewable schema file* (honoring the "plain, diff-friendly files" invariant; the determinism boundary in its strongest form — the diff is over two genuine declared schemas; for a **structural** change this schema pair is the whole input, never a hand-written migration recipe (a **value-semantic** rename additionally carries an authored old→new map — still a deterministic CLI input, not an LLM call; see *Value-semantic renames* below)). It lives **outside `schemas/`** by necessity: the freeze gate enumerates `schemas/` and keys by doctype, so a snapshot there would collide on `type` and break the 6-doctype freeze assertion. The freeze manifest stays the `type → version + hash` declaration, untouched; snapshots are a separate kind, invisible to it.
- **`from`-selection (per committed doc, by stamp):** stamp **absent** (the v0 corpus state) → the doctype's **earliest shipped snapshot**, stamp-stripped — falling back to `strip_stamp(current)` **only** for a doctype that has never bumped, whose earliest shape *is* its current one (the bound below); stamp **`k`, `1 ≤ k < current`** → load `schema-snapshots/<type>.v<k>.yaml`; a **missing** snapshot **blocks** that doc with a route (never a silent `already-current`); stamp **above `current`** (2026-07-24 — a future/foreign stamp) → **blocked** as `migrate-corpus.schema-version-ahead` with a human route (upgrade jigc, or restore the stamp from git history) — this binary has no schema to migrate the doc *to*, and a silent `already-current` would hide it from every future run. Only a stamp **exactly at** `current` reports `already-current`.

  **The v0 arm is bounded by the snapshot set, and that bound is load-bearing (M42 completion audit, Finding 1).** It originally sourced `from` as `strip_stamp(current)` on the reasoning that *the stamp is the only v0→v1 change* — true, but it silently asserts something stronger: **that the doctype never bumped past v1.** That held when every doctype sat at v1 and was falsified at M36, when `adr` went to schema-version 2 (the `## Options` section). For a **v0 ADR** the diff then carried *only* the stamp add-field — `AddedOptionalSection` never classified, the empty-diff backstop blind to it (the diff is *non-empty*), the doc failing its parse-under-v2 gate — so it was blocked with the prose-needing route: **a permanent dead end**, whose route lied on all three counts (there is no new *required* prose; the write verbs cannot author the optional section, because the doc does not parse under v2; and re-running changes nothing), while the version-aware detector went on routing the doc at the verb that refused it. `deferral-ledger` (v2, the enum rename) carried the same trap. So the v0 arm derives the prior shape from **the earliest shipped snapshot** — the snapshots exist precisely so a prior shape is *knowable*, and this arm was the one that never consulted them — and the diff becomes the honest **v0→current union** (the stamp add-field *plus* every structural link since v1), which migrates the doc in one pass. The `strip_stamp(current)` fallback survives exactly where it is still true — no snapshot shipped, i.e. no bump ever made.
- **The stamp value-bump (the v1→v2 transition, distinct from the v0→v1 add).** A present-but-below stamp is *updated* to the current version via `write::set_field` (the field already exists — `added-field` only covers the absent case). This closes the Inc-3 detector/verb divergence ([DECISIONS.md](../DECISIONS.md) → Finding 2): a doc the detector routes `migrate` (stamp absent **or** below) is migrated by the verb, never reported `already-current`.
- **Snapshot integrity (deferred, bounded).** Prior-version snapshot hashes are **not** frozen in the manifest in v1: a drifted snapshot fails the migration transform/round-trip loudly (the acceptance catches it), so a second hash gate is premature. **Both set-growth arms have since fired and the defer holds** (M36 the first real v1→v2; M41 the first methodology snapshot; M49 the first doctype with TWO snapshots) — the disposition, and the driven evidence it now rests on, live in [decisions-pending.md](../implementation/decisions-pending.md) → Prior-schema snapshot integrity + `jigc upgrade`, and are not restated here.

## Value-semantic renames — the authored old→new map (M41 `ValueRemapped`)

Every transform kind above — `added-optional-field`, `added-optional-section`, `widened-cardinality`, `fixed-slot→repeatable`, `relocated`, `display-title-changed` — is **auto-derived from the schema pair**: the schema-diff over the two `Schema` values fully determines both *what changed* and *the bytes to splice*, with no input beyond the two declared schemas. That auto-derivation is the exact property the two "never a hand-written recipe" claims above (Prior-schema sourcing and the Relocation-safety census row) assert — and it holds for every **structural** kind.

A **value-semantic** change breaks that property. Renaming an enum member's *spelling* — the methodology `deferral-ledger.kind` `D`→`Decision` / `I`→`Idea` (schema-version 1→2) — is **unrecoverable from the schema pair alone**: the two schemas record only that `of:` went from `[D, I]` to `[Decision, Idea]`; *which* new member each old committed value maps to is a semantic fact the schemas do not encode (the diff is equally consistent with `D→Idea`). So the migration needs an authored old→new **map**, and `SchemaChange::ValueRemapped { section, field, map }` is the **first parameterized transform kind** — one that carries a migration input the schema-diff cannot supply.

**The determinism *boundary* still holds; only the narrower *auto-derivation* property does not** (design-review A2). The map is a **deterministic CLI-supplied migration input** — threaded into the emitted `ValueRemapped` before the engine corpus fold, the `with_stamp_default` precedent (a migration-time value fed into the fold) — **not an LLM call**. Same schemas + same authored map in → same bytes out. The pack author writes the map once, alongside the schema edit; the CLI owns placement and the conformance gate exactly as for every other kind. So the CLI-vs-LLM line the whole pair rests on is intact — the map is authored *structure*, not authored *prose*.

Mechanics, pinned:

- **The classifier detects the delta, never the map.** It fires `ValueRemapped` on an enum `of:` value change over **both** a simple field (`diff_fields`) and a **repeatable-item** field (the `diff_section` `(Repeatable, Repeatable)` branch the empty-diff strand otherwise hides — an un-classified `of:` delta diffs to `[]`, bumps the version, and **strands** the whole committed corpus at v2-failing-its-own-`field-value`-gate, unmovable by any kind). The map is authored elsewhere and threaded in by the CLI.
- **The driver remaps every instance and blocks on an uncovered value.** It applies the map via the item write path (`set_item_field` — correctly the **update-only** primitive here: a remap *overwrites an existing* bullet, so its refusal-when-absent is the right behaviour; contrast `AddedItemField`, whose bullets do not yet exist) for a repeatable section / `set_field` for a simple one, byte-faithful (every other byte preserved, the stamp value-bumped `1→2`), and **surfaces a hard error** — never a silent no-op — when a committed value the map does not cover is met. A bump that ships *no* map entry leaves the classifier's empty map and the driver blocks loudly, so a value-semantic bump can no longer strand the corpus.
- **At every item locus, through the one primitive** (M50 Increment 7 / T5). `set_item_field` takes the item's **id chain**, so a *nested* item's value is the same value-span splice one level deeper — the flat form is the single-segment chain, not a second code path. That choice is load-bearing rather than tidy: the insert-capable dual (`set_nested_item_field_or_insert`, which `AddedItemField` must use because its bullet is absent by definition) **used to re-render the item's whole committed region**, so bytes the parse does not model — a paragraph hand-appended after the `<!-- fields -->` group — were destroyed by it, which was **measured on this arm before it was written** rather than argued. A value span cannot take what is around it, so the nested arm needs no pre-image guard and no refusal, and the outcome one locus down is the *same* outcome. **The measurement held for `AddedItemField` too, and was answered at the primitive rather than at this arm** (M50 Increment 7 fix): `set_nested_item_field_or_insert` now makes the flat dual's splice-or-insert — the present bullet's value span, else the bullet inserted **into** the item's own field group — so no item-field write re-renders a committed region at any locus, and the *same outcome* claim holds for both kinds over a doc carrying unmodelled bytes. The whole-item re-render survives only where the change genuinely reshapes the item (`AddedItemSlot`), and there it is guarded by the pre-image compare below.
- **The authored map is keyed by the locus path.** `authored_remap`'s key is `(doctype, locus path, field)` — `entries` at a section or its item block, `releases/changes` one level down — never the bare section id, which cannot tell a nested block's leaf from an identically-named outer one (`date` on `changelog.releases` is the shipped collision) and would silently hand one block's semantics to the other's rename. It is also, byte for byte, the key the map-gap refusal's route tells the operator to declare.
- **The snapshot supplies the prior shape.** The v1 side comes from the versioned snapshot store above — `schema-snapshots/deferral-ledger.v1.yaml`, the **first methodology snapshot** — so the diff still runs over two genuine declared schemas; the authored map is the *only* added input.

Driven first by the `deferral-ledger` `D`/`I` rename (the first methodology v1→v2 migration ever run); the kind is **general** — an `adr.status` / `completion-record` enum rename reuses the same classifier + driver with its own authored map ([DECISIONS.md](../DECISIONS.md) → 2026-07-11 M41 Inc 5 T1/T3; the Fork-4 charter).

## The classifier's holes — completing the kind inventory (M42)

Every kind above was built for a change a frozen doctype had *already made*. The rc.6 wave took the inventory as a whole and found **six holes and one stranding defect** — three that block the M42 bumps outright, two more the sweep turned up ([The two silent-classification holes](#the-two-silent-classification-holes-schema_diffrs298-320), below), and a **sixth the design review turned up** while checking the backstop's precondition (`optional: true → false` — *The structural projection*, below), each reproduced live through the real binary ([DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 Settle; the sixth added at the settled-design review the same day). They share one shape: **an unclassified change diffs to `[]`, and an empty diff is not a no-op** — the below-version branch stamp-bumps anyway, so the corpus lands at **v2 failing its own gate**, exactly the strand the `AddedOptionalSection` note above exists to prevent. *(That the count went 3 → 5 → 6 on successive passes over the same inventory is the honest headline: the class is what matters, not the enumeration.)* That shared shape is itself the fix: M42 also builds an **empty-diff backstop** so the *next* hole refuses the migration instead of stranding a corpus.

The three that block M42's own bumps:

- **A wholly-new *repeatable* section diffs to `[]`.** `added_section` classifies the simple-slot cases and closes with the fact in its own comment: *"A wholly-new repeatable section is not one of the transform kinds"* ([schema_diff.rs:294](../crates/engine/src/schema_diff.rs)).
- **Any field added to a repeatable *item block* diffs to `[]`.** `diff_item_fields` emits `ValueRemapped` and nothing else — *"Narrow by design"* ([schema_diff.rs:250-273](../crates/engine/src/schema_diff.rs)). An **optional** added item field means the doc "migrates by accident": the stamp flips, nothing is spliced, and a declared `default:` silently never lands. A **required** one is a **permanent mutual dead-end** — `validate` says *run the corpus migration*, `migrate-corpus` says *author the prose then re-run*, and neither instruction is actionable. This is not a corner: **9 of 14 persisted doctypes carry a repeatable**, and for the work-doc family the item block *is* the document (`decisions-log` has exactly one section and it is a repeatable, so **zero** content changes to it are migratable today) — the verb cannot migrate the half of the schema model where the corpus's content lives, while this doc sells it as the artifact that *bounds* an adopter's lock-in cost.
- **An enum *widening* is misclassified as a rename.** `enum_members_renamed` fires on **any** `of:` delta ([schema_diff.rs:246](../crates/engine/src/schema_diff.rs)), so a widened enum emits `ValueRemapped { map: {} }` and the driver blocks on the uncovered values. Safe — it blocks loudly and corrupts nothing — but **unusable**: there is no map to author, because nothing was renamed.

**The stranding defect: a migration is not re-runnable.** `AddedOptionalSection` **strands a doc that already carries the section**. `per_doc_changes` ([migrate_corpus.rs:396-408](../crates/cli/src/migrate_corpus.rs)) guards `ProseNeeding` for idempotency — *"kept iff the doc does not already carry that section heading"* — and lets every other heading-minting kind through unconditionally (`_ => true`). The driver's block-insert (`write::generate_section`) **refuses** the already-present section (`GenerateError::AlreadyPresent`, [write.rs:2587-2591](../crates/engine/src/write.rs)) — it does not duplicate the heading, it **halts the doc** — and the route it then collects is a **dead end**: it says *author the new required prose … then re-run*, but the section is **optional and already authored**, so there is nothing to write and re-running changes nothing. The doc can never migrate. *(The refusal, not a duplicate splice, is the mechanism: recorded wrong here until M42 Inc-5 T2 drove the red and corrected it — the outcome was right, which is why the wrong mechanism went unchecked.)* This is live in the flagship `adr` v1→v2 `options` migration — **any adopter who hand-added `## Options` before the bump is permanently stranded on rc.5**. It survived M36–M41, two RC trials, three completion audits and a cross-model review, because the stranding shape needs a doc that *already has* the section and **every fixture is a historical doc that lacks it**: the hole is invisible to precisely the tests we would rely on to catch it. So "acceptance would have caught it" is retired as an argument for the narrow cut.

M42 closes the three holes with three kinds, generalizes the idempotency guard to **every heading-minting kind**, and declares the missing re-run property (the census below). *(Two further kinds land with the backstop — `PresentationOnly`, and whatever the removal/narrowing calls settle on — see below; the full inventory is the matrix in [doctype-authoring.md](../implementation/doctype-authoring.md).)*

- **`EnumWidened`** — `new.of ⊇ old.of`: every committed value is still a declared member, so the change is a **byte no-op**, the `WidenedCardinality` sibling. Only a genuine member *rename* (a non-superset `of:` delta) still demands the authored map. Note the direction this cuts: it **deletes** the need for identity-map entries rather than growing the authored table. First driver: the `milestone-record` `status` enum widened to `[active, joined, discarded]` — the terminal status the milestone-abandon path needs ([team-ready-state.md](team-ready-state.md)).
- **`AddedRepeatableSection`** — mint the empty `## Heading` at its schema-ordered offset, through the **same block-insert** `AddedOptionalSection` already uses. A **zero-item repeatable conforms**: `schema-conformance.repeatable-populated` is a store *advisory*, not a conformance break ([validation.md](validation.md) → Repeatable-section conformance), so the empty section canonicalizes a historical doc to the v2 writer's shape and needs no prose. *(The block-insert is the right primitive, but it was **shape-blind**: `render_generated_section` rendered every section as a **simple** body — heading + empty prose + field group — over-padding a repeatable's zero-item home by one newline and breaking `render(parse(x)) == x` for a **non-trailing** section. Corrected in M42 Inc-5 T6 with one branch; the recorded "no new primitive, verified by probe" was true only for a *trailing* section — [DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 Inc-5 T6.)*
- **`AddedItemField`** — parse the doc, loop its items, and call the already-shipped **`write::set_item_field_or_insert`** ([write.rs:3186-3216](../crates/engine/src/write.rs)) — **not** `set_item_field`, which the M42 pass first named here and which **cannot do this job**: it is **update-only**, refusing with `SpliceError::NotPresent` when the field bullet is absent from the item ([write.rs:1382-1386](../crates/engine/src/write.rs)) — and an absent bullet is **every item, by definition of `AddedItemField`**. The insert-capable primitive is a different function with a different error type (`GenerateError`, not `SpliceError`) that additionally **adjudicates the value against its declared type before touching bytes**. *(The wrong cite looked true because `ValueRemapped` genuinely does drive `set_item_field` — it **overwrites an existing** bullet, which is exactly the case the update-only primitive is for. Recorded because "the primitive already exists" was the claim the cost estimate rested on, and the primitive it named was the wrong one.)*

  **The per-item semantics mirror `classify_added_field`** ([schema_diff.rs:324-330](../crates/engine/src/schema_diff.rs)) — the header-field classifier this is the item-block twin of — with the same three arms, and **every locus asks one predicate**, [`validate::is_author_required`](../crates/engine/src/validate.rs), the conformance gate's own absent-field rule, so classification and placement cannot disagree (M46 Inc-4 T1). The middle arm has been wrong twice: the first draft said *"every item spliced"*, which is wrong for the optional case, and the M42 correction that replaced it still named a `set:`-derived leaf alongside a defaulted one as a value the driver places — wrong for a `set:` that carries no `default:`, which the binary refused with `TransformError::Unsupported` until M46 Inc-4, routing the doc to *author the prose, then re-run* when the gate never asked for the field and re-running changed nothing:
  - **`default:` present** → the declared value is **spliced into every item** (`set_item_field_or_insert`), the only arm that writes bytes.
  - **an absence that already conforms** — `optional:`, an optional `ref`, a pack-declared type, or a **`set:` carrying no `default:`** — → **classified, and a byte no-op.** `is_author_required` exempts all four, so `schema_conformance` never asks the item for the value: it **already conforms** without the bullet, inventing one would fabricate a value, and an `on-create` / `on-transition` value does not exist for a historical doc at all. It still emits a kind, which is what the backstop requires of it; it just folds to zero bytes, like `WidenedCardinality`. The derived member is not left **silent**: the run names every leaf it left unfilled ([command-output-contract.md](command-output-contract.md) → the `migrate-corpus.*` sub-table, `set-field-unfilled`), so a doctype author who expected a value hears about its absence.
  - **author-required, with no value source** → **`ProseNeeding { leaf: Some }`** — no deterministic value exists *and* the gate does ask for it, so it routes to the agent and **blocks loudly**. The change is that it is now *named* instead of silently diffing to `[]`: same refusal, but a true one.

  **The extension point is untouched — only the nobody-threaded-a-value behaviour changed.** A caller that *has* a deterministic value threads it in **as a schema `default:`** — the CLI's `with_stamp_default` for the version stamp, `authored_remap`'s sibling shape for a value remap — and it splices through the first arm exactly as before, at every locus. What M46 Inc-4 retired is what fired when **nobody** threaded one in: a derived leaf is now left absent, conformantly and audibly, instead of refusing a migration whose route could not be followed.

### The item locus's other leaf — a slot, i.e. item prose (M49)

M42 closed the item locus for `Field` leaves and left **the filter itself** standing: `item_field` returned `None` for `Leaf::Slot` and `Leaf::Repeatable` alike, at the added pass, at the shared existing-leaf pass and at the removed pass. So a doctype whose entries needed **prose** had no path at any arity — the delta reached the residual, `jigc migrate-corpus` refused `unclassified-change`, and the route it printed named `crates/engine/src/transform.rs`, a file no adopter can edit, while `jigc validate` routed the operator back the other way. That is not the bound on an adopter's lock-in cost this doc sells; it is the absence of one ([settle-record](../completions/artifacts/M49/settle-record.md) → D3(B)). And because the backstop is a **residual**, the same delta riding alongside any classified change was not refused at all — it was **dropped silently**, which is `RemovedField`'s recorded reason (*:188*, above) that **the kind must exist rather than ride the backstop**, applied to the three deltas the filter still dropped.

- **`AddedItemSlot`** — the item block gains a slot. **One kind carries both requirednesses**, because the byte work is identical either way: the item's committed prose moves under the old leaf's `#### <Leaf-Title>` sub-label and the added leaf mints empty, so splitting it across two kinds would split one relabel in half. The **per-doc conformance gate** then adjudicates — an optional leaf leaves every item conformant and the doc migrates; a required one breaks the gate, the scratch rolls back byte-identical with the stamp unmoved, and the doc collects the doc-authorable `migrate-corpus.prose-needed` (Framing A, never a build-the-kind route). Routing the required arm through `ProseNeeding { leaf: Some }` instead is **unreachable by construction**: `per_doc_changes` drops a `ProseNeeding` whose section heading the doc already carries, which an item block's always is. The driver folds through **`write::insert_item_slot`** — the insert-capable primitive, `set_item_field_or_insert`'s twin (`set_item_slot` is update-only, i.e. refuses every committed item by definition of this change) — reading the committed prose through the **old** schema, since a v1-shaped instance does not parse under a v2 multi-slot template, and splicing back to front so every region located against that one parse stays valid. Below two declared slots it writes **zero bytes**: a lone slot renders bare, under no sub-heading, so a slot-less item already carries the v2 bytes and an **optional** first slot's correct output is the stamp alone (the `WidenedCardinality` shape). *Declared bound (M49 Inc-4 T1): an item whose committed bare prose happens to carry a `#### <Added-Leaf-Title>` heading of its own reads as already migrated — the ambiguity is inherent to the shape being migrated **from**, and leaving those bytes alone is the answer that cannot destroy committed prose.* **The re-render is fenced by a byte-fidelity guard** (M49 Inc-4, validation): the reshape replaces an item's **whole committed region**, so it first re-renders that item under the **old** template and compares the result to the region byte-for-byte. Equal means the parse models every byte and the re-render is faithful; unequal means the region holds bytes the parse does **not** carry — prose hand-appended *after* the item's `<!-- fields -->` group is the reachable instance, since the canonical order is slots-then-fields, and it is invisible to `doc show` and to `jigc validate` alike — so the doc is **refused** at `migrate-corpus.item-unmodelled-content` rather than silently rewritten. **No-data-loss** is a declared property of this pair, and it is the same property that refuses `RemovedItemSlot` one bullet up; a whole-item re-render that drops authored prose would be the larger exception, not a smaller one. *Declared bound: the check is byte equality, so a **conformant but non-canonical** item region — an extra blank line, a hand-spaced field bullet — is refused rather than re-canonicalized; that is the safe side of a check that cannot tell the two apart, and the refusal names the item, so the repair is a one-item edit.*
- **`RemovedItemSlot`** — `RemovedField`'s **sibling**, not a reuse of it. The recorded pick transfers unchanged (*refuse, not strip*) and is sharper here, because what a strip arm would splice away is the entry's **authored prose**: the exception to **No-data-loss** would be the larger one. The *route* is what cannot transfer — an author told to restore a *field* the schema never declared cannot follow it — so the refusal names the **slot** (`migrate-corpus.removed-item-slot`, a schema-authoring repair), with the doc's bytes and stamp untouched. Additive to build later, exactly as the field strip is.
- **A nested-repeatable leaf stopped vanishing at M49, and got a kind at M50.** M49 Inc-4 T2 made an added, dropped or reshaped nested leaf **name** the backstop kind rather than only reach it through the residual, so it refused in a mixed bump too — but the leaf itself still had no kind of its own, which is as far as that wave went. **M50 Increment 6 closed that half**: the recursion descends and each such leaf classifies at its own locus (*The third locus*, below). The comparison is over the **erased** projection (`projected_leaf`, built on `erase_block` so it recurses to any depth), so a hint reword *inside* a nested block stays the out-of-projection no-op it is instead of becoming a false refusal — the failure direction that costs an author a shippable typo fix.
- **A slot's own `optional:` delta joins the one shared rule.** `slot_flag_change` serves the section's anonymous slot and the item block's named slot leaf alike: a relaxation is `OptionalRelaxed`, a tightening is **always** `ProseNeeding`, because a slot carries no `default:`, no `set:` and no pack-declared type, so `is_author_required`'s exemptions cannot apply and the field rule's refinement collapses.

### The third locus — a nested item block's leaves (M50)

A repeatable item block may itself declare a repeatable, so the classifier's **locus set is not a pair**: it is one locus per repeatable nesting level, plus the section's own fields and slot — `LOCI`, **derived from `MAX_NESTING_DEPTH`** and never written down, because a literal would re-enact M45's *statement == constant* failure the day the address grammar grows a hop pair ([schema_diff.rs](../crates/engine/src/schema_diff.rs) → `Locus` · `LOCI`). Until M50 Increment 6 `diff_item_fields` compared a nested `Leaf::Repeatable` **wholesale** and pushed the backstop kind on any inequality, so every kind the item locus classifies answered `migrate-corpus.unclassified-change` one level down — a route into the jigc source tree, over the one shape a `changelog`-like doctype actually evolves in.

- **A leaf edit inside an existing nested block classifies with the leaf's own kind.** The recursion is the *same* code at every depth (`diff_item_fields` descends through the nested leaf at `locus.nested_in(id)`), which is what makes the M42 rules hold one level down without being restated (*The two silent-classification holes*, below — the failure they were written against was two loops disagreeing). The flat `section: String` the item-locus variants carried becomes a **locus path** (`Locus` — the section plus the nested leaf ids hopped into, rendered `releases/changes`), and every refusal and route interpolates it in place of a bare section id, so a locus-3 refusal says *where*. The path is also what the **driver** resolves an added leaf along: by section id alone, a nested leaf whose id also exists in the outer block (`date` on `changelog.releases` is the shipped collision) answered with the outer declaration, took its no-op branch, wrote nothing and restamped the doc.
- **`kind × locus` is a table the driver asks, not prose.** `locus_disposition` dispositions all of `SchemaChangeKind::ALL × 1..=LOCI` exhaustively — so a nineteenth kind cannot compile without being placed at every locus — and [`transform`](../crates/engine/src/transform.rs) consults it **before folding**, so a cell whose byte-writing arm is not built refuses, naming the kind and the locus path, rather than splicing an item-locus primitive at the wrong depth. Increment 7 folded the three arms Increment 6 left open — `AddedItemField`'s `default:`-carrying half (T3), `AddedItemSlot` (T4) and `ValueRemapped` (T5) — so `LocusDisposition::Unbuilt` now has **no occupant**, and that emptiness is a *fence* rather than a remark: `every_kind_x_locus_cell_is_dispositioned` asserts the empty set over `1..=LOCI`, not over a hand-listed pair of loci, so the next kind to arrive half-built announces itself at the cell rather than at an adopter's corpus. The variant stays for exactly that kind. Both claims are measurements rather than assertions: `crates/cli/tests/migrate_locus_axis.rs` drives the locus-3 column kind by kind and asserts it is the locus-2 column **minus the backstop**, `crates/cli/tests/migrate_corpus_nested_item_slot.rs` drives the slot reshape one level down over the shipped `changelog`, and `crates/cli/tests/migrate_corpus_map_gap.rs` drives the value remap's refusal at every item locus.
- **What still rides the backstop is the block itself, never its leaves.** A nested repeatable **block** added, dropped, or its own `id-from` re-keyed sits outside the table deliberately: no transform kind mints, drops or re-slugs a nested block, and a block's `id-from` is a **non-leaf** key inside the projection that a leaf-only recursion would never see. Each emits `Unclassified` **explicitly** rather than only reaching the residual, so it refuses beside a classified change too — and `AddedNestedRepeatable` stays deferred with its trigger, on the half M50 did not build ([decisions-pending.md](../implementation/decisions-pending.md)).

### The empty-diff backstop — no silent bump

Fixing three holes one at a time is the move that produced the three holes. The **class** is the thing: *an unclassified schema change diffs to `[]`, and an empty diff is not a no-op* — the below-version branch stamp-bumps anyway and the corpus lands at **v2 failing its own gate, silently**. Nothing in the system says otherwise; the only guard against it has been prose in a checklist **nobody is gated on**, and that prose failed twice (M41's `ValueRemapped`, M42's three).

**The backstop, settled:** if a doctype's **`schema-hash` moved** but `schema_diff` emits **zero kinds**, **refuse loudly** — with a route that names the actual repair (*build the transform kind first*), not a migration instruction. This is the *mechanical* enforcement of the rule both waves paid to learn, and it converts the whole class from a silent corpus-strand into a loud, actionable block: the next hole — and there will be one, because the kind inventory is open-ended by construction — announces itself at the bump instead of at an adopter's stranded corpus a wave later. Declared as a property in the census below (**No silent bump**).

**What "loudly" costs, and where it is paid (M42 completion audit, Finding 2).** *Loud* is not a property of the prose in a route — it is the **exit code** and a **machine-readable finding**, and the verb shipped with neither. A refused migration exited **0** (`Outcome::success()` unconditionally on any `Ok`), so a run in which **every** doc was refused reported success; and the `blocked` list was untyped `[path, route]` string tuples — no `code`, no `key`, no `(code, target)` — i.e. entirely outside the finding-key contract. So the loudest refusal in the verb was, to a machine, **silent** — and combined with the version-currency exit-flip above it is an **infinite CI loop**: `validate` → exit 1, *"run `jigc migrate-corpus`"* → `migrate-corpus` → exit **0** → `validate` → exit 1 → forever, nothing naming why. **Settled:** a run that refuses any doc **exits non-zero**, and every refusal is a real `Finding` — seven `migrate-corpus.*` codes, targeted at the doc's **file path**, each carrying a diagnosis (`message`) and a repair (`route`), projected through the structural findings seam ([command-output-contract.md](command-output-contract.md) → the `migrate-corpus.*` sub-table, which owns the codes + the target-form rationale). The old rationale — *a routed block is an expected interim state, not a run failure* — was right about the **doc** (a blocked doc is a waypoint, and the run's other writes still land and still commit) and wrong about the **run**: a corpus with a refused doc in it is **not migrated**, and the caller that asked for it to be must hear so.

**It is a *migration refusal*, not a build error — be exact about where it fires.** The first draft of this section (and the checklist's) called it *"a build error, not a migration."* It is not: nothing at `cargo build` or at pack-load detects it (the **freeze assert** at pack-load compares hashes, and a bumped version + recomputed hash passes it clean — that is the author doing the right thing as far as the freeze is concerned). The backstop fires at **`jigc migrate-corpus` runtime**, when the verb classifies the diff and finds nothing to do: it **refuses the migration** and routes to *build the kind first*. The distinction matters to the author who has to find it: you learn at the migration run, not at compile.

**The precondition — and it is *made true*, not assumed.** The backstop is sound only if **every real change emits *some* kind, content no-ops included**. That is what `WidenedCardinality`, `Relocated` and `DisplayTitleChanged` already do: they classify, and *then* fold to zero bytes. A change that legitimately alters no bytes must still be **named**, or the backstop cannot tell it from a hole. That property is **not** true at HEAD, and M42 makes it true by closing every way a real change can currently emit nothing:

- the **three holes** above (new repeatable section · added item field · enum widening) — real, structural, and today invisible;
- the **two silent-classification holes** below (field removal · `card` narrowing) — likewise;
- **a sixth hole nobody had named — `optional: true → false`** (tightening a slot or field to *required*) — see the projection below;
- and the class that is *not* a hole but would otherwise become a **false refusal**: every schema key **outside the conformance-relevant projection**.

#### The structural projection — stated as a set, because a half-stated one is what went wrong

The backstop's rule quantifies over "the schema's **structural projection**", so the projection has to be an **enumerated set**, not a gesture. The M42 pass wrote it as *"only `description` / `usage` / `hint` differ"* — **and that is one member of a class of nine.** The classifier, for a leaf present in **both** schemas, inspects **only `card` and `of`** ([schema_diff.rs:298-320](../crates/engine/src/schema_diff.rs) for a simple section's fields; [:250-273](../crates/engine/src/schema_diff.rs) for a repeatable item block's). Everything else on `Field` ([schema.rs:249-318](../crates/engine/src/schema.rs)) and `Slot` ([:219-230](../crates/engine/src/schema.rs)) is **invisible to it and inside the hash** — so it moves the hash, classifies to `[]`, and under a naive backstop would be **falsely refused, i.e. unshippable**: `optional: false → true` · `default:` · `set:` · `inverse:` / `inverse-card:` · `check:` (the M13 per-field predicate selector) · `title-names-symbol`. The claim this section used to close on — *"the rule is **exact, with no false-positive class**"* — was made after sweeping **one** member and is **false**; it is retracted here. That is the same un-enumerated-sibling failure this wave keeps finding (the census that under-counted twice; the idempotency guard that covered one heading-minting kind of three), and it is worth naming as such rather than quietly patching: *the first draft swept the member it had just been thinking about.*

**The projection is defined as the *conformance-relevant* projection** — exactly the schema facts a committed doc's bytes can violate:

| in the projection (a delta here is **conformance-relevant**) | outside it (a delta here **cannot** make a conformant doc non-conformant) |
|---|---|
| the **section set** + their **ordering** (body sections map positionally onto H2s) | `description:` · `usage:` ([schema.rs:53,:59](../crates/engine/src/schema.rs)) |
| **slot presence** + **requiredness** (`Slot.optional`) | a slot's `hint:` ([schema.rs:222](../crates/engine/src/schema.rs)) |
| the **field set** + **requiredness** (`Field.optional`) | `default:` · `set:` — mint-time derivers; a doc lacking the value already conforms |
| a field's **type** (`type:`, and for a `ref` its `to:` target type — what `ref-resolves` resolves against) | `inverse:` · `inverse-card:` — derived back-edge + a **store advisory**, never a per-doc conformance break |
| a field's **enum members** (`of:`) | `check:` — selects the `doc-code` predicate, adjudicated against *code*, not the doc's bytes |
| a field's **cardinality** (`card:`) | `title-names-symbol:` — a `doc-code` advisory over the item title |

Doctype-level home (`location:` / `placement:`) and `display-title:` are **already** in the projection by other means — they carry their own kinds (`Relocated`, `DisplayTitleChanged`), classified outside the per-section loop precisely because the section diff never inspects them.

**Everything outside the projection classifies as one kind: `PresentationOnly`** — *classify → fold to zero bytes → restamp → ship*, the shape `DisplayTitleChanged` and `WidenedCardinality` already establish. **The name is narrower than the extent**, and it is kept only for continuity with the Settle record ([DECISIONS.md](../DECISIONS.md) → 2026-07-13): read it as **outside-the-projection** — it covers presentation (`description`/`usage`/`hint`) *and* semantics (`default`/`set`/`inverse`/`inverse-card`/`check`/`title-names-symbol`) alike, because the property that matters is not "is it cosmetic" but "**can a committed doc's bytes violate it**" — and for these, they cannot. Without this kind the backstop would make a typo fix in an authoring hint, or adding a `default:` to an existing field, **unshippable**.

**Inside the projection, the two flag deltas get *named kinds*, because they are not no-ops:**

- **`optional: false → true`** (a **relaxation**, on a slot or a field) — always safe: every doc conformant under the strict rule is conformant under the loose one. A declared **no-op kind** (`OptionalRelaxed`), so it emits rather than diffing to `[]`.
- **`optional: true → false`** (a **tightening**) — a **real `ProseNeeding`**. It can render a currently-conformant doc **non-conformant**: an optional slot legitimately left empty, or an optional field legitimately absent, now blocks `required-slot-present` / `required-field-present`. This is the **sixth hole, and nobody had named it** — today it diffs to `[]`, the stamp bumps, and the corpus **silently strands** at v2 failing its own gate, which is the exact class this backstop exists to close, sitting *inside* the backstop's own precondition. Named and classified: it routes to the agent (Framing A), like every other prose-needing change.

  **Two refinements the flat rule above misses, both made in-increment against the gate that actually adjudicates** ([DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 Inc-5 T4). *(i)* A tightening is `ProseNeeding` **iff the leaf thereby becomes author-required**. A *slot* always does (it carries no value source), but a **field** carrying `default:`/`set:` — or an optional `ref`, or a pack-declared type — does **not**: `schema_conformance`'s absent-field arm consults `validate::is_author_required`, which exempts exactly those, so **no committed doc can fail the tightened schema** and blocking it would be a **false refusal**. It classifies the out-of-projection no-op kind and ships. The classifier calls that same predicate rather than re-deriving it, so the two verdicts cannot drift. *(ii)* **A tightening mints nothing.** `ProseNeeding`'s driver mints an *empty* section, which is right for a wholly-new required section and fatal for a tightened *existing* one (`generate_section` → `AlreadyPresent`, which would hard-block even the conformant docs). The generalized idempotency guard drops a `ProseNeeding` whose heading the doc already carries, so the tightening's byte-work is **zero** and the shipped per-doc conformance gate is the adjudicator: a doc carrying the prose migrates and restamps; one that legitimately left the slot empty is blocked with the Framing-A route, its stamp unmoved.

The backstop's rule, restated with a projection that is now actually enumerated: ***the conformance-relevant projection changed **and** zero kinds classified ⇒ refuse.*** Its false-refusal class is not "none by assertion" — it is *empty by construction*, and the construction is the table above.

> **Recorded honestly, because the next author will meet it and it is surprising — and then done, at M47.** Prose *inside* the schema-hash was a **design choice with a cost**: an authoring-hint typo fix was a **frozen-schema bump** (version + manifest hash + a `migrate-corpus` run over the corpus, to restamp). M42 flagged it forward rather than fixing it — *"narrowing the hash to a structural projection would be a freeze-semantics change, out of scope here"* — and M47 does the narrowing, **narrower than the line above contemplated**: only the three authored-prose keys leave (`Schema.description` · `Schema.usage` · `Slot.hint`), and the **six semantics keys stay in** (`default` · `set` · `inverse` · `inverse-card` · `check` · `title-names-symbol`), which is why it is *not* a reuse of `erase_out_of_projection` (*The freeze*, below). So a prose reword is now free at the freeze and still classifies `PresentationOnly` at the *migration* — the two questions are different, and the two functions stay separate.

### The two silent-classification holes (`schema_diff.rs:298-320`)

Both are the backstop's precondition, and both were silent **wherever the classifier looked** — `diff_fields` for a simple/header section's leaves ([schema_diff.rs:298-320](../crates/engine/src/schema_diff.rs)) and `diff_item_fields` for a repeatable item block's ([:250-273](../crates/engine/src/schema_diff.rs)) — because *both loops iterate `new`'s leaves and inspect only `card` + `of`*. (Those were the loci the classifier had when this was written; the set is `LOCI`, derived — *The third locus*, above. The fixes below are stated as **one rule each**, in one function, which is what makes them hold at a locus that did not yet exist: the recursion carries the same code down.) The item-block locus is strictly worse (it inspects only `of`, so it does not even mis-classify a `card` delta — it emits nothing), and it is the same code path `AddedItemField` opens, so the fixes land together:

- **A removed field never classified.** The diff loops **`new`'s** leaves ([schema_diff.rs:298-320](../crates/engine/src/schema_diff.rs) — `for field in new`, matching back into `old_by_id`), so a leaf deleted in v2 was simply invisible: zero kinds, stamp bumped, and every committed doc keeps a field line the current schema no longer declares. The repair shape was left a genuine open — **(a) a `RemovedField` kind** that strips the field line as a byte-stable splice (the `set-field --unset` primitive's shape: deterministic and *declared*, but it **destroys the committed values** — the doc's history holds them, the corpus does not) *or* **(b) refuse the removal outright** (a frozen doctype cannot drop a leaf; dropping one requires an explicit escape). **The pick, made and recorded in-increment: `RemovedField` classifies — at every locus — and is REFUSED** ([DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 Inc-5 T5). The census already stands on that side: **No-data-loss** is a *declared property of this pair* (*"a migrated doc retains every pre-migration slot/field value"*), and the strip is a knowing exception to it while the refusal is not. And **no frozen doctype needs a removal** — M42's own bumps *add*, the deferred spec lifecycle *adds* — so building the strip is the premature generality the freeze's minimalism rejects, while the **silent** hole is the actual defect, which refusal closes at zero risk. It is **not a one-way door**: a strip arm with a deliberate data-loss opt-in stays purely additive if a real driver ever appears — which is exactly the *build the kind first* rule this wave mechanizes, applied to itself. **The kind must exist rather than ride the backstop**, because the backstop is a *residual*: a removal accompanied by any classified change leaves the diff non-empty, so the backstop never fires and the dropped leaf would be silently ignored. `transform` surfaces `Unsupported`; `migrate-corpus` blocks the doc at classification with a **schema-authoring** route (restore the leaf, or build the strip arm) — the doc's bytes, and the committed value itself, untouched.
- **A cardinality *narrowing* misclassifies as a widening — and inside an item block, a `card` delta of *either* direction classifies as nothing at all.** `diff_fields` fires `WidenedCardinality` on **any** `card` delta, direction-blind (`if prev.card != field.card`), and the kind's own doc-comment records the intent: *"Narrowing is data-losing and unsupported — not a separate kind."* But *unsupported* here means **silently no-op**, not *refused*: a `0..*` → `0..1` narrowing folds to zero bytes while the corpus may hold instances carrying **two or more** values that violate the new bound — non-conformant, stamped current, and past the gate. `diff_item_fields` does not reach `card` at all, so an item-block widen (a legitimate no-op) *and* an item-block narrow (a real break) both emit `[]` — the coverage matrix shipped an unconditional ✅ for the widen case that the classifier never honoured ([doctype-authoring.md](../implementation/doctype-authoring.md) → the matrix, corrected). The fix is to **classify on direction, at every locus**: a widening (`WidenedCardinality`) is the declared byte no-op; a narrowing is a **content-affecting** change that must either validate every committed instance against the new bound (passing only if the corpus already satisfies it) or **refuse**. Either way it emits a kind — which is what the backstop requires of it. **The pick, made and recorded in-increment: refuse** (`NarrowedCardinality` → `transform` blocks; `migrate-corpus` routes the doc to the *schema-authoring* repair — restore the wider bound, or build the validating arm; [DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 Inc-5 T3). The validating arm is **net-new validation surface** — nothing anywhere counts a committed instance's edges against a `card` bound (`schema_conformance` → `check_field` → `write::check_value` type-checks each scalar and never counts them; the only cardinality surface in `validate.rs` is family 5's `inverse-cardinality` *store advisory*) — so it is a new finding code + knob + inventory row + store sweep, squarely outside this wave. Refusal is strictly better than the silent no-op it replaces and leaves that door open, additively.

**Direction is read from the bounds, and an equal-bounds respelling is the no-op direction.** A widening is `new.min ≤ old.min ∧ new.max ≥ old.max` (with `*` the greatest upper bound), so spelling out the *default* `card:` (absent ⇒ `"0..1"`) as an explicit `"0..1"` — a real hash move, and the projection covers `card:` — classifies as the byte no-op rather than a false refusal. Every other delta is a tightening (a raised minimum included: `0..*` → `1..*` demands a value a committed doc may legitimately lack), as is an unparseable bound — which refuses loudly rather than folding silently, the safe direction of the failure the backstop exists to close.

The kind inventory — not the schema-definition format — is the real limit on what a frozen doctype can become, so it is stated per-change-kind where an author meets it: [doctype-authoring.md](../implementation/doctype-authoring.md) → the transform-kind coverage matrix, which also names what stays **unbuilt** (the over-build line above) — and, with the backstop, what an unbuilt kind now *does*: **`migrate-corpus` refuses**, instead of stranding the corpus. (The refusal lands at the migration run, not at compile — *It is a migration refusal, not a build error*, above.)

## The corpus walk — the placement branches become a union (M42)

`candidate_docs` ([migrate_corpus.rs:626-667](../crates/cli/src/migrate_corpus.rs)) enumerates a doctype's committed instances, and for a **placement** doctype its two branches — *relocated* (walk the prior snapshot's `location`, land at the `placement.file`) and *placement-born* (migrate the literal `placement.file` in place) — are **mutually exclusive**, keyed on whether the prior snapshot carries a `location`. That key is wrong, and for the one doctype that has ever relocated it is fatal: `changelog` is at schema-version 2, so `load_prior_schema(changelog, 1)` resolves `crates/cli/pack/schema-snapshots/changelog.v1.yaml`, which carries `location: changelog/`. `prior_location` is therefore **always** `Some`, the relocation walk runs over an empty `docs/changelog/`, and the in-place branch is **dead code for this doctype**. Live: a stale root `CHANGELOG.md` → `jigc migrate-corpus` → `0 migrated, 0 already current, 0 blocked`. **The stamp stays at 1 forever.**

M42 makes the two branches a **union** — walk the prior home **and** the placement file — so a placement doctype's instances are found wherever a partially-completed migration left them.

**What *dedupe* means, now that both homes can be populated at once.** The word was carrying two different jobs, and the union is what makes the second one reachable, so both are named:

- **The identical pair.** The placement file can itself sit *under* the prior home (a `docs/x.md` placement whose prior home was `docs/`), so the two walks enumerate the byte-identical `(source, destination)` pair twice. The candidate list is sorted and deduped — a set, not a bag.
- **The shared destination — the both-homes state.** Two *different* candidates (an instance at the prior home, an instance at the placement home) land at the same destination. This is not deduplicable at enumeration: it is a **collision**, and it is resolved at the **write boundary**, against the destination's bytes — never by candidate order (today's protection is an ordering accident: `prepared` is sorted by source path and `CHANGELOG.md` happens to sort before `docs/changelog/…`; invert the paths and the relocation write clobbers the destination). The rule:
  - the destination already holds **exactly the relocating doc's migrated bytes** ⇒ an **interrupted move** (write-before-remove aborted between its halves). Complete it: the write is a byte-identical no-op, the old-home strand is removed, and the target is reported **once**, as migrated.
  - the destination holds **anything else** ⇒ a genuine collision. The doc is **blocked with a route**; nothing is written, nothing is removed. No deterministic merge of two documents exists, and **No-data-loss** is a *declared property of this pair* (the property census) — so the migration refuses and routes the reconciliation to the operator, exactly as the freeze's unbuilt-kind backstop refuses rather than stranding.

  **Which bytes "the destination holds" means: the ones *this run leaves there*** — the run's **claim ledger** (destination → the migrated bytes an earlier doc in this run landed on it) consulted **before** disk. Reading disk *alone* is what makes the outcome depend on a side effect, and it is exactly what **`--dry-run` suppresses**: with the write gone, a second candidate for a destination the first candidate just claimed sees an *empty* destination and is reported `migrated` — the same target listed twice — where the applying run reports it `blocked`. That is a preview of an outcome that does not occur, and it falsifies dry-run's own contract (*the identical triage report an applying run prints*); the topology is not exotic — two instances at the prior home is precisely the partially-completed-migration state the union exists to find. Adjudicating against the ledger-then-disk makes the rule a function of the **run's own outcomes**, so it is **order-invariant** in the sense that matters (whichever candidate the fold reaches first, the other sees the real destination bytes and adjudicates against them) *and* **mode-invariant** (`--dry-run` and the applying run print the same report, by construction).

This is not a polish item, and it is **coupled to the detect-half fix above**: without it, finishing the family-5 census lights a stale `CHANGELOG.md` with a *blocking* finding whose route is a verb that reports **total silence**. A **false green** would become a **false route** — strictly worse, because the operator now follows an instruction that does nothing. Detect and fix ship together, or neither does.

## The foreign arm — the file the verb is not for (M46)

**The verb's subject, stated once: `migrate-corpus` upgrades the *managed* corpus.** A committed file at a managed doctype's home that jigc was never handed — a brownfield repo's own Keep-a-Changelog `CHANGELOG.md`, its hand-written `VISION.md`, an MADR `docs/decisions/*.md` — is the **adoption** case, not an unmigrated corpus. Until M46 this verb had never said so anywhere, and the omission was not academic: the walk above *finds* such a file (that is what the union is for), and the fold then treated it as a doc to prepare. It halted on the prose the schema wants, reported it **blocked** at exit 1, and printed *author the prose, then re-run* over a file jigc never wrote — a route that, followed exactly, changes nothing. Worse than noise: the fold halts at its first blocker, so a genuinely **stale managed** doc sitting behind a foreign squatter was reported `deferred` and never migrated. The verb's real subject was held hostage by a file that was not its subject.

**The discriminator is the shipped one, asked before the fold.** `engine::validate::is_unadopted_foreign` — the stamp-keyed classifier whose arms, precondition and declared bound are owned by [validation.md](validation.md) → The managed-vs-foreign discriminator and are deliberately **not** restated here — is asked at the stamp-absent arm, fed the same `all_schemas` shape and the same three pack facts the store sweep feeds it. That sameness is the point: a file it calls foreign never becomes a `PreparedDoc` and lands in **neither** `blocked` nor `migrated` nor `already_current`, and the two doors adjudicate one file with one predicate. It is also what makes [validation.md](validation.md)'s *"never to `migrate-corpus`, a verb that would do nothing for it"* a statement about the **verb**, not only about the route pointing away from it.

**Reported, never silently skipped — and never in `blocked`.** An exclusion's own hazard is silence — the same hazard the **never a silent already-current** rule guards at the stamp-ahead arm ([validation.md](validation.md) → Version-aware routing), and the one a *skip* re-opens by construction. So the excluded set rides its own report field: counted in the text headline, listed per file with its code and route exactly as a blocked doc is, and carried into the invocation log — a run that declined to act on three files is not the same event as a run that found nothing. It is **not** `blocked`, whose emptiness *is* the exit rule (*The commit boundary*, below): putting it there would re-mint the exit the store door now owns for this fact. The advisory itself is the store door's, **verbatim, from the one producer** (`AdoptionInputs::unadopted`), never a second constructor on this side — two surfaces minting one finding from one seam cannot disagree about a file again, which is the whole shape of the fix. The check is pure, so `--dry-run` prints the identical triage.

**The paired exit change lives at the other door, and is not optional** ([validation.md](validation.md) → Exit semantics). With the foreign file out of this verb's blocking set, `jigc validate`'s exit is the only surface left that makes a squatter at a managed home audible at all, so the adoption advisory flips it. Excluding the file here *without* that would not have been a fix: it would have converted one door's false route into both doors' false green.

## The commit boundary — the verb lands its own migration (M42)

`migrate-corpus` is **git-free** by design (the relocation note above: `fs::rename`, staging left to the caller). In practice that leaves the operator holding an unstaged delete, an unstaged modify, and an **untracked** relocated file — so the only way to land a migration is `git add -A && git commit`: the raw-git drive-around the adapter contract forbids, and **the adoption trial's agent did exactly that**. A verb whose own output can only be landed by bypassing the tool is not finished ([DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 Settle, fork 1).

M42 gives it a commit boundary, on the real mold of `jigc setup` ([setup.rs:949-1017](../crates/cli/src/setup.rs)) — the one other verb that commits its own writes:

- **A pathspec-limited self-commit.** `git add` over exactly the paths the migration touched (added, modified, and both halves of a move) — explicitly **never a blanket `git add -A`**, so an ambient dirty tree is never swept in; `git diff --cached --quiet` for idempotence, so a clean re-run commits nothing; a loud `Err` on a genuine git rejection, never a silent skip.

  **The touched-path set is *surfaced*, not re-derived** — the report carried only *destinations* (`report.migrated` is pushed the `target`), and the relocated **source** (removed from the old home) appeared nowhere. A pathspec built from the report as it stood would have staged the **add half alone** and landed a **half-migration** — the silent-partial-commit class this wave exists to kill. So the fold records both halves of every write as it makes them.

  **The mold is setup's; the *hook posture* is `finalize`/`rename`'s — and no existing helper is both.** `setup`'s install commit supplies the pathspec `git add`, the `--quiet` idempotence and the loud `Err`, but it commits **`--no-verify`** on a rationale that **does not transfer**: its commit *"carries install artifacts, not managed docs"* (and its hook must not self-trigger on the very commit that installs it). `migrate-corpus` commits **managed docs**, so it follows the standing rule — **never `--no-verify`**: the user's hooks are **policy**, and a `pre-commit` rejection surfaces git's stderr verbatim and **fails the run non-zero**, never a silent skip behind a success banner (`finalize.md` → 6. Commit). *(`task::git_commit` is the right posture but the wrong shape — it commits the **whole index** with no pathspec. The verb's commit is neither helper reused: setup's pathspec form, minus `--no-verify`, with `git_commit`'s bail-on-rejection.)*
- **`--no-commit`** — leave the tree exactly as the verb leaves it today, for an operator who wants to review the migration or fold it into a larger commit. *Setup itself has no such flag*: the **commit** is copied from setup, the **opt-out is new**.
- **`--dry-run`** — suppress the disk write and print the triage report. Say precisely what that means, because the shorthand misleads: there is **no operator-facing `persist` stage** to skip (`engine::state::persist` is an internal call that writes the bytes and flips the file-state baseline in one motion). Dry-run is defined as *suppressing the write*, not as *stopping before a stage*.

**A rejected commit's re-run *recovers* (M47).** The boundary stages **before** it commits, so a `pre-commit` rejection leaves the migration **written and staged but unlanded** — and the re-run, which judged currency from the **worktree**, read back the stamp it had just written itself, reported the doc `already-current` and, with the touched set empty, committed nothing at **exit 0**. The migration was stranded in that one clone: the operator saw success while every other clone still carried the unmigrated corpus and still routed `migrate-corpus`. That makes the survivable frame's standing promise — *a re-run after any rejection recovers* — a Law-1 lie for this door, so the **currency judgment is keyed on the committed corpus**: the verb walks `HEAD` as well as the worktree, and a doc whose `HEAD` copy is behind while the worktree already holds the migrated result at the current stamp is **unlanded** — its paths rejoin the pathspec, so the re-run re-stages the *identical* pathspec the refused run built and lands it. Both halves of a relocation move included: the earlier run's source is already staged as a deletion, present in neither the index nor the worktree, so `git add` cannot name it while `git commit -- <path>` must — the commit pathspec is therefore **wider** than the `add` pathspec, or the recovery lands the add half alone and leaves exactly the half-migration this boundary exists to prevent. The commit-status line names the recovery rather than claiming this run migrated (Law 1) — **and since M48 so does the headline**: an unlanded doc is counted and listed apart from `already current` at both render sites, `recovered from an earlier run` when the run commits and `unlanded from an earlier run` when it does not (`--dry-run` / `--no-commit` land nothing, so only a committing run may claim the recovery). Reporting it `already current` described the *scan* while the action sat in the trailing line — and it described it in the very words a fresh clone would contradict. *Declared bound:* the refused run's staged residue is **stated** by the door's rejection frame, not removed — a `migrate-corpus` rollback is not in M47's scope.

The per-doc fold stays git-free and the move stays `fs::rename` — nothing about the transform changes. Staging happens once, at the boundary, where git's rename-detection collapses the delete+add into the clean `R` the relocation note already predicted. What changes is that the boundary now **exists**, and belongs to the verb.

## Completing v1 — the five schema-engine opens

So the robust cut is a *complete, correct* v1 — all five deferred schema-engine opens are **built into v1**, not deferred past the freeze (the cheap path that guarantees a future migration). The one genuine *schema-shape* change among them, the `spec.derived-from` ref, **shipped in M33** (commit `3c859c6`) and is now part of frozen v1 — so it is **not** an M34 transform case (the change already happened pre-freeze; [DECISIONS.md](../DECISIONS.md) → 2026-06-25 reconciliation). Because no post-freeze shape change is yet pending (the freeze working as intended), M34's transform earns its end-to-end proof on **reconstructed historical** shape changes plus the one live add-field (the stamp); see [the increments](../implementation/roadmap.md) (M34 Inc-2/Inc-3) for the branch-split.

## The freeze — declared *and* enforced

M33's deliverable is **declaration + enforcement**, not prose discipline:

- **Declare the doctype set + schema-definition format v1-complete.** The format (`id-from`/`card`/`set`/`of`/`header`/`to`/`inverse`/`inverse-card`) is already **shipped + golden-locked** ([document-type-schema.md](document-type-schema.md)) — M33 *formalizes* it, and corrects the stale "placeholders pending implementation" line as the act of declaring. The frozen *set* is the persisted doctypes enumerated in [doctype-map.md](../implementation/doctype-map.md).
- **A versioned, hashed doctype-set manifest.** An enumerated `doctype → schema-version + schema-hash` artifact, so the freeze can *self-enforce*: a schema-shape change that bumps no version + ships no M34 migration is **blocked**, rather than caught by review. This is the net-new artifact that makes the discipline mechanical.
- **The enforcement gate fires at pack-load / build time, not at `validate` (review Finding 3 — scope pin).** It is an **engine assertion** that recomputes each shipped doctype's `schema-hash` and compares it to the manifest, failing **loudly** on a mismatch — the sibling of the existing intrinsic-floor assertion ([validation.md](validation.md) → Severity inventory), *not* the report-only `validate` store sweep (which exits 0 and would never gate). A hash mismatch with no bumped manifest version is the un-migrated schema change the freeze forbids; the fix is to bump the version + ship the M34 migration (or revert). This firing surface is **pinned now** even though the manifest's on-disk home/format is settled at the increment that builds it.
- **The gate binds at every layer that can change a schema (M49 Increment 3).** The assertion's subject is the **cascade-resolved** schema, not each pack's own bytes alone: a project-layer whole-file shadow at `.jigc/config/schemas/<ty>.yaml` ([overrides.md](overrides.md) → Authored metadata on a definition resolves by whole-file shadow) *is* the resolved schema at every surface, so hashing only the pack's copy left the freeze bypassable from the layer that outranks every pack. It was not a theoretical hole: a shadow that dropped four sections from a frozen doctype made `jigc validate` report **"the committed store validates clean" at exit 0** over a corpus it had just broken, while `jigc doc schema` reported the frozen `schema-version` for an unfrozen shape and `doc create` wrote a third. A project-owned id is therefore hashed **as resolved** — through the same field-type-resolving loader and against the **origin pack's** manifest entry (the M40 per-origin rule), and **before** `docs-root` nesting, since the manifest stores the raw declared `location:`.
  - **Hashed, not refused by name.** The whole-file schema shadow is the *documented* mechanism for overriding a doctype's authored `description:` / `usage:` / slot `hint:`, and the presentation projection (below) already erases exactly those three keys. So hashing the resolved schema refuses precisely what the pack layer forbids and permits precisely what the pack layer permits — **one rule, both layers** — where refusing the shadow by name would have deleted a documented capability for all sixteen shipped doctypes (6/6 dev + 10/10 methodology are manifest-listed).
  - **The opt-out reaches the project layer unchanged.** A shadow is checked only where its **origin pack** declares the doctype in a manifest: a pack that ships no `schema-manifest.yaml` freezes nothing, at either layer, so its doctypes stay project-reshapable. The freeze records what a pack *declares* frozen — the same wholesale, pack-level opt-out, applied consistently.
- **The gate binds a *declared* home, never a resolved one (M49 Increment 7).** A doctype's `location:` / `placement.file` is inside its `schema-hash`, so a **schema** home change is version-gated exactly like a shape change — and the two **cascade** home knobs are outside it. `docs-root` has re-pointed every located doctype's resolved home since long before the freeze, and `placement-root` now does the same for a re-rootable placement home ([storage.md](storage.md) → Placement); neither is a schema change, both are **project-layer resolution**, and the hash is computed over what a pack *ships*. The reconciliation is therefore not a carve-out but an identity: the freeze check never sees a knob, because it hashes the schema as loaded from the pack (or from the project shadow) **before** `CascadeDefs` applies either knob. Both halves are driven, not reasoned: with `placement-root` set, pack-load is clean and every door exits 0; a project schema shadow that edits `changelog`'s `placement.file` blocks with the shipped `pack-load freeze check failed … schema-hash mismatch`, whose route says *changing the shape or the home of a manifest-governed doctype means bumping its `schema-version`* — still exactly true, because the home it names is the declared one. **The declared-home route stays refused at every layer**; what M49 added is a way to resolve a home, not a way to redeclare one.
- **The gate fires at `jigc setup` too — it just does not refuse there; it forecasts (M50 Increment 12).** The install cannot refuse over a corpus — it is what puts the tool within reach of repairing one — so a repo carrying a shape-changing project schema shadow installs at exit 0. Until M50 it also installed *silently*, and the adopter met the freeze block for the first time on their next command. `setup` now reports one **advisory**, `setup.pack-load`, relaying the block's own first line and carrying its own route ([project-setup.md](project-setup.md) → What the install says about the corpus it installed into). The freeze is its **motivating** instance, not its subject: the advisory is keyed on pack-load failing, so a *malformed* shadow — which the loader refuses with no code and no route — is forecast the same way.
- **Convergence is evidence, not a promise.** Beyond the gate, the freeze is *proven* by a defined run of milestones with zero schema-shape commits — tracked after the declaration, not gated inside M33.
- **The hash is a *presentation projection* (M47).** `engine::manifest::schema_hash` hashes the schema with three authored-prose keys erased — `Schema.description`, `Schema.usage`, and every `Slot.hint` (at every locus: a simple section's slot **and** a slot leaf inside a repeatable item block, recursing into nested repeatables). Everything else stays in, the six *semantics* keys included (`default` · `set` · `inverse` · `inverse-card` · `check` · `title-names-symbol`): they change what the tool **writes and adjudicates**, so they are declared contract changes even though no committed doc's bytes can violate them. **This is a different question from the migration classifier's** — *is this a declared change to the contract?* versus *can a committed doc's bytes violate this?* — so `erase_presentation` is its **own** function, an erase-list with an exhaustive `Schema` destructure (a field added to the model breaks the build rather than silently falling out of the hash), deliberately **not** a call into `schema_diff`'s `erase_out_of_projection`, whose erase set is designed to *grow* and would silently narrow the freeze each time it did. **The reason is not cheap typo fixes: while prose sat inside the hash the freeze was unfenceable** — a hint reword and an enum widening were the same keystroke (re-pin, green), guarded only by a comment saying *never to silence this gate* ([DECISIONS.md](../DECISIONS.md) → 2026-07-26 the Settle, Decision 3).
- **The successor rule — stated at M47 Increment 1, fenced at M48 Increment 11.** A **schema-shape** change moves a doctype's `schema-hash` only together with its `schema-version`, and a **slug-rule** change moves `slug-rule.hash` only together with `slug-rule.version`. **M47 Increment 1 is the declared genesis exemption and the only one:** the narrowing re-pins all 16 doctype hashes at unchanged `schema-version`s *by construction* (no schema's shape moves — only what the hash is computed over), and the slug fork moves `slug-rule.hash` together with its co-located `version` 2→3, which already satisfies the rule. Each re-pin lands in the same commit as the code that makes it correct, so the exemption is reviewable as a diff rather than asserted ([storage.md](storage.md) → Identity, where the same rule is stated for the slug side) — and it is now also the **fixture** the fence's own acceptance runs on.
  - **Where it fires.** The check runs in CI, over the pushed range — both manifests read at the base of the range and at its tip, one violation per entity whose hash moved while its co-located version stood still (`crates/cli/tests/manifest_freeze_fence.rs`, run by the named `manifest-freeze fence` step, whose arm is `#[ignore]`d so the local four-command gate is untouched). The base is `github.event.before` for a push and the PR base for a pull request, falling back to a `HEAD~1` **floor** — Actions fires one run per push, at the tip, and this repo pushes in large batches, so a tip-only window would have missed `6e81d53`, the only real instance in the repo's history. It is **not a pack-load assert**: pack-load still only recomputes each hash against the shipped schema, and one state of the tree cannot tell a legitimate re-pin from a silent breach — which is the whole gap, since *"re-pin the hash"* is otherwise one keystroke with two meanings.
  - **The named escape.** A legitimate re-pin declares itself **per entity**, on the commit that does it: a line-leading `Manifest-Repin: <doctype | slug-rule>` trailer, matched by exact equality. Never blanket — a blanket escape would restore the one-keystroke-two-meanings ambiguity, merely renamed.
  - **Two declared bounds, recorded rather than glossed.** The fence protects **this repo only, not adopters** (it lives in this repo's CI, and this repo is the only party that edits a manifest), and it is **a build fence, not a surface** — it mints no finding code, no route and no verb. The two other candidate mechanisms stay **refused**: an **append-only** `(type, version) → hash` ledger asserted at pack-load would protect adopters too, but it is **a new stored format**; and the rule as an in-process check is **unimplementable in-process**, for the reason M47 recorded — a pack-load assert cannot observe a *change* **without a recorded prior** ([DECISIONS.md](../DECISIONS.md) → 2026-08-13 the M48 Settle; [decisions-pending.md](../implementation/decisions-pending.md) → **(D)**, discharged).

## Acceptance flows (spiked against the real binary)

The engine-behaviour claims these flows encode were **exercised at Scope** (the baseline audit drove the real binary): store-scope `validate` runs four families exit 0; `conformance_for` is a pure task-less function; `write.rs` primitives are byte-stable; `migrate` is foreign-adoption (not corpus-upgrade). The acceptance flows therefore rest on verified, not assumed, behaviour.

- **The detect flow** — a committed corpus at v1; a schema-shape change ships; `jigc validate` **reports** every stranded instance at store scope (pre-M34: silent, exit 0). **Since M42 it also *fails*:** each managed below-version instance raises `schema-conformance.schema-version-current` and the run **exits non-zero**, routed to `jigc migrate-corpus` — the headline regression-retirement is that an unmigrated corpus can no longer read as green. *(The "**reports** … exit 0" wording here was left standing by the M42 pass and is corrected with the scope pin above; the two are the same claim stated twice, which is why one going stale was invisible.)* **The brownfield arm is the guard on it:** a stock repo whose real `CHANGELOG.md` was never handed to jigc raises the **adoption** advisory, which blocks nothing and gates no door — and since **M46** the run **exits non-zero** on it all the same, the sweep's verdict on its own run rather than a gate the advisory carries ([validation.md](validation.md) → Exit semantics; the withdrawal of M42's exit-0 for this arm, and what it bought, are recorded where M42 wrote it).
- **The migrate flow** — the same stranded corpus run through `jigc migrate-corpus`: the **add-field stamp** (v0→v1) applied deterministically byte-stable (Inc 3, proven live); the **structural kinds** (widen-card / slot→repeatable / prose-needing) applied byte-stable for a **v1→v2** change once the verb sources the prior shape from the versioned snapshot store (Inc 4 — proven on the reconstructed M25 `prd.requirements` reshape through the real binary); a prose-needing change routed to the agent; the result conformance-gated and adopted; the stamp value-bumped to the new version.
- **The dogfood flow** — the v0→v1 stamp migration *is* the first add-field transform over the existing corpus.
- **The freeze-enforcement flow** — a schema edit with no version bump is blocked by the manifest check.
- **The adr v1→v2 flow (M36 — the first *live* shape change, the first *embedded*-snapshot migration).** The adr `options` optional slot ships as a real v1→v2 bump: adr `schema-version` 1→2 + recomputed hash in the manifest, and the pack ships `schema-snapshots/adr.v1.yaml` (the **embedded** pack's *first-ever* `schema-snapshots/` entry — every prior migration test used a `FilesystemPack`, so `load_prior_schema` over the `EmbeddedPack` is unexercised). Acceptance drives the **real binary with no `JIGC_PACK_DIR`** over a fixture repo carrying ≥1 committed v1 ADR: `jigc validate` routes each below-version ADR `migrate`; `jigc migrate-corpus` resolves the embedded `adr.v1` snapshot, classifies the delta as exactly `[AddedOptionalSection]`, splices the empty `## Options` heading, re-gates clean, and stamps `schema-version: 2` — every prior slot value byte-preserved. The embedded snapshot must be the **exact current adr shape** captured *before* `options` is added (`supersedes` at `0..*`), **not** the reconstructed `0..1` flow36 test fixture (which would spuriously classify `WidenedCardinality`). *(jigc's own repo is **not** a migration target — `docs/decisions/` holds no managed dev-pack ADR instances; the fixture repo is the corpus.)*

These land in [worked-examples.md](worked-examples.md) when the increments build them.
