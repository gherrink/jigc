# Finalize transaction

The ordered transaction that turns a task's working area into a committed change. `finalize` is the site that turns **task** work into a commit — everything on the task path is staging, and the one transition between staged and committed happens here. Specifying it as a single transaction keeps the rest of the system honest: read paths see committed state, write paths stage into the task area, and the one transition between them happens here. *(Two task-less direct-store ops touch the committed store outside this boundary, each with its **own** transaction + rollback: `migrate-corpus` ([corpus-migration.md](corpus-migration.md)) and `jigc rename` ([reconciliation.md](reconciliation.md) → Rename detection, the transaction). They are not staged-then-promoted — they mutate committed paths directly — so they define their own atomicity rather than riding finalize's.)*

Builds on [VISION.md](../VISION.md) (the commit boundary; the determinism boundary), [write-commands.md](write-commands.md) (`finalize ≡ validate + commit`; the task as staging unit; the two check times), [validation.md](validation.md) (the validate phase and its probes), [storage.md](storage.md) (the per-task working area, derived caches, "CLI orchestrates, git executes"), [workflow-dialect.md](workflow-dialect.md) (`fan-out`/`join` and sub-agent finalization), and [document-type-schema.md](document-type-schema.md) (the commit doc type). For the *why*, see [DECISIONS.md](../DECISIONS.md). Notation is **illustrative** ([what that disclaims](../CLAUDE.md#how-we-work-together)).

## What `finalize` is

`finalize ≡ validate(task) + commit`. One task → one logical commit. The shape:

```
jigc task finalize <task-id>
  → validate                (blocking findings abort cleanly)
  → render commit-doc       (→ git message string)
  → promote managed docs    (working area → canonical paths)
  → stage                   (git add: promoted docs + first-commit config, into the agent-staged index)
  → git commit              (pre-commit hook may reject)
  → post-commit             (invalidate caches, update hashes, cleanup)
```

The transaction is **atomic up through `git commit`**: any failure before that point rolls back to "as if `finalize` was never called" — the working area is intact, canonical paths unchanged. After `git commit` succeeds, post-commit steps are **best-effort** with cache stamps absorbing partial failures (a failed hash update only means the next read rebuilds the cache).

## The seven phases

### 1. Preflight

Cheap rejections before any expensive work:

- **A valid task id that exists.** Two answers, not one. The id is first checked against the work-unit grammar — a token that is not a well-formed slug was never an id, and is refused with the blocking `work-unit.malformed-id` whose route states the grammar, never the roster ([structural-grammar.md](structural-grammar.md#work-units-and-runtime-identity) → resolution). Only a **well-formed** id reaches the existence test: `.jigc/tasks/<task-id>/` must exist, otherwise reject with "no task `<id>`" and the `jigc task list` route. Both refusals land here, before the base-pin read — the grammar check sits at the resolve seam, so nothing has joined the token onto a path yet.
- **Base pin matches HEAD.** The task was started at base `<A>`; if HEAD ≠ `<A>`, reject with the divergence-routing prompt ("switch back to `<A>` or discard") — same philosophy as [out-of-band reconciliation](write-commands.md#out-of-band-reconciliation). The CLI never operates a task off its pinned base.
- **The repository posture is one this door may act in.** **Three** predicates, not one — **HEAD detached** · **HEAD unborn** · **an operation in progress**, the third being **any operation git can leave un-concluded** rather than a list of the markers git happens to write — each refused with its own blocking code and a **`Human` route naming the git command that resolves the state**: `repo.head-detached` → `git switch <branch>`, `repo.head-unborn` → a first commit, `repo.operation-in-progress` → the command that concludes or abandons **this** operation rather than a menu ([validation.md](validation.md) → The M51 registrations — Increment 2, and the M52 widening that registers the inventory). **The refusal carries no override**: a posture is a repository state the user can resolve, not bytes only they can value, so no flag carries a door past it — `--force` at `jigc setup` keeps exactly one meaning, and `--carry-staged`, whose documented consent is *carry my staged work*, stops concluding a merge it never consented to conclude. The CLI still does **not** require a clean working tree (see [Dirty-tree policy](#dirty-tree-policy)).

**The third predicate was the promise this row carried from the day it was written, and it had no probe behind it.** *"No in-progress merge/rebase/bisect"* shipped here with **zero** probes in either crate, and the two members it never named were driven at the M51 baseline as live damage at **exit 0** — 13 doors committing branchless on a detached HEAD (after which `git checkout main` drops the prose and `jigc validate` reports a *phantom* out-of-band edit), and git's **empty-tree hash** pinned as a base into a *committed* milestone record on an unborn one. M51 Increment 2 **implements** the promise rather than narrowing it ([DECISIONS.md](../DECISIONS.md) → 2026-09-14 M51 Increment 2).

**The predicate's subject is every checkout the door commits *from*, not only the one the command was run in (M53 post-review fix, 2026-09-22).** The probe has always answered about *a path*; until this fix every consumer handed it the process cwd's repository and nothing else. `jigc milestone finalize` is the door where that is not the same thing: both commit models read `git diff --cached` out of each provisioned sub-task worktree's **own** index — the `squash: false` chain per sub-task, the `squash: true` combine in aggregate — so the bytes come from checkouts the caller is not standing in. Driven on `1.0.0-rc.17` across **every member of `cli::repo::InProgress::ALL` buildable in a linked worktree — all ten**, the boundary landed at **exit 0**, committed the user's un-concluded operation under jigc's synthesized subject — at `squash: false`, inside the sub-task's own commit under the sub-agent's **authored** message — and destroyed that operation's authored message (`MERGE_MSG` / `SQUASH_MSG`) with the worktree teardown, while `jigc task finalize` run *inside* that same worktree refused one command earlier ([DECISIONS.md](../DECISIONS.md) → 2026-09-22; the M53 per-axis review, axis 2 `DEFECT 1`). So the boundary asks the **same** probe, through the same `cli::repo::adjudicated_breach` composition the door guard asks, once per provisioned worktree it will commit from, before anything durable is written — and the refusal says *which* worktree and routes at `git -C <worktree> …`, because a route the caller cannot run from where they are standing is not a route. `jigc task validate <sub-id>` previews it from the main checkout on the same rule that made it preview the cwd's posture; **`jigc milestone finalize` has no `--dry-run`**, so that preview is the only forecast there is. The fan-out worktree's one exemption is unchanged and comes from `posture_subject`, not from a rule restated at the boundary: jigc detached those worktrees itself, so `repo.head-detached` is never raised there.

**The third predicate's member set is the operations, never the markers (M52 Increment 3).** This doc first named it *"a merge, rebase or bisect"* over three marker files, and the M52 baseline drove what a marker list costs: a clean `git merge --squash` writes **`SQUASH_MSG` and nothing else**, a conflicted `git stash pop` writes **no marker at all**, and `rebase-apply/` is written by **two** operations — so the list reached neither of the first two and named the third's `git am` *a rebase*, routing it at `git rebase --abort`, a command git refuses at exit **128**. The member is therefore **any operation git can leave un-concluded**, each with its own detector, its own noun and its own command, and the inventory below is `cli::repo::InProgress::ALL` member-for-member in probe order — fenced against the enum, and against [validation.md](validation.md)'s equal statement of it, by `crates/cli/tests/posture_member_inventory.rs`; every command in the right-hand column is run out of the **emitted route** and accepted by git in `crates/cli/tests/repo_posture.rs`, so a row here and a live route cannot drift apart silently. The *why* of each member — the evidence git leaves, and why it is its own row — is stated once, in [validation.md](validation.md)'s third column.

| the operation | the route abandons it with |
|---|---|
| a merge | `git merge --abort` |
| a squash merge | `git reset --merge` |
| a rebase | `git rebase --abort` |
| a `git am` | `git am --abort` |
| a cherry-pick | `git cherry-pick --abort` |
| a revert | `git revert --abort` |
| a cherry-pick or revert | `git cherry-pick --quit` |
| a bisect | `git bisect reset` |
| an uncommitted cherry-pick | `git reset` |
| a conflict | `git reset --merge` |

Where git also offers a way to **finish** the operation rather than abandon it, the route names that command first and the abandoning one second — each followed by **the member's own qualifier, never the mold's**. The clause that makes naming a command true is a property of the member, not of the sentence that prints it, and the uncommitted cherry-pick is the member that proves it both ways: *once its conflicts are resolved* is true of a member git detects only in a state the user is **stopped** in, and false of that one, whose clean cells have no conflicts at all — so it declines the shared clause and states what `git commit` does there instead; and its `git reset` abandons the operation while **keeping** the bytes it applied, a claim no bare command name carries and the reason a user who cannot tell *abandoned* from *discarded* re-does the work or loses it. So both qualifiers travel with their command (`cli::repo::InProgress::conclude` and `::abandon_qualifier`; [settle-record](../completions/artifacts/M53/settle-record.md) → §10), and in `crates/cli/tests/repo_posture.rs` every member's rendered route line is compared against the line its **own** qualifiers compose, each member that named a concluding command before the qualifiers had a per-member home against a byte literal besides. **The abandoning qualifier is owed wherever the command does more than abandon, which is most of the inventory** (M53 completion audit, finding 7): driven with one unrelated file staged in the caller's index before the emitted command ran, every `--abort` and `git reset --merge` in the column above **discarded it, from the index and from the working tree** — so each of those members states that, in one sentence shared verbatim across them, and only the members that genuinely leave a staged entry as they found it carry no clause. Which members those are is not declared here or in the code: `crates/cli/tests/repo_posture.rs` plants the file, runs the member's own emitted bytes and observes what happened, for every member and with no exemption. For the four members that name no concluding command, the route still offers concluding as a choice and the column above is the only command it spells: a dangling `sequencer/` has no current commit to continue, a bisect ends rather than concludes, and an unmerged index is resolved rather than continued. ~~a squash merge is concluded by the user's own `git commit`~~ **[Struck 2026-09-22 (M53 Increment 4):** that clause explained nothing — the uncommitted cherry-pick is concluded by the user's own `git commit` too and **names** it, so the reason does not distinguish the two rows. The squash-merge row is kept as shipped rather than reworded here, and the question carries a trigger in [decisions-pending.md](../implementation/decisions-pending.md).**]**

**Declared deferral — the inventory is a property of one git, and says so.** Every marker fact above was driven on **git 2.54.0**, including the two that no amount of care could derive from documentation: `determine_whence()`'s blindness to `REVERT_HEAD`, and the `rebase-apply/applying` vs `rebase-apply/onto` discriminator that separates `git am` from `git rebase --apply`. It is **declared as a bound, not fenced** against a git this repo has not run. **Reopening trigger:** *the first CI or adopter report on another git major/minor where a marker cell diverges* ([settle-record](../completions/artifacts/M52/settle-record.md) → §16).

**Where it binds is wider than this preflight, and the two classes refuse different things.** The family is adjudicated **at the door**, before anything is resolved, over a **total classification of every clap leaf** into *commit-on-behalf* / *move-on-behalf* / *neither* (`cli::cli::BEHALF_DOORS`, on `VERB_KINDS`' mold and ⇔-fenced against the real clap tree, so a new verb **reddens until someone answers it**; `COMMITTING_DOORS ⊆ commit-on-behalf` is asserted, because a lower bound plus one named element is not a membership rule). A **committing** door refuses the **full family**. A **mover** — the two leaves that `git mv` a committed file and commit nothing, `jigc config set` (`docs-root` / `placement-root`) and `jigc relocate` — refuses **operation-in-progress only**: a `git mv` lands in the index and which commit it joins stays the user's to place, so HEAD's shape is none of the mover's business, while moving a *tracked* file out from under a half-finished merge is. A door that does neither is asked nothing — a refusal with no damage behind it is one the user cannot act on. The class is decided at the **act**, never at the verb's name: `jigc rename` moves *and* commits, and the commit decides, so it is commit-on-behalf and refuses the full family; `migrate-corpus` is commit-on-behalf and no mover at all, its relocation arm being an `fs::rename` staged once at its own commit boundary.

**One stated *door* exemption, and it is a row rather than a hole.** `jigc setup` does not adjudicate **unborn**: setup owns committing its own install footprint regardless of HEAD state (the M30 audit finding, quoted verbatim onto the exemption row rather than paraphrased), and applying the family uniformly would turn **the QUICKSTART on-ramp — the first command an adopter runs** — into a refusal routed at `jigc setup --force`, training the very override reflex the wave's staged-set guard prices as its own honest weakness. The *detached* and *operation-in-progress* members still apply there. The family's **other** exemption is not a door's at all — a fan-out worktree is exempt from *detached*, because jigc detached it itself — so it is carried on the **subject**, and a merge left un-concluded inside that worktree is as real there as anywhere.

**The door is not the act, so the posture is re-probed at the seam.** A per-task finalize validates, promotes, retires and stages before it reaches `git commit`, and the milestone boundary runs the user's hooks in a worktree sharing the same `.git` before it reaches its `merge --ff-only` — so a hook, a concurrent process or an earlier phase of the same run can move HEAD in between. The posture is therefore re-probed **immediately before every `git commit`, before the `git mv`, and before the live-checkout fast-forward**, against a **typed** subject (`cli::repo::SeamSubject`, threaded through the commit seam in place of a bare path so a caller must *say* which checkout it is). What it verifies is **repository identity and the expected ref** — the canonical per-worktree git dir, and the *value* `git symbolic-ref HEAD` returned when the act was decided — not merely *HEAD is attached*. Drift between the door and the act **mints no fourth code**: the three `repo.*` identities name **postures**, and a checkout that moved is not one, so it refuses naming both refs and `git switch <the ref this act was decided for>`. **Typed rather than sniffed, because sniffing is provably wrong here**: a fan-out worktree answers `git symbolic-ref -q HEAD` with exit 1, **byte-identically** to a user's detached HEAD, so the dedicated variant has exactly one constructor and it takes a `&DedicatedWorktree` — neither a path nor a boolean, the two forgeable shapes M50's audit condemned in `fanout_worktree_paths`' `is_dir()`. The move seam is the one case that takes **no** subject parameter and builds a fresh one at the act: there is one `git mv` in the product and no mover runs in a fan-out worktree, so a threaded subject would carry no choice and would be a *stale* expectation by the time it reached the `mv`.

**Declared bound — the `GIT_DIR` redirect is OUT of the family, and this is the paragraph that says so.** A `GIT_DIR` exported by the user redirects git's answer to a *different repository*, and the baseline drove a committing door writing its record into repo A while landing the commit in repo B at exit 0. The probe does not adjudicate that: its subject is the path it is handed, and it passes the ambient environment through untouched. **The scope of the rationale is jigc_home binding, not a prohibition on a probe shelling out** — `crates/cli/src/repo.rs`'s module header, **quoted** rather than paraphrased:

> It is **layered** so the ~15 fake-`.git` unit fixtures stay green: it shells to git (`dirname(git rev-parse --git-common-dir)`) **only** when a *real linked-worktree* `.git` is present — which is exactly the case where `.git` is a *file* (a `gitdir:` pointer). A main checkout and a fake `create_dir_all(".git")` fixture both keep `.git` as a *directory*, and for both the answer is the `.git`-bearing dir itself — resolved by walk-up, never by shelling out (so a fake `.git` can never walk up to, and bind against, a real ancestor repo).

**The reopening condition, written rather than implied:** the cell reopens the moment a repository-**identity** check exists that those ~15 fixtures survive. `dirname(git-common-dir) != toplevel` is **not** that check — a legitimate linked worktree has the identical asymmetry, so it would refuse jigc's own fan-out. Stating the cell is the point: the family closes over **three of the four** members driven at the baseline, and leaving the fourth unmentioned is the one arm the record forbids.

### 2. Validate

Runs `validate(task)` ([validation.md](validation.md)). Three outcomes:

- **Blocking findings present** → abort with the finding list. No side effects. Agent fixes and re-runs `finalize`.
- **Advisory findings only** → surface them in the output, continue.
- **No findings** → continue silently.

`finalize` has no private check path **at this phase**, and since M46 the claim rests on a construction rather than on an author remembering it: the membership is one set — the checks `TaskArea::preview_gates` runs — reached from **two entry points at their own positions** (`jigc task validate`, before the transaction; `finalize`, inside it), each computing it itself, reported twice and never merged twice; and what the surfaces *say* about that set is enumerated in **one code-side table** (`cli::gate_coverage`), which fences the exclusion list below across the eight sites that state this split. So what `validate` reports here is what `finalize` blocks on here, and `jigc task validate` previews this phase in full ([write-commands.md](write-commands.md) → Staging and the transaction model). **In full** includes the members the CLI merges into this phase's report beside the shared engine sweep — the carryover gate, the six staging-independent `owner-artifact` causes, and the **granted-but-unused changelog gate**. That last one was the sentence's counter-example until M46: the advisory was merged into the phase-2 report on the **committing path only**, so a *"no private check path"* claim was true of the engine sweep and false of the phase — and since one cascade line promotes the advisory to `blocking`, a project that had promoted it read a clean `task validate` over a state `finalize` was about to refuse ([DECISIONS.md](../DECISIONS.md) → 2026-08-18 M46 planned, F-E). It now runs at both doors, and each door routes it at verbs that are live there. **It previews exactly one phase *around* it, and no other: the repository posture** (M52; [DECISIONS.md](../DECISIONS.md) → the 2026-09-17 M52 Settle, D2 as amended by §4). The door adjudicates that family before the preflight above runs at all — an un-concluded merge, rebase, `am`, pick, revert, squash merge or conflicted index, or a detached HEAD — and until M52 `jigc task validate` reported this task's content findings over such a state and exited 0 or 3 while `finalize` refused at **1**. So the preview asks the **committing door's own guard**, with that door's own exemptions, and renders the identical finding at the identical exit code; it is invoked **separately at the door** rather than folded into this phase, because the family is a fact about the repository rather than about the task's content, and a member of this phase would be reported at this phase's severity and exit code (`cli::gate_coverage::Invocation` carries that distinction to every surface stating the coverage claim). The boundary is widened deliberately and by exactly this much: the one pre-commit phase a caller can **resolve** before finalizing. It does **not** preview the rest: the preflight above (the base pin) and phases 3–6 below each adjudicate their own failures — the empty-commit guard, `finalize.render-io`, `promote-clobber`, `stage-failed`, the untracked `owner-artifact` cause, and the commit hook's rejection. That is why a clean `task validate` says *nothing this side of the commit blocks it*, not *this will commit*.

**One cause is deliberately adjudicated later (M45, narrowed at M47).** `owner-artifact.present` has seven causes ([validation.md](validation.md) → The M45 registrations). Six are **staging-independent** — empty · absolute · `..` · not-under-home · names-no-file · symlink-escape — and run **here**, under a constant-true `tracked` predicate, so they preview at `jigc task validate`. The seventh, **untracked**, asserts the named artifact is already tracked — a state phase 5 has not yet produced when this phase runs, so checking it here would fire on an artifact `finalize` is about to stage; it runs *after* phase 5 and only there. **The later position changes what the report contains** — over an untracked artifact this phase is silent and the post-stage gate blocks — so it is the same check, different report, later position, and that difference is exactly what the preview surfaces must say out loud ([DECISIONS.md](../DECISIONS.md) → 2026-07-24 M45 Increment 8 planning, Decision 6 — narrowed to its own stated grounds, not overturned, by the 2026-07-26 M47 Settle, Decision 1). The mechanism and its cost are § [5. Stage](#5-stage).

**The milestone boundary is where it did diverge — closed at M45.** That sentence, and the `fan-out` transaction's step 2 below (*"**Validate** the merged effective state — one validate run, not N"*), were **design of record that was never built**: `plan_milestone_finalize` takes no `ValidationReport` (its per-task sibling `plan_finalize` takes `report: &ValidationReport` and blocks on `has_blocking()`), and the CLI's `run_milestone_finalize` never ran a validate at all. So corruption authored in a sub-task worktree passed `join` **and** `milestone finalize` into a **commit** — live-reproduced twice at the M45 baseline: a non-conformant sub-area doc carrying three blocking findings, and a cross-worktree code-anchor dangle no per-area check can see. M45 builds the gate ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle, Decision 2). **This is deleting a divergence the phase-2 statement above rules out, not new capability.** What it *checks* — scope and families — is owned by [validation.md](validation.md) → The milestone-boundary gate; what this doc owns is its place in the transaction:

- **Where it runs — after `materialize`, before the record flip and the plan** (revised at the pre-decompose review; the Settle's *before-`materialize`* position was wrong twice over). The by-task-id merged doc set **is** `materialize`'s output — it runs `join`, re-gathers the groups, and writes each `resolved_body` into `<milestone>/merged/docs/` — so a gate ahead of it would have to re-implement the merge, the exact divergence class this closes. The *"so a blocked milestone writes nothing"* rationale was hollow too: `materialize` writes only into the gitignored `.jigc/milestones/<id>/merged/`, which it **clears and rebuilds every call**, so blocking after it still writes nothing durable. Three constraints pin the slot exactly: after `provisioned_worktrees` (computed *after* `materialize` today); **after the base guard**, because the gate reads **`base.sha`**, not the literal `"HEAD"` that `combine_commit` passes on a `base == HEAD` guarantee the planner's preflight establishes *below* this point; and **before the `squash` knob branch**, so the gate adjudicates once for both modes — `combine_worktree_trees` is called today only on the `squash: true` path, while the `squash: false` sibling runs `detect_code_collision` up front and commits per sub-task (§ [`fan-out` finalize](#fan-out-finalize) — the M31 sibling-site shape, named here rather than rediscovered at build). **The gate is not knob-*independent*, and M49 corrected the claim rather than the position**: it still runs before the branch, but it *reads* the knob, because its subject is everything the boundary commits and the knob is what decides whether a sub-task's transient `commit:<sub-id>` doc is committed bytes or is never read at all ([validation.md](validation.md) → The milestone-boundary gate).
- **Never inside engine `join`**, which returns `Result<_, Finding>` and would drip findings one per invocation instead of reporting them as a set. The cheaper arm — a per-sub-area check at `join` — was **declined** for a second reason: `join` is **skippable** (finalize runs the join itself), so a gate living there is bypassable, and a per-area check misses the cross-area class by construction.
- **How the `doc-code` arm reaches the merged code.** `combine_worktree_trees` returns a **tree SHA**, while the probe resolves anchors by filesystem path (`snapshot.working_tree_root.join(file)`) and the probe protocol carries no git-object channel. So the merged tree is **checked out into a throwaway detached worktree** — the `DedicatedWorktree::add` + `git read-tree --reset -u` idiom, which today exists only at commit time — with the probe request's `working_tree_root` pointed at it, and **torn down on both exits** (blocked and clean). The cost is stated rather than hand-waved: one worktree add plus a full checkout of the merged tree per milestone finalize — paid once per milestone, on the gate that decides whether the milestone commits at all.
- **What `combine_worktree_trees` actually guarantees.** It is **not** "pure / side-effect-free": it creates a temp index and runs `read-tree` / `apply --cached` / `write-tree`, writing loose objects into the ODB. The accurate — and load-bearing — claim is that it **touches neither the live index nor the worktree**, which is what makes it callable from a gate that may block.
- **How it exits** — through the existing `blocked()` path, which already builds a real `ValidationReport` and emits the findings envelope at the gate exit code; no new exit shape.

### 3. Render the commit message

The commit doc instance (`commit:<task-id>`) is rendered into a git-message string. The renderer reads the instance **against the schema** (it locates the header section by the schema's `header` flag) but addresses the commit vocabulary by **well-known id**; the schema itself stays cascade-overridable. The pack-default for the development pack follows Conventional Commits — full mapping, and the bound on that coupling, in [Commit-doc rendering](#commit-doc-rendering) below.

This phase has **no disk side effects** — it returns a string. A missing required slot would have surfaced at phase 2 (`validate` blocks on required-slot presence); the renderer trusts validate.

### 4. Promote managed docs

For each managed doc instance in the task's working area (`.jigc/tasks/<task-id>/*.md`):

- **Copy** (not move) the file from the working area to its canonical path. The path comes from the doc type's `location:` field ([document-type-schema.md](document-type-schema.md) → On-disk definition format): an ADR lands in `decisions/`, a SPEC in `specs/`, and so on.
- **Placement doctypes promote to their literal home (M38).** A doctype declaring `placement: { file: … }` has `location: None`, so it promotes to its exact `placement.file` — a repo-root literal (`VISION.md`, `CHANGELOG.md`) or a direct `docs/roadmap.md` — never `<location>/<slug>.md` ([storage.md](storage.md) → Placement). `plan_promotions` computes this branch on both the single-task and fan-out-join paths. This is how M37's vision-render mechanism is **retired**: the `vision` is *promoted (managed) at root* `VISION.md` — one file, proper reconciliation — not regenerated as a mirror of a docs-buried source.
- The commit doc (`commit:<task-id>`) is **not** promoted — its sink is the git message rendered in phase 3, not a repo file ([write-commands.md](write-commands.md) → Instance provisioning).

Promotion is **copy, not move**, so rollback (if a later phase fails) is removal of the copies — not a complex undo. The working area stays intact until phase 7.

### 5. Stage

The agent has already `git add`ed its own code edits as it worked (the **agent-stage contract** — [Dirty-tree policy](#dirty-tree-policy)). This phase stages **jigc's own** managed artifacts into that existing index:

- every promoted doc (canonical paths from phase 4),
- on a first commit, the project config layer (`.jigc/config`, `.jigc/.gitignore`),
- since M45, every **recorded owner-artifact path** — the `owned-location` field values on the task's working-area docs (below).

The commit set is therefore **the git index** — the agent's staged code plus jigc's just-staged docs/config — committed whole (no curated pathspec, so an agent-staged owner-artifact like `completions/artifacts/**` rides along). finalize **never** runs `git add --all`: untracked and unstaged working-tree changes stay out of the commit and are surfaced (see [Dirty-tree policy](#dirty-tree-policy)).

**The recorded owner-artifact is staged, not merely ridden along (M45).** The `owner-artifact.present` gate asserts a `completion-record`'s named artifact is *durably staged/committed* ([methodology-docs.md](methodology-docs.md) → The recording surface; [validation.md](validation.md) → Severity inventory) — but until M45 nothing staged it, so the gate passed only on an artifact the agent had already `git add`ed *itself*, and the natural authoring order was a **closed two-node cycle**: stage the artifact → mint the recording task → `finalize` refuses `finalize.carried-staged` (the stage predates the task) → follow that route's `git -C <repo> restore --staged` branch → `finalize` refuses `owner-artifact.present` "stage it", whose route names the *path or field*, both already correct. Neither route ever said `git add`. M45 cuts the cycle on three sides ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle, Decision 5):

- **Finalize stages the recorded paths — and the gate moves after the stage.** This phase walks the task's working-area docs for `owned-location` field values and stages each, so the artifact lands in the **same transaction** as the record naming it — which is what [methodology-docs.md](methodology-docs.md) → The recording surface has claimed since M16. The ordering is **settled, not left to fall out**: the presence gate requires the path already **tracked** at phase 2, so a phase-5 stage could never satisfy it, and the alternative — relaxing the gate's `tracked` clause — would stop it proving durability *at gate time*, which is the only thing it proves. So the **gate moves after the stage**: the check keeps its meaning, at the cost of **reordering the finalize transaction**. That is not a small change to the doc's own seven-phase spine, and it makes this the wave's **riskiest change**; its acceptance says so. The gate keeps its teeth either way — it still adjudicates the path's safety and the artifact's presence, and still blocks when the named artifact is absent; staging a path is not evidence a path was authored.
- **A pre-staged artifact stops being carryover.** Owner-artifact paths join the carryover gate's exemption list (§ [The carryover gate](#dirty-tree-policy)) — pre-staging the artifact is the *expected* authoring order, not a foreign change riding the task's whole-index commit.
- **The finding names the command.** `owner-artifact.present` previously named only the *state* ("durably staged"), never the command that produces it; it now names **`git -C <repo> add -- <path>`** — aimed at the checkout the task commits in, and with git's own `--` option guard, both since M53 ([surface-contract.md](surface-contract.md) → The printed-path fence, the *pasteable shell bytes* rule). That route is **`Human`, not `Mechanical`** — a mechanical route's argv must lead with `jigc` or it cannot be constructed at all (the route fence, debug-posture, so a `git`-leading `Mechanical` reddens the suite). A `Human` route whose *text* names the exact command is the shipped precedent: `finalize.carried-staged` names `git -C <repo> restore --staged` that way ([validation.md](validation.md) → The route floor; [surface-contract.md](surface-contract.md) → The route fence).

The staging arm's headline risk is a **third rollback axis**, held to the M40 F7 discipline — restore each owner-artifact path's **pre-finalize index entry**, never merely un-stage (§ [Rollback discipline](#rollback-discipline)).

### 6. Commit

`git commit -F <rendered-message-file>` (a temp file, deleted after). The CLI **never** passes `--no-verify` — the user's `pre-commit` and `commit-msg` hooks are policy and the CLI respects them.

Outcomes:

- **Commit succeeds** → **relay any hook output to the agent**, then proceed to phase 7. A successful `git commit` can still produce hook output (a *non-blocking* `pre-commit`/`commit-msg` hook that warns but exits 0 — e.g. the M19 doc↔code backstop, below); the CLI surfaces that captured stdout/stderr to the agent on success, not only on rejection (M19 — resolves the [open question](#open-questions) below). Without this the warning is silently swallowed and the agent never sees it. **Placement + scope (M19 review S1):** the relay is **general** — git exposes one combined hook stream, so the CLI cannot single out jigc's own backstop from a user's linter/formatter hook; *all* non-blocking hook output is relayed. It is emitted in a **clearly delimited section after** the success result and **never inside** the routing footer, and the **relay** never rides the `--format json` document's stream (an agent parsing structured output must not have it corrupted). **Qualified at M45:** what M19 forbids is the *relay* riding the document's stream — the same captured text now also rides the envelope as the declared `hook_output` key, so stdout still parses as exactly one document and stderr still carries the verbatim relay ([command-output-contract.md](command-output-contract.md) → Stream discipline). This is a deliberate behavior change: a verbose user hook that previously had its success output swallowed by finalize now surfaces it — the honest fix (an agent committing through jigc *should* see its hooks speak), recorded here so it isn't a surprise.

  **Which stream — stated at M45, because the bullet above never said.** Under **`--format json` the structured envelope owns stdout and the hook relay goes to stderr**; under the agent format the relay goes to stdout with the rest of the result. The field-reported *"JSON pollution"* was harnesses **merging** the two streams, not a contract breach — the relay was already conformant, the discipline was simply unwritten ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle, the corrected charter premises). The **machine-contract** statement — the stream discipline as a pinned property, and the `hook_output` envelope field that carries the relayed text — is owned by [command-output-contract.md](command-output-contract.md); this bullet states only that finalize's relay obeys it.
  - **Fan-out finalize relays every fan-out commit (M19 review B1; rewired M31 Inc 5).** Both fan-out commit paths run the user's hooks and relay their output. Under **`squash: false`** there are **N+1** commits — one per *code-carrying* sub-task (each carrying that sub-task's own worktree code) plus the aggregate `git_commit` that promotes the merged docs + config; the user's `pre-commit`/`commit-msg` hooks fire on **each** and the success-relay surfaces **each** commit's output. Under **`squash: true`** there is one aggregate commit — the off-line combined tree committed with hooks running from a dedicated worktree ([§ `fan-out` finalize](#fan-out-finalize)) — and its hook output is relayed. A warn-only doc↔code backstop therefore runs the whole-store sweep once per fan-out commit (redundant across the N+1 `squash: false` commits but harmless; warn-only never aborts). *(A future optimization could skip the sweep on an unchanged diff; named so it isn't silently assumed.)*
- **Hook rejects, or other git error** → roll back: restore each promoted destination's **captured pre-finalize index entry** (the third-axis capture/restore primitive — never a `git restore --staged` reset to HEAD, which destroyed a blob the user staged at the destination mid-task; the confidence-audit promotions-axis fix, 2026-07-24) and undo the promote's worktree write (HEAD's bytes for a tracked destination, the promoted copy deleted for a new one). The working area is untouched; the agent sees the hook's stderr verbatim and re-runs `finalize` after fixing. The hook output **is** the correction signal — never bypassed.

  **The message must say the recoverability this bullet declares (M42).** The behaviour above is real and verified — after a hook rejection HEAD is unchanged, the staged set is still staged, and the task area survives *including its authored commit doc*, so removing the hook's cause and re-running `finalize` lands the commit. But the **message never says so**: it prints `` `git commit` was rejected (no commit was made): `` plus git's verbatim stderr, with **no finding code and no route** — an agent reading it cannot tell a recoverable hook rejection from a destroyed task. It gains the missing half: **task `<id>` is intact — fix the hook's complaint and re-run `jigc task finalize <id>`**. The hook's own stderr stays **verbatim and unwrapped** (the M40 refinement below is explicit that the routed wrap covers jigc's *own* staging acts, never the user's hook channel) — this adds jigc's sentence *around* it, never edits it.

  **The frame is the whole committing family's, not one door's (M47).** M42 landed it at `jigc task finalize` and left the other **eight** doors that run a hook-capable `git commit` on the user's behalf printing a bare `{err:#}` — no statement of what survived, no route, and (for the two `milestone finalize` arms) the *task* door's error code in the log, naming the wrong verb. The frame is therefore parameterized on the two halves only a door knows, and every door on the axis carries it:

  - a **state-truth clause** describing what *this* rejection leaves. It differs per door and must be true of that door: `task finalize` leaves the task's staged docs in its working area **and** whatever was `git add`-ed in the index, named as two areas rather than one word (M46 Inc 8 — a docs-only task stages nothing in git, so the single borrowed word described a state git could not show); `migrate-corpus` leaves the migrated bytes written and staged (and the corpus recorded unmigrated); a rejected `milestone create` unwound its record write **and** its workbench mint, so nothing of it survives at all (M47 Inc 2 — the captured-pre-image rollback is what makes the sentence true rather than a bricking notice). The clause that proves the rule is `add-from-spec`: its seeding is **resumable**, landing one record commit per sub-task, so a rejection at the *k*-th leaves the *k*−1 earlier commits as history no rollback takes back — it may not say "unchanged", and its acceptance drives the *k* > 0 state directly rather than only the first-commit case every other door's arm reaches;
  - the door's **own** copy-runnable re-run argv, echoing the flags a repeat run genuinely needs to reach the same commit phase again (`--carry-staged`, `--approve`, `--workflow`, `--force`, `--slug`) — an operator lifts the printed line verbatim. **"Copy-runnable" is a shell claim, so it is emitted shell-safe**: ids, slugs and addresses bare, every other token POSIX **single**-quoted, and the printed span fenced with a backtick run longer than any inside it. The doors embed **author-owned prose** (a milestone title, a sub-task intent, a rename target) — LLM-written by the determinism boundary — so `$`, a backtick and `;` are ordinary input, and a line that expands, substitutes or severs them **exits 0 having created a different artifact than the frame promised to recover** (verified live: `milestone create 'Cache $HOME rework'` re-ran as printed minted a milestone named after the *expanded* path). The fence is a real shell over the metachar axis, not the whitespace case the door fixtures feed;
  - the door's **own** route-exempt error identity, one per door ([surface-contract.md](surface-contract.md) → The error-code namespace, which holds the ten-member mirror and the enforcement).

  **The state-truth clause is a function of the rollback's OUTCOME, not a constant (M52 completion audit).** The clause above is composed *before* the transaction runs, and therefore before its rollback does — while M52 Increment 5 minted the two outcomes in which the rollback deliberately does **not** do what the constant asserts: `<door>.rollback-conflict`, where the compare-and-swap declines to overwrite a racer's bytes so jigc's own write survives, and `<door>.foreign-bytes`, where the minted-area unwind declines to remove an area holding a third party's file so the area survives. Both are carried as findings **beside** the frame, in one document — so the document contradicted itself. Driven at `c80b3f8f`: `jigc milestone create` under a record-racing hook printed *"nothing of milestone:text-arm-probe survives"* one line above `milestone.rollback-conflict` naming the record that did, with the file on disk; and `jigc milestone add-task` under an area-planting hook printed *"the sub-task mint was rolled back, so milestone:<id> is unchanged"* above `milestone.foreign-bytes` naming the surviving area. In **both** cells the frame's third part was falsified too: the re-run it prescribed was refused, by `milestone.record-exists` and by `task.serial-collision` respectively. So the clause is now composed against the rollback's own report — `conflicts.len()`, one finding per path the rollback could not put back, which is what every `cli::rollback::ROLLBACK_POPULATIONS` row promises — and with something left standing it **opens with the exception** rather than trailing it (an absolute that stands in the reader's first breath is the law-1 failure), keeps the door's own clause scoped rather than discarded, and prescribes the re-run only **behind** the surviving paths' own routes. Nothing about the clean cell moves: at `surviving == 0` the bytes are M42's, unchanged. The composition is one function serving all three render arms — hook rejection, git's own refusal, and the non-hook `CommitFailed` cell (M51's N20 widening) — so no arm can take the constant and skip the outcome. Driven per door at `crates/cli/tests/rejection_frame_outcome.rs`, over the doors **derived** from `COMMITTING_DOORS ∩ <the conflict-capable rollback populations>`.

  The doors are the enumerated axis of the one hook-capable commit seam (`task::git_commit_capture`), with `jigc setup`'s install commit excluded by its recorded `--no-verify` reason. `jigc task finalize`'s bytes are unchanged. Under `--format json` the framed text rides the `operational_error` envelope, as before.

**M40 (the rc.4 wave — settled 2026-07-10) refines the migration arm of stage + commit in three ways** ([DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 planning: Settle; [auto-migration.md](auto-migration.md) → the transaction mechanism):

1. **Staging discriminates the retirement pathspec on the *index*, not HEAD.** `stage_migration` includes the retire pathspec iff the path is still in the index (`git ls-files`), not iff it exists at HEAD — so a user who pre-staged the deletion themselves (`git rm` before finalize) no longer makes the stage-phase `git add` fatal on a vanished path. Skipping the pathspec loses nothing: the commit is whole-index.
2. **Stage-phase git failures are routed.** A git failure during *staging* is wrapped in a **routed finding with the git stderr embedded verbatim** — previously a raw enveloped operational error with no code and no route.
3. **Commit-phase hook rejections stay verbatim-raw.** The recorded decision above — the agent sees the hook's stderr verbatim; the hook output *is* the correction signal — is explicitly honored, not revised: the routed wrap covers jigc's *own* staging acts, never the user's hook channel.

**The M19 doc↔code backstop fires here (and is warn-only by construction).** `jigc setup` can install an assistant-neutral `pre-commit` hook that runs `jigc validate` (the store-wide doc↔code sweep) — so it fires on *this* commit too. It is **warn-only** (always exits 0, surfacing stale-anchor findings but never rejecting): a *blocking* store-sweep here would reject `finalize`'s commit for **unrelated pre-existing drift the task never touched** — re-introducing the masking-trap M18 designed `jigc validate` to avoid ([validation.md](validation.md) → Store-scope re-validation), and self-gating `finalize` on whole-store drift. So the backstop's output reaches the agent via the success-relay above, never as a `finalize` block. ([assistant-adapter.md](assistant-adapter.md) → neutral install; [roadmap.md](../implementation/roadmap.md) → M19.)

### 7. Post-commit (best-effort)

After the commit lands, three updates happen — none can affect commit truth, all self-heal if they fail:

- **Invalidate the edge-index stamp** ([storage.md](storage.md) → Derived caches). The next read rebuilds from the new HEAD.
- **Update `file-state` hashes** for every committed managed doc. The next `file-state` probe sees them as in-sync.
- **Keep what jigc did not write, then remove `.jigc/tasks/<task-id>/`.** The staging area's job is done; it persisted until here so rollback was possible across phases 4–6. The removal's subject is jigc's own files only: the area's **complement** ([team-ready-state.md](team-ready-state.md) → The working area's two populations) is moved aside first, to `.jigc/displaced/<task-id>/` with its relative paths intact, and named on stderr and on the landed envelope ([storage.md](storage.md) → The per-task working area, which owns the rule and its rationale). The removal is **never skipped for what jigc wrote, and never taken for what it could not move** (M53): it removes the area's own registry members and then the directory non-recursively, so an entry whose move failed — or one a hook wrote into the area during the commit — is left standing rather than destroyed, and the area it kept is named by one `finalize.foreign-bytes` advisory at exit 0.

A failure in any of these is **logged**, not raised — the commit is real, the system reads correctly because the edge-index stamp invalidates eventually, and a stale `.jigc/tasks/<id>/` gets cleaned up by `jigc task discard <id>`. **The second exit that clause used to name — *"or the next finalize reusing the slot"* — is struck: it was never true.** Driven on `rc.16` at M53 Increment 2 / T3, over both shapes a left-over area takes: re-finalizing one whose **base pin survived** exits **3** on `finalize.empty-commit` (it gets as far as the plan and there is no diff left to land), re-finalizing one whose pin is already gone exits **1** on *could not read the base pin*, and minting a task from the same intent refuses with `task.serial-collision` at exit 1. No path reuses the slot, which is why the advisory's route sends the operator to the path rather than to a re-run.

## Dirty-tree policy

A task is pinned to base commit `<A>` at start. **The commit set is the git index, not a sweep of the working tree** ([DECISIONS.md](../DECISIONS.md) 2026-06-20 → M30; this inverts the pre-M30 "everything differing from `<A>`" sweep). Under the **agent-stage contract**, the agent `git add`s its own code edits as it works; at `finalize` the CLI stages **its own** managed artifacts into that same index — the promoted docs (phase 4) and, on a first commit, the project config layer (`.jigc/config`, `.jigc/.gitignore`) — then commits the whole index as one logical change. The agent stages code; the CLI commits the index; neither places what the other owns ([write-commands.md](write-commands.md) → Staging and the transaction model).

**The sibling obligation — every work-workflow states the contract to the agent (M42).** Declaring the agent-stage contract *here*, as a system invariant, is **not sufficient**, and the RC adoption trial proved it: the agent never reads this document. The contract only binds if the **composed workflow says it**, so the invariant carries a second half — **every work-workflow's implement/finalize step states the `git add` contract to the agent, in every pack.** Without that line the next pack drops it, and one already has: the dev pack states it twice (`crates/cli/pack/steps/implement.yaml:1-2`, `finalize.yaml:1-3`), while the **methodology pack states it nowhere** — `dev-task` / `planning` / `increment` / `completion` compose **zero** mentions of `git add` — and its `packs/methodology/steps/finalize.yaml` **overloads the word "Stage"** to mean *set the commit-doc slot* ("Stage the subject line", "Stage the body"): an active semantic collision **in the one step where the git contract belongs**. That is the whole root cause of the trial's silent partial commits — a **prompting gap, not a mechanism gap** (the mechanism below is correct and blocks on an empty index). This is the same **un-enumerated-sibling** failure shape as the `schema.location` census ([storage.md](storage.md) → Placement): a rule declared once, applied at some sites, and never swept across the family — so it is written here as an obligation on *the family*, not as a fix to one file.

**Narrowed at M47 — the obligation over-covered the code-less family, and both packs' halves have now landed.** The M42 obligation above is affirmed on its rationale (the contract binds only if the composed workflow says it) and **narrowed on its scope**, because it was written when every workflow carrying it wrote code. It does not: **twelve** shipped workflows compose no code-writing step at all yet reach `finalize` — six in the dev pack (`architecture-documentation` · `plan` · `record-change` · `record-decision` · `project-setup` · **`amend`**, which reaches `finalize` to rewrite a message and must stage *nothing at all* — its arm refuses over a non-empty index outright, so the imperative is not merely untrue there but the opposite of the contract) and six in the methodology pack (`do-research` · `form-vision` · `park-idea` · `planning` · `completion` · `record-dogfood`) — and to every one of them the imperative *"`git add` your **code edits** first"* is a law-1 lie about work they will never do. So the obligation splits by what the step actually is:

- **The imperative belongs to the code-writing family.** *"`git add` your code edits as you work"* is stated in the step that tells the agent to write code — `crates/cli/pack/steps/implement.yaml`, `implement-quick.yaml`, `packs/methodology/steps/implement.yaml` — never in the shared commit step. That is where the trial's silent partial commits were actually authored, and it is the only family the imperative is true of.
- **The shared commit step states the contract descriptively.** `step:finalize` in both packs says *what finalize commits* — the git index: only what has been staged, plus the docs it manages, with unstaged edits and untracked files left out — which is true for every workflow that reaches it, including the code-less ones — two of which (`completion` · `record-dogfood`) genuinely stage an **unmanaged owner-artifact** by hand, so the consequence binds them even though no code is involved. The consequence half is what an agent needs; the instruction to stage *code* is not.

The M42 census in the paragraph above is therefore **historical**: as of M47 Increment 5 the solicit for the commit doc lives in `step:author-commit` in **both** packs (S1 — a rule-shaped fix lands on the whole surface or on half of it; [DECISIONS.md](../DECISIONS.md) → 2026-07-26 the Settle, Decision 5), composed by every task-minting non-migrate workflow immediately before its finalize include, and the *"Stage the subject line"* collision is long gone. The obligation is fenced two ways: structurally by `states-constraints:` (below / [surface-contract.md](surface-contract.md) → Structural stated-at), and over its whole axis by `crates/cli/tests/commit_solicit_axis.rs`, which sweeps the composite registry — every workflow both packs ship — and `crates/cli/tests/methodology_staging_contract.rs`, which holds the descriptive contract in the code-less methodology composes.

What this means for the working tree:

- **No `git add --all`.** Untracked files and unstaged tracked edits are **left out** of the commit — they are not the task's work until the agent stages them. The index *is* the declared touch-set, expressed by `git add`, not inferred from the tree's delta from base.
- **Left-out WIP is surfaced, not committed (and not refused)** — a landed `finalize` names what it left behind (see *Surfaced, not prevented*, below), so a stray `scratch.txt` stands out rather than riding the commit silently.
- **Block on nothing staged.** If the narrowed commit set is empty while the tree is dirty, `finalize` blocks (*"you staged nothing — `git add` your changes"*) rather than sweeping unrelated WIP in to avoid an empty commit (see [Empty commit](#commit-doc-rendering), below).
- **Parallel hand-editing** (a human editing other files on the same branch while a task runs) is caught upstream by the base-pin: if the human commits, HEAD moves and the base-mismatch rejection in phase 1 fires; if the human only edits without committing, the changes show in `jigc task diff <id>` before `finalize` and stay out of the commit unless the agent stages them.

  **Amended at M17 planning (2026-06-12) — phase 1 gains a re-pin path.** The unconditional rejection proved wrong for serial-task shapes the methodology itself mandates: a completion task minted at audit-start finalizes *after* its fix commits land, so its base has moved **by design**, and discard-and-reauthor was the only route (verified by exercise on a foreign repo). Phase 1 now **auto-re-pins** when the moved history is disjoint from the task's work: re-pin to the new HEAD iff *(paths changed in commits between the recorded base and HEAD)* ∩ *(currently-dirty working-tree paths ∪ the task's promote destinations)* = ∅, then re-run the preflight sweep against the new base. Any overlap keeps the block — now with a conflict route naming the overlapping paths — which is exactly the parallel-hand-editing case this bullet exists to catch. ([DECISIONS.md](../DECISIONS.md) 2026-06-12; the M17 pre-fix set.)

  **Widened at M47 (N7) — the rule is the *task's*, not finalize's.** The amendment above was written as a phase-1 fix and its scope bound was drawn against the **milestone** sibling (`plan_milestone_finalize` stays consciously strict); the **read-only resume door** was never enumerated, so `jigc start --task <id>` kept a blanket `base != HEAD` refusal and was therefore *stricter than the commit door it precedes* — one repo state gave resume a refusal, `task validate` exit 0, and `finalize` a landed commit. Resume now makes the **identical decision** — the same function over the same facts (base→HEAD changed paths, dirty working-tree paths, promote destinations from the shared phase-4 sweep), never a re-implementation — and its re-pin is likewise **in-memory only**. The change is *un-refusing*: every state it converts was already a refusal, so no driver that succeeds today begins to fail. The widening is scoped to **top-level** tasks, whose commit door this is: a **milestone sub-task** keeps the blanket refusal at *both* its per-task read doors (`jigc workflow <W> --task <sub>` re-entry **and** `jigc start --task <sub>` resume), matching the strict milestone commit boundary that is its only one. ([DECISIONS.md](../DECISIONS.md) → 2026-07-26 the M47 Settle, Decision 10; [storage.md](storage.md) → The per-task working area.)

The benefit is precision: the commit carries exactly what the agent staged plus the docs/config jigc manages — no hidden allow/deny list the agent must reason about, and no unrelated working-tree WIP silently riding along.

**The staging policy — per-task, migration, and fan-out combine (M30/M31).** The index-honoring scope above is the **per-task** finalize policy (`StagePolicy::IndexHonoring`; a migration task uses the fixed `MigrationFixed` narrowing). The **milestone fan-out** isolates each sub-agent's code in its **own git worktree** (M31; [storage.md](storage.md#cli-and-git) → the third combine mode), so a fan-out commit reads sub-agent code **from the worktrees**, never from a `git add --all` sweep of the shared checkout — the whole-tree `Sweep` is **retired** (under worktree isolation it dropped every line of sub-agent code, the data-loss the redesign fixes). The two squash modes diverge: **`squash: true`** folds the N worktrees' staged code-sets into one combined tree **off-line** (`StagePolicy::Combine`), then commits that tree from a clean dedicated worktree so the user's hooks run against it WIP-safely ([§ `fan-out` finalize](#fan-out-finalize)); **`squash: false`** commits each sub-task's worktree code per-sub-task (hooks run + relay on each) and then promotes the merged docs through `IndexHonoring` over the now-clean index. So the staging policy is three-way — per-task non-migration → `IndexHonoring`, per-task migration → `MigrationFixed`, `squash: true` fan-out → `Combine` ([DECISIONS.md](../DECISIONS.md) 2026-06-20 → M30, the SPLIT + G1; 2026-06-21 → M31 Inc 5).

**Surfaced, not prevented (B1, [DECISIONS.md](../DECISIONS.md) 2026-06-19; narrowed at M30).** A landed `finalize` emits a **change-set manifest** — the committed set (the index: the agent's staged code + the promoted docs + first-commit config), each path tagged by how it entered (promoted / modified / deleted / added — a deliberately-staged new file — and, since M43, **carried-over**: a pre-task staged entry riding under a declared `--carry-staged`, labeled identically at all four render sites — dry-run forecast, pre-commit print, landed text, landed JSON; the carryover gate below), **plus a distinct `left-out` list** naming what the commit excluded (untracked files + unstaged tracked edits) so a stray `scratch.txt` stands out as left-behind rather than swept in. A staged-then-further-modified path appears in **both** lists — its staged bytes commit, its later worktree delta is left out. `jigc task finalize <id> --dry-run` prints that manifest and stops — committing nothing, no destructive side effect (and needing no `--approve` on a migration task) — **and, since M50, names the commit's subject line above it** (`would commit — <subject>`; `subject` on the JSON envelope). The forecast reads the *same* render phase 3 already produced (`FinalizePlan::subject`, the first line of the rendered message), so the string it forecasts is byte-for-byte the one the landed ack prints as `finalized <hash> — <subject>` — never a second spelling, which for an unset optional `scope` would compose `feat(): …`. **Declared bound:** the forecast claims what jigc will hand git, never what git ends up with — a `commit-msg` hook may still rewrite the message (RC-m50 → F-7). This *surfaces* the set; it does not refuse anything beyond the empty/nothing-staged block — and, since M43, the carryover gate below.

**The `left-out` advisory prints BEFORE the commit too (M42).** The `left-out` list above lands **after** the commit — by which time the partial commit is history and the agent's only recourse is a follow-up. A **pre-commit advisory print** joins it: when the index is non-empty but the tree carries unstaged/untracked work, `finalize` **says what it is about to leave out, before it commits**. It still commits — the block stays reserved for the *empty*-index case.

**The carryover gate — a second sanctioned refusal (M43).** Each of the three task-minting doors (`jigc start` compose forms, `jigc migrate`, `jigc milestone create` for the shared checkout's aggregate index) snapshots the pre-task staged state — the staged set (path + blob) **and the staged-deletion set** — into the working area. The `finalize` **committing path** — after the `--dry-run` branch, so the forecast always renders — re-probes the index and **refuses** when any of it was staged *before the task existed*: **one blocking routed `finalize.carried-staged` per carried path** (file-path target form; [command-output-contract.md](command-output-contract.md) → the finalize sub-table), so a foreign pre-staged change (add, modify, or delete) cannot silently ride the task's whole-index commit. Override with `--carry-staged` (the `--approve` mold — undecidable intent converted to a declared one; on a migration finalize it **composes** with `--approve`, two independent declarations). The migration's own retire pathspec is exempt (that deletion is the task's work), **since M45 a recorded owner-artifact path is exempt too** (§ [5. Stage](#5-stage) — the artifact is the task's work, and finalize now stages it in-transaction), and a **missing snapshot fails open** — a task minted pre-M43 finalizes as today (the declared bound). **Since M51 the gate's subject is the wider class — *a door committing paths it does not own* — and `jigc setup`'s install commit is its second member**: it mints no task, so it asks its own install pathspec against `HEAD` **before it writes a byte** instead of a snapshot, and refuses with one blocking routed `setup.dirty-install-path` over the whole dirty set **having installed nothing** — the pre-write ask being the only way the refusal's *every path still has its pre-run bytes there* can be true at a path the install rewrites whole (the conjunction that also required the path to be dirty *afterwards* is struck with its falsifying datum at the M51 completion audit) — with the same predicate re-asked before the commit as the hook's backstop, and `jigc setup --force` the single consent, which consents rather than preserves and says so ([validation.md](validation.md) → The M51 registrations — Increment 3). **The widening is scoped to Increment 2's commit-on-behalf partition, and to the doors in it that ask** — as a universal it is false at HEAD, `jigc rename`, `migrate-corpus` and the milestone record-only doors committing without this question at all (`completions/artifacts/M51/settle-record.md` → §13). Full contract: [surface-contract.md](surface-contract.md) → The carryover gate.

**The M30/B1 "surfaced, not prevented" record — the M42 reading, revised at M43 on its changed factual basis.** That rationale is about **refusing**, and its basis was the **pre-M30** danger: jigc sweeping unrelated files **in**. M30 **inverted** the danger — the commit set is now the index, so the live failure the M42 print addresses is work left **out** (the trial's silent partial commits). A pre-commit *print* is **still surfacing**, and that M42 settle **stands untouched**: left-out WIP is never refused, and no `--strict` dirty-tree knob exists. What changed is the ride-**in** half: the lacon-trial evidence (A6/A7/A10, postdating the M42 re-affirmation) showed the pre-M30 danger returning **through the index** — a foreign pre-staged change silently riding the whole-index commit — which the index-as-declared-touch-set model cannot distinguish from the task's own work without the mint-time snapshot. The carryover gate above is therefore a **second sanctioned refusal**, joining the empty/nothing-staged block: scoped precisely to what predates the task, and overridable by declaration. The record's rationale stands for the *left-out* direction; its "refuse nothing beyond the empty-index block" reading is superseded for the *carried-in* one.

**It reads *every jigc transaction*, not *`finalize` before phase 6* (M52).** The M51 wording named the phases because the phases were what anyone had enumerated: the populations it could be checked over were this executor's. Driven, the class is larger than this table — `jigc rename`, `jigc config set docs-root` / `placement-root`, the five record-only doors and the two minted-area unwinds each undo what a failed transaction wrote — bytes put back, or a minted working area removed — and **not one of them has a phase 6** — and at M52's base they did not share a discipline: `jigc rename` deleted a hook's bytes at the landing path, `jigc milestone create` deleted a racer's file at the record path, and the mint unwind took the whole area, each at **exit 1 with nothing on any surface saying so** (`completions/artifacts/M52/baseline-rollback.md` §2.1a · §2.3b; the third is the datum quoted in the config-layer row above). A promise scoped to the phases would have been kept by a binary that loses your file at a door this doc does not describe, which is a promise about a *section* rather than about jigc. So the subject is the **transaction**, wherever one runs, and what makes that checkable rather than aspirational is that the class is now enumerated in code with a discipline per member — `cli::rollback::ROLLBACK_POPULATIONS`, fenced in both directions by `crates/cli/tests/rollback_population_registry.rs`: a restore site the source gains without a row reddens, and every row's discipline is bound by the source rather than declared (M52 Increment 5; `completions/artifacts/M52/settle-record.md` → D1).

**The promise's one stated exception, and it is not an escape hatch.** A rollback can only put back what it can put back *without destroying something else*. When a path's bytes changed between jigc's write and the rollback, the transaction has no honest all-or-nothing move available: restoring overwrites a third party's edit, and doing nothing leaves jigc's bytes behind. It takes neither silently — it **preserves both versions and says so**, with one blocking `<door>.rollback-conflict` naming each (`finalize.rollback-conflict` at the two finalize doors; since M52 the record-only doors, `jigc rename` and the root-knob re-point raise their own, and the membership is `cli::rollback::ROLLBACK_DOORS` rather than a list here — fenced against the codes production mints and the codes [validation.md](validation.md) registers, in both directions). So the invariant a reader can rely on is: *nothing jigc wrote inside a transaction survives that transaction's failure except where surviving it is the only way to avoid destroying someone else's bytes, and every such survival is named.*

After phase 6, the commit defines truth and any post-commit residue is a chore, not a transaction issue.

**The chore is the worktree teardown, and *chore* binds the transaction, never the account it gives (M51).** Tearing the fan-out worktrees down is post-commit: it may fail without failing a boundary that has already landed, and it is best-effort by design (§ [`fan-out` finalize](#fan-out-finalize)). It is also one of the **destroying doors** — the verbs that delete bytes existing in no object DB — and that membership is not relaxed by sitting after the commit: it must not claim a destruction it did not perform, must not stay silent about one it did, and must name what it found in the *same* terms the refusing doors name it in, because an operator reading two accounts of one path has no way to tell which is the true one. **Its subject is the worktrees git has registered here**, which is narrower than theirs (`jigc milestone provision` / `discard` / `uninstall` each read a path on disk) — so a leftover nothing registered is neither removed nor narrated at this door, and the shapes that reach the other three genuinely cannot arrive here. Driven where the two halves disagreed: over a **symlink** at a sub-task's worktree path, the refusal named *the file itself* while the consenting run called the same path a directory, listed three of the repository's own committed docs as *not recoverable*, and removed the link alone (`completions/artifacts/evidence-check-1.0/data-loss-hunt.md` §2; [DECISIONS.md](../DECISIONS.md) → 2026-09-15).

**A failed finalize must be legible in the invocation log (M42).** Every failure path above rolls back correctly — but not every one is *identifiable afterwards*. A finalize blocked at **phase 2** logs its finding codes (exit 3, `finding_codes: [schema-conformance.…, …]`) because a validate block travels as `Finding`s. A finalize rejected at **phase 6** by a git hook does not: it bails as an operational error and logs `finding_codes: []` at exit 1 — **indistinguishable in the log from "no such task."** The failed-finalize class the RC adoption trial actually hit is the one the log cannot name ([measurement.md](measurement.md) → the invocation log). The gap is *error identity*, not record-writing: errored verbs do write records, and blocked ones do carry their codes; what is missing is that **jigc has no error-code vocabulary at all** — operational errors are unstructured prose with no code and no route, so only failures that happen to route through a `Finding` are ever identifiable.

The constraint that shapes the fix, stated here because it is a **design** constraint and not a coding detail: under the M41 output contract **every advisory carries a route** ([command-output-contract.md](command-output-contract.md) → the findings envelope), so routing the operational-error paths through `Finding` would give **every** error a *mandatory* route — including errors whose honest route is "nothing you can do." Whether the finalize failure paths earn finding codes, a separate error-code vocabulary, or a route-exempt error variant is therefore a **surface decision**, not a free refactor; it is settled at increment level, not here. What this doc pins is the requirement: **a finalize that did not commit must be identifiable, from the log alone, by *why*.**

## `fan-out` finalize

A `fan-out` workflow's parent task's `finalize` is the commit boundary; sub-agents **stage code in their own worktree and author their managed docs, but never commit** ([workflow-dialect.md](workflow-dialect.md#fan-out--join)). The two substrates isolate differently (M31; [storage.md](storage.md#cli-and-git) → the three combine modes): a sub-agent's **code** lives in its own git worktree (`.jigc/worktrees/<sub-id>`, `git add`ed there), while its **managed docs** are written into its directory-isolated `tasks/<sub>/` area. The transaction expands:

1. **Combine the substrates into the parent.** **Docs** merge by the deterministic by-task-id join — by task-id order; slug collisions resolve via the deterministic suffix ([workflow-dialect.md](workflow-dialect.md#fan-out--join), [storage.md](storage.md#the-by-task-id-join-m7)). **Code** is combined by reading each worktree's staged set in task-id order with **disjoint-apply + block-on-collision** (a cross-worktree same-file write blocks + routes the named paths, never `git merge`; [storage.md](storage.md#cli-and-git) → the third combine mode) — checked **up front**, before any commit.
2. **Validate** the merged effective state — one validate run, not N. **Built at M45** (§ [2. Validate](#2-validate) — in `run_milestone_finalize` after `materialize` and the base guard, before the record flip, the plan, and the `squash` branch below; never inside engine `join`); until then this step was design of record only and the milestone boundary had no conformance gate.
3. **Render, promote, stage, commit — gated by the `finalize.fan-out.squash` cascade knob.** M7 shipped only the synthesized single-commit form; **M8 added per-sub-task authored commit docs and the knob** ([DECISIONS.md](../DECISIONS.md) 2026-06-04 → M8 Settle); **M31 made both paths carry the worktree-isolated code and run the user's hooks** ([DECISIONS.md](../DECISIONS.md) 2026-06-21 → M31 Inc 5). The two modes:
   - **`squash: true` (default) — one aggregate commit.** The CLI folds the N worktrees' staged code-sets into one combined tree **off-line** (a throwaway index), overlays the promoted docs + first-commit config, and commits that tree from a **clean dedicated worktree** — where `git commit -F` (never `--no-verify`) runs the user's `pre-commit`/`commit-msg` hooks against the combined tree — then **fast-forwards main only after the commit lands**. The main checkout is never mutated until that clean fast-forward, so a blocked combine or a hook rejection lands nothing and leaves unrelated main-checkout WIP intact (WIP-safe). The message is **synthesized deterministically by the CLI** — a structural projection of the milestone id + its id-ordered sub-task list (no authored prose, so it's *structure* the CLI owns, not a slot; like git's auto-generated merge message); it is byte-identical across feed orders, which the determinism acceptance requires.
   - **`squash: false` — one commit per code-carrying sub-task in task-id order, then the parent's aggregate commit.** Each per-sub-task commit applies **that one worktree's** staged code onto the checkout and `git commit -F`s the sub-task's own authored `commit` doc — `git commit` (never `--no-verify`) runs the user's hooks on **each**, and **each** commit's hook output is relayed. A sub-task that staged no code contributes no commit. The **merged docs ride the parent's aggregate commit** (the by-task-id doc-join is a cross-sub-task merge with suffix resolution — [storage.md](storage.md#the-by-task-id-join-m7) — not cleanly partitionable, so docs are a milestone-level artifact, not a per-sub-task lie). The parent renders each sub-task's commit doc in id order, so the commit *sequence* is deterministic (byte-identical across feed orders) even though each message carries LLM prose — consistent with the determinism boundary (the CLI owns ordering + placement; the prose is the sub-agent's).
4. **Post-commit** runs once for the whole batch.

**The landing manifest names what each sub-task contributed — including the sub-tasks that could not (M47, its warrant corrected M46).** A landed boundary prints one contribution entry per sub-task in id order (`<id>: 1 doc, 1 code file`; the no-work one `nothing staged`, never silently credited). The isolated worktree is the **only** place a sub-agent's code can live, so a sub-task with **no worktree at its path** contributed no code — a fact a bare `code_files: 0` cannot distinguish from "the sub-agent staged nothing." Every such sub-task is therefore named — `no worktree provisioned`, on the agent text and as `provisioned: false` on the `--format json` envelope — so the degrade is visible rather than silent ([DECISIONS.md](../DECISIONS.md) → 2026-07-26 M47 Increment 3 halt resolution, call (b)(ii)). The clause states the *code channel's* absence, so it rides a sub-task that merged docs just as it rides an empty one.

**The landing ack names every commit the boundary made, and attributes every landed file to the sha that landed it (M50).** Under `squash: false` the boundary is a *chain*, not a commit — so an ack naming HEAD alone beside the whole boundary's landed-file set says that sha landed files it does not contain. It does not: the ack carries `commits`, every commit in the range `<pre-boundary-HEAD>..HEAD` oldest first with the paths **that** commit changed, and each sub-task's contribution carries its **own** sha (`null` where the boundary minted none — `squash: true`, or a sub-task that staged no code). The landed-file manifest keeps its boundary-wide membership; `commits` is the attribution laid beside it, and where a path was landed by more than one chain commit its owning sha is the **last** commit that landed it, the one whose bytes are at HEAD ([command-output-contract.md](command-output-contract.md) → the pre-1.0 additive-key window, the M50 declaration). The range is read from git rather than reported by the commit path, so the set is complete by construction — including after the `squash: false` chain's fast-forward, which is where the shas the chain built in its dedicated worktree actually become HEAD's ancestors.

**The subject is the on-disk path, never the registered set** — and the *by construction* warrant this paragraph carried until M46 is **withdrawn**, because it was a claim about `.git/worktrees/` admin records rather than about the disk. A `cp -R` or `mv` of a repo leaves those records naming the **source's** paths, so the boundary saw no worktrees at all exactly where the sub-agents' live work sat: `no worktree provisioned` printed over directories holding the work, and a docs-only commit at exit 0 (M46 Inc 2 — the same wrong subject M48 had already retired at the destroying doors, [team-ready-state.md](team-ready-state.md) → Abandon refuses on a dirty worktree). Membership is the shipped `OwnWorktree` verdict on a path that **exists** — never registration, and never mere existence either, since `git diff --cached` in a plain directory under `.jigc/worktrees/` answers with the *enclosing* repo's staged set. The third case is a third fact rather than a shade of the second: a path git cannot read is named as **unread** (`unreadable worktree at …, no code counted`), and `nothing staged` is withheld there, because that clause is a measurement and nothing could be measured.

Either mode keeps fan-out reproducible: the committed bytes (message(s) + tree) are identical given the same `definition + cascade + live state`, independent of completion/feed order. The default (`true`) is the conservative continuation of M7's one-commit boundary; `false` is the opt-in for projects that want per-sub-task commit history. Both honor finalize.md's never-`--no-verify` contract — the user's hooks run on every fan-out commit ([What `finalize` does NOT do](#what-finalize-does-not-do)).

## The amend arm

`jigc task finalize <id>` has a **second commit model**, selected by the task rather than by a flag: a task minted through **`jigc task amend`** carries an `amend` marker holding the sha it pinned, and finalizing it runs `git commit --amend -F <message>` with the **tree untouched** — it rewrites `HEAD`'s message and adds nothing (F-10; the settle of record, `completions/artifacts/M53/f10-amend-settle.md`; the origination door is [write-commands.md](write-commands.md) → Task origination). It is the `milestone finalize` two-arm precedent applied to the task door: one leaf, two commit constructions, each with its own `COMMITTING_DOORS` row, its own `commits:` help clause and its own error identity (`finalize.amend-rejected`).

**Why the door exists at all, and why it does not parse.** The rc.14 trial's only adapter bypass was a worker who landed a finalize with a wrong summary, found no jigc path, and rewrote the commit with raw `git commit --amend` — typing `<type>(<scope>): <summary>` by hand, which is precisely the structural operation the product exists to take away. The repair could have read `HEAD`'s message *back* into a commit doc; it deliberately does not, and the reason is driven rather than aesthetic. The render is **lossy and ambiguous**: a body paragraph shaped `Refs: <value>` is indistinguishable from a trailer item on the way back (driven — a doc with **zero** trailer items lands a message any last-block parser re-authors into `#trailers`), the schema's `implements:` ref is projected into no message at all, and under `finalize.fan-out.squash: true` there is no authored commit doc behind the boundary message in the first place. So the agent **re-authors from scratch** through the ordinary `jigc doc` verbs and jigc renders — the determinism boundary held at the one place the thesis is sharpest.

**The index is the hazard, and the refusal is not a papercut.** `git commit --amend` rewrites `HEAD` **from the index**, so anything staged when it runs is folded into the rewritten commit, silently, at exit 0 — driven: `HEAD` held one file, an unrelated path was staged, the amended commit carried two. That is `finalize.carried-staged` re-enacted on a commit that has *already landed*, so the arm refuses over a **non-empty index** with one blocking `finalize.amend-index-dirty` per staged path, routed at `git restore --staged -- <path>`, and it takes **no `--carry-staged`**: on the ordinary model a carry can be deliberate, while here every staged path is wrong by construction — the arm's whole contract is that the committed tree does not move. The carryover gate itself is **exempt** for these tasks, and this is the reason stated at its row: an amend stages nothing, so that gate has nothing to decide, and this one is its stricter replacement. Both are the same *member* of the previewed set (`cli::gate_coverage::GATE_COVERAGE` → `carryover` — the **index gate**, whose check is the commit model's), so `jigc task validate` and `--dry-run` preview this arm's check at the same severity and the same exit the committing door takes.

**The other refusals.** `jigc task amend` refuses a `HEAD` an amend cannot rewrite — unborn, a root commit, or a merge commit — with `amend.head-shape`, adjudicated **before anything mints**; a root is refused although git would take it, with the route handing the act back by name. At the finalize arm, a `HEAD` that has **moved** since the mint is `finalize.base-mismatch`, re-worded for this arm because an amend's pin is the commit it *rewrites* rather than the history its work sits on — *"switch back"* would silently mean a different repository state. The **repository-posture** family transfers unchanged: the mint door is `BEHALF_DOORS`' `Neither` and adjudicates none of it, exactly as `jigc start` does, while the finalize arm is commit-on-behalf and refuses every member — which is also what makes a fan-out worktree's detached `HEAD` safe. A rejected commit leaves `HEAD` **byte-identical** (driven: `git commit --amend` is atomic with respect to `HEAD`), which is this door's state-truth clause in the survivable frame and the cheapest in the registry: nothing was promoted, nothing was staged, and there is no rollback to scope.

**What it deliberately does not do.** It cannot tell *which door made `HEAD`* — there is no trailer, no persisted sha, and task ids are re-mintable, so a milestone boundary's structural message, a record-only bookkeeping commit and a foreign commit are indistinguishable from an ordinary one. Inventing a discriminator (matching jigc's own message format) would be the pattern-match this repo refuses elsewhere, so instead the verb's name and help say what is true — *amend `HEAD`, whatever `HEAD` is* — the composed step names the three shapes an agent should not re-author, and the mint ack prints `HEAD`'s current subject line **above** the instructions so the reader sees what is about to be replaced. It cannot tell whether the commit was **pushed** either (driven: `git branch -r --contains HEAD` is empty for a never-*fetched* remote as well as a never-pushed commit), so that rides the ack as an advisory sentence and never as a fence. And **content amend is not built**: the tree is untouched by construction, which is why a promoted doc in `HEAD`'s tree stays valid across an amend — jigc's file-state baseline is content-keyed, so a message-only rewrite is genuinely invisible to it. A wrong *change* is a new task, not an amend.

## Commit-doc rendering

The commit doc's schema (pack-default for the development pack — Conventional Commits) is:

| schema element | git-message slot | rule |
|---|---|---|
| `type` field (enum) | subject `<type>` | required |
| `scope` field (string, optional) | subject `(<scope>)` | omitted entirely if empty (no empty parens) |
| `summary` slot | subject line text after `: ` | required |
| `body` slot (optional) | body paragraph(s) | preceded by one blank line; section skipped if empty |
| `trailers` repeatable section | footer `key: value` lines | preceded by one blank line; section skipped if empty |

The rendered shape:

```
<type>(<scope>): <summary>

<body>

<trailer-key>: <trailer-value>
<trailer-key>: <trailer-value>
```

**Line limits.** Conventional Commits suggests 50/72 for subject/body. These ship as `commit-rendering.line-limit-subject` and `commit-rendering.line-limit-body`, both **advisory at pack-default severity** ([validation.md](validation.md) → Severity inventory). A project can promote to blocking via the cascade if it requires hard enforcement (`validation.commit-rendering.line-limit-subject.severity: blocking`).

**Cascade customization.** The commit doc's schema lives in the pack and is overridable like any doc type. A project that rejects Conventional Commits ships its own commit schema in its project layer.

**Trailers are authored *items*, not schema fields — this passage said the opposite, and both halves were false (corrected M45).** It previously read *"the renderer reads the schema, so no code changes"* and *"[trailer fields] are added as **`field` declarations** under the `trailers` repeatable section."* The shipped shape is `id-from: key` + a `value` field, so **each trailer is an item the task authors** (`jigc doc add-item` per trailer: the key is the item's heading, the value its one field) — extending the trailer *set* is authoring, not schema editing. And the message projection is **not** generic schema-driven rendering: it addresses the commit doctype's well-known ids by name (the `COMMIT_*` constants in `crates/engine/src/write.rs`) — a deliberate, documented coupling for the one doctype whose sink is the VCS message, with a schema-declared message template left post-MVP ([DECISIONS.md](../DECISIONS.md) 2026-05-31). So a `field` declaration added under `trailers` would render an inert bullet the renderer never reads, and a project's own commit schema does not get the projection for free.

**M45 fixes the renderer's half — the trailers were dead on the entire real write path.** Under `id-from: key` the key renders as the item's **heading**, never as a trailing `key:` bullet, while the renderer looks the key up as a *field* — so no authored trailer has ever reached a rendered message, and the defect survived 2195 green tests because the `commit` doctype was exempted from the round-trip suite on the false premise that it *"has no on-disk round-trip to fence"* (it does: `.jigc/tasks/<id>/docs/commit:<slug>.md`, `render` ↔ `instance_from_source`). The fix reads the key from the item **title** under id-from semantics (the heading **is** the key), paired with a **shape guard over every id-from field** as an engine intrinsic — required, not optional: one whitespace key kills the whole trailer block, so a title-reading fix without the guard is a regression ([validation.md](validation.md) → the id-from shape intrinsic; [DECISIONS.md](../DECISIONS.md) → 2026-07-23, Decision 4).

**Empty commit.** If validate passes but the narrowed commit set (`git diff --cached` + the promoted docs + first-commit config) is empty, `finalize` aborts — no empty commits. The CLI selects the message by *why* it is empty: a **dirty tree with nothing staged** blocks with *"you staged nothing — `git add` your changes"* (the agent has work but never staged it); a **genuinely clean** tree aborts with *"task validated but produced no diff — nothing to finalize."* This narrowed empty-check is **per-task only**. The milestone fan-out paths have no whole-tree empty-check: under `squash: false` a sub-task that staged no code simply contributes no commit, and under `squash: true` the combine reads staged code from the worktrees — a milestone whose sub-tasks were never provisioned still lands its **merged docs** as a docs-only aggregate ([§ `fan-out` finalize](#fan-out-finalize)).

**The zero-contribution refusal — the milestone boundary's own sanctioned block (M47).** The degrade above was stated unconditionally and was **wrong at its floor**: with *no* merged docs and *no* staged worktree code, the boundary's only change is the milestone record's own `active → joined` flip, which `has_diff` counts as a diff (the M39 fold — a docs-only milestone's record flip is not an empty commit). So a **fresh clone**, which carries the committed record but none of the gitignored `.jigc/` workbench, finalized at **exit 0 having landed zero work** — and flipped the record to the *terminal* `joined`, so the milestone could never be finalized again (verified live). `finalize` now **refuses a boundary that would land no work**: one blocking `milestone.zero-contribution` keyed at `milestone:<id>`, whose route names both honest exits — `jigc milestone provision <id>` (give the sub-tasks a working area, execute, `git add`, re-run) or `jigc milestone discard <id>` (settle the record as abandoned). The record flip is restored by its guard, so the milestone stays finalizable. It cannot false-fire on a genuine docs-only milestone: that one *promotes* its merged docs.

**The predicate is what would land, not `has_diff`.** *"Blocks when `has_diff` rests solely on the record flip"* is the motivating case, not the rule — and taken literally it leaves the same zero-work commit reachable one channel over: `has_diff`'s doc term counts every **materialized** address, and a sub-task's `commit:<sub-id>` doc is **transient** — materialized by the join, never promoted (a doctype with neither `location` nor `placement` has no store destination). So a milestone whose sub-agents authored their commit messages and staged no code landed the identical zero-work commit at exit 0, verified live. The refusal therefore keys on the plan's **promote set ∪ the worktrees' staged code** — the set that actually lands — closing the whole contribution-channel axis at one seam. It sits immediately after the planner, so the planner's staging / base-mismatch / **empty-commit** blocks keep precedence, and its message states the terminal-`joined` consequence **only** under a project that has a record to flip. This replaces the settled *"refuse when a milestone **recorded as provisioned** has no live worktrees"*, **withdrawn as unbuildable** — no such record exists, and a `.jigc`-local marker fails open by construction on the very fresh-clone case it would exist to catch; its only durable home is the committed `milestone-record`, a frozen manifest-governed doctype, i.e. a one-way door deferred to M46 ([DECISIONS.md](../DECISIONS.md) → 2026-07-26 M47 Increment 3 halt resolution, call (b)(i)).

## What `finalize` does NOT do

- **No three-way merge.** A true conflict between the task's working area and an out-of-band edit is blocked, not auto-resolved ([write-commands.md](write-commands.md) → Out-of-band reconciliation); three-way merge is deferred and parallels override-conflict resolution.
- **No schema migration.** A doc-type schema version bump that requires re-rendering existing instances is a separate operation; `finalize` only writes content the task authored against the current schema.
- **No LLM call.** Like the rest of the CLI core, this transaction is deterministic — same `(task working area + base commit + cascade)` in → same commit out ([VISION.md](../VISION.md) principle #1).
- **No `--no-verify`.** Pre-commit and commit-msg hooks are the user's policy. The CLI respects them; bypass would be silent-data-loss territory. *(Re-confirmed at M42, not re-argued: `--no-verify` is absent from every finalize path. The one occurrence in the codebase is `jigc setup`'s own install commit (`crates/cli/src/setup.rs:1002`) — a **distinct** self-commit boundary over jigc's own config paths, not a task's work.)*

## Open questions

- **Multi-doc promotion ordering** — when a task produces multiple managed docs (e.g., an ADR plus edits to an existing SPEC), the stage set is order-independent for git, and the edge-index updates after commit. Flagged as a non-issue under the current edge-index design; revisit if it surfaces.
- **`finalize --dry-run`** — **resolved (B1 / M30; widened at M50):** `jigc task finalize <id> --dry-run` walks the transaction without committing and prints the **change-set manifest** — the commit's forecast **subject line**, what would be committed (the index) and what would be left out (untracked / unstaged WIP) — alongside the validation preview `jigc task validate <id>` already gives. See [Surfaced, not prevented](#dirty-tree-policy).
- **Commit-msg hook output capture** — **resolved (M19):** the CLI relays the captured `git commit` stdout/stderr to the agent **on success** (not only on rejection — phase 6), so a non-blocking hook's warning (e.g. the M19 doc↔code backstop) reaches the agent instead of being swallowed. The richer structured blocked/error-payload shape ([write-commands.md](write-commands.md#open-questions)) stays the broader open question; M19 settles the success-relay specifically.
