# The doc read surface — `jigc doc show` + the pinned `--format json` contract

**M39 design of record.** Where the *committed-doc read* is pinned. `jigc doc show <ref>` is the one verb that reads a **filled** managed doc (or an addressed slice of one) back out of the store — committed by default, a task's staged working copy on `--task <id>` (M43, below). It is the read-path counterpart to the write verbs (`jigc doc set`/`add-item`/…) and the sibling of the two other read surfaces — [introspection.md](introspection.md) (`jigc describe`, the *menu* of what can be composed, deliberately excluding filled prose) and [validation.md](validation.md) (`jigc validate`, the *check*). Homed here (settled 2026-07-06, M39 Settle — [DECISIONS.md](../DECISIONS.md)) rather than folded into [write-commands.md](write-commands.md) (the write side) or [introspection.md](introspection.md) (which by charter excludes filled-prose reads), because the read-back of authored content is a distinct concern with a **1.0 stable machine contract** that neither of those docs owns.

Reads after the surfaces it consumes — the address grammar ([storage.md](storage.md) → Identity/addressing), the schema ([document-type-schema.md](document-type-schema.md)), and the byte-exact slice path ([storage.md](storage.md)) — alongside the other read-path/integration surfaces. Its conformance witness (the machine-consumed record whose shape pins the contract) is the **milestone record** ([team-ready-state.md](team-ready-state.md) → The read surface).

## What it reads — committed by default; the staged copy on `--task` (the M43 revision)

`jigc doc show` is **committed-by-default**: task-less, it resolves the cascade schema set + repo root exactly as `jigc validate` does and reads the **committed** store — the surface a fresh agent session (or a teammate on a clone) uses to see current authored state. *(Revised at M43. The M39/M40 record said committed-**only**, but its rationale — fresh-session semantics — motivates the **default**, not a prohibition, and three trials in a row demanded the staged read verbatim; [DECISIONS.md](../DECISIONS.md) → 2026-07-16 M43 Settle item 3.)*

**`--task <id>` serves that task's staged working copy** through the **identical** parse/slice/render path (the engine's source-selection extraction: one shared parse/slice tail, source selection the only difference between the arms — [store.rs](../crates/engine/src/store.rs) `read_slice_staged`), so an in-flight agent reads back its own staged write at any slice depth — whole-doc, `#section`, item, leaf — with the same plain/`--format json` split as the committed read. The task id is always **explicit**, never inferred: a task-less read is the committed read, full stop. A bad `--task` id routes to `jigc task list`, the shared wrong-id route.

- **The transient staged address** (the Settle-12 rider). A transient doctype (`commit:<task-id>` — sink = the git message, no committed home) was previously readable through **no** sanctioned surface. Its staged working copy is a real staged doc, and `jigc doc show commit:<task> --task <task>` reads it — the B9 staging-key leak closed from the read side. Task-less, a transient address still blocks `store.transient-type`, routed at the staged read.
- **An absent staged instance blocks `store.not-staged`, routed on the real state**: a committed sibling exists → the route names the task-less read (`jigc doc show <addr>`); nothing exists anywhere → nothing to read yet, create or author it in the task first.
- **The `store.not-found` route names the staged read** — `jigc doc show <addr> --task <task-id>` — superseding the M40 `jigc task diff` route (the working diff shows a *changeset*, not a doc at an address; it was the sanctioned read only because no real one existed).
- A read-side block (unknown type / not-found / not-staged / an unparseable doc / a `#fragment` naming nothing) routes through the same non-zero-exit + route envelope a write block uses, on **both** arms. The staged arm's `store.unparseable` route says *"fix the staged working copy…"* (the shared tail claiming a staged doc is committed would be a lie), and the read verb's foreign-adoption reroute (below, `jigc doc list`) never fires on the staged arm — a staged working copy is jigc-written by construction, never a foreign squatter.
- **The stale-read hint.** A task-less read of a doc that is **also staged in an open task** serves the committed copy unchanged and adds one advisory line on **stderr** — naming the open task id(s) + the staged-read command (`jigc doc show <addr> --task <id>`) — so the serve says it may be behind the staged working copy; stdout stays the canonical render / the pinned json, **byte-identical** with and without the open task (no second additive key rides the pin). Existence check only, over the single task enumeration source — never a content read, so the hint says *may be* stale, never *is*. **It is phrased for a reader who may *be* the staging task (M47).** A task-less read carries no task id, so the note cannot know whose task it names — and in the field the commonest stager is the reader's own open task, where the original *"the committed copy served here may be stale"* framing read as a third-party warning about someone else's edit. It therefore states which copy this read served, that **any** edits staged in the named task are not in it (hedged, because the check is existence-only), and hands over the staged read under an explicit ***if that task is yours*** clause — true whether the stager is the reader or a teammate, with the plural branch asking whether *one of them* is.

**The staged marker key.** A **staged whole-doc `--format json`** serve carries the **staged-only additive top-level key** — `"staged": "<task-id>"` — beside the pinned `{ type, slug, fields, sections }` (and the `item-count` / `schema-version` additive keys below, which ride *both* serves), so a driver can never mistake a staged read-back for committed state. A committed serve carries **no `staged` key, ever**: `staged` is the one key that distinguishes the two views. **Fragment slices carry no marker** — a slice is a bare value (a prose string, an item array/object, a leaf) with no object to hang the key on, and the driver that needs the discrimination on a slice read has it in the command it just composed (`--task` was explicit). A conscious bound, not an oversight.

## The slice grammar — whole-doc, `#section`, item, leaf

The `<ref>` is a doc address, optionally carrying a `#fragment` that names a sub-node. The read surface does **not** define a grammar of its own: it **conforms to** the one address grammar ([structural-grammar.md](structural-grammar.md) → Addressing), which permits every depth *uniformly* — `fragment := unit ( "/" leaf )?` in a non-repeatable unit, `unit "/" item ( "/" leaf )?` in a repeatable one — and leaves it to the **schema** to say which depths are valid for a given unit. The table below is that grammar's depths *as they resolve on the read path*, not a narrower dialect of it:

| Address | Resolves to |
|---|---|
| `type:slug` (whole-doc) | the whole document |
| `type:slug#section` | one section — a **slot** section's prose, a **repeatable** section's item array, or a **fields-only** (header) section's fields (M42 — below) |
| `type:slug#section/<leaf>` | one **leaf inside a non-repeatable section** — a field's value, a sub-labelled slot's prose (M42 — the grammar's `unit/leaf` depth) |
| `type:slug#section/<item>` | one repeatable **item** object |
| `type:slug#section/<item>/<leaf>` | one **leaf** — a slot's prose, a field's value, or the `id-from` leaf (the item's heading) |
| `type:slug#section/<id>/<block>/<gid>` | one **nested item** object (M40 — a nested repeatable's member) |
| `type:slug#section/<id>/<block>/<gid>/<leaf>` | one **nested leaf** (M40) |

**The M42 rows are a defect correction, not an extension of the contract.** Both depths were settled by the foundation doc and honoured everywhere *except here*. [structural-grammar.md](structural-grammar.md) → Addressing tabulates `type:slug#unit/leaf` as *"a named leaf inside a non-repeatable unit (a field, a sub-labelled slot)"*, states that *"the schema determines which depths are valid; the grammar permits every depth uniformly"*, and pins the rule for all of them — *"**one grammar, every reference** … write commands, **validation targets**, override ops, data-values."* The **write** path honours it (`jigc doc set-field 'adr:use-rust#status/status'` → exit 0). **`jigc validate` emits it**: `schema-conformance.required-field-present` ([validate.rs:1759-1768](../crates/engine/src/validate.rs)) and `field-value-conformant` ([validate.rs:1797-1806](../crates/engine/src/validate.rs)) both address `#<section>/<field>`. Only the **read** path violated it — `jigc doc show 'adr:use-rust#status/status'` answered `blocking · store.no-such-item`, exit 1 ([store.rs:290-298](../crates/engine/src/store.rs): the leaf branch is guarded on `rest.len() >= 2` **and** a `chain_repeatable` template, so a leaf was only ever resolved inside a *repeatable* — a one-hop leaf in a simple section matches neither branch and falls through to the item-miss block at [store.rs:321-329](../crates/engine/src/store.rs)). **The tool emitted an address its own read surface could not resolve.** Blast radius: the 11 header sections across 10 doctypes in both packs — including `milestone-record`, this contract's own conformance witness (above). The slice table is **the drifted artifact and is corrected**; the grammar is not renegotiated (M42 — [DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 planning: the Settle).

**A fields-only (header) section slice serves its fields (M42).** `jigc doc show 'adr:use-rust#status'` returned the **empty string at exit 0** — a header that genuinely carries `status`/`date`/`supersedes` answering "nothing here". That is precisely the **wrong-node-exit-0** this doc forbids by name (below: *honest error or correct answer, never wrong-node-exit-0*), and it is the same silent-wrong-answer class the wave exists to close. Settled: the slice **serves the section's fields** — `--format json` → the section's leaves keyed by leaf id (shaped exactly as the whole-doc `fields` project them), plain → those field lines as the writer renders them.

- **Physical consequence: this slice is a canonical re-emit, not a byte slice.** A `ParsedSection` carries **no `fields_span`** — the parser hoists a doc's fields into one flat map keyed by leaf id, with no per-section byte range — so the slice is rendered *from the parse*, in schema order. That is not a special case: the plain path is a canonical re-render throughout (below).
- **The fields do not move.** The whole-doc rule below — *"a header/fields-only simple section contributes to `fields` alone and has no `sections` entry"* — stands unchanged. A slice is a **projection of the addressed node**, not a relocation of it: the fields-only section still has no `sections` entry in the whole-doc shape *and* it answers at its own address. Same fields, two views, one grammar.

## Plain text vs. `--format json`

- **Plain text** (default / `--format agent` / `--format human`) is the **canonical markdown re-render of the addressed node** — the node in the shape the writer emits it, so a human or agent reads committed content in its committed form. The **whole-doc** read is the store's own bytes; a **slice** is re-rendered from the parse, and coincides with the stored bytes wherever the render is faithful to them (which, for a conformant store, is most of the time — the store is written through the same canonical writer).
- **`--format json`** is the **pinned 1.0 stable contract** below — a machine-legible projection of the parsed structure (a one-way door, pinned now rather than left to the first implementation).

The two are complementary: legibility-in-committed-shape is the plain path's job; the json path trades markdown for a clean, keyed, deserializable shape.

**Stdout carries the addressed content alone — a stated guarantee, not observed behaviour (M47).** A served read emits the addressed node on **stdout** and nothing else: no routing footer, no banner, no ack. Diagnostics, blocks, and the stale-read hint above ride **stderr**, and a *blocked* read carries the footer there with stdout empty — purity is a property of the served read, not of the verb. The behaviour has held since the surface shipped, but it was stated on no surface the agent is sanctioned to consult: a trial worker round-tripped a leaf through a shell file (`doc show <leaf> > f` → edit → `set-slot --from-file f`) and verified with `tail -c` that nothing rode along, because *"plain text is the canonical render"* implies the guarantee without stating it. `jigc doc show --help` now states it, and the emitted bytes are pinned across the slice depths (`crates/cli/tests/doc_show.rs`). One named bound: the whole-doc serve closes with the newline the stored bytes already end in — a doubled line terminator, which is neither a footer nor a banner.

**The rendered `{#id}` anchor is the item's address id, and the read surface says so (M47).** The anchor restored at M42 (above) *is* the `<id>` every `#section/<id>` slice and every item write verb takes — minted from the title, not always equal to it (a release titled `1.0.0` has the id `1-0-0`), and frozen across a retitle. Through rc.9 that connecting sentence lived only on **write-verb** long help (`add-item` / `retitle-item` / `remove-item`) — nowhere the reader who has just rendered an item heading stands — so two trial workers inferred the fact and one distrusted the inference. It is now stated on `jigc doc show --help`, beside the `id` key the json arm carries for the same value.

**The old claim — *"the byte-exact slice … the store's own bytes for that node, verbatim"* — was false, and is retired (M42).** It was already false before M42, in two ways the code itself documents. `render_item_at` ([store.rs:477-480](../crates/engine/src/store.rs)) is **anchorless by design** — it re-heads from `item.title` alone, dropping the `{#id}` anchor that carries the item's frozen identity. And a nested slice is **re-rooted**: `#releases/1-0-0/changes` renders `### added` where the source has `#### added`, because the render re-heads at `2 + depth` relative to the *slice*, not the document. M42 **restores the `{#id}` anchor on rendered item headings** (the identity an agent needs in order to address the item back — see the item `id` below), closing the first gap; the re-rooting is inherent to lifting a sub-tree out of its document and stays. Byte-exactness was never the property the plain path had, so it is not the property it promises: it promises the **canonical render of the node you addressed**.

## The pinned `--format json` contract (1.0)

Pinned once here; every doctype's json read conforms. The **milestone record is the conformance witness** — the first doctype whose *primary* consumer is a machine read (fresh-clone continuation), so its shape is the pin's proof.

**Whole-doc** → an object keyed by the four pinned top-level keys `{ type, slug, fields, sections }` (joined pre-1.0 by the additive `item-count` and `schema-version`, below):

```json
{ "type": <doctype>, "slug": <slug>, "item-count": <n>, "schema-version": <v>|null, "fields": { … }, "sections": { … } }
```

- **`type`** — the doctype id. **`slug`** — the addressed slug.
- **`fields`** — every *simple* section's leaves flattened, keyed by leaf id (the header front-matter + any body field group). A **scalar** field serializes as its string; a **list**-cardinality field as a json array of strings; an **enum** leaf as its **lowercase string** (the enum member is already its canonical lowercase form). The one **compound** field in the pinned surface is the milestone-record's `base` pin: it projects as a structured object `{ "sha": …, "short": … }` (clean lossless access to both SHAs; the committed `.md` stores the space-joined `<sha> <short>` scalar, so this is json-projection-only — [team-ready-state.md](team-ready-state.md) → The read surface, [DECISIONS.md](../DECISIONS.md) → 2026-07-07). Every other field stays a scalar.
- **`sections`** — one entry per **slot** section (its **trimmed prose string** — the clean machine value; leading/trailing whitespace stripped) and per **repeatable** section (its **item array**). A header/fields-only simple section contributes to `fields` alone and has no `sections` entry. An unfilled/absent slot is the empty string.
- **`item-count`** (additive, M44) — an integer: the doc's **total top-level repeatable item count**, summed across every repeatable section (a simple section contributes none; a **nested** item is a member of its enclosing item object and is *not* counted — a changelog with one release counts **1**, not the release's change-notes). It rides **every** whole-doc serve — committed **and** staged alike — so it never becomes the staged/committed differentiator (that stays `staged`, above). **A `#fragment` slice carries no `item-count`** — a slice is a bare value with no object to hang it on (the same bound the staged marker states).
- **`schema-version`** (additive, M49) — an integer or `null`: the **doc's own stamp**, the version the instance was authored against (`design/corpus-migration.md` → The schema-version stamp), as a json **number**. It is the same value `fields["schema-version"]` carries as a **string** — the `fields` map stays uniformly stringy, so the generic scalar projection's rule (*a scalar field serializes as its string*) holds for every key in it and a driver iterating that map is unaffected. It is **`null`** when the doctype carries no stamp field at all — the transient `commit`, which the pack loader's `location`/`placement`-gated injection skips — and equally when a stamp on disk is not an integer (only a hand edit produces that, and the `int` field-type check blocks it at validate); never a coerced `0`, and never an absent key, so a driver's read of it is total. It rides **every** whole-doc serve, committed and staged alike (`staged` stays the sole staged/committed differentiator), and **a `#fragment` slice carries none** — the same bound the two keys above state. Its purpose is the cross-surface comparison: see *One name, two json types*, below.

**A `#fragment` slice** returns the corresponding sub-node of the whole-doc shape:

- a **slot section** → its trimmed prose string;
- a **repeatable section** (`#section`) → its **item array**;
- a **fields-only section** (`#section`) → an object of its leaves, keyed by leaf id, each shaped as in `fields` (M42 — above);
- a **leaf in a non-repeatable section** (`#section/<leaf>`) → the leaf value, shaped as in `fields` (M42 — above);
- an **item** (`#section/<item>`) → its item object;
- a **leaf** (`#section/<item>/<leaf>`) → the leaf value (a slot's trimmed prose string, a field value shaped as in `fields`, or the block's `id-from` leaf → the item's heading string).

**An item object** carries its **`id`** — the item's minted, frozen id, the handle every address into the item takes (M42, below) — its `id-from` leaf keyed by the block's declared `id-from` → the item's heading (its stable id-source), each other field keyed by leaf id (scalar → string, list → array), and each slot keyed by leaf id → its trimmed prose.

**The item `id` closes the json contract under its own address grammar (M42).** Without it the contract is **not closed**: a driver can read an item array and address **none** of it. The id is *not* derivable from the heading — it is **minted once and frozen**, so a driver that re-slugs the title is guessing, and earns a `write.not-present` (an item-id miss at every write verb since M47 — [command-output-contract.md](command-output-contract.md) → The M47 correction) wherever the two have diverged: after a `jigc doc retitle-item` they diverge **permanently, by design** ([write-commands.md](write-commands.md) → `jigc doc retitle-item`; [storage.md](storage.md) → Identity); the mint-time word/char caps and a `-2` collision suffix diverge them at mint; and a **slug-rule generation** diverges them for a whole corpus (a release titled `1.0.0` carries the id `100` where it was minted before slug-rule-version 2, and `1-0-0` where it is minted today — [storage.md](storage.md) → Identity → *The slug rule is itself a versioned rule*). Before M42 the id lived only in the transient write-ack and in the raw markdown `{#id}` anchor, which every slice render stripped — so the one contract whose purpose is machine consumption withheld the one value a machine needs to write back. The **`id` key is reserved at schema load**: a pack declaring a leaf named `id` inside a repeatable block is rejected loudly at pack-load, so a future doctype cannot silently collide with the pinned key (no shipped doctype declares one, and none uses `id-from: id`).

**Nested repeatables join the pin (M40 — supersedes the M39 exclusion).** Nested `Leaf::Repeatable` groups (the M22 changelog nested shape) **join the pinned item object**: each nested repeatable keys the item object by its declared block id → an **array of recursive item objects** — e.g. a changelog release item: `{"title":"1.0.0","date":"…","changes":[{"category":"added","notes":"…"}]}`. The **section-qualified write address is accepted on show**: `#releases/<id>/changes` → the nested array, `…/changes/<gid>` → the nested item object, `…/<gid>/<leaf>` → the leaf. Two undeclared defects die with the pin: the false `store.no-such-item` on the canonical write address, and the segment-less **wrong-node degrade** (a deeper path silently returning the enclosing item, exit 0) — the rule is *honest error or correct answer, never wrong-node-exit-0*. The **plain** (markdown) item/section slice likewise carries the item's fields + nested content (a defect recorded at the M40 Settle and fixed in the rc.4 wave — before it, fields + nested groups were dropped and only the whole-doc plain read was complete; [DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 Settle). What that fix did *not* buy is byte-exactness, which the plain path never had — see the retired claim above.

**The leaf slice resolves against the *declaring template*, never the item's sole span (M47).** The read-side statement of the same rule the write side now holds on every face — *resolve the addressed leaf against the declaring template before answering* ([write-commands.md](write-commands.md) → Every write resolves its address before it moves bytes). `engine::store::resolve_leaf` and its CLI json twin `leaf_json` both gate the slot span on the template's own declaration, so an undeclared leaf **blocks** — `store.no-such-leaf`, routed, on **both** surfaces (plain and `--format json`) — and no read ever hands back a neighbour's prose: *honest error or correct answer, never wrong-node-exit-0*, one hop deeper than the rule above. **The read side was already right where the write side was not; what it lacked was a witness** — no **dev-pack** repeatable declares two slots, so the discriminating case had never been exercised on the corpus this contract was written against. M47 pins it against a **synthetic two-slot fixture pack** (`crates/cli/tests/doc_show_item_leaf.rs`) in both item states — mint-empty, where a leaf-blind resolver would hand back the whole item body, and filled, where each leaf must resolve to *its own* prose — rather than re-declaring the bound ([DECISIONS.md](../DECISIONS.md) → 2026-08-04 M47 Inc 6 T5). **The bound as first written here dropped the *dev-pack* qualifier the fixture's own doc-comment carries, and the generalization was false the day it landed:** `roadmap.milestones` (`proves` + `decomposition`) is a shipped multi-slot repeatable, and since M16 the only one in either pack. What that sentence cost was not this read side, which was already correct, but the **write** side sharing the same seam — an item's leaf region ended at the first *deeper* heading while a slot sub-label **is** one — believed unreachable because no corpus was thought to carry the shape, and left unswept until M49 Increment 1 keyed the boundary on the schema ([DECISIONS.md](../DECISIONS.md) → 2026-08-28 M49 Settle → D3).

**Evolution posture (declared — previously undeclared).** Additive keys are permitted **pre-1.0 only**; from the 1.0 pin, the shape evolves only by an **explicitly versioned extension** — never a silent additive key. Two additive keys land in the rc.4 wave under the pre-1.0 rule: the milestone-record's `fields` gains `schema-version` (the methodology stamp — [corpus-migration.md](corpus-migration.md) → The freeze-exempt sibling), and nested repeatable groups join the item object (above). The rc.6 wave (M42) lands the item **`id`** under the same rule — and the one that makes the contract closed under its own address grammar (above). The rc.7 wave (M43) lands the **staged marker key** inside the closing window — `staged` on a **staged** whole-doc serve only (above), so the committed shape the pin governs is untouched: the key rides the new `--task` read arm, never the committed read. The rc.8 wave (M44) lands the **`item-count`** key under the same rule — on **every** whole-doc serve (committed *and* staged) and on each `doc list` row (above); unlike `staged` it *does* touch the committed whole-doc shape, which is precisely what the pre-1.0 additive window permits. It carries **no version integer** — `doc show`/`doc list` have none of their own (the `contract-version` is `doc schema`'s), so this is an additive key, not a contract-version bump. The rc.6 wave's other read-path changes are **not** additions and do not spend the window: the `#unit/leaf` and fields-only slices are *defect corrections* against the foundation grammar, and the retirement of the byte-exactness claim corrects prose against behaviour that never matched it.

**The window closes here — the discharge (M48, the rc.11 wave).** The paragraph above has been an **open ledger** since rc.4, adding a wave's keys each time and never saying when it ends. It ends at the **1.0 pin**: *M48 is the last pre-1.0 wave* was its premise here too, and is **withdrawn** — M46, the combined pre-1.0 wave, follows it, so the close is keyed to the pin rather than to a wave name (the form a spend must take until then is homed once, on the write side). From that pin every one of the three read contracts evolves solely by an **explicitly versioned extension** — an absent key is a decision, not an oversight. **These three read contracts spend nothing at M46**; that wave's one additive key is on the write side. What M48 spends it on, on this side, is **not** an additive key at all: `doc schema`'s id-source entries gain **`write-key`** — the payload key the field's value is actually written under — landed as a **`contract-version` 4→5 bump** ([DECISIONS.md](../DECISIONS.md) → 2026-08-13 M48 Increment 7 T1), which is the successor regime exercised one wave before it becomes the only option. `doc show`'s and `doc list`'s pinned shapes are untouched by this wave. And the rule stops being only a statement: the standing parity fence (`crates/cli/tests/text_json_parity_axis.rs`) bijects the clap leaf-verb tree, classifies every verb that speaks `--format json`, and carries each of these three read surfaces with its census disposition — *governed by its own versioned contract, so the parity rule does not run over it* — so a value printed but withheld reddens a suite instead of shipping. The write/compose side's identical discharge, and the keys it spent the window on, are homed in [command-output-contract.md](command-output-contract.md) → Evolution posture.

**The last spend before the pin (M49, the surface-completion wave).** The window is still open — it closes at the **1.0 pin**, not at a wave name — and M49 spends it once on this side: `doc show`'s whole-doc serve gains the top-level **`schema-version`** number (above), on **every** whole-doc serve, committed and staged alike, and on no fragment slice. It is an **additive key**, so the pre-1.0 rule covers it exactly, and it is spent **now on purpose**: after the pin the same repair costs a minted versioned extension, and what it repairs — *one name, two json types* (below) — is a defect a driver hits on its first automated upgrade check. **No version integer moves anywhere for it**: `doc show` has none of its own, `doc schema` already emits the number this key compares against and is therefore the surface that does *not* change, and `doc list` is refused the key outright with its reason stated (below). This is the third read contract's last additive key; from the pin, an absent key is a decision.

## Why json is a contract here (and describe's is the opposite)

`jigc describe`'s output is deliberately **non-contractual** — format-hostile to parsing so nothing depends on it ([introspection.md](introspection.md) → Non-contractual by design). `jigc doc show --format json` is the deliberate inverse: its whole purpose is machine consumption (fresh-clone continuation re-derives milestone state from it), so it **is** a stable contract, pinned at 1.0. The two read surfaces sit on opposite sides of the same axis on purpose: describe is a menu you orient by, `doc show` is content you compute over. **A third surface joins at M40**: `jigc doc schema <doctype> --format json` — the structural projection that *cannot* ride describe (its format predicate forbids parseable structure) — ships as a **separately-pinned, explicitly versioned contract**, pinned here:

```json
{ "contract-version": 5, "type": <doctype>, "schema-version": <the doctype's stamped version, else null>,
  "fields":   [ { "id", "type", "of"?, "required", "author-required", "default"?, "set"?, "section"?,
                  "set-field"? }, … ],
  "sections": [ { "id", "kind": "slot"|"repeatable", "optional"?, "set-slot"?|"add-item"?,
                  "item": { "fields": [ { …, "set-field"? | ( "add-item"? + "retitle-item"? + "write-key" ) }, … ],
                            "slots": [ { "id", "optional"?, "set-slot" }, … ],
                            "nested": [ { "id", "add-item", "item" }, … ] } }, … ] }
```

— the `item` object is **recursive** for nested repeatables (`nested` carries the inner blocks); a field's `of` carries an `enum`'s legal members (universal across depths — an agent reads the legal values from the contract, no failed-write probe), and `section` names the owning simple-section id (**top-level fields only** — an item field carries its section structurally, under `sections[].item`). **Every settable entry names its owning write verb by carrying its concrete address under that verb's key** (M43 rc.7): a field's `set-field`, a slot section's / item slot's `set-slot`, a repeatable's / nested block's `add-item`, and — on an **item** field only — the `id-from` pair below, an `id-from` leaf living inside a repeatable block by definition and never among the top-level `fields` — instance parts **placeheld** (`<slug>` for the doc, `<id>` for each enclosing item's minted id at that depth; the real values come from `doc list` / `doc show`'s item `id` key — the projection stays type-level, e.g. adr `status` → `adr:<slug>#status/status`). The key is **absent** where the entry is settable under **no** write verb — a `set:`-derived (CLI-stamped) field, whose value the CLI owns — absence meaning *not settable*, never an error. `contract-version` bumps on any structural change to this projection — **no additive carve-out** (the M41 rc.5 addition of the `of`/`section` keys bumped it **1→2**; the M43 rc.7 addition of the write-address keys bumped it **2→3**; the M45 settability states **3→4**; the M48 id-source `write-key` **4→5**) — the *values* track the schemas as they evolve, the *keys/structure* are the pin; golden-pinned at ship ([introspection.md](introspection.md)).

**Three settability states, because two of them collapsed a required field into silence (M45).** Through rc.8 the projection had exactly two states — an address under a write verb's key, or nothing — and *nothing* carried two different facts at once. Verified at rc.8: every `id-from` leaf projects as `required: true, author-required: true` with **no address and no marker**, at **11 sites across 9 doctypes**, and the string `retitle-item` appears **nowhere** in the projection. So the pinned contract told an agent that a required, author-supplied field exists and named no way to write it — law 2's *nothing hides*, violated by the surface that produces the state ([surface-contract.md](surface-contract.md)).

*The record is revised on its rationale, not merely appended to.* The retired clause — *"absence meaning not directly settable, never an error"* — was **right** that an `id-from` leaf is genuinely not `set-field`-settable: the heading *is* the value, and the write-time guard (`write.id-from-field`) refuses it correctly. What it got wrong is that *not settable by `set-field`* and *not settable at all* are different facts, and that the designated recovery must be **named by the surface producing the state** rather than inferred by the reader. The projection therefore says which of three states an entry is in, reusing the existing rule verbatim — *the concrete address under its owning write verb's key* — and minting no new key kind:

| State | How the projection says it | Example |
|---|---|---|
| **directly settable** | the address under its owning direct-set verb — `set-field` / `set-slot` / `add-item` | adr `status` → `set-field: adr:<slug>#status/status` |
| **settable under a different verb** (the id-source) | the address under **that** verb's key: the leaf is supplied at mint by `add-item --title` and changed afterwards by `retitle-item`, so it carries both — `add-item` at the block's address, `retitle-item` at the **item** address — plus `write-key`, the payload key both take (below) | changelog `releases` `title` → `add-item: changelog:<slug>#releases` + `retitle-item: changelog:<slug>#releases/<id>` + `write-key: --title` |
| **directly settable, CLI-defaulted** (an author-overridable stamp) | the address under `set-field` — the CLI *defaults* the value at mint but an author may overwrite it | changelog `releases` `date` → `set-field: changelog:<slug>#releases/<id>/date` (`set: on-create`) |
| **not settable** (a machine-maintained absolute) | **no verb key at all** | adr `schema-version` (`set: schema-version`), milestone-record `base` (`set: on-transition`) |

Two precisions the shape has to carry, because getting either wrong ships a law-1 lie in the surface built to end one:

- **`retitle-item`'s address is the *item*, one hop shallower than the leaf's own** (`<type>:<slug>#<section>/<id>`, or the nested section-qualified chain — [write-commands.md](write-commands.md) → `jigc doc retitle-item`). Projecting the leaf address under that key would advertise an address the verb rejects — and would redden the M45 address-grammar round-trip on the very entry the state exists to fix.
- **An `enum` `id-from` leaf carries no `retitle-item` key at all.** `retitle-item` refuses it **unconditionally** — a member change is an identity change (M40, the enum-id-from refusal) — so its only write is `add-item` at mint, and its repair is remove + re-add. Advertising `retitle-item` there would be exactly the *route naming a verb that hard-errors* that [validation.md](validation.md)'s two-tier route was written to stop.

**The extra states are a precondition, not an ornament.** M45 also ships the projection↔write-path **parity assertion** — *advertised-set == accepted-set* from one shared predicate rather than two duplicated ones ([pinning.md](../implementation/pinning.md) → §2). Under a two-state projection those two deliverables contradict each other: advertise the `id-from` leaf under `set-field` and parity reddens (the write path refuses it, correctly); advertise nothing and law 2 stays violated. So the parity predicate keys on **which verb** an entry is advertised under, and the states are what make that keying possible — an entry advertised under `retitle-item` is neither *accepted by `set-field`* nor *hidden*.

**The `set:` kinds are not one state — the split is load-bearing (M45 Inc 3).** A `set:` derivation says the CLI *supplies* the value; it does **not** uniformly say the author may never write it, and reading it that way ships the freeze-stamp hole's mirror image — a false *"not settable"* over a leaf a shipped flow must write. Two kinds, two states: **`set: on-create` is an author-overridable stamp** — the CLI defaults it at mint (`today_iso()`), but the changelog-migration path *depends* on overwriting it with the foreign file's historical date ([auto-migration.md](auto-migration.md) → no false history; the acceptance is `flow25_migrate_changelog.rs`), so it is **directly settable** and the projection advertises `set-field` for its four leaves (adr/idea/research `date`, changelog `releases/<id>/date`). **`set: schema-version` and `set: on-transition` are machine-maintained absolutes** — the freeze stamp and the milestone base — which the write path refuses (the freeze-stamp hole M45 Inc 3 closes) and the projection leaves unadvertised. The shared settability predicate keys on the `set:` *kind*, not on the presence of `set:`. One doctype-level caveat the parity assertion must carry: `milestone-record` is machine-maintained **whole** (`machine_maintained_guard` refuses *every* `doc` write to it, [write-commands.md](write-commands.md)), so its `set: on-create`-adjacent leaves stay unadvertised by a **doctype** exclusion, not the per-leaf `set:`-kind rule — else parity reddens against `write.machine-maintained`. (Verified at rc.8: a `set:`-derived field already announces its kind — it carries its own `set` key, e.g. `"set": "on-create"` vs `"set": "schema-version"` — so the projection reads the kind directly. State 2, the id-source, is the one that carries **nothing at all**, distinguishable today only by `author-required: true` — a coincidence of two unrelated predicates, not a declaration, and pinned by nothing.)

**The id-source names its write key, because the address says which verb and the field id answers which key — wrongly (M48).** The three states above settled *which verb* writes each leaf. On the id-source that left one hop unstated: `add-item`/`retitle-item` take the value under a **flag**, and the projection's own field id is the misleading candidate. A `changelog` change-group projects `category: enum […] (add-item: changelog:<slug>#unreleased-changes)` and both verbs take **`--title`** — *"always literally `--title`, whatever the doctype's `id-from` field is called; the flag names the role, not the field"* ([write-commands.md](write-commands.md) → The argument convention). A pre-1.0 trial worker wrote a payload from that projection, was rejected with `unknown field 'category'`, and found the working spelling by trial: the capability was present and correct, and **no surface named its key** — law 2's *nothing hides* on the one read surface an agent is *told* to consult ([surface-contract.md](surface-contract.md)). Settled: an id-source entry carries **`write-key`**, the payload key its value is supplied under, beside the addresses that say which verb takes it. Three precisions:

- **It rides the id-source state alone**, and the omission is the point. A `set-field` entry's payload is that verb's **`--value` / `--unset`** pair and a slot's is **`--from-file <path|->`** — neither is *one* key, so naming one would understate the verb rather than teach it — and neither is shadowed by a field id, which is the whole failure mode here. A key that lands on every entry marks nothing.
- **It is derived from the `add-item` address, not passed beside it**, so the key and the state it belongs to cannot drift apart — and a **suppressed** leaf (the machine-maintained-whole `milestone-record`, advertised under no verb) names no key either: the doctype exclusion keeps winning.
- **The plain listing mirrors it in the json's own key spelling** — `(write-key: --title)` — like every other address it mirrors: the non-contractual arm teaches the pinned arm's vocabulary rather than inventing a second one (the M47 `doc list` header rule).

**`contract-version` 3 → 4, once, for the whole wave.** This projection bumps on **any** structural change with **no additive carve-out** (above), so *every* M45 change to it lands in **one** bump and therefore in **one** increment ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle). Splitting them across two increments would spend two version numbers on one wave's worth of change and hand a driver two contracts to track where the shape changed once.

**`doc schema`'s plain listing legends its `*` where the markers land, and only when one lands (M47).** The `*` marking an author-required leaf is appended at **every** depth — top-level fields *and* item leaves under `sections:` — but its legend rode the `fields (…)` header, which was wrong on both faces. It sat away from most of its markers (`spec`'s only `*` is on `criteria/<id>`'s title, two levels below a header that carries none), and four shipped doctypes — `adr`, `research`, `vision`, `milestone-record` — have fields with **no** author-required leaf anywhere, so the header announced a convention their listing never used. The legend is now a **listing-level line** between the `doctype:` line and the body, printed **iff a marker actually renders**, and the predicate is read off the *rendered body* rather than recomputed from the contract — a second walk could drift from what the reader sees. This is non-contractual presentation (the `--format json` shape is the pin, and it is untouched: `author-required` has always been a per-field boolean there), so it costs no `contract-version` bump; it is compose-golden-pinned, like every other printed surface.

## `jigc doc list` — the fourth read surface (M42)

`jigc doc show` answers *"what does this doc say"* — and presupposes you already know the doc exists. Nothing answered *"which docs exist"*. `jigc describe` projects **doctypes and workflows, zero instances**, and its format predicate actively *forbids* parseable structure ([introspection.md](introspection.md) → Non-contractual by design), so it cannot grow into an index. `jigc ingest --format json` enumerates *git candidates by path*, not the managed corpus by identity — and it mutates. So an agent's only route to the corpus was to guess a slug or read the filesystem directly, which is exactly the raw-file read the adapter rule forbids ([assistant-adapter.md](assistant-adapter.md)).

`jigc doc list [<doctype>]` projects the **committed store surface by identity**: the instances of one doctype (or of every persisted doctype), slug-sorted, each carrying its identity `<type>:<slug>`, its path, and its **registration state** (below). **Its substrate already exists** — `engine::index::committed_instances` ([index.rs:718-752](../crates/engine/src/index.rs)) returns exactly those slug-sorted `(identity, path)` pairs and **already handles both the placement branch and the located branch** ([storage.md](storage.md) → Placement); it is `pub(crate)` and no verb exposes it. **This is the same placement-aware enumerator the store-scope schema-conformance family needs** in order to stop skipping placement doctypes — the M42 false-green fix ([validation.md](validation.md); [corpus-migration.md](corpus-migration.md) → The freeze-exempt sibling). **One primitive, two consumers**: promote it once and both read the same enumeration, or it gets written twice and the second copy drifts — the failure mode the M38 placement census has already produced twice ([storage.md](storage.md) → Placement).

**It lists the store *surface*, and flags what is not adopted — because "one primitive, two consumers" inherits the foreign-squatter problem, and listing only the managed would hide it.** `committed_instances` yields a **placement** doctype's instance on **mere file existence** ([index.rs:724-731](../crates/engine/src/index.rs) — `path.exists()`, no registration test). So in a stock brownfield repo carrying an ordinary Keep-a-Changelog `CHANGELOG.md`, a naive `doc list` would report `changelog:changelog` as a **managed doc** — while `jigc doc show changelog:changelog` blocks `store.unparseable` and (post-M42) `jigc validate` correctly calls the same file **foreign, adopt it**. Three surfaces, three stories about one file, in the wave whose whole claim is that *the tool's own routes tell the truth*. Settled:

- **The discriminator is the committed `schema-version` stamp**, not the `.jigc` file-state record — the record is a gitignored, rebuildable cache and is empty on a fresh clone, so it cannot adjudicate what a teammate sees. The discriminator and its three-way route (**managed-current** / **managed-stale → `migrate-corpus`** / **never-adopted → `ingest` · `jigc migrate <path> --as`**) are [validation.md](validation.md)'s — owned there, not restated here. `doc list` **reads that same discriminator**; it never grows a second one.
- **A row is emitted for every instance the enumerator yields, carrying its state** — `managed` (stamped) or `unregistered` (no stamp: a foreign file squatting at a canonical home, or a never-ingested doc). **Each row also carries the additive `item-count` key** (M44) — the same top-level repeatable item count the whole-doc serve projects, computed by parsing the instance (`doc list` did not parse instances before this — the count is a new parse). It is **best-effort**: an instance that does not parse against its current schema — an `unregistered` foreign file, or a stale-shape managed doc — counts **0** (never a block: `doc list` is a report, and `state` already tells the agent the file is not adopted). **Not** managed-only: `doc list` is the agent's *only* sanctioned route to the corpus (the adapter rule forbids reading the store directly — [assistant-adapter.md](assistant-adapter.md)), so a listing that **omits** the very file jigc is telling the agent to adopt sends it straight to `cat`. Surfacing the file *and* its state is the honest answer and the useful one; the state is the projection of a fact the store already carries, not a new judgement.
- **`doc show`'s block on an unregistered instance routes to adoption**, not to hand-repair. Today it emits `store.unparseable` routed *"fix the committed file so it conforms to its schema"* ([store.rs:186-192](../crates/engine/src/store.rs)) — true of a *corrupted managed* doc, a lie about a *never-adopted foreign* one, whose repair is `jigc migrate`/`ingest`. The route splits on the same stamp discriminator. With that, the three surfaces tell **one** story: `doc list` says *unregistered*, `doc show` says *adopt it*, `validate` says *foreign — adopt it*.
- **Flow 43 must prove it**, on the archetypal case: a stock brownfield repo with a foreign root `CHANGELOG.md` + `jigc setup` → `doc list` flags it `unregistered`, `doc show` routes to adoption, `validate` routes to adoption, and after the adoption all three flip to `managed` together ([worked-examples.md](worked-examples.md) → flow 43).

**The plain arm names its columns (M47).** The human/agent listing printed three bare space-separated columns, leaving the reader to infer what the third one meant — `managed`/`unregistered` reads as a *state* only once something says `state`. It now leads with a header naming the columns in **row order**, in the **pinned json's own key spelling** (`id  path  state`), so the plain arm teaches the machine arm's vocabulary rather than inventing a second one. The header is **row-gated**: it prints where rows do, never above the empty-set line (a header over nothing names nothing), and never on `--format json`, whose keys *are* the shape. The plain listing stays non-contractual presentation — only the json shape is the pin.

**`--task <id>` lists what a task stages — the index read learns that a task has a surface too (M48).** `jigc doc show` gained the staged arm at M43; the *index* read did not, so nothing answered *"which docs does my task hold"* and the only way to find out was the raw filesystem read the adapter rule forbids. The pre-1.0 trial made that gap countable rather than described — all three blind sessions went to the filesystem to read their own in-flight work — so `doc list` takes the same arm, on the same terms as its sibling: the task id is **always explicit** (a task-less listing is the committed listing, full stop), a bad id gets the shared `jigc task list` route, and the doctype positional narrows the staged surface exactly as it narrows the committed one. It is **staged-only** — a committed doc the task has not copied in is *not* in it — the same non-merging the staged content read makes (`read_slice_staged` blocks rather than falling back); a doc the task *has* copied in is listed once, from the staged surface.

**The `--task` arm adds no key, and settles three row facts by reusing shipped rules.** **`state` is `managed` on every staged row** — a staged working copy is jigc-written by construction, never a foreign squatter, which is the same reason the staged content read runs no adoption reroute; the managed-vs-foreign discriminator adjudicates the *committed* store and is not consulted here. **`path` is where the instance promotes to at finalize** — the M43 A14 staged display rule, so that a printed path is repo-real or a typed identity and never the `docs/<type>:<slug>.md` working-area fiction; a **transient** doctype (`commit:<task-id>`, sink = the git message) and a type the resolved cascade no longer defines have no committed home, so they list at their `<type>:<slug>` identity — law 1's second legal form ([surface-contract.md](surface-contract.md)). *The consequence is recorded rather than hidden: on such a row `path` repeats `id`, and a driver reading `path` as a filesystem path must key on the doctype having a committed home — which the committed arm can never produce, because its enumerator yields no transient instance.* **`item-count` is the same best-effort parse** the committed arm makes. No `provenance`-style key joins here: nothing on this path computes one, and a key for a value nothing computes is not the withheld-value gap the pre-1.0 parity sweep exists to close.

**A task-less listing routes at the staged one — the `stale_read_hint` mold on the index read.** When an open task stages docs, the committed listing says which surface it just served and hands over the staged listing, on **stderr**: stdout — the pinned json *and* the plain listing, empty-set line included — is **byte-identical** with and without an open task, so no second key and no second line reaches the pin. It is an **existence check only** (the single task enumeration source ∩ the staged-doc enumerator), never a content read, so it claims only that the task stages *something*. Two properties it inherits deliberately: the **reader's scope survives into the route** (a `doc list <doctype>` routes at the same doctype's staged listing, never a wider one), and the sentence is **phrased for a reader who may *be* the staging task** (the M47 D5 revision applied to its sibling — a task-less listing carries no task id, so it says *if that task is yours* rather than warning about someone else's edit; with more than one staging task the ids are listed and the command carries the shared `<task-id>` placeholder). The **empty** committed listing routes too, and that is the case the finding is sharpest in: a store with nothing committed yet, while the reader's own task holds every doc they have written.

**Its posture is declared as it ships.** The M41 lesson is that an *undeclared* output calcifies into a *de-facto* contract with no evolution rule — **the one-way door is the posture, not the field count** ([command-output-contract.md](command-output-contract.md) → Why this is a contract). A fourth read surface shipping undeclared one wave before the 1.0 pin would re-open exactly that door. `jigc doc list` is an **index/identity projection, not a content read**: it projects the identities, paths, and registration state the store already carries, never authored prose. It therefore rides **`doc show`'s posture, not `doc schema`'s** — one pinned shape, additive keys permitted **pre-1.0 only**, **no in-band version integer** (a per-call version stamp on a listing is noise on every call), evolving after the pin solely by an explicitly versioned extension. Golden-pinned at ship, like its siblings.

**The read-surface axis, with four members.** The three read surfaces sit on one axis: `jigc describe` is a **non-contractual menu**, `jigc doc show` a **contract-pinned content read**, `jigc doc schema` a **separately-versioned schema read**. `jigc doc list` joins as the **contract-pinned index read** — it answers *which docs the store surface holds, and which of them are managed* (identity, not content, not schema, not menu), and it is the surface `doc show` has silently presupposed since M39.

## The version/posture map — five regimes, named in one place

Five independently-governed version/posture regimes ride jigc's machine surfaces, and until M42 no document named them together — two of them were named in **no** document at all. The map is homed here, on the read side that owns three of the five; [command-output-contract.md](command-output-contract.md) links it rather than restating it.

| Surface | In-band version | Posture |
|---|---|---|
| `jigc doc show --format json` (above) | **none** — no version key, and no version constant exists in the code (the top-level `schema-version` M49 adds is the **document's** stamp, not this contract's version — a fourth integer on the axis below, and the reason the row still reads *none*) | pinned shape; additive keys **pre-1.0 only**, then a versioned extension |
| `jigc doc list --format json` (M42, above) | **none** — by declaration, above | the `doc show` posture |
| `jigc doc schema --format json` (above) | **`contract-version`**, **3** at rc.8 → **4** at the M45 settability-state change → **5** at the M48 id-source `write-key` (both above) | bumps on **any** structural change — **no additive carve-out** |
| The command-output contract — composed output, write-acks, findings ([command-output-contract.md](command-output-contract.md)) | **none** — by declaration | the `doc show` posture |
| The **result contract** — `engine::result::SCHEMA_VERSION`, currently **3** (**2** → **3** at M50 Increment 5, for `jigc describe`'s per-definition `origin_pack` — [introspection.md](introspection.md) → the attribution; [result.rs:19](../crates/engine/src/result.rs)) | **`schema_version`**, a top-level key on every result envelope (orientation, `describe`, the validation report, the block/error envelope — **and the probe wire**, whose request and response stamp the *same* constant, `probe.rs:40`; a bump therefore moves what the engine writes to a probe's stdin and what the shipped `doc-code` probe writes back, while [validation.md](validation.md) → The wire contract leaves the probe *versioning policy* deferred, so no consumer compares the integer) | bumped only when a public result type's json projection changes in a way an external consumer must notice |
| `jigc describe` (prose) | n/a | **explicitly non-contractual** ([introspection.md](introspection.md) → Non-contractual by design) |

The **result contract's `schema_version`** is the one named here for the first time: it has ridden every block/error envelope and every orientation since the engine's first result type and appeared in **neither** governing doc — a version integer nobody owned. It is a *third*, orthogonal integer: it versions the **envelope**, where `doc schema`'s `contract-version` versions the **schema projection** and a doctype's `schema-version` versions the **document shape**. The document-shape integer has **two readings, not one** — the doctype's *expected* version and an instance's *actual* stamp — and since M49 a driver reads both as numbers, one per surface (below).

**One name, two json types — repaired additively (M49; recorded, not repaired, M42).** A doctype's **schema-version** surfaces on two pinned contracts, and the two integers are different *things*: `jigc doc schema` emits `"schema-version": 2` — the **expected** version read from the freeze manifest (`SchemaContract::schema_version: Option<u32>`) — while a doc carries its **actual** stamp. Comparing the two is exactly the upgrade-path check a driver automates (*is this doc's stamp behind its schema?*). Until M49 that comparison needed a **cast**: `jigc doc show`'s only stamp was `fields["schema-version"]`, the **string** `"2"`, projected like every other scalar field (`show_json` → `header_field_json` → `field_json`'s `Value::Scalar(s) => Value::String(s)`). *(Cite corrected, M42: the M42 pass cited `schema.rs:585` — which is the `SCHEMA_VERSION_FIELD` **const**, not a projection site. The claim was right and re-verified live; the coordinates were not — exactly the class that wave said it was eliminating.)*

M42 **recorded** the asymmetry rather than papering it, on the ground that unifying the type is a **breaking** change to one of two pinned contracts, and that a fix wave does not get to make that call by accident. That reasoning stands and is what settles the shape of the repair — the type is **not** unified. Two candidate repairs were refused: typing the `fields` entry breaks the map's own stated universal (*a scalar field serializes as its string*) and every driver iterating it; bumping `doc schema` has no basis, since `doc schema` already emits a number and is the surface that does **not** change. **What M49 lands instead is purely additive**: `doc show` gains a **top-level `schema-version` number** beside `type` / `slug` / `item-count` (above), carrying the doc's actual stamp. The driver's comparison is cast-free, `fields` is untouched and still uniformly stringy, the expected-vs-actual distinction the M42 record insists must survive is carried by *which surface* each integer sits on, and **no `contract-version` moves on either side**. Decided deliberately, in the wave that spends it (`completions/artifacts/M49/settle-record.md` → D8), which is what `:177` asked for.

**`doc list` rows are refused the key, explicitly.** A listing row does not carry the same gap: it carries **no** stamp in any type, so adding one is a **new fact** on that contract, not the repair of a two-typed one. The comparison this key exists for is **per-doc** and `doc show` answers it; a `doc list` row's declared job is identity, path and registration **state** (above), and a version integer per row is the sort of key the rc.4 parity sweep calls a value nothing on that path computes. Refused, not overlooked — an absent key is a decision.
