# The doc read surface — `jigc doc show` + the pinned `--format json` contract

**M39 design of record.** Where the *committed-doc read* is pinned. `jigc doc show <ref>` is the one verb that reads a **filled** managed doc (or an addressed slice of one) back out of the store — committed by default, a task's staged working copy on `--task <id>` (M43, below). It is the read-path counterpart to the write verbs (`jigc doc set`/`add-item`/…) and the sibling of the two other read surfaces — [introspection.md](introspection.md) (`jigc describe`, the *menu* of what can be composed, deliberately excluding filled prose) and [validation.md](validation.md) (`jigc validate`, the *check*). Homed here (settled 2026-07-06, M39 Settle — [DECISIONS.md](../DECISIONS.md)) rather than folded into [write-commands.md](write-commands.md) (the write side) or [introspection.md](introspection.md) (which by charter excludes filled-prose reads), because the read-back of authored content is a distinct concern with a **1.0 stable machine contract** that neither of those docs owns.

Reads after the surfaces it consumes — the address grammar ([storage.md](storage.md) → Identity/addressing), the schema ([document-type-schema.md](document-type-schema.md)), and the byte-exact slice path ([storage.md](storage.md)) — alongside the other read-path/integration surfaces. Its conformance witness (the machine-consumed record whose shape pins the contract) is the **milestone record** ([team-ready-state.md](team-ready-state.md) → The read surface).

## What it reads — committed by default; the staged copy on `--task` (the M43 revision)

`jigc doc show` is **committed-by-default**: task-less, it resolves the cascade schema set + repo root exactly as `jigc validate` does and reads the **committed** store — the surface a fresh agent session (or a teammate on a clone) uses to see current authored state. *(Revised at M43. The M39/M40 record said committed-**only**, but its rationale — fresh-session semantics — motivates the **default**, not a prohibition, and three trials in a row demanded the staged read verbatim; [DECISIONS.md](../DECISIONS.md) → 2026-07-16 M43 Settle item 3.)*

**`--task <id>` serves that task's staged working copy** through the **identical** parse/slice/render path (the engine's source-selection extraction: one shared parse/slice tail, source selection the only difference between the arms — [store.rs](../crates/engine/src/store.rs) `read_slice_staged`), so an in-flight agent reads back its own staged write at any slice depth — whole-doc, `#section`, item, leaf — with the same plain/`--format json` split as the committed read. The task id is always **explicit**, never inferred: a task-less read is the committed read, full stop. A bad `--task` id routes to `jigc task list`, the shared wrong-id route.

- **The transient staged address** (the Settle-12 rider). A transient doctype (`commit:<task-id>` — sink = the git message, no committed home) was previously readable through **no** sanctioned surface. Its staged working copy is a real staged doc, and `jigc doc show commit:<task> --task <task>` reads it — the B9 staging-key leak closed from the read side. Task-less, a transient address still blocks `store.transient-type`, routed at the staged read.
- **An absent staged instance blocks `store.not-staged`, routed on the real state**: a committed sibling exists → the route names the task-less read (`jigc doc show <addr>`); nothing exists anywhere → nothing to read yet, create or author it in the task first.
- **The `store.not-found` route names the staged read** — `jigc doc show <addr> --task <task-id>` — superseding the M40 `jigc task diff` route (the working diff shows a *changeset*, not a doc at an address; it was the sanctioned read only because no real one existed).
- A read-side block (unknown type / not-found / not-staged / an unparseable doc / a `#fragment` naming nothing) routes through the same non-zero-exit + route envelope a write block uses, on **both** arms. The staged arm's `store.unparseable` route says *"fix the staged working copy…"* (the shared tail claiming a staged doc is committed would be a lie), and the read verb's foreign-adoption reroute (below, `jigc doc list`) never fires on the staged arm — a staged working copy is jigc-written by construction, never a foreign squatter.
- **The stale-read hint.** A task-less read of a doc that is **also staged in an open task** serves the committed copy unchanged and adds one advisory line on **stderr** — naming the open task id(s) + the staged-read command (`jigc doc show <addr> --task <id>`) — so the serve says it may be behind the staged working copy; stdout stays the canonical render / the pinned json, **byte-identical** with and without the open task (no second additive key rides the pin). Existence check only, over the single task enumeration source — never a content read, so the hint says *may be* stale, never *is*.

**The staged marker key.** A **staged whole-doc `--format json`** serve carries the **staged-only additive top-level key** — `"staged": "<task-id>"` — beside the pinned `{ type, slug, fields, sections }` (and the `item-count` additive key below, which rides *both* serves), so a driver can never mistake a staged read-back for committed state. A committed serve carries **no `staged` key, ever**: `staged` is the one key that distinguishes the two views. **Fragment slices carry no marker** — a slice is a bare value (a prose string, an item array/object, a leaf) with no object to hang the key on, and the driver that needs the discrimination on a slice read has it in the command it just composed (`--task` was explicit). A conscious bound, not an oversight.

## The slice grammar — whole-doc, `#section`, item, leaf

The `<ref>` is a doc address, optionally carrying a `#fragment` that names a sub-node. The read surface does **not** define a grammar of its own: it **conforms to** the one address grammar ([structural-grammar.md](structural-grammar.md) → Addressing), which permits every depth *uniformly* — `fragment := unit ( "/" leaf )?` in a non-repeatable unit, `unit "/" item ( "/" leaf )?` in a repeatable one — and leaves it to the **schema** to say which depths are valid for a given unit. The table below is that grammar's depths *as they resolve on the read path*, not a narrower dialect of it:

| Address | Resolves to |
|---|---|
| `type:slug` (whole-doc) | the whole document |
| `type:slug#section` | one section — a **slot** section's prose, a **repeatable** section's item array, or a **fields-only** (header) section's fields (M42 — below) |
| `type:slug#section/<leaf>` | one **leaf inside a non-repeatable section** — a field's value, a sub-labelled slot's prose (M42 — the grammar's `unit/leaf` depth) |
| `type:slug#section/<item>` | one repeatable **item** object |
| `type:slug#section/<item>/<leaf>` | one **leaf** — a slot's prose, a field's value, or the `id-from` leaf (the item's heading) |
| `type:slug#section/<id>/<block>/<gid>` | one **nested item** object (M40 — a nested repeatable's member) |
| `type:slug#section/<id>/<block>/<gid>/<leaf>` | one **nested leaf** (M40) |

**The M42 rows are a defect correction, not an extension of the contract.** Both depths were settled by the foundation doc and honoured everywhere *except here*. [structural-grammar.md](structural-grammar.md) → Addressing tabulates `type:slug#unit/leaf` as *"a named leaf inside a non-repeatable unit (a field, a sub-labelled slot)"*, states that *"the schema determines which depths are valid; the grammar permits every depth uniformly"*, and pins the rule for all of them — *"**one grammar, every reference** … write commands, **validation targets**, override ops, data-values."* The **write** path honours it (`jigc doc set-field 'adr:use-rust#status/status'` → exit 0). **`jigc validate` emits it**: `schema-conformance.required-field-present` ([validate.rs:1759-1768](../crates/engine/src/validate.rs)) and `field-value-conformant` ([validate.rs:1797-1806](../crates/engine/src/validate.rs)) both address `#<section>/<field>`. Only the **read** path violated it — `jigc doc show 'adr:use-rust#status/status'` answered `blocking · store.no-such-item`, exit 1 ([store.rs:290-298](../crates/engine/src/store.rs): the leaf branch is guarded on `rest.len() >= 2` **and** a `chain_repeatable` template, so a leaf was only ever resolved inside a *repeatable* — a one-hop leaf in a simple section matches neither branch and falls through to the item-miss block at [store.rs:321-329](../crates/engine/src/store.rs)). **The tool emitted an address its own read surface could not resolve.** Blast radius: the 11 header sections across 10 doctypes in both packs — including `milestone-record`, this contract's own conformance witness (above). The slice table is **the drifted artifact and is corrected**; the grammar is not renegotiated (M42 — [DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 planning: the Settle).

**A fields-only (header) section slice serves its fields (M42).** `jigc doc show 'adr:use-rust#status'` returned the **empty string at exit 0** — a header that genuinely carries `status`/`date`/`supersedes` answering "nothing here". That is precisely the **wrong-node-exit-0** this doc forbids by name (below: *honest error or correct answer, never wrong-node-exit-0*), and it is the same silent-wrong-answer class the wave exists to close. Settled: the slice **serves the section's fields** — `--format json` → the section's leaves keyed by leaf id (shaped exactly as the whole-doc `fields` project them), plain → those field lines as the writer renders them.

- **Physical consequence: this slice is a canonical re-emit, not a byte slice.** A `ParsedSection` carries **no `fields_span`** — the parser hoists a doc's fields into one flat map keyed by leaf id, with no per-section byte range — so the slice is rendered *from the parse*, in schema order. That is not a special case: the plain path is a canonical re-render throughout (below).
- **The fields do not move.** The whole-doc rule below — *"a header/fields-only simple section contributes to `fields` alone and has no `sections` entry"* — stands unchanged. A slice is a **projection of the addressed node**, not a relocation of it: the fields-only section still has no `sections` entry in the whole-doc shape *and* it answers at its own address. Same fields, two views, one grammar.

## Plain text vs. `--format json`

- **Plain text** (default / `--format agent` / `--format human`) is the **canonical markdown re-render of the addressed node** — the node in the shape the writer emits it, so a human or agent reads committed content in its committed form. The **whole-doc** read is the store's own bytes; a **slice** is re-rendered from the parse, and coincides with the stored bytes wherever the render is faithful to them (which, for a conformant store, is most of the time — the store is written through the same canonical writer).
- **`--format json`** is the **pinned 1.0 stable contract** below — a machine-legible projection of the parsed structure (a one-way door, pinned now rather than left to the first implementation).

The two are complementary: legibility-in-committed-shape is the plain path's job; the json path trades markdown for a clean, keyed, deserializable shape.

**The old claim — *"the byte-exact slice … the store's own bytes for that node, verbatim"* — was false, and is retired (M42).** It was already false before M42, in two ways the code itself documents. `render_item_at` ([store.rs:477-480](../crates/engine/src/store.rs)) is **anchorless by design** — it re-heads from `item.title` alone, dropping the `{#id}` anchor that carries the item's frozen identity. And a nested slice is **re-rooted**: `#releases/100/changes` renders `### added` where the source has `#### added`, because the render re-heads at `2 + depth` relative to the *slice*, not the document. M42 **restores the `{#id}` anchor on rendered item headings** (the identity an agent needs in order to address the item back — see the item `id` below), closing the first gap; the re-rooting is inherent to lifting a sub-tree out of its document and stays. Byte-exactness was never the property the plain path had, so it is not the property it promises: it promises the **canonical render of the node you addressed**.

## The pinned `--format json` contract (1.0)

Pinned once here; every doctype's json read conforms. The **milestone record is the conformance witness** — the first doctype whose *primary* consumer is a machine read (fresh-clone continuation), so its shape is the pin's proof.

**Whole-doc** → an object keyed by the four pinned top-level keys `{ type, slug, fields, sections }` (joined pre-1.0 by the additive `item-count`, below):

```json
{ "type": <doctype>, "slug": <slug>, "item-count": <n>, "fields": { … }, "sections": { … } }
```

- **`type`** — the doctype id. **`slug`** — the addressed slug.
- **`fields`** — every *simple* section's leaves flattened, keyed by leaf id (the header front-matter + any body field group). A **scalar** field serializes as its string; a **list**-cardinality field as a json array of strings; an **enum** leaf as its **lowercase string** (the enum member is already its canonical lowercase form). The one **compound** field in the pinned surface is the milestone-record's `base` pin: it projects as a structured object `{ "sha": …, "short": … }` (clean lossless access to both SHAs; the committed `.md` stores the space-joined `<sha> <short>` scalar, so this is json-projection-only — [team-ready-state.md](team-ready-state.md) → The read surface, [DECISIONS.md](../DECISIONS.md) → 2026-07-07). Every other field stays a scalar.
- **`sections`** — one entry per **slot** section (its **trimmed prose string** — the clean machine value; leading/trailing whitespace stripped) and per **repeatable** section (its **item array**). A header/fields-only simple section contributes to `fields` alone and has no `sections` entry. An unfilled/absent slot is the empty string.
- **`item-count`** (additive, M44) — an integer: the doc's **total top-level repeatable item count**, summed across every repeatable section (a simple section contributes none; a **nested** item is a member of its enclosing item object and is *not* counted — a changelog with one release counts **1**, not the release's change-notes). It rides **every** whole-doc serve — committed **and** staged alike — so it never becomes the staged/committed differentiator (that stays `staged`, above). **A `#fragment` slice carries no `item-count`** — a slice is a bare value with no object to hang it on (the same bound the staged marker states).

**A `#fragment` slice** returns the corresponding sub-node of the whole-doc shape:

- a **slot section** → its trimmed prose string;
- a **repeatable section** (`#section`) → its **item array**;
- a **fields-only section** (`#section`) → an object of its leaves, keyed by leaf id, each shaped as in `fields` (M42 — above);
- a **leaf in a non-repeatable section** (`#section/<leaf>`) → the leaf value, shaped as in `fields` (M42 — above);
- an **item** (`#section/<item>`) → its item object;
- a **leaf** (`#section/<item>/<leaf>`) → the leaf value (a slot's trimmed prose string, a field value shaped as in `fields`, or the block's `id-from` leaf → the item's heading string).

**An item object** carries its **`id`** — the item's minted, frozen id, the handle every address into the item takes (M42, below) — its `id-from` leaf keyed by the block's declared `id-from` → the item's heading (its stable id-source), each other field keyed by leaf id (scalar → string, list → array), and each slot keyed by leaf id → its trimmed prose.

**The item `id` closes the json contract under its own address grammar (M42).** Without it the contract is **not closed**: a driver can read an item array and address **none** of it. The id is *not* derivable from the heading — a changelog release titled `1.0.0` mints the id `100`, so a driver that slugifies the title guesses `1-0-0` and earns a `write.wrong-shape`; and after a `jigc doc retitle-item` the heading and the frozen id diverge **permanently, by design** ([write-commands.md](write-commands.md) → `jigc doc retitle-item`; [storage.md](storage.md) → Identity). Before M42 the id lived only in the transient write-ack and in the raw markdown `{#id}` anchor, which every slice render stripped — so the one contract whose purpose is machine consumption withheld the one value a machine needs to write back. The **`id` key is reserved at schema load**: a pack declaring a leaf named `id` inside a repeatable block is rejected loudly at pack-load, so a future doctype cannot silently collide with the pinned key (no shipped doctype declares one, and none uses `id-from: id`).

**Nested repeatables join the pin (M40 — supersedes the M39 exclusion).** Nested `Leaf::Repeatable` groups (the M22 changelog nested shape) **join the pinned item object**: each nested repeatable keys the item object by its declared block id → an **array of recursive item objects** — e.g. a changelog release item: `{"title":"1.0.0","date":"…","changes":[{"category":"added","notes":"…"}]}`. The **section-qualified write address is accepted on show**: `#releases/<id>/changes` → the nested array, `…/changes/<gid>` → the nested item object, `…/<gid>/<leaf>` → the leaf. Two undeclared defects die with the pin: the false `store.no-such-item` on the canonical write address, and the segment-less **wrong-node degrade** (a deeper path silently returning the enclosing item, exit 0) — the rule is *honest error or correct answer, never wrong-node-exit-0*. The **plain** (markdown) item/section slice likewise carries the item's fields + nested content (a defect recorded at the M40 Settle and fixed in the rc.4 wave — before it, fields + nested groups were dropped and only the whole-doc plain read was complete; [DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 Settle). What that fix did *not* buy is byte-exactness, which the plain path never had — see the retired claim above.

**Evolution posture (declared — previously undeclared).** Additive keys are permitted **pre-1.0 only**; from the 1.0 pin, the shape evolves only by an **explicitly versioned extension** — never a silent additive key. Two additive keys land in the rc.4 wave under the pre-1.0 rule: the milestone-record's `fields` gains `schema-version` (the methodology stamp — [corpus-migration.md](corpus-migration.md) → The freeze-exempt sibling), and nested repeatable groups join the item object (above). The rc.6 wave (M42) lands the item **`id`** under the same rule — and the one that makes the contract closed under its own address grammar (above). The rc.7 wave (M43) lands the **staged marker key** inside the closing window — `staged` on a **staged** whole-doc serve only (above), so the committed shape the pin governs is untouched: the key rides the new `--task` read arm, never the committed read. The rc.8 wave (M44) lands the **`item-count`** key under the same rule — on **every** whole-doc serve (committed *and* staged) and on each `doc list` row (above); unlike `staged` it *does* touch the committed whole-doc shape, which is precisely what the pre-1.0 additive window permits. It carries **no version integer** — `doc show`/`doc list` have none of their own (the `contract-version` is `doc schema`'s), so this is an additive key, not a contract-version bump. The rc.6 wave's other read-path changes are **not** additions and do not spend the window: the `#unit/leaf` and fields-only slices are *defect corrections* against the foundation grammar, and the retirement of the byte-exactness claim corrects prose against behaviour that never matched it.

## Why json is a contract here (and describe's is the opposite)

`jigc describe`'s output is deliberately **non-contractual** — format-hostile to parsing so nothing depends on it ([introspection.md](introspection.md) → Non-contractual by design). `jigc doc show --format json` is the deliberate inverse: its whole purpose is machine consumption (fresh-clone continuation re-derives milestone state from it), so it **is** a stable contract, pinned at 1.0. The two read surfaces sit on opposite sides of the same axis on purpose: describe is a menu you orient by, `doc show` is content you compute over. **A third surface joins at M40**: `jigc doc schema <doctype> --format json` — the structural projection that *cannot* ride describe (its format predicate forbids parseable structure) — ships as a **separately-pinned, explicitly versioned contract**, pinned here:

```json
{ "contract-version": 3, "type": <doctype>, "schema-version": <the doctype's stamped version, else null>,
  "fields":   [ { "id", "type", "of"?, "required", "author-required", "default"?, "set"?, "section"?,
                  "set-field"? }, … ],
  "sections": [ { "id", "kind": "slot"|"repeatable", "optional"?, "set-slot"?|"add-item"?,
                  "item": { "fields": [ { …, "set-field"? | ( "add-item"? + "retitle-item"? ) }, … ],
                            "slots": [ { "id", "optional"?, "set-slot" }, … ],
                            "nested": [ { "id", "add-item", "item" }, … ] } }, … ] }
```

— the `item` object is **recursive** for nested repeatables (`nested` carries the inner blocks); a field's `of` carries an `enum`'s legal members (universal across depths — an agent reads the legal values from the contract, no failed-write probe), and `section` names the owning simple-section id (**top-level fields only** — an item field carries its section structurally, under `sections[].item`). **Every settable entry names its owning write verb by carrying its concrete address under that verb's key** (M43 rc.7): a field's `set-field`, a slot section's / item slot's `set-slot`, a repeatable's / nested block's `add-item`, and — on an **item** field only — the `id-from` pair below, an `id-from` leaf living inside a repeatable block by definition and never among the top-level `fields` — instance parts **placeheld** (`<slug>` for the doc, `<id>` for each enclosing item's minted id at that depth; the real values come from `doc list` / `doc show`'s item `id` key — the projection stays type-level, e.g. adr `status` → `adr:<slug>#status/status`). The key is **absent** where the entry is settable under **no** write verb — a `set:`-derived (CLI-stamped) field, whose value the CLI owns — absence meaning *not settable*, never an error. `contract-version` bumps on any structural change to this projection — **no additive carve-out** (the M41 rc.5 addition of the `of`/`section` keys bumped it **1→2**; the M43 rc.7 addition of the write-address keys bumped it **2→3**) — the *values* track the schemas as they evolve, the *keys/structure* are the pin; golden-pinned at ship ([introspection.md](introspection.md)).

**Three settability states, because two of them collapsed a required field into silence (M45).** Through rc.8 the projection had exactly two states — an address under a write verb's key, or nothing — and *nothing* carried two different facts at once. Verified at rc.8: every `id-from` leaf projects as `required: true, author-required: true` with **no address and no marker**, at **11 sites across 9 doctypes**, and the string `retitle-item` appears **nowhere** in the projection. So the pinned contract told an agent that a required, author-supplied field exists and named no way to write it — law 2's *nothing hides*, violated by the surface that produces the state ([surface-contract.md](surface-contract.md)).

*The record is revised on its rationale, not merely appended to.* The retired clause — *"absence meaning not directly settable, never an error"* — was **right** that an `id-from` leaf is genuinely not `set-field`-settable: the heading *is* the value, and the write-time guard (`write.id-from-field`) refuses it correctly. What it got wrong is that *not settable by `set-field`* and *not settable at all* are different facts, and that the designated recovery must be **named by the surface producing the state** rather than inferred by the reader. The projection therefore says which of three states an entry is in, reusing the existing rule verbatim — *the concrete address under its owning write verb's key* — and minting no new key kind:

| State | How the projection says it | Example |
|---|---|---|
| **directly settable** | the address under its owning direct-set verb — `set-field` / `set-slot` / `add-item` | adr `status` → `set-field: adr:<slug>#status/status` |
| **settable under a different verb** (the id-source) | the address under **that** verb's key: the leaf is supplied at mint by `add-item --title` and changed afterwards by `retitle-item`, so it carries both — `add-item` at the block's address, `retitle-item` at the **item** address | changelog `releases` `title` → `add-item: changelog:<slug>#releases` + `retitle-item: changelog:<slug>#releases/<id>` |
| **not settable** | **no verb key at all** | changelog `releases` `date` (engine-`set:`, CLI-stamped) |

Two precisions the shape has to carry, because getting either wrong ships a law-1 lie in the surface built to end one:

- **`retitle-item`'s address is the *item*, one hop shallower than the leaf's own** (`<type>:<slug>#<section>/<id>`, or the nested section-qualified chain — [write-commands.md](write-commands.md) → `jigc doc retitle-item`). Projecting the leaf address under that key would advertise an address the verb rejects — and would redden the M45 address-grammar round-trip on the very entry the state exists to fix.
- **An `enum` `id-from` leaf carries no `retitle-item` key at all.** `retitle-item` refuses it **unconditionally** — a member change is an identity change (M40, the enum-id-from refusal) — so its only write is `add-item` at mint, and its repair is remove + re-add. Advertising `retitle-item` there would be exactly the *route naming a verb that hard-errors* that [validation.md](validation.md)'s two-tier route was written to stop.

**The third state is a precondition, not an ornament.** M45 also ships the projection↔write-path **parity assertion** — *advertised-set == accepted-set* from one shared predicate rather than two duplicated ones ([pinning.md](../implementation/pinning.md) → §2). Under a two-state projection those two deliverables contradict each other: advertise the `id-from` leaf under `set-field` and parity reddens (the write path refuses it, correctly); advertise nothing and law 2 stays violated. So the parity predicate keys on **which verb** an entry is advertised under, and the three states are what make that keying possible — an entry advertised under `retitle-item` is neither *accepted by `set-field`* nor *hidden*. (Verified at rc.8: state 3 already announces itself — a `set:`-derived field carries its own `set` key, e.g. changelog `releases` `date` → `"set": "on-create"`. State 2 is the one that carries **nothing at all**, distinguishable today only by `author-required: true` — a coincidence of two unrelated predicates, not a declaration, and pinned by nothing.)

**`contract-version` 3 → 4, once, for the whole wave.** This projection bumps on **any** structural change with **no additive carve-out** (above), so *every* M45 change to it lands in **one** bump and therefore in **one** increment ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle). Splitting them across two increments would spend two version numbers on one wave's worth of change and hand a driver two contracts to track where the shape changed once.

## `jigc doc list` — the fourth read surface (M42)

`jigc doc show` answers *"what does this doc say"* — and presupposes you already know the doc exists. Nothing answered *"which docs exist"*. `jigc describe` projects **doctypes and workflows, zero instances**, and its format predicate actively *forbids* parseable structure ([introspection.md](introspection.md) → Non-contractual by design), so it cannot grow into an index. `jigc ingest --format json` enumerates *git candidates by path*, not the managed corpus by identity — and it mutates. So an agent's only route to the corpus was to guess a slug or read the filesystem directly, which is exactly the raw-file read the adapter rule forbids ([assistant-adapter.md](assistant-adapter.md)).

`jigc doc list [<doctype>]` projects the **committed store surface by identity**: the instances of one doctype (or of every persisted doctype), slug-sorted, each carrying its identity `<type>:<slug>`, its path, and its **registration state** (below). **Its substrate already exists** — `engine::index::committed_instances` ([index.rs:718-752](../crates/engine/src/index.rs)) returns exactly those slug-sorted `(identity, path)` pairs and **already handles both the placement branch and the located branch** ([storage.md](storage.md) → Placement); it is `pub(crate)` and no verb exposes it. **This is the same placement-aware enumerator the store-scope schema-conformance family needs** in order to stop skipping placement doctypes — the M42 false-green fix ([validation.md](validation.md); [corpus-migration.md](corpus-migration.md) → The freeze-exempt sibling). **One primitive, two consumers**: promote it once and both read the same enumeration, or it gets written twice and the second copy drifts — the failure mode the M38 placement census has already produced twice ([storage.md](storage.md) → Placement).

**It lists the store *surface*, and flags what is not adopted — because "one primitive, two consumers" inherits the foreign-squatter problem, and listing only the managed would hide it.** `committed_instances` yields a **placement** doctype's instance on **mere file existence** ([index.rs:724-731](../crates/engine/src/index.rs) — `path.exists()`, no registration test). So in a stock brownfield repo carrying an ordinary Keep-a-Changelog `CHANGELOG.md`, a naive `doc list` would report `changelog:changelog` as a **managed doc** — while `jigc doc show changelog:changelog` blocks `store.unparseable` and (post-M42) `jigc validate` correctly calls the same file **foreign, adopt it**. Three surfaces, three stories about one file, in the wave whose whole claim is that *the tool's own routes tell the truth*. Settled:

- **The discriminator is the committed `schema-version` stamp**, not the `.jigc` file-state record — the record is a gitignored, rebuildable cache and is empty on a fresh clone, so it cannot adjudicate what a teammate sees. The discriminator and its three-way route (**managed-current** / **managed-stale → `migrate-corpus`** / **never-adopted → `ingest` · `jigc migrate <path> --as`**) are [validation.md](validation.md)'s — owned there, not restated here. `doc list` **reads that same discriminator**; it never grows a second one.
- **A row is emitted for every instance the enumerator yields, carrying its state** — `managed` (stamped) or `unregistered` (no stamp: a foreign file squatting at a canonical home, or a never-ingested doc). **Each row also carries the additive `item-count` key** (M44) — the same top-level repeatable item count the whole-doc serve projects, computed by parsing the instance (`doc list` did not parse instances before this — the count is a new parse). It is **best-effort**: an instance that does not parse against its current schema — an `unregistered` foreign file, or a stale-shape managed doc — counts **0** (never a block: `doc list` is a report, and `state` already tells the agent the file is not adopted). **Not** managed-only: `doc list` is the agent's *only* sanctioned route to the corpus (the adapter rule forbids reading the store directly — [assistant-adapter.md](assistant-adapter.md)), so a listing that **omits** the very file jigc is telling the agent to adopt sends it straight to `cat`. Surfacing the file *and* its state is the honest answer and the useful one; the state is the projection of a fact the store already carries, not a new judgement.
- **`doc show`'s block on an unregistered instance routes to adoption**, not to hand-repair. Today it emits `store.unparseable` routed *"fix the committed file so it conforms to its schema"* ([store.rs:186-192](../crates/engine/src/store.rs)) — true of a *corrupted managed* doc, a lie about a *never-adopted foreign* one, whose repair is `jigc migrate`/`ingest`. The route splits on the same stamp discriminator. With that, the three surfaces tell **one** story: `doc list` says *unregistered*, `doc show` says *adopt it*, `validate` says *foreign — adopt it*.
- **Flow 43 must prove it**, on the archetypal case: a stock brownfield repo with a foreign root `CHANGELOG.md` + `jigc setup` → `doc list` flags it `unregistered`, `doc show` routes to adoption, `validate` routes to adoption, and after the adoption all three flip to `managed` together ([worked-examples.md](worked-examples.md) → flow 43).

**Its posture is declared as it ships.** The M41 lesson is that an *undeclared* output calcifies into a *de-facto* contract with no evolution rule — **the one-way door is the posture, not the field count** ([command-output-contract.md](command-output-contract.md) → Why this is a contract). A fourth read surface shipping undeclared one wave before the 1.0 pin would re-open exactly that door. `jigc doc list` is an **index/identity projection, not a content read**: it projects the identities, paths, and registration state the store already carries, never authored prose. It therefore rides **`doc show`'s posture, not `doc schema`'s** — one pinned shape, additive keys permitted **pre-1.0 only**, **no in-band version integer** (a per-call version stamp on a listing is noise on every call), evolving after the pin solely by an explicitly versioned extension. Golden-pinned at ship, like its siblings.

**The read-surface axis, with four members.** The three read surfaces sit on one axis: `jigc describe` is a **non-contractual menu**, `jigc doc show` a **contract-pinned content read**, `jigc doc schema` a **separately-versioned schema read**. `jigc doc list` joins as the **contract-pinned index read** — it answers *which docs the store surface holds, and which of them are managed* (identity, not content, not schema, not menu), and it is the surface `doc show` has silently presupposed since M39.

## The version/posture map — five regimes, named in one place

Five independently-governed version/posture regimes ride jigc's machine surfaces, and until M42 no document named them together — two of them were named in **no** document at all. The map is homed here, on the read side that owns three of the five; [command-output-contract.md](command-output-contract.md) links it rather than restating it.

| Surface | In-band version | Posture |
|---|---|---|
| `jigc doc show --format json` (above) | **none** — no version key, and no version constant exists in the code | pinned shape; additive keys **pre-1.0 only**, then a versioned extension |
| `jigc doc list --format json` (M42, above) | **none** — by declaration, above | the `doc show` posture |
| `jigc doc schema --format json` (above) | **`contract-version`**, **3** at rc.8 ([doc.rs:2165-2170](../crates/cli/src/doc.rs)) → **4** at the M45 settability-state change (above) | bumps on **any** structural change — **no additive carve-out** |
| The command-output contract — composed output, write-acks, findings ([command-output-contract.md](command-output-contract.md)) | **none** — by declaration | the `doc show` posture |
| The **result contract** — `engine::result::SCHEMA_VERSION`, currently **2** ([result.rs:19](../crates/engine/src/result.rs)) | **`schema_version`**, a top-level key on every result envelope (orientation, `describe`, the validation report, the block/error envelope) | bumped only when a public result type's json projection changes in a way an external consumer must notice |
| `jigc describe` (prose) | n/a | **explicitly non-contractual** ([introspection.md](introspection.md) → Non-contractual by design) |

The **result contract's `schema_version`** is the one named here for the first time: it has ridden every block/error envelope and every orientation since the engine's first result type and appeared in **neither** governing doc — a version integer nobody owned. It is a *third*, orthogonal integer: it versions the **envelope**, where `doc schema`'s `contract-version` versions the **schema projection** and a doctype's `schema-version` versions the **document shape**.

**One name, two json types — recorded, not repaired.** A doctype's **schema-version** surfaces on two pinned contracts with two different json types: `jigc doc schema` emits `"schema-version": 2` — a **number**, the *expected* version read from the freeze manifest (`SchemaContract::schema_version: Option<u32>`, [doc.rs:1759-1761](../crates/cli/src/doc.rs)) — while `jigc doc show` emits `"schema-version": "2"` — a **string**, the doc's *actual* stamp, projected like every other scalar field (`show_json` → `header_field_json` → `field_json`'s `Value::Scalar(s) => Value::String(s)`, [doc.rs:2360-2362](../crates/cli/src/doc.rs)). *(Cite corrected, M42: the M42 pass cited `schema.rs:585` — which is the `SCHEMA_VERSION_FIELD` **const**, not a projection site. The claim was right and re-verified live; the coordinates were not — exactly the class this wave says it is eliminating.)* Comparing the two is exactly the upgrade-path check a driver automates (*is this doc's stamp behind its schema?*), and today that comparison needs a cast. Note the two integers are different *things* — expected vs. actual — which is the substance, and must survive any repair. M42 **records** the asymmetry rather than papering it: unifying the type is a **breaking** change to one of two pinned contracts (a type change is not an additive key, so the pre-1.0 window does not cover it, and on the `doc schema` side it would spend a `contract-version` bump), and a fix wave does not get to make that call by accident.
