# Team-ready state — the milestone record as a managed doctype

**M39 design of record.** The pre-1.0 team-readiness slice: work-unit state a teammate (or a fresh agent session) continues from moves *out* of the gitignored workbench and becomes a committed, managed, legible doctype. Settled at M39 planning ([DECISIONS.md](../DECISIONS.md) → 2026-07-06 M39 planning: Settle + review-baked). Reads after [methodology-docs.md](methodology-docs.md) (the work-doc-doctype surface it extends) and against [storage.md](storage.md) (the layout + source-of-truth model it revises). The exhaustive fold-back into the reading-order docs is an M39 build increment (the M38 Inc-6 pattern), not restated here.

## The principle — `.jigc/` is the workbench, the repo is the record

The classification axis is **working vs record**, and it assigns each side a *home*, not just a `.gitignore` line ([ideas/team-ready-state-externalization.md](../ideas/team-ready-state-externalization.md), the settled direction):

- **The record lives OUTSIDE `.jigc/`**, at a legible committed home — reconciled, `jigc doc show`-able, migratable, uniform with every other managed artifact.
- **`.jigc/` is a pure working directory** — WIP staging, per-machine caches, worktrees. Gitignored as a matter of **identity**, not convenience.

Today (verified at HEAD `eaca116`) the milestone's authoritative state is raw engine JSON in gitignored `.jigc/milestones/<id>/`: `base.json` (`{sha, short}` base-pin, read by `engine::milestone.rs::read_base_pin`) + `tasks.json` (`{tasks: [<sub-task-id>, …]}` ordered list, `read_task_list`), with per-task `intent`/`status` in `.jigc/tasks/<id>/`. A teammate cloning the repo cannot see or continue in-flight milestone work — the genuinely-lost-on-clone set (`index`/`state` re-derive on a stateless clone; the milestone record does not).

## What graduates, and what stays WIP — the split is field-granular

The record/working line is drawn at **field granularity**, not by directory (a directory-level "all task state is WIP" re-strands the very continuation state this milestone targets):

| State | Home | Role |
|---|---|---|
| Milestone base-SHA pin | milestone record (doctype) | ✅ **source of truth** |
| Ordered sub-task list + each sub-task's `intent` + `status` | milestone record (doctype) | ✅ **source of truth** |
| `.jigc/milestones/<id>/{base,tasks}.json` | `.jigc/` | **rebuildable cache** (re-derived from the record) |
| Sub-task working areas (`docs/` staging, provenance) | `.jigc/tasks/<id>/` | gitignored WIP |
| Fan-out merge staging (`merged/`), worktrees | `.jigc/milestones/<id>/` | gitignored WIP |
| Derived caches (`index/`, `state/`), logs | `.jigc/` | gitignored (re-derived) |

**Scope:** the **milestone** record graduates; a standalone (non-milestone) single-task's in-flight state stays WIP (its durable value is already captured in the finalize-rendered commit / decisions-log / changelog; parked for validation in [ideas/task-record-graduation.md](../ideas/task-record-graduation.md)).

The one code split this forces: `engine::milestone.rs`'s `milestone_dir` roots **both** the record and the WIP staging under one `.jigc/milestones/<id>/`. M39 splits *record-home* (committed, outside `.jigc/`) from *WIP-home* (gitignored, inside `.jigc/`); every `<jigc_root>/milestones/<id>/` consumer learns the two-home layout. The `.gitignore` string — today a hardcoded literal duplicated across **three** divergent sites (`adapter.rs`, `task.rs`, `milestone.rs`, already drifted on `worktrees/`) — collapses to one source of truth and changes meaning (ignore WIP subpaths; the record home is committed).

## The `milestone-record` doctype

Named **`milestone-record`** (mirroring `completion-record`, which deliberately avoids reusing the reserved work-unit name) — **not** `milestone`, because the work-unit already occupies the `milestone:<id>` address (`engine::milestone.rs` emits `Location::addressed("milestone:{id}")`) and `doctype-map.md:51` locks "`task`/`increment`/`milestone` are not doctypes." The doctype governs the *state a milestone emits*, not its *identity* — the `completion-record` precedent (milestone-*close* state as a doctype) exactly. Addressed `milestone-record:<slug>`, where **the slug IS the milestone work-unit id** (both are the same kebab slug), so `milestone-record:cache-rework` names the record for work-unit `milestone:cache-rework` and `doc show` can locate the matching `.jigc/milestones/cache-rework/` WIP.

- **Methodology-pack**, multi-instance. **Freeze-exempt at M39** (no `schema-manifest.yaml` entry, no version-gate); **manifest-governed since M40** — it joined the methodology pack's own manifest at schema-version 1, stamp-injected + freeze-asserted + migrate-corpus-owned ([corpus-migration.md](corpus-migration.md) → the M40 revision; [doctype-map.md](../implementation/doctype-map.md) → the freeze scope pin). **Schema-version 2 at M42** — the `discarded` lifecycle member (below, [The lifecycle](#the-lifecycle--active--joined--discarded-m42)).
- **Home:** `location: milestone-records/` — **flat**, consistent with its sibling per-milestone record `completion-record` (`location: completions/`); under the composed `[dev ▸ methodology]` cascade the dev pack's `docs-root` applies (→ `docs/milestone-records/`), exactly as `completions/` → `docs/completions/`. It uses `location:` (composition-variant), **not** `placement:` (composition-invariant) — so unlike `VISION.md`/`CHANGELOG.md` its resolved path differs methodology-alone vs. co-composed; acceptable, the acceptance runs `[dev ▸ methodology]`.
- **Header fields:** `base` — the base-SHA pin, materialized `set: on-create`; `status` — active / joined / **`discarded`** (M42 — [The lifecycle](#the-lifecycle--active--joined--discarded-m42)), materialized on transition.
- **A repeatable `tasks` section**, one item per sub-task: `task-id` (the item `id-from`, a plain **string** — not a managed `ref`: a `task` is a work-unit, `ref-resolves` cannot walk it, the `deferral-ledger.trigger` precedent) + `intent` + a `status` field (the **same** three-member enum as the header), both CLI-materialized.

It carries **no LLM-authored prose slot** — purely machine-maintained structured state (the "human surface" fork was settled *pure machine-maintained*, not an authored goal slot). This is the shape the managed-doctype vocabulary does not express today (every existing leaf is an LLM-filled `slot` or an author-required `field`; the only CLI-`set` is `set: on-create` on `date`). It earns **two** engine capabilities (below); everything else is assembled from proven primitives — M16 repeatable-section + `add-item`, M22 on-create materialization + the clock-free `on_create` seam, M16 `singleton`-slug discipline, M38 `location` homing.

### Engine capability 1 (write) — `set: on-transition` machine-maintained leaves

Extend the M22 CLI-side materialization seam from **on-create** to **on-transition**: a leaf tagged `set: on-transition` is (re)materialized by the CLI at a milestone state change. **The engine stays clock-free and LLM-free** — the CLI supplies the values from work-unit state it already owns, exactly as it supplies the fan-out join message ("structure the CLI owns, like git's auto-generated merge message"). The determinism boundary is intact: a *structural* write (which items exist, their machine-set fields), never prose. Two distinct write arms, designed separately (the review's F5 census):

- **`add-task` — append.** Appends one `tasks` item (`id`/`intent`/`status: active`) via the M16 `add-item` primitive. Ordered, byte-stable.
- **`join` — in-place mutate.** Rewrites the machine-set `status` field of **every already-committed `tasks` item** (active → joined) and the header `status`. This is an in-place item-leaf rewrite of N existing items — a *different* operation from append, routed through the byte-stable item-leaf splice path (the `set_item_field` splice, but writing the **committed record directly**, outside any task working area — net-new plumbing vs. the task-scoped author path). Byte-stability of the in-place rewrite is a red acceptance obligation (create → add-task ×2 → join → both items' `status` flip, doc byte-identical modulo the two flipped values).

**No-silent-overwrite discipline (the review's F3 fix).** Because every field is CLI-owned, an OOB human edit to a machine-set field cannot be *merged* — but it must not be silently *clobbered* either. Each milestone-op write runs a **reconcile preflight** (`reconcile_committed_store` over the record) and **conflict-blocks on drift** before any `set: on-transition` write, routing the human to reconcile via the CLI. The record is thus *detected + conflict-blocked*, **not** "hand-editable and merged like an authored doc" — the honest framing: it is a CLI-maintained structural record whose OOB drift is caught, not absorbed.

**The discipline does not depend on the gitignored cache (the rc.24 fix pass).** *Drift* is a comparison, and the preflight's first witness — the hash jigc recorded at its last landed record write — lives in `.jigc/state/`, which no clone carries. Until this pass a checkout with no key for the record (every fresh clone, a deleted cache, a `jigc unmanage` of the record) adopted whatever was on disk at its first record op and wrote the record over it: driven, a hand line appended to the record was re-rendered away by `jigc milestone add-task` at exit 0, in the worktree and in `HEAD`. So where there is no recorded hash the preflight asks git whether the record differs from its **blob at `HEAD`** — every record write lands in a commit, so that blob is what jigc last wrote; and the comparison is git's own, so the byte form a converting checkout or the door's own in-place splice leaves is not a difference — and a record git calls modified conflict-blocks at **every door that rewrites the record** (`add-task`, `add-from-spec`, `milestone discard`, a sub-task's `task discard`, the finalize flip), with nothing adopted and nothing written. The route is the one restore that is true of that comparison, `git checkout HEAD -- <record>`, after which the same command lands. An untouched clone, and an edit that arrived by `git pull` (the bytes on disk are then `HEAD`'s), are adopted as before; and a recorded hash keeps its own stricter answer — every drift from it blocks, a pulled one included ([reconciliation.md](reconciliation.md) → Baseline adoption, the record door's witness).

### Engine capability 2 (read-back) — the committed record is the engine's authority

The committed `.md` record is the **source of truth**; `.jigc/milestones/<id>/{base,tasks}.json` is demoted to a **rebuildable cache**. `engine::milestone.rs`'s operational reads (`read_base_pin`/`read_task_list`, and `join`/`add-task`) resolve through the cache, and the cache is **re-derived from the committed record when absent or stale** — so on a **fresh clone** (no `.jigc/` working state) the first milestone op parses `docs/milestone-records/<id>.md` back into `BasePin` + `TaskList` and re-seeds the cache. This is what makes the [storage.md](storage.md) invariant — "delete `.jigc`, **rebuild from the `.md`s**, nothing lost" — *genuinely* true for milestone state (F1): the record is not merely committed, it is the rebuildable operational source.

**"Continue" means resume, not WIP recovery.** A teammate on a fresh clone re-derives the milestone's shape (base, task list, intents, statuses) from the record and **resumes un-joined tasks from scratch** — the existing stateless restart-from-scratch resumption policy (the fan-out resumption model, [decisions-pending.md](../implementation/decisions-pending.md)). Joined tasks are done; active tasks re-run from their recorded `intent`. Half-done sub-task WIP (gitignored) is *not* recovered — correct and consistent with the resumption policy.

**Re-seeding rebuilds the sub-task *working areas*, not only the cache (M47).** "Resumes un-joined tasks from scratch" is only true if there is something to resume *into*: a sub-task is re-entered as `jigc workflow <W> --task <sub-id>`, which reads `.jigc/tasks/<sub-id>/`. Re-deriving `{base,tasks}.json` alone left that directory absent, so the milestone-execution workflow's own emitted `Spawn:` line — the one composed step a fresh-clone operator is handed — dead-ended on *"no task"*, routed straight back at `jigc milestone list-tasks`, which names that same sub-task. A **loop**, and the one the [finalize](finalize.md) zero-contribution refusal routes a fresh clone into. So the re-seed has **two halves at one site**: the milestone cache, and one standard working area per sub-task the record names — the recorded `{#id}` anchor as the id (never a re-slug of the intent), the milestone's shared base pin, and the item's verbatim `intent`. A sub-task whose area already exists is skipped untouched, so a live session is never clobbered — **and so is one the record has settled** (M49): the skip keys on the *item's* own `status` through the same terminal vocabulary the header guard uses, because a per-item terminal now exists ([below](#jigc-task-discard-sub-id--the-per-sub-task-terminal-m49)) and the premise this re-seed used to rest on — *both terminals flip the header and every item in one write, so a live header has no settled items* — stopped being true the day one sub-task could be abandoned on its own. **The recorded workflow is fresh-clone durable (M49).** It was the opposite, as a *declared bound*: the record carried `task-id`/`intent`/`status` and nothing about the minting workflow, so the re-seed re-derived the pack's default sub-task workflow — right for every un-overridden sub-task, and for an overridden one the operator's own `jigc workflow <other> --task <id>` re-entry was refused by the [re-entry W-equality guard](write-commands.md) **naming a workflow the re-seed had itself invented**. That is false provenance asserted with full confidence, and the durable home was never in doubt: the record is what a fresh clone resumes from, so the workflow belongs in it. `schema-version` 3 declares a per-item `workflow` leaf, the `add-task` append arm records the workflow it actually minted against, and the re-seed sources **each item's own** recorded value. The pack default survives only as the **fall-back for an item with no leaf** — every record committed before the bump, which the migration leaves byte-untouched (the leaf is machine-maintained and `default`-less), so those milestones resume exactly as they did.

**And the re-seed belongs to the doors that *operate*, never to the one that *reads* (M49).** `jigc milestone list-tasks` is the one milestone verb classified `VerbKind::Read`, and it reached this same site — so a *read* rebuilt the milestone cache and every absent sub-task area, each with a `workflow` file the record did not then carry and therefore could not source. For an `--workflow`-overridden sub-task that is a **fabricated provenance**, written by a read verb into the one file a later `jigc workflow <W> --task <id>` re-entry treats as authority. The record carries the leaf now, so the *value* is no longer invented — but the shape of the objection is untouched and is why `list-tasks` stays off this site: a read verb may not materialize a working area, whatever it would put in it. `list-tasks` reads the committed record directly now and materializes nothing — both behaviours it needed are read-only (the fresh-clone answer is [`read_back_record`](#engine-capability-2-read-back--the-committed-record-is-the-engines-authority)'s own parse, and the terminal refusal below is a pure parse of the record's `status`). The promise above is unchanged for every door that goes on to operate.

**Stale-base edge (history rewrite).** The record content survives a rebase/squash/filter as ordinary tracked content (jigc re-derives from the *current* file, never from the record's own commit history). The one genuine fragility is the base-SHA pin naming a commit a rewrite orphaned — a property of *any* sha pin (today's `base.json` included, unchanged by this move). Handled by **graceful stale-base detection → route to the human** (re-pin or error), never silent corruption. Bound: the live in-flight window is short, mid-milestone rewrite is unusual; degrade cleanly, revisit if a real case appears.

**And the record can only be the source of truth where a record can exist (M52).** Every `jigc milestone` door refuses a repository with no `jigc setup` — the shipped `locate::not_set_up()` answer on the `{error}` arm, one ask at the family's dispatch above every verb. Eight of the nine never asked — six of them landing state at **exit 0**, `provision` among them registering a real detached worktree — so the whole arc lived in a gitignored `.jigc/` that no clone sees and no fresh clone can re-derive: the exact inverse of the settlement above, produced by the doors that are supposed to uphold it. The answer is deliberately the one every other door requiring the project layer already gives (21 of the 47 leaves when M52's baseline measured it) rather than a milestone-specific finding code — consistency with the shipped surface, not an omission (`completions/artifacts/M52/settle-record.md` §13); re-coding not-set-up as a registered finding at every leaf is a separate move this wave does not carry. Driven per door in `crates/cli/tests/milestone_not_set_up_axis.rs`, whose subject is `VERB_KINDS`' `milestone` family, so a tenth door joins the sweep the day it is added.

### Why this preserves, not breaks, the source-of-truth invariant

[storage.md](storage.md) states: "the committed Markdown at type locations is the **only source of truth**; every other artifact is a rebuildable cache or a transient working copy." With capability 2, the milestone record *joins* the `.md` set as a first-class member and the `.jigc` JSON becomes exactly a *rebuildable cache* — so the invariant's wording is revised in the **strengthening** direction (a new `.md` member), not relaxed. A committed *non-doctype* record (raw JSON at a visible path) would instead be a *second, non-rebuildable source of truth* — reintroducing the dual-source-of-truth the caches are gitignored to avoid. That is the decider recorded at Settle: (c) is the only option that keeps the model uniform *and* keeps the record readable through `jigc doc show` — the read surface M39 itself builds.

## The commit model — path-scoped commit at each milestone op

The record is written **and committed at each structural milestone op**, so a teammate cloning at any moment sees true current state (settled at planning). The commit is **path-scoped** (the review's F4 fix): it stages and commits **only the record file** (`git add <record> && git commit -- <record>`, index-restricted), never sweeping the agent's in-flight index/worktree WIP — honoring the M30/M31 staging discipline ([storage.md](storage.md) → dirty-tree policy). Arm by arm:

- **`create` / `add-task`** — a **separate** record-only path-scoped commit each.
- **`join`** — already a finalize/commit boundary (the fan-out finalize commits code + docs); the record's `status`-flip write **folds into the existing join commit** (path-added alongside the promoted docs), not a second commit.

**Each per-op record commit is a transaction with a rollback boundary (M47).** *"Writes are transactional"* is a `CLAUDE.md` invariant, and the record-only doors were outside it: they wrote the record, `git add`ed it, and committed it, so a rejected `pre-commit` hook left the write **and** the index entry behind while the baseline stayed at the pre-write hash — one rejected hook **bricked the milestone permanently** (every later door conflict-blocked, and the staged residue tripped the *next unrelated task's* carryover gate). So the discipline is stated as a **rule about doors, never as a *prose* list of them** (an enumeration in prose here has been falsified twice — see the teardown rule under [The lifecycle](#the-lifecycle--active--joined--discarded-m42), whose door list was overtaken first by `uninstall` and then by `provision`): **every door that writes the committed record and commits it captures the record's pre-image before writing and restores it — worktree *and* index — on any failure of that commit**, leaving no residue and re-baselining nothing. **Since M52 the list does exist, and that is what makes the rule checkable rather than a retraction of it**: the **five record-only doors** are `cli::rollback::ROLLBACK_POPULATIONS`' `milestone-record` row — the four milestone ops (`create`, `add-task`, `add-from-spec`, `discard`) and, since M49, a sub-task's `jigc task discard` ([below](#jigc-task-discard-sub-id--the-per-sub-task-terminal-m49)) — held to the source in both directions by `crates/cli/tests/rollback_population_registry.rs`, so a restore site the code gains without a row reddens and a row whose site is deleted reddens. The datum for the distinction is what happened while only prose held the set: this doc named all five and [finalize.md](finalize.md)'s rollback row named four, from M49 — when `jigc task discard` became the fifth — until this increment, with nothing comparing the two (`completions/artifacts/M52/settle-record.md` → §19). A door added later still inherits the obligation by **writing the record**, not by being appended — which is why the restore lives in the shared commit seam rather than in each caller, and why the row is fenced against the seam rather than hand-maintained beside it. **A door unwinds its own mint with it**, because the committed half is only half the state: `create` removes the milestone area *it* created, `add-task` removes the sub-task area and restores the task-list cache to its captured pre-append bytes — otherwise the workbench survives the rollback and the identical re-run blocks on a serial collision forever, while the cache names a sub-task the record does not. The unwind belongs to the **door**, never to the engine's identity guard: both mints still refuse a pre-existing id before creating anything, which is exactly what makes removing what this call minted safe. The recovery is therefore the ordinary one: fix the hook's complaint, re-run the identical command, it lands ([finalize.md](finalize.md) → Rollback discipline, the record-only-door row; [reconciliation.md](reconciliation.md) → Hash re-baselining, the fourth site).

**`add-from-spec` recovers by *resuming*, because it lands N commits, not one.** It mints one sub-task per spec criterion and commits the record once per sub-task, so a rejection of the k-th commit has k−1 commits already in history that no rollback can take back. Its atomicity is therefore the property that *is* reachable: **the workbench names exactly what the record names** — the mints the record never named are unwound (their areas removed, their ids dropped from the task-list cache, which re-renders byte-identical to its k−1 state). And the seeding pass is **resumable**: a criterion the milestone already carries is *skipped*, never collided, so re-running the same command seeds exactly the remainder and acks the rest as already seeded — with the rejection printing that command, so the recovery is the one the operator was told to run. **The skip set is what the committed record names, never the demoted cache** — the source-of-truth rule applied to the one place it decides whether work is *dropped*: an id that reached the gitignored workbench but never the record (a mint aborted mid-loop, an unwind that could not finish, a process killed between the two writes) would otherwise be absorbed as "already seeded" and that acceptance criterion would be absent from the committed record **forever**, at exit 0 with a positive ack. Keyed on the record it is not skipped, so it is re-minted or it blocks loudly. The set is read **once, at entry**, which is what keeps a resume and an *authoring* collision distinguishable: two criteria of one spec slugging alike still block rather than being absorbed — and that block now unwinds this call's own mints through the same primitive the rejected k-th commit uses, so neither half of the pass can leave the workbench naming what the record does not.

This does **not** breach the finalize-transaction invariant, which governs the **doc-content integrity gate** (required-slot presence, forward-ref resolution) — the record carries no authored prose to gate; it is a *structural* artifact the CLI maintains, the same class as the code commit the CLI already makes at finalize.

**The finalize base-guard refinement (settled 2026-07-07, mid-build — [DECISIONS.md](../DECISIONS.md) → 2026-07-07 M39 build).** Per-op record commits advance HEAD, so the pinned milestone base no longer equals HEAD at `finalize`; and `record.base` is structurally always ≥1 commit behind HEAD (a record commit cannot store its own resulting sha), so the old `plan_milestone_finalize` preflight `base.sha == head_sha` (the M31 worktree-combine external-drift guard) can *never* pass in this model — on a fresh clone too. The guard is **refined, not removed**: proceed if `base == HEAD` (fast path), **or** if `base` is a linear ancestor of HEAD *and every commit in `base..HEAD` touches only this milestone's record path* (`docs/milestone-records/<id>.md`) — then advance `base → HEAD` and proceed; **any non-record commit in the range still blocks** (`base-mismatch`). *(The "**this** milestone's record path" half is **corrected at M42** — one predicate too narrow, it wedges concurrent milestones on their *record bookkeeping* alone; the guard's corrected scope — and the real constraint it sits on top of, which the widening does **not** remove — are below, § [What the base-guard is for](#what-the-base-guard-is-for--the-fix-and-the-real-constraint-underneath-it).)* This makes the guard catch what it was *for* — **external** drift, which would invalidate the worktree-combine — while tolerating the milestone's own record-only bookkeeping (which touches no code, so the combine base is unaffected). The **engine does no git I/O**: the CLI computes the range's linearity + record-only-ness and feeds the result to `plan_milestone_finalize`. (Owed to [finalize.md](finalize.md)/[storage.md](storage.md) at the Inc-8 reading-order fold-back.)

## The working area's two populations — jigc's writer set, and its complement (M52)

A working area holds two kinds of byte, and until M52 no document said so. `.jigc/tasks/<id>/` and `.jigc/milestones/<id>/` are gitignored scratch that jigc mints, writes and tears down — and they are also an ordinary directory an agent working in the repo can write into, which agents do: the destroying-door baseline planted a `NOTES.md` at a task-area root and an `analysis/perf.txt` under it, and `jigc task discard` removed both at exit 0 with an empty stderr. Three places in this codebase named a subject for that removal and **no two of them agreed** — this doc scoped the rule to worktree-shaped paths under `.jigc/worktrees/`, widened it only as far as a sub-task's `docs/*.md`; `crate::setup`'s teardown asked a third question; and [finalize.md](finalize.md)'s phase-7 bullet authorized removing the whole directory with no guard at all. So the rule is stated here, once, and the doors take it from here.

**Jigc's own writer set is a registry** — `engine::state::TASK_AREA_FILES` and its milestone sibling `MILESTONE_AREA_FILES`, with one home both crates read, whose members are the filename declarations **themselves** rather than copies of their values, so the registry cannot drift from the writer. Before M52 that set was owned by nobody: thirteen constants scattered across three modules, eleven of them private, and any list drawn by hand off that scatter drove **short**. The hand-drawn one missed `renames.json` — written at the ordinary `jigc doc rename --task` door — so a guard cut from it would have called jigc's own file foreign at every task that had renamed a doc. A **counted source scan** over the production `<…dir>.join(<name>)` sites in both crates now holds the registry to the writers (`crates/cli/tests/task_area_writer_registry.rs`): a fourteenth writer reddens rather than silently joining the complement, and a member deleted from the registry reddens too.

**Two rules qualify membership, and both come from bytes that were lost by their absence:**

- **`docs/` is a tree, not a name.** Inside a task area's `docs/`, jigc's set is the provenance manifest plus the staged doc bodies — every entry whose name reads as a staged `<type>:<slug>` identity. It is deliberately the `.md`-name set rather than `provenance.json`'s key set, which is the more *precise* answer to *"did jigc stage this?"*: the doors this feeds destroy or move the complement, so the precise rule's failure mode is losing authored prose and the loose rule's is keeping one file too many. Only one of those may be wrong. **The milestone row's `merged/` is a tree the same way, and it is walked** — under it jigc's set is the `docs/` directory the join materializes into, and inside that it is the staged-identity name set **alone**, not the task branch's wider rule: `materialize` writes only `<type>:<slug>.md` bodies, so a `merged/docs/provenance.json` is a third party's file here even though the identically-named entry in a *task* area is jigc's. M52 shipped it as the one exclusion — *"the join's staging area, jigc's wholesale, never walked"* — and that is an exclusion resting on the predicate **nothing but jigc's bytes are in `merged/`**, which is false four ways (M53): a finalize blocked at exit 3 leaves the area standing with its materialized bodies in it, where a human edits beside them; a succeeding `pre-commit` hook writes into the area *during* the commit, which is the writer this codebase had already recorded; `materialize` took an editor `.swp` on a finalize that committed nothing; and the carve-out **defeated the consent gate** at the two doors that have one — driven, `jigc milestone discard` with no `--force` over `merged/top.txt` and `merged/docs/deep.txt` exited 0, printed *"workbench removed"* and took both, while the identical byte at the area **root** refused. One state, two answers, from one carve-out.
- **Shape is part of membership.** A member's name on the wrong kind of entry — a *directory* called `base.json`, a plain file called `docs`, a symlink wearing either — was written by no jigc operation, and the shape is read without following symlinks, because jigc writes regular files and real directories and never a link. This is M52's L-3 lesson asked at the door's own question: a directory named `<type>:<slug>.md` was a staged identity at four surfaces, one of them the 1.0-pinned `doc list --task`, until that increment.

**The complement is the subject of every door that destroys a working area.** What a door *does* with it is that door's own disposition — refuse without a consent, narrate under one, or move it aside — recorded with the door and enumerated in `DESTROYING_DOORS`; what no door may do is take it silently, which is what all five did. The enumeration is derived, never walked by hand: a **foreign directory is the unit**, returned whole and never descended, because the entry is what a door names, refuses over or moves, and moving the top of a subtree preserves it.

**The probe is fail-closed**, on `staged_task_prose`'s discipline: an **absent** area is the empty complement — and absence is `NotFound` and nothing else — while a present area that cannot be read, or an entry whose shape cannot be stat'd, is an error the door holds on. Enumerating nothing and finding nothing are the same empty list to a caller about to delete, and only one of them is safe.

## The lifecycle — active / joined / discarded (M42)

M39 pinned the record's lifecycle as **active → joined**, and that is the *finalize* path only. A milestone that is **abandoned** — the work is dropped, the fan-out never joins — had **no terminal state to reach**: the `status` enum was closed at `[active, joined]` on both the header and the `tasks` item block, and enum members are inside the frozen `schema-hash`, so there was **no value to flip to**. The committed record therefore stayed `status: active` with every task item `active` **forever**, and store-scope `validate` saw nothing wrong with it. *The repo is the record* is this doc's own principle; a record that permanently states a milestone is in flight when it was thrown away is a defect **in the principle**, not a missing convenience verb — so M42 settles the abandon path ([DECISIONS.md](../DECISIONS.md) → 2026-07-13 M42 planning: the Settle, fork 3).

**The enum widens to `[active, joined, discarded]` at `milestone-record` schema-version 2** — a frozen bump, riding M42's new `EnumWidened` transform kind (a widening is a byte no-op on the corpus: no committed value changes meaning; [corpus-migration.md](corpus-migration.md)). This is the member that makes an abandoned milestone *observable*.

### `jigc milestone discard <id>` — the record-settling op

The verb that settles the record and tears the workbench down ([write-commands.md](write-commands.md) → the milestone verb family, for the surface). Three properties, each load-bearing:

- **Per-item semantics — a joined sub-task stays joined.** A sub-task that **genuinely joined** keeps `status: joined`: it really did land, its code and docs are in the history, and flipping it to `discarded` would make the record lie about **landed work**. Every **non-joined** item flips to `discarded`; the header flips to `discarded`. The record stays true on **both** axes and reads as *what actually happened*. (This is the same honesty rule as the join arm's in-place item-leaf rewrite — a machine-set structural write over the committed record, never prose.) **Bound, corrected at the M42 completion audit:** a *mixed* record — a `joined` item under a still-live header — is **not reachable through the verbs**, because `finalize` joins the milestone *whole* (header and every item) and `joined` is a terminal (below). The M42 build reached one only by *resurrecting a finalized milestone* through the reseed hole the audit found, and its e2e fixture did exactly that. The per-item rule stands as the engine's honest handling of any record that **does** carry a joined item — it is proven at engine scope over a directly-constructed record — but it is not a state the verbs can produce, and this doc no longer claims it is. (6) `jigc task validate <sub-task-id>` does not preview `milestone.unlanded-work`: it is a milestone-boundary gate, like `milestone.zero-contribution`, outside the set that preview claims.

- **The workbench is actually removed.** `discard` removes the sub-task areas **and `.jigc/milestones/<id>/`** — for which **no reachable remover exists today** (teardown is reachable only from the milestone finalize path, so an abandoned milestone leaves its base pin, its task list, and its registered git worktrees behind, and `milestone provision` will happily re-provision a worktree for a sub-task that was discarded, because it reads the cache rather than the live areas). The cache is rebuildable from the record ([Engine capability 2](#engine-capability-2-read-back--the-committed-record-is-the-engines-authority)) — but only while the record says the milestone is live; once it is `discarded`, the cache has nothing to rebuild *for*, and leaving it is the workbench outliving the record. **The sub-task areas hold a second subject, and it is named before it is taken** (M46 Inc 2, on the wave's own claim): a sub-agent's authored `docs/*.md` lives at `.jigc/tasks/<sub-id>/docs/` and is in **no object DB at all** — on the abandon path nothing landed, so the workbench is its only copy — yet this teardown removed it at exit 0 in silence while `jigc uninstall` **refused** over byte-identical state and named the same docs (`uninstall.staged-prose`). The rule above is a rule about **doors**, not about worktree-shaped paths only, so the abandon now names every staged doc of **its own** sub-tasks before removing their areas, through the emitter `uninstall` already uses — scoped to those sub-task ids, since an unrelated open task's area this door never touches must not be claimed either. ~~The same **visible, not prevented** bound applies: the abandon's premise is that the work is being thrown away, and the refusal it does carry is the worktree one.~~ **Struck at the M50 completion audit (finding 4), with the datum that falsifies it.** The clause was the whole warrant for narrating here rather than refusing, and it is false in the only cell where bytes die. Driven as a 2×2, one milestone per cell, through the real binary: with a **clean** worktree and a sub-task staging `commit:<sub-id>.md`, `git status --porcelain` is empty — because an agent authoring through jigc writes into `.jigc/tasks/<sub-id>/docs/`, which **is not inside the worktree** — so the worktree refusal structurally cannot see the subject, and the abandon narrated the loss and then took it at **exit 0** while `jigc task discard` refused over the identical bytes. So this teardown now **refuses** over its own sub-tasks' staged docs with **`milestone.staged-prose`**, naming each sub-task and its staged identities, routing read → land → consent, and `--force` is the single consent for **both** of this door's guards (a pair that consents through two mechanisms is a pair that will diverge again). The **visible, not prevented** bound is unmoved where it was measured — the *worktree*'s unstaged, untracked and ignored bytes, and the landed-finalize door — and the guard's omitting context is what keeps it off the ordinary path: `milestone add-task` and `milestone provision` stage nothing, so a milestone abandoned before anyone re-entered a sub-task still discards at exit 0 with no consent.

### `jigc task discard <sub-id>` — the per-sub-task terminal (M49)

The milestone-level abandon above settles the record **whole**. One sub-task abandoned on its own had no terminal at all: `jigc task discard <sub-id>` was workbench-local — it knew nothing of milestones — so it removed the working area at exit 0 and the committed record went on calling that sub-task `status: active` **forever**. The same defect as the un-abandonable milestone, one level down, and against this doc's own principle: *the repo is the record*.

So a sub-task discard is a **record-only door** ([The commit model](#the-commit-model--path-scoped-commit-at-each-milestone-op)), with the family's whole discipline rather than a second one — the reconcile preflight, the captured pre-image, the path-scoped commit of the record alone, the baseline advance, the survivable frame on a rejecting hook. Three properties are its own:

- **One item, and only that item.** The item's `status` flips to `discarded` through the byte-stable item-leaf splice; **the header stays `active` and every sibling item is byte-untouched**, because the milestone is still in flight — abandoning one sub-task is not abandoning the milestone. A *mixed* record is therefore now **reachable through the verbs**, which the M42 bound above said of a `joined` item it was not; the engine's per-item honesty rule is what makes the reachable case correct rather than newly wrong.
- **It settles before it destroys.** The record commit runs **before** the working area is removed, so a rejected `pre-commit` hook leaves the record *and* the task exactly as the frame says — and the printed re-run lands what the rejected run would have. A door that removed the area first could only tell the operator to re-run something that no longer resolves.
- **Inert where there is no record to settle.** An ordinary task is named by no record, and a dev-only project (no methodology pack) resolves no `milestone-record` doctype at all: both discard exactly as before, writing no record and landing no commit. The owning milestone is resolved from **what the committed record names**, never from the gitignored `.jigc/` cache — the source-of-truth rule the `add-from-spec` skip set already applies, and for the same reason: on a fresh clone the cache is a rebuild of the record, so keying on it would silently answer *"no milestone"* and leave the record lying.
- **It refuses over its own staged docs, and `--force` is the consent (M50).** The abandon path destroys uncommitted work by definition, so it carries the same guard `jigc uninstall` has carried since M48, from the same probe: a working area staging a `docs/*.md` blocks with **`task-discard.staged-prose`** and removes nothing. The two doors could not otherwise agree — `uninstall` refused over the identical bytes this door deleted at exit 0, and *routed the operator here to do it*. The scope is what each door removes: `uninstall` asks about the whole workbench, this one about its single area, so neither names nor is blocked by prose it will not touch. The **sub-task cell is the one that stays bare**: `milestone add-task` stages nothing at mint, so settling a never-re-entered sub-task needs no consent — which is also what proves the guard is keyed on staged bytes rather than on being a task. **M52 adds the second subject at the same door** — the working area's *other* population, refused with **`task-discard.foreign-bytes`** and asked ahead of the staged-prose guard, because the mint stages the commit doc and a guard asked after it could never fire here. Surface + the stated behaviour change: [write-commands.md](write-commands.md) → Abandoning a task.

**And the record write alone would have fixed one door of eight.** [Engine capability 2](#engine-capability-2-read-back--the-committed-record-is-the-engines-authority)'s re-seed rebuilt any sub-task area the record named and the workbench lacked — so the moment the discard removed the area, the next milestone door rebuilt it, `jigc milestone list-tasks` (a *read*) included. The settled-item skip therefore lands in the same change as the record write, at the one shared re-seed site every door passes through. (`list-tasks` was then taken off that site entirely — a read verb rebuilds nothing at all, [above](#engine-capability-2-read-back--the-committed-record-is-the-engines-authority); the settled-item skip stands for the seven doors that still re-seed.)

### The terminal is terminal — a settled record has no workbench (M42 completion audit)

**Removing the workbench is not a guard.** The M42 build shipped the teardown above and stopped there — and the teardown was undone by the very next command. [Engine capability 2](#engine-capability-2-read-back--the-committed-record-is-the-engines-authority) **rebuilds** `.jigc/milestones/<id>/` from the committed record whenever the cache is absent (the fresh-clone continuation path), and it never read the record's `status`. So the abandoned milestone came straight back **out of its own discarded record**: `provision` re-provisioned worktrees at the abandoned base, `add-task` appended an `active` sub-task to a `discarded` record — both exit 0. The lying committed record the whole abandon path exists to prevent, restored by the tool, from the record that said it was abandoned.

The invariant, and the one predicate that carries it:

> **A record in a terminal state does not re-seed a workbench.**

- **Both terminals, one predicate.** `discarded` and `joined` are the same state operationally — *the milestone is over and has no workbench* — and the hole was identical at both: `finalize` also tears the area down, so `add-task` after a finalize resurrected a **landed** milestone just as happily. They are fixed together, keyed on *terminal*, never on either member, because a guard written for one member is a guard the other leaks through. (Fixing the instance and not the class is this wave's signature failure; it is not repeated here.)
- **Continuation is of the un-joined.** This is not a new rule — it is [Engine capability 2](#engine-capability-2-read-back--the-committed-record-is-the-engines-authority)'s own words (*"resumes un-joined tasks from scratch — joined tasks are done"*). A settled milestone has nothing to resume, so there is nothing to rebuild the cache **for**. The reseed is the continuation path; a terminal record is where it stops.
- **Every verb, one site.** `add-task` · `add-from-spec` · `provision` · `execute` · `join` · `finalize` · `discard` all pass through the reseed before their own guards, so the refusal (`milestone.terminal`, blocking, exit non-zero) lands at **one** site and none of them can forget it. `list-tasks` left that site at M49 (it re-seeds nothing) and carries the same predicate at its own, read-only: the guard is a pure parse of the record's `status`, so taking the write away did not take the refusal with it.
- **One code, two producers — the milestone's and the sub-task's.** The bullet above is about the *milestone* verbs, and `jigc task discard <sub-id>` is not one of them: its subject is one **item** of a live record. A sub-task the record has already settled (`joined` or `discarded`) whose working area is standing again — an `unwind_area` fault at the task teardown leaves it whole, base pin included — is a **leftover, not live work**, and flipping its item would make the record lie about work that landed. So that door refuses under the same code, keyed on the item's own `status` leaf through the same `item_is_settled` predicate, with its **own** sentence: target `task:<sub-id>`, and a route naming the leftover area to clear by hand. The shipped milestone producer composes message *and* route inside itself and would say *"milestone `<sub-id>` is `joined`"* at `milestone:<sub-id>`, routed at a `milestone-record:<sub-id>` that does not exist — one state, two answers, one of them addressed at a document nobody can open. **The code names the state; the sentence names the unit.**
- **Refused is *operating*, never *reading*.** `list-tasks` is refused along with the rest, and that costs the operator nothing — not because it needs a workbench (since M49 it needs none), but because it is the *operating* surface's enumeration: it names the ids the next `provision` / `execute` / `join` acts on, and a settled milestone has none to act on. The record itself stays fully readable — the finding routes to `jigc doc show milestone-record:<id>`, which serves the settled record, its sub-tasks and their statuses ([doc-read-surface.md](doc-read-surface.md)), and is strictly more than `list-tasks` ever returned. **A milestone that is over is read, not operated.**
- **Drift outranks the terminal.** The verbs that carry the [F3](#engine-capability-1-write--set-on-transition-machine-maintained-leaves) reconcile preflight run it **before** the status is read. A hand edit can write `joined` into the machine-owned `status` leaf, and reading the lifecycle off tampered bytes would announce *"this milestone is over"* about a milestone nobody joined — a route that lies, from the wave that exists to stop routes lying. Drift is diagnosed before the drifted content is interpreted.
- **The id belongs to the record, not the workbench.** `milestone create`'s collision check reads `.jigc/milestones/<id>/`, which is *legitimately absent* on a fresh clone **and** after a terminal op — so it could not see that the id was taken, and re-creating a settled milestone's title **overwrote its committed record** with a fresh `active` one, at exit 0. That destroys a committed record (a *landed* one, in the `joined` case) — the same class of hole through the identity door, so it is closed with the same authority: `create` refuses when a record already owns the slug (`milestone.record-exists`), routing to *continue it* when the record is live and to *pick a different title* when it is settled. **The record's home is asked what its entry is, never what it points at (the rc.24 fix pass, `(R6, D-7)`).** That check was `exists()`, which follows links, so a **dangling** symbolic link at the record's home read as a free id: `create` wrote the record *through* the link and its record-only commit took the **link** — exit 0, a record commit holding no record, the body in an untracked file nothing named. It is the record-side twin of the promote's write-through ([finalize.md](finalize.md#4-promote-managed-docs)), at the one other door that mints a managed doc at its home, and it is closed the same way: the entry is read without following a link, any entry that is not a regular file — a link, a directory — refuses under the same `milestone.record-exists` (the message says what is there, and the route offers no `add-task`, there being no milestone to continue), and the record is written by an exclusive create, which follows no link and fails on an entry that turned up since. **And a home with nothing on disk is a free id only when git holds nothing there either (the rc.24 fix pass, the completion audit's CPL-5).** A committed record deleted from the worktree and not committed as deleted — in a checkout with no workbench for the milestone, which is every fresh clone — read as free, and `create` minted a new record over it: a record-only commit replacing the committed record, task list and all, under its own id at exit 0. The guard now asks git itself what `HEAD` and the index hold at the record's home, by the question both finalize doors ask of a promote destination ([finalize.md](finalize.md#4-promote-managed-docs) → *a home git holds is occupied*), and refuses under the same `milestone.record-exists`: nothing is written, and the route names the aimed `git checkout` that brings the record back — after which the milestone is *continued* — or a different title. **And the doors that write the record afterwards never write it through a link either (the rc.24 fix pass, the store doors).** `add-task`, `add-from-spec`, `milestone discard`, `milestone finalize`'s flip and a sub-task's `task discard` each rewrite a record that already exists, and each first runs the No-silent-overwrite preflight — which compares **bytes**, and bytes are read through whatever stands at the path. So a record replaced by a link to a byte-identical copy read as in sync and was then written *through*: driven, `jigc milestone add-task` exited 0 over a record commit that held the **link**, with the record's new body in the link's untracked target — every other clone handed a record that is not there — and over a *committed* link each door wrote through it, failed its own commit for holding nothing, and reported a hook's complaint. The preflight now asks the record's home for its **own entry, without following a link, before it reads a byte**: an entry that is not a regular file is that door's standing `reconciliation.conflict-block`, keyed at the record's path — a machine-maintained record that is not as jigc left it is never merged, never clobbered, and never written through, whatever the link points at. Nothing is written, minted or committed. The route names both restores: where `HEAD` still holds the record as a file, the `git checkout HEAD -- <record>` it prints (git replaces the entry with the file; it does not write through it); where the entry itself was committed, the record put back as a regular file by hand and committed. The writes behind the preflight are in place and never through a link (`engine::store::rewrite_home`; [finalize.md](finalize.md#4-promote-managed-docs) → the doors that write a committed home in place).

### The store advisory that was chartered and dropped — and why

M42's charter carried a store-scope advisory for *"a `milestone-record` with `status: active` and no live workbench."* **It is dropped, and the reason is worth recording: it was unbuildable, and this doc says so.** [Engine capability 2](#engine-capability-2-read-back--the-committed-record-is-the-engines-authority) designs **exactly that state** as the **fresh-clone continuation** case — *a teammate on a fresh clone re-derives the milestone's shape from the record and resumes un-joined tasks*. An active record with no `.jigc/` workbench is not a symptom; it is the **feature**. The advisory would fire on every legitimately in-flight milestone, on every clone, every teammate, every CI checkout — a false-positive class shipped into the very wave whose claim is *the tool's own routes tell the truth*.

The general lesson: **abandoned-vs-clone-continuable is not locally observable from the committed store.** The workbench's absence carries no information (it is gitignored by *identity*, §The principle). Only a **terminal status** makes the distinction observable — which is precisely what the `discarded` member buys, and why the fix is a schema member rather than a detector.

### What the base-guard is for — the fix, and the real constraint underneath it

The record-only base-guard relaxation (§ The commit model, above) is **scoped by what it exists to prove**, and M42 corrects its scope — then corrects the correction. Both halves are recorded, because the second is the more useful one.

**What it proves.** The guard is the M31 worktree-combine's precondition: a milestone's sub-agent code was staged in worktrees cut from the **pinned base**, so combining them onto HEAD is only sound if **no code moved** in `base..HEAD`. That is the whole question. The relaxation exists because the milestone's *own* record commits move HEAD without moving code — bookkeeping, not work — so blocking on them made the guard un-passable in the very model M39 built.

**What it must therefore accept — the widening (M42, and it stands).** *Any* commit that touches **only milestone-record paths** — **any milestone's**, not just this one's. Another milestone's record is **not code**: it cannot invalidate this milestone's combine base, so the guard has no grounds to reject it. Today it does: `record_only_range` requires every path touched in `base..HEAD` to equal **this** milestone's record path (`crates/cli/src/milestone.rs:483-487`), which rejects a class of commit it was never designed to catch — **record bookkeeping**. So `record_only_range` accepts a range whose touched paths are **all milestone-record paths** (any milestone's).

**What the over-narrow guard produced — verified against the real binary:**

- Two concurrently-live milestones **wedge on bookkeeping alone**: milestone B's ordinary per-op record commits (`create`, `add-task` — commits that move **no code**) land inside A's `base..HEAD` range as foreign paths → `finalize.base-mismatch`, exit 3.
- **Interleaved** creation (A create → B create → A add-task → B add-task) — the shape any real session lands in — wedges **both**: a **symmetric deadlock** over commits that touched nothing the combine cares about.
- It is **silent at the point of no return**: the second `jigc milestone create` exits 0, warns nothing, and says nothing in `--format json`.
- It is **invisible afterwards**: `jigc validate` over a wedged repo reports *no findings — the committed store validates clean*, exit 0. Another false green.
- It is **unrecoverable in-tool**: no jigc verb escapes it, and `git revert` fails for the same structural reason (`--name-only` lists a path that was touched *and then reverted*, so the revert commit itself touches the other milestone's record — predicted verbatim by the comment at `crates/cli/src/milestone.rs:470-471`).

The widening kills exactly that class: **record-bookkeeping** commits stop wedging anything, and a repo wedged *only* by them recovers on upgrade.

**What the widening does NOT buy — correcting a claim this doc made earlier the same day.** An earlier M42 draft of this section concluded that the guard had *"manufactured a phantom product constraint"* and that with the widening *"the wedge class disappears; concurrent milestones stop being a trap."* **The second half is false**, and an independent review of the settled design proved it from the code:

- A milestone finalize that lands any work **commits code** — the per-sub-task commits plus the aggregate promote commit (`crates/cli/src/milestone.rs:1324-1360`) — and an empty diff is itself a hard block (`has_diff == false` → the empty-commit finding, `crates/engine/src/finalize.rs:527`). A *successful* milestone finalize therefore **always touches non-record paths**; the only range that stays record-only is a milestone that landed nothing.
- Milestone B's base is pinned once, at its own `create` (`crates/cli/src/milestone.rs:203`), and is **never re-pinned**. The serial-task re-pin amendment is *consciously* not extended to the milestone sibling (`engine::finalize::decide_base_repin`, which says so in its own doc comment) — a task's footprint is its dirty paths + promote destinations, which the overlap test can see; a milestone's footprint is **code sitting in worktrees cut from the base**, which it cannot.
- So the moment A finalizes, A's **code** commit sits inside B's `base..HEAD` → `record_only_range` returns false → B is `finalize.base-mismatch` **permanently**.

**The real constraint, stated plainly: milestones serialize against landed work.** A live milestone is invalidated by **any** code/doc commit landing after its base — another milestone's finalize, an ordinary `jigc task finalize`, a `jigc rename`, or a human's own `git commit`. **One milestone's work must land before another milestone's base can survive it.** That is the M31 worktree-combine guard doing exactly its job: the sub-agent worktrees were cut from the **pinned base**, and combining them onto a HEAD whose code has moved is precisely the unsound operation the guard exists to refuse. The constraint is **real** — the price of the isolated-worktree fan-out, a property of the design and not a bug in it.

**The route — the actual defect.** What was never true is that the constraint is **routed**. `finalize.base-mismatch` tells the operator to *"switch back to `<A>` or discard the task with `jigc task discard`"* — which on a milestone id returns `no task '<id>'`, exit 1 (verified), and which post-M42 would merely upgrade to *"discard the milestone"*: **throw the work away**. In a wave whose claim is *the tool's own routes tell the truth*, "your only exit is to destroy what you built" is the same disease one level up. The route's obligation (its surface lives in [write-commands.md](write-commands.md) → Abandoning a milestone):

- **Name what happened** — commits landed after this milestone's base, so the base its sub-task worktrees were cut from no longer reflects HEAD, and the combine cannot be proven sound against it.
- **Name the real options, and be honest that both are out-of-band git** (there is no verb for either — see below) — **land the milestone first** (return HEAD to the pinned base, finalize the milestone, re-land the other work on top: available while the landed commits are still local, a history rewrite once they are shared), or **re-cut the milestone's work onto the new base** (re-pin, re-provision the worktrees, re-apply each sub-task's staged patch: always available, and the shape a future verb would automate).
- **Never present `discard` as the exit.** `discard` settles the record of a milestone being **abandoned** (§ [The lifecycle](#the-lifecycle--active--joined--discarded-m42)); it is not a recovery for work you still want, and offering it as the only way out tells the operator to delete their work to satisfy a guard.

**No base re-pin verb is built at M42.** A `jigc milestone rebase` — re-pin the base and re-cut the worktrees — is the shape that would *dissolve* the constraint rather than route it. It is deliberately not built on speculation: chartered as a follow-on, keyed to a trial that demands it (§ [Deferred / flagged](#deferred--flagged-logged-not-forgotten)).

**The lesson — and it is not the one this doc first wrote.** The M42 pass caught a real bug (the guard was one predicate too narrow) and **introduced another in the same motion** (it declared the constraint underneath it phantom). The honest statement is sharper than either: **the guard was one predicate too narrow, *and* the constraint underneath it is real — and both were invisible because the constraint had no route.** The tell was never *"the rule is phantom."* The tell was **"the rule has no route."** A constraint that no design doc asserts, that no message states, and that surfaces only as a permanent block at the end of the work is *unrouted* — and from the outside an unrouted constraint is **indistinguishable from a bug**. That ambiguity is exactly what a route resolves, which is why "route it" is the right first move whether the rule turns out to be real or not: reading the same deadlock, the M42 pass guessed *bug*, was half right, and came within one review of shipping a design doc asserting the trap was gone. The standing rule applies to this correction too — *a recorded rationale is a claim, not a fact* ([DECISIONS.md](../DECISIONS.md) → 2026-07-11); this one was checked against the code by a reviewer who did not write it.

**`milestone discard` depends on the guard widening and ships with it.** Discard's record-settling commit touches **its own** record path — which, in *another* live milestone's `base..HEAD`, is a foreign record path. So under today's narrow guard, discarding B does not clear B's bookkeeping out of A's range: it adds one more foreign-path commit to it, failing for the same structural reason `git revert` does. Discard only clears a record-bookkeeping wedge once the guard accepts foreign record paths. The two land together. *(Discard does not, and cannot, recover a milestone wedged by **landed code** — nothing does; that is the constraint above, and it routes rather than resolves.)*

### The record is not writable through the `jigc doc` verbs

`jigc doc set-field milestone-record:<id>#status --value joined` — with **no `--task`** — exits 0 today: it silently auto-selects the sole live task (a milestone sub-task), copies the committed record into that task's area, and stages it to promote at that task's finalize. The no-silent-overwrite preflight (§ [Engine capability 1](#engine-capability-1-write--set-on-transition-machine-maintained-leaves)) guards *milestone-op* overwrites and does not see this path at all. The result is a **committed record mutated outside the milestone verbs**, by a verb that never consults milestone state.

**The intended protection follows straight from the principle — `.jigc` is the workbench, the repo is the record:** the milestone record is **machine-maintained**, and every one of its leaves is `set:`-bearing (there is no author-owned prose slot and no author-required field — §The `milestone-record` doctype). A doctype with **no author-owned leaf has no legitimate `jigc doc` write** — so the **`jigc doc` write verbs (`create` / `author` / `set-field` / `set-slot` / `add-item` / `remove-item` / `retitle-item` / `reorder`) refuse a `milestone-record` target**, and the finding routes to the milestone verbs. The **read** verbs stay open and unchanged — `jigc doc show` / `doc schema` read the record like any managed doc; that uniformity is the whole reason the record is a doctype rather than a raw-JSON island (§Why this preserves the source-of-truth invariant).

This **completes** a rule the codebase already applies piecemeal: `jigc rename` refuses a milestone-record reslug, and `jigc doc retitle-item` refuses a milestone-record item — both because *the record is machine-maintained through the milestone verbs* ([write-commands.md](write-commands.md) → `jigc rename`, `jigc doc retitle-item`). The other write verbs were simply never enumerated. That is the same **un-enumerated-sibling** failure shape as the `schema.location` census ([storage.md](storage.md) → Placement): a rule stated at two sites and never swept across the family.

## What a fan-out worktree isolates — and what it does not (M45)

The continuation model above rides the fan-out's isolation model, and two properties of that model were never stated anywhere — one a straight design property, one a design property whose *consequences* were mis-recorded as absent ([DECISIONS.md](../DECISIONS.md) → 2026-07-23 M45 planning: the Settle).

**A provisioned worktree carries tracked files only.** `git worktree add --detach` populates from the pinned base's *tree*, so it is tracked-only by construction: a gitignored runtime or vendor directory (`node_modules/`, `vendor/`, a built `target/`) never arrives — while the sub-task walk tells the agent to build the code and run the tests. It belongs beside the model's two already-stated constraints — **WIP-safety** ([finalize.md](finalize.md) → `fan-out` finalize: the combine commits from a clean dedicated worktree so unrelated main-checkout WIP survives) and the **base-pin** (§ [What the base-guard is for](#what-the-base-guard-is-for--the-fix-and-the-real-constraint-underneath-it)) — and it is the same property those two rest on: the worktree is isolated *from* the checkout's untracked state, which is precisely why the runtime deps are absent. Unstated, it reaches the operator as a mystery build failure inside a sub-agent. The fix-shaped half is **surfacing it at provision time**; copying untracked state in would dissolve the isolation the model exists for.

**A half-provisioned milestone is a state of its own, and `jigc milestone execute` is the surface that says so (M49).** `execute` composes the fan-out walk and emitted byte-identical text whether every sub-task's worktree was there, some were, or none were — so a `Spawn: cd .jigc/worktrees/<id> && …` line for a directory that does not exist read exactly like one whose working area is waiting. The trigger is the **partial** set alone, and the reason is that only it carries information: never-provisioned is a settled state whose repair is literally the walk's own first step (`Run: jigc milestone provision …`, which is why the response is an advisory and not a refusal — blocking would refuse the orientation read that teaches the fix), fully-provisioned is the other settled state, and both stay silent, byte-identical reads. A **mixed** set says something neither of them can: a provision ran and did not finish. So `execute` carries one advisory per live sub-task with no usable worktree — each located at its own path, each routed to the idempotent `jigc milestone provision <id>` re-run that reuses what landed and adds the rest — beside the composed walk rather than inside it, so the pinned `{task, text}` contract is untouched ([command-output-contract.md](command-output-contract.md) → Stream discipline). The other half of the same state is the provision that produced it: a failure in the door's **mutating** phase has already put worktrees on disk, so it surfaces as `milestone.provision-failed` naming the path it stopped at, the count that landed, and that same re-run route — where before it was a bare error with no code and no route at all ([DECISIONS.md](../DECISIONS.md) → 2026-08-30).

**The `.jigc` layer is shared across worktrees.** A worktree binds to the **main checkout's** `.jigc` (`crates/cli/src/start.rs` → `require_project_config`, the M31 Inc-2 rule that a worktree resolves the one shared project layer rather than its own absent one). So under a fan-out:

- **isolated** — each sub-task's doc area (`.jigc/tasks/<sub-id>/`) and its own code worktree;
- **shared by all N sub-agents** — `.jigc/state/*` (one `file-state.json`), `.jigc/index/*`, and the milestone's `tasks.json` — i.e. every derived-cache row of § [What graduates](#what-graduates-and-what-stays-wip--the-split-is-field-granular), including the one [Engine capability 2](#engine-capability-2-read-back--the-committed-record-is-the-engines-authority) demotes to a rebuildable derivative of the committed record.

That corrects a **recorded rationale**: v1's no-locking acceptance rests on *"fan-out sub-agents write isolated areas by design"* ([decisions-pending.md](../implementation/decisions-pending.md) → Multi-process concurrency), which holds for the first list and is false for the second — the verification trial ran five parallel worktrees against one `.jigc`. M45 lands the **corruption-removing subset**: the atomic-write temp sibling becomes process-unique, and `FileStateRecord::save` — the one state writer bypassing the shared persist path — is routed through it, so concurrent writers can no longer leave an unparseable shared state file behind. **Lost-update semantics landed at M46 Increment 1**, discharging the deferral this paragraph used to carry: a base-relative three-way merge behind a save-scoped lock for the file-state record, the lock alone for the stamp-rebuildable index, and a reasoned exclusion for `tasks.json` (atomic, unmerged). Those rules are stated once, in [storage.md](storage.md) → Concurrent writers, and are not restated here ([DECISIONS.md](../DECISIONS.md) → 2026-08-18; the superseded deferral is struck at [decisions-pending.md](../implementation/decisions-pending.md) → Multi-process concurrency).

## The read surface — `jigc doc show` + a pinned `--format json` shape

The milestone record is the first doctype whose *primary* consumer is a **machine** read (fresh-clone continuation), so its `jigc doc show --format json` output is a **1.0 stable contract** (a one-way door — pinned now, not left to the first implementation, the review's F6 fix): whole-doc = `{ type, slug, title, item-count, schema-version, fields: { base, status, schema-version }, sections: { tasks: [ { id, task-id, intent, status, workflow }, … ] } }` — the four pinned keys `{ type, slug, fields, sections }` plus every key added since under [doc-read-surface.md](doc-read-surface.md)'s declared evolution posture, which owns that ledger and is not restated here (`fields.schema-version` the M40 additive-pre-pin methodology stamp, the item `id` M42, `item-count` M44, the top-level `schema-version` and the item `workflow` M49, `title` M55). **A witness that under-states the shape it witnesses certifies a narrower contract than the one that ships** — which is what this enumeration did from M42 until M51, unread by anything — so it is fenced against the binary's emitted key set at every level of the shape (`crates/cli/tests/read_contract_witness.rs`). `base` is a **structured object** `{ sha, short }` (the compound base pin — clean lossless machine access to both SHAs, resolving the Inc-3 audit advisory that flagged the space-joined scalar; the committed `.md` still stores `base: <sha> <short>` as a scalar line, so this is json-projection-only — [DECISIONS.md](../DECISIONS.md) → 2026-07-07) and every other field is a scalar; a `#tasks` slice returns the item array; the `status` enum serializes as its lowercase string. Pinned in the doc-read-surface design; the milestone record is its conformance witness.

## Interactions

- **`jigc doc show`** reads the record like any managed doctype — the uniformity dividend; the reason (c) beats a raw-JSON island.
- **Reconciliation** ([reconciliation.md](reconciliation.md)) — an OOB edit is detected + **conflict-blocked** (not merged; §capability 1).
- **The relocation floor** (M39) — the record rode the freeze-exempt detect+route floor *at M39* (no version-gate); **since M40** it is a methodology-manifest member, so a home change version-gates like any manifest member and `jigc relocate` refuses it ([corpus-migration.md](corpus-migration.md) → the M40 revision).
- **No managed edge** — `milestone-record → task`/`roadmap-entry` are not minted (task-ids stay strings; the M16 "no per-entry managed ref until a driver earns it" bound holds).

## Deferred / flagged (logged, not forgotten)

- **Standalone task-record** — parked, validate-first ([ideas/task-record-graduation.md](../ideas/task-record-graduation.md)).
- **`jigc milestone rebase`** — the verb that would *dissolve* the serialization constraint (§ [What the base-guard is for](#what-the-base-guard-is-for--the-fix-and-the-real-constraint-underneath-it)) instead of routing it: re-pin the base and re-cut the sub-task worktrees onto the new HEAD. **Not built at M42** — the constraint routes honestly, and a re-cut is a real transaction (uncommitted sub-task WIP, per-worktree replay, a fresh combine base) that no evidence yet demands. **Trigger:** a trial in which the block is hit on work the operator still wants — i.e. the route fires and its named options are all unacceptable ([decisions-pending.md](../implementation/decisions-pending.md)).
- **Planning-gate-record reopen** — if a planning workflow is (re-)encoded to *read* the record, the condition-keyed planning-gate-record deferral may fire; flagged, not triggered by M39.
- **Config-layer / per-developer `local` distribution** stays deferred (that is *config* distribution; this is *state* legibility). The record's stored shape must not pre-decide it.
- **Concurrent-OOB-during-a-fan-out** over the committed mutating record inherits the existing concurrent-OOB deferral bound ([decisions-pending.md](../implementation/decisions-pending.md)) — not a new promise.

## Acceptance (the M39 decomposition owns the increment cut)

On a `[dev ▸ methodology]` repo: `jigc milestone create` → `add-task` ×2 → the committed `docs/milestone-records/<id>.md` carries the base pin + both sub-tasks' `id`/`intent`/`status: active` as a repeatable section, each op a path-scoped record-only commit that leaves unrelated staged/untracked WIP untouched; `join` flips both items' + the header `status` to joined **byte-stable** (folded into the join commit); a **fresh clone** (delete `.jigc/`) re-derives the cache from the record and `jigc doc show milestone-record:<id> --format json` returns the pinned shape; an OOB edit to a `status` field is **conflict-blocked** at the next op (not silently overwritten); a stale base-SHA (rewritten-away pin) routes to the human, not corruption.
