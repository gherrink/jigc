# Multi-pack composition

How one project composes **more than one domain pack at once** — the embedded **dev** pack and the M12 **methodology** pack — without the engine learning about either. This is the generalization of [VISION.md](../VISION.md) principle #3 (*engine-neutral; packs supply content*) from internal discipline to validated architecture: the `pack-default` layer of [the cascade](overrides.md#the-cascade) stops being **one** pack and becomes an **ordered set** of packs, with deterministic collision resolution where two packs declare the same id.

Builds on [overrides.md](overrides.md) (the cascade this composes *inside* — `project > team > pack-default`; the 9-phase [resolution algorithm](overrides.md#resolution-algorithm) whose **phase-2 by-id shadowing** this extends; the [provenance header](overrides.md#the-cascade) it widens; the `FilesystemPack`/`JIGC_PACK_DIR` [seam](overrides.md#upgrade-reconciliation--override-default-m5) it generalizes), [self-hosting.md](self-hosting.md) (the methodology pack this co-composes — the M12 *subsume* that created the real overlap, and the M14 seam it names), [workflow-dialect.md](workflow-dialect.md) (`{{include: step:…}}`, whose resolution becomes pack-local), and [validation.md](validation.md) (`workflow-refs`, the engine-native probe that already adjudicates same-id collisions *within* a layer). Notation is **illustrative** — the docs cited are the source of truth. For the *why*, see [DECISIONS.md](../DECISIONS.md) (2026-06-08).

> **Scope bound (M14).** Compose **our two packs only** (dev + methodology). The precedence/collision **mechanism is inherently general** — it cannot honestly be cut to a two-pack special case — but it stays **internal: not published or stabilized as a public pack-authoring API**. [VISION.md](../VISION.md)'s *"not a second domain / not a public extension API"* non-goal holds at that **publication** line, not the generality one. What ships in M14 vs. what is deferred-with-trigger is pinned in [Scope and deferrals](#scope-and-deferrals) below.

## Why this is its own doc, not an `overrides.md` elaboration

[overrides.md](overrides.md) owns *deltas over a versioned base* — how a **project** customizes a **single** pack. Multi-pack composition is a different concern one altitude *below* it: how the `pack-default` **base is itself assembled** from N packs *before* any project delta applies. It introduces a **second ordering axis** (pack-precedence *within* the pack-default layer) that the cascade's specificity ordering (`project > team > pack-default`) does not model, and it is a **base-construction** step, not a delta kind. Folding it into the deltas-and-cascade doc would conflate two systems overrides.md is careful to keep distinct. So it earns its own doc (the [doctype-map / M13 doc-home precedent](../CLAUDE.md): a first-class new mechanism gets its own home; an in-model elaboration stays put). It **cross-references** overrides.md heavily and **reads after** it — the cascade vocabulary must be in hand first.

The load-bearing relationship: multi-pack composition produces **one** `PackDefaultLayer` from the pack-set, and the existing [9-phase resolution algorithm](overrides.md#resolution-algorithm) then runs **unchanged** over that layer. The cascade does not learn about packs; it receives a pre-merged base, exactly as it does today.

## The pack-set — base plus listed packs

The `pack-default` layer is an **ordered set of packs**, highest-precedence first:

1. **Listed packs** — named in a new project-config setting **`.jigc/config/packs:`** (an ordered list of pack directories), read at **pack-assembly time** — *before* the cascade resolves, because the packs *are* the base the cascade resolves over. Earlier in the list = **higher precedence**. This setting is a **pre-cascade pack-assembly input** (its own `.jigc/config/packs.yaml` resource read by the pack-source factory): it is **not** a cascade knob and **not** subject to the closed `knobs.yaml` surface — it cannot be, since knobs are resolved *by* the cascade this bootstraps (routing it through `resolved.scalar()` would reject it as `UndeclaredScalar`). It stays a literal directory list, deliberately off the public-pack-API line ([Open questions](#open-questions)).
2. **The base pack** — the pack the binary already selects today: `JIGC_PACK_DIR` if set, else the compiled-in `EmbeddedPack` ([overrides.md](overrides.md#upgrade-reconciliation--override-default-m5) → the `FilesystemPack` seam). The base sits **lowest** (implicitly last), so it is the foundation every listed pack composes on top of.

```yaml
# project .jigc/config/packs.yaml  — the ordered pack-set (highest-precedence first)
packs:
  - /opt/jigc-packs/methodology     # wins same-id collisions against the base
# (the embedded dev pack is the implicit base below this list)
```

So a **methodology-driven** project that also wants the dev pack's richer doctypes (`adr` / `spec` / `arch-doc`) and workflows (`single-task` / `router` / …) lists `methodology` and keeps the embedded dev pack as base: methodology wins where they collide, dev supplies everything methodology doesn't.

**Cold-start = today, byte-for-byte (the floor).** When `.jigc/config/packs:` is **absent or empty**, the pack-set is exactly `[base]` — a single pack — and composition is **byte-identical** to the current single-pack path. This is the most important regression to hold ([M13 cold-start discipline](../implementation/milestone-planning-workflow.md)): the multi-pack machinery must add **zero** observable change to a one-pack project. The acceptance pins it ([flow 17](worked-examples.md#17-multi-pack-composition--dev--methodology-co-composed-m14), assertion 1). The M12 *compose-alone* path (`JIGC_PACK_DIR=<methodology>`, no listed packs) is exactly this single-pack floor with the base swapped — so the methodology pack's "composes alone" regression tests stay green untouched.

## Collision resolution — precedence-override, whole-definition

When two packs declare the **same id**, the **highest-precedence pack's whole definition wins** — the same *whole-file shadow* model the cascade already uses when a project shadows a pack definition ([overrides.md](overrides.md#authored-metadata-on-a-definition-resolves-by-whole-file-shadow)). **No field-level merge across packs** — a definition shadows or it doesn't, the same invariant overrides.md holds for layers ([overrides.md](overrides.md#what-the-algorithm-does-not-do)), now extended to the intra-pack-default pack axis. This is the minimal honest choice: it reuses a mental model already in the product and introduces **no new merge primitive**.

Per id-space, against the real dev × methodology overlap ([self-hosting.md](self-hosting.md) → the subsume):

| id-space | overlap | resolution |
|---|---|---|
| **workflow** | ∅ (`dev-task` is methodology-only; dev's 10 are dev-only) | union — both packs' workflows compose; no collision |
| **step** | `implement`, `finalize` (same id, **divergent** bodies) | **pack-local** — a workflow's `{{include: step:X}}` resolves to *its own* pack's step; no top-level winner-takes-all — see [Pack-local body-references](#pack-local-body-reference-resolution-a-correctness-rule-not-a-policy) |
| **command** | `set-commit-summary`, `finalize-task` (identical); methodology has 5, dev 11, **not mutual supersets** | **pack-local** — a workflow's `{{cli.X}}` resolves against *its own* pack's `commands.yaml`; same rule as steps |
| **doctype** | `commit` (**divergent** — methodology dropped `implements→spec`) | precedence-winner's whole schema wins (both proven compatible — below) |
| **knob** | all 25 keys; 24 identical, **`default-workflow` divergent** (disjoint enums) | precedence-winner's whole `knobs.yaml` wins (whole-file shadow) — below |
| **field-type** | ∅ ids (methodology ships none) — but dev doctypes *use* `code-anchor` | **schema-pack-local** — a schema's declared field-types resolve from *its own* pack, so dev's `spec`/`arch-doc`/`adr` see dev's `code-anchor` even in a methodology-primary project; same pack-origin rule as body-references |

The **selectable-workflow catalog is the union** of both packs' workflow files (they don't collide), independent of the knob resolution — so `jigc start --workflow single-task` works in a methodology-primary project even though `default-workflow` resolves to `dev-task`.

### The sharp case — `default-workflow`'s disjoint enums

The dev pack declares `default-workflow: {of: [router, single-task, quick-fix, plan, implement-from-spec], default: router}`; methodology declares `{of: [dev-task], default: dev-task}`. The two `of:` sets are **disjoint**, and the resolved `default-workflow` must be a **single** value that names a workflow the composed pack actually ships ([self-hosting.md](self-hosting.md) records why methodology *had* to rewrite the enum — a value outside `of:` fails compose).

Under **precedence-override (whole `knobs.yaml` shadow)**: the highest-precedence pack's `default-workflow` declaration — enum **and** default — wins outright. In a methodology-primary project (`packs: [methodology]`), the resolved `default-workflow` is `dev-task` (enum `[dev-task]`), so a bare `jigc start` composes the methodology dev-task loop. The 24 identical severity/squash knobs resolve to the same bytes either way (the shadow is inert for them).

**The accepted consequence (recorded honestly):** the winner's enum **constrains** what the project layer may then set `default-workflow` to — a methodology-primary project cannot set the default to `single-task` without a project override the `[dev-task]` enum would reject (dev's `single-task` stays *invocable* via `--workflow`, just not *defaultable*). This is the inherent cost of precedence-override over **union**; it is acceptable for the bounded two-pack slice (the project chose its primary pack). Union of the closed `of:` sets — which would let either pack's workflow be the default — is the **first** field-level merge-across-packs primitive the cascade has ever had; it is **deferred** ([Scope and deferrals](#scope-and-deferrals)), reserved for a recurring real need, exactly as overrides.md reserves field-granular metadata merge.

### Why the `commit` doctype collision is safe either way

Both packs ship `commit`, divergent by one field: dev's carries `implements: {type: ref, to: spec, card: "0..1"}`; methodology's dropped it ([self-hosting.md](self-hosting.md) → the M12 audit). Whichever wins is **compatible** with both packs' commit-authoring, verified at Settle against the real validator:

- methodology's `dev-task` fills only `{type, scope, summary, body}` — a strict **subset** of *both* schemas, so it authors cleanly against either.
- dev's extra `implements` is **not author-required** (`card "0..1"` → `is_author_required` returns false, `crates/engine/src/validate.rs`), so a methodology task that never binds a spec passes finalize against dev's schema.

So the `commit` collision is **determinism-policy, not correctness** — precedence-override picks one deterministically and both choices work. In a methodology-primary project methodology's (subset) `commit` wins; the recorded consequence is that dev's `implements→spec` edge is **shadowed** in that composition (a spec-driven dev workflow could not bind `commit.implements` there), **and** dev's `implemented-by` inverse edge to `spec` is likewise un-registered — inert, because `schema-completeness.inverse-cardinality` is advisory/store-scope and `spec` carries no own-side `implemented-by` field ([validation.md](validation.md)). Accepted — the project chose methodology as primary; this is the same precedence-vs-union tradeoff as `default-workflow`. (A dev-primary ordering would keep `implements` and lose the `dev-task` default — the symmetry confirms it's a policy pick, not a defect.)

## Pack-local body-reference resolution — a correctness rule, not a policy

This is **distinct** from the user-facing collision policy above and is **load-bearing for correctness**. It governs the two reference kinds a composed definition emits *from within its body*: **`{{include: step:X}}`** (the steps it expands) and **`{{cli.X}}`** (the command-refs it renders). Both must resolve against the **defining workflow's own pack**, never a merged surface.

**Steps.** Methodology's `dev-task` body is `{{include: step:implement}}` meaning *methodology's* test-first `implement`; the dev pack ships a **different** `step:implement` (direct-edit). If includes resolved against a **globally-merged** step namespace where the precedence winner owned `step:implement`, then in a *dev-primary* ordering methodology's `dev-task` would silently compose **dev's** implement body — injecting the wrong discipline into the wrong workflow. The M3-class silent corruption.

**Command-refs (the same hazard, a second resource).** The command catalog (`config/commands.yaml`) is a **whole-file** pack resource, and the two packs' catalogs are **not mutual supersets**: methodology vendored only the 5 command-refs its `dev-task` uses (`set-commit-type/scope/summary/body`, `finalize-task`); dev ships 11 (incl. `create-adr`, `validate-task`, `bind-spec`, …). So a *whole-file precedence-override* of the catalog would strip the loser's workflows of their `{{cli.X}}` — dev's `single-task` emits `{{cli.create-adr}}`, absent from methodology's catalog → it fails `workflow-refs.command-ref-resolves`; methodology's `dev-task` emits `{{cli.set-commit-type}}`, absent from dev's → symmetric break. Exactly the steps hazard, one resource over.

**The rule (both kinds): a workflow's body-references resolve against the catalog/steps of the pack that *defines the workflow*** — `{{include: step:X}}` against that pack's steps, `{{cli.X}}` against that pack's `commands.yaml` — never the merged surface. Methodology's `dev-task` always gets methodology's steps **and** command-refs; dev's `single-task` always gets dev's. So the `commands` and `steps` resources are **never** precedence-shadowed across packs; only the *user-facing top-level* definitions (which `commit`, which `default-workflow`, which workflows the catalog lists) resolve by precedence. The two are **independent axes** — a pack may lose a top-level collision yet still resolve its own workflows' bodies correctly.

**Field-types are the same rule, one definition kind over.** A doctype schema declares fields of pack-provided types (dev's `code-anchor`); the type name is a body-reference resolved from the **schema's own pack**. So in a methodology-primary project, loading dev's `spec`/`arch-doc`/`adr` resolves their `code-anchor` from **dev's** `field-types.yaml` — even though methodology (the precedence winner) ships none. Without this, "dev's doctypes co-compose" ([flow 17](worked-examples.md#17-multi-pack-composition--dev--methodology-co-composed-m14) assertion 4) would break the moment a dev doctype with a pack-field-type is loaded. This is **in scope** (it is correctness for *composing* both packs, not the deferred *probe-collision* case — methodology ships no field-type, so nothing collides; the requirement is only that a schema sees its own pack's types). Today `pack_field_types(pack)` (`crates/cli/src/pack.rs`) reads one pack; the pack-of-origin scoping extends to it.

So three definition-body reference kinds resolve **pack-locally** (against the defining definition's pack): a workflow's `{{include: step:X}}`, a workflow's `{{cli.X}}`, and a schema's field-type names. Only the *user-facing top-level* ids (which `commit`, which `default-workflow`, which workflows/doctypes the menus list) resolve by precedence. The check surface follows: **`command-ref-resolves`, the include/cycle checks (`workflow-refs`), and field-type resolution fire per-definition against that definition's own pack** — a methodology `dev-task` (or a dev `spec`) referencing something its own pack doesn't ship is an authoring error *in that pack*, caught exactly as a dangling reference is today. Today these resolvers (`CascadeStepSource::step`, `load_catalog` → `read(Config, "commands")`, `pack_field_types`) do flat single-pack reads with **no pack-of-origin**; the new capability M14 builds is the pack-of-origin scoping for all three, while the composite source still resolves top-level definitions by precedence.

**The boundary — pack-local is for *pack*-authored bytes; project/team references go through the cascade.** "The defining pack" is well-defined only for a definition authored in a **pack's** workflow/step/schema bytes. A **project**- or **team**-layer override is *not* pack-authored: a project that shadows `workflows/dev-task.yaml` or `insert`s a `step:implement` delta authors bytes that belong to **no** pack. Those references resolve through the **normal cascade layer semantics** ([overrides.md](overrides.md#resolution-algorithm) — phase-2 by-id shadowing, project > team > the composed pack-default), *not* pack-locally. And a project structural delta whose target id is *itself* a cross-pack collision (which pack's `step:implement` does `replace workflow:dev-task#implement` target?) is exactly the **reconciliation-over-a-composed-base** case [deferred below](#scope-and-deferrals) — M14's flow 17 layers no project structural delta over the composed packs, so the bounded slice does not resolve it. The pack-local rule is scoped to pack-authored references; the project/team-over-composed-base surface is deferred-with-trigger.

## Where it sits — a pre-merge step, the cascade untouched

The collision resolution is a **new pre-merge step** that runs at pack-assembly time and produces a **single** `PackDefaultLayer` from the pack-set. The existing [`cascade::resolve`](overrides.md#resolution-algorithm) then runs **unchanged**: it still receives one pack-default layer with one flat scalar surface and a file-owner map. This keeps the blast radius off the cascade core — `resolve` and `PackDefaultLayer`'s *shape* need not change; what changes is **how the layer is built** (from N packs with collision resolution) and the **provenance it carries** (below).

Concretely (illustrative): the single-pack `make_pack()` factory (`crates/cli/src/pack.rs`) generalizes to assemble an **ordered composite `PackSource`** — `read(kind, id)` returns the precedence-winner's bytes; `list(kind)` returns the union **deduped-by-id then sorted** (byte-identical to a single pack's existing sorted `list()` contract, so the `[base]` path and any union both emit ids in stable sorted order — the floor depends on this); a **pack-scoped** read serves the pack-local body-references (steps + command-refs). Every production call site keeps the same `&dyn PackSource` it holds today — the composite hides behind the existing trait object, so the 22 call sites do not ripple. The pre-merge resolver that flattens the pack-set's knob surfaces into one closed scalar map (whole-`knobs.yaml`-shadow winner) is the substantive new engine code.

## Embedded second pack + setup auto-wiring (M21)

M14 composes a **`FilesystemPack` (absolute path)** over the embedded base — proven, but it needs the pack present on disk and a hand-authored `packs.yaml`. **M21 makes the methodology pack reach a real project on a clean `cargo install`** by embedding it *in the binary* as a **second `EmbeddedPack`** and composing it automatically at `jigc setup` — so a fresh project gets vision→milestones→MVP out of the box without staging any pack tree or hand-writing config. Design home for the embed/extract mechanism: [module-layout.md](../implementation/module-layout.md) → Pack distribution.

**Two embedded packs, composed dev-highest.** `EmbeddedPack` becomes **field-carrying** (selecting which `&'static Dir` — a second `include_dir!` carries the ~45KB methodology tree; pure data, no `target/` bloat — contrast the M20 probe lesson). The pack-source factory composes `CompositePack([dev, methodology])` with **dev at higher precedence** — the *inverse* of the listed-pack convention (listed > base), chosen deliberately and spiked against the binary (2026-06-14). Dev-highest is what makes the two real collisions resolve the way a real project needs, **with zero pack-data edits**:

- **`knobs` (`default-workflow`)** — dev wins the whole-file shadow → `default-workflow = router`, so a bare `jigc start` lands on the **selection menu** (the vision + MVP on-ramp — `project-setup`, `single-task`/`dev-task`, …), not methodology's `dev-task`. This is the M21 on-ramp ([DECISIONS.md](../DECISIONS.md) 2026-06-14). **The router catalog does *not* surface `planning`** (it lists only `selectable` workflows; `planning` is deliberately off-router, [methodology-docs.md](methodology-docs.md)) — so the milestone half of the on-ramp is delivered by **orientation route-prose** (the G6 off-catalog discoverability surface, [project-setup.md](project-setup.md) → Flow 2 hardening), not the router menu. Dev winning `knobs` is safe because the two `knobs.yaml` files differ on **only** `default-workflow` (every severity/squash knob is byte-identical), so methodology's workflows lose no knob value when dev's whole `knobs.yaml` wins.
- **`commit` doctype** — dev wins → the composed `commit` **keeps `implements→spec`**, so a spec-driven task can still bind the edge (methodology's `dev-task` authors a strict subset `{type,scope,summary,body}`, so it composes cleanly against dev's superset schema — `implements` is `card "0..1"`, never author-required).
- **methodology's surface is union, not shadowed** — `roadmap`/`planning`/`decisions-log`/… don't collide with dev, so they all compose; and methodology's `dev-task` body still resolves **pack-locally** to *its own* test-first `step:implement` (the [pack-local rule](#pack-local-body-reference-resolution-a-correctness-rule-not-a-policy) — `origin_pack` anchors body-refs to the defining pack, independent of who won the top-level collision).

So the **methodology-primary** ordering this doc describes above (`packs: [methodology]` → methodology wins → `default-workflow=dev-task`, `commit` drops `implements`) and the **dev-primary** ordering M21 wires at setup are **both valid compositions of the same mechanism** — the precedence *order* is the only difference, and it is a deliberate per-configuration choice, not a defect. Methodology-primary stays the self-hosting dogfood's ordering ([self-hosting.md](self-hosting.md), unchanged); dev-primary is the new-project setup default. The "accepted consequence" tradeoffs recorded for methodology-primary (winner's enum constrains the override; `implements` shadowed) **do not bind the M21 setup path** — dev-highest simply wins them the favorable way.

**Opt-in by a setup-written marker, so the single-pack floor holds.** The two-embedded-pack composition fires **only when `jigc setup` has wired it**. The marker is **a key in the existing `.jigc/config/packs.yaml`** — `compose-embedded-methodology: true` — which the pack-source factory **already reads pre-cascade** at `make_pack()` (the `discover_pack_list` CWD-walk to the repo root, `crates/cli/src/pack.rs`), so **no new discovery walk** is added: the factory reads the same file it reads today, and on that key composes `[dev ▸ methodology]` from the two in-binary trees. Absent the file or the key, the pack-set is exactly `[dev]` — **byte-identical to today** — so every existing dev-only test and the M14 single-pack byte-identity floor stay green untouched. The marker carries **no path** (both packs are in-binary), which sidesteps the M14 `packs.yaml` CWD-relative-path landmine ([decisions-pending.md](../implementation/decisions-pending.md) — relative paths resolve against process CWD) entirely.

**Bounded:** M21 supports the marker (→ the embedded `[dev ▸ methodology]` pair) **or** a hand-written `packs:` list of filesystem packs (the M14 path), but **combining the marker with additional listed packs is out of M21 scope** — the precedence of listed filesystem packs *relative to* the two embedded packs is a deferred composition (it reopens the finer-precedence-control deferral, [Scope and deferrals](#scope-and-deferrals)); the M21 live test wires only the marker. The embedded methodology pack's `pack_version` ties to the **binary release** (same invariant as the embedded dev pack), not its own `defaults.yaml: 0.1.0`, so override-reconciliation keys both embedded packs to one version. *(The methodology tree is ~45KB of YAML across 39 files — block-allocated ~184K on disk, but the embedded bytes are the content size; no `target/` build-tree, so the M20 bloat lesson does not apply.)*

## Provenance under N packs

[overrides.md](overrides.md#the-cascade) makes cascade provenance a **hard determinism contract** — *the resolved cascade is a declared input; hidden cascade variance is the failure this discipline prevents.* With N packs that contract widens: the orientation/`--explain` header must show **every composed pack** and, where a collision was adjudicated, **which pack won**. The single `Pack: <id>/<version>` segment becomes the composed set (illustrative): `Pack: methodology/0.1.0 ▸ dev/0.0.0` (highest-precedence first).

**A listed pack's id/version is not its identity — its path and content are.** Unlike the single compiled-in pack, a `.jigc/config/packs:` entry is a literal **directory** ([the pack-set](#the-pack-set--base-plus-listed-packs)): two different packs can share an `id/version`, and a directory's contents can change between runs. So id/version alone in the header would *hide* the real input — the exact failure the contract forbids. The compact orientation header stays `id/version` for readability, but **`--explain` surfaces each composed pack's resolving directory path and a content hash** (blake3 over the pack's bytes — the hashing primitive already in use), alongside each resolved collision's winner and the existing per-key override provenance + rejected-scalar-set lines. Showing the winner *and* the exact pack input is **how flow 17 demonstrates determinism** — in scope, not deferred (a deterministic outcome whose basis the human cannot *see* would violate the very contract the header exists to serve).

## Scope and deferrals

**In M14's bounded slice:** the composite pack-source + ordered pack-set; the `.jigc/config/packs:` selection surface; per-id-space precedence-override collision resolution (doctype + knob); **pack-local body-reference resolution** for all three kinds (`{{include: step:X}}`, `{{cli.X}}`, schema field-types); the multi-pack provenance header (naming each pack + path + content-hash + each collision winner); the single-pack **byte-identity floor**; the dev × methodology acceptance ([flow 17](worked-examples.md#17-multi-pack-composition--dev--methodology-co-composed-m14)).

**Deferred — with triggers** (recorded in [decisions-pending.md](../implementation/decisions-pending.md), not lost):

- **Union of colliding closed enums** (`default-workflow.of`) — the first field-level merge-across-packs primitive; precedence-override suffices for two packs. *Trigger:* a real, **recurring** need for a composed project to default to either pack's workflow.
- **Override-default + upgrade reconciliation over a *composed* base** — the M5/M6 probe re-reads the base pack-direct and keys `base-hash`/`base-version` to a **single** pack ([overrides.md](overrides.md#upgrade-reconciliation--override-default-m5)); a project delta recorded against a multi-pack base has no pack-id in its recorded basis, so clean/conflict/orphaned classification is ambiguous across packs. This also subsumes the long-pending **`override-default` content-target check** (which "revisits with a future multi-workflow pack" — [decisions-pending.md](../implementation/decisions-pending.md); M14 *is* that trigger, and the answer is: defer the reconciliation generalization, since flow 17 does not layer a project override over the composed packs). *Trigger:* a project records a delta against a multi-pack-composed base, or a real upgrade of a composed pack.
- **Cross-pack probe / field-type *collision*** — schema-pack-local field-type *resolution* (a dev doctype seeing dev's `code-anchor`) is **in scope** ([above](#pack-local-body-reference-resolution-a-correctness-rule-not-a-policy)). What is **deferred** is the *collision* case: two packs each shipping a `field-types.yaml` declaring the **same** type id, or each shipping a probe program — the `doc-code` probe is resolved single-sourced (`crates/cli/src/invoke.rs`) and there is no probe-program registry across packs. In the bounded slice **methodology ships no probe and no field-type**, so nothing collides. *Trigger:* a second pack ships its own `field-types.yaml` (same-id type) or probe.
- **Finer pack-precedence control** (e.g. placing the embedded base *above* a listed pack, or per-id-space precedence) — the bounded slice fixes the base lowest. *Trigger:* a real composition the base-lowest model cannot express.
