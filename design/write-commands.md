# Write-command vocabulary

The verbs through which the agent (and humans) put content *into* document instances via the CLI — the write side of [VISION.md](../VISION.md) principle #3 (the CLI is the only interface for reads *and* writes). The addressing, unit kinds, override ladder, and validation framework these verbs build on are dialect-neutral and specified in [structural-grammar.md](structural-grammar.md); the `slot`/`field`/`relation` leaves they target are in [document-type-schema.md](document-type-schema.md). **Read those first.**

Scope: the **write layer** only. The override layer (customizing a *type*) is its own future part-doc. For the *why*, see [DECISIONS.md](../DECISIONS.md). Notation is **illustrative**; the on-disk format is an open question (the form-marker syntax open was resolved at M24 — the batch path is declarative whole-doc, below).

## Write layer vs override layer

Two layers share the address model but have different verbs and act on different things:

- **Write** fills *instances* — `slot`/`field` values, and items in repeatable sections.
- **Override** customizes *types* — inserting / replacing / removing sections in the schema ([structural-grammar.md](structural-grammar.md#override)).

`remove`-ing a section from a *type* hits every instance; you can't remove a schema-defined section from one instance without breaking the contract. So the layers stay distinct. The only per-instance structural variation is repeatable-section items — which is why those are write-layer verbs.

The guarantee that makes this safe: **the agent addresses content by name; the CLI does the placement.** Placement-safety comes from address-keying, not from how coarse or fine the verbs are — so the vocabulary can be ergonomic without ever letting the LLM place anything.

## The verbs

**Write primitives** — `jigc doc <verb> <addr>`:

| verb | targets | content handoff |
|---|---|---|
| `create <type> --title …` | — (mints the instance) | id-source inline (the flag is literally `--title` — see *The argument convention*, below) |
| `set-slot <addr>` | a `slot` leaf | **stdin** (`--from-file -`, or a path) |
| `set-field <addr>` | a `field` leaf | **inline** (`--value …`); validated |
| `add-item <section-addr> --title …` | a repeatable section | id-source inline (likewise literally `--title`) → returns the item address |
| `remove-item <item-addr>` | an item | — |
| `retitle-item <item-addr> --title "<new>"` *(M40)* | an item's heading — its `id-from` field | inline (`--title …`); the `{#id}` anchor frozen |
| `rename <addr> --to "<new>"` *(M48)* | a staged doc's `# H1` — and its slug while the identity is uncommitted | inline (`--to …`, `--slug` overrides the mint) |
| `reorder <section-addr> --order …` | the item ordering list | deterministic edit of the ordered list |

**Lifecycle** — a task is born at `jigc start` (see [Task origination](#task-origination)) and then managed with `jigc task <verb> <id>`: `bind` (bind an existing committed doc to a context role — see [Binding a context role](#binding-a-context-role)) · `diff` (see the working changeset) · `validate` (check it — the preview of the gate up to the commit) · `finalize` (validate + the commit-time gates + commit) · `discard` (abandon).

**Every mutating verb acknowledges (M42).** `jigc task bind` and `jigc task discard` both mutate durable state — one records a binding, one deletes a working area — and both print **nothing at all** on success, in **every** format: no line, no JSON. An agent cannot tell a successful discard from a no-op, and a driver gets an empty stdout on a state change. They gain a **one-line success ack + the `--format json` envelope**, like every other mutating verb — the ack shape (the decomposed op + `target` + `findings`-as-data) is pinned in [command-output-contract.md](command-output-contract.md) → Write-acks; this doc only records that the two lifecycle verbs are **in** that surface, not outside it.

**Read verbs** — `jigc doc show` (a committed doc or a slice of one), `jigc doc schema` (a doctype's shape), and **`jigc doc list` (M42)** — the managed-corpus index: the doctype's committed instances by **identity**, not by path (the only enumeration surface today is `jigc ingest`, which lists *git candidates* by path and is a **mutating** verb, so an agent asking "what ADRs exist?" has nothing to call). All three are read-only, take no `--task`, and never touch a working area; their output contracts and evolution postures are [doc-read-surface.md](doc-read-surface.md)'s, not this doc's.

**Batch authoring — `jigc doc author <doctype> --from-file <payload>` (built at M24; the per-leaf primitives above are the floor).** Authoring a large instance one leaf at a time is hundreds of round-trips at scale (a 50-release changelog migration); the batch path collapses it. The chosen shape is a **declarative whole-doc** payload, not an emit-fill-extract form: the **agent authors one structured payload** describing the whole instance (its sections, items, and slot/field values — owning the prose), and the **CLI applies the equivalent `create` + N `add-item` + `set-slot`/`set-field` sequence over a single in-memory buffer**, persisting **once** at the end (rollback = discard the buffer; persist only on full success). **Implementation is pinned to the chain-the-existing-primitives path** ([DECISIONS.md](../DECISIONS.md) → 2026-06-16, review B1): the create runs through the same `create_gated` path (so the **create-gate is enforced** and the **in-location-squatter blank-seed fix applies** — both live in `state::create`), then each `add-item`/`set-*` splice primitive (each a pure source→source transform) is chained over the running buffer with **no persist between leaves**. This is exactly the per-verb chain M23 proved byte-stable, **minus the intermediate persists (which are byte no-ops)** — so byte-stability, the create-gate, and the squatter seam are all inherited unchanged. It deliberately does **not** build an `Instance` and `render` it (that canonicalizing re-emit would bypass the splice primitives' byte-preservation *and* the create-gate / squatter seams). The determinism boundary is unmoved: the **agent authors the payload** (the prose + which-content-goes-where), the **CLI places every leaf** (the agent still places nothing). The payload's slot/field values use the settled `<<slot>>`/scalar conventions; a corrupt payload is rejected whole (atomic), never half-applied. This **supersedes** the earlier "fillable form (`jigc doc edit` emit-fill-extract)" sketch — that was scoped for multi-*slot* single docs and had no story for repeatable-item expansion (adding the Nth item to a section), which is exactly the migration-at-scale need ([DECISIONS.md](../DECISIONS.md) → 2026-06-16 M24 planning). The batch is **doctype-general**; migration is its first heavy consumer.

**The four-way write over a *committed* doc, the item collision (M47), and the title (M48).** `author` over an already-committed instance copies the committed body in as the edit base ([corpus-migration.md](corpus-migration.md) → the copy-in contract) and then does exactly four things, which the authoring surfaces must state together because an agent meets the last two by surprise: a payload item the doc does **not** hold is **appended** (the committed items are byte-untouched); an existing **doc-level leaf** re-authored in the payload **overwrites in place** (`set_slot`/`set_field` semantics, unchanged); a payload item whose title mints an id the doc **already holds** is **refused** — `write.already-present`, and because the chain persists once at the end, the refusal rejects the **whole payload** and stages nothing (the `create_gated` pre-image is rolled back too); and it does **not rewrite the doc's own title** — which, until M48, it acked success over. The recovery for the third is to edit that item in place (`set-slot`/`set-field`), which is what `write.already-present`'s route has always said; what was missing until M47 is any surface *stating the rule before the write* — the four methodology `author-*` steps and `jigc doc author --help` stated the append half alone, which reads as "re-authoring is safe" ([surface-contract.md](surface-contract.md) → law 3, the ambush class; [DECISIONS.md](../DECISIONS.md) → 2026-08-08 M47 Inc 10 T7). Note the collision is adjudicated on the **minted id**, not the title text: two titles that slug to the same id collide, and the message names the id.

**The set stays closed — the fourth member is a *revision*, not an extension** (M48). The three-way statement was true of every *payload leaf* and silent about the payload's own `title:`, and that silence was a write path acking success over a title that never landed. Both minting doors — `jigc doc create` and `jigc doc author` — now share **one pre-check**, running **before either persists**, so the whole payload is rejected with nothing staged and nothing to roll back. It refuses two shapes, and they are not the same defect:

- **The silent no-op** — the supplied title will not become the doc's `# H1`: the call lands on an identity the task already **stages**, or on a **committed** doc it would copy in, and a create-or-update hands that body back as found; or the doctype is a `placement` / `display-title` **singleton**, whose H1 is the schema's own whatever the corpus holds. This is **not** an identity change — [storage.md](storage.md) → Identity calls an ordinary retitle identity-**stable** — so `write.identity-change` firing here would be a law-1 lie. It mints one new member, **`write.title-ignored`**, whose sentence is *the title you supplied will not become this doc's `# H1`*.
- **Identity divergence** — the workflow gate entry's `as:` role is already bound to `<type>:<slug>` and the call would mint or re-point a **different** identity (a divergent `title:`, or a `--slug` at a constant title). That is a second document beside the first, so it converges on the shipped **`write.identity-change`** — no code minted, joining its producers at `retitle-item`'s enum `id-from` and `doc rename`'s two refusals.

Both route at **`jigc doc rename`** (above) — argv-complete, the `--slug` carried through — and the divergence message states the **declared behaviour change** rather than ambushing with it: a hand-driven *second* mint of one doctype in one task is what stops working, and a genuinely separate second document is its own task. No shipped workflow wants two: all 31 `allows-create` entries across both packs declare an `as:` role, and every shipped workflow is one-doc-per-role in its own prose. Ranking: the payload-shape parse outranks doctype admission (unknown / gate-blocked), which outranks the title — a title complaint about a doctype the workflow cannot create at all is a misdirection. The **fixed-title** arm is adjudicated from the doctype alone, above any instance read, and it is the one arm that does **not** route at `doc rename` (which refuses a singleton outright): `create` routes at itself under the schema's title, `author` at the payload line to correct. The singleton rule ratifies a seam the pack already ships — the `{{schema:<doctype>}}` skeleton renders a singleton's `title:` **literally as the `display-title`** — and the two are one predicate, `Schema::fixed_title`, which the mint reads too. The cells join the write-verb × miss-shape axis as a **title-miss column** (`crates/cli/tests/write_miss_shape_axis.rs`).

### `jigc doc retitle-item` — retitle-without-reslug, at item level (M40)

**`jigc doc retitle-item <item-addr> --title "<new>"`** splices the item's heading text (`{hashes} {title}  {#id}`) with the **`{#id}` anchor frozen** — the declared retitle-without-reslug invariant ([VISION.md](../VISION.md) → Stable IDs; [storage.md](storage.md) → Identity) finally getting its verb. Headings sit at level 2+depth; nested items ride the existing chain address grammar (`#releases/<id>/changes/<gid>`), no new addressing. Because the heading **is** the item's `id-from` field's value, the new title **re-validates against that field's declared type** — and an **enum** id-source (changelog's change-group `id-from: category`) is **refused outright**: the heading IS the member and the anchor equals it, so a member change is an identity change, not a retitle; the finding routes to `remove-item` + `add-item` under the target category, moving the prose in the same motion. A **milestone-record** item is refused outright too, regardless of field type (the Milestone-record reslug rule's item-level mirror, below): the record is machine-maintained and a `tasks` item's heading IS the sub-task's work-unit id (`id-from: task-id`, a plain string), so the finding routes to the milestone verbs, never a manual retitle.

**The set-field id-from guard (same motion):** `jigc doc set-field` on a heading-derived (`id-from`) field is **rejected**, with a **type-aware route** — it names `doc retitle-item` only when the id-from field is a plain string (`id-from: title`); for an enum id-from it routes to `remove-item` + `add-item` (retitle-item refuses the enum case, above); and on a **milestone-record** it names neither — the route points at the machine-maintained milestone verbs (retitle-item refuses the record too, above) — mirroring the `add-item` `ID_FROM_ENUM_CODE` guard. It previously or-inserted a contradictory field bullet under the heading, with three live failure shapes (task-wedging non-reparseable corruption · **silent divergence committed clean** · a recovery trap loop) — the 2026-07-10 baseline ledger's worst set-field finding ([DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 Settle).

### `jigc doc rename` — the in-task title change, split on committed-store identity (M48)

**`jigc doc rename <addr> --to "<New Title>" [--slug <s>] [--task <id>]`** is `retitle-item`'s **doc-level** sibling and `jigc rename`'s **in-task** one: it corrects a staged doc's `# H1`, and re-slugs it when — and only when — its identity is not yet committed. Until M48 a doc-level title correction had **nowhere to go**: `jigc rename` refuses outright while any task is in flight (it is task-less and self-committing, and its own guard blocks on a live task dir), and no `jigc doc` verb moved a doc title at all. So an agent that mistyped a title re-ran `doc create` / `doc author` with the right one and got a **second document at exit 0** — the reject T2 of that increment installs needs this verb as its destination ([DECISIONS.md](../DECISIONS.md) → 2026-08-13 the Settle, F2).

**It is a `jigc doc` leaf, not a `--task` arm on `jigc rename`** — by the rule the `jigc rename` section below states about itself: `rename` is top-level *because* it is task-less and self-committing, and its body is a committed-store git transaction end to end (clean-tree precondition, committed-index referrer repoint, `git mv`, `git commit -F`, rollback via `git restore`). An in-task title change uses none of it, and would contradict `rename`'s own in-flight-task refusal at its first guard. The spelling follows [The argument convention](#the-argument-convention--title-for-docs-a-positional-for-work-units-m42): `--to` is *"a rename's new title"*, whichever of the two verbs performs it.

**The split is committed-store identity**, which is the identity model's own subject ([storage.md](storage.md) → Identity: *"identity is the path"*):

- **Never committed** — the doc was minted in this task, so there can be **no committed referrer by construction** and re-slugging it is the same act as minting it correctly. `--to` rewrites the `# H1` **and** moves the identity: the staged body, its `docs/provenance.json` entry (re-keyed, its recorded provenance intact — the by-task-id join classifies by it), every `roles.json` binding, every **staged doc's** `ref` fields, and a migration task's recorded `slug-override`. The set is **derived, not hand-listed** — that is the whole reason the re-slug is confined to the uncommitted case: there, the CLI owns every referrer. Note the transient `commit` doc is simply another doc in the area here, so its `implements` edge **is** repointed — where `jigc rename` can only *report* it, because in the committed store it is not a file.
- **A committed doc copied in** — retitle-only. Its path is its identity for every other clone and every committed referrer, so the `# H1` is corrected in place, the slug frozen, and a `--to` that would move the slug **blocks** (`write.identity-change`) with a route at **`jigc rename`**, argv-complete, stating its precondition (that op runs once the task is out of flight). This is the same degenerate-retitle arm `jigc rename` already has, seen from the other side.
- **Fixed identity — refuse.** A **singleton** has no author-owned title *or* slug: its slug IS the type id and its `# H1` is the schema's (`display-title` when declared, else the type id), which is why a reslug there is **undefined** rather than blocked (see Placement singletons, below). The predicate is `Schema::fixed_title` — `singleton:` itself, the one home the mint, the `{{schema:…}}` skeleton, and both write doors read — *not* the `placement:` / `display-title:` knobs every shipped singleton happens to carry alongside it; keying on those would let a `singleton: true` + `location:` doctype re-slug through this verb while the create door refuses it. A **transient sink** (no `location`, no `placement`, no doc-level `id-from` — today `commit`) refuses for the mirror reason: its slug IS the task id its finalize renders it for. Both refuse by **doctype**, before any instance is read, and both carry a `Human` route — the correction is a pack change or a different verb, never a command to re-run.
- **`milestone-record` refuses above all of it**, through the shipped doctype-wide `machine_maintained_guard` — the record is maintained through the milestone verbs ([team-ready-state.md](team-ready-state.md)) — and the **item-level** enum-`id-from` refusal is unchanged (see `jigc doc retitle-item`, above).

**The discriminator is the *persisted* provenance, not a fresh path probe.** `docs/provenance.json` records the outcome of `state::create`'s own copy-in predicate at stage time (`edited-from-base` iff the committed body was carried in) — **including its in-location-squatter exception**: a migration whose source path IS the doctype's canonical destination stages `created` over a *foreign* file, and a bare `canonical_path(..).is_file()` would read that squatter as a committed managed identity and hand back a `jigc rename` route that blocks on a doc it cannot find. Same predicate, read where it was already answered.

**Bounds, stated:** the address is whole-doc — a `#fragment` is rejected with the corrected form, never silently dropped onto its container; a re-slug onto an id this task already stages **blocks** rather than clobbering that doc; and the staged-referrer repoint reaches doc-level `ref` fields only, the same bound `jigc rename`'s `repoint_ref` carries (no shipped doctype declares a `ref` inside a repeatable item block).

### `jigc doc set-field --unset` — clearing an optional field (M41)

**`jigc doc set-field <addr> --unset`** is `set-field`'s clearing mode: `--value` and `--unset` are **exactly-one-of** (clap `conflicts_with` / `required_unless_present`). It performs a **byte-stable field-line splice-remove** — the inverse of the `set-field` insert path — so the doc round-trips `render(parse(x)) == x` after the clear:

- a **header (front-matter)** field removes its `key: value` line from the `---` block;
- a **body / item field group** field removes its `- key: value` bullet, and when it clears the **last** field of the group it drops the whole `\n\n<!-- fields -->` sentinel group (the canonical writer emits the sentinel *iff* ≥1 field has a value, so the last-field removal must drop it or the canonical byte form breaks — the #1 retired byte-stability invariant).

**The set-field machine-maintained guard (M45 Inc 3):** `jigc doc set-field` on a `set:`-derived leaf **splits on the `set:` kind — because "the CLI supplies it" is not "the author may never write it".** A **machine-maintained absolute** — `set: schema-version` (the freeze stamp) or `set: on-transition` (the milestone base) — is **rejected**, closing the hole where `set-field <adr>#status/schema-version --value 99` committed a forged stamp that `migrate-corpus` then skips forever (`stamp ≥ current` → byte-untouched) and `version_currency_break` never reports. An **author-overridable stamp** — `set: on-create` — is **allowed**: the CLI defaults it at mint, but the changelog-migration path *depends* on overwriting `releases/<id>/date` with the foreign file's historical date ([auto-migration.md](auto-migration.md) → no false history; acceptance `flow25_migrate_changelog.rs`), so refusing it would break a shipped flow and fabricate history. The guard reads `item.title`/the raw value, not the slug, and shares its seam with the id-from guard (`apply_field_target`, the one door both `set-field` and the batch `author` payload lower through) — **not** the engine write primitives, which `transform.rs`'s optional-field fill and `migrate_corpus`'s own stamp bump legitimately write through. `milestone-record` is refused **whole** by the pre-existing `machine_maintained_guard` (every `doc` write to the record is illegitimate — the record is maintained through the milestone verbs), so its derived leaves stay unwritable by a **doctype** rule, above the per-leaf `set:`-kind split. This is the `set-field` **write** counterpart of the `--unset` eligibility below — *cannot be unset* (every derived field) is a strictly wider set than *may not be overwritten* (the absolutes only). Projection parity: [doc-read-surface.md](doc-read-surface.md) → the settability states.

**Eligibility — allow iff `!is_author_required(field) && field.default.is_none() && field.set.is_none()`** (equivalently, **reject** when the field is author-required **OR** carries a `default:` **OR** carries a `set:` deriver). The shorthand "reject author-required / `set:`-stamped" is *insufficient*: an enum field with a `default:` (adr `status`, `default: proposed`) reads as **not** author-required (`required-field-present` treats a defaulted absence as conformant), so it must be rejected via the **`default:` arm**, not the author-required one. Witnesses: `#status --unset` blocks (the `default:` arm) · the engine-injected `schema-version` stamp blocks (the `set:` arm — unsetting it corrupts the freeze/version gate; the message is stamp-specific) · adr `cites-code` (a `code-anchor`, no default/set, absence conformant) clears · an optional `0..*` ref (`supersedes`) was already clearable via `[]`. The guard lives in the engine write wrapper (self-protecting — no caller can corrupt the freeze/defaulted-field state). This is the clearing path that **section-level optional scalars had none of** before M41; the **empty-`--value`** (`--value ""`) reject's route now names `jigc doc set-field <addr> --unset` (previously a dead-end route).

**The `[]` non-ref-scalar reject (N2, M41).** `--value "[]"` on a **non-ref scalar** (a `string` / `owned-location` / `code-anchor` field) is **rejected** (`write.malformed-value`, old value untouched) — the misapplied ref-clear idiom, which previously spliced a literal `[]` as the value (accepted, a footgun). The `[]` / `[a, b]` list forms stay valid **only** for a **ref field** (`0..*`/`0..1`): `[]` clears its edges, `[a, b]` replaces the list — `check_ref` validates the bracket-list form *before* delegating to the opaque-scalar floor that now guards it. The reject's route points at `--unset` (a non-ref scalar has no list to clear; `--unset` is the correct clearing verb).

### Every write resolves its address before it moves bytes (M47)

**A write verb resolves its addressed leaf against the declaring schema *before touching bytes*** — an undeclared address is **rejected, never written**. That was the rule all along; what M47 shipped is the rule holding on every face of the nine-cell `{set-field, set-slot, doc author} × {section leaf, top-level item leaf, nested item leaf}` table, swept as data in `crates/cli/tests/undeclared_address_writes.rs` (Settle Decision 9; [DECISIONS.md](../DECISIONS.md) → 2026-07-26). **Eight of the nine cells did not** — only `set-field` at an undeclared *section* leaf was ever guarded — and the failures wore three faces: an undeclared **item field** or-inserted its bullet anyway, after which every read of the doc was `store.unparseable` and only `jigc task discard` recovered; an undeclared **item slot** leaf spliced the item's one real slot while the ack named the phantom leaf — **exit 0, the quietest face** (it does not break the doc, it lies about where the prose went); and the CLI's `slot_target` / the batch payload lowering dropped the trailing hop and the undeclared **section-level** key onto the section's own slot.

- **The reject is `write.unknown-field` for every leaf kind** — one contract member for *"the schema declares no such leaf here"*, the same code and route `set-field --unset` (`unset_item_field_validated`) already emitted for the identical miss ([validation.md](validation.md) → The `write.*` route split). Only the **sentence** differs: a `set-slot` reject says *slot*, and the section arm names the leaf-less address form (*"its prose slot is the section itself — address it as `#<section>`"*) **only when the section declares a slot** — over a fields-only section it says so plainly rather than pointing at an address that would fail too.
- **The batch `jigc doc author` is covered by construction, not by a second guard.** It lowers every payload key through the same `apply_field_target` / write-caller seams the per-leaf verbs use, so a tenth cell is a row, not a rediscovery. Its one payload-shaped rule is now *enforced* rather than merely documented: a section that is one slot is authored `set: {<section-id>: <<…>>}` — the key `doc author --help` states and the `{{schema:}}` skeleton generates — and any other slot-shaped key keeps its hop, to be adjudicated exactly as the per-leaf verb adjudicates it. The `<<…>>` cross-check narrowed in the same motion: it no longer demands the wrapper for a key that has no home either way.
- **Adjudication order is shape → item presence → leaf declaration.** A miss at a higher rank keeps its own code (`write.unknown-section` / `write.wrong-shape` / `write.not-present`), so the undeclared-leaf guard fires by **falling through** (`undeclared_field_reject` returns `None` for both higher ranks), never by out-ranking a structural miss it cannot see past. A source that no longer parses answers *"is the item present?"* with *"cannot tell"*, which is not a yes: it falls through too, which is what keeps the migration `transform.rs` caller byte-identical.
- **The rank governs *every* pre-check, not only the leaf-declaration one.** Any check that answers from the **schema alone** — it never reads the corpus — must be outranked by item presence, because at an item that was never minted it states a property of a nonexistent item (a [surface-contract.md](surface-contract.md) law-1 lie) and hands back a route whose first verb blocks on the same absence, costing a hop and answering nothing. Three such checks sat *above* presence and now fall through it: the CLI-side **set-field id-from guard** and **retitle-item enum-id-from refusal** (both gated at their shared seam, so a guard added there later is ranked by construction) and the engine's **`retitle_item` id-from re-validation** of the new title. What legitimately keeps its place above presence is a check that claims nothing about the addressed item: an **argument-shape** reject (an empty or anchor-injecting `--title`) and a **doctype-wide** refusal (`milestone-record` admits no `jigc doc` write at all, and routes informationally rather than at a verb that would block). The axis is swept as data at `crates/cli/tests/write_miss_shape_axis.rs` — one row per `{write verb} × {miss shape}` cell, each asserting the code, the emitted route **run verbatim**, and that the staged bytes are unchanged.
- **`ParsedItem::slot_span` is unchanged**, deliberately: its second consumer is conformance adjudication, which needs the single-slot leniency. So the guards sit at their **write callers**, after the item is resolved (presence keeps its own `write.not-present`) — the read-side mirror of the rule is [doc-read-surface.md](doc-read-surface.md) → the leaf slice.

### The argument convention — `--title` for docs, a positional for work-units (M42)

The verb surface has followed one rule since M7 and has **never stated it**, so an agent's only route to the right spelling was trial and error (a real, repeated cost in both RC trials). Stated:

| you are naming… | form | verbs |
|---|---|---|
| the **content** of a doc-level or item-level leaf | a **`--title` flag** | `doc create --title`, `doc add-item --title`, `doc retitle-item --title` |
| a **work-unit's** intent or title | a **positional** | `start "<intent>"`, `milestone create "<title>"`, `milestone add-task <id> "<intent>"` |
| a **rename's** new title | **`--to`** | `rename <old-slug> --to "<New Title>"`, `doc rename <addr> --to "<New Title>"` |

The rule behind it: a **doc** verb's title is a *value being written into a named leaf* — one flag among the leaf-addressed flags (`--value`, `--from-file`, `--slug`), and flags are how this vocabulary hands content to a named target. A **work-unit** verb's string is not a leaf at all — it is the unit's *reason for existing*, the one thing the verb cannot run without, so it is the positional. `rename`'s `--to` is the deliberate third spelling: it is neither writing a leaf nor minting a unit but **re-pointing an identity**, and `--to` reads as the direction of that move (`rename <old> --to <new>`).

**`--title` is always literally `--title`**, whatever the doctype's `id-from` field is called — the flag names the *role* (the title being minted from), not the field. `jigc doc create --help` has been advertising a `--<id-source>` form that **does not exist**; the help is what is wrong, not the convention.

## `jigc rename` — the CLI-owned identity refactor (M35)

A **committed** doc-level **identity change** (re-slug) is allowed only through one explicit, atomic op — and it is a **top-level** verb (`jigc rename`), because unlike every `jigc doc <verb>` (which stages into a task working area, promoted at `finalize`) it is **task-less and self-committing**, mutating the committed store directly — the shape of the other top-level direct-store ops (`unmanage`, `migrate-corpus`). Its in-task sibling `jigc doc rename` (M48, above) moves the identity of a doc that is **not yet committed** — where there is no committed store to mutate and no committed referrer to repoint — and routes here the moment there is. This is the project thesis applied to renaming: *take the structural operation from the LLM, give it to the CLI*. It is the prevention happy-path; the store-wide rename/`ref-resolves` detection is the backstop under it ([reconciliation.md](reconciliation.md) → Rename detection).

**Surface — one command, retitle + reslug + repoint unified:**

> **`jigc rename <old-slug> --to "<New Title>"`** — `--to` is **required**; `--slug <explicit>` (only valid alongside `--to`) overrides the derived slug.

The agent's natural act is *"this decision is now about X"*; one call gets everything right rather than making it learn and sequence two verbs. The CLI:

1. **Derives the new slug** = `slugify("<New Title>")` (the same `engine::slug::slugify` the `create` path uses via `id-from: title`, so a renamed doc is byte-identical to a freshly-created one of that title), unless `--slug` overrides.
2. **Validates** up front: target exists · tree clean · **not mid-fan-out** (a coarse guard — blocked whenever **any task working area *or* milestone is in-flight**, since a rename changes the by-task-id join's same-doc-clash key *and* a gitignored task working area may hold an `edited-from-base` copy of the renamed doc or a referrer that the tree-clean check is blind to — [storage.md](storage.md) → the join; the worktree/clean signal misses the docs-only case, so the guard keys on the task-dir + milestone-dir markers, not the git tree). **Collision:** the new slug must be free in the doctype's cascade-resolved location, *excluding the doc being renamed itself* — a collision with a **different** existing doc **blocks** (an identity refactor, never the by-task-id join's silent-suffix for new docs). **Degenerate (no-op) reslug:** if the derived/`--slug` slug equals the doc's **own current slug** (the new title slugs identically — identity unchanged), rename **degrades to a retitle-only**: rewrite the H1 and commit, with **no `git mv` and no referrer repoint** (there is no identity change, so nothing dangles). One command thus always "makes the title right," and moves identity only when the slug actually changes. **Idempotent (nothing to write):** when that title is *also* the H1 the doc already carries, the retitle rewrites nothing either — the run stages no change, so it **commits nothing** and acks the no-op at exit 0 (`commit: null` on the wire). It never manufactures an empty commit, and — the point — it never lets git's refusal of one reach the operator as a **commit rejection**: nobody rejected the run, so the survivable hook-rejection frame must not fire, its re-run route (which could only fail identically) must not be offered, and git's unrelated untracked-file listing must not be relayed as the cause. The emptiness is discriminated *before* the commit, at the same axis pre-flight every committing door shares.
3. **Repoints every persisted referrer** — walks the target's **inverse edges** in the committed edge index ([storage.md](storage.md) → Edge-index lifecycle) and rewrites each referrer's structured ref-field old→new across the **three persisted ref-fields** (`adr.supersedes`, `arch-doc.cites`, `spec.derived-from`). Both `supersedes` (`0..*` since M25) and `cites` are list-valued, so the rewrite swaps the one element and re-emits the canonical whole-list (the splice is per-field-value). `commit.implements` is **transient** (the git message, no committed file) → **reported, never rewritten**.
4. **Rewrites the moved doc's H1** to `<New Title>` (the unified retitle), then **`git mv`** old→new path. Combining the one-line H1 change with the move keeps `git log --follow` intact (well within git's rename-similarity threshold) and the diff legible.
5. **One transaction with its own rollback** (its own boundary, *not* `finalize`'s — see [reconciliation.md](reconciliation.md) → Rename detection, the transaction): captures pre-image bytes of the old path + every referrer, applies the rewrites + `git mv`, **re-baselines `file-state`** (`forget(old)` + `record(new)` + re-record every rewritten referrer) and rebuilds the edge index, stages, runs the user's git hooks (never `--no-verify`), commits; on **any** pre-commit failure restores all captured bytes, the `git mv`, **and** the file-state record (file-state is *inside* the rollback inventory, not a best-effort post-commit step — so a failed rename leaves the store byte-and-record identical to before). **Post-commit interruption is self-healing:** the committed tree is authoritative, so a crash after the commit but before the process exits cannot strand the store — the recovery rule is that a committed doc present at a new path whose recorded old path is absent from the committed tree is **re-baseline-adopted as the rename's landing** (re-keyed `old→new`), *not* routed to the weak-signal "restore the old file" (which would wrongly resurrect a deliberately-renamed-away doc). *(Build RED obligation: prove the crash-window recovery — a rename whose file-state re-baseline is interrupted self-heals on the next sweep rather than emitting a restore route.)*

**Placement singletons — reslug is undefined (M40).** A placement doctype's identity is **fixed to its type** — the singleton's slug *is* the type id (`vision:vision`, `changelog:changelog`; [storage.md](storage.md) → Placement), so there is no reslug to perform: reslug is **undefined** for a placement singleton, not merely blocked. `jigc rename` on one supports **retitle-only** (the H1 rewrite; the degenerate-reslug arm above), and a reslug attempt is rejected with an error that says exactly that — replacing the misleading "a different doc already exists at `<path>`" collision text (it is the *same* file, not a collision). This is the rule [doctype-authoring.md](../implementation/doctype-authoring.md) asserts; its design home is here.

**Milestone-record reslug — refused always (A4.4, M40).** `jigc rename` **refuses a milestone-record reslug unconditionally** — between milestones too: the slug **is** the milestone work-unit id, joining `.jigc/milestones/<id>` and every milestone op ([team-ready-state.md](team-ready-state.md)), so a reslug would sever the committed record from its work unit. The guard keys on the **committed** record (fresh-clone survivable, not the gitignored workbench). Retitle-only stays legal. The rule has an **item-level mirror**: `jigc doc retitle-item` refuses on a milestone-record likewise — a `tasks` item's heading IS the sub-task's work-unit id, so the record is machine-maintained through the milestone verbs (see `jigc doc retitle-item`, above).

**Boundary (determinism boundary — the honest line):** the CLI rewrites **structured ref-fields in the managed store** and nothing else. It **reports** (a boundary-safe report, *never* rewrites) old-slug occurrences it finds in **managed-doc prose** and **unmanaged files** (READMEs, code, tests) so the agent can fix them — the CLI does not author prose and cannot rewrite files outside the managed store. The report is a **word-boundary/token match** on the old slug (so `cache` does not match `caches`), scoped to **tracked worktree files** (respecting `.gitignore`), and is **advisory** (it never blocks and never rewrites).

**No freeze interaction:** rename is a pure data-value + path + cache operation; it adds **no persisted doctype field** and **preserves** each doc's `schema-version` stamp (it is not a migration). The identity-model invariant amendment this verb rests on is recorded in [VISION.md](../VISION.md) → Stable IDs and [storage.md](storage.md) → Identity.

**Post-MVP verb — pinned, not designed in detail:**

- **`jigc delete <addr>`** — confirms a deletion (the file is gone, the human meant it). Removes the `file-state` record and surfaces dangling referrer refs as integrity findings. MVP detects deletions and routes to restore ([reconciliation.md](reconciliation.md) → Rename detection); the explicit op ships when the verb is needed.

## `jigc migrate-corpus` — the commit boundary and its two opt-outs (M42)

`migrate-corpus` is the third **task-less, direct-store** op (with `rename` and `unmanage`, above) — but unlike them it has **never committed its own writes**. A successful run left an unstaged delete, an unstaged modify, and — for a relocation — an **untracked** file at the new path (the move is an `fs::rename`, git-free). The only way to land a migration was `git add -A && git commit` by hand: precisely the raw-git drive-around that the adapter contract exists to make unnecessary, and precisely what the adoption trial's agent did. A verb that mutates the committed store and then hands the operator a half-staged tree is not a direct-store op; it is a diff generator.

- **It commits its own writes**, on `jigc setup`'s **real** mold — a **pathspec-limited** `git add` over exactly the paths the migration touched (never a blanket `git add -A`), a no-op on a clean re-run, and a loud error on a genuine git rejection. The relocated path is `git mv`-visible rather than an untracked orphan. The migration's *own* transaction and rollback are unchanged and stay [corpus-migration.md](corpus-migration.md)'s — this adds the boundary at the end of it, and does not fold the op into `finalize`'s (which [finalize.md](finalize.md) opens by excluding: the task-less direct-store ops define their own atomicity).
- **`--no-commit`** performs the migration and leaves the changes staged for the operator to commit — for a human who wants the migration inside a larger commit, or wants to read the diff first. **Stated honestly: this flag is net-new.** The record has twice described it as *copying `setup`'s `--no-commit` opt-out* — **`setup` has no such flag**, and never did. The pathspec-limited self-commit is what is being copied; the opt-out is being **invented**, deliberately, because a corpus migration rewrites documents the operator is entitled to inspect before they enter history, in a way a `setup` install never does.
- **`--dry-run`** reports what the migration *would* do and **writes nothing** — no disk write, no commit. Also stated honestly: the charter described this as *"the report without `persist`"*, but there is **no operator-facing `persist` stage** to skip — persisting is an internal call inside the transform. So `--dry-run` means exactly *suppress the disk write*, which is the same shape as `jigc task finalize --dry-run` (walk the transaction, print the manifest, commit nothing; [finalize.md](finalize.md) → Surfaced, not prevented).

## Content handoff

Splits by leaf kind, falling straight out of the slot/field distinction:

- **Fields** (short, adjudicable) → **inline** `--value …`. No escaping pain.
- **Slots** (multi-line prose) → **stdin** `--from-file -` (or a file path). Never inline — prose through a shell arg is unreadable and escape-fragile.

`add-item` follows the same rule: the id-source field is supplied inline so the slug can mint, the call returns the new item's address, and the item's prose slots are filled by follow-up `set-slot <item-addr>#<leaf>`. One slot per call; bulk fill is the **batch path's** job (`jigc doc author --from-file`, above), not a back-door all-at-once `add-item`.

## Task origination

The front door is `jigc start`. The agent — knowing only the bootstrap ([bootstrap.md](bootstrap.md)) — runs it; the CLI does the rest. Four forms, all deterministic:

- **bare `jigc start`** — **orients** (read-only): project state, in-progress tasks, the workflow catalog with each workflow's `when` hint, recent finalizations. Never mints, never composes a side-effectful workflow. Adapter `SessionStart` hooks call this ([assistant-adapter.md](assistant-adapter.md)).
- **`jigc start "<intent>"`** — composes the cascade's **default workflow** (the cascade knob `default-workflow: <id>`, [overrides.md](overrides.md)) with `{{task.intent}}` = `<intent>`. Whether this mints a task is the workflow's own **`creates-task`** declaration ([workflow-dialect.md](workflow-dialect.md)). The two knobs are orthogonal — any workflow can be the default, any workflow can mint or not.
  - MVP: `default-workflow: single-task` (a `creates-task: true` work-workflow) → one call mints.
  - M2 onward: cascade flips `default-workflow` to a `router` (`creates-task: false`) → composing it presents the catalog (the engine-native `catalog` root, [workflow-dialect.md](workflow-dialect.md) → Workflow selection) and emits the explicit `--workflow X` call, which is what mints.
- **`jigc start --workflow <X> "<intent>"`** — composes `X` explicitly, bypassing the cascade default. Mints iff `X` declares `creates-task: true`. The id is a **slug from `<intent>`** — minted at **word boundaries** with a **~5-word cap** (M39, the readable-mint fix — [structural-grammar.md](structural-grammar.md#open-questions)) — frozen, collision-suffixed under the same discipline as artifacts; pinned to base = HEAD; opens `.jigc/tasks/<id>/`. A mint-time **`--slug <explicit>`** overrides the derived slug on `jigc start` (and likewise on `jigc doc create`, below): the agent proposes identity, the CLI still validates the grammar + owns collision handling — strictly cheaper than a `jigc rename` after a bad mint, and untouched by the freeze (mint policy is CLI behaviour, not doctype schema shape; [ideas/slug-minting-ergonomics.md](../ideas/slug-minting-ergonomics.md)). Tasks are first-class identities in the **work-unit family** ([structural-grammar.md](structural-grammar.md#work-units-and-runtime-identity); planned siblings: `milestone`, `increment`). This is the agent's "I know what I want" path, and what the router's output names. `--workflow` combines with the `<intent>` positional and is **mutually exclusive with `--task`**; an unknown `<X>` (not in the catalog) is **rejected** with a routed finding.
- **`jigc start --task <id>`** — resumes an existing task: loads its working area, recomposes the task's own persisted workflow, shows where it is. No minting. *(A fanned sub-agent enters its sub-task differently — `jigc workflow <W> --task <id>`, which composes an explicitly-named sub-workflow and provisions the sub-area; see [Sub-agent re-entry](#sub-agent-re-entry--jigc-workflow-w---task-id-m8).)*

Minting is **structure declared by the workflow**, never inferred — the CLI reads `creates-task` and acts. The cascade decides the default, the router (when present) presents options, the agent's reasoning chooses, and a human can pre-pick via a catalog-generated adapter command ([assistant-adapter.md](assistant-adapter.md)). The agent supplies the *intent* (content); the CLI mints the *id* and opens the area (structure) — the determinism boundary holds.

**Composing a `creates-task: false` workflow** (the router is the canonical case) takes **no task context**: the CLI does not mint, open a working area, provision a commit doc, or bind any context role. Such a workflow therefore may not reference `task.*` — a `task`-rooted placeholder in a `creates-task: false` workflow is a `workflow-refs` conformance error at validate-time ([validation.md](validation.md)). It threads the user's intent forward only through an **agent-substitution marker** in its emitted re-run command (`jigc start --workflow <chosen> "<intent>"`), never a resolved data-value. The `{{task.intent}}` binding above applies only on the minting path.

**Task-id collision & resume — serial vs parallel.** The same slug can arrive twice; policy splits by *how*:

- **Active task already exists with the slugged id** (serial retry of `jigc start "<intent>"` or `--workflow X "<intent>"`) → **reject**, with the existing task's status surfaced. The agent uses `jigc start --task <id>` to resume or `jigc task discard <id>` to abandon and retry. *Never silently suffixed, never silently reused* — a re-issued intent that lands on the same slug is almost always a forgotten resume, and silent suffixing would strand the original work.
- **Base mismatch on an existing task** (the task is pinned to commit `<A>`, you're on `<B>`) → the **overlap-aware** pin test ([storage.md](storage.md) → The per-task working area; [finalize.md](finalize.md) → Parallel hand-editing): moved history **disjoint** from the task's footprint re-pins to `<B>` in memory and proceeds; moved history that **overlaps** it is blocked with a routed `finalize.base-mismatch` naming the overlapping paths — resolve them, or `discard`. Applies identically at a **top-level** task's explicit `--task <id>` resume door — where the serial-collision route lands — and at its `finalize` commit door (M47/N7: the read-only door may not be stricter than the commit door it precedes). A **milestone sub-task** keeps the blanket refusal at *both* its read doors (`jigc workflow <W> --task <sub>` re-entry **and** `jigc start --task <sub>` resume), matching the strict milestone finalize that is its only commit boundary — there, relaxing a read door would make it *looser* than its commit door. *(`finalize.base-mismatch` is shared with the **milestone** boundary, where its unit kind, its cause, and its exits are all different — the route is unit-aware; see **Abandoning a milestone**, below.)*
- **`--task <id>` for a nonexistent id** → reject with "no task `<id>`". The in-progress catalog lives in bare `jigc start` orientation output, so the agent has a path to discover live ids.
- **Finalized task, slug reusable** → after `finalize` the working area is gone (`.jigc/tasks/<id>/` removed), so the task-id slot is free; a re-issued intent slugs to the same id and mints normally. Any *managed-artifact* ids the prior task minted (`commit:<slug>`, `adr:<slug>`) live in committed storage and follow the artifact minting rule's collision-suffix discipline if the new task tries to mint the same name ([structural-grammar.md](structural-grammar.md#ids-provenance-and-minting)).
- **Parallel collision under `fan-out`** (two sub-agents mint the same slug simultaneously) → the by-task-id merge applies the deterministic collision-suffix and rewrites *local* self-references ([workflow-dialect.md](workflow-dialect.md#fan-out--join)). This is the **only** place the suffix runs at task scope; the serial cases above all reject.

The principle: **suffix only in the deterministic parallel case** (where both works are legitimate and the join needs to disambiguate); **reject in the serial case** (where it's almost certainly a forgotten resume the agent should see).

### Minting a milestone + its task list (M7)

The `milestone` work-unit is the **fan-out container** ([structural-grammar.md](structural-grammar.md#work-units-and-runtime-identity)) — `milestone > task` for M7. Three verbs, all on the same work-unit-family minting discipline as `jigc start`:

- **`jigc milestone create "<title>"`** — mints a milestone work-unit (id = frozen slug from the title), opens its area with an empty task list, and **pins one shared base** (= HEAD) that every sub-task inherits — so the join's "present at the milestone base" test is a deterministic lookup against a frozen commit ([storage.md](storage.md#the-by-task-id-join-m7)). No sub-task minted yet.
- **`jigc milestone add-task <milestone-id> "<intent>"`** — mints a sub-task under the milestone (a task work-unit: id = slug from intent, pinned to the **milestone's** base, isolated `tasks/<sub>/` area) and appends it to the milestone's task list. Incremental — called once per sub-task; a serial slug collision within one milestone **rejects** (the deterministic suffix runs only at the join, never at incremental add).
- **`jigc milestone add-from-spec <milestone-id> <spec-addr>`** — the convenience populator (requested alongside incremental add): seeds the task list from a committed spec by **enumerating its repeatable `criteria` items** (the parse-items read path — `parse_sections` → the section's `items`, *not* the `jigc task bind` slice path) and minting one sub-task per criterion, the criterion's text as that sub-task's intent. A spec with **zero criteria items** is a blocking *"nothing to seed from"* — never a silent empty milestone. **Re-runnable (M47):** a criterion whose sub-task the **committed record** already names is *skipped* (the record, never the gitignored cache — a mint that never reached the record is re-minted, not silently counted as seeded), and the ack names both halves (seeded / already seeded), so re-running the verb seeds exactly the remainder — the recovery path after an interrupted seeding pass ([team-ready-state.md](team-ready-state.md) → The commit model). Two criteria of *one* spec slugging alike still block: that is an authoring collision, not a resume.

The task list is what the by-task-id join enumerates ([storage.md](storage.md#the-by-task-id-join-m7)). M7 builds the work-unit, these verbs, and the join; the `{{milestone.tasks}}` data-value root that exposes the list to the read path, and the `milestone-execution` *workflow* that fans out over it, are M8.

**The sub-task's recorded workflow (M8).** M7's `add-task`/`add-from-spec` hard-recorded each sub-task's workflow as `single-task`; M8 gives both a **`--workflow <id>` argument (default `sub-task`)** — the finalize-less sub-workflow real sub-agents run — and **records it** in the sub-task area. This is what makes the re-entry equality guard meaningful: the `milestone-execution` fan-out's `run: workflow:<W>` must equal the value `add-task` recorded, so `jigc workflow <W> --task <id>` asserting `<W>` == the recorded workflow (below) is a genuine guard, not a tautology — a stale template or a fan-out naming a workflow the sub-tasks weren't seeded for **fails loudly** instead of silently composing the wrong thing.

**Executing the milestone — `jigc milestone execute <id>` (M8).** The milestone-level counterpart to the sub-agent re-entry verb: it composes the **`creates-task: false`** `milestone-execution` workflow over the milestone work-unit `<id>`, feeding the milestone's id-sorted task list into `{{milestone.tasks}}` so the `fan-out` step resolves it — **minting nothing** (the milestone and its sub-tasks already exist). It lives in the `jigc milestone` verb family (`create`/`add-task`/`add-from-spec`/`execute`/`join`/`finalize`, joined at M42 by `discard`), *not* on `jigc start` — `start --workflow` stays mutually exclusive with `--task` and `start --task` stays top-level-task resume (the invocation-surface fork settled 2026-06-05, [DECISIONS.md](../DECISIONS.md)): a milestone is a distinct work-unit kind, so executing it is its own verb rather than an overload of `--task`. (Which workflow `execute` composes is the pack's single milestone work-workflow today, `milestone-execution`; a cascade knob can choose among several when a second one earns it — the same evolution `default-workflow`/the router followed.)

**Abandoning a milestone — `jigc milestone discard <id> [--force]` (M42).** The family's missing terminal verb: `jigc task discard <id>` abandons a *task*, and until M42 the *milestone* had no counterpart at all — so an abandoned milestone left a committed record permanently claiming to be in flight, a `.jigc/milestones/<id>/` no verb removed, and registered git worktrees behind it. `discard` settles the record (the `discarded` lifecycle member, and the per-item rule that a genuinely-joined sub-task **stays** `joined`) and tears the workbench down. **Record semantics + the lifecycle: [team-ready-state.md](team-ready-state.md) → The lifecycle.** Two things belong to *this* doc, because they are surface:

- It is a **milestone-family verb** (`jigc milestone discard <id>`), not `jigc task discard` widened — the same call the `execute` fork above made: a milestone is a distinct work-unit kind, so terminating one is its own verb rather than an overload of the task verb. **It is the terminal verb for an *abandoned* milestone, and nothing else.** In particular it is **not** the escape hatch for a `finalize.base-mismatch` on work you still want: it settles the record by declaring the work dropped and tears the workbench down — offering it as the recovery for a blocked-but-wanted milestone is telling the operator to throw the work away to satisfy a guard. *(Discard's own record-settling commit depends on the M42 base-guard widening, which ships with it — [team-ready-state.md](team-ready-state.md) → What the base-guard is for.)*
- It **refuses on a dirty sub-task worktree**, naming the offending paths, and destroys uncommitted work only under an explicit **`--force`**. Teardown runs `git worktree remove --force`, which is safe at *finalize* (the commit landed first) and destructive at *abandon* (the work is uncommitted by definition) — the guard, and why it is a **property of the abandon path** rather than an implementation detail, is in [team-ready-state.md](team-ready-state.md).

**The `finalize.base-mismatch` route is unit-aware — and it stops offering `discard` as the only exit.** Today the route reads *"switch back to `<A>` or discard the task with `jigc task discard`"*; on a **milestone** id `jigc task discard` returns `no task '<id>'`, exit 1 — a dead end that calls a milestone "the task" (wrong verb, wrong unit kind). Naming the *milestone*-family verb instead would fix the unit kind and keep the disease: for a milestone the block's cause is **landed code**, and its honest exits are not "abandon." The milestone arm of the route therefore **names the cause** (commits landed after the milestone's base, so the base its sub-task worktrees were cut from no longer reflects HEAD — the M31 worktree-combine cannot be proven sound against it) and **names the real options** (put the milestone's work in first — return HEAD to the base, finalize, re-land the other work on top; or re-cut the milestone's work onto the new base out of band), with `discard` reserved for the case where the work is genuinely being abandoned. There is **no `jigc milestone rebase`** — deliberately, at M42. The constraint underneath (a live milestone is invalidated by any code/doc commit landing after its base — **one milestone's work must land before another's base can survive it**) is real and is stated where it belongs: [team-ready-state.md](team-ready-state.md) → What the base-guard is for.

### Sub-agent re-entry — `jigc workflow <W> --task <id>` (M8)

A fan-out spawns sub-agents; each re-enters the CLI to get its instructions. The re-entry verb is **`jigc workflow <W> --task <id>`** — a top-level verb parallel to `jigc start`, the surface the adapter's launch template renders ([assistant-adapter.md](assistant-adapter.md) → Bind the spawn mechanism). It is the design's named contract, distinct from `jigc start --task <id>`:

- **`jigc start --task <id>`** *resumes a top-level task* and recomposes the task's **own persisted minting workflow** (read from `.jigc/tasks/<id>/workflow`); it takes no workflow argument (`--workflow` is mutually exclusive with `--task` on `start`). This is the human/main-agent "pick up where I left off" path.
- **`jigc workflow <W> --task <id>`** *enters a milestone sub-task as a fanned sub-agent*: it composes the **explicitly-named sub-workflow `<W>`** (the fan-out step's `run:` workflow, which the launch template fills as `{{workflow}}`) for sub-task `<id>`. `<W>` is **explicit, not redundant**: a sub-task minted by `jigc milestone add-task` records its sub-workflow, and re-entry asserts `<W>` equals it (a mismatch is rejected — the fan-out and the recorded mint must agree), so the launch line is self-describing and a stale template that names the wrong workflow fails loudly rather than silently composing the wrong thing.

**Re-entry provisions the write-ready area.** `jigc milestone add-task` mints a sub-task area with `base`/`intent`/`workflow` but **no `docs/`** — it is resume-*composable* but not write-*ready*. The first `jigc workflow <W> --task <id>` re-entry **provisions** the sub-workflow's deterministic instances (the commit doc, any workflow-provisioned docs) into the sub-area — mirroring how `jigc start` provisions at mint time, just deferred to the sub-agent's first entry rather than at `add-task` (so areas that are never spawned are never provisioned). After re-entry the sub-agent writes through the normal `jigc doc` verbs, scoped to its sub-task (below).

### The write-time `--task`-scoped barrier (M8)

Under a fan-out, multiple sub-task working areas coexist, so a write must name *which* area it targets. Every `jigc doc <verb>` gains a **`--task <id>`** selector (the create-gate enforcement already anticipates "`.jigc/tasks/<id>/` from cwd, or `--task <id>` explicit" — [The create-gate](#the-create-gate)); the **active-task resolution** becomes: explicit `--task <id>` wins; else the single active task; else (zero, or **more than one** with no `--task`) reject. The barrier scopes **staging writes** — a `create` / `set-slot` / `set-field` / `add-item` / the copy-in whose **staged-doc destination path** would land outside `tasks/<id>/` is rejected at write-time, not deferred to the join. It does **not** restrict reads of committed state: `jigc task bind <role> <addr> <id>` targets a *committed* doc by design ([Binding a context role](#binding-a-context-role)) — it stages nothing into any area, so the barrier's "destination outside the sub-area" rule never applies to it. This is the *write-time* complement to the M7 *join-time* isolation check ([storage.md](storage.md#the-by-task-id-join-m7)): join-time catches a mis-attributed staged doc after the fact; the barrier refuses the mis-directed staging write up front, so a sub-agent physically cannot stage into a sibling's area.

**Editing a base-committed doc — copy-on-first-touch (M8).** A sub-agent that edits a doc which existed at the milestone's shared base must record `edited-from-base` provenance for the join's clash rule ([storage.md](storage.md#the-by-task-id-join-m7); [workflow-dialect.md](workflow-dialect.md#fan-out--join)). The first write to such a doc **copies the committed body into the sub-area** (`copy_in` → `edited-from-base`), then splices; a `create` of a new doc stages `created` as today (`provision_doc`). **Provenance is recorded once, at first touch, keyed on whether the slug existed in the committed store at the milestone base** — `created` (absent at base) is **sticky** across later edits in the same area (a created-then-edited doc stays `created`, never flips); only a doc present at base records `edited-from-base`. This is what makes the join's clash discriminator stable (the mixed-case `created` × `edited-from-base` block keys on base-membership, not on "did this area edit it"). It makes both provenance bits — and therefore the `same-doc-clash` block — reachable through the real `--task`-scoped write path, where pre-M8 only `created` was reachable and only for a single active task. (`provision_commit_doc` likewise records `created` provenance under M8 — a per-sub-task commit doc must appear in the provenance manifest the join consumes; this is **collision-safe by construction**, because `commit:<sub-id>` is sub-task-id-derived and therefore unique per sub-area, so per-sub-task commit docs never reach the join's same-slug suffix/clash rules.)

A task carries **context roles** its workflow declares; `task.<role>` ([workflow-dialect.md](workflow-dialect.md)) navigates the bound doc, and **the CLI never infers a binding** — the agent binds explicitly, by one of two routes depending on where the doc comes from:

- **agent-created, same task** — `jigc doc create <type>` under a create-gate entry whose object form declares `as: <role>` binds the new instance in one step ([The create-gate](#the-create-gate)).
- **an existing committed doc** — `jigc task bind <role> <addr>` ([Binding a context role](#binding-a-context-role)) binds a doc a *prior* task committed; this is how the spec → implementation arc threads a `spec` written by one task into the task that implements it.

A role the workflow declares but the agent has not yet bound resolves to **empty** (the slice is absent, not an error); a `task.<role>` whose role the workflow does **not** declare is a `workflow-refs` conformance error ([validation.md](validation.md)).

## Staging and the transaction model

**The staging unit is the task.** The per-task isolated working area — already required for sub-agent concurrency ([VISION.md](../VISION.md) → Parallelism) — *is* the staging area. There is no separate proposal object: every write lands in the current task's working area immediately (no `begin`), and "propose / review / apply" is just `write / validate / finalize` over that area. The task id is the changeset name.

**Two check times** ([VISION.md](../VISION.md): integrity holds at `finalize`, not per-write):

- **Write-time — local adjudication.** A `set-field` rejects a malformed date or a non-member enum *now*; a mint rejects a bad slug; an `add-item` rejects an id-source value outside its field's enum (re-slug membership) *now*. Fast, local feedback. *(M24 closed the gap here: pre-M24 only section-level `set-field` adjudicated at write time — `add-item`'s id-from enum and item/nested-item field values were caught only at finalize. M24 extends the write-time check to `add-item` id-from and item-field values via a **single shared slug+enum-membership helper called by both the write-time path and finalize's `check_id_from_enum`** — one function, so the two cannot disagree by construction (not a mirrored copy, which would drift when M25 generalizes it 4×). The finding **code** is shared; the emitted **address** leaf-suffix may differ by call site (at `add-item` time there is no parsed item yet); [DECISIONS.md](../DECISIONS.md) → 2026-06-16.)*
- **Finalize-time — integrity the task can fix.** Forward-ref resolution (dangling refs), required-slot presence, and unreconciled drift run at `finalize` — a ref may dangle in the working area until then, because its target can be created in the *same* task. **Finalize blocks only on what the task can fix itself**; inverse/minimum-cardinality ("a PRD needs a SPEC") depends on *other* tasks and is **completeness, not a per-task gate** (see [document-type-schema.md](document-type-schema.md), [validation.md](validation.md)). This split is what stops the bootstrap from deadlocking.

**`finalize` ≡ `validate` + the commit-time gates + commit.** Finalize has no private check path *at the validate phase* — it runs the same `validate` and commits only if it passes, so every check `validate` runs is a check `finalize` blocks on, and `jigc task validate` previews the gate **up to the commit**. The rest of the transaction is the rest of the gate: the preflight's base pin before it, and the staged set, render, promote, stage and the commit itself after it, each adjudicate their own failures at a **different position** in the same transaction — a difference of position, not of scope ([finalize.md](finalize.md) → 2. Validate). One task → one logical commit. The **ordered transaction** (preflight → validate → render → promote → stage → commit → post-commit), atomicity rules, rollback discipline, the change-set scoping (the commit is the agent-staged git index plus jigc's promoted docs/config, not a working-tree sweep), and the commit-doc → git-message mapping are specified in [finalize.md](finalize.md).

- `validate` is **scope-flexible** — a task (the working area; what the hard-block uses), a single doc, or the whole store — one engine ([structural-grammar.md](structural-grammar.md#validation); probe split per [VISION.md](../VISION.md) principle #6).
- Findings are **severity-tagged**: *blocking* (integrity must hold) stops `finalize`; *advisory* is surfaced but doesn't. **Which severity a check carries is a cascade setting** — a project can promote or demote, say, `doc↔code` staleness without touching code.
- `finalize` **defaults to autonomous**; an opt-in cascade setting can require human confirmation. The durable correction point is the git/PR review regardless.

## Instance provisioning

A working instance must exist before you can `set-slot` into it. The CLI **always** owns the structural act — mint the id (slug from the type's id-source field) and place it at the schema-defined location ([structural-grammar.md](structural-grammar.md#ids-provenance-and-minting)). There are two triggers:

- **Workflow-provisioned** (deterministic) — the composed workflow creates the instances the task obviously needs (e.g. the task's commit doc) and fills the id-source field deterministically, yielding a task-derived id like `commit:add-rate-limiter`. The agent only fills slots.
- **Agent-initiated** (judgment) — `jigc doc create adr --title "…"` when the agent decides a *new* doc is warranted mid-task. The CLI mints + places; the agent supplied only content.

The minted skeleton **pre-stamps every author-required header field as an empty `key:` line** (M40 — the commit doc's `fillable_form` precedent generalized via the shared engine `is_author_required` predicate), so a required field is never invisible at create; `jigc doc schema <doctype>` is the companion read surface ([doc-read-surface.md](doc-read-surface.md)).

This keeps the determinism boundary intact: **deciding a doc is warranted is reasoning (agent); creating and placing it is structure (CLI).** Agent-initiated `create` is **workflow-gated** — the catalog of types creatable in a given context is structure (workflow/cascade-owned); *choosing* among them is reasoning.

### The create-gate

The gate lives on the workflow's front-matter as **`allows-create: [<doctype-id>, ...]`** ([workflow-dialect.md](workflow-dialect.md) → On-disk definition format). **Default is empty — no agent-initiated creates allowed unless the workflow explicitly opts in.** Workflow-provisioned instances (e.g. the task's commit doc) bypass the gate; they're not shell-visible and are declared by the workflow's own structure.

**Two entry forms.** Each `allows-create` entry is either a bare doctype id (`adr`) or an object `{type: <doctype-id>, as: <role>}`. The object form additionally **declares a context role and binds the created instance to it**: creating that doctype under the gate makes the new instance reachable as `task.<role>` ([workflow-dialect.md](workflow-dialect.md)) with no separate bind step. MVP `single-task` ships `allows-create: [{type: adr, as: decision}]`, so an agent-created ADR is reachable as `task.decision` — the surface the superseding-decision context-slice composes from (`{{@task.decision.supersedes#decision}}`, see [worked-examples.md](worked-examples.md) → Superseding decision). The bare form grants create permission without declaring a role.

**Enforcement at every `jigc doc create <type> --<args>`:**

1. Identify the active task — `.jigc/tasks/<id>/` from cwd, or `--task <id>` explicit. **No active task** → reject: `"no active task — start one with \`jigc start\`"`.
2. Identify the task's workflow and resolve its effective `allows-create` through the cascade ([overrides.md](overrides.md) → Resolution algorithm).
3. **Unknown doctype** (`<type>` not in the cascade-resolved schema set) → reject: `"unknown doctype \`<type>\`"`. (This is a separate failure mode from the gate; it fires before the gate check.)
4. `<type>` ∈ `allows-create` → proceed: mint id, place per the schema's `location:`, **bind it to the entry's `as:` role if the entry declares one**, return the new address.
5. `<type>` ∉ `allows-create` → reject with the structured gate-block error:

```text
error: workflow 'single-task' does not allow `jigc doc create spec` in-task.
       allowed doctypes: [adr]
       to loosen: set `workflows.single-task.allows-create` in project config
```

The rejection carries a **`run-command` route** the agent can act on (the cascade-set command, formatted via the [command catalog](command-catalog.md)). Plain-text format above is the human surface; the structured payload shape rides on the broader blocked/error-payload open question (below).

**Cascade override.** Loosening or tightening is a standard delta:

```yaml
# project config
scalar:
  workflows.single-task.allows-create: [adr, spec]   # also allow agent to create SPECs
```

Resolves through the [9-phase algorithm](overrides.md#resolution-algorithm) — phase 3 (scalar deltas), project wins because it applies last. A structural-op replacing the workflow's front-matter wholesale works equivalently.

**`fan-out` sub-agents.** Each sub-agent runs its own sub-workflow, and *that* sub-workflow's `allows-create` applies. A sub-agent inherits no permissions from the parent. (Revisit if a real `fan-out` pattern demands parent → child gate inheritance.)

A worked payoff: the **commit message is just a doc type.** Its format — a `type` enum, a `scope` field, a `summary` slot, a `body` slot, a repeatable `trailers` section, a mandated issue-ref — is the commit type's schema plus cascade overrides. A project gets *any* commit convention it requires (conventional commits, custom trailers, …) with no special-casing; the same machinery that structures an ADR structures the commit. The agent writes the prose; the CLI guarantees the required format.

### Binding a context role

`jigc task bind <role> <addr> <id>` binds an **already-committed** document (`<addr>`) to one of task `<id>`'s declared context roles ([workflow-dialect.md](workflow-dialect.md) → `reads`), so `task.<role>` resolves to it. The `<id>` is the task positional, consistent with the `jigc task <verb> <id>` family (`validate`/`finalize`/`discard`). It is the counterpart to the create-gate's `as:` form: the gate binds a doc the task *creates*; `bind` binds a doc a *prior* task already committed — the only way a managed doc crosses a task boundary into a later task's context.

This is the **spec → implementation seam**: a `plan` task authors and commits a `spec`; a later `implement-from-spec` task runs `jigc task bind spec <spec-id> <task-id>`, and its `locate` step's `{{@task.spec#criteria}}` then resolves over that committed file.

**Why a verb, not a `start` flag.** Binding is a per-task write like any other, kept *off* `jigc start` so origination stays the single simple sentence the agent learns from the bootstrap. The composed workflow routes the agent to it — a `locate` step emits `` Run: `jigc task bind spec <SPEC_ID> <task-id>` `` (the `<SPEC_ID>` is a `<NAME>` agent-substitution marker, the trailing task id is CLI-resolved from `{{task.id}}` so the emitted line is runnable as-is, [command-catalog.md](command-catalog.md)) — exactly as it routes every other structural op back to the CLI.

**Resolution timing.** Binding happens *after* compose, so the bound slice is empty on the first composition and resolves on the **resume re-compose** (`jigc start --task <id>`) — the same deferred-bind-then-resume path the superseding-decision flow already uses for `{{@task.decision.supersedes#decision}}` ([worked-examples.md](worked-examples.md) → Superseding decision).

**Enforcement at every `jigc task bind <role> <addr> <id>`:**

1. Resolve task `<id>`. **No such task** → reject: `"no task \`<id>\` — list live tasks with \`jigc task list\`"` (the shared wrong-id route — M43: every wrong-task-id surface converges on `jigc task list`).
2. `<role>` ∉ the workflow's declared read-roles → reject, listing the declared roles.
3. `<addr>` does not resolve in the **committed store** → reject: `"no such doc \`<addr>\`"`. `bind` targets committed docs only — a doc the *same* task creates uses the create-gate's `as:` form instead.
4. The target's doctype ≠ the role's declared `type` → reject with the mismatch.
5. Otherwise record the binding in the task's `roles` and return the bound address. Re-binding a role overwrites (last-write-wins, surfaced in `task diff`).

The agent supplies only the *which-doc* choice; recording the binding and resolving it stay the CLI's — the determinism boundary holds.

## Out-of-band reconciliation

Humans edit files directly, and because the **files are the source of truth** ([storage.md](storage.md)), the system **honors a clean edit, not merely tolerates it** ([VISION.md](../VISION.md) principle #3). The CLI never forbids file edits and never silently discards them — every drift is detected, classified, and routed.

The deterministic classifier (states, transitions, parse classification, hash re-baselining, MVP vs post-MVP scope) is specified in [reconciliation.md](reconciliation.md). Three outcomes the agent sees: **absorb** (clean edit accepted; hash advances), **conformance-block** (parse / schema failure surfaces precisely; never auto-repaired in MVP), **conflict-block** (both sides changed; explicit discard, no silent default; three-way merge deferred). `finalize` blocks on the latter two and absorbs the first.

## Worked example — the MVP write loop

```text
# task add-rate-limiter; the workflow has provisioned commit:add-rate-limiter (empty)

jigc doc set-field commit:add-rate-limiter#type    --value feat
jigc doc set-slot  commit:add-rate-limiter#summary --from-file -      # prose piped in
jigc task validate add-rate-limiter                                   # blockers? (preview)
jigc task finalize add-rate-limiter                                   # validate + commit
```

Agent-initiated create within the same task:

```text
jigc doc create adr --title "Rate-limit at the gateway"   # → adr:rate-limit-at-the-gateway
jigc doc set-field adr:rate-limit-at-the-gateway#status  --value accepted
jigc doc set-slot  adr:rate-limit-at-the-gateway#context --from-file -
```
