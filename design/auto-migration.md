# Auto-migration (Flow-B transform path)

**Status: settled at M23 planning (2026-06-14); extended at M24 planning (2026-06-16) with the hardening section below.** Auto-migration (G1) is the second of the two milestones the paired post-M21 deferral was **split** into ([DECISIONS.md](../DECISIONS.md) → 2026-06-14 split; the doctype-expansion track G2 shipped as M22). It adds the **transform** arm to existing-project ingestion: an existing project's non-conformant foreign doc is **rewritten into conformant shape and adopted**, where M9/M21's [detect-and-route](project-setup.md) ([Flow 2](project-setup.md)) only classifies + routes and never rewrites. **Changelog is the only target this milestone migrates** (it has the live Flow-B demand and M22 shipped its schema); generalizing to the location-bearing doctypes (`adr`/`spec`/`prd`/`arch-doc`) is **M25** — but **M24 first hardens this changelog reference** (a real-repo smoke test surfaced friction that is mostly *general* migration/authoring mechanism, fixed once here rather than N times across the generalized doctypes; see "Hardening (M24)" below; [DECISIONS.md](../DECISIONS.md) → 2026-06-16 M24 planning). The north star (M25+): introducing jigc into an existing project reads everything already there — code, docs, planning files — and rewrites it into jigc structure through the CLI.

## The determinism boundary stays intact (Framing A)

The standing charter framed G1 as "research-grade — relaxes the determinism boundary, needs tolerant/fuzzy heading-mapping machinery the strict parser withholds." **That framing is superseded.** It conflated two different acts:

- **The LLM does the fuzzy mapping** — reads the foreign file and *reasons* about which content becomes which section/slot, emitting a canonical-shape rewrite. This is **prose/structural reasoning → a proposal**, already inside the boundary ([VISION.md](../VISION.md#the-determinism-boundary) → the mixed-decision clause: "the agent reasons; the CLI executes").
- **The CLI does the fuzzy mapping** — heuristic heading-match / alias tables / edit-distance. *This* would relax the boundary by making the CLI a second, non-strict structural authority. **It is not built.**

Under Framing A the CLI's strict `parse → conformance-gate` stays the **sole** structural authority: the LLM's rewrite is just another upstream proposal that must survive the existing strict gate, exactly as a `create`-gated authoring does. The [determinism-boundary table](../VISION.md#the-determinism-boundary) does **not** change. This is the load-bearing argument of the milestone: migration is *reuse of the existing author + adopt path*, not new placement machinery.

## What it proves

The Framing-A migration mechanism, end-to-end, on one real doctype:

1. An existing non-conformant foreign `CHANGELOG.md` is read by the CLI and its content surfaced to the LLM as **deterministic workflow context** (a CLI-owned source seam — not an out-of-band agent read).
2. The LLM rewrites it to canonical `changelog` shape **through the existing write verbs** (`doc create` / `add-item` / `set-slot` / `set-field` — the proven [record-change](changelog.md) spine).
3. The CLI **strict-parses + conformance-gates** the rewrite; a non-conformant rewrite is **rejected and routed**, never adopted.
4. A **human review gate** shows the fidelity diff (foreign original → canonical rewrite) and blocks on approval — because the strict parse guarantees *structure*, never *content-faithfulness* (a structurally-perfect doc with dropped or hallucinated content passes the gate). Fidelity is LLM prose, unverifiable by the CLI ([VISION.md](../VISION.md) → "never guarantees the prose"); the human is its only check.
5. On approval, finalize **adopts** the managed doc (the existing register-only adopt: parse → conformance-gate → `index.absorb_doc` → file-state hash) at its canonical home **and retires the foreign original**, in one transaction.

This flips the `changelog` doctype's [Flow-A-only honest bound](changelog.md) for changelog: an existing `CHANGELOG.md` becomes trackable. It unblocks the **Flow-B existing-project live test** against a real foreign-doc corpus.

## Does not prove (honest bounds, recorded so the completion audit can't charge them)

- **Changelog only.** `adr`/`spec`/`prd`/`arch-doc` migration is M25 (M24 hardens changelog first). The verb + workflow + review-gate + retire mechanism is built **to generalize** (target doctype is a parameter), but only changelog is exercised + accepted here.
- **No CLI fuzzy heading-mapping.** A foreign heading is mapped to a schema section by the *LLM's rewrite*, never by CLI heuristics. A rewrite that fails the strict gate is rejected, not coerced.
- **Migration fidelity is human-judged, not CLI-verified.** The strict gate adjudicates structure + field values; whether the rewrite faithfully preserved the foreign content is the review gate's (human's) call. By design.
- **Accepted content drops.** Real Keep-a-Changelog files carry surfaces the `changelog` schema has no home for — the doc-level preamble paragraph, a per-release prose summary, the `[Unreleased]` compare-link, foot-of-file reference-style link definitions. These are **dropped** in migration (mostly boilerplate); the same honest-bounds posture [changelog.md](changelog.md) takes for entries-as-prose. A release's compare URL maps to the optional `link` field; everything else above has no slot and is lost.
- **Version-slug collisions block, not resolve.** See *Slug collision* below.
- **In-location squatter — failed cleanly in M23, fixed in M24.** M23 migrates a foreign file at a **non-canonical** path (a root `HISTORY.md`, or the old `docs/changelog/changelog.md` folder home). A non-conformant file already *at* the canonical managed path could not be authored over end-to-end in M23: the **idempotent-create copy-in** (`crates/engine/src/state.rs` `create` step 4, the M16 clobber-fix) reads the committed non-conformant squatter in as the edit base, so the author sequence builds onto non-conformant bytes and finalize blocks (a Frankenstein doc with misleading section errors — *not* a clean `write.wrong-shape` at the write verb, as earlier text here claimed; corrected at M24 planning). It failed **cleanly** (no data loss; the retire collision-guard is defensive). **M24 fixes it** (see "Hardening (M24)" below): seed the working area **blank** over an occupied canonical path, gated by the migration `source-path == canonical-destination` discriminator. See *Path-collision guard* below. **(Post-M38:** `changelog`'s canonical home relocated from `docs/changelog/changelog.md` to a root **`placement`** at `CHANGELOG.md`, so the *common root `CHANGELOG.md`* is now the canonical destination itself — an in-location squatter that **adopts in place** (M38 taught the create-side discriminator the `placement.file` destination; `design/storage.md` → Placement).**)**

## The mechanism

### The `jigc migrate` verb (the trigger)

A new verb: `jigc migrate <path> --as <doctype>`. Settled because the alternatives **cannot reach the target**: a foreign off-canonical changelog (a root `HISTORY.md`, or a `CHANGELOG.md` before its M38 relocation made root the canonical home) classifies `Unmanaged` (no finding, no route, no hook — `crates/cli/src/render.rs` renders an Unmanaged row as "left untouched"), so extending the `needs-reconcile` arm of `ingest` is structurally unable to reach it, and `jigc start` has no source-path parameter. An explicit verb taking `path + --as <doctype>` addresses an arbitrary foreign file directly, sidestepping location-based classification. (This also makes real the `migrate` verb the existing advisory route string at `crates/engine/src/file_state.rs` already names — today vaporware.)

`jigc migrate <path> --as changelog`:
1. Reads the foreign file's bytes.
2. Mints an **off-router migration task** (mirrors `record-change`: `creates-task: true`, `selectable: false`, `allows-create: [{type: changelog, as: changelog}]`), recording the foreign source path on the task.
3. Loads the foreign content into the task as **CLI-owned context** (see the source seam) and composes the migration workflow.

### The byte-floor advisory (the trivial-source rider, M44)

When the foreign source is **below a small byte floor** (`TRIVIAL_SOURCE_FLOOR`, `crates/cli/src/migrate.rs` — calibrated below every shipped foreign fixture so a real document, even a minimal one, never trips it), `jigc migrate` surfaces a **non-blocking advisory** (`migrate.trivial-source`) naming the byte count + floor and routing to the from-knowledge `jigc start --workflow record-decision "<intent>"` path. The migration still composes; the run still exits 0 — the advisory is a *nudge*, not a gate.

This is **Framing A intact**: the guard is a **mechanical byte count, never a content judgment** — the CLI does not read or grade the source's meaning, it counts bytes. A near-empty or placeholder source has little prose to preserve, and an agent reaching for `jigc migrate` on such a file is almost always exploiting migration as an authoring back door (the rc.7 placeholder-source loophole, [DECISIONS.md](../DECISIONS.md) → 2026-07-20) — the honest door is to author the decision from knowledge through `record-decision` ([surface-contract.md](surface-contract.md) → law 1: the fidelity guarantee must not read zero over a source there was nothing to be faithful to). The advisory **rides the agent/human presentation surface only** — the composed `--format json` stays the pinned `{task, text}` contract, byte-identical ([command-output-contract.md](command-output-contract.md)); the presentation nudge never leaks into the machine surface. The **from-knowledge `record-decision` path never reaches `migrate`** (it is `jigc start`/router-selected, with no source), so it is **exempt from the floor by construction** — there is no source to measure.

### The source seam (foreign content → composed context)

The read-path placeholder grammar is closed over managed state only (`data_value.rs` heads are `task`/`store`/`milestone`/managed-doc-id; `compose.rs` includes only `step:<id>`). Migration needs the foreign file's content in the composed workflow. **Settled: a CLI-owned source seam** — the `migrate` verb stages the foreign bytes into the task (a task-scoped source artifact) and a new placeholder surfaces them into the composed migration workflow as deterministic context. Composition stays reproducible and the read stays on the determinism boundary (the CLI owns the read; the agent does not fetch the file out-of-band). The seam carries **raw foreign bytes as read-only context** — it is *input to the LLM's reasoning*, never a managed doc or an addressable slot.

**The resume re-feeds the seam (M43).** The staged artifact (`<task_dir>/source`) is not a mint-time-only feed: `jigc start --task <id>` — and sub-agent re-entry, which shares the compose spine — reads it back when present and re-feeds the seam, so a resumed migration surfaces the same foreign bytes the minting `jigc migrate` composed (byte-identical minus the `task minted:` header). This is what makes the serial-collision route honest: re-invoking `jigc migrate` on a live migration blocks with `task.serial-collision` routing to `jigc start --task <id>`, and that resume now carries the source. (Before M43 the resume spine fed the seam nothing, so the route it named landed on a view whose `{{source}}` rendered empty — RC-lacon log surprise 1.) A non-migration task stages no source artifact, so its resume feeds `None`, unchanged.

### The migration workflow (the rewrite)

An off-router `migrate-changelog` workflow (the `record-change` shape) whose body: surfaces the foreign content (the source seam) → directs the LLM to author the canonical `changelog` through the existing `doc create changelog` + `add-item` (releases, nested change-groups) + `set-field` (`date`, optional `link`) + `set-slot` (`notes`) sequence → `step:migrate-finalize`. The LLM never places; every structural act is a CLI write verb. The release `date`: a foreign file that *has* a historical date sets it (the `set: on-create` today-stamp is overwritable by a `set-field` — confirmed at planning), so historical dates survive. **A *dateless* foreign file (the common case — both M24 acceptance corpora) omits the date entirely**: M24 suppresses the `set: on-create` today-stamp in migration mode (CLI-side, gated by the recorded `source-path`) so a release with no known date renders with **no date** rather than fabricating the migration day's date — an absent date finalizes clean (the engine already treats a `set: on-create` field as not author-required). See "Hardening (M24)" below.

### The review gate (fidelity)

A **net-new finalize approval gate** (not the compose-time [`checkpoint` step kind](workflow-dialect.md) — that resembles it but is a compose-time halt directive, the wrong mechanism here; and no finalize confirm-gate exists to reuse — the "opt-in confirm-gate cascade setting" referenced in older notes is unbuilt). Concretely: on a **migration task**, `jigc task finalize <id>` *without* `--approve` renders the **fidelity diff** and **exits non-zero, committing nothing**; `jigc task finalize <id> --approve` proceeds through the retire + commit + adopt. The diff compares **{the staged source-seam bytes}** (the foreign original) against **{the task working-area rendered doc}** (`.jigc/tasks/<id>/docs/changelog:changelog.md`), both read **pre-retire**; the `--approve` re-invocation re-reads both (the retire executes only within the approved run). On rejection (the human simply does not re-run with `--approve`, or `task discard`s) the foreign original is left **untouched** and nothing is adopted. This is the milestone's net-new human-in-the-loop surface and the **only** check on rewrite fidelity — the strict parse guarantees *structure*, never *content-faithfulness*.

### Retire-the-foreign-original (the first destructive write)

An off-canonical foreign path (a root `HISTORY.md`, or the old `docs/changelog/changelog.md` folder home) ≠ the managed home (post-M38 the root `placement` at `CHANGELOG.md`), so the managed write lands *beside* the original; if the foreign file is left, the reconcile sweep routes it `needs-reconcile`/advisory **forever**. (A foreign file already *at* the managed home — post-M38 a root `CHANGELOG.md` — is instead the in-location squatter that adopts in place, retire skipped; see *Path-collision guard*.) **Settled: a CLI-owned retire step folded into the finalize transaction** removes the foreign original — but **only after the review gate's approval**. This is jigc's **first byte-destructive operation on a repo file** (the `unmanage`/`uninstall` teardown verbs deliberately leave bytes on disk). It is scoped to migration, human-authorized through the review gate, and transactional with the managed write + adopt: `--approve` → {write canonical doc · retire foreign original · commit · adopt} as one finalize; reject → nothing changes. The agent never removes the file (that would be the boundary-forbidden direct placement); the CLI owns the deletion. **Replacement precondition (the retire never deletes with nothing to take its place):** the retire fires **only when the migration actually produced its canonical replacement** — i.e. the finalize promote set names a persisted managed doc. Because a migration always stages a fillable (transient, never-promoted) `commit:<id>` doc, an empty promote set means the agent authored no replacement; finalize then **blocks** (`finalize.migration-no-replacement`) rather than wipe the foreign original with no managed doc to replace it.

**The transaction mechanism (so the increment doesn't guess).** The retire rides the finalize plan (`FinalizePlan.retirements: Vec<PathBuf>`, `crates/engine/src/finalize.rs`), executed **inside the commit closure** (`crates/cli/src/task.rs` → `try_execute_finalize_plan`); the deletion is staged by the migration's own fixed pathspec staging (`stage_migration` — the #9 narrowing below, never `git add --all`) and lands in the same commit as the promoted doc. **The retirement pathspec is discriminated on the *index* (`git ls-files`), not HEAD (M40):** if the user already staged the deletion (a pre-finalize `git rm`), the pathspec is skipped — the commit is whole-index, so nothing is lost, and the stage-phase `git add` no longer fatals on a vanished path. **The rollback obligation is scoped (M40):** a commit failure *after* the retire (e.g. a rejecting pre-commit hook) must restore **what jigc deleted or staged — never what the user deleted**. Worktree restores key on the retire **byte-capture set** (`retired`); index restores key on the **staged-pathspec set** `stage_migration` now returns. The rationale is the same no-silent-destruction rule that motivated the original restore-each-retired-path obligation, extended to the *user's* acts: an unconditional restore of every *planned* retirement resurrected a user's pre-staged deletion on any commit failure — silently destroying the user's expressed intent (the F7 sibling defect; [DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 Settle; [finalize.md](finalize.md) → Rollback discipline). Atomicity = {promote + retire + commit} all-or-nothing, the same discipline promote already has.

**Path-collision guard (the in-location squatter) — defensive in M23, end-to-end authoring landed in M24.** A foreign file already at the canonical managed path is **not** a separate original to retire — the managed write would *be* the in-place rewrite. The guard (normalized path comparison): when the resolved foreign source path **equals** a promote destination, **skip the retire** so the migration never deletes the doc it just wrote. This guard is **defensive and built since M23** (it prevents data loss). What M23 could **not** do was author over the squatter end-to-end: the **idempotent-create copy-in** (`crates/engine/src/state.rs` `create` step 4, the M16 clobber-fix) seeds the migration working area by copying the *committed* doc at the canonical path in as the edit base, so a non-conformant squatter is read as the base and the author sequence builds onto non-conformant bytes — finalize then blocks (a Frankenstein doc with misleading section errors; *not* a clean `write.wrong-shape` at the write verb — the earlier wording here mislocated the seam). **M23 delivered the primary case** — a foreign file at a **non-canonical** path (a root `HISTORY.md`, the live Flow-B demand), which mints a blank canonical doc and works fully (flow 25); the squatter failed **cleanly** (nothing committed or deleted — no data loss). **The M24 fix (settled 2026-06-16):** seed the migration working area **blank** when the canonical path is occupied by the file being replaced, **gated by the same `source-path == promote-destination` discriminator the retire guard above already uses** — extended from the retire side to the create side (`state.rs` step 4 reads `read_source_path(task_dir)`; the discriminator is the migration source-path match, **never** singleton-ness, so the M16 clobber-fix stays intact for non-migration callers). See "Hardening (M24)" below. **(Post-M38:** when `changelog` relocated to a root `placement` at `CHANGELOG.md`, the *common root `CHANGELOG.md`* became the canonical destination — so the create-side discriminator (`migration_targets_canonical_destination`) was taught to derive that destination from `placement.file`, not `location`; a foreign root `CHANGELOG.md` now seeds blank + adopts in place, byte-stable, `M CHANGELOG.md` never `D`. See flow-26 `flow26_at_canonical_root_changelog_adopts_in_place`.**)**

### Adopt (the existing path)

Once the canonical doc is written + the foreign original retired, finalize adopts via the unchanged register-only path (parse → conformance-gate → `index.absorb_doc` → file-state hash). Confirmed at planning: the previously-Unmanaged state of the target path does not block the fresh conformant write (no `DRIFTED+TOUCHED` conflict — the managed write lands at the lowercase singleton path, distinct from the foreign sibling, which the retire step removes).

## Engine / validation work this milestone earns

1. **Enforce the enum on `id-from` fields.** Conformance today exempts the `id-from` field at every level (`crates/engine/src/validate.rs` → `check_item_leaves`), and the changelog change-group's `category` (the enum) *is* its `id-from` — so a foreign category (`Performance`, `Breaking Changes`) is currently adopted as "conformant" with a value the schema's own enum forbids. This hollows out the "adopted iff conformant" guarantee the whole migration leans on. **The fix is a *new* code path, not un-exempting `check_item_field`:** the id-from value is **not** in `item.fields` — it lives in the parsed item **heading** (`ParsedItem.title`/`.id`), so `check_item_field` (which looks the value up in `item.fields`) would wrongly emit `required-field-present`. The new path reads the id-from value off the heading and, when that field declares an `enum`, checks membership by **re-slugging** the heading value and comparing against the (slug-form) enum members — so a foreign `Fixed`/`Added` normalizes to the valid member `fixed`/`added` and **passes** (the same re-slug discipline the multi-word-section-id parser fix uses), while a genuinely foreign `Performance` → `performance` ∉ enum is **rejected**, forcing the LLM to map it. (The check thus guarantees *membership of the normalized value*, not *semantic faithfulness* — a foreign category that coincidentally slugs to a valid member is the human review gate's residue, not the enum's.) **Scope:** the shared `schema_conformance` path (the gate `migrate`'s strict-parse and `finalize` both call) — additive; an `id-from` field with a **non-`enum`** type stays exempt (every other shipped doctype's `id-from` is a `title`/`key` string — verified at planning — so none newly fails). **Build-pin:** the exact finding code (expected `schema-conformance.field-value-conformant`) and the leaf-suffix of the emitted address are pinned at the build spike against the real binary, and flow 25's RED 1 updated to match.
2. **The source seam** (above) — the CLI-owned foreign-content-into-context surface.
3. **The `migrate` verb + the retire step** — the new CLI surface + the destructive-write-in-finalize-transaction.
4. **The review-gate halt** — the foreign-vs-canonical diff + the approval block (a `checkpoint`-class halt specialized to a fidelity diff).

**Slug collision — accept-and-block (no new work).** `slugify` drops dots, so `1.2.0` and `1.20` both mint `120`; `add-item` hard-rejects the second with `write.already-present` (it does **not** suffix — `suffixed()` is the join-time assigner's, never the mint site's). **Settled: accept-and-block** — a foreign changelog whose versions collide under slugify blocks loudly and routes to the human, rather than silently fabricating a fake version id. Rare, loud, and consistent with the review-gate posture. No engine change; recorded as a bound.

**Byte-stability finding — deferred (off the critical path).** The logged empty-slot + field-group render instability ([decisions-pending.md](../implementation/decisions-pending.md)) lives only in items carrying *both* a slot and a field group. The changelog's items are slot-only (change-group `notes`) or field-only (release `date`/`link`) — never both — so changelog migration is **clear** of it. Decompose must confirm the migration author-sequence never re-parses a minted-empty slotted item (it won't — changelog has no such item; and M24's declarative batch is parse-once/render-once, so it adds no inter-verb reparse). The fix stays its own focused milestone (**M26 — arch-doc**, whose slot+field component items are the natural trigger; re-keyed from M24 at the 2026-06-16 sequence reset).

## Hardening (M24) — make the changelog reference correct before generalizing

**Settled at M24 planning (2026-06-16; [DECISIONS.md](../DECISIONS.md) → 2026-06-16 M24 planning).** A manual smoke test ran the M23 spine on two real dateless repos (project-delta, project-gamma). It proved the spine works end-to-end at scale but surfaced friction that is **mostly general migration/authoring mechanism** — so M24 fixes it **once, on the changelog reference**, before M25 copies the pattern to `adr`/`spec`/`prd` (and M26 to `arch-doc`). **No new schemas.** The fixes (each verified against the binary at planning by capability-auditors + gap-detectors):

1. **Declarative whole-doc batch authoring** (the largest fix; the verbosity-at-scale answer). A new `jigc doc author <doctype> --from-file <payload>` verb: the **agent authors one structured payload** (owning the prose), the **CLI applies create + N `add-item` + `set-slot`/`set-field` over a single in-memory buffer, persisting once**. Migrating project-delta' 12 / project-gamma's ~50 releases per-leaf is hundreds of agent round-trips; the batch collapses it. The shape is **declarative whole-doc**, *not* the originally-deferred fillable emit-fill-extract form (that was scoped for multi-*slot* single docs and has no story for repeatable expansion — "add the 13th release"; see [write-commands.md](write-commands.md)). **Implementation pinned (review B1):** the **chain-the-existing-splice-primitives** path — the create runs through the same `create_gated` path (so the create-gate *and* the squatter blank-seed fix #8 both apply), then each splice primitive is chained over the running buffer with **no persist between leaves**; it does **not** build an `Instance` and re-`render` (that canonicalizing path would bypass byte-preservation, the create-gate, and the #8 seam). This is exactly the per-verb chain M23 proved byte-stable at 607 lines minus the intermediate persists (byte no-ops), so byte-stability is inherited **by construction**. The batch is **doctype-general** and operates on the *staged buffer* — it does **not** touch the `{{source}}` seam (which feeds compose context), so the determinism boundary is intact (agent authors the payload; CLI places every leaf).
2. **`remove-item` verb (top-level AND nested).** Expose `jigc doc remove-item <addr>` as a general recovery verb. The engine's `remove_item` is top-level-only; the smoke test's own example (a wrong *category*) is a **nested** change-group, so M24 also builds `remove_nested_item` (the parent-scoped id-chain dual of `add_nested_item`).
3. **Write-time value validation** (immediate feedback instead of finalize-only). Move the id-from-enum check to `add-item` time (the category enum is the id-from in the item *heading*, not in `item.fields`), and **close the logged item-field value-validation parity gap** (wire the existing `check_value` into the item/nested-item `set-field` write path). **One shared slug+enum-membership helper** is called by both the write-time path and finalize's `check_id_from_enum` (not a mirrored copy — drift risk, esp. as M25 copies the mechanism to four doctypes; review S3): same finding *code* at write-time and finalize, by construction; the emitted *address* leaf-suffix may differ by call site (at `add-item` time there is no parsed item yet).
4. **Auto-provision a formulaic migration commit doc.** The migration commit is mechanical, so the CLI provisions it filled rather than blocking finalize on empty author-required commit fields. **`type`/`scope` are *fields*** → filled through the **existing doc-level `default:`/`set: on-create` materialization** (M22 inc-4, no boundary crossing). Only **`summary`/`body` are *slots*** → the genuine (narrow) crossing. **Bounded rule (review S2):** the CLI may fill a slot only when its content is a *pure deterministic function of structural facts* (here: source path + doctype) — **never judgment**; this is what keeps the precedent from generalizing toward the "not an auto-doc-writer" non-goal. The templated summary/body is exactly such a function.
5. **Structural fidelity summary at the review gate.** Beside the raw foreign-vs-canonical diff, list the release-level delta ("source releases absent from the rewrite: …") so a reviewer needn't eyeball that N of M releases were dropped. The canonical side is reparseable for release ids; the foreign side is non-conformant, so it is a **heuristic version-scan**. **Negative guard (review C4):** the scan's output is **rendered to the human only** — it feeds **no** structural decision, no gate, no agent logic — and is **labeled fuzzy** in the diff (the foreign side being non-conformant, the scan can miss or invent a release). This keeps it an advisory review aid, never a second structural authority (Framing A intact). **M40 calibration fix ([DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 Settle):** the kept-set side of the scan was **heading-only** — a changelog-shaped assumption (there, releases *are* headings) that false-alarmed on every other doctype (a version token kept in body prose still read as "dropped"); the kept-set now scans the **whole rewrite text**. The trailing-dot under-report (`since 1.5.` — the sentence dot escaped the token scan) is fixed in the same motion. The honest "heuristic / advisory, human-only" label survives unchanged.
6. **Dateless release date.** Real changelogs are commonly dateless; the `set: on-create` stamp would fabricate the migration day as false history. M24 suppresses the today-stamp in migration mode (CLI-side, gated by the recorded `source-path`), rendering **no date** when the source has none. No schema change (an absent `set: on-create` date already finalizes clean).
7. **Category map + merge guidance.** The `author-migration` step guidance must instruct the agent to map foreign categories onto the enum **and merge many-to-one** (two foreign categories → one member can't be two groups — the enum is the id-from, so they collide), plus infer the member from `feat:`/`fix:` prefixes when a foreign file has no category headings. Guidance-only; the merge constraint is already structurally enforced.
8. **In-location-squatter authoring** (see *Path-collision guard* above) — seed the working area blank over an occupied canonical path.

## Generalizing to adr/spec/prd (M25)

**Settled at M25 planning (2026-06-17; [DECISIONS.md](../DECISIONS.md) → 2026-06-17 M25 planning).** M24 made the changelog migration a *correct* reference; M25 copies the corrected pattern to the three **location-bearing, multi-instance** doctypes `adr`/`spec`/`prd`. The verb arg surface, the source seam, the review gate, the retire transaction, and the declarative `doc author --from-file` batch are all **doctype-parameterized and proven on the changelog singleton** — M25's work is the *shape differences*, baseline-verified by exercise against the binary (not reasoned by analogy). `arch-doc` migration + code-inferred docs stay **M26+** (out of scope). **No determinism-boundary change** — the same Framing A: LLM rewrites foreign prose through the write verbs; the CLI strict-parses + conformance-gates + adopts iff conformant.

### Migration model — one file, one task, sequential (NOT a repo sweep)

`jigc migrate <path> --as <doctype>` stays **one foreign file → one managed doc → one commit**; a corpus of N foreign ADRs is **N invocations**, not a directory sweep. The multi-doctype/multi-instance one-pass (the Open-questions fork below) is **explicitly not built** — it would need an N-source seam + multi-valued source-path recording + a retire-planner loop, and the smaller model delivers "a real corpus migrated end-to-end, measured" without new transaction code. (Multi-*promotion* per task is already built — `plan_promotions` walks all staged docs — but the source seam + `plan_retirements` are single-file *by construction*, so one-source-one-task is the grain.)

The one blocker the model forces: the **migration task id is the fixed singleton `migrate-<doctype>`** (`crates/cli/src/start.rs:114`; `mint_task` hard-rejects a collision, never suffixes), so a second `migrate --as adr` collides — a multi-instance corpus can't be expressed. **Fix:** derive the migration task id-source from the source file (`migrate-<doctype>-<slug(stem)>`). **Blast radius is contained** (verified) — the source-path recording, retire guard, and squatter discriminator all read the task *directory*, not the id string; the `commit:<id>` slug and the `{{task.id}}` placeholder follow the id automatically. Only the mint id-source string changes. *Owed (I)-pick at build pickup:* `mint_task` hard-rejects a colliding id (never suffixes, `state.rs:421`), so two foreign files with the **same stem in different dirs** (`docs/adr/0001-x.md`, `archive/0001-x.md`) would collide — the id-source must be made unique either **path-aware** (fold the dir into the slug) or via a **mint-suffix loop**. Name the pick so the build doesn't ship the naive stem-only id and rediscover the collision.

### Edge migration + the ordering contract (adr.supersedes)

Changelog was edge-free; `adr` carries `supersedes` (adr→adr) + `cites-code`. Migrating a set of cross-referencing foreign ADRs must wire + resolve the forward-refs at finalize. The `ref-resolves` gate resolves a target in **the committed store OR this task's working area** — so under the one-file-one-task model, B-`supersedes`-A resolves only if **A is committed before B finalizes**. M25 does **not** add cross-task transaction machinery; instead the `migrate-adr` guidance carries a **dependency-ordering contract**: migrate + finalize a supersession *target* before the ADR that supersedes it. (A within-task multi-adr authoring would resolve edges in the shared working area without ordering, but that is the multi-instance-one-pass model M25 declined.)

**Out-of-set targets drop to prose (the partial-corpus escape).** A foreign ADR commonly supersedes a prior the operator does **not** migrate (it predates the corpus, or is deliberately left foreign). Such a `supersedes` resolves in neither the store nor the working area and would **block finalize forever** — there is no edge to satisfy. So the `migrate-adr` guidance must instruct: **a `supersedes` whose target is not (and will not be) a migrated ADR is dropped to prose** (the same accepted-drop posture as "Related ADRs"), never authored as a dangling ref. Only an *in-set* supersession becomes a structural edge.

**`supersedes` widened `0..1` → `0..*`** (inverse `superseded-by` likewise). Cardinality is **not enforced today** — a bracket-list `[adr:a, adr:b]` already authors *and* validates clean, so `0..1` is a decorative lie — and a real ADR commonly supersedes multiple priors. *Re-pin churn the increment inherits* (verified): the widen touches `crates/engine/src/schema.rs:636`, the snapshot `engine__schema__tests__schema_adr.snap:35`, and the embedded schema text in `crates/cli/tests/validate_envelope.rs:457`; existing supersedes fixtures already use the typed `adr:<slug>` form, so the ref-shape check below breaks none of them.

**Write-time ref-shape check (net-new, scope-pinned).** A `ref`-typed value is shape-blind at write today (`crates/engine/src/write.rs` `check_value` → the opaque-scalar floor): a bare slug (`use-postgres` instead of `adr:use-postgres`) authors clean and only dangles at finalize with a *missing-target* message rather than a *malformed-shape* one. Migration *manufactures* these addresses from foreign prose, so M25 adds an immediate shape check in the shared `check_value`: **a ref value must be `<type>:<slug>` with `type` matching the field's declared `to:` AND the `<slug>` portion matching the slug grammar** (for a list ref, each element). Validating the slug body — not just the type prefix — is deliberate: it **catches the unbracketed comma form** (`adr:a, adr:b` splits to type `adr` + a non-slug remainder `a, adr:b` → rejected), closing that footgun at write rather than letting it dangle at finalize. *Scope — two call sites (the M24 enum precedent):* `check_value` is reached from `set_field_validated` (`write.rs`, emitting **`write.malformed-value`**) **and** the conformance gate (`validate.rs`, wrapping the same error as **`schema-conformance.field-value-conformant`**); the addition therefore also blocks a malformed ref at finalize as `field-value-conformant` rather than at `ref-resolves`. The finalize `ref-resolves` gate stays the *existence* check for well-formed refs. Additive — non-ref fields and well-formed refs unaffected. Pin both finding codes at the build spike. *(Guidance still recommends the bracket-list for multi-supersede readability, but it is no longer the only guard — the comma form now fails loudly.)*

### Doc-level date-suppression (the M24 trap M25 inherits)

M24's migration date-suppression is **item-level only** (`on_create_item_fields(…, migration)`); `adr`'s `date` is a **doc-level header field**, materialized by `on_create_doc_fields` (`crates/cli/src/doc.rs:765`) which takes **no migration flag** and unconditionally stamps today. So a *dateless* foreign ADR would fabricate the migration day as false decision history — the exact bug M24 fixed for changelog releases. **Fix:** thread the migration discriminator into `on_create_doc_fields` (mirror the item-level deriver), skipping the today-stamp in migration mode. An *explicit* date in the payload already survives (the on-create stamp is overwritable — proven), so only dateless ADRs need this. `spec`/`prd` carry no date field — moot for them.

### Per-doctype migration workflows + author guidance

Each target gets a `migrate-<doctype>.yaml` workflow (the `migrate-changelog` shape: source seam → author step → migrate-finalize) and a **doctype-specific author-migration guidance step** — the shipped `author-migration.yaml` is changelog-shaped (category enum, KaC `[Unreleased]` rules) and is **not** a reusable shell. The guidance describes that schema's section/field/ref map: `adr` → Status/Context/Decision/Consequences heading map + the `supersedes` bracket-list + ordering contract + foreign-status→enum mapping; `spec` → goal/context slots + criteria extraction; `prd` → vision/context slots + the repeatable requirements. The review-gate **structural fidelity summary** (changelog's version-scan) has no analog here — M25 falls back to the **raw foreign-vs-canonical diff** for the location-bearing doctypes (a per-doctype structural summary is not earned).

### prd — repeatable requirements (no engine code, but NOT a free pack swap)

`prd`'s `requirements` fixed slot becomes a **repeatable section** (per-requirement `title` field + `statement` slot, mirroring `spec.criteria` minus the code-anchor); `vision`/`context` stay fixed slots. **No engine code** — `add-item` (M13) + multi-word-heading (M22) are both built and exercised; the repeatable item carries no on-create field, so it does **not** trip the M26-keyed empty-slot+field-group byte-instability.

**But it is not "pack-only zero-cost" (M25 review correction).** `requirements` is authored as a **prose slot** by `prd`'s only shipped driver — the project-setup **Flow-1 greenfield** path (`crates/cli/pack/steps/author-prd.yaml` → `<<author: {{ task.brief#requirements }}>>`; acceptance `crates/cli/tests/flow11_new_project_arc.rs:194` `set-slot prd:…#requirements`). Converting the slot to a repeatable section **breaks that slot-author directive and its test**, and raises a real design question the migration path doesn't answer: a greenfield idea-development flow has no foreign requirement list to read, so **how does it author repeatable requirements?** M25 owns this: route the Flow-1 prd authoring onto the **per-requirement item path** (the agent develops each requirement as an `add-item`/`doc author` item, the same shape migration uses), and absorb the blast radius — **`author-prd.yaml`** (+ `develop-idea.yaml` if it references the slot), **`flow11_new_project_arc.rs`**, and the **prd render golden**. The `prd —decomposes-into→ spec` edge stays **deferred** (needs a new header section — prd has no field-bearing section — and re-incurs the ref landmine with no migration driver).

### The author-migration-arch-doc guidance (the substance of M26)

Framing A intact — the LLM rewrites foreign prose through the write verbs; the CLI strict-parses + places. The guidance describes arch-doc's section/field map and its six obligations, each exercise-confirmed at planning:

- **Heading map.** Foreign Overview/Introduction/Summary → the `overview` slot; foreign component/module sections → `components` items (`title` + `description` + optional `implemented-by`); foreign "see ADR-N"/decision references → the doc-level `cites`. Section ids stay the fixed single words (`meta`/`overview`/`components`) — a multi-word id trips the latent title-case reparse defect (component *titles* on `###` headings are free text, unaffected).
- **Every required slot must be filled — `overview` *and* each component `description`.** Both block finalize at `required-slot-present` when empty (neither can drop-to-prose like an optional field). The guidance instructs the agent to **synthesize** when the foreign source has none: a one-line responsibility for a `description` (from the component's name + its implementing symbol), and a one-line boundary/scope statement for the `overview` (from the document title + the component set) when the foreign doc has no dedicated overview/introduction/summary section. (Keeping `description` required is deliberate — making it optional would turn the empty-slot+field-group shape into a *persistent, promotable* doc, an unexercised round-trip.)
- **`implemented-by` is author-optional — anchor a concrete symbol verbatim, else omit.** Architectural components are coarser than one symbol; a foreign prose pointer ("the auth module") is not a resolvable `path#symbol`. The guidance mirrors spec-migration's `maps-to-test` posture: wire `implemented-by` only when carrying over a concrete `path#symbol`, else omit (an omitted anchor finalizes clean). **A present but non-resolving anchor blocks** at `doc-code.symbol-exists`.
- **`cites` is bracketed, in-store-only, drop-to-prose otherwise.** Multi-cite must be authored as **one bracketed list** `[adr:a, adr:b]` (set-field replaces, does not append). A foreign "see ADR-12" becomes `cites: [adr:<slug>]` **only** when that adr is in the committed store; an out-of-store decision reference **drops to prose**, never authored as a dangling ref (a dangling `cites` blocks finalize forever). Mirrors the adr-migration `supersedes` posture.
- **Committed-first ordering.** A cited adr must be migrated + committed **before** the arch-doc that cites it (the `ref-resolves` gate resolves against the committed store OR this task's working area; arch-doc's `allows-create` cannot mint an adr in-task). Relevant when a corpus migrates ADRs and arch-docs together — migrate the `decisions/` corpus first.
- **Slug-distinct component titles + no agent-authored commit.** Two component titles that slugify identically fail the whole batch atomically (`write.already-present`) — the guidance requires distinct titles. The migration `commit` doc is **auto-provisioned** (the M24 path); the agent authors only the one arch-doc batch (agent-call count = 1), never `doc author commit` (gate-blocked).

### Byte-stability (the M26-keyed fix — corrected and decoupled)

The empty-slot+field-group instability ([decisions-pending.md](../implementation/decisions-pending.md)) **does fire** on arch-doc's `components` (a `description` slot + an `implemented-by` field) — and it fires through the **declarative batch**, not only individual verbs: `doc author --from-file` applies leaves **per-leaf over one buffer**, so an `AddItem` leaf (`slot:None` → `\n\n`) followed by a `SetField` leaf reparses to `slot:Some("")` → `\n\n\n\n`. **The earlier "the batch is parse-once/render-once, so it never trips the bug" reasoning was factually wrong** (M24/M25 decompose notes) — the trigger is the inter-leaf reparse. **But the conclusion holds:** `required-slot-present` blocks the unfilled-`description` component from committing, and the unstable form is a non-growing fixed point. So the fix is a **#1-risk byte-stability paydown decoupled from migration working** (it lands as M26 Increment 1, isolated and **non-gating**; its acceptance is an engine `render(parse(x))==x` test, not a migration flow). Direction + blast radius live in the fix's design home, [parsing.md](../implementation/parsing.md) → Round-trip guarantees.

### doc↔code on a migrated arch-doc (the genuinely-new combination)

M26 is the **first** migration to author a *resolving* code anchor — M25 deliberately omitted them (adr's `cites-code` deferred to "a separate cross-code pass"; spec authored zero `maps-to-test`). The `doc-code` `symbol-exists` probe runs at finalize over each migrated `implemented-by`; the sibling probe binary is found beside the installed `jigc` from any repo (the M20 embed-extract — verified from a non-jigc repo at planning). **Caveat (Rust-only): `doc-code` resolves symbols only in `.rs` files** — a present non-`.rs` file with a *vanished* symbol finalizes clean (the probe returns no verdict). So a foreign arch-doc over non-Rust code makes its anchors **file-exists-only**; genuinely exercising the symbol-exists guarantee requires a **Rust target**. (At M26; generalized at M27 — `doc-code` now resolves symbols across six languages, so a non-`.rs` anchor returns a real verdict, [validation.md](validation.md) → Multi-language resolution / worked-examples flow 29.) This drives the corpus shape below.

## Generalizing to the methodology work docs (M40 — the rc.4 wave)

**Settled at M40 planning (2026-07-10; [DECISIONS.md](../DECISIONS.md) → 2026-07-10 M40 planning: Settle).** The adoption trial's migration half ran a full foreign GSD corpus against rc.3 and hit the gap precisely: `migrate --as` routes by a `migrate-` prefix scan of the composed packs' workflows (no Rust enumeration), and the methodology pack ships **zero** — so the adopter's majority doc class (planning docs) was unreachable. **All seven templates are mechanical decision trees — the dashbard lesson.** The trial showed agents excel where the template *pre-makes* a decision and flounder where they must *derive* one; so each guidance step is written as a decision tree the agent transcribes, never judgment it exercises. Two rules recur:

- **Historic dates: TRANSCRIBE or OMIT, never fabricate.** Migration mode already suppresses the `set: on-create` today-stamp at doc level *and* per item, so a foreign entry with a date `set-field`s it verbatim and a dateless one renders dateless (the M24 rule). The `decisions-log`/`deferral-ledger` templates must carry this rule **explicitly, per entry** — or every migrated entry silently goes dateless.
- **Refs to nonexistent targets are OMITTED, never authored dangling** (the M25 drop-to-prose posture).

Per doctype:

- **vision** — the three slots (`thesis` / `invariants` / `open-questions`). The template instructs **OMIT `grounded-in`** (legal — it is `0..*`): a foreign vision has no managed `research` to ground in, so the ref would dangle at finalize. Surplus foreign content with no slot home **folds into `open-questions` or drops** — a **conscious departure** from changelog's "preamble dropped" precedent: a changelog preamble is boilerplate; a vision's stray content is usually a live open question worth keeping.
- **roadmap** — per-milestone items carry a **two-slot payload** (`proves` + `decomposition`) authored in one `doc author --from-file` item. The two-slot item payload is exercised (spiked against the installed rc.3 binary at M40 planning) — one item with both slot keys in one `set:` map renders both `#### Proves` / `#### Decomposition` sub-headings.
- **decisions-log / deferral-ledger** — the historic-date rule above, per entry. `deferral-ledger`'s `kind` enum gets explicit **`[D, I]` mapping guidance** (a deferred *decision* → `D`; a parked *idea/direction* → `I`).
- **idea** — a mechanical mirror; the template **names the `trigger` field explicitly** (the F1 lesson: a required field the guidance never names is invisible at the create path).
- **research** — a mechanical mirror (ref-free leaf). Included deliberately as the seventh: the coverage map called it optional, but the orphan advisory's unregistered-arm route ([validation.md](validation.md) → Orphan detection, the M40 two-tier) dead-ends on `research/notes.md` — its own motivating example — without it.
- **completion-record — the artifact ladder.** `owner-artifact` is an owned-location, author-required field whose presence gate is **floored blocking and stays untouched — no migration carve-out** (M17's rationale holds). The template resolves it as a mechanical ladder: **rung 1** — evidence already lives under `completions/artifacts/<milestone>/` → point `owner-artifact` at it; **rung 2** — evidence exists elsewhere → copy it under the owned home + stage it; **rung 3** — no evidence file exists → **the verbatim foreign source itself is the artifact** (copy it under the home *before* finalize retires the original); **refusal rung** — no verdict is derivable from the source → it is **not** a completion record; route it to stay-unmanaged or another doctype.

**Exclusions, with reasons:** **`milestone-record`** (machine-maintained — minted and advanced by the milestone machinery, no authored prose to migrate) and **`dogfood-record`** (foreign instances implausible — nothing outside this methodology writes one).

**Couplings, recorded so the build doesn't rediscover them:** setup composes the methodology pack unconditionally, so all seven workflows go live in every project (the migratable set → 12 everywhere); `jigc migrate --help`'s hardcoded doctype enumeration (×2, compile-time clap text) is **de-enumerated** in the same wave ("any doctype with a shipped `migrate-<doctype>` workflow — see the error message for the live set"); and the fidelity-scan calibration (#5 above) lands **before** these workflows — methodology corpora are version-token-saturated, so the heading-only kept-set would drown their acceptance in false alarms.

## Migration-quality measure (the done-bar)

The milestone's goal is the Flow-B live test, so its done-bar is a **measured migration-quality baseline** (the M17 discipline: "a capability installs" ≠ "a comparative win").

- **M23 corpus:** 3–5 real public `CHANGELOG.md` files of varying conformance (clean Keep-a-Changelog, a loosely-structured one, a non-KaC-categories one, a multi-release one).
- **M24 corpus (the hardening done-bar):** the **FULL** `project-delta` + `project-gamma` live migration on throwaway clones — **all** releases, not a sampler — the same two real repos the smoke test ran on.
- **Metrics:** (a) **round-trip conformance** — does the rewrite parse + conformance-gate + adopt? (b) **human-acceptance of fidelity** — the review gate's verdict (did the rewrite faithfully preserve the content?); (c) **content-preservation spot-check** — no silent data loss beyond the accepted-drops bound above; **(d) agent-call count** (M24) — the number of CLI/agent round-trips to author the full migration, the verbosity signal the declarative batch (#1) is built to cut. This is a migration-specific headline distinct from [measurement.md](measurement.md)'s adapter-adherence stance (where raw invocations are telemetry, never the headline).

The measure is recorded alongside the run (the [measurement.md](measurement.md) posture), not engine-emitted.

## Acceptance — worked-examples flow 25

[worked-examples.md](worked-examples.md) → flow 25 is the **M23** acceptance bar: a real non-conformant foreign off-canonical changelog (a root `HISTORY.md`, `Unmanaged`) → `jigc migrate HISTORY.md --as changelog` mints the off-router task and surfaces the foreign content → the LLM rewrites it through the write verbs → the review gate shows the fidelity diff → **approve** → finalize writes the canonical `changelog` (post-M38 root `CHANGELOG.md`), retires the foreign original, adopts (the managed doc round-trips byte-stable; the foreign file is gone; a follow-up `ingest` reports it adoptable/adopted); plus the reds — a non-conformant rewrite (a foreign category outside the enum) **blocks** at conformance, and a **human-reject** of the diff leaves the foreign original untouched and adopts nothing. (A foreign file already *at* the post-M38 canonical root `CHANGELOG.md` instead **adopts in place** — the retire is skipped; flow-26 `flow26_at_canonical_root_changelog_adopts_in_place`.)

**M24 acceptance — [worked-examples.md](worked-examples.md) → flow 26 (the hardened path):** the **full** `project-delta` + `project-gamma` live migration (all releases, throwaway clones), authored through the **declarative batch** (#1), measured on the four facts above incl. **agent-call count**; with the hardened behaviours exercised — dateless releases render with no date (#6), a write-time enum reject fires at `add-item` not finalize (#3), `remove-item` retracts a mis-authored nested change-group (#2), the migration commit doc is auto-provisioned (#4), the review gate shows the structural release-delta summary (#5), and the in-location squatter now authors end-to-end (#8).

**M25 acceptance — [worked-examples.md](worked-examples.md) → flow 27:** the real `adr`/`spec`/synthetic-`prd` corpus migrated one file at a time, edge-wiring + ordering contract across the set, measured on the four facts.

## Open questions

- **The source-seam placeholder syntax** — the exact spelling of the foreign-content placeholder (a `{{source}}`-class read-only context surface) is an elaboration for the build; it must stay syntactically distinct from a managed-doc deref (`{{@…}}`) since it carries non-managed bytes.
- **Multi-doctype / multi-instance migration in one pass** — **resolved at M25 planning (2026-06-17): NOT built.** `migrate` stays **one-file-one-`--as`-invocation, sequential** (see *Generalizing to adr/spec/prd* above); a corpus is N invocations, each one file → one doc → one commit. A repo/dir sweep + an N-source seam + multi-valued retire stays a future fork (the larger model), re-opened only if a real corpus makes the N-invocation cost hurt.
- **Code-inferred docs** (M25+, the north star) — inferring an `arch-doc` from the codebase or ADRs from scattered notes is the destination, not M25. Stays open.
