Verdict: **not ready to decompose**. D1, D2, D3, D4, and D5 still contain safety- or contract-defining forks disguised as implementation detail. Decomposing now would let increment authors silently settle them.

## Findings

### 1. CRITICAL — D1 remains vulnerable to symlink substitution between validation and deletion

D1 validates a pathname and later reopens it by name. The shipped predicate canonicalizes the current target at [trackable.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/src/trackable.rs:55), but `retire` independently reconstructs and opens it at [task.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/src/task.rs:3016). Between those operations, an in-repository path or ancestor can be replaced with a symlink to an external file. The subsequent `read` and `remove_file` follow the new resolution.

The same weakness exists if D1 validates `plan.retirements` once before entering the commit closure: promotions and other work occur before retirement at [task.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/src/task.rs:2760), enlarging the substitution window.

Concrete correction: D1 must require a race-resistant sink, not merely “CLI-side validation before retire.” Open the repository root and traverse components without following symlinks, then unlink relative to the held directory descriptor; on platforms where that cannot be supported, fail closed. At minimum, bind validation and deletion to an identity tuple and re-check immediately before deletion, while acknowledging that this only narrows—not closes—the race.

Also prohibit non-literal Git pathspec syntax before any recorded path reaches Git. `--` prevents option parsing, not pathspec magic such as `:(top)…`.

### 2. HIGH — D2 probes the wrong boundaries; ordinary commits retain a posture TOCTOU hole

D2 says “probe at the door and at `overlay_docs_commit_and_ff`.” Ordinary commits still reach `git_commit_capture` at [task.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/src/task.rs:4255) without a mandatory seam-level posture check.

A door can pass its initial probe, then a hook, concurrent process, or earlier command phase can detach or move HEAD, create an operation marker, or change the checked-out branch before `git commit`. The dedicated-worktree exemption does not justify omitting the check: the commit seam needs an explicit typed posture subject.

Concrete correction: make the posture token mandatory at every commit/move seam:

- `LiveCheckout { expected_repo, expected_branch }`
- `DedicatedWorktree { expected_parent }`

Re-probe immediately before each `git commit`, `git mv` batch, and live-checkout fast-forward. Verify repository identity and expected ref, not merely “HEAD is attached.” Keep the second live-checkout probe immediately before `merge --ff-only` at [task.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/src/task.rs:4447).

The exemption must have a private constructor minted only by `DedicatedWorktree::add`; a public enum variant or caller-supplied boolean merely makes it forgeable inside the codebase.

### 3. HIGH — D3’s `StagedSnapshot` pair cannot answer “bytes setup did not write”

`StagedSnapshot` describes index state. D3’s subject includes unstaged worktree bytes. The already-driven `MM CLAUDE.md` case proves the distinction:

- pre-run index contains A;
- pre-run worktree contains B;
- setup stages B;
- post-run index contains B.

Comparing staged snapshots sees A→B and can incorrectly classify B as setup-authored, although B existed before setup. Conversely, a same-blob pre-existing staged edit can be mistaken for previously installed content.

This is not fixed by rerun idempotency. On a fresh clone, unchanged committed installation bytes should yield no commit; that case is easy. The hard cases are upgrades and locally edited host files where current committed bytes, index bytes, worktree bytes, previous generated bytes, and newly generated bytes may all differ.

Concrete correction: replace “a pathspec-scoped `StagedSnapshot` pair” with a four-state per-path attribution record captured before any write:

- HEAD blob or absence;
- index blob or absence;
- worktree bytes or absence;
- exact bytes setup proposes to write.

After installation, refuse the commit if the staged result contains any pre-run worktree or index bytes not exactly attributable to setup’s deterministic output. For merged host files, record ownership at marker/block granularity; whole-file hashes cannot distinguish preserved user content from generated content. Specify upgrade and fresh-clone truth tables before decomposition.

### 4. HIGH — D4 rollback can destroy a concurrent user edit

D4 captures a worktree pre-image, mutates `.jigc/.gitignore` and `.jigc/version`, and restores the captured bytes after failure. If a user or editor modifies either file after capture but before rollback, unconditional restoration clobbers that new edit.

The existing operation spans promotion, retirement, ignore maintenance, staging, hooks, and possibly fan-out commits, so this is not a negligible interval; see [task.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/src/task.rs:2760).

Concrete correction: every worktree rollback entry must contain:

- pre-image;
- exact post-write image produced by jigc;
- file identity where available.

Restore only if the current file still equals the jigc-produced post-image. If it differs, do not overwrite it; report a rollback-conflict finding and preserve both versions through a recoverable side file or explicit route. Absence restoration needs the same compare-and-swap rule.

### 5. HIGH — D5 does not define “arm,” so its proposed bijection is not sound

The existing recipe registry has one row per clap leaf at [format_json_success_axis.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/tests/format_json_success_axis.rs:389). D5 changes this to `(path, arm)` but never defines an arm enumerator.

Several leaves have more semantic/output arms than the Settle counts:

- `start`: orientation, default non-minting compose, explicit minting compose, resume, and explain;
- `workflow`: preview and sub-task re-entry;
- `setup`: committed, unchanged, and benign-uncommitted success;
- `task finalize`: dry-run, review hold, blocked, ordinary landed, and milestone/fan-out contexts;
- `milestone finalize`: record-only, squash aggregate, per-subtask chain, blocked, and no-op/error-adjacent shapes;
- `migrate-corpus`: dry-run, no-commit, committed migration, and recovery/previously-unlanded success;
- `describe`: selector combinations;
- list verbs: empty and non-empty collections where top-level shape or optional keys can differ.

A hand-written arm string cannot be bijected against clap because clap enumerates syntax, not runtime result variants.

Concrete correction: define `EnvelopeArm` in production beside each renderer, with an exhaustive `ALL` or derive it from the result enum. Registry keys must be `(leaf path, EnvelopeArm)`. Tests must prove:

1. every clap leaf has at least one arm;
2. every production arm has exactly one registry row;
3. every registry row is driven;
4. the driven key set equals the declared key set.

Until that exists, D5’s “every verb × arm” is not an implementable completeness claim.

### 6. MEDIUM — D1’s six-member registry is complete only as an argument-ID census, not as a rule registry

The six IDs—`path`, `file`, `from_file`, `from`, `target`, `value`—match the current `ArgToken::Plain` documentation plus the discovered `value` case at [cli.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/src/cli.rs:1490). I found no seventh plain argument ID in the reviewed clap tree that directly becomes a filesystem join or Git pathname.

But “one rule per member” is unsound because one ID appears at semantically different leaves:

- `path` is both `migrate` input and `unmanage` input;
- `file` occurs at both insert-step and replace-step;
- `target` describes several non-filesystem address grammars;
- `value` is path-like only when `key == docs-root`;
- `from_file` includes the sentinel `-`, which is not a path;
- `from` can describe a directory or literal file home.

Concrete correction: key the registry by `(leaf path, argument id, conditional arm)`, not argument ID alone. For example, `("config set", "value", key == "docs-root")` and `("config fill", "from_file", File | Stdin)`. The ⇔ fence must cover occurrences, not deduplicated clap IDs.

### 7. MEDIUM — D2’s registry subject is internally ambiguous about staged moves

The proposed registry is named “doors that commit or move on the user’s behalf.” That necessarily includes more than the current committing seams:

- `config set docs-root`, which stages `git mv` operations;
- `relocate`;
- `rename`;
- migration relocation;
- milestone live-checkout fast-forward;
- setup;
- task and milestone commits.

If the registry instead contains only commands that make commits, its name and D2 claim are false. If it contains staged movers, the design must decide whether detached HEAD, unborn HEAD, or an in-progress merge should prohibit a non-committing `git mv`. That workflow policy was not settled.

Concrete correction: split it into `COMMIT_ON_BEHALF_DOORS` and `MOVE_ON_BEHALF_DOORS`, with explicit posture requirements per class. Do not infer the requirements from a superset relationship.

### 8. MEDIUM — amend-to-union is underspecified and therefore not byte-idempotent yet

Current `gitignore::ensure` rewrites the entire file to `ENTRIES` whenever any entry is missing at [gitignore.rs](/Users/maurice/projects/gherrink-jigc/crates/cli/src/gitignore.rs:32). D4 correctly rejects that, but “amend-to-union” does not specify:

- preservation of comments, blank lines, whitespace, CRLF, missing final newline, or duplicate existing entries;
- exact insertion position;
- whether semantically equivalent patterns such as `/tasks/` satisfy `tasks/`;
- handling of non-UTF-8 bytes;
- symlinks and non-regular files.

Concrete correction: settle a byte algorithm. The safest minimal rule is: preserve all existing bytes exactly; append only missing canonical entries in fixed order; insert exactly one separator newline only when required; never normalize or deduplicate existing content; reject non-regular, symlinked, or undecodable files. Test every real caller—currently milestone has two call sites, plus finalize, adapter/setup, and relocation test/helper paths—not merely three conceptual modules.

### 9. MEDIUM — the 17-key disposition is still a substantive decision, not decomposition work

The baseline’s “17” is itself unstable: the displayed list contains more than 17 names unless keys already declared elsewhere are subtracted. D5 delegates the actual declare/delete table to decomposition, even though declaring a key is the one-way action D5 exists to govern.

I would delete only `hook_output` from `milestone list-tasks`: it is structurally empty on a read verb and falsely implies a hook-capable operation. I would retain and declare the other observed facts when they communicate non-derivable outcomes—such as `identity`, `moved`, `displaced`, `reslugged`, `layer`, `rejected`, `anchor`, `side`, `step`, and `overlay`. Wrapper/status keys should be deleted only if a concrete consumer-equivalence argument shows they are redundant; absence from `design/` is not sufficient.

Concrete correction: the Settle itself must contain the exact census, owning verb/arm, present declaration, and final disposition for every key. Do not let increment authors decide which keys become the 1.0 contract.

### 10. LOW–MEDIUM — D1’s sink sweep still permits inconsistent trust decisions among five consumers

The five `read_source_path` consumers use the value for different purposes: validation context, carryover exemption, changelog behavior, clobber comparison, and retirement. “Read through” one CLI validation point is insufficient unless it returns a typed validated value that raw strings cannot substitute for.

Concrete correction: introduce an opaque `ValidatedRepoPath`/`ValidatedRetirement` containing the normalized literal path and bound repository identity. All five consumers must accept that type; keep raw `read_source_path` private to the loader. `retire_exempt` must be derived from the same validated value, never independently normalized at [finalize.rs](/Users/maurice/projects/gherrink-jigc/crates/engine/src/finalize.rs:738).

## Decision contradictions and zero-bump bound

I found no decision that explicitly requires a frozen doctype schema hash or `schema-version` bump. D13 and the confirmed scope correctly exclude those.

However, D5 and its riders deliberately move pinned command-output shapes:

- additive `retires`;
- `findings` on finalize dry-run;
- `relocated` on `ConfigAck::Set`;
- removal of `hook_output`;
- potentially the remaining undeclared-key dispositions.

Those are compatible with “zero schema-hash movement” only because command envelopes are not doctype schemas. They are not compatible with calling the wave purely a fence/documentation closure: it spends the pre-pin command-output window. The plan must explicitly distinguish command-envelope movement from frozen-schema movement.

There is also a D3/D10 tension: D3 requires a new setup-side carryover code and route, while D10 admits no pack step can declare it under the current stated-at model. “Derive the owe-set” does not supply the missing declarer. The store-surface answer and the setup route need to be settled together, not left to separate increments.

## Required corrections before decomposition

1. Settle a race-resistant D1 deletion primitive and Git literal-pathspec rule.
2. Put typed posture checks at every actual commit/move/fast-forward seam.
3. Replace D3’s staged-snapshot proposal with a HEAD/index/worktree/generated-byte attribution model.
4. Specify compare-and-swap rollback for D4.
5. Define a production-enumerable `EnvelopeArm` and publish the complete key-disposition table.
6. Change the path registry from six deduplicated IDs to leaf-specific argument occurrences.
7. Split committing doors from merely staged-moving doors and decide posture policy for each.
