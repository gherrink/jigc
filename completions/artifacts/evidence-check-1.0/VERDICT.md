# The 1.0.0 evidence check — VERDICT (2026-09-10)

**Provenance:** run 2026-09-10 on **`1.0.0-rc.14`** built from HEAD **`74627547`**. The product code at that HEAD is identical to the rc.14 trial sha `82075cc3` — the only intervening product-tree change is `crates/cli/tests/foldback_truth.rs`, a prose fence — so every repro below is a fact about the binary the rc.14 trial ran. The release binary was built from HEAD and every driving reviewer used it (`dev/jigc-rig <state> --binary target/release/jigc`, two-step eval, throwaway roots under the session scratchpad). The check was orchestrated from the main session as **five Opus reviewers** (trial-evidence audit · the five untrialled M50 surfaces driven · a data-loss hunt · a contract + release-mechanics audit · a live reproducer for the Codex claims) **plus one independent Codex source review**, prompted unseeded by the Opus results and asked to break the case for 1.0.0. No reviewer ran cargo; no reviewer edited a repo file. **The gate passed at HEAD** — `dev/gate`: probe · fmt · clippy · build · test all exit 0, **3341 passed / 0 failed** over 17 test binaries ([gate-rc14-at-74627547.log](gate-rc14-at-74627547.log)). Every report is persisted verbatim beside this record (see *Companion files*); this record adds only the ledger, the cross-report reading, and the bounds.

## Verdict in one line

**Not 1.0-ready as rc.14 stands — two data-loss-at-exit-0 defects that no trial reached, both outside every M50 registry and both driven live here; and, separately, the rc.14 trial evidence itself holds and is *stronger* than the record states, its single strongest stated caution against the 3/3 headline being false as written.**

The two are independent conclusions and should be read as such. The product defect is not a trial defect: the trial's instrument is sound where it was scored, and the blockers sit on axes the trial never charted — a path-taking argument that no registry classifies, and a git posture that no registry has a cell for.

## The ledger question

The rc.14 conversion ledger — *"every trial repro block carries `pinned-by:` or a stated `UNPINNED: <why>`"*, the human's own written gate on the 1.0.0 call — is read **two ways** by this check, and the reading is the human's.

**Closed, under the stated criterion** (reviewA §3). All thirteen rows carry one or the other, and **both prior closures used exactly this test** — RC-pre-1.0 (*"every row … now carries a `pinned-by:` citation … or a stated `UNPINNED: <why>`"* → *"the conversion ledger closed"*) and RC-1.0-gate (same words, same conclusion). Calling it OPEN applies a third, unstated criterion (presumably *all rows pinned*), under which **no trial's ledger has ever closed**. On this reading the mechanical condition is satisfied and what remains open is the human's *reading* of it — a different obligation that should be named as one. §3's conversion discipline is also asymmetric — *refuted* claims must become standing tests, *confirmed* claims' blocks become **the fix's red test** — and every confirmed row here is `SHIPS RECORDED` with no fix shipped, so an unpinned confirmed row is procedurally correct; §5's addendum (*"would pinning it now pin the bug?"*) answers yes over these rows. The one refuted row that carries `UNPINNED` (F-1) names its pinnable half as already fenced; F-12's citation was read line-by-line and is real.

**Substantively open** (codex §B, reviewD §6.1). `pinning.md` §3's rule is that a confirmed claim becomes the fix's red standing test; `UNPINNED` is an audit exception, not a substitute for conversion. **F-3, F-5, F-9 and F-11 are CONFIRMED defects with no standing test** — F-5 affects 22 doors and its own reason concedes the existing suite covers only *malformed* ids; F-11 sits upstream of every write-miss test; F-9's cited rename suite asserts acknowledgements and referrer repointing, not the stale commit-doc interaction; F-3's row admits no suite asserts it (and carries the placeholder citation of EC-35).
