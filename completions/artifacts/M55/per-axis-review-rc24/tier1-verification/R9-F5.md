# (R9, F5) — independent verification

**Finding.** `jigc uninstall`, without `--force`, destroys files inside `.jigc/logs/`, `.jigc/state/`
and `.jigc/index/` at exit 0, named by nothing, where its help says every such file blocks; without
any plant the opt-in invocation log goes from its records to the uninstall's own one.

**Binary.** `~/.local/bin/jigc` → `jigc 1.0.0-rc.24` (asserted first; release posture; the rig's
`$JIGC` was that path in every drive). Verifier did not build, drive or reconcile the row.

**Verdict in one line.** Reproduces in full, wider than recorded (two more members of the class).
Both halves of the predicate are shown. No declared bound covers it. **Tier 1 on the predicate and on
the project's own precedent — at the low end of tier-1 severity** (no authored doc, no repository
harm, a human-only door whose declared purpose is removing the tree). The tier-3 reading is real and
is stated in §5; I do not think it survives the design's own sentences.

areas is nobody's). It is independent of environment, format, corpus state and whether `HEAD` is born.
The guard holds at the `.jigc/` root, in `config/`, in any directory jigc does not name, inside a
working area, anywhere under `worktrees/` and anywhere under `displaced/`.

## 4 · Is it declared?

**No.** I found no sentence in `design/`, `crates/cli/guides/`, the `--help` text or `DECISIONS.md` that
states this behaviour as intended or as a known bound. What I found, with homes:

*Sentences the binary contradicts (the published and the designed universal):*

- `jigc uninstall --help` (verbatim, rc.24): *"Four states it refuses instead of destroying, because
  `.jigc/` is their only copy — … and any other file under `.jigc/` that no index has a copy of — a
  recorded config delta among them — blocks with `uninstall.untracked-workbench-file` (`git add <path>`
  is enough to make it recoverable) … Any of them removes nothing until you re-run — or pass `--force`,
  which deletes all four with the install"*.
- `design/worked-examples.md`, flow 52 arm 2: *"**No destroying door destroys bytes it does not name, and
  none takes a path it never looked at.**"*
- `design/worked-examples.md`, flow 50 arm 6: *"the teardown gives one answer per kind of byte"*.
- `crates/cli/src/setup.rs`, `uninstall`'s doc-comment: *"unless `force`, it removes nothing at all while
  `.jigc/` holds the sole copy of anything"*.
- `design/project-setup.md` → Teardown / cleanup (G5), (c): *"Authorship is not a discriminator here
  either: jigc's own writes are not exempt from the rule jigc's own guards run on"* — said of
  `.jigc/config/manifest.yaml`, the precedent for a jigc-written sole-copy file refusing.

*The scope sentence the tier-3 reading rests on — a scope, not a declared loss:*

- `design/project-setup.md` (c): *"a file under `.jigc/` that lies **outside** those transient prefixes
  and that **no index has a copy of** blocks with `uninstall.untracked-workbench-file`"*, and
  `DECISIONS.md` 2026-09-05 (M50 Inc 4 / T4): *"a path under `.jigc/` outside the transient
  `gitignore::ENTRIES` prefixes that no index carries"*. The binary matches this scope. But the same
  paragraph's (d) then says the excluded part is owned: *"It is (c)'s ground stated over the two subtrees
  (c) structurally excludes … the reason (c) refuses does not stop at the `ENTRIES` complement"*, and
  `workbench_paths`' doc-comment says of `displaced/` that until M52 it was *"the one excluded prefix
  **no** door owned"*. Both are a miscount — (c) excludes seven directories, and three (plus the two
  leaf positions) are still owned by no door. The design believes coverage is complete; it does not
  declare a gap.

*Neighbouring, milder declared costs — none covers this:*

- `design/storage.md` → the source-of-truth paragraph: *"Every other artifact — the staging working
  area, the edge index, the file↔state hashes — is either a rebuildable cache or a transient working
  copy. Delete all of it, rebuild from the `.md`, and nothing committed is lost"*. This declares
  **jigc's own** `index/` and `state/` content disposable. It says nothing of a byte jigc did not write
  there, and it does not name `logs/`.
- `design/worked-examples.md`, flow 52 arm 2, the declared bound: *"an ignored path's loss is made
  *visible, not prevented*"* — about gitignored build output inside a fan-out worktree. Here the loss is
  neither prevented **nor visible**, so even the mildest bound the project has declared for a destroying
  door is not met.
- `design/measurement.md` → The in-repo invocation log: the log is *"a **jigc product feature** … so a
  real external-repo RC run yields analyzable in-repo data"*, *"log rotation — lean NONE for v1"*. Nothing
  says a teardown takes it. `crates/cli/guides/QUICKSTART.md` names the file as *"the gitignored
  `.jigc/logs/invocations.jsonl`"* and says nothing about `uninstall`.

## 5 · Tier — my verdict, and the strongest case each way

**The strongest case FOR tier 1.**

1. *The letter.* Exit 0 through a `DESTROYING_DOORS` member without its consent flag, `findings: []`,
   and sole-copy bytes shown present before and absent from every place after (§2).
2. *The project has already ruled on this exact shape, in the tier vocabulary, by the human's own
   charter.* `implementation/decisions-pending.md` → *The rc.17 fix pass (M53)* → Tier 1, row `(3, A3-1)`:
   *"`jigc milestone finalize` removes `.jigc/milestones/<id>/` with `remove_dir_all` and destroys every
   byte jigc did not write there, at exit 0, named by nothing, while `milestone discard` and `uninstall`
   refuse or narrate over the identical plant"* — a hand-planted foreign file in a gitignored jigc
   directory. And at **this door**, M52's `L-2` (a plain file **at** an `ENTRIES` name) was chartered in
   the loss tier and fixed. F5 is `L-2` one level down.
3. *The argument "only jigc's bytes live there" has been tried and rejected in the design of record.*
   `design/team-ready-state.md` → The working area's two populations, on the `merged/` carve-out: *"an
   exclusion resting on the predicate **nothing but jigc's bytes are in `merged/`**, which is false four
   ways … One state, two answers, from one carve-out."* F5 is the same carve-out over three more
   directories: the identical byte one directory over (`.jigc/config/`, `.jigc/`, `.jigc/scratch/`)
   refuses.
4. *No declared bound* (§4), and the published help states the opposite universal — a careful operator
   who read it is entitled to run the bare verb expecting a refusal over anything unrecoverable.
5. *One member needs no plant.* Knob on + `jigc uninstall` is deterministic, and the log is
   non-rebuildable, sole-copy, and carries the operator's intent text in `argv`.

**The strongest case AGAINST tier 1 (the tier-3 reading).**

1. *The verb's declared act is removing `.jigc/`.* The operator asked for the destruction of this tree;
   the help's first sentence says so, and the log's documented home is inside it. An uninstaller taking
   its own logs and caches is ordinary.
2. *The binary matches the guard's designed scope* (the `ENTRIES` complement, §4). What is wrong is the
   help's paraphrase *"any other file under `.jigc/`"* — a surface saying something the binary does not
   do, which is the definition of tier 3.
3. *No surface of the product ever directs a user byte into `logs/`, `state/` or `index/`.* Unlike a
   working area, which the design says agents write into, there is no observed foreign population here.
   The planted member is synthetic.
4. *No authored work dies.* `state/` and `index/` are declared rebuildable caches; the log is
   machine-written telemetry, default off.
5. *The door is human-only* (`Bash(jigc uninstall:*)` is on the adapter's deny floor,
   `design/assistant-adapter.md`), deliberate and rare, so no unattended agent reaches it; and a blanket
   refusal over the log would put `--force` on every opted-in adopter's uninstall, which the project's
   own reasoning (`DECISIONS.md` → the `--ignored` bound) calls *strictly worse than no guard*.

**Where I land: tier 1.** Points 1–2 of the against-case are answered by the design itself: the door's
contract of record is not "removes `.jigc/`" but "non-destructive — removes nothing while `.jigc/` holds
a sole copy, and names what it takes", and the design text claims the excluded prefixes are owned when
three are not — a guard gap behind a miscount, not a declared scope. Point 3 is the same precondition
`(3, A3-1)` and `L-2` had, and both were ruled loss. Point 5's `--force`-reflex argument is a reason the
*fix* for the log may be a narration rather than a refusal; it is not a reason the un-narrated
destruction is not a loss today. Point 4 is what sets the **severity**, and I state it plainly: this is
the weakest kind of tier 1 — no doc, no code, no repository state is damaged, and the realistic victim
is a telemetry file or a stray note. If the human rules that the predicate's *loss* means authored work
only, the row falls to tier 3 **for the log member**; the planted member would still stand on
`(3, A3-1)`'s precedent unless that ruling is also taken to supersede it. A re-tier to 3 leaves the
help's universal false on rc.24 and is itself a declaration that would need a home.

**On the two questions asked.** (a) *Are user-planted files inside jigc-only directories loss the
product owes a guard for?* By the product's own stated ground — *no index has a copy* — and its own
precedents, yes: it owes either a refusal or, at the declared minimum, a name. It gives neither.
(b) *Is the invocation log sole-copy user data whose silent destruction is tier 1?* It is sole-copy,
non-rebuildable, operator-opted data, destroyed at exit 0 unnamed — the predicate's letter is met. It is
the weaker member on value and the stronger member on reachability. Standing alone I would still tier it
1 on the letter, and flag it as the member a human ruling could most defensibly move.

## 6 · How a real adopter reaches it

- **The log (no plant):** `jigc config set invocation-log true` (the RC-trial protocol's own step —
  `design/measurement.md` item 5a makes enabling it the trial's responsibility), work, then `jigc
  uninstall` — for instance at the end of an evaluation, which is exactly when the data is wanted.
  Certain given those two acts. Absolute likelihood low to moderate: the knob is default off, the door
  is run once per repository lifetime, and a trial harness that copies evidence out first is unaffected.
- **A foreign file:** the most plausible are a hand-rotated log (`mv invocations.jsonl
  invocations.1.jsonl` — the design ships no rotation), an analysis or notes file written beside the
  log, or an agent's scratch output dropped into a gitignored jigc directory and left for the human who
  later uninstalls. Low. An editor swap file is the commonest foreign byte there and is worthless.
- **A leaf under `tasks/` or `milestones/`:** a note saved one level too high. Low.
- **Not reachable by an adapter-installed agent:** `Bash(jigc uninstall:*)` is denied; a human runs it.

## 7 · Code (read-only; nothing edited)

- **Site.** `crates/cli/src/setup.rs` → `workbench_paths` — the third guard's subject is derived as the
  complement of `crate::gitignore::ENTRIES` (`tasks/ index/ state/ milestones/ worktrees/ logs/
  displaced/`): any **directory** child of `.jigc/` whose name is an `ENTRIES` prefix is skipped whole.
  `uninstall` (same file) then runs four guards whose union is supposed to be the tree:
  `dirty_fanout_worktrees` (`worktrees/`), `workbench_foreign_areas` → `crate::task::foreign_areas`
  (the **directory** children of `tasks/` and `milestones/`, plus `displaced/`), `staged_task_prose`
  (`tasks/<id>/docs/*.md`), `untracked_workbench_files` (the complement). `logs/`, `state/`, `index/`
  are in nobody's subject; a non-directory child of `tasks/` or `milestones/` is dropped by
  `foreign_areas`' `Ok(_) => continue` and is in nobody's subject either. `pending_teardown` reads the
  same derivations, so the narration has the same hole (`--force` over `.jigc/logs/notes.txt` names
  nothing). The sink is `std::fs::remove_dir_all(<repo>/.jigc)`.
- **Introduced (git log / blame — read, not driven on an older binary).** The complement derivation is
  `1bd5efaf`, 2026-09-05 (*uninstall stops taking the workbench bytes no index has a copy of*, M50
  Increment 4 / T4). `a165a0dd`, 2026-09-18 (M52 Increment 4 / T5) added the foreign-bytes guard and the
  doc-comment that calls `displaced/` *the one excluded prefix no door owned*. `logs/` has been an
  `ENTRIES` member since `e0d80ffc`, 2026-07-07. The functions were last touched by `b37bdb5e`,
  2026-09-23. `ec1aa0f7` (M54, 2026-09-29) and `28ca86b4` (the trailer, 2026-10-03) touch `setup.rs`
  but zero lines naming any guard or `ENTRIES`. **Outside M54, M55 and the co-author trailer.**
- **The class.** At this door: `logs/**`, `state/**`, `index/**`, leaf children of `tasks/` and
  `milestones/` (the last two driven here, not in the record); the tracked-but-edited leg inside those
  directories; the narration under `--force`; and, by construction, **any prefix later added to
  `ENTRIES`** — `workbench_paths`' doc-comment advertises *"a prefix added to `ENTRIES` narrows this set
  automatically"*, which is the derivation failing open. No other door removes these directories
  (`completions/artifacts/M52/baseline-destroying.md` §1.2: site 10 is the only whole-workbench sink;
  `engine/index.rs` removes `edges.json` alone). (R9, F3) is the same door and the same log, the residue
  side.
- **The contract a fix must restore.** *Without `--force`, `uninstall` removes nothing while `.jigc/`
  holds a byte no index has a copy of that jigc cannot vouch for as its own disposable state — and
  whatever it does take, it names.* Equivalently: the union of the guards' subjects is the whole tree
  minus jigc's declared-disposable writer set, and the narration reads the same set. The help's count
  (*four states* / `--force`'s *three guards*) and `project-setup.md`'s *two subtrees* must agree with
  whatever the code does.
- **The fork (no patch proposed).**
  - *Cheap:* keep the complement derivation and add a condition to the existing guards — inside the
    unowned `ENTRIES` directories, everything outside jigc's own named files (`state/file-state.json`
    and its lock, `index/edges.json` and its lock, `logs/invocations.jsonl`) and every leaf child of
    `tasks/`/`milestones/` joins an existing refusing subject and its narration. Cost: a hand-kept list
    of jigc's files in three directories (the M52 `renames.json` lesson — a short list calls jigc's own
    file foreign), and the derivation still fails open for the next prefix.
  - *Robust:* invert the derivation — the subject is everything under `.jigc/` minus a writer registry
    covering all seven prefixes, fenced by a source scan as `task_area_writer_registry.rs` fences the
    working-area set. Cost: a new registry and fence (new mechanism, which M53's boundary made a halt to
    the human), and a wider over-refusal surface on first contact.
  - *A separate decision inside either:* what the door owes the **invocation log**. Refuse (consistent
    with *authorship is not a discriminator*; costs every opted-in adopter a `--force` or a manual move,
