# (R6, D-7) — independent verification

**Finding:** a dangling symlink at the minted home passes the create-gate, and `task finalize` exits 0
committing the symlink while the finding's prose lands in an untracked file; in a clone
`doc list <type>` exits 1 for the whole doctype.

**Binary:** `~/.local/bin/jigc` → `jigc 1.0.0-rc.24` (asserted first; release posture, registry build).
**Source read at:** `bffa6667` — `git diff --stat jigc-v1.0.0-rc.24 HEAD -- crates` is empty, so the
crate source read is the released one. Every code statement below is a **read**, not a drive.
**Rigs:** five `dev/jigc-rig fresh` rigs (r1–r4 plus one hand-initialised repo for the placement cell),
each from `mktemp -d`, two-step eval, stdout only, `[ -n "$REPO" ]` guarded.

## Verdict in one paragraph

**The finding reproduces exactly as recorded, and it is wider than recorded.** `task finalize` exits 0,
says `promoted … 1 file committed`, and the commit holds a `120000` entry; the prose is in no commit.
No pre-existing byte is lost in the filed form — the prose survives in an untracked file that `git status`
and the finalize's own `left-out` line both name. **The mechanism is not M55's gate**: it reproduces on
`adr` under `record-decision` (no `new: true`) and on the `vision` placement singleton, because the
write-through is `promote`'s `fs::copy` (2026-05-31) behind two `is_file()` occupancy probes. Two members
of the same class are worse than the filed one and were not in the record: an **out-of-repository**
dangling target (jigc creates a file outside the repo at exit 0 with `left_out: []` and a clean
`git status` — nothing names where the prose went), and a link to a **non-regular** target
(`/dev/null`: exit 0, `promoted`, and the authored prose is in **no place at all** afterwards).
**Tier: 1 on the predicate's letter, harm disjunct — the lowest-weight tier-1 row**, because every
reach needs a symlink somebody else put at exactly the minted path. Not declared anywhere; the design
states the opposite invariant.

## 2 · The two halves

### Exit 0 — shown

`task finalize` exits 0 in text, `--format json` and `--format human`. Under `--format json` (rig r4, the
same plant): `committed.promoted = ["docs/inconsistencies/json-home.md"]`, `files = 1`, `displaced = []`,
`findings` = two advisories (`file-state.staged-copy` on the home, a `baseline-adopt` on an unrelated
file), neither about the link. `task finalize --dry-run` (text and json) prints
`promoted docs/inconsistencies/<slug>.md` as the manifest and exits 0. `task validate` exits 0.
**No finding, warning or route says the doc was not committed.**

One qualification the record under-states: in the **in-repo** variant the finalize *does* print the path
the prose landed at — as a `left-out` row (`docs/inconsistencies/nowhere.md`, json `kind: untracked`).
It is framed as somebody else's untracked file, not as this task's doc, so it names the path and not the
problem. In the out-of-repo variant (§3, V2) even that row is absent.

### Loss — NOT shown for the filed form (confirmed: none)

Marker `DANGLING-MARKER-7Q`, before-control found it in the task's staged copy. After finalize:

| place | result |
|---|---|
| worktree | **found** — `docs/inconsistencies/nowhere.md` (untracked) |
| index (`git grep --cached`) | absent |
| HEAD / every ref (`git grep … HEAD`, `git log --all -S`) | absent — 0 commits |
| every object, reachable or not (`git cat-file --batch-all-objects`, each blob grepped) | absent — 0 blobs |
| `git fsck --unreachable --lost-found` | no output |
| `git stash list` | 0 |
| reflog | 4 entries, all commits; none carries it |
| `.jigc/` (`command grep -r`, before-control positive) | absent — the task area is removed, nothing is displaced |

**The bytes survive in exactly one place: an untracked worktree file.** Discoverability is good in the
filed form — `git status` shows `?? docs/inconsistencies/nowhere.md`, the finalize names it, and the local
`jigc doc list inconsistency` even lists it as a second managed doc (`inconsistency:nowhere`, same title).
Recovery is two git commands and a commit. No pre-existing byte is lost.

### Harm — shown

What repository state is damaged, exactly:

1. **The commit the door made carries a symlink where it says it promoted a doc.** HEAD now holds a
   `120000` entry at the doc's home whose target is in no commit. The finding is absent from history while
   the ack, the dry-run manifest, the json `promoted` array and jigc's own `file-state.json` all record it
   as landed.
2. **Every other checkout of that commit cannot list the doctype.** In a clone (`git clone "$REPO" <tmp>/c`):

   ```text
   git checkout HEAD~1 ; jigc doc list inconsistency                → exit 0   (port-mismatch listed)
   git checkout -      ; jigc doc list inconsistency                → exit 1
     reading the committed doc at "<root>/docs/inconsistencies/dangling-home.md": No such file or directory (os error 2)
   jigc doc list inconsistency --format json                        → exit 1, {"error": "reading the committed doc …"}
   jigc doc list                         (no type)                  → exit 1, the same line
   jigc doc show inconsistency:dangling-home                        → exit 1, store.not-found
   jigc doc show inconsistency:port-mismatch                        → exit 0   (other docs still read)
   jigc validate                                                    → exit 0, no row names the link
   ```
   The error is code-less and carries no route. Filing a *new* finding in the clone still works (driven:
   start → create → finalize exit 0), so the damage is the **read index of the doctype**, not the write
   path. A second reporter re-using the title in the clone passes the gate again (create exit 0) and would
   repeat the write-through.
3. **The local reads hide it.** In the originating checkout `doc show inconsistency:dangling-home` serves
   the finding through the link at exit 0 and `doc list` exits 0 — so the person who filed it has no jigc
   surface that says it is not in the commit.

**What the door did not cause:** the local `doc list` break exists *before* any jigc door runs (the
untracked dangling link alone gives exit 1 — control above). The door's contribution is committing the
link under a `promoted` ack and writing the prose to a path nobody named.

**True boundary:** the guards answer "is there a *regular file reachable through this path*". They hold for
a regular file and for a link to one; they do not hold for any directory entry that is not that — a
dangling link, a link to a device or FIFO, (a directory fails later, loudly). The write then follows the
link wherever it points, inside the repository or not.

## 4 · Declared?

**No.** No sentence in `design/`, `crates/cli/guides/`, the `--help` text or `DECISIONS.md` states that a
promote writes through a link at the home, or bounds it. What is stated points the other way:

- `design/findings-channel.md` (the `create.already-exists` row): the gate fires when *"the minted identity
  already exists on disk at the doctype's location"*, subject *"the doctype's home on disk (committed or
  untracked)"*. A dangling link is a directory entry on disk at that path.
- `jigc doc create --help`: *"an id already on disk at the doctype's home is refused before anything is
  copied in (`create.already-exists`)"*.
- `jigc task finalize --help`: the planner refuses *"`finalize.promote-clobber` over a file already sitting
  at a promote destination"*.
- `design/finalize.md` → 4. Promote managed docs: *"**Copy** (not move) the file from the working area to
  its canonical path."* The bytes land at a different path.
- `design/team-ready-state.md` → Shape is part of membership: *"the shape is read without following
  symlinks, because jigc writes regular files and real directories and never a link."* Here jigc commits a
  link under its own `promoted` row.
- `DECISIONS.md` (the leftover probe): *"`probe_leftover` reads `symlink_metadata`, not `exists()`. A
  symlink is a leaf whose own bytes the removal takes, and a **dangling** one read as absent through
  `exists()` while still standing in the way…"* — the same lesson, recorded for another door.
- `crates/engine/src/finalize.rs` (doc comment on the staged-shape leg, M53): a symlink named `adr:y.md`
  in the **staging** directory *"was read **through**, and its target's bytes were promoted into the commit
  as a managed doc at **exit 0**"* — fixed on the source side. D-7 is the destination-side twin.

The review record's "symlinked paths are numbered axis 1's class" is a scoping statement of the review,
not a product declaration.

## 5 · Tier

**Strongest case FOR tier 1.** A committing door exits 0 and acks `promoted … 1 file committed` over a
commit that holds a link instead of the doc; the authored prose is in no commit and the task's working
area — jigc's only copy — is destroyed by the same finalize. The committed state is newly damaged by the
door (HEAD was sound before it) and breaks `doc list`, typed and untyped, for every other checkout with a
code-less exit 1. No surface fix could make this truthful — the defect is the behaviour, so tier 3 does not
describe it — and there is no dead end, so tier 2 does not either. The same mechanism writes outside the
repository with no row naming where (V2), and with a non-regular target it destroys the authored prose
outright at exit 0 (V2b), which is the loss disjunct. It violates an invariant the design states in its own
words, and it is the unfixed twin of a source-side read-through M53 treated as a defect.

**Strongest case AGAINST tier 1.** No pre-existing byte is lost and, in the filed form, the new prose is
not lost either: it sits in the worktree, `git status` shows it, the finalize names its path, recovery is a
`git rm`, a `git mv` and a commit. Every reach needs a symlink that no jigc door creates at exactly the
path a title will slug to (or at a placement home); with it planted and untracked, the doctype's local
listing is *already* broken before the door runs, so the visible breakage is the read's fragility, which
the door only carries into a commit. The damage is one forward-repairable entry in one new commit. The
loss member (V2b) needs a link to a device at a doc home, which has no organic story. Read strictly — both
halves on the loss disjunct — this row does not count, and the review record already says so.

**Where I land: tier 1, on the harm disjunct, by the predicate's letter — and the weakest tier-1 row.**
The driver's tier 3 answers only the loss disjunct ("no pre-existing byte is lost") and does not engage
the harm one; the reconciler's re-tier survives. I could not refute it: the committing door newly damages
committed state at exit 0, and the class reaches an out-of-repo write and a real loss. What I can add is
the weight, which is lower than a bare "tier 1" suggests: this is planted-or-inherited-link only. If the
human reads the predicate as needing a reach an adopter arrives at without a foreign link, this row is not
the one that should cost a release cycle on its own — but it is cheap to fold into a fix pass that other
rows already trigger, and the fix is one predicate at one seam.

## 6 · How a real adopter reaches it

- **A link planted by hand at a minted slug** — no reason to; adversarial or a test.
- **An inherited stale link.** A repository that keeps doc aliases as symlinks, where a target was moved
  or deleted and the tracked link stayed. A later decision or finding whose title slugs to the link's name
  hits V13/V3 (tracked) — low, because the slug must coincide; less low for a re-recording of the same
  decision, where the stale link *is* the old doc's name.
- **A placement home that is a link** (`VISION.md`, `CHANGELOG.md`, `docs/roadmap.md` → a path not yet
  created). Fixed homes need no slug coincidence (V11 driven for `vision`). Uncommon, but the one organic
  shape I would expect to meet first.
- **A hostile or careless upstream.** A cloned repository carrying a tracked dangling link at a doc home
  whose target is outside the repo makes an agent's finalize create a file at a path the upstream chose
  (V2's mechanism with V3/V13's tracked plant). Content is the agent's prose, location is the upstream's.
  Not driven end to end with an out-of-repo *tracked* link; V2 (untracked, out-of-repo) and V3 (tracked,
  write-through still happens at exit 1) each drive one half.
- **jigc itself** never creates the state: it writes no links (V3/V7/V9 confirm none of the adjacent doors
  leaves one), and the K-1 race is a different finding.

Overall likelihood for an ordinary adopter: **very low**. For an agent working in repositories it did not
author: low, non-zero, and silent when it happens.

## 7 · Code (read-only)

- **Sites.**
  - `crates/engine/src/state.rs:create_occupied` — `canonical_path(…).is_some_and(|path| path.is_file())`.
    `is_file()` follows links, so a dangling link reads as unoccupied. Introduced `e9f7f081` (2026-10-03,
    M55, *"an allows-create entry carrying `new: true` refuses an id already on disk"*).
  - `crates/engine/src/finalize.rs:plan_clobber_guard` — `repo_root.join(&promotion.destination).is_file()`.
    Same probe, same blind spot. Introduced `e1cbe581` (2026-06-17).
  - `crates/cli/src/task.rs:promote` — `std::fs::copy(&promotion.source, &dest)` follows a link at `dest`
    and writes its target. The copy dates from `6a4e9c59` (2026-05-31, the promote phase); the current line
    is `655b3e31` (2026-09-18). The stage step then `git add`s the home path, which records the link.
  - `crates/cli/src/rollback.rs` `PreImage::capture` reads through the link (`NotFound` → absent), so the
    rollback treats the link as "a file this run created" and removes it (V7).
  - `crates/engine/src/state.rs:bound_instance_present` — the same `is_file()` on the same path.
- **Introduced by:** the write-through and the planner guard predate M54/M55 by months; M55 added one more
  guard on the same probe. **Outside the new code** — V4 (`adr`, no `new: true`) reproduces without M55's
  gate being in play.
- **Class — every path sharing the mechanism.**
  - every **promote destination** on both committing doors: `task finalize` (driven) and
    `milestone finalize` — the fan-out join shares the one `promote` call inside the commit transaction
    (read, not driven);
  - every doctype with a `location:` home (driven: `inconsistency`, `adr`) and every **placement**
    doctype (driven: `vision`; by the same code: `changelog`, `roadmap`, and the rest);
  - the **migrate** landing, which promotes through the same function (read, not driven);
  - the two **occupancy probes** above plus `bound_instance_present`, for any non-regular entry: dangling
    link, link to a device/FIFO, a directory (the last fails loudly later);
  - the **rollback** of a promote over a link (V7);
  - the **live-link** edit path — a tracked link to a real doc, edited via copy-in and promoted through
    the link, leaving the edit in an unstaged target — reasoned from the same `fs::copy`, **not driven**;
  - the reads: `doc list`'s code-less exit 1 over one unreadable entry (the record's L-3 lead) is what
    turns the committed link into a whole-doctype outage. It is a separate seam and a separate fix.
- **Contract a fix must restore.** *A promote lands a regular file at exactly its canonical path, or the
  transaction refuses before anything is written.* Equivalently: the occupancy question is asked of the
  directory entry (no-follow), at the gate and again at the planner, and the promote never writes through
  a link. A link at a home is a third party's entry, to be refused and named like any other occupant.
- **Cheap vs robust — a genuine choice.**
  - *Cheap:* make the two occupancy probes no-follow, so any non-regular entry at a home is
    `create.already-exists` / `finalize.promote-clobber`. Cost: small and local; but it is a
    check-then-write, so it leaves the K-1 window open and leaves the write itself willing to follow a
    link that appears after the check, and it does not touch the rollback or the live-link edit path.
    Note the engine hosts no `symlink_metadata` on a store path by its own stated rule, so the predicate
    may have to be CLI-supplied, as `ValidatedRetirement` is.
  - *Robust:* make the **write** refuse a non-regular destination (the sink re-validates, the pattern M51
    used for `retire`), with the capture/rollback reading the entry no-follow so a link is never removed
    as "created by this run". Cost: touches the commit transaction and its rollback family, needs a
    decision on a *live* link at a home (refuse, or declare supported), and wants an axis suite over
    destination shapes on both committing doors.
  Either way the `doc list` read's all-or-nothing failure is a separate row.

## 8 · Pin

**UNPINNED for the shape.** The nearest pins plant a **regular** file only:

- `crates/cli/tests/create_only_gate.rs::an_untracked_file_at_the_home_is_refused` — the test that should
  have carried it; its one fixture is a hand-placed regular file, so "on disk" was pinned for one entry
  shape.
- `crates/engine/src/state.rs` unit test `create_occupied_probes_the_home_on_disk_whatever_is_staged` —
  `fs::write` of a regular file.
- the `finalize.promote-clobber` suites (`crates/cli/tests/create_or_update.rs`,
  `placement_acceptance.rs`, the engine unit tests in `finalize.rs`) — regular files.

No test listed under `create.already-exists` or `promote-clobber` mentions a symlink. The M53 staged-shape
axis (links and directories in the **staging** directory) and the M51 path-argument axis
(`{absolute, ../, symlink, .git/}` over **arguments**) both stop short of the **promote destination**.
