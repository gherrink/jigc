The `roadmap` schema — the managed singleton at `docs/roadmap.md`.

- `meta` (front-matter fields):
    - `schema-version`: int — CLI-stamped (schema-version) unless authored
- `milestones`: repeatable items, one per `title`:
    - `title`: string — the item's id-source (authored as the item's `title:` payload key)
    - `proves`: prose slot — What this milestone proves — the differentiator it converts from supported to demonstrated.
    - `decomposition`: prose slot — The increments, as prose: each increment's deliverable and the tasks that build it, one level.

Author the whole document in ONE `jigc doc author` batch payload — fill each `<…>` value. The `<<…>>` wrapping on slot prose is REQUIRED literal syntax: keep the `<<`/`>>` markers and replace only the text between them (an inline field takes a bare value — wrapping one is rejected). Inside slot prose, headings must sit at `#####` depth or deeper — `##`/`###`/`####` are schema-reserved, and Setext headings are rejected. An entry marked `# optional` may be omitted entirely. A repeatable's demonstrated item entry is a template — repeat one `- title:` entry per item. Multi-line slot prose wraps WHOLE inside one `<<…>>` pair within its block scalar — a two-line slot is authored as

<slot-id>: |-
  <<The first line of the prose
  and its second line, inside the SAME pair.>>

Pipe the payload on stdin:

jigc doc author roadmap --from-file - --task your-task-id <<'EOF'
title: Roadmap
sections:

    items:

            <<What this milestone proves — the differentiator it converts from supported to demonstrated.>>

EOF

If a `roadmap` is ALREADY committed in the store (a re-run, or one adopted earlier),
the CLI does not mint a fresh one — it copies the committed body in as your edit
base, so the milestones you author below APPEND to those already there and any slot
you set overwrites. Re-author only what the foreign source adds; a milestone the
committed doc already holds would double. The lone exception is a same-path
migration — when the foreign file you are migrating IS the canonical
`docs/roadmap.md` — where the CLI seeds a blank skeleton and your authoring rebuilds
the whole doc.

Re-author every MILESTONE from the foreign roadmap, in the foreign order, as one item
under `milestones` — a foreign milestone / phase / epic / numbered-stage heading maps
to one item, titled from the foreign name. BOTH slot keys go in the ONE `set:` map of
the same item — never split a milestone across two items. Fill the two slots
mechanically:

  - `proves` — the foreign goal / outcome / "done means" statement for that
    milestone; when the foreign roadmap states none, derive it from the milestone's
    own deliverable ("<the deliverable> works end-to-end") — never leave the slot
    empty;
  - `decomposition` — the foreign breakdown under that milestone (its steps, tasks,
    or increments), transcribed as prose, one level; when the foreign roadmap lists
    no breakdown, state the single deliverable as one line ("one increment: <the
    deliverable>").

A foreign reference to another document (a spec, an ADR, an issue) stays plain prose
inside the slot it appears in — the roadmap schema declares no managed ref, so never
invent a field for it. Foreign preamble with no milestone home (a legend, a status
table, a badge block) is dropped.

Finalizing a migration adds a review hold: a plain finalize commits NOTHING —
it renders the foreign source against the canonical rewrite and holds (exit 4),
because the CLI guarantees structure, never content-faithfulness. Review that
fidelity diff, then re-run the same finalize with `--approve` to write the
canonical doc, RETIRE the foreign original, and commit — approval is the one
destructive gate. Retired means removed: the foreign file is deleted from the
worktree and the deletion staged, so the removal lands in the same commit as
the canonical doc (a `git rm` in effect). A source already sitting at its
canonical destination is
rewritten in place on approval — the committed file is modified, nothing is
retired. A destination already committed when the doc was authored was copied
in as the edit base (the create said so), so approval updates that committed
file in place — review the fidelity diff before approving. Finalize blocks
(finalize.promote-clobber) only when a file appeared at the destination after
the doc was created: resolve that collision, or retitle the doc so it slugs
differently, then finalize again.
Land the change as exactly one logical commit. finalize commits the git index —
`git add` your code edits before you finalize, because it commits only what you
have staged, plus the docs it manages. Unstaged edits and untracked files are
left out of the commit; with nothing staged over a dirty tree, finalize
refuses. Anything still staged from BEFORE this task was minted makes finalize
refuse too (one blocking finding per carried path): unstage it, or pass
`--carry-staged` to declare the carryover deliberate.

finalize renders the commit doc; it does not fill it, so set its header and prose
first. Inside slot prose, the reserved heading depths are schema-relative to the
address you write — the CLI owns the section, item, and sub-label heading levels
there, so your headings sit below them; Setext headings are rejected at every
depth, and a rejected write names the shallowest depth free at that address.
