# Migrating to jigc — field notes

Two different migrations get called "migrating to jigc." Both have now been run for real on a brownfield repo (the RC adoption trial, 2026-07-09 → 07-12); these notes distill what worked and what bites. They are working notes, not polished docs — updated as trials land.

1. **Adopting an existing project** — foreign docs (a `.planning/` tree, loose Markdown, an old spec system) become jigc-managed docs. Verb: `jigc ingest` to classify, `jigc migrate <path> --as <doctype>` per doc.
2. **Upgrading a jigc corpus across versions** — committed managed docs move to a new doctype schema-version. Verb: `jigc migrate-corpus`.

## Adopting an existing project

The full method write-up from the reference migration (220 foreign files → 41 managed docs, ~55 commits, one day) is archived at [completions/artifacts/RC-adoption/rerun-rc4/migration-method.md](../../../completions/artifacts/RC-adoption/rerun-rc4/migration-method.md). The short version:

1. **Triage with the tool first.** `jigc ingest` classifies every candidate against the managed schemas before you decide anything. Conformant-but-misplaced docs can be adopted; everything else is a re-authoring job through the write verbs. Knowing the split up front sets the whole plan's cost.
2. **Treat every claim in the old docs as unverified.** This is the load-bearing rule, and it is why adoption is a *verification* job, not a reformatting job. Your existing docs may already be lying about the code — status claims especially ("shipped", "passes audit", "the gate works"). Check each claim against the code before carrying it over; a false claim migrated into jigc is *worse* than a deleted one, because the new system lends it credibility (managed, validated, green). Don't migrate what you haven't verified — and where a claim can't be cheaply verified, either drop it or carry it explicitly marked as unverified and put the verification question to the human.
3. **Mine history for the four things worth keeping:** design decisions whose rationale isn't recoverable from the code, still-open debt, architecture knowledge, and work claimed complete that the code doesn't support. Everything else (plan summaries, validation reports, velocity tables) is process exhaust — drop it.
4. **Put the genuine forks to the human** — not "should I proceed" but the actual decisions (delete vs mine-then-delete, is this doc still live, where does the backlog land).
5. **Draft in parallel, write strictly sequentially.** Prose drafting and code-verification parallelize. Since rc.8 the *draft/author* half of bulk migration parallelizes even for docs sharing a directory: two same-directory sources whose slugs would collide today mint **distinct** task ids (a `blake3` of each source path is folded into the migration task id), so their `.jigc/tasks/<id>/` working areas no longer race the tool state. The jigc *writes* still run strictly sequentially — the git-index race is unchanged, each doc mints its own commit, so the finalize/commit path is one process, never parallel.
6. **Author in dependency order.** Cross-referencing docs must land after their targets: ADRs before the arch-docs that cite them — finalize blocks a citation to a doc that doesn't exist.
7. **Let `jigc migrate` retire each source in the same commit as its promoted doc.** The old tree drains itself; there is never a window where content exists in neither place. Then sweep for what the migration broke *outside* the corpus (READMEs pointing at the deleted tree, a stale CLAUDE.md).
8. **Prefer block scalars (`key: |`) in author payloads** for any multi-paragraph prose (the templates demonstrate this since rc.5; double-quoted YAML folds newlines).

## Upgrading a jigc corpus across versions

Verified on the first real committed-corpus upgrade (rc.4 → rc.5, a 41-doc corpus, one doctype with an enum rename across 41 entries — byte-stable, zero prose touched, idempotent re-run). That trial found the *routing* around the upgrade silent, so the rc.6 wave hardened it; the steps below are the shipped surface.

1. **Ask `jigc validate` whether you need to migrate — it blocks if you do.** A committed doc below its doctype's current schema-version raises `schema-conformance.schema-version-current`, routed at `jigc migrate-corpus`, and takes the exit code **non-zero**. The discriminator is each doc's own committed `schema-version` stamp, so the answer never depends on when the store was last stamped.
2. **Run `jigc migrate-corpus` first, `jigc setup` second — and the tool now says so.** Over a stale corpus the `store-version.binary-mismatch` advisory routes at `migrate-corpus` first, and re-stamping the store no longer buys a green: `validate` still blocks on the per-doc stamps. Re-stamp with `jigc setup` once the corpus is current (with the corpus current, the advisory drops `migrate-corpus` from its route). *(Before rc.6 the ordering was yours to enforce — a re-stamped store over an unmigrated corpus validated clean.)*
3. **Look first: `jigc migrate-corpus --dry-run`** prints the triage report the run *would* produce and changes nothing — no migrated bytes, no relocation move, no commit. Run the real thing on a clean tree, so the diff is the whole story.
4. **The run lands its own commit.** `migrate-corpus` writes the migration and commits it, pathspec-limited to the paths it migrated (a half-landed migration — rewritten docs beside a removed relocation source, only some of them staged — is the failure mode that closes). `--no-commit` keeps the writes in the working tree instead, to review them or fold them into a larger commit yourself.
5. **Audit what landed.** The transform is deterministic and the triage tells you exactly what moved. In `--format json` the run reports **five** sets, not three: `migrated` and `already_current` (the paths), plus three finding arrays — `blocked`, `unadopted` and `unfilled` — and alongside them `commit` (the sha the run landed, or `null`), `hook_output` and `dry_run`. Only **`blocked`'s emptiness is the exit rule**: a non-empty `blocked` exits non-zero, and the other two are reported without gating. `blocked` docs are first-class output — they need a human or a prose rewrite, never a workaround. `unadopted` names committed files sitting at a managed home that jigc was **never handed**; they are excluded from the fold before it runs, `migrate-corpus` still exits 0 over them, and they are an *adoption* job (`jigc ingest` / `jigc migrate <path> --as <doctype>`), not an upgrade one — but note that `jigc validate` **does** exit non-zero over them, so an unadopted squatter that leaves this verb green will still redden your CI until you route it. `unfilled` names the leaves a migration *added* that carry a `set:` deriver and no default, so the fold had no deterministic value to write for them: the doc migrated, the exit stays 0, and the advisory exists so a silent no-op is not read as a filled field. The line accounting should close exactly (every changed line either a `schema-version` stamp or a declared transform).
6. **A stamp *above* what your binary knows is the other direction, and it blocks too.** The gates above are about a corpus that is *behind*. A committed doc stamped at a schema-version **higher** than the current one — a newer jigc wrote it, or the stamp was edited out of band — is `schema-conformance.schema-version-ahead` at `jigc validate` and `migrate-corpus.schema-version-ahead` at the fold, both blocking, both exiting non-zero, and neither is fixable by migrating: there is no schema on this machine to migrate *to*. The two ways out are the two the route names — upgrade `jigc` to a build whose schema-version for that doctype is at least the stamped one, or restore the stamp from git history — and then re-run. This is the one corpus state where *"run `migrate-corpus`"* is the wrong answer, which is why it carries its own code rather than the below-version one.

## What an upgrade may change, and what it may not

Everything above assumes you will upgrade `jigc` again. This is the rule that upgrade follows, so a script or a CI job you write against jigc's output has a stated shelf life rather than a guessed one.

- **Inside `1.x`, nothing pinned is removed or reshaped.** A key this project has declared on a `--format json` envelope keeps its name, its type and its meaning, and an envelope keeps its shape. Growth is **additive only**, and every addition is declared as it ships.
- **Version integers only increase, and each increase ships its migration.** A doctype's `schema-version` increase ships the corpus migration that `jigc migrate-corpus` runs (the first half of this document). The two machine surfaces carrying a version of their own increase it with a declared note naming what moved, so no consumer has to diff two releases to find out: `contract-version` on `jigc doc schema`'s projection, and the `schema_version` riding jigc's structured result envelopes. `jigc doc show` and `jigc doc list` carry **no** version of their own — they are pinned by declaration, under the rule above, and the `schema-version` you see on a `doc show` is the *document's*, not the contract's.
- **A removal or a reshape is `2.0`** — a new major, never a minor carrying a note.
- **Until the `1.0.0` release itself the window is still open.** This binary is a release candidate, so a key may still be added, removed or reshaped before the pin; each such change is declared when it ships. From the `1.0.0` pin onward the first three rules above bind, and an absent key is a decision rather than an oversight.

Two things this rule is not about. It does not promise anything about **prose** — the wording of an agent-facing line is free to improve, and only the machine surfaces are pinned. And it says nothing about **your** customizations: those are recorded deltas against a known base version, and `jigc upgrade` is the read that checks them against the pack the new binary ships and reports what it found — it writes nothing itself, under the one jigc-wide exception [QUICKSTART.md](QUICKSTART.md) states (with the opt-in `invocation-log` knob on, every jigc run appends one record to the gitignored `.jigc/logs/invocations.jsonl`).

**The `pre-commit` hook gains an end marker — re-run `jigc setup` after upgrading.** `jigc setup` writes jigc's block of the hook between two marker comments, and `jigc uninstall` removes exactly the lines between them, whatever stands around them. A hook installed by `1.0.0-rc.24` or earlier has no end marker; `jigc setup` by the new binary replaces that block with the delimited one and keeps any line you added beside it. An old hook you edited *inside* jigc's lines is treated as your own file: `jigc setup` keeps it and adds the delimited block beside it, and a `jigc uninstall` that meets it as it was leaves it in place and says so (`--force` removes it).

**`jigc uninstall` removes only the settings entries `jigc setup` recorded — an install from before the record keeps them.** `jigc setup` now writes the entries it adds to `.claude/settings.json` — permits, the deny floor, the `SessionStart` hook — into `.jigc/settings-entries.json` and commits that file with the install; `jigc uninstall` removes exactly the entries listed there, and reads the list only where git tracks the settings file. An install made by `1.0.0-rc.24` or earlier has no such list, and re-running `jigc setup` after upgrading does not make one for it: the entries are already in the file, so the new run adds none and claims none (a deny pattern the new binary adds is listed, and is the one a later uninstall takes back). `jigc uninstall` on such an install leaves the entries in place and prints each one. Remove them by hand, or run `jigc uninstall --force`, which removes every entry identical to one jigc installs — including one you wrote yourself, which is what the plain command no longer does.

**One file an older install leaves behind.** Upgrading the binary is [QUICKSTART.md](QUICKSTART.md)'s install line again. An install of `1.0.0-rc.21` or earlier ran the doc↔code probe as a second executable, `doc-code`, which `jigc setup` wrote beside that `jigc` — `~/.cargo/bin/doc-code` after a `cargo install`, `~/.local/bin/doc-code` beside a hand-placed binary. The probe now runs inside `jigc` itself, so nothing reads that file any more, and nothing removes it either: once you have upgraded, delete it yourself.

## Reconciling and backing out

Nothing in either migration is destructive until you say so. The gates, in the order you meet them (each verified against the shipped binary).

**One thing to know before you read a route.** Every `git` command jigc prints with a path in it leads with `git -C <the repository's absolute path>`, so you can paste it from any directory — a subdirectory, or a fan-out worktree — and it acts on the checkout the finding is actually about. The paths jigc *names* (an `at:` line, a listing, a finding's message) stay relative to the repository root, because those are what you read and what a tool keys on.

**And one thing to know about where you stand.** jigc's doc store has one home: the main checkout. A linked worktree you made yourself (`git worktree add`) **commits code only** — a task there lands its code on that worktree's branch exactly as you would expect, and a `jigc doc` write of a managed doc from there is refused (`finalize.linked-worktree-doc`) with a route to the main checkout, where a task started with `jigc start` writes it. So a change to both code and a managed doc is two tasks and two commits, and code that breaks a committed doc's code anchor lands from the main checkout together with its repair — the refusal prints that route step by step. `jigc start` says so, from such a worktree, before you write anything. (The worktrees `jigc milestone provision` cuts are jigc's own: a sub-task's doc writes from its worktree land with its milestone, the way the milestone flow describes. Any *other* task typed in one is refused the same way and told to wait for that milestone — a commit on the main checkout's branch before it lands would block it.)

1. **Look before landing: `jigc task finalize <id> --dry-run`.** It prints the manifest the finalize *would* commit — each path tagged by how it enters (`promoted` / `modified` / `deleted` / `added` / `carried-over`, the five a committed path can carry; the manifest's left-out list adds two that no committed path ever carries: `untracked`, and on a doc-only task `left-staged` — a path staged for another task, which that task's path-scoped commit leaves staged) — and stops. Nothing is committed, and on a migration task the forecast needs no `--approve`. It forecasts no green it would refuse: over a state the carryover gate below blocks, the dry-run emits those findings and takes the refusing exit instead of a manifest (declare the carry with `--carry-staged` and it forecasts it, labelled `carried-over`).
2. **A plain finalize on a migration task holds for review.** `jigc task finalize <id>` without `--approve` renders the fidelity diff — the foreign source beside the canonical rewrite — and exits with nothing committed. The rewrite is the agent's; the CLI guarantees structure, never content-faithfulness, so this hold is where you read. **`--approve` is the sole destructive gate:** only the approving re-run writes the canonical doc, retires the foreign source, and commits. **What it replaces or retires is the source as `jigc migrate` recorded it** — the bytes the rewrite was authored against, and the ones the diff shows. If you edit the foreign file after the migration was minted, that edit is in neither, so the finalize refuses — with or without `--approve` — on `reconciliation.conflict-block` at that path and leaves the file as you left it: back the migration out (gate 6 below — the refusal prints the exact line) and run the `jigc migrate` line beside it to migrate the file again as it now reads, or undo the edit and finalize again.
3. **A same-path migration lands `M`, never `D`+`A`.** When the foreign file already sits at the canonical destination (`jigc migrate docs/decisions/use-postgresql.md --as adr` — the common brownfield case), `--approve` rewrites it **in place**: one commit, `M <path>` in the log, nothing retired. Since rc.7 this holds for every doctype, not just singletons.
4. **Pre-task staged changes refuse to ride: the carryover gate.** Minting a task snapshots the git index, and at finalize anything staged *before the task existed* refuses — one blocking `finalize.carried-staged` per carried path — instead of silently riding the task's commit. Unstage it (`git -C <repo> restore --staged -- <path>`) if it is not the task's work, or declare the carry deliberate with `--carry-staged`; the manifest then labels it `carried-over`. On a migration finalize `--carry-staged` composes with `--approve` — two independent declarations. You meet the gate before the commit boundary now: `jigc task validate <id>` and `jigc task finalize <id> --dry-run` run the same probe and refuse the same states, and both take `--carry-staged` as the same declaration. **The gate's subject is wider than a minted task**: the rule is that a door committing paths it does not own says so instead of sweeping them in, and `jigc setup`'s install commit is its **second member** — it mints no task, so it asks its own install pathspec against `HEAD` **before it writes a byte** instead of a snapshot, and refuses with one blocking `setup.dirty-install-path` over every dirty path having installed nothing (one exception, in a repository with no commit yet: an untracked file the install *merges into* rides the first commit, while one it would *replace* refuses there too), `jigc setup --force` the single consent — which consents rather than preserves, and names the paths it was spent on. It is not a universal over every jigc commit: `jigc rename`, `jigc migrate-corpus` and the milestone record-only doors commit without asking this question at all.
5. **A rejecting hook refuses the commit, and the message says how to recover.** No jigc commit of *your* work passes `--no-verify` — your `pre-commit`/`commit-msg` hooks are policy there — so a hook that exits non-zero stops the run and **nothing was committed** (HEAD does not move). (The one exception carries none of your work: `jigc setup`'s own install commit passes `--no-verify`, so the warn-only hook `setup` has just written cannot fire on the commit installing it, and that commit refuses outright rather than carrying bytes `setup` did not write — gate 4 above, second member.) What comes back is the hook's own stderr **verbatim**, a sentence naming what survived, and the exact line to re-run: fix the hook's complaint, run that line, and the commit lands. What survives differs per door and the message states *that door's* truth — `jigc task finalize <id>` leaves the task intact — its staged docs still in `.jigc/tasks/<id>/docs/`, anything you had `git add`-ed still in git's index, HEAD unmoved (the message names the two areas separately, because a docs-only task has nothing in git's index for you to check); `jigc migrate-corpus` leaves the migrated bytes written and staged, and its re-run **lands** them instead of reporting "already current"; a rejected `jigc milestone create` unwound both its record write and its workbench, so nothing of that milestone survives. All eleven committing doors carry the frame, each with its own error code in the invocation log, so a failed run is identifiable afterwards.
6. **Back out a task: `jigc task discard <id>`.** For an ordinary task, workbench-only — it removes the task's working area (`.jigc/tasks/<id>/`) and touches nothing else: no commit, the committed store exactly as it was. **One task shape carries a condition, and it is the only one:** a **milestone sub-task** is named by a committed milestone record, so discarding it is a record-only door — it settles that sub-task's item to `discarded` and commits the record on its own, and the ack names the sha on a `record commit:` line. That makes it the tenth committing door. The commit runs *before* the area is removed, so a commit that gets refused leaves both the record and the task exactly as they were and the line it prints to re-run still resolves. Nothing of *yours* is committed on either path — only the record item moves, and every sibling item and the milestone's own status are byte-untouched, because abandoning one sub-task is not abandoning the milestone. **It refuses first over the two populations that removal would destroy** — docs that area stages which no commit has a copy of (`task-discard.staged-prose`, listing them, with the route to read them back via `jigc doc show <address> --task <id>` or land them via `jigc task finalize <id>`), and every path there jigc did not write (`task-discard.foreign-bytes`, naming each; `.jigc/` is gitignored whole, so nothing else has a copy). **`--force` is the single consent** that removes them with the area, and it is the same word `jigc uninstall` and `jigc milestone discard` take for the same reason. Minting a task stages its commit doc, so expect the refusal on any task you have started. A migration task discarded before `--approve` leaves the foreign source committed and untouched — abandoning costs nothing.
7. **Back out a milestone: `jigc milestone discard <id>`.** The committed milestone record settles to `status: discarded` in one record-only commit — a genuinely joined sub-task stays `joined`; it really did land — and then the workbench (sub-task areas, fan-out worktrees) tears down. It refuses before it settles the record or removes anything, over all three populations the teardown would destroy — a sub-task worktree holding uncommitted work, or one whose registration with git holds a commit no ref reaches or (its directory gone) paths still staged in its index (`milestone.dirty-worktree`, which prints the command that keeps the commit and the one that brings the checkout back), a sub-task area staging docs no commit has a copy of (`milestone.staged-prose`), and any path under those areas jigc did not write (`milestone.foreign-bytes`) — each named, each cleared by the same single `--force`. **Landing has a refusal of its own over the same worktrees, and no `--force`.** `jigc milestone finalize` lands what each sub-task has staged in a live worktree and then removes the worktrees, so it refuses first — `milestone.unlanded-work`, exit 3, nothing committed, the milestone still active — while a sub-task worktree holds work it would land without: a commit made inside the worktree that no ref reaches, paths still staged where the worktree's directory or `.git` link is gone, and, for a sub-task you dropped from the milestone while the others went on (its item in the record reads `discarded`), anything left in its worktree that is in no git object — staged paths, unstaged edits, untracked files git does not ignore. The refusal names each path and prints the command that keeps or lands the work (for a dropped sub-task, `git -C <worktree> stash --include-untracked`); run it and re-run the same `finalize`, or abandon the milestone with `jigc milestone discard`. Files git ignores (build output) are named as the worktree goes and never refused over, and so are the unstaged and untracked leftovers of a sub-task that did land.
8. **Hand edits are detected and routed — never silently merged, never forbidden.** Editing a committed managed doc outside the loop is expected (it is plain Markdown in git). `jigc validate` names the drifted path with a route to re-author it through the owning workflow; the report is exit-0 at store scope and gates at `jigc task validate` / `jigc task finalize`. **A hand edit to a doc an open task has already written blocks that task's finalize** — in a fresh clone as much as anywhere, for a file git has never committed as much as a committed one, and whatever other jigc command ran in between: the task's first write records, in the task's own working area, what it copied in, so its finalize (and `jigc milestone finalize`) compares the file with that, blocks on `reconciliation.conflict-block` and leaves your bytes on disk, with two exits — discard the task, or put the file back as it was and finalize again. `jigc unmanage` is not a third: it drops a baseline the task's finalize does not decide on. The rule is one rule: **an edit you made *before* the task first wrote the doc is in the task's staged copy and lands with the task — committed or not, baselined or not — and an edit you make *after* it blocks.** (The task's own writes apply on top of what it copied in, so a slot the task then rewrites holds what the task wrote; commit an edit first if you want it in history regardless.) Undoing an edit on disk after the task has copied it in is an edit after it, and blocks too: the staged copy still carries what you removed. git checking the file out again in another line-ending form is not an edit. So while a task holds a doc, make the change through the task (`jigc doc set-slot … --task <id>`) rather than in the file. One bound: a task that was started and first wrote the doc with a jigc older than this rule holds no such record, and is decided the old way — by the doc's recorded baseline and its committed copy — until it is finalized or discarded. **The milestone record is the one managed doc that is jigc's alone to write**, so a hand edit to `docs/milestone-records/<id>.md` is never merged either: the next milestone command that would rewrite the record (`add-task`, `add-from-spec`, `discard`, a sub-task's `task discard`, `finalize`) blocks on the same `reconciliation.conflict-block` and leaves the file as you left it — in a fresh clone too, where the committed record at `HEAD` is what it is compared against — and its route is the one restore that makes the command land, `git -C <repo> checkout HEAD -- <record>`; a note you want to keep belongs somewhere other than the record. One refusal there is not about an edit of yours: in a checkout that converts line endings, a branch switch and back or a stash makes git write the record out again in its converted form, and the next milestone command — still holding the hash of what it last wrote — refuses the record as *edited out of band* while `git status` shows nothing. The restore has nothing to restore there; the route says so and names the exit, `jigc unmanage <record>`, after which the same command lands. **A hand edit that *removes* a managed doc is the harder case, and it takes the sweep's exit with it.** When a doctype homes its one document at a single declared path — a **placed** doctype such as the repo-root `CHANGELOG.md`, or a singleton at its `location:` — and the last document the repository committed at that path was a **managed** one (it carries jigc's `schema-version:` stamp) while nothing is there now, `jigc validate` raises blocking `schema-conformance.home-vacated` and exits non-zero: a home jigc's own document is missing from is not something re-authoring elsewhere repairs. Where the removal is **committed**, the store has genuinely *lost* the document — every clone is missing it; where it is not, nothing is lost and the finding says so, because the question *is the document there* is asked of the worktree. Your project's **own** pre-jigc history at such a path is never a subject — a `CHANGELOG.md` you wrote and retired years before you met jigc is your file, not a document jigc lost — so adopting a brownfield repository does not turn it red. A doctype whose instances carry per-author slugs is never a subject either, so a collection that legitimately retired its last ADR stays green. **The route is a function of how the document went, and jigc works that out before it tells you anything.** If the removal is *committed* — every clone of the repository is missing the document — the exit is to restore it at that path and commit it, then `jigc ingest` to re-register it, and the route **names the commit that removed it** (it runs the query first, and simply leaves the clause out when there is no such commit to name rather than handing you a locator that prints nothing). If the removal is not committed, nothing is lost and the route says so: an uncommitted deletion is `git -C <repo> checkout -- <path>`, a **staged** one is `git -C <repo> restore --source=HEAD --staged --worktree -- <path>`, and neither needs a re-registration. You may also see `reconciliation.rename` on the same path, which is the file-state gate grading the deletion itself; it offers `jigc unmanage` as a way to confirm the deletion, and that is an exit for **its** baseline and not for this declared home — which is why this route names `jigc unmanage` as **not** an exit: it drops a file-state baseline and leaves the home declared, so on its own it clears nothing. Retiring the doctype for good means taking the pack that declares the home out of the composition.

## What migration does *not* give you

- **Truthful prose.** jigc's gates keep docs naming *real code* (anchors, refs, structure); they do not detect that a paragraph's *claim* went stale. A migrated corpus is only as honest as the verification you did at step 2 above — and it starts rotting again the first time a fix lands without its doc pass.
- **Linear-time authoring of a very large document.** Every `migrate-*` workflow hands `jigc doc author` the whole document in **one** payload, and the apply chain re-reads the growing buffer once per lowered leaf — so the cost is **quadratic in the item count**, not linear, and that residual is the shipped bound. It used to be worse: the read itself was quadratic too, making the batch cubic (an 800-item document took 77 s to author, a 1500-item one never finished). That factor is gone — the same 800-item document now takes under 7 s, 1500 items under 30 s — but quadratic is still quadratic: a single source document with several thousand items is minutes, not seconds. The batch is atomic, so a long run is a long run and never a partial one; if a foreign document is enormous, splitting it at a real boundary beats waiting.

- **A finished doc set.** Migration carries what exists. The gaps the old system had (undocumented decisions, missing specs) are still gaps — now visible ones.
